Detailed Description

Portable, tamper-evident firmware-update audit log.

One surface across SoMs. The software tier (every target) gives a hash-chained, monotonic-counter-anchored log that detects mutation, truncation, rollback, and reorder. On SoMs with a secure backend the same API is hardware-enforced through a secure owner (secure-world Protected Storage + a replay-protected high-watermark counter). Query alp_update_log_assurance to learn which.

Persistence vs. trust boundary (software tier)
With CONFIG_ALP_SDK_UPDATE_LOG_PERSIST and an alp_ulog_partition fixed partition in the devicetree, the software tier stores the log and its monotonic counter in Zephyr NVS, so entries survive reboot and firmware update. Without the partition it falls back to RAM (entries vanish on reboot). Persistence does NOT change the assurance level: the software tier is tamper-EVIDENT, not tamper-proof – alp_update_log_verify detects out-of-band mutation, truncation, rollback, and reorder, but code that can write the backing partition can rebuild the store and counter consistently and forge history. App-immutability is the ALP_UPDATE_LOG_HW_ENFORCED tier's job.
Hardware-enforced tier status (ALP_UPDATE_LOG_HW_ENFORCED)
The application-side backend is a client; the log writer and backing store live behind a hardware boundary the application core cannot rewrite. The TF-M route (CONFIG_ALP_SDK_UPDATE_LOG_TFM) uses a secure owner with PSA Protected Storage. The Alif E4/E8 AEN route uses a trusted M55 owner plus an SE/device-firewalled MRAM log partition; physical rollback protection still depends on a board-provisioned non-decrementable counter or equivalent device policy. If the trusted owner or the hardware isolation proof is absent, alp_update_log_open transparently falls through to the software tier, or fails closed when CONFIG_ALP_SDK_UPDATE_LOG_REQUIRE_HW_ENFORCED is set. Query alp_update_log_assurance rather than assume the tier – it is the only portable signal of which assurance actually backs the log on a given SoM.
Full log (software tier)
The log is append-only and never wraps – wrapping would erase audit history. When the backing partition is full, alp_update_log_append fails cleanly and the existing chain stays intact and verifiable.
Authenticated boot metadata
Prefer alp_update_log_append_boot for update-result entries when the platform provides authenticated boot metadata. That path asks the SDK's boot-metadata provider for the booted image version, image SHA-256, and verification status, then appends the entry without accepting app-supplied identity fields. Platforms without a provider return ALP_ERR_NOSUPPORT so callers can avoid writing forged-but-well-formed audit entries by accident.
ABI status: [ABI-EXPERIMENTAL]
v0.7 new. Surface may change until the hardware backend is silicon-proven. See docs/abi-markers.md.
