Detailed Description

Alp SDK portable JPEG-encoder abstraction.

Encodes a source frame into a JPEG byte stream in one call. The caller declares the frame's buffer LAYOUT via alp_jpeg_encode_req_t::format (alp_pixfmt_t) – fully-planar Y/U/V or semi-planar NV12, see the struct doc. Maps to the Alif Ensemble E8's Hantro JPEG hardware encoder on AEN-family SoMs; every other SoM is served by a portable software encoder fallback so customer code compiles + runs identically across silicon (each backend accepts a different subset of layouts – query alp_jpeg_caps_t::pixfmt_mask rather than assuming one).

Task 1 of the encoder rollout shipped only the portable surface, the class dispatcher, and a NOT_IMPLEMENTED stub backend. Task 2 adds a portable software baseline-JPEG encoder (4:2:0 + 4:0:0 only, src/backends/jpeg/sw_baseline.c) that now wins backend selection on every SoM without JPEG hardware, so alp_jpeg_encode actually encodes out of the box. Tasks 3-4 add the Alif Ensemble E8 Hantro VC9000E hardware backend (src/backends/jpeg/alif_hantro.c), which outranks the software backend on AEN silicon, plus the explicit format field so the two backends' differing buffer-layout needs (planar vs. NV12) are a declared part of the request instead of an implicit per-backend reinterpretation of the same pointers.

ABI status: [ABI-EXPERIMENTAL]
v0.13 new – portable surface + stub (Task 1), then the software baseline encoder (Task 2) in the same v0.13 cycle. See docs/abi-markers.md for the convention.

Encode one source frame into a JPEG byte stream.

Parameters
[in]hHandle from alp_jpeg_open.
[in]reqFrame + quality descriptor. Must be non-NULL, with non-zero width / height and a format the opened backend's alp_jpeg_caps_t::pixfmt_mask advertises.
[out]out_bufDestination buffer for the encoded stream.
[in]out_capCapacity of out_buf, in bytes.
[out]out_lenReceives the encoded length on success; on ALP_ERR_NOMEM the backend sets it to the required size when known.
Note
A hardware-accelerated backend (alp_jpeg_caps_t::hw_accelerated true) DMAs directly to/from the caller-supplied buffers – it does NOT bounce them through an intermediate copy or translate the pointer. When hw_accelerated is true, req's input plane(s) (y_plane / u_plane / v_plane) AND out_buf must reside in memory the hardware's DMA master can reach: globally-addressable system RAM, NOT core-local tightly-coupled memory (TCM), and should be cache-coherent. A backend that detects a buffer it cannot DMA to returns ALP_ERR_NOSUPPORT rather than encode incorrectly (or hang); the caller can relocate the buffer or fall back to a software backend (hw_accelerated false), which has no such placement restriction.
Returns
ALP_OK on success, or one of:
  • ALP_ERR_INVAL – NULL h / req / out_buf / out_len, or a zero width / height.
  • ALP_ERR_NOSUPPORT – format or subsample the backend can't do, or (hardware backends only) a buffer that is not DMA-reachable – see the
Note
above.
  • ALP_ERR_NOMEM – out_cap too small for the result.
  • ALP_ERR_IO – hardware-engine fault.
  • ALP_ERR_NOT_IMPLEMENTED – backend has no encode path.
  • ALP_ERR_NOT_READY – handle not open / mid-close.
