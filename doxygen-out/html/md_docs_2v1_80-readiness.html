1z. E1M instance-ID rename + pin-as-GPIO fallback (CRITICAL, pre-ABI-freeze)

‍Correction (verified against the tree and CHANGELOG.md): this section, as originally written on 2026-05-14, describes the first of two renames and stops there — reading it alone gives the inverse of today's namespace. What actually happened, in order:

  1. 2026-05-14 (this section, item 1 below): ALP_E1M_* → bare E1M_* (prefix dropped).
  2. v0.9.0 (2026-07-06, CHANGELOG.md under [v0.9.0], "**BREAKING: pin/instance macros renamed `E1M_*` -> `ALP_E1M_*`**"): the bare names collided with vendor BSP defines, so the prefix was restored — reversing step 1.

Current, final state: the macros are ALP_E1M_* / ALP_E1M_X_* (with the prefix). Confirmed against scripts/gen_board_header.py ("the generator prefixes `ALP_` when emitting the C tokens") and every symbol in include/alp/e1m_pinout.h. The item-1 narrative below is kept verbatim for historical accuracy but describes an intermediate state, not the shipped one.

Captured 2026-05-14 from maintainer: the instance identifiers formerly in <alp/e1m_pinout.h> (then ALP_E1M_*) carried redundant prefix + over-granular channel selection. Three changes required before v1.0 ABI freezes the surface:

  1. ✅ Drop the ALP_ prefix (DONE, this session; reversed at v0.9.0 – see the correction note above). The old ALP_-prefixed instance names became the bare E1M_* forms: ALP_E1M_I2C0, ALP_E1M_PWM3, etc. Rationale: E1M is the open-standard form factor, not an Alp-specific concept – the prefix was redundant noise. The ALP_* namespace stays reserved for SDK-internal abstractions (ALP_OK, alp_status_t, etc.).
  2. ✅ Collapse channel selection (DONE, this session). The old per-channel DAC_CH<N> alias had a pin-granular peer of identical value – the _CH<N> aliases got removed so the pin-granular ALP_E1M_DAC<N> (e.g. ALP_E1M_DAC0) is the single name. Rationale: callers pick the pin and its matching peripheral mode; the pin-to-channel routing is part of the E1M-spec mapping, not a per-call choice. Confirmed no _CH<N> suffixes survived on any other peripheral (ALP_E1M_PWM* / ALP_E1M_ADC* / ALP_E1M_ENC* were already pin-granular).
  3. ✅ Pin-as-GPIO secondary (shipped). Any pin that supports ADC / PWM / QENC is also openable as a plain GPIO via its GPIO-secondary index ALP_E1M_GPIO_<class><N>. The two ID spaces stay deliberately separate: the peripheral-instance space (ALP_E1M_ADC0..7 = 0..7) selects the analog/timer function, while the GPIO-index space (ALP_E1M_GPIO_IO0..25 = 0..25, ALP_E1M_GPIO_PWM0..7 = 26..33, ALP_E1M_GPIO_ADC0..7 = 42..49, ...) drives the same pad digitally – e.g. alp_gpio_open(ALP_E1M_GPIO_ADC0) opens ADC0's pad as GPIO. No silent unification; the caller names the role explicitly (decision resolved – was the v0.x "fallback" TBD).

1a. GD32 firmware HAL bodies (wave-2 opcodes)

All five wave-2 opcode groups below now have real bridge_hw_* bodies (not the default-case STATUS_NOSUPPORT branch). What remains is HIL verification on real GD32G553 silicon, plus two follow-up gaps: #494 (ADC oversample/resolution) and #495 (PWM alignment) have now landed — leaving only 14/16-bit effective resolution and the physically-unroutable PWM dead-time/break on V2N as STATUS_NOSUPPORT — plus one deferred runtime path (#496 ADC-stream DSP application).

‍Status: bodies landed; verification on real GD32G553 silicon still HiL-gated. Flip from 🟡 to ✅ once the HiL rig exercises them.

  • 🟡 **bridge_hw_pwm_capture_begin/read/end** (opcodes 0x23 / 0x24 / 0x25) — GD32 timer input-capture mode on the eight PWM channels. Bodies landed §C.15a (polled drain + state machine + ns conversion); READ reports STATUS_NOSUPPORT ("ring empty") on real hardware today because every V2N PWM pad binds the timer's CHxN (complementary) output while the capture stage samples the main CHx pad — a hardware bring-up commit reworking the pad routing is still needed before edges land.
  • 🟡 **bridge_hw_pwm_single_pulse** (opcode 0x26) — implemented via the timer's one-pulse mode (OPM); HIL round-trip against <alp/pwm.h> still ahead.
  • 🟡 **bridge_hw_timer_sync** (opcode 0x27) — master/slave timer sync via TIMx_SMCR. Body landed §C.15b (master/slave id 0..2 → TIMER0/7/19; mode 0..5 → SMC encoding via switch; master TRGO0=UPDATE; slave listens to ITI0); HIL round-trip still ahead.
  • 🟡 **bridge_hw_power_mode_set** (opcode 0x28) — Sleep / Deep-Sleep / Standby via PMU registers. Modes 2 + 3 landed §C.15c (pmu_to_deepsleepmode / pmu_to_standbymode); wake-source bitmap fully applied for RTC / GPIO / TIMER (RTC wakeup timer at 0.5 ms LSB via IRC32K/DIV16; GPIO enables WAKEUP_PIN0..4); UART_RX / USB / ETH_LINK remain STATUS_NOSUPPORT by design (no hardware path on the GD32G5 baseline). HIL verification of the sleep transitions still ahead.
  • 🟡 **bridge_hw_adc_dsp_chain_open/stage_push/chain_bind** (opcodes 0x37/0x38/0x39) — chain ADC stream output through the on-firmware DSP slot. All three landed §C.15d (4-chain pool + per-stage chunk reassembly into a 260-byte buffer + ordering / kind / completion guards; chain_bind validates and stores the binding). The runtime dispatch that would route a bound chain's stages onto the stream's samples has NOT landed — CMD_ADC_STREAM_READ still emits raw mV regardless of any bind (tracked #496).
  • 🟡 ADC_CONFIGURE oversample/resolution (opcode 0x32, #494 landed) — bridge_hw_adc_configure() now applies oversample_ratio (floored to a power of two 1..256, OVSS shift normalises back to full-scale) and resolution_bits (6/8/10/12 → hardware DRES, mV divides by that width's full-scale) alongside sample_cycles, inside the ADCON == 0 window. 14/16-bit effective-resolution modes still return STATUS_NOSUPPORT. HIL verification on real GD32G553 silicon ahead.
  • 🟡 PWM_CONFIGURE align/dead-time/break (opcode 0x22, #495 alignment landed) — bridge_hw_pwm_configure() applies align_mode (edge / center-up / -down / -both) timer-wide; PWM_SET/GET convert period/duty for the center-aligned 2*ARR period. dead_time_ns / break_cfg remain STATUS_NOSUPPORT because V2N routes only the complementary CHxN output (no pair for a dead-time gap) and no BRK pad — a hardware-routing limit, same root cause as the PWM_CAPTURE note above. HIL verification of the alignment path ahead.
