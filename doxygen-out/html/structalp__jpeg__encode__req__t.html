Detailed Description

One encode request: a source frame plus quality target.

format (alp_pixfmt_t) selects the source buffer's memory LAYOUT – which of y_plane / u_plane / v_plane are live, and how they relate to each other:

  • ALP_PIXFMT_YUV420_PLANAR (I420) – fully planar: y_plane / u_plane / v_plane are three independent buffers, each with its own stride. This is what the portable software backend (src/backends/jpeg/sw_baseline.c) consumes.
  • ALP_PIXFMT_NV12 – semi-planar: y_plane is the base of a single contiguous buffer (Y plane, then at y_stride * height an interleaved U/V plane); u_plane / v_plane are NOT consulted and must be NULL. This is what the Alif Hantro VC9000E hardware backend (src/backends/jpeg/alif_hantro.c) latches as its single raw-frame pointer.

subsample stays a SEPARATE field from format on purpose: it is the chroma SAMPLING RATIO (4:0:0 mono / 4:2:0 / 4:2:2) a backend encodes at, orthogonal to which buffer LAYOUT carries the samples in. Both currently-registered pixel formats happen to be 4:2:0-only, but collapsing the two fields would force inventing alp_pixfmt_t values for "mono, planar layout" and "4:2:2, planar layout" that <alp/peripheral.h>'s display/camera callers have no use for – format only needs to grow when a new BUFFER LAYOUT shows up, subsample only needs to grow when a new SAMPLING RATIO shows up. u_plane / v_plane are unused (and must be NULL) when subsample is ALP_JPEG_SUBSAMPLE_400, independent of format.
