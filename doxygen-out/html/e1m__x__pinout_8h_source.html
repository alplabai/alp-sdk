166/* Counter is padless -- no e1m-spec connector pad backs these ids
167 * (metadata/e1m/pinout-x-v1.json carries no counter entry, unlike
168 * the pinned classes above), so this is an E1M-X namespace
169 * convention rather than a claim tied to the file's `N <
170 * ALP_E1M_X_<CLASS>_COUNT` portability-bound block below -- counter
171 * has no such bound macro. These four ids are not a per-SoM
172 * promise either: a different SoM in this family may serve all
173 * four. A published id this SoM does not serve never reports
174 * ALP_ERR_INVAL -- a published id is not a bad argument -- but the
175 * status it DOES report is per-backend, so branch on "open failed",
176 * not on one code:
177 * - src/backends/counter/gd32_bridge.c: ALP_ERR_NOSUPPORT for an id
178 * at or beyond GD32G553_BRIDGE_COUNTER_CHANNELS. This is the
179 * V2N/V2M path, which serves ALP_E1M_X_COUNTER0 only.
180 * - src/backends/counter/zephyr_drv.c: its `alp-counter<N>` alias
181 * table is a fixed four entries, so every published identity is
182 * inside it and a board with no alias for one reports
183 * ALP_ERR_NOT_READY (alias unresolved), not NOSUPPORT.
184 * - src/backends/counter/yocto_drv.c: no id range of its own -- it
185 * probes /sys/bus/counter and maps the POSIX errno.
186 * Only gd32_bridge.c populates alp_counter_capabilities()->channel_count
187 * today; the others leave it zero, so read a zero as "not reported",
188 * not as "serves none".
189 * V2N/V2M serve COUNTER0 only, via the GD32 bridge
190 * (src/backends/counter/gd32_bridge.c); see docs/portability.md
191 * §4.5 (alp-sdk#1242). */
