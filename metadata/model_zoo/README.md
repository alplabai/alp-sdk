# Model-zoo entries (`metadata/model_zoo/`)

One file per model, `metadata/model_zoo/<id>.yaml`, validated against
`metadata/schemas/model-zoo-v1.schema.json` by `scripts/validate_metadata.py`.

This is the **data half** of the model-zoo pipeline per ADR-0028
(`docs/adr/0028-tan-owns-the-model-engine.md`, **Status: Proposed** -- not
yet a decided/accepted architecture, so treat its split as a working
plan, not settled history): alp-sdk owns this directory and its schema as
hardware truth -- the entries, the licence allowlist, the SKU/SoM
cross-checks. The engine that reads them (`tan model zoo` / `tan model
add`) is planned to live entirely in tan-cli (tan-cli#1286); there is no
second implementation here, no `scripts/alp_model/zoo.py`.

## Entry shape, in brief

```yaml
schema_version: 1
kind: model                       # or: fixture (see below)
id: person-detection-int8
task: person-detection            # closed enum -- see the schema
description: ...
license: Apache-2.0               # closed, permissive allowlist -- see below
source:
  url: https://example.com/model.tflite
  sha256: <64 lowercase hex chars>
# -- OR --
source:
  bundled: starters/<file>        # must exist, exactly starters/<file>, no subdir
validated_soms: [E1M-AEN801]      # real SoMs this exact model was bench-run on
compile: {...}                    # optional; same shape as board.yaml's models[].compile
example_app: examples/ai/ai-anomaly-detection-vibration  # optional; must exist + carry board.yaml
```

`example_app` must be a **tan-buildable** example -- `board.yaml` is a
deliberate requirement, not an oversight. The `examples/aen/aen-npu-inference*`
demos look like the obvious thing to link (they ARE NPU-inference demos)
but do not carry `board.yaml` and therefore cannot be linked here today;
loosening this requirement to accept a non-buildable demo is a future,
additive decision, not the default.

`source` is EXCLUSIVELY one of two shapes, enforced at the schema level:

- an upstream link, `{url, sha256}` -- `url` is `https://` only (no
  `file://`, no embedded whitespace, no userinfo/credentials), `sha256` is
  REQUIRED alongside it (so a consumer can refuse a fetch that doesn't hash
  to what the manifest claims);
- a bundled starter, `{bundled}` -- a path of the exact shape
  `starters/<file>`, which must resolve to a real, case-exact-matching file
  inside `metadata/model_zoo/starters/`, no subdirectory, no `../` escape.

**No weight redistribution either way.** A `{url, sha256}` entry LINKS the
upstream model; the bytes are never committed here. A `{bundled}` starter
may only be a genuinely clean, tiny model with no real upstream weights --
`example-tiny.tflite` is a synthetic, non-trained fixture generated by
`tests/fixtures/models/gen_tiny_model.py`, not a real checkpoint.

## `kind: model` vs `kind: fixture`

`kind: model` is a real, published model-zoo entry. `kind: fixture` is a
wiring/smoke entry that exists only to exercise the zoo machinery end to
end -- it is NEVER a hardware claim, and BOTH the schema (an `allOf` of
two `kind`-gated `if`/`then` pairs -- one for `kind: fixture`, one for
`kind: model`, deliberately not a single `if`/`then`/`else`, so a missing
or invalid `kind` doesn't also manufacture an unrelated `task` complaint)
AND `scripts/validate_metadata.py`'s `_check_model_zoo_semantics` (for a
friendlier, specific error message) enforce that a fixture:

- declares `task: smoke` (reserved for fixtures; a `model` entry must never
  claim `task: smoke`, and a `fixture` entry must never claim anything
  else);
- carries an empty `validated_soms: []`;
- uses a `bundled` source, never a `url` link to an unreviewed upstream
  model.

`example-tiny` is the one fixture in this directory today.

## `validated_soms` semantics

`validated_soms` is the list of SKUs this EXACT model has actually been
bench-run on. **Empty means no SoM has been bench-validated yet** --
`tan model zoo --sku <SKU>` matches NO entry whose `validated_soms` is
empty. Never treat an empty list as "unfiltered" or "works everywhere"; it
is the opposite claim, "nothing confirmed." `scripts/validate_metadata.py`
checks that every listed SKU names a real, shipped
`metadata/e1m_modules/<sku>.yaml` preset -- it does NOT and cannot check
that the bench run actually happened. That remains the entry author's
responsibility, the same division of labour `metadata/model_perf/`'s own
bench-capture points use.

## Licence allowlist

The `license:` field is validated against a permissive, **closed**
allowlist -- no `LicenseRef-*` escape:

```
Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, CC0-1.0
```

It describes the SPDX id of the linked upstream model's own licence (its
WEIGHTS + graph), or of the bundled starter -- not the training dataset's
licence, which is a separate question this field does not answer.

**Extending this allowlist is a deliberate human decision (legal review),
not a metadata edit.** Add the SPDX id in BOTH
`metadata/schemas/model-zoo-v1.schema.json` (`license.enum`) and this list,
in the same change (`tests/scripts/test_model_zoo_metadata.py` fails if
the two differ), with the legal rationale in the commit body -- mirroring
`metadata/libraries/README.md`'s own licence-allowlist process.

Copyleft (including AGPLv3 -- SPDX `AGPL-3.0-only` / `AGPL-3.0-or-later`),
non-commercial, and vendor-customer-only terms are rejected until
explicitly admitted. This is not hypothetical:
many popular real-time detector checkpoints are AGPLv3 and are therefore
**not** admitted here by policy -- Ultralytics YOLO checkpoints (e.g.
`yolo11n`) ship under AGPLv3 (`docs/vendor-partnerships.md:242` records
DEEPX's own `ultralytics-deepx` fork as AGPLv3) and cannot be added to
this zoo under their current licence. DEEPX's `dx-modelzoo` is separately
MIT (`docs/vendor-partnerships.md:241`) but that MIT licence covers
DEEPX's OWN reference models -- it does not relicense an
Ultralytics-derived checkpoint vendored or fine-tuned elsewhere; an
AGPLv3 YOLO weight stays AGPLv3 regardless of which repository ships
it.

Where a genuinely permissively-licensed equivalent exists it is the one
to curate instead -- upstream `Megvii-BaseDetection/YOLOX` itself is
Apache-2.0. That said, Apache-2.0 upstream is not automatically true of
every build derived from it: the actual benched artifact in this repo,
RUHMI's `yolox-S_VOC.onnx` (`src/yocto/inference_drpai.cpp:19`,
`metadata/model_perf/README.md:13-14`), has NO RECORDED licence of its
own and is **not admitted** to this zoo until that is verified --
licence-compatible upstream provenance is not itself an admission, and
neither is a real entry's remaining data-authoring work: a verified
`source`, bench-validated `validated_soms`, and a reviewed
`description`.

## Adding an entry

1. Pick a real, permissively-licensed upstream source (or author a
   genuinely clean, tiny fixture for `kind: fixture`).
2. Write `metadata/model_zoo/<id>.yaml` against the schema above. Keep
   `validated_soms` empty until you have bench-run it on real silicon.
3. If bundling a starter, add it under `metadata/model_zoo/starters/<file>`
   (flat, no subdirectory; `scripts/validate_metadata.py` caps starter
   size and rejects an orphan/unreferenced file).
4. Run `python3 scripts/validate_metadata.py` and
   `python -m pytest tests/scripts/test_model_zoo_metadata.py`.
