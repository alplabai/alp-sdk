### Fixed — `check_atoc_reservation.py`'s whole-device-alias exemption ignored `write_authority`, so a runtime-writable row spanning the ATOC band passed (#2086)

4b (`_check_aperture_tiling`, `scripts/check_atoc_reservation.py:406`) and 4c
(`_check_class_disagreement`, `scripts/check_atoc_reservation.py:501`) both exempted a
`memory_map:` row from aperture tiling and flash-class agreement purely on `lo == full_lo and hi
== full_hi` — the row's extent equalling the SoC's declared MRAM aperture. Neither check read the
row's `write_authority`, so a preset could declare a row spanning the full App MRAM window,
including the Secure Enclave-owned `atoc` band at the top, with `write_authority:
customer_runtime` (runtime-writable by the application, per `metadata/schemas/som-preset-v1.schema.json:723`)
alongside a correct six-band tiling, and every ATOC check passed.

Both sites now check the alias's own `write_authority` before exempting it
(`scripts/check_atoc_reservation.py:454` and `scripts/check_atoc_reservation.py:547`,
`_RUNTIME_WRITABLE_AUTHORITY = "customer_runtime"` at `scripts/check_atoc_reservation.py:144`) —
`customer_runtime` is the ONLY `write_authority` value the schema defines as writable by the
application at runtime; every other value (`customer_image`/`vendor_image`: flash-tool only,
`secure_enclave`: SE at provisioning, `none`: no writer, `composite`: a whole-device alias
deferring to its contained rows — `mram_main`'s own tag today) stays exempt, unchanged. A row
that IS runtime-writable now fails naming the row and its authority
(`_alias_write_authority_failure`, `scripts/check_atoc_reservation.py:147`) instead of silently
passing. ABSENT `write_authority` stays exempt too: the schema says absent means unresolved,
never `customer_runtime` (ADR-0034 clause 4), so a consumer must treat it as ineligible for
runtime write — not defaulting permissively means never treating absent AS `customer_runtime`,
not refusing it as though it were.

No committed preset is affected: the only real whole-device alias, `mram_main`, already carries
`write_authority: composite`. Checked `scripts/alp_orchestrate/partition.py` for the same hazard
on the `storage[].flash_device:` path per the issue's open question — it never reads
`write_authority` at all, and its allocator only avoids OTHER named `memory_map:` siblings with a
resolved base, not the alias's own authority; today that's masked only because this same gate's
top-of-aperture rule (`_check_preset`) already forces a distinct `atoc`-named sibling to exist
wherever an alias does. Left as a follow-up issue rather than fixed here — out of scope and not a
small change.
