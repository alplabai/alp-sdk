### Fixed — `check_atoc_reservation.py`'s whole-device-alias exemption ignored `write_authority`, so a runtime-writable row spanning the ATOC band passed (#2086)

4b (`_check_aperture_tiling`) and 4c (`_check_class_disagreement`) exempted a `memory_map:` row
from aperture tiling and flash-class agreement purely on its extent equalling the SoC's declared
MRAM aperture. Neither read the row's `write_authority`, so a preset could declare a row spanning
the full App MRAM window, including the Secure Enclave-owned `atoc` band at the top, with
`write_authority: customer_runtime` — runtime-writable by the application, per
`metadata/schemas/som-preset-v1.schema.json:723` ("runtime-writable by the application") —
alongside a correct six-band tiling, and every ATOC check passed. A correctly-NAMED `atoc` row
carrying the same authority passed too: naming the top row right was never checked against what
could actually write it.

The fix lives in `_check_preset()`'s existing top-of-window rule
(`scripts/check_atoc_reservation.py:644` ("def _check_preset")) — every row ending exactly at the
declared window top is the ATOC band regardless of its own name or extent, since SETOOLS
top-anchors the ATOC there and grows it DOWNWARD, so checking that one set of rows already covers
both a mis-named partition (#2069's existing rule) and a whole-device alias (its extent always
reaches the same top). 4b/4c do not read `write_authority` — the single top-of-window guard covers
both shapes, so a per-site copy in each would only duplicate the failure.

`_check_top_write_authority()` (`scripts/check_atoc_reservation.py:607` ("_check_top_write_authority"))
runs from both the aperture-resolving branch and the no-aperture fallback branch
(`scripts/check_atoc_reservation.py:729` ("_check_top_write_authority") and
`scripts/check_atoc_reservation.py:759` ("_check_top_write_authority")). The fallback branch needs
the same guard for a different reason than the aperture branch: with no SoC aperture declared,
SETOOLS's real ATOC anchor point can't be confirmed at all — the file-wide max is only a
fail-closed stand-in (an out-of-window OSPI0 HyperRAM row can sit far above the real window, the
same hazard the aperture-scoped rule guards against), so the fallback's own failure message says
so instead of claiming a confirmed SETOOLS anchor address. `customer_runtime`
(`_RUNTIME_WRITABLE_AUTHORITY`, `scripts/check_atoc_reservation.py:154` ("customer_runtime")) is
the ONLY `write_authority` value the schema defines as writable by the application at runtime;
every other declared value (`customer_image`/`vendor_image`: flash-tool only, `secure_enclave`: SE
at provisioning, `none`: no writer, `composite`: a whole-device alias deferring to its contained
rows — `mram_main`'s own tag today) stays exempt, unchanged. A row that IS runtime-writable now
fails naming the row and its authority (`_runtime_writable_top_failure()`,
`scripts/check_atoc_reservation.py:157` ("def _runtime_writable_top_failure")); the remedy it
suggests depends on the same exact-extent test 4b/4c already use to spot a whole-device alias —
`composite` only for an alias (`lo == floor and hi == top`), `secure_enclave` for the atoc band
itself, since suggesting `composite` for a mis-authored `atoc` partition would let an author retag
it that value and pass (`composite` is itself exempt). ABSENT `write_authority` stays exempt too —
the schema says absent means unresolved, never `customer_runtime` (ADR-0034 clause 4) — but is now
SKIP-noted by name rather than silent, since the schema also says a consumer must treat it as
ineligible for runtime write and say so.

No committed preset is affected: the only real whole-device alias, `mram_main`, already carries
`write_authority: composite`.

Checked `scripts/alp_orchestrate/partition.py` for the same hazard on the `storage[].flash_device:`
path per the issue's open question — it never reads `write_authority`, and its allocator only
avoids OTHER named `memory_map:` siblings with a resolved base, not the alias's own authority.
Two OTHER, unrelated mechanisms mask it today, not this gate: the #1556 Devicetree-label gate
(`_has_real_dt_label()`, `scripts/alp_orchestrate/partition.py:339` ("def _has_real_dt_label"),
enforced at `scripts/alp_orchestrate/partition.py:729` ("verified_dt_label")) refuses `status: ok`
for any `memory_map:`-sourced `flash_device:` — alias or not — that lacks an explicit `dt_label:`
override, which nothing in the tree declares yet (`on_module.ospi_memories:` devices skip this gate
entirely, `scripts/alp_orchestrate/partition.py:551` ("is_ospi_device or _has_real_dt_label")); and
`check_atoc_reservation.py` itself only ever walks the in-tree `metadata/e1m_modules/` preset
directory (run with no metadata-root argument at
`.github/workflows/pr-metadata-validate.yml:560` ("check_atoc_reservation.py")), so a customer
preset loaded through a `--metadata-root` override (`effective_metadata_root()`,
`scripts/alp_orchestrate/models.py:403` ("effective_metadata_root")) never runs through this CI
gate at all. #2088 tracks `partition.py`'s own gap as a follow-up.
