### Fixed — CC3501E GPIO proxy: per-pin, fail-closed revision guard (#2144)

`src/backends/gpio/cc3501e_proxy.c:259` ("static bool is_rev_dependent")
replaces the old all-or-nothing `g_hw_rev_mismatch` guard (#1859) with a
PER-PIN check at `src/backends/gpio/cc3501e_proxy.c:310` ("is_rev_dependent(pin_id) && !g_hw_rev_confirmed_match"), refusing only the E1M pins that `metadata/e1m_modules/aen/hw-revisions.yaml:44-46` ("dispatch: direct") move between the Alif SoC and the CC3501E across AEN hw_revs -- IO8 (:44), IO10 (:45) and IO21 (:46) -- instead of dropping every proxied pin, including revision-independent ones like IO20 (the SD mux enable), on any hw_rev disagreement.

It also fails CLOSED: `src/backends/gpio/cc3501e_proxy.c:126` ("static bool g_hw_rev_confirmed_match") defaults false, and `src/backends/gpio/cc3501e_proxy.c:143` ("cc3501e_proxy_hw_rev_confirmed_match") only reports a match past a CRC-valid `alp_hw_info_read()` AND a `CONFIG_ALP_SDK_SOM_HW_REV` compare -- a missing, unprovisioned or corrupt identity-EEPROM manifest now refuses a revision-dependent pin instead of the old guard's fail-open default. `alp_gpio_cc3501e_attach()` logs a one-shot `LOG_WRN_ONCE` naming the read status, the live manifest `som_hw_rev` (when read), and the build's `CONFIG_ALP_SDK_SOM_HW_REV` when it cannot confirm a match; `px_open()` separately logs a one-shot-per-pin `LOG_WRN` naming the #2144 guard specifically, since it returns the SAME `ALP_ERR_NOSUPPORT` as the unrelated #1854 unrouted-pad guard.

The revision-dependent pin set is derived from metadata, not hand-typed: `scripts/gen_cc3501e_gpio_routes.py:125` ("def _revision_dependent_e1m_pads") reads `metadata/e1m_modules/aen/hw-revisions.yaml`'s `pad_route_overrides:` and, unlike an earlier draft of this change, writes it ONCE into an SDK-owned generated file, `src/backends/gpio/cc3501e_rev_dependent_pins.c`, compiled unconditionally alongside `src/backends/gpio/cc3501e_proxy.c` (`zephyr/CMakeLists.txt`) -- not duplicated into every AEN example's `cc3501e_gpio_routes.c` the way `cc3501e_gpio_routes[]`/`cc3501e_gpio_unrouted[]` correctly are (this list is identical on every AEN board regardless of hw_rev or carrier, so a per-app copy was the exact triplication issue #1859 already removed once for `cc3501e_gpio_routes[]` itself). `tests/scripts/test_gen_cc3501e_gpio_routes.py` imports `scripts/gen_cc3501e_gpio_routes.py:147` ("REVISION_DEPENDENT_E1M_PADS") rather than recomputing it, so generator and test can never disagree.

`examples/aen/aen-evk-demo/prj.conf:81` ("CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BUS_ID=0") and `examples/aen/aen-evk-demo/prj.conf:93` ("CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BITRATE_HZ=100000") now configure that standalone app (previously built with the EEPROM bus disabled and no recorded hw_rev, per the issue) to read the identity manifest over the same bus phase 5 already reads it from, at the same 100 kHz phase 8's `ctx.carrier_bus` open already uses -- the Kconfig's 400 kHz default would otherwise leave that shared controller reconfigured to 400 kHz for the rest of the app's lifetime (`.close = NULL`; nothing restores it), which is not bench-validated on this bus. This lets phase 11's `alp_gpio_open(ALP_E1M_GPIO_IO8)` be confirmed instead of refused -- provided the running module carries a CRC-valid manifest reporting `hw_rev` `"2626-r2"`. Phase 11 itself stays compiled OUT by default (`AEN_EVKDEMO_SOUND_PLAYBACK 0`, `examples/aen/aen-evk-demo/src/main.c:4049`), and this change has NOT been run on the bench -- the manifest-confirms-IO8 path is a design claim, not a silicon-verified one. A factory-fresh or unprovisioned module still fails closed.
