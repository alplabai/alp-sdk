### Fixed — CC3501E GPIO proxy: per-pin, fail-closed revision guard (#2144)

`src/backends/gpio/cc3501e_proxy.c:228` ("static bool is_rev_dependent")
replaces the old all-or-nothing `g_hw_rev_mismatch` guard (#1859) with a
PER-PIN check at `src/backends/gpio/cc3501e_proxy.c:253` ("is_rev_dependent(pin_id) && !g_hw_rev_confirmed_match"), refusing only the E1M pins that `metadata/e1m_modules/aen/hw-revisions.yaml:44` ("dispatch: direct") and `metadata/e1m_modules/aen/hw-revisions.yaml:46` ("dispatch: cc3501e, dispatch_pin: 30") move between the Alif SoC and the CC3501E across AEN hw_revs -- IO8, IO10 and IO21 -- instead of dropping every proxied pin, including revision-independent ones like IO20 (the SD mux enable), on any hw_rev disagreement.

It also fails CLOSED: `src/backends/gpio/cc3501e_proxy.c:111` ("static bool g_hw_rev_confirmed_match") defaults false, and `src/backends/gpio/cc3501e_proxy.c:128` ("cc3501e_proxy_hw_rev_confirmed_match") only reports a match past a CRC-valid `alp_hw_info_read()` AND a `CONFIG_ALP_SDK_SOM_HW_REV` compare -- a missing, unprovisioned or corrupt identity-EEPROM manifest now refuses a revision-dependent pin instead of the old guard's fail-open default.

The revision-dependent pin set is derived from metadata, not hand-typed: `scripts/gen_cc3501e_gpio_routes.py:115` ("def _revision_dependent_e1m_pads") reads `metadata/e1m_modules/aen/hw-revisions.yaml`'s `pad_route_overrides:` and emits it into every generated board's `cc3501e_gpio_routes.c` as `cc3501e_gpio_rev_dependent[]` (`include/alp/chips/cc3501e/gpio.h:167` ("extern const uint32_t cc3501e_gpio_rev_dependent")); the two standalone hand-written tables (`aen-evk-demo`, `aen-sdcard-readout`) carry the same list, and `tests/scripts/test_aen_cc3501e_routes.py` imports `scripts/gen_cc3501e_gpio_routes.py:137` ("REVISION_DEPENDENT_E1M_PADS") rather than recomputing it, so generator and test can never disagree.

`examples/aen/aen-evk-demo/prj.conf:81` ("CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BUS_ID=0") and `examples/aen/aen-evk-demo/prj.conf:82` ("CONFIG_ALP_SDK_SOM_HW_REV") now configure that standalone app (previously built with the EEPROM bus disabled and no recorded hw_rev, per the issue) to read the identity manifest over the same bus phase 5 already reads it from, so phase 11's `alp_gpio_open(ALP_E1M_GPIO_IO8)` can be confirmed instead of refused -- provided the running module carries a CRC-valid manifest reporting `hw_rev` `"2626-r2"`. A factory-fresh or unprovisioned module still fails closed.

New host coverage: `tests/unit/gpio_cc3501e_rev_guard` (native_sim ztest) proves `cc3501e_proxy_hw_rev_confirmed_match()` against a matching, mismatched, corrupt (`ALP_ERR_IO`) and missing (`ALP_ERR_NOT_PROVISIONED`/`ALP_ERR_NOSUPPORT`) manifest, and proves `px_open()`'s gate itself is wired in: a revision-dependent pin (`tests/unit/gpio_cc3501e_rev_guard/src/test_gpio_cc3501e_rev_guard.c:139` ("test_rev_dependent_pin_refused_when_not_confirmed")) refuses with `ALP_ERR_NOSUPPORT` unless confirmed, while a revision-independent pin (`tests/unit/gpio_cc3501e_rev_guard/src/test_gpio_cc3501e_rev_guard.c:162` ("test_revision_independent_pin_opens_regardless")) always opens.
