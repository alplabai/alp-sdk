### Fixed — CC3501E GPIO proxy: per-pin, fail-closed revision guard (#2144)

`src/backends/gpio/cc3501e_proxy.c:305` ("static bool is_rev_dependent")
replaces the old all-or-nothing `g_hw_rev_mismatch` guard (#1859) with a
PER-PIN check at `src/backends/gpio/cc3501e_proxy.c:357` ("is_rev_dependent(pin_id) && !g_hw_rev_confirmed_match"), refusing only the E1M pins that `metadata/e1m_modules/aen/hw-revisions.yaml:44-46` ("E1M_GPIO_IO") move between the Alif SoC and the CC3501E across AEN hw_revs -- IO8 (:44), IO10 (:45) and IO21 (:46) -- instead of dropping every proxied pin, including revision-independent ones like IO20 (the SD mux enable), on any hw_rev disagreement.

It also fails CLOSED: `src/backends/gpio/cc3501e_proxy.c:129` ("static bool g_hw_rev_confirmed_match") defaults false, and `src/backends/gpio/cc3501e_proxy.c:146` ("cc3501e_proxy_hw_rev_confirmed_match") only reports a match past a CRC-valid `alp_hw_info_read()` AND a `CONFIG_ALP_SDK_SOM_HW_REV` compare -- a missing, unprovisioned or corrupt identity-EEPROM manifest now refuses a revision-dependent pin instead of the old guard's fail-open default. `alp_gpio_cc3501e_attach()` logs a one-shot `LOG_WRN_ONCE` naming the read status, the live manifest `som_hw_rev` (when read), and the build's `CONFIG_ALP_SDK_SOM_HW_REV` when it cannot confirm a match; `px_open()` separately logs a one-shot-per-pin `LOG_WRN` naming the #2144 guard specifically, since it returns the SAME `ALP_ERR_NOSUPPORT` as the unrelated #1854 unrouted-pad guard.

The revision-dependent pin set is derived from metadata, not hand-typed: `scripts/gen_cc3501e_gpio_routes.py:125` ("def _revision_dependent_e1m_pads") reads `metadata/e1m_modules/aen/hw-revisions.yaml`'s `pad_route_overrides:` and, unlike an earlier draft of this change, writes it ONCE into an SDK-owned generated file, `src/backends/gpio/cc3501e_rev_dependent_pins.c`, compiled whenever `src/backends/gpio/cc3501e_proxy.c` itself is (`zephyr/CMakeLists.txt`) -- not duplicated into every AEN example's `cc3501e_gpio_routes.c` the way `cc3501e_gpio_routes[]`/`cc3501e_gpio_unrouted[]` correctly are (this list is identical on every AEN board regardless of hw_rev or carrier, so a per-app copy was the exact triplication issue #1859 already removed once for `cc3501e_gpio_routes[]` itself). `tests/scripts/test_gen_cc3501e_gpio_routes.py` imports `scripts/gen_cc3501e_gpio_routes.py:147` ("REVISION_DEPENDENT_E1M_PADS") rather than recomputing it, so generator and test can never disagree.

`examples/aen/aen-evk-demo/prj.conf:81` ("CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BUS_ID=0") and `examples/aen/aen-evk-demo/prj.conf:93` ("CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BITRATE_HZ=100000") now configure that standalone app (previously built with the EEPROM bus disabled and no recorded hw_rev, per the issue) to read the identity manifest over the same bus phase 5 already reads it from, at the same 100 kHz phase 8's `ctx.carrier_bus` open already uses -- the Kconfig's 400 kHz default would otherwise leave that shared controller reconfigured to 400 kHz for the rest of the app's lifetime (`.close = NULL`; nothing restores it), which is not bench-validated on this bus. This lets phase 11's `alp_gpio_open(ALP_E1M_GPIO_IO8)` be confirmed instead of refused -- provided the running module carries a CRC-valid manifest reporting `hw_rev` `"2626-r2"`. Phase 11 itself stays compiled OUT by default (`AEN_EVKDEMO_SOUND_PLAYBACK 0`, `examples/aen/aen-evk-demo/src/main.c:4049`), and this change has NOT been run on the bench -- the manifest-confirms-IO8 path is a design claim, not a silicon-verified one. A factory-fresh or unprovisioned module still fails closed.

`examples/aen/aen-evk-demo/src/main.c:4162` ("mux_en_open_err") captures `alp_last_error()` immediately after IO8's `alp_gpio_open()`, before any later call can overwrite it; the phase 11 failure message at `:4178` now names the #2144 revision guard specifically when `mux_en_open_err == ALP_ERR_NOSUPPORT`, instead of blaming phase 8's bridge attach or the build for every mux-not-drivable case.

New host coverage: `tests/unit/gpio_cc3501e_rev_guard` (native_sim ztest) proves `cc3501e_proxy_hw_rev_confirmed_match()` against a matching, mismatched, corrupt (`ALP_ERR_IO`) and missing (`ALP_ERR_NOT_PROVISIONED`/`ALP_ERR_NOSUPPORT`) manifest, both with hand-set inputs and -- `tests/unit/gpio_cc3501e_rev_guard/src/test_gpio_cc3501e_rev_guard.c:191` ("test_classify_bad_crc_does_not_confirm") and `:206` ("test_classify_blank_eeprom_does_not_confirm") -- with CRC-valid/CRC-corrupt/blank `alp_hw_info_eeprom_t` buffers routed through the real `alp_hw_info_classify_manifest()`. It proves `px_open()`'s gate itself is wired in: a revision-dependent pin (`:234`, "test_rev_dependent_pin_refused_when_not_confirmed") refuses with `ALP_ERR_NOSUPPORT` unless confirmed, while a revision-independent pin (`:257`, "test_revision_independent_pin_opens_regardless") always opens. `:277` ("test_attach_resets_stale_forced_true_on_read_failure") closes the gap a dev-review mutation found: forcing the cached decision `true` via the test hook, then calling the REAL `alp_gpio_cc3501e_attach()` (not the hook), proves attach() re-derives the decision from a real (and, on native_sim, failing) `alp_hw_info_read()` rather than leaving a stale forced value standing -- the earlier test suite never called `attach()` itself, so a mutation hardcoding `g_hw_rev_confirmed_match = true;` inside it passed all 8 prior tests unnoticed.

A second review round found the mirror gap: no test observed attach() PRODUCE a confirmed match, so a mutant hardcoding `g_hw_rev_confirmed_match = false;` in `alp_gpio_cc3501e_attach()` (`src/backends/gpio/cc3501e_proxy.c:216`) passed all 13 tests unnoticed. `tests/unit/gpio_cc3501e_rev_guard/src/test_gpio_cc3501e_rev_guard.c:320` ("test_attach_confirms_match_from_injected_manifest") closes it with a new `CONFIG_ZTEST`-only seam, `cc3501e_proxy_test_inject_hw_info_read()` (`src/backends/gpio/cc3501e_proxy_internal.h`, `src/backends/gpio/cc3501e_proxy.c:175`): it arms a one-shot canned `alp_hw_info_read()` result for the next `attach()` call, so attach()'s real body -- not the pre-existing force hook -- derives and assigns the cached decision, and a confirmed IO8 opens. Chosen over an I2C EEPROM emulator (native_sim has no devicetree I2C0 node backing `CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BUS_ID` in this test build, and wiring a real 24C128-protocol emulator is a materially larger diff) and hand-verified red against the exact mutant above before being restored. A third hook, `cc3501e_proxy_test_reset_bridge_ctx()`, resets the cached bridge-context pointer to NULL after each test that stands up the never-dereferenced sentinel `(cc3501e_t *)(uintptr_t)1`, so it cannot outlive its test and be dereferenced by a later one.
