### Fixed — `gd32g553_init()` gave up on the first STATUS_BUSY in the OTA post-COMMIT/ROLLBACK trial window (#2314)

After `OTA_COMMIT`/`OTA_ROLLBACK` commits a trial-capable image (firmware
release >= 0.2.14, wire protocol 0.12, gd32-bridge-firmware#246), a GD32
bridge reboots into an unconfirmed TRIAL image. That image answers
`STATUS_BUSY` to every opcode, `PING`/`GET_VERSION` included, until it decodes
its first CRC-valid frame. That frame confirms the trial and triggers one
more reset before the link settles (`docs/gd32-bridge-protocol.md` §10). If
no valid frame lands before the bootloader's watchdog (FWDGT) window expires
(~32.8 s nominal), the bootloader reverts to the previously-active slot.

`gd32g553_init()` used to return on the first `ALP_ERR_BUSY`. It now rides
out a bounded (~2 s, one shared `alp_uptime_ms()` deadline across both the
PING and GET_VERSION phases) retry ladder, gated on: `ALP_ERR_BUSY` is always
transient; `ALP_ERR_IO`/`ALP_ERR_TIMEOUT` are transient **only** once this
same `init()` call has already seen at least one `ALP_ERR_BUSY` -- proof a
trial is genuinely in progress and a confirm-triggered second reset is the
explanation. An absent or unflashed bridge never answers `BUSY` at all, so it
still fails fast on the very first `IO`/`TIMEOUT`, unchanged from before this
fix -- load-bearing for `src/zephyr/v2n_supervisor.c`, which re-runs this
init on every `acquire()` while the bridge stays absent and budgets that on a
~1 ms bridge op, not a 2 s retry ladder. Non-transient failures (NOSUPPORT,
INVAL, a genuine version mismatch) still return immediately.

An `OTA_BEGIN` sent in the legacy 8-byte form (no `fw_version` triple) is
treated as an unknown incoming version, which is itself sufficient reason to
boot the result into TRIAL -- but this is only the right call for an image
that is ITSELF trial-capable (>= 0.2.14): an older image committed this way
is reverted by the watchdog ~33 s later, having no confirm logic of its own
to run. To install an older image that must survive, pass its real, known
version instead; an explicitly known version below 0.2.14 is a deliberate
downgrade guard -- the bridge commits/rolls back to it WITHOUT the TRIAL
dance at all (no `STATUS_BUSY` window). The watchdog-revert protection is the
bootloader's doing, not the app's: an old bootloader paired with a new,
trial-capable app still runs the TRIAL/confirm dance but never reverts a hung
image, so bootloader and app must ship together for the protection to apply.

Bench status: both the app-side confirm path (BUSY -> first valid frame ->
second reset -> normal operation) and the bootloader's watchdog-driven revert
path are silicon-validated on E1M-V2M103, 2026-09-26 -- a deliberately hung
image (misconfigured HXTAL) committed via the legacy `OTA_BEGIN` form was
reverted to the previous slot after ~33 s, `RESET_REASON` read back `WDT`,
and the bridge's own health check cleared the reverted slot's `slot_valid`
flag.
