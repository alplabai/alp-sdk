### Fixed — `docs/bench/model-perf-capture.md`'s blocker 3 claimed `<alp/inference.h>` has no latency accessor; it has had one since #1541 (#2054)

The tier-2 model-perf capture doc listed three open blockers gating a bench
capture campaign. The third, "No timing harness," said `<alp/inference.h>`
"exposes no latency accessor" and that "the first capture campaign has to
lift one" itself before it could fill any `perf.latency_ms` field. That
stopped being true on 2026-08-18: commit `409e4c31`
("`feat(inference): add alp_inference_last_invoke_latency_us accessor
(#1541)`") added `alp_inference_last_invoke_latency_us(alp_inference_t *inf,
uint64_t *out_us)` at `include/alp/inference.h:481`, and
`docs/abi-markers.md:69` already names it "the model-perf-capture latency
accessor" in the `inference.h` classification row. The accessor is wired
into both dispatchers (`src/inference_dispatch.c` for Zephyr/M-class,
`src/yocto/inference_yocto.c` for Yocto/A-class) and the stub
(`src/common/stub/stub_inference.c`), so the doc was describing a gap that
had already closed.

Verified the accessor's actual contract before rewriting anything, rather
than trusting the doc's paraphrase: it reports only the LAST successful
`alp_inference_invoke()` call — no history, no running statistics, so a
caller building a distribution reads it once per invoke and keeps the
samples itself. `out_us` is filled in whole MICROSECONDS, rounded to
nearest. It returns `ALP_OK` with a real duration once any invoke has
completed `ALP_OK` on the handle, or one of `ALP_ERR_INVAL` (`out_us` is
NULL), `ALP_ERR_NOT_READY` (`inf` is NULL/closed, or no invoke has ever
completed `ALP_OK` on this handle — never returned merely because the last
invoke was slow), or `ALP_ERR_NOSUPPORT` (a stub build with no inference
backend compiled in at all, so there is no timing mechanism to have
populated). It carries a function-level `[ABI-EXPERIMENTAL]` marker; the
file-level marker on `inference.h` stays `[ABI-STABLE]`.

Blocker 3 had no residual real blocker once the false claim was removed —
the recipe's step 4 now names the exact API and header instead of "once it
exists," and review of the first draft of this fix surfaced three
correctness traps in that step that needed closing before it could be
trusted, so the shipped step 4 also covers all three. First, checking only
the accessor's own return code is not enough: `alp_inference_invoke()` can
itself return `ALP_ERR_TIMEOUT` (NPU stuck) or `ALP_ERR_IO` (NPU error),
and a failed invoke does not update the accessor's stored value, so
reading it after a failed invoke silently returns the PREVIOUS successful
invoke's duration with `ALP_OK` — recording that as the new sample
duplicates an old value and drops exactly the invoke that blew its timing
budget, biasing `p95` low in a way `scripts/validate_metadata.py` cannot
detect. The step now requires checking `alp_inference_invoke()`'s own
return first and discarding/re-running on anything but `ALP_OK`, never
recording. Second, "divide by 1000" without a type/rounding contract
invites `out_us / 1000` as C integer division on the `uint64_t` reading,
which truncates every value to a whole millisecond (a 1500 us invoke
under-reports as `1` ms instead of `1.5`, a 33% error that still passes
`metadata/schemas/model-perf-v1.schema.json`'s `latency_ms` block — its
fields are typed `number` with only a positivity/non-negativity floor, no
precision requirement — and can even collapse `stdev` to `0` on a tight
distribution). The step now spells out a floating-point division by
`1000.0` with the fractional result kept, mirroring step 3's existing
worked-example standard of care for its bytes→KiB conversion. Third,
`ALP_OK` from the accessor is necessary but not sufficient: on a target at
60 MHz or below under stock Kconfig, or any target without
`CONFIG_TIMER_HAS_64BIT_CYCLE_COUNTER`, the hardware cycle counter wraps
modulo 2^32 and the accessor reports `ALP_OK` with a plausible-looking but
too-small duration, not an error — now called out explicitly, alongside a
pointer at the two in-tree examples (`examples/camera-vision/ai-object-detection-realtime/src/main.c`
and `examples/camera-vision/ai-camera-viewer/src/inference_loop.c`) NOT to
copy, since both predate this accessor, hand-roll `k_cycle_get_32()` /
`k_cyc_to_us_floor32()`, and discard `alp_inference_invoke()`'s status via
`(void)`.

The doc's "three blockers" language was renumbered to "two blockers"
throughout `docs/bench/model-perf-capture.md`; blockers 1 (the vela
profile question) and 2 (the const-region question) are untouched and
remain open — neither was re-checked as part of this change.
`metadata/schemas/model-perf-v1.schema.json`'s `latency_ms` field
description carried the same stale claim ("no AEN example times an
inference today and `<alp/inference.h>` exposes no latency accessor") and
is corrected too; the field stays schema-optional, now because no bench
capture has run yet rather than because no accessor exists. The pending,
still-unreleased `changelog.d/1520.md` fragment repeated the identical
false "three blockers" / "no latency accessor" claim in its own prose (it
folds into the same `[Unreleased]` section as this fragment and #1541's),
so it is corrected in place to "two blockers" with the accessor clause
dropped, rather than left to ship a self-contradicting release note.

This is a documentation-only correction. No `perf` data was added, changed,
or measured on silicon, and `metadata/model_perf/` still ships empty — this
issue is deliberately separate from the bench data campaign tracked under
#1894.
