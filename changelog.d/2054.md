### Fixed — `docs/bench/model-perf-capture.md`'s blocker 3 claimed `<alp/inference.h>` has no latency accessor; it has had one since #1541 (#2054)

The tier-2 model-perf capture doc listed three open blockers gating a bench
capture campaign. The third, "No timing harness," said `<alp/inference.h>`
"exposes no latency accessor" and that "the first capture campaign has to
lift one" itself before it could fill any `perf.latency_ms` field. That
stopped being true on 2026-08-18: commit `409e4c31`
("`feat(inference): add alp_inference_last_invoke_latency_us accessor
(#1541)`") added `alp_inference_last_invoke_latency_us(alp_inference_t *inf,
uint64_t *out_us)` at `include/alp/inference.h:481`, and
`docs/abi-markers.md:69` already names it "the model-perf-capture latency
accessor" in the `inference.h` classification row. The accessor is wired
into both dispatchers (`src/inference_dispatch.c` for Zephyr/M-class,
`src/yocto/inference_yocto.c` for Yocto/A-class) and the stub
(`src/common/stub/stub_inference.c`), so the doc was describing a gap that
had already closed.

Verified the accessor's actual contract before rewriting anything, rather
than trusting the doc's paraphrase: it reports only the LAST successful
`alp_inference_invoke()` call — no history, no running statistics, so a
caller building a distribution reads it once per invoke and keeps the
samples itself. `out_us` is filled in whole MICROSECONDS, rounded to
nearest. It returns `ALP_OK` with a real duration once any invoke has
completed `ALP_OK` on the handle, or one of `ALP_ERR_INVAL` (`out_us` is
NULL), `ALP_ERR_NOT_READY` (`inf` is NULL/closed, or no invoke has ever
completed `ALP_OK` on this handle — never returned merely because the last
invoke was slow), or `ALP_ERR_NOSUPPORT` (a stub build with no inference
backend compiled in at all, so there is no timing mechanism to have
populated). It carries a function-level `[ABI-EXPERIMENTAL]` marker; the
file-level marker on `inference.h` stays `[ABI-STABLE]`.

Blocker 3 had no residual real blocker once the false claim was removed —
the recipe's step 4 now names the exact API and header instead of
"once it exists": bracket each timed run with `alp_inference_invoke()`
followed immediately by `alp_inference_last_invoke_latency_us()`, discard a
handful of warm-up readings, take at least 30 back-to-back timed invokes,
and divide the microsecond reading by 1000 before writing the schema's
`latency_ms.*` fields (which are milliseconds — the accessor does no unit
conversion itself). So blocker 3 was removed outright and the doc's "three
blockers" language was renumbered to "two blockers" throughout
`docs/bench/model-perf-capture.md`; blockers 1 (the vela profile question)
and 2 (the const-region question) are untouched and remain open — neither
was re-checked as part of this change. `metadata/schemas/model-perf-v1.schema.json`'s
`latency_ms` field description carried the same stale claim ("no AEN
example times an inference today and `<alp/inference.h>` exposes no
latency accessor") and is corrected too; the field stays schema-optional,
now because no bench capture has run yet rather than because no accessor
exists.

This is a documentation-only correction. No `perf` data was added, changed,
or measured on silicon, and `metadata/model_perf/` still ships empty — this
issue is deliberately separate from the bench data campaign tracked under
#1894.
