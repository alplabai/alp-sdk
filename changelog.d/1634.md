### Fixed — ADC stream/filter/spectrum handles had no lifecycle, so close() recycled a slot under an in-flight read (#1634)

`alp_adc_stream_t`, `alp_adc_filter_t` and `alp_adc_spectrum_t` carried a bare
`bool in_use` — no lifecycle byte, no `active_ops` counter. The read paths
validated the handle with a plain non-atomic load and then blocked for a long
time with nothing holding the slot: `alp_adc_stream_read_mv()` waits inside
`alp_z_v2n_supervisor_acquire()` (bounded by
`CONFIG_ALP_SDK_V2N_SUPERVISOR_ACQUIRE_TIMEOUT_MS`) and then runs a GD32G553
bridge transaction. `close()` tore the slot down unconditionally across that
whole window, so a concurrent close could hand the slot to a new caller while
the old read was still writing into it.

The three handles adopt the lifecycle discipline every other handle type in this
SDK already uses — `alp_handle_op_enter()` / `alp_handle_op_leave()` around the
op, `ALP_HANDLE_LC_OPEN` published after a successful open, and close draining
`active_ops` rather than assuming none. No new mechanism was invented for this;
the existing one in `src/common/alp_slot_claim.h` is the point.

**Not closed by this change:** the issue asks for a `native_sim` open/read/close
stress test proven to fail against the pre-fix code. That is still owed — the
verification done here was a throwaway host harness, which is not a committed
regression test and does not stop the defect returning.
