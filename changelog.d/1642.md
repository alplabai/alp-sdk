### Fixed — DAC/I3C admission now consults the backend registry, not a SoC cap-table count that inverted itself to zero (#1642)

`alp_dac_open()` and `alp_i3c_open()` carried a dispatch-level admission gate
shaped `if ((ALP_SOC_<CLASS>_COUNT > 0) && id >= ALP_SOC_<CLASS>_COUNT) reject`.
The `> 0` term meant the gate went permissive exactly when a SoC's count was
`0` — the one case a "reject an unsupported instance" gate exists to catch.
Both guarding comments were also wrong: `src/dac_dispatch.c` claimed
`ALP_SOC_DAC_COUNT` is `0` under `CONFIG_ALP_SOC_NONE` (it is `UINT16_MAX`,
the accept-any sentinel, in `include/alp/soc_caps.h`), and
`src/i3c_dispatch.c` claimed the `> 0` term rejects "a SoC that genuinely has
no I3C" when it does the opposite — skips the check entirely there.

A naive fix (flip the condition to reject when the count is `0`) is wrong too:
`src/backends/dac/gd32_bridge.c` registers an *exact* `silicon_ref` match for
`renesas:rzv2n:n44`, a SoC whose `ALP_SOC_DAC_COUNT` is `0` (it has no on-die
DAC), and serves channels 0/1 over the GD32 IO-MCU bridge. Rejecting on the
cap-table count would refuse a DAC that genuinely works on that SoM.

Both gates are deleted. Admission is now the backend registry alone —
`alp_backend_select()` plus each backend's own `open()`-time bound check —
matching the pattern every other class dispatcher (`adc`, `counter`,
`inference`, ...) already uses; none of them ever had a dispatch-level
instance-count gate. `src/dac_dispatch.c` and `src/i3c_dispatch.c` were the
only two sites in `src/` with this shape (confirmed by grep across `src/`
for the `_COUNT > 0` pattern — no other class dispatcher shares it, so no
sibling fix is needed).

Two `tests/zephyr/peripheral/` scenario tests that pinned the old gate's
behaviour (`test_dac_out_of_range_channel`, `test_i3c_out_of_range_bus`) are
updated: the specific `ALP_ERR_INVAL` assertion under a finite, non-`NONE`
SoC count is dropped, since which error a now-selected backend returns for
an out-of-range instance (`NOSUPPORT` if it declines outright, `INVAL` if it
bounds-checks the instance itself) is backend-specific, not a dispatch
contract. A new test,
`test_dac_bridged_channel_admitted_despite_zero_soc_count` (gated on
`CONFIG_ALP_SDK_V2N_SUPERVISOR`), pins the corrected decision directly: on
`renesas:rzv2n:n44` (`ALP_SOC_DAC_COUNT == 0`), `alp_backend_select("dac",
ALP_SOC_REF_STR)` still resolves to `gd32_bridge`, and opening channel 0
reaches that backend's `open()` and fails for the real hardware reason (no
GD32 bus configured — supervisor `ALP_ERR_NOT_READY`), not a cap-table
refusal. Confirmed this test (and `test_v2n_supervisor_dac_open_not_ready_
without_buses`) both fail under the naive "reject on count == 0" fix, then
reverted that probe.

Per ADR-0002 as amended (`docs/adr/0002-error-mechanism.md`), the deleted
gate's `ALP_ERR_INVAL` for an out-of-range instance was itself the wrong
code for "config exceeds hardware caps" (the ADR's original decision reserves
`ALP_ERR_OUT_OF_RANGE` for that, distinct from `ALP_ERR_INVAL` "programmer
error") — moot now that the gate is gone rather than recoded, since the
still-existing `be == NULL` branch (`ALP_ERR_NOT_PRESENT_ON_THIS_SOC`) and
each backend's own bound check are unchanged and outside this fix's scope.

The broader redesign the issue also describes — a declarative
`instance_count` field on `alp_backend_t` plus honoring the existing
`probe()` hook's return value as the admission verdict across all 16
dispatchers that currently discard it — needs its own design pass and is not
part of this change.
