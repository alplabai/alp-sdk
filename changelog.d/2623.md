### Added — bmap support: write and verify only the used blocks of the system image (#2623)

`scripts/provision_som.py` `write_rootfs` wrote the whole uncompressed wic to the eMMC and read all of it back for the md5 (7,001,391,104 bytes for som-0.2.0). With a block map in the bundle it now writes and reads back only the blocks that hold data.

`metadata/schemas/som-release-bundle-v1.schema.json` gains the optional component role `system_image_bmap` and the `flash_target` value `none`; the two go together (the bmap must use `none`, no other role may). The legacy flat flow skips a `none` component, and `--build-dir` picks up a single `*.wic.bmap` (`scripts/provision_som.py:450`, "system_image_bmap").

`scripts/provision/bmap.py` parses the bmaptool file (format 2.0) and refuses what it cannot vouch for: a wrong `BmapFileChecksum`, a `MappedBlocksCount` that disagrees with the ranges, a `ChecksumType` other than sha256, ranges that overlap, are out of order or run past the image, and a DOCTYPE/ENTITY declaration. `verify_image()` checks the bundle's `.wic.gz` against it: every range's sha256, the image size, and that every byte outside the ranges is zero. The last check matters because the write, the readback and the probe all look only at the listed blocks, so a bmap listing too few ranges would otherwise leave a unit reported as written without the unlisted data. A bmap built from another image, or an under-mapping one, fails the new `preflight` gate `bmap` before anything is written (`scripts/provision/steps.py:871`, "def _wic_bmap").

The unit needs no `bmaptool`. `scripts/provision/board_bmap.py` is copied to the unit's `/tmp` and imports only `os` and `sys`; hashing stays with busybox `md5sum`. The same `.wic.gz` is streamed over SSH (`scripts/provision/linux_target.py:471`, "def rootfs_bmap_write_verify"): `gunzip -c | python3 board_bmap.py write <emmc> <spans> <image_size> && sync`. The writer fails unless the stream is exactly `ImageSize` bytes. The readback and the "already written?" probe hash the same mapped blocks, and the reader prints its byte count so a reader that died behind `| md5sum` is a failure, not a digest of partial output. A unit without `python3` (rc 127) gets the full-image write and the plan log says so; any other failure of that check raises instead of falling back. The step result reads `wic written (mapped blocks only, N of M bytes)`.

Blocks the bmap leaves out are not written and keep what the eMMC held before, so the eMMC is no longer a byte-for-byte copy of the wic.

`meta-alp-sdk/recipes-images/alp-image-common.inc:240` ("IMAGE_FSTYPES:append:rzv2n-family") adds `wic.bmap` for the V2N/V2M machines, so every `alp-image-*` build emits `<image>.wic.bmap` next to the `.wic.gz`.

Not verified: no bitbake build was run for the `IMAGE_FSTYPES` change, the mapped-block path has not run on a unit, and no bmaptool-emitted file has been through the parser (the format rules were checked against bmaptool 3.9.0's source). Coverage is `tests/scripts/test_provision_bmap.py`, which runs the real unit-side script against a plain file standing in for the eMMC. The time saved per unit is unmeasured. The ledger fact `rootfs_wic_sha256` does not record which write ran.
