### Added — one machine source for per-product core ownership: `assignable:` + board.yaml `ownership:` (#2660)

`metadata/e1m_modules/v2n/core-ownership.yaml` keeps `core_ownership:` for fixed facts and gains an `assignable:` block keyed by E1M instance (`e1m_uart0`, `e1m_uart1`, `e1m_spi0`, `e1m_can0`, `e1m_can1`), each with a `default` (`a55`), the `candidates` that have a real backend today, and references to existing `(peripheral, pad)` pinmux rows. A project may name an instance in a top-level `ownership: {<instance>: <core>}` in `board.yaml`; the loader rejects an unknown instance, a core outside `candidates`, a `hw_blocked` instance, and a non-default core unless both trees can follow it (see the per-project Linux fragment entry), and `--emit system-manifest` gains an additive `ownership:` map (omitted for SoMs without assignable resources). `core-ownership-v1.schema.json` is new and `validate_metadata.py` checks that assignable rows exist in `metadata/pinmux/v2n.yaml`, are not also fixed rows, and name real SoC cores. No instance lists `m33` as a candidate yet: UART0 waits for the P51 RX pull-up bench proof, UART1 has no CM33 node, CAN-FD has no CM33 driver, SPI0 waits for its `m33:` block. An override naming a core the project does not declare under `cores:` is rejected. Assignable entries may carry an `m33:` devicetree block (pinctrl function codes come from the SoC `linux_dt`): `gen_zephyr_board.py` then emits the node `disabled` with metadata-derived pinctrl, and `--emit dts-overlay` / `zephyr-conf` enable it only for a project whose resolved owner is `m33`. No entry carries that block yet (RSPI0/CAN-FD PFC codes and the SPI_B CM33 interrupt routing are not in metadata), so generator output is unchanged and an `m33` assignment of `e1m_spi0` errors at emit. `check_amp_pad_claims.py` now checks both directions: a Linux DT claim on a pad resolved to the CM33, and an enabled CM33 board node claiming a pad resolved to the A55, using the fixed `core:` rows plus each assignable instance's SoM default. Assignable entries now name a `soc_instance` (SoC JSON `linux_dt`: node label, PFC function codes, CPG clock names) and may carry `hw_blocked` (`e1m_spi0`: P90-P92 not 3.3 V tolerant, refused on every core). `scripts/gen_linux_ownership_dt.py` generates `e1m-v2n-ownership.dtsi` (included from `e1m-v2n-som.dtsi`, installed by the linux-renesas bbappend, checked by the generated-files gate): an a55-owned node is enabled only with `linux_enable: true` + `linux_evidence` (none today, so the default fragment changes no Linux behaviour -- an alias-less `&sci0` would steal the console); missing PFC codes are a reported gap. The CM33 clock hold is now data-driven: `0001-clk-renesas-r9a09g056-keep-CM33-owned-RSCI7-on.patch` (hard-coded `DEF_MOD_CRITICAL` on the five `rsci_7_*` clocks) is replaced by `0001-clk-renesas-rzv2h-cpg-cm33-owned-clocks.patch`, which makes `rzv2h-cpg` keep every clock named in the CPG node's `renesas,cm33-owned-clocks` on, and the generated fragment fills that list from the resolved ownership (RSCI7 for the GD32 link always, plus the clocks of each instance whose SoM default owner is the M33; clock names from SoC `linux_dt.cpg_clocks`). The patch applies to the BSP kernel (6717c06) but the DT-driven form is not yet bench-validated. The patch logs each held clock, errors on a listed name that matches no module clock, and warns once if the property is absent on r9a09g056. Downstream: tan-cli re-derives the system manifest and `alp.conf` itself, so it must pick up the new additive `ownership` key of `--emit system-manifest` (coupled pins with the SDK emit, as with the other tan pin moves).
