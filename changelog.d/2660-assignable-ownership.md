### Added — one machine source for per-product core ownership: `assignable:` + board.yaml `ownership:` (#2660)

`metadata/e1m_modules/v2n/core-ownership.yaml` keeps `core_ownership:` for fixed facts and gains an `assignable:` block keyed by E1M instance (`e1m_uart0`, `e1m_uart1`, `e1m_spi0`, `e1m_can0`, `e1m_can1`), each with a `default` (`a55`), the `candidates` that have a real backend today, and references to existing `(peripheral, pad)` pinmux rows. A project overrides a default with a top-level `ownership: {<instance>: <core>}` in `board.yaml`; the loader rejects an unknown instance or a core outside `candidates`, and `--emit system-manifest` gains an additive `ownership:` map (omitted for SoMs without assignable resources). `core-ownership-v1.schema.json` is new and `validate_metadata.py` checks that assignable rows exist in `metadata/pinmux/v2n.yaml`, are not also fixed rows, and name real SoC cores. `m33` is a candidate only for `e1m_spi0`; UART0 waits for the P51 RX pull-up bench proof, UART1 has no CM33 node, CAN-FD has no CM33 driver. An override naming a core the project does not declare under `cores:` is rejected. Assignable entries may carry an `m33:` devicetree block plus per-row `pfc_*` triples: `gen_zephyr_board.py` then emits the node `disabled` with metadata-derived pinctrl, and `--emit dts-overlay` / `zephyr-conf` enable it only for a project that assigned it to `m33`. No entry carries that block yet (RSPI0/CAN-FD PFC data and the SPI_B CM33 interrupt routing are not in metadata), so generator output is unchanged and an `m33` assignment of `e1m_spi0` errors at emit.
