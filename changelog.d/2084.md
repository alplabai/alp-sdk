### Added — generated the `E1M-AEN803` Zephyr board tree (#2084, #1966)

Every module on the AEN bench is an `E1M-AEN803`
(serial `2026W36-0001`, serial `2026W36-0002`), but until
now no Zephyr board tree existed for that SKU at all -- its
`topology.<core>.board:` targets were still bare placeholder names.
`scripts/alp_project.py --emit zephyr-board` now generates
`zephyr/boards/alp/e1m_aen803_m55_hp/` and `.../e1m_aen803_m55_he/` straight
from
[`metadata/e1m_modules/E1M-AEN803.yaml`](../metadata/e1m_modules/E1M-AEN803.yaml)
+ the shared E8 SoC JSON, the same way the committed `E1M-AEN801` tree is
produced -- no special-casing in the generator itself, since #2062/#2065/#2073
already landed the pieces (whole-device-alias exception, `chip:`-derived
banner) this depended on.

The preset's `topology.m55_hp`/`m55_he` `board:` targets are now qualified
with the `<soc>/<cpucluster>` suffix
(`metadata/e1m_modules/E1M-AEN803.yaml:183`, `:188`,
`board: alp_e1m_aen803_m55_hp/ae822fa0e5597ls0/rtss_hp`), matching
`E1M-AEN801`'s naming and the #720 qualified-board-target rule, now that
the tree they name actually exists.
`scripts/check_board_target_tree_parity.py`'s `_NOT_YET_SUPPORTED` allowlist
dropped its two AEN803 entries accordingly -- the gate itself would have
flagged them stale.

The generated `.dts` banner reflects AEN803's real BOM, not AEN801's: `zephyr/
boards/alp/e1m_aen803_m55_he/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.dts:15`
names "OSPI0 NOR (IS25WX256-JHLE) + HyperRAM (S80KS5122GABHM02) are
populated" (both CS0/CS1 fitted), where the committed AEN801 tree still
correctly says neither is. Boot and storage stay MRAM-only for both SKUs
today -- `flash_ospi_alif.c` ships no `flash_driver_api` (#915), so wiring
either external memory into the boot/storage partition map is separate,
follow-on board-bring-up work, not done here.

`E1M-AEN801`'s own committed tree is untouched -- `git diff --stat` on
`zephyr/boards/` shows only the two new `e1m_aen803_m55_*` directories.
`board.cmake` and the bare `Kconfig` (hand-maintained in every AEN board
directory, never emitted -- see `scripts/gen_zephyr_board.py`'s module
docstring) were hand-authored for AEN803 the same way, off the AEN801
sibling: same SETOOLS device profile (`AE822FA0E5597LS0_HE`/`_HP`, same
silicon) and the same custom E8 MPU-region-table select.

**The two new targets are actually built in CI, not just pinned
byte-for-byte against the generator.** A board tree that only matches its
own generator's output proves the generator is deterministic, not that the
board builds -- so `examples/aen/aen-adc-regcheck` gained AEN803-qualified
overlays for both cores and both `alp_e1m_aen803_m55_{he,hp}` entries in its
`testcase.yaml` `platform_allow`, and `.github/workflows/pr-twister-aen.yml`
gained the matching `-p` flags (both changes are required together --
neither alone selects anything). `tests/scripts/test_gen_zephyr_board.py`'s
byte-equivalence check now also verifies the reverse direction for every
`PARITY_COVERED` board (AEN801, AEN803, V2N101, V2M101): a hand-added file
sitting in a committed board directory that the generator never claims is
now a failure, not silently invisible.

**What this change does NOT fix, tracked separately:**
`scripts/bench/aen/bench-env.sh`'s `AEN_BOARD` default still resolves to the
`E1M-AEN801` target, and `build.sh` uses it unconditionally -- a bench build
with no explicit `AEN_BOARD` override still targets the AEN801 tree even on
the AEN803 hardware actually on the bench. This is deliberately NOT
repointed here: only `aen-adc-regcheck` carries AEN803-qualified overlays
today, and Zephyr's board-overlay auto-apply only fires on an exact
fully-qualified-board-name match, so repointing the default now would make
every OTHER AEN bench example build silently with no overlay applied under
the new default. Filed as #2094, which needs either AEN803 overlays across
every AEN bench example or a loud-failure fallback in `build.sh` before the
default can move safely.

This also lands the doc-facing piece of #1966: `docs/soms/aen.md` gains the
`E1M-AEN803` SKU-table row plus a short paragraph on what distinguishes it
from `E1M-AEN801` -- same PCB and E8 silicon, dual external memory BOM.

`python3 scripts/validate_metadata.py`, `python3 scripts/check_pin_conflicts.py`,
`python3 scripts/check_emit_snapshots.py`, `python3 scripts/check_atoc_reservation.py`,

for `examples/aen/aen-adc-regcheck` on both
`alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he` and

`-DCONFIG_COMPILER_WARNINGS_AS_ERRORS=y`.
