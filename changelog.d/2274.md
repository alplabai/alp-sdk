### Fixed — the `alif_flash` runner now refuses a multi-domain sysbuild flash instead of silently overwriting the resident ATOC entry (#2274)

Zephyr's own sysbuild flash plumbing runs `scripts/west_commands/runners/
alif_flash.py`'s `do_run` ONCE PER DOMAIN, not once per `west flash`
invocation. Confirmed against Zephyr v4.4.1 (this repo's pinned revision,
`west.yml`'s `zephyr:` entry): its `scripts/west_commands/flash.py` hands
`do_run_common` the sysbuild's top-level `domains.yaml`, and its
`run_common.py`'s `get_domains_to_process`/`do_run_common` loop
instantiates and calls the board's runner once per resolved domain, each
time with that domain's own per-domain `build_dir` (upstream Zephyr's
`run_common.py`, `for d in domains: ... do_run_common_image(..., d.
build_dir, ...)`). On an
AEN MCUboot sysbuild both the `mcuboot` domain (ITCM `0x58000000`) and the
app domain (HE slot0) map to the SAME ATOC section name `ALP-HE` via
`_atoc_section_name`. The #2262 ATOC-replace guard identifies a resident
entry by NAME ONLY, so on a SECOND invocation any `ALP-HE` entry a
previous `alif_flash` run of the OTHER domain wrote is already this run's
own `allowed` set — the guard reports `clear`, but burning a fresh
single-entry ATOC over it silently replaces whatever the earlier run
wrote. This is not a regression (the pre-`#2262` runner did the same with
no check at all); it is a real, unclosed gap the guard's name-only
matching can never catch on its own, tracked as this issue since the
`#2262` changelog fragment first documented it. (On a factory-provisioned
module the resident MCUboot entry is instead named `MCUBOOT-` (entry name
TBD/unverified, see `zephyr/sysbuild/aen/README.md`'s provisioning
section), which the #2262 guard already refuses as foreign; this gap is
specifically about two
`alif_flash` runs of the same repo's own sysbuild both writing `ALP-HE`,
e.g. a from-scratch bring-up or a re-keyed module.)

`do_run` now refuses, before ANY staging/gettoc/J-Link/burn side effect,
whenever the build being flashed is itself a multi-domain sysbuild — keyed
on the build's OWN `domains.yaml` declaring more than one FLASHABLE
domain, not on how many domains THIS `west flash` invocation happens to
process. A single `--domain <x>` invocation of a 2-domain sysbuild refuses
too: flashing only one domain would still replace any `ALP-HE` entry a
previous run of the other domain wrote, the same way. A plain
(non-sysbuild) build with no `domains.yaml`, and a sysbuild with exactly
one flashable domain, are unaffected and behave exactly as before.

The new pure helper `_parse_sysbuild_domains_yaml` (in `alif_flash.py`)
reads `domains.yaml` from the sysbuild's top build dir — one level ABOVE
the per-domain `build_dir` `west flash` hands this runner as `self.cfg.
build_dir`. Confirmed against Zephyr v4.4.1: `share/sysbuild/cmake/
domains.cmake` generates the file at `${CMAKE_BINARY_DIR}/domains.yaml`
(the top build dir), and `share/sysbuild/cmake/modules/
sysbuild_extensions.cmake` sets each domain's own binary dir to
`${CMAKE_BINARY_DIR}/${ZBUILD_APPLICATION}`, one path component below. It
prefers `flash_order:` over the full `domains:` list when computing which
domains are "flashable" — `domains.cmake` builds `flash_order:` already
filtered to exclude each image's `BUILD_ONLY` property, the same list
Zephyr's own `run_common.py` reads for a plain multi-domain `west flash` —
so a build-only image (never a candidate for `west flash` to process at
all) does not trip the refusal. It is deliberately independent of
Zephyr's own `Domains` class (`scripts/pylib/build_helpers/domains.py`),
which is only importable from an active west workspace — this runner
already avoids that dependency for the same reason its module docstring
gives for importing only `runners.core` + the stdlib.

Four cases are handled explicitly: no `domains.yaml` (not a sysbuild —
proceed as today); exactly one flashable domain (proceed as today); this
build's own `build_dir` not listed among ANY of its domains.yaml's domains
at all (a relocated/stale build tree — refuse with a distinct "does not
list this build dir" message, fail-closed, since a same-name overwrite
against an unknown build is unverifiable rather than safe); more than one
flashable domain (refuse, naming the domains found and pointing at the
supported J-Link path, `docs/aen-provisioning.md` §0.5 Option B). Every
refusal message includes the `domains.yaml` path it read. A `domains.yaml`
that exists but cannot be read, does not parse as the documented shape
(`default`/`build_dir`/`domains: [{name, build_dir}]`/`flash_order`),
declares an empty `domains:` list, has a non-string `name`/`build_dir`, or
declares two `domains:` entries with the same `name`, also refuses —
fail-closed, never silently treated as "not a sysbuild" or "single
domain, proceed". `_sysbuild_domains_path` locates `domains.yaml` with
`.absolute()`, not `.resolve()` — a symlinked per-domain `build_dir` must
resolve `domains.yaml` relative to the symlink's own location (where
Zephyr's `flash.py` actually navigated), not its resolved target;
`.resolve()` is used only for the listed-build-dir equality comparison,
where both sides must be resolved the same way for the check to be
meaningful.

The refusal message additionally states that the Option B J-Link path it
points at writes the **app only** — it requires MCUboot already resident,
and names the SETOOLS provisioning steps (`zephyr/sysbuild/aen/README.md`)
needed first on a bare, wiped, or re-keyed module, since a missing
MCUboot otherwise leaves the module unable to boot (recoverable via
SETOOLS re-provisioning).

`tan flash` does **not** hit this refusal on AEN: tan-cli's
`select_flash_method` dispatches any `zephyr_west_flash` entry carrying
`jlink_flash_device` (every published Ensemble SoC variant does) to Flow
D (`alif_mram_jlink`, a direct J-Link/SWD burn) instead of `west flash`,
so `alif_flash`'s `do_run` is never reached.

The MEDIUM-3 (#2262) stale-verdict `atoc-guard.json` unlink now runs
BEFORE the #2274 check, not after: clearing this runner's own prior
output is not an MRAM/ATOC side effect, so a #2274 refusal must still
clear it the same as every other early-abort path — otherwise a refused
run would leave a PREVIOUS run's `clear`/`replaced` verdict looking like
its own. `docs/aen-provisioning.md` §0.6 (the verdict contract) now notes
this as a second honest exception to "a refused run always leaves a
verdict": a #2274 refusal leaves none at all, clearing any stale one.

This fix makes moot, but does not itself resolve, the separate open
question of whether `zephyr.signed.bin` might already be rejected
earlier by `_reset_vector`/`_select_app_shape` on a signed image's
header — that remains unclaimed either way.
