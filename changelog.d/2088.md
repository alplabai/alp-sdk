### Fixed — `partition.py` placed a runtime mount on any `memory_map` region without checking `write_authority` (#2088)

`_resolve_flash_device()` (`scripts/alp_orchestrate/partition.py:479` ("def _resolve_flash_device"))
resolved a `storage[].flash_device:` reference to any named `memory_map:` region -- including a
whole-device alias like `mram_main` -- purely on name and size, never reading `write_authority`.
The schema is explicit that `customer_runtime` is "the ONLY value ... a row may claim DIRECTLY for
... a runtime mount to land on" (`metadata/schemas/som-preset-v1.schema.json:723`); nothing in the
allocator enforced it. `scripts/check_atoc_reservation.py` closed the equivalent hole for rows
covering the ATOC band (#2086); this closes the allocator's own gap, flagged as a follow-up in
that fix's changelog entry.

The guard lives in `_resolve_flash_device()` itself (`scripts/alp_orchestrate/partition.py:499`),
the one place every caller routes through -- the main allocator
(`resolve_storage_partitions()`, `scripts/alp_orchestrate/partition.py:765`) and both alt-device
remedy scans (`_verified_alt_devices()`, `scripts/alp_orchestrate/partition.py:717`; the inlined
overlap-block scan, `scripts/alp_orchestrate/partition.py:991`) all resolve through it, so one
guard covers every path a customer preset can reach, not just the board.yaml-driven one. A region
whose authored `write_authority` is neither `customer_runtime` nor `composite` is refused outright,
naming the region, the offending value, and the remedy. An ABSENT value is refused too, but only
where an on-die MRAM aperture resolves for the SoM (Alif) -- mirrors `carveout.py`'s own
`_region_ipc_eligibility()` gate; a no-op on every non-Alif SoM, none of which author
`write_authority` on a derived region today.

`composite` -- the tag a whole-device alias like `mram_main` carries, meaning "consult the
contained rows instead" (the schema's own words) -- is not an unconditional pass: refusing it
outright would break `examples/connectivity/production-deployment/board.yaml`'s
`flash_device: mram_main`, the only whole-device alias any committed preset declares. Instead
`_composite_alias_coverage_gap()` (`scripts/alp_orchestrate/partition.py:274`) actually consults
the contained rows the tag promises: every resolved `memory_map:` row CONTAINED in the alias's own
address window must declare its own `write_authority`, and together the contained rows must
CONTIGUOUSLY tile the window -- no gap, no overlap -- before the alias is accepted; a row whose
own base or size doesn't resolve is deferred rather than an immediate refusal (it is named as a
candidate only if a gap remains for it to plausibly explain), and a row outside the window is
ignored as unrelated. Placement itself routes through a SEPARATE, older function
(`_reserved_spans()`) with its own weaker origin/window derivation, so a composite alias whose
contained rows verify safe is refused anyway if that function can't actually reserve them.

Review round 1 found the first cut of this fix skipped the consultation entirely (a blanket
`composite` exemption) and reproduced the hole three ways against the real E1M-AEN801 preset with
only `memory_map:` swapped, landing a `storage[]` entry inside the live Secure-Enclave-owned
`atoc` band (bench-observed at 0x80578000..0x80580000,
`scripts/alp_orchestrate/carveout.py:100-104`) or at MCUboot's own address. Review round 2 found
the consultation itself was two more of the same class of hole:

- **Sum, not tiling.** The first cut of the consultation summed contained rows' sizes and compared
  the total to the alias's capacity -- an overlap of N bytes plus a hole of N bytes passes a sum
  check while the hole itself stays unprotected. Reproduced by deleting `atoc` and widening
  `he_slot0` by exactly `atoc`'s size (2688 -> 2720 KiB): the sum still matched, and
  0x80578000..0x80580000 stayed undeclared. The consultation now sorts the contained spans and
  walks them, refusing a gap OR an overlap and naming the offending pair.
- **The allocator's own degradation went unnoticed.** `_reserved_spans()` -- the function placement
  actually uses -- derives its own window top as `max(hi)` across every `memory_map:` row with a
  resolved base, INCLUDING a row entirely unrelated to this alias; an out-of-window sibling pushes
  that derived top past the alias's real one, failing `_reserved_spans()`'s own identity check and
  degrading it to reserving NOTHING -- not even `mcuboot` -- with only a stderr warning. The
  consultation verifying the contained rows individually didn't make placement itself safe. Fixed
  by treating that degradation as a refusal for a `composite` target: an alias whose contained rows
  can't actually be reserved can't be consulted either, the same principle already applied to an
  unresolved base.

No committed preset's behaviour changes: every AEN SKU's `memory_map:` already resolves,
authorizes, and contiguously tiles `mram_main`'s declared capacity with no gap and no overlap, so
`_resolve_flash_device("mram_main", ...)` still succeeds on all seven of them -- `_reserved_spans()`
still reserves every named sibling regardless of authority (including `storage` itself), so
`mram_main` remains 100% tiled with zero free bytes for a new entry either way
(`test_fully_tiled_device_blocks_with_an_actionable_reason`, unchanged). `carveout.py`'s
`_region_ipc_eligibility()` independently refuses `mram_main` as an IPC carve-out target outright
in every state it can resolve to (`composite` != `customer_runtime` while unresolved; flash-class,
never eligible, once resolved) -- the two enforcers agree in effect that a `customer_runtime`
write never lands broadly across `mram_main` on real metadata today, even though `partition.py`
now resolves the alias as a device (an explicit pin still needs somewhere to point) where
`carveout.py` never treats it as one eligible carve-out target.
