### Fixed — `partition.py` placed a runtime mount on any `memory_map` region without checking `write_authority` (#2088)

`_resolve_flash_device()` (`scripts/alp_orchestrate/partition.py:417` ("def _resolve_flash_device"))
resolved a `storage[].flash_device:` reference to any named `memory_map:` region -- including a
whole-device alias like `mram_main` -- purely on name and size, never reading `write_authority`.
The schema is explicit that `customer_runtime` is "the ONLY value ... a runtime mount may ever
land on" (`metadata/schemas/som-preset-v1.schema.json:723`); nothing in the allocator enforced it.
`scripts/check_atoc_reservation.py` closed the equivalent hole for rows covering the ATOC band
(#2086); this closes the allocator's own gap, flagged as a follow-up in that fix's changelog entry.

The guard lives in `_resolve_flash_device()` itself (`scripts/alp_orchestrate/partition.py:463`),
the one place every caller routes through -- the main allocator
(`resolve_storage_partitions()`, `scripts/alp_orchestrate/partition.py:699`) and both alt-device
remedy scans (`_verified_alt_devices()`, `scripts/alp_orchestrate/partition.py:651`; the inlined
overlap-block scan, `scripts/alp_orchestrate/partition.py:925`) all resolve through it, so one
guard covers every path a customer preset can reach, not just the board.yaml-driven one. A region
whose authored `write_authority` is neither `customer_runtime` nor `composite` is refused outright,
naming the region, the offending value, and the remedy. An ABSENT value is refused too, but only
where an on-die MRAM aperture resolves for the SoM (Alif) -- mirrors `carveout.py`'s own
`_region_ipc_eligibility()` gate; a no-op on every non-Alif SoM, none of which author
`write_authority` on a derived region today.

`composite` -- the tag a whole-device alias like `mram_main` carries, meaning "consult the
contained rows instead" (the schema's own words) -- is not an unconditional pass: refusing it
outright would break `examples/connectivity/production-deployment/board.yaml`'s
`flash_device: mram_main`, the only whole-device alias any committed preset declares. Instead
`_composite_alias_coverage_gap()` (`scripts/alp_orchestrate/partition.py:265`) actually consults
the contained rows the tag promises: every OTHER `memory_map:` row whose resolved extent falls
inside the alias's own address window must resolve a concrete base+size, declare its own
`write_authority`, and together fully tile the window, before the alias is accepted. Review round
1 found the first cut of this fix skipped that consultation entirely (a blanket `composite`
exemption) and reproduced the hole three ways against the real E1M-AEN801 preset with only
`memory_map:` swapped: a sibling with an unresolved base (`atoc`'s `base: "TBD"`, its real shape
before a SoM is HW-mapped) silently dropped out of `_reserved_spans()`'s reservation, landing a
storage[] entry inside the live Secure-Enclave-owned `atoc` band (bench-observed at
0x80578000..0x80580000, `scripts/alp_orchestrate/carveout.py:100-104`) two different ways, and a third case where
`mram_main`'s own base was ALSO unresolved (its real shape on every committed AEN preset) degraded
`_reserved_spans()` to sibling-only checking with a warning, not a refusal, landing an entry at
MCUboot's own address. All three now refuse at `_resolve_flash_device()` time, before the
allocator ever runs.

No committed preset's behaviour changes: every AEN SKU's `memory_map:` already resolves,
authorizes, and fully tiles `mram_main`'s declared capacity, so `_resolve_flash_device("mram_main",
...)` still succeeds on all seven of them -- `_reserved_spans()` still reserves every named
sibling regardless of authority (including `storage` itself), so `mram_main` remains 100% tiled
with zero free bytes for a new entry either way (`test_fully_tiled_device_blocks_with_an_actionable_reason`,
unchanged). `carveout.py`'s `_region_ipc_eligibility()` independently refuses `mram_main` as an IPC
carve-out target outright in every state it can resolve to (`composite` != `customer_runtime` while
unresolved; flash-class, never eligible, once resolved) -- the two enforcers agree in effect that a
`customer_runtime` write never lands broadly across `mram_main` on real metadata today, even though
`partition.py` now resolves the alias as a device (an explicit pin still needs somewhere to point)
where `carveout.py` never treats it as one eligible carve-out target.
