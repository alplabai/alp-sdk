### Fixed — `partition.py` placed a runtime mount on any `memory_map` region without checking `write_authority` (#2088)

`_resolve_flash_device()` (`scripts/alp_orchestrate/partition.py:265` ("def _resolve_flash_device"))
resolved a `storage[].flash_device:` reference to any named `memory_map:` region -- including a
whole-device alias like `mram_main` -- purely on name and size, never reading `write_authority`.
The schema is explicit that `customer_runtime` is "the ONLY value ... a runtime mount may ever
land on" (`metadata/schemas/som-preset-v1.schema.json:723`); nothing in the allocator enforced it.
`scripts/check_atoc_reservation.py` closed the equivalent hole for rows covering the ATOC band
(#2086); this closes the allocator's own gap, flagged as a follow-up in that fix's changelog entry.

The guard lives in `_resolve_flash_device()` itself (`scripts/alp_orchestrate/partition.py:311`),
the one place every caller routes through -- the main allocator
(`resolve_storage_partitions()`, `scripts/alp_orchestrate/partition.py:514`) and both alt-device
remedy scans (`_verified_alt_devices()`, `scripts/alp_orchestrate/partition.py:466`; the inlined
overlap-block scan, `scripts/alp_orchestrate/partition.py:740`) all resolve through it, so one
guard covers every path a customer preset can reach, not just the board.yaml-driven one. A region
whose `write_authority` is authored and is neither `customer_runtime` nor `composite` (the
schema's own tag for a whole-device alias that "defers to contained rows", `mram_main`'s tag on
every AEN preset) is refused, naming the region, the offending value, and the remedy
(`write_authority: customer_runtime`, or point `flash_device:` at the region that already carries
it). `composite` is deliberately NOT refused here: it is not itself runtime-writable, but it is
also not the #2088 hazard by itself -- refusing it would break
`examples/connectivity/production-deployment/board.yaml`'s `flash_device: mram_main` and every AEN
storage test that targets it, for a row whose per-placement safety is `_reserved_spans()`'s job,
not this guard's.

An ABSENT `write_authority` stays legal: the field is deferred-to-required for som-preset v1
(#2024) -- a customer preset authored before it existed must not be hard-refused by this guard --
but it is not silent either, printing a `WARNING:` naming the device and SoM so a reviewer sees
the gap. No committed AEN preset is affected: every `memory_map:` region on every AEN SKU already
authors `write_authority` explicitly.
