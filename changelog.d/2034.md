### Fixed — five E1M-EVK chip drivers never worked on silicon, and the tests said PASS anyway (#2034)

A bench run on `E1M-AEN803` serial `2026W36-0002` printed
`RESULT PASS: 13/13 devices answered` while **every sensor returned its own
documented reset sentinel**: both IMUs reported `accel{-32768,-32768,-32768}`
(`0x8000` per axis), the BMP581 reported `p_raw = t_raw = 8355711` (`0x7F7F7F`),
and all six INA236 reported `0 uA`. Chip IDs read back byte-correct throughout,
which is what made the failure survive so long: the example's tally counted a
successful ID read as a pass, so the data layer was never checked at all.

Root-causing that, then verifying every register claim against the primary
datasheets, turned up defects in five drivers:

* **BMI323 never enabled its accelerometer.** `ACC_CONF`'s `acc_mode` is a
  three-bit field at bits `[14:12]` (BST-BMI323-DS000-13 Rev 1.7 pp. 88-91), and
  the driver wrote `|= (1 << 12)` — the value `0b001`, which is not in the
  encoding table at all. Normal mode is `0b100`. The same defect sat in
  `bmi323_set_gyro()`. Data registers therefore held `0x8000`, which the
  datasheet states verbatim is "invalid value" for a disabled sensor.
* **ICM-42670's `ACCEL_ODR` enum was shifted one code low** across the whole
  100 Hz-1.6 kHz range (TDK DS-000451 Rev 1.0 p.57): `ODR_1600_HZ` was `0x4`, a
  *reserved* code, and a comment called `0x9` reserved when it is 100 Hz. The
  gyro path also validated against the accelerometer's legal set, accepting
  `0xD`/`0xE`/`0xF`, which `GYRO_CONFIG0` reserves (p.56).
* **BMP581 was never started.** The driver's own header says `bmp581_init()`
  "does not start sampling", and the example never called `bmp581_set_sampling()`,
  so `OSR_CONFIG.press_en` stayed at its `0x00` reset and the data registers
  returned their `0x7F` power-on values.
* **INA236 current was read before the first post-calibration conversion.**
  `CALIBRATION` powers on at `0000h` and `CURRENT` is only recomputed when a
  shunt conversion completes (TI SBOSA81D §8.1.2), so a read issued inside the
  2.2 ms cycle returns a stale zero.
* **RV-3028-C7's `CONTROL_2` bit map was wrong.** Bit 6 is `CLKIE` and bit 7 is
  `TSE` (App Manual Rev. 1.4 p.24), but the driver named them `24H` and `CLKIE`
  and never touched the real `12_24` bit at all — so "force 24-hour mode" set
  `CLKIE`, and `set_int_enable(SRC_CLKF)` toggled Time Stamp Enable. The
  EEPROM-mirrored writes also never issued the `EECMD` commit sequence, so a
  BSIE or CLKOUT change was RAM-only and reverted at the next 24-hour refresh;
  and a bus transaction slower than 950 ms returns all-`0xFF`, which the driver
  decoded as a valid BCD time.

Every fix carries a test that was **shown to fail against the unfixed code** —
mutating `acc_mode` back to `(1 << 12)`, pointing `route_int` at the wrong
`INT_SOURCE`, or comparing the endurance guard against the RAM mirror instead of
an EEPROM readback each turn exactly the expected assertions red.

The RV-3028-C7's new EEPROM commit is gated on the byte actually changing:
endurance is **100 cycles minimum at the hot corner** (p.98), and one example in
this tree performs three commits per run, which would have consumed the part in
roughly thirty runs.

`examples/peripheral-io/i2c-device-hub`'s verdict now requires every operation to
succeed **and** the data not to match the part's documented invalid pattern.
Where no such sentinel exists — INA236 voltage and current, EEPROM contents —
the return codes are the whole check and the example says so rather than
inventing one.
