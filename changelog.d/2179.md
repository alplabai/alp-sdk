### Fixed — an I2S interrupt the half-duplex `dir` gate cannot service left `i2s_dw_isr()` returning without changing anything, so the NVIC tail-chained straight back in (#2179)

**Defensive hardening, and the diagnosis is NOT confirmed on silicon.** Read
this entry as four independently-correct fixes, not as "the #2179 HardFault is
fixed". What is **measured**: `alp_i2s_start(RX)` on `i2s3` left the M55-HE
spinning in `i2s_dw_isr()` / `_isr_wrapper` on E1M-AEN803 serial 2026W36-0002
(Alif Ensemble E8) in 6 of 6 runs — `CFSR (0xE000ED28) = 0x00000000`,
`BFAR (0xE000ED38) = 0x00000000`, `CycleCnt` advancing, thread mode starved, no
fault taken, PCs decoded against the exact ELF that ran. Also measured: the
block is **not** in the SYSRESETREQ reset domain — `CER` (`0x4901700C`) and
`TER` (`0x4901702C`) both persisted at `0x00000001` across a J-Link `loadbin`'s
implicit SYSRESETREQ, and a RESETPIN reset (`RSetType 2` / `r` / `RSetType 0`)
cleared both to `0x00000000`. What is **inferred**: that an orphaned TXFE is
what the core was spinning on. A follow-up bench campaign passed 8/8 and never
reproduced the fault, so no `ISR`/`IMR`/`IPSR` capture exists to confirm it, and
none of the four changes below is claimed to fix the observed hang. Each is
worth making on its own terms; issue #2179 stays open for the capture that
settles it.

**The shape of the defect.** `i2s_dw_isr()` gates both data branches on
`dev_data->dir`, a SINGLE field this half-duplex driver keeps for both streams
(`I2S_DIR_BOTH` is `-ENOSYS`). A source that is asserted **and unmasked** but
whose branch the `dir` gate skips made that function read `ISR`, match no
branch, change **nothing**, and return. These sources are level-held, so the
interrupt is still asserted on return and the NVIC re-enters immediately. It is
the only path in this driver that never terminates: every path that actually
reaches `i2s_rx_irq_handler()` self-terminates within ~2 blocks against the
backend's 2-block slab (`src/backends/i2s/zephyr_drv.c`), so even an RXDA flood
clears itself.

TXFE while `dir == I2S_DIR_RX` is the reachable case. TXFE is asserted by an
**empty** TX FIFO — the resting state — whereas RXDA needs data to arrive; and
`i2s_enable_rx_interrupt()` clears only `RXDAM|RXFOM`
(`zephyr/drivers/i2s/i2s_dw.h:753-760` ("i2s_enable_rx_interrupt")), so `TXFEM`
left unmasked by an earlier TX phase survived into the next RX stream. That
asymmetry is why RX-after-TX is the exposed ordering and TX-after-RX is not.

**Four sites, all in `zephyr/drivers/i2s/i2s_dw.c`.**

- **`i2s_dw_isr()` — the root-cause guard.** It now computes `ISR & ~IMR` on
  entry (`ISR` and `IMR` share a bit layout, and `IMR` is mask-to-disable, so
  that is exactly the set of sources holding the line up), each branch clears
  the bit it services, and anything left at the bottom is **masked**
  (`zephyr/drivers/i2s/i2s_dw.c:933` ("unserviced = int_status & ~i2s_get_interrupt_mask(i2s);")).
  Masking is the one action guaranteed to change the interrupt condition, so
  the function can no longer return without having changed it. Note that adding
  a clear inside `i2s_tx_irq_handler()`/`i2s_rx_irq_handler()` does **not**
  close this — on the unserviced path the handler is never called at all. The
  mask is not lost: `i2s_enable_tx_interrupt()`/`i2s_enable_rx_interrupt()`
  unmask again on that direction's next `tx_stream_start()`/`rx_stream_start()`.
  A source that IS serviced is never masked, so both working single-direction
  paths behave exactly as before.
- **`rx_stream_start()` / `tx_stream_start()` — the same defect at its source.**
  Each already disabled the OTHER direction's channel on every start but left
  that direction's interrupts unmasked; disabling the TX channel does not
  deassert TXFE, since an empty FIFO is exactly what asserts it. Both now mask
  the opposite direction's `IMR` bits alongside the channel disable
  (`zephyr/drivers/i2s/i2s_dw.c:1288` ("mask TX's interrupts alongside the TX channel")
  and `zephyr/drivers/i2s/i2s_dw.c:1413` ("mask RX's interrupts alongside the RX channel")).
  No behaviour change for a TX stream that is still meant to run: `dir` has
  already been repointed to `I2S_DIR_RX` by the `i2s_dw_configure(I2S_DIR_RX)`
  that precedes any RX start, so `i2s_tx_irq_handler()` was unreachable from
  there on regardless — see this file's header for that known full-duplex gap,
  which this change makes explicit rather than widening.
- **`i2s_dw_configure()` assigned `dev_data->dir` before validating it.** It was
  the first statement in the function, so a call that then failed — `-ENOSYS`
  for `I2S_DIR_BOTH`, `-EINVAL` for an unknown direction, `-EINVAL` for an
  invalid stream state — still repointed the only field `i2s_dw_isr()` consults,
  permanently, while changing nothing else. `I2S_DIR_BOTH` is the worst of the
  three: it leaves `dir` matching **neither** ISR branch, so every subsequent
  I2S interrupt is unserviced. The assignment now happens only once the call is
  committed to (re)configuring a stream
  (`zephyr/drivers/i2s/i2s_dw.c:397` ("dev_data->dir = dir;")).
- **`i2s_dw_initialize()` armed the NVIC before masking.** `i2s->irq_config()`
  (`IRQ_CONNECT` + `irq_enable`) ran two statements *before* the mask writes,
  with `dev_data->dir` fresh from BSS as `0` (== `I2S_DIR_RX`) and no stream
  configured at all. Since the block survives SYSRESETREQ (measured above), a
  fresh image inherits the previous one's `IER`/`IMR`/`IRER`/`ITER`/`RER`/`TER`.
  `IER`/`IRER`/`ITER`/`RER`/`TER` are now quiesced and every interrupt masked
  **before** `irq_config()`
  (`zephyr/drivers/i2s/i2s_dw.c:1051` ("quiesce the block and mask every interrupt")),
  and the two `k_sem_init()` calls move above it for the same reason (both ISR
  handlers `k_sem_give()` those semaphores). `CER` is deliberately **not**
  cleared: `i2s_enable_controller()` still sets `CER.CLKEN`, just a few
  statements later, so #2149's and #2150's shared invariant — "`CER.CLKEN`
  reads 1 from `i2s_dw_initialize()` onward" — is unchanged.

**Not a change to the half-duplex contract.** `I2S_DIR_BOTH` still returns
`-ENOSYS`, `dev_data->dir` is still a single field, and the two full-duplex gaps
#2150 phase 1 recorded in this file's header are unchanged in substance — the
first is now worded to include the interrupt masking as well as the channel
disable. TX-only and RX-only streaming behave exactly as before.

**Tests.** `tests/unit/i2s_dw_underrun` — the suite that compiles
`zephyr/drivers/i2s/i2s_dw.c` directly into its own translation unit against a
RAM-backed `struct I2S_Type` — gains seven cases and now drives `i2s_dw_isr()`
and `i2s_dw_initialize()` by name rather than one layer below them:
`test_isr_txfe_with_dir_rx_masks_txfe`, `test_isr_rxda_with_dir_tx_masks_rxda`,
`test_isr_rxda_with_dir_rx_is_serviced_not_masked` (the no-regression half: a
guard that simply masked everything asserted would pass the first two while
killing a working RX stream on its first interrupt),
`test_rx_start_masks_tx_interrupt`, `test_tx_start_masks_rx_interrupt`,
`test_failed_configure_leaves_dir_unchanged`, and
`test_initialize_quiesces_before_arming_irq` — the last reading the register
state captured **inside** a fake `irq_config()` callback, since the instant the
NVIC is armed is the only point at which the ordering is observable. `ISR` is
declared `__IM` (`volatile const`), so presenting an asserted source casts the
qualifier away through `uintptr_t` rather than a bare `(uint32_t *)`: this suite
is the first to compile the driver on a 64-bit host
(`native_sim/native/64`), where that distinction matters. The fake
`clock_control` device also gained a `struct device_state`, since
`i2s_dw_initialize()`'s `device_is_ready()` dereferences `dev->state`
unconditionally.

**Bench check still owed**, and the capture that would settle the diagnosis, on
an AEN EVK bench unit with the core halted after a reproduction: `IPSR` and NVIC
`IABR4` (`0xE000E310`) bit 16 to identify the instance (`i2s3` is
`interrupts = <144 3>`, so `IPSR` `160` / `0xA0`), then `IMR` (`0x49017038`'s
neighbour `0x4901703C`) and `ISR` (`0x49017038`) to compute `ISR & ~IMR`, then
`TER` (`0x4901702C`), `RER` (`0x49017028`), `IRER` (`0x49017004`), `ITER`
(`0x49017008`). `ISR & ~IMR` bit 4 (TXFE) set with `dir != 1` confirms the
mechanism above. **Keep any J-Link memory window off `0x49017020`-`0x49017044`
while gathering that evidence**: `ROR`/`TOR` are clear-on-read (reading them
*is* the overrun clear), `LRBR`/`RRBR` and `RXDMA` each pop the RX FIFO on read,
and `0x49017020`/`0x49017024` are `LTHR`/`RTHR` on write — writing them pushes
TX data and deasserts TXFE, erasing the fault.

**Separate finding, not addressed here.** Both in-tree `i2s3` overlays declare
**TX-only pinmux** — `PIN_P9_3__I2S3_SDO_A`, `PIN_P9_4__I2S3_SCLK_A`,
`PIN_P9_5__I2S3_WS_A`, with SDI (`P9_2`) explicitly not declared. Any RX probe
reusing either unchanged has no SDI pad muxed at all, which matters
independently of this hang.
