### Fixed — E8 ISP-Pico's TPG branch refuses a 0x0 port rect instead of leaving `VSI_MPI_ISP_SetChnAttr` to fail with `-EINVAL` (#2256)

`isp_configure()`'s test-pattern-generator branch (`zephyr/drivers/video/isp_pico.c`)
set the TPG pixel format but never `port_fmt.width`/`height`, so
`VSI_MPI_ISP_SetChnAttr` got a 0x0 port rect and failed with `-EINVAL`
("Setting the Channel config failed!", bench-confirmed on E1M-AEN803
2026W36-0009 -- runs 179-181 confirmed 1280x720 and 1920x1080 both make
`SetChnAttr` succeed). The binding
(`zephyr/dts/bindings/video/vsi,isp-pico.yaml`) now carries
`tpg-width`/`tpg-height` (default 0, fail closed); `examples/aen/aen-isp-regcheck`'s
two overlays now set 1920x1080, the TPG's real size (below). `isp_set_fmt(INPUT)` also no longer calls
`video_set_format()` on a NULL `config->controller` (TPG-only builds have no
camera pipeline to forward to), per the issue's "Next step". Adds a
`native_sim` unit test for the new `isp_tpg_geometry_is_valid()` guard
(`tests/unit/isp_pico_tpg_geometry`).

Finding 2 narrowed on silicon (E1M-AEN803 serial 2026W36-0001). The TPG's
frame size is not hidden: disassembling `VSI_ISP_CoreSetTpg` in `libisp_gcc.a`
shows it writes fixed timing whatever size is requested -- only the CTRL
resolution bits change -- and a read-back after configure gives
`TPG_ACT_IN` = 1920 x 1080 active (total 2844 x 1968), with the acquisition
window (`ACQ_H_SIZE`/`ACQ_V_SIZE`) also at 1920 x 1080. With the geometry
matched end to end, every TPG frame still raises `INTR_SIZE_ERR`
(`int_st 0x00000008`, 143 frames), so the violation comes from another
window in the closed pipeline, not the TPG/acquisition size. That, and
finding 3 (YUYV MI output never completing), stay open. Refs #2256, does
not close it.
