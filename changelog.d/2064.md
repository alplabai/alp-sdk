### Fixed — AEN bench helpers selected a J-Link probe by serial alone, and multiple probes on the bench share one cloned OEM serial (#2064)

`-SelectEmuBySN` cannot disambiguate on alplab-gw: several J-Link probes all
answer OEM serial `000603000869` (the exact count enumerated has drifted
before and is not repeated here), and `JLinkExe` has no USB-path selector, so
a bare serial selection took whichever same-serial probe it happened to
enumerate first -- not necessarily the one on the board the operator's
labgrid reservation actually covered. The existing SW-DP IDR safety gate
(`bench_jlink_assert_aen_dpidr`) only ever answered "is this an Alif E8"; all
three AEN places answer the identical DPIDR, so it could not catch a
wrong-BOARD attach among them, only a wrong-CHIP one (a GD32 or a V2N CM33).

Every `JLinkExe` invocation under `scripts/bench/aen/` now routes through a
new `bench_jlink_run()` (`bench-env.sh`) -- an in-tree port of the mechanism
already proven on this bench (`board-farm/bin/jlink-run.sh`), so nothing
committed depends on a host-specific external path. It resolves the target
probe's USB topology from `LG_SWD_PATH` (the `LG_PLACE`-resolved path from
#2032) and, inside an unprivileged `unshare -rm --net --ipc --propagation
private` namespace, `mount --bind`-masks every OTHER probe's
`/dev/bus/usb/<bus>/<dev>` node **and** its sysfs device directory before
selecting by the now-unambiguous serial. All four parts are load-bearing,
each found only after a simpler theory failed on the real bench:

1. `-SelectEmuBySN` must be explicit -- `JLinkExe` never auto-selects, even
   with exactly one probe visible.
2. Masking only the usbfs node is not enough: the device still enumerates
   from sysfs, so `JLINK_EMU_SelectByUSBSN` finds the first match for the
   shared serial there and never falls back to a working one.
3. `--net`/`--ipc`: a second `JLinkExe` does not even reach USB once one is
   already open -- it finds the first instance over loopback and attaches to
   THAT probe, regardless of any USB masking.
4. `ip link set lo up` inside the fresh netns -- a new namespace starts with
   loopback down, and the J-Link DLL segfaults on it.

`bench_jlink_run()` also carries the two guard rails around the mechanism
itself, both found in review:

- **Probe-brick guard, ported from `jlink-run.sh`**: these probes are CLONES
  and a SEGGER firmware-update write to one is unrecoverable. `exec
  DisableAutoUpdateFW` is now injected ahead of the caller's
  `-CommandFile`/`-CommanderScript` before any probe is opened, and
  `bench_jlink_run()` refuses outright when neither flag is present (nowhere
  to inject the guard).
- **Reservation-holder check**: `bench_labgrid_resolve()` (the `#2032`
  resolver `LG_SWD_PATH` comes from) now confirms the place's `acquired:`
  line names the CALLING operator (`"$(hostname)/$(whoami)"`, the same
  identity labgrid-client itself records), not merely that SOME reservation
  is held. A place another operator holds previously resolved cleanly and
  would have let this invocation drive their board -- exactly the failure
  #2064 exists to prevent.
- Both the mask computation and the post-mask verification (every `mount
  --bind` actually took; exactly one vendor-`1366` device remains visible in
  sysfs afterwards, which is what `-SelectEmuBySN` enumerates) now abort
  rather than silently proceeding when a sibling probe can't be fully masked
  (an unreadable `busnum`/`devnum`, or a vanished usbfs node).

`bench_jlink_run()` **refuses rather than guesses** in every case above --
the expected behaviour #2064 asked for.

The DPIDR preflight (`bench_jlink_assert_aen_dpidr`) is kept as a separate,
additional check, not deleted as "now redundant": it still catches a GD32 or
V2N CM33 on the other end, which the USB-topology masking alone does not
prove.

`ram-run.sh` (#2076) already carried an equivalent, independently-built
mechanism, hard-required (exit 2 if unset) via an external `AEN_JLINK_RUN`
wrapper + `BENCH_PLACE`. That path is preserved as an operator opt-in (its
wrapper also suppresses the same probe-firmware-update prompt
`bench_jlink_run()` now suppresses itself), but is no longer required:
`ram-run.sh` falls back to the in-tree `bench_jlink_run()` when
`AEN_JLINK_RUN` is not exported, so it no longer hard-depends on an
unshipped, host-specific path.

`bench_jlink_run()` is unit-tested (`tests/scripts/test_bench_jlink_run.py`)
via two test-only overrides -- `BENCH_JLINK_SYSFS_ROOT`/`BENCH_JLINK_DEV_ROOT`
point the mask computation at a fake probe tree, and
`BENCH_JLINK_RUN_DRY_RUN` prints the computed target node, masks and
selection instead of masking/exec-ing anything -- covering the mask
computation, the injected prelude's content, and both refusal paths without
a real USB topology or `unshare`. Neither override is set on a real bench
host.

**Bench verification on an AEN EVK bench unit found one blocker: `bench_labgrid_resolve()`
made the `seuart` labgrid resource mandatory on EVERY resolution, including
J-Link-only flows that never touch SE_UART.** Two of the three AEN places
export only `console` and `swd` -- the physical boards have
no SE-UART -- so `LG_SWD_PATH` could never resolve on them and every helper
(`ram-run.sh`, `reread.sh`, `flash-jlink*.sh`, ...) died at source time with
"exports no 'seuart' resource path", before `bench_jlink_run()` was ever
reached. That shipped the isolation fix unusable on exactly the two boards
where the wrong-board risk is highest -- all three AEN places share DPIDR
`0x4C013477` and OEM serial `000603000869`. Fixed: `seuart` is resolved when
present but no longer required for the resolve itself to succeed (`swd`
still is); `SE_UART` simply comes back empty on a place with no `seuart`
resource, exactly as `LG_CONSOLE_DEV`/`HOST`/`PORT` have always been
optional. The property this was protecting is preserved at the right
layer, not removed: `flash-run.sh`/`flash-run-dualcore.sh`'s own
`[ -z "${SE_UART:-}" ]` gate ahead of `app-write-mram`, and
`bench_atoc_replace_guard`'s own "SE_UART is unset" abort, both still
refuse loudly rather than write blind -- they just no longer block a flow
that was never going to touch SE_UART in the first place.

Everything else bench-verified clean on an AEN EVK bench unit: all four
load-bearing masking parts (the post-mask sysfs count read exactly 1; both
other probes' usbfs nodes bind-mounted to `/dev/null`'s major:minor; fresh
`net`/`ipc`/`mnt` namespace IDs; `lo` up), the probe-brick guard on the real
`unshare`/`exec` path (the probe opened only after `exec
DisableAutoUpdateFW`), `-SelectEmuBySN` carrying the serial read from the
resolved target's own sysfs node, and DPIDR `0x4C013477` on `AP[3]
APAddr 0x00300000` -- matching evk-03's own recorded AP, not evk-01's
`0x00200000`, independent confirmation it landed on the right board. All
four refusal paths fired on real hardware (rc 9, rc 1 then 9, rc 10, rc 9).

Two things this bench session deliberately did NOT exercise, and are not
claimed: the held-by-another-operator refusal branch (both other AEN places
read `acquired: None`, so the not-acquired branch fires first -- reaching
the other one needs a second real operator), and the `--net`/`--ipc`
loopback-attach failure mode being adversarially re-provoked (that needs a
second concurrent `JLinkExe` on another board, which would violate
serial-bench discipline to set up deliberately). The namespace freshness and
`lo` state that mechanism depends on were proven; the specific failure it
prevents was not re-created live.
