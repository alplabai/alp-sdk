### Documented — the SERAM ↔ services-library version pairing on E1M-AEN, and the API break below v109 (#1700)

Alif Semiconductor, answering our escalation on a customer AE822 (2026-08-28):

> there is an API break between SERAM v106 and v109 for E8 devices. v106 is a
> really early version for E8 platform, and you definitely need to update SERAM
> on your HWs to a newer version (v110 is recommended). It works ok with also
> with services library v109. General guideline is that you should always use a
> matching SERAM and services library.

This is the answer to the first of the five questions we escalated, and it is a
constraint no part of this repo previously stated. The SE firmware image (SERAM,
what `se_service_get_se_revision()` reports) and the services library (the
hal_alif `se_services` client this SDK links, `hal_alif v2.3.0` at the current
`west.yml` pin) are versioned together and are not independently upgradable.
Nothing in the SDK could have told a reader that, and the failure mode of
getting it wrong does not name itself: the customer's module runs SERAM
**1.106.2** (Jul 14 2025) against a services library from SETOOLS **1.109**,
which straddles the break.

`docs/aen-se-services.md` gains §0.1 with the pairing rule, a supported-pairs
table, the one read-only call that tells you what a module is running
(`se_service_get_se_revision()`, already in §1's zero-risk set), and the remedy
— a System Package update over the SE-UART, not an application change.

It also records the symptom seen on the mismatched pair, because that is what a
reader will arrive with rather than a version number: the *first* SE service
request stops HFXTAL and unlocks the PLL, and the M55-HP drops from 400 MHz to
76.8 MHz and stays there. It reproduced through `SERVICE_CRYPTOCELL_GET_RND`
(reached from a DHCP client's randomness source) but is not RNG-specific —
shifting application code by `0x100` changes the outcome. Alif has **not** said
the break causes this fault, and §0.1 does not wait on that: across an API break
any behaviour is permissible, so nothing measured on a mismatched pair is
evidence about anything and a workaround built on one is unsafe to ship even
when it appears to work. Fix the pairing first, triage after. #1700 stays open
for the causal question.

**ADR 0030** records the standing position the answer forces: SERAM and the
services library are one versioned pair that moves together, and E1M-AEN tracks
Alif's latest released SERAM — floor and current baseline **v110** — rather
than sitting on whatever a module shipped with. A `hal_alif` bump stops being a
routine dependency bump under that rule: it moves the services library, so it
moves the required SERAM floor with it. The ADR also records why the two obvious
alternatives lose — pinning a known-good older pair means standing on v106, the
version Alif are telling us to leave, and leaving the pairing to each module
owner is the status quo that produced #1700.

`docs/aen-provisioning.md` gains the same check as a prerequisite note ahead of
§2, since the SE-UART a reader is already wiring is the channel the SERAM update
travels over.

§1's `se_service_get_se_revision()` row carried `SES A0 v1.106.2 Jul 14 2025` as
its bench value — a capture taken before the reference board's System Package
update, and now precisely the version Alif says to move off. Left alone it
advertised a pre-break baseline as this SDK's reference. The row now reads
`SES A0 v1.110.0 Mar 4 2026` with the old capture kept alongside it, so the
change is legible rather than silent.

Two facts checked against upstream while writing this, both recorded: hal_alif
documents `se_service_get_se_revision()` as "Retrieve SERAM version banner"
(`se_services/include/services_lib_protocol.h`), which is what makes it the right
call to name; and `hal_alif v2.3.0` is already the newest `hal_alif` release tag,
so the services-library half needs no bump — the work is entirely module-side.

One thing this does **not** settle, and the pin cannot answer it: hal_alif
versions its services library independently of SETOOLS — `v2.3.0` declares
`SE_SERVICES_VERSION_STRING "0.50.10"`, a number with no stated relation to SERAM
v106/v109/v110 — and Alif publish no mapping between the two schemes. So which
SERAM floor this SDK's pin actually requires is unknown. §0.1 and ADR 0030 both
say so, and take v110 as the module baseline on the strength of Alif's own
recommendation and the reference board running it.
