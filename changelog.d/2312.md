### Fixed — the ethos_u adapter shipped a zero-SRAM footprint whenever vela's NPU-placement line couldn't be read, instead of refusing it (#2312)

`compile()`'s zero-SRAM check read `if npu_ops:` on `_parse_vela_placement()`'s
result, and `None` (the line absent from vela's stdout) is just as falsy as
`0` — an unreadable placement line skipped the refusal and shipped
`req_sram_kib = 0` exactly as a genuine full CPU fallback would, and that zero
then passes the on-device fit gate at
`src/backends/inference/alp_model_select.c:95`
("return e->arena_sram_kib == 0u || t->req_sram_kib <= e->arena_sram_kib;")
against ANY arena. `_parse_vela_placement()`
(`scripts/alp_model/adapters/ethos_u.py:182-188` ("def _parse_vela_placement")) now reads BOTH the `CPU` and
`NPU` placement lines vela prints per run, and `compile()`'s check
(`scripts/alp_model/adapters/ethos_u.py:262`
("if npu_ops != 0:")) refuses unless the NPU count was read AND is exactly
`0` — a confirmed full CPU fallback. An unreadable line is fail-closed, not
silently zero.

### Fixed — every compile target shared one output directory, so a stale summary CSV from a different accel_config could be read as this run's footprint (#2312)

`build_model()` (`scripts/alp_model/build.py`) reuses one `out_dir` across
every target a SoM declares, and `_parse_vela_summary()` globbed
`out_dir.glob(f"{stem}_summary_*.csv")` and took `sorted(matches)[0]` — right
only by accident of sort order. A summary CSV left over from a different
accel_config's compile (or planted by another process) answered for this
one's `req_sram_kib`. `VelaAdapter.compile()` now compiles each accel_config
into its own subdirectory of `out_dir`
(`scripts/alp_model/adapters/ethos_u.py:104-113` ("def _run_dir"), `_run_dir`), so a sibling
target's output is never glob-visible to this run, and
`_parse_vela_summary()` (`scripts/alp_model/adapters/ethos_u.py:137-160`
("missing, unparseable, or AMBIGUOUS")) now
refuses (returns `(0, 0)`, composing with the placement-fail-closed fix above)
when more than one `*_summary_*.csv` matches inside a run's own directory,
rather than guessing which one is this run's.

### Fixed — the ethos_u adapter ran vela with no memory profile at all rather than refuse, silently compiling against vela's own DRAM-backed default (#2312)

`compile()` accepted a `target=None` or a `TargetSpec` with an empty
`vela_memory_mode` and simply omitted `--memory-mode`/`--system-config` —
vela then falls back to `Ethos_U85_SYS_DRAM_Mid` / `Dedicated_Sram_384KB` and
reports the working set in `dram_memory_used` on a part that may have no DRAM
at all. `compile()`
(`scripts/alp_model/adapters/ethos_u.py:236-245` ("no vela memory profile for")) now raises a `RuntimeError`
naming the missing `npu_toolchain.vela.memory_mode` up front instead.
`build_model()` always threads a real, resolved `TargetSpec` (`target=spec`,
`scripts/alp_model/build.py:100` ("opts=backend_opts, target=spec)")), so no production caller is affected; this
closes the gap for direct/test callers that built one by hand.

### Fixed — a named `system_config` waited for `ALP_VELA_CONFIG` even when the SoC spec said it needed no vendor file (#2312)

`TargetSpec.vela_system_config` carried a `system_config` name unconditionally
and `_profile_flags()` always withheld `--system-config` until a vendor `.ini`
was on hand via `ALP_VELA_CONFIG` — ignoring
`npu_toolchain.vela.system_config_requires_vendor_config`
(`metadata/schemas/soc-spec-v1.schema.json`). `TargetSpec` now splits the name
into two fields by that flag: `vela_system_config` (a built-in Arm
`System_Config`, safe to pass alone) and `vela_vendor_system_config`
(vendor-gated, passed only alongside `--config` when
`ALP_VELA_CONFIG` names a readable file) —
`scripts/alp_project_loader.py:727-750` (`_soc_targets`). `_profile_flags()`
(`scripts/alp_model/adapters/ethos_u.py:116-133` ("def _profile_flags")) passes the former
unconditionally and the latter only with its vendor file. No shipped SoC spec
names a `system_config` today (every Alif Ensemble part and the NXP i.MX 93
leave it unset), so this is latent, not a behaviour change for any part in
metadata/ yet.

### Fixed — the zero-SRAM refusal said "zero SRAM working set in any memory area" even though the measured DRAM figure was nonzero (#2312)

The refusal message (`_refuse_zero_sram_footprint`,
`scripts/alp_model/adapters/ethos_u.py:191-215` ("def _refuse_zero_sram_footprint")) claimed no memory area
reported a working set at all; measured, a defaulted profile reports
`dram_memory_used = 0.28125` for the exact model the refusal fires on — the
SRAM figure is the only one that came back zero. The message now says "zero
SRAM", not "zero SRAM working set in any memory area", and separately reads
"vela's own NPU-operator-placement line could not be read from its stdout, so
this zero cannot be confirmed as a full CPU fallback" for the unreadable-line
case above, rather than crediting an unread `npu_ops` with an operator count.

### Changed — `req_sram_kib` is arena-only by design; the const/weight region is never counted (#2312, tan-cli#1011)

Settles the open question from #2312 (follow-up to #1470): `perf.req_sram_kib`
/ the `.alpmodel` manifest's `Target.requires.sram_kib` count the compiled
tensor **arena** alone (vela's `sram_memory_used` column), never the
const/weight region (vela's `on_chip_flash_memory_used` column). The const
region is carried in the model blob itself and sized by the blob's own byte
length (`blob_len`), provisioned by the integrator per the target's
`vela_memory_mode` placement — it is never summed into `req_sram_kib`. No
schema field changed and no `.alpmodel` version bump; the on-device selector
at `src/backends/inference/alp_model_select.c:95`
("return e->arena_sram_kib == 0u || t->req_sram_kib <= e->arena_sram_kib;")
is unchanged, comparing the arena against the arena as it always has. This is
the SAME contract tan-cli records for its own adapter (tan-cli#1011) and the
SRAM-port pinning in `src/backends/inference/ethos_u_aen.cpp`; it is not a
port of tan-cli's `_footprint()` implementation, which additionally reads
every memory area and a DRAM-declared-or-not caveat this adapter does not
carry. Documented in `docs/bench/model-perf-capture.md` and
`metadata/schemas/model-perf-v1.schema.json`'s `perf.req_sram_kib`
description.

### Documented — `ALP_VELA_CONFIG` (the vendor vela profile env var) has a customer-facing home in the docs (#2312)

`docs/reference/model-compile-backends.md` (Ethos-U/vela section) and
`vendors/nxp-imx93/README.md` now name `ALP_VELA_CONFIG` alongside the
`memory_mode`/`system_config` profile fields it complements: it points at a
customer's own vendor vela `.ini` (e.g. Alif's `ensemble_vela.ini`), which
alp-sdk does not redistribute.
