### Fixed — `alp_gpio_write()` (and every other op) on a closed pin answered NOT_READY on Zephyr and INVAL on Yocto (#1734)

`src/yocto/peripheral_gpio.c` gated every GPIO op on `pin == NULL || !pin->in_use`
and returned `ALP_ERR_INVAL` for both a NULL handle and a closed (non-NULL,
`in_use == false`) one, while every Zephyr dispatcher -- and ADR-0002's
2026-08-27 amendment recording the convention -- treats a NULL-or-closed
handle as a lifecycle condition and returns `ALP_ERR_NOT_READY`. The same
public symbol, `alp_gpio_write(closed_pin, ...)` among them, answered
differently depending on which backend the build selected.

`alp_gpio_configure`, `alp_gpio_write`, `alp_gpio_read`, `alp_gpio_irq_enable`,
and `alp_gpio_irq_disable` in the Yocto backend now return `ALP_ERR_NOT_READY`
for a NULL-or-closed pin, matching the Zephyr dispatch layer. Where a
lifecycle check was previously fused into the same condition as a malformed-
argument check (a NULL `level` out-param on read, a NULL `cb` on IRQ enable),
the two are now split: the lifecycle check runs first and short-circuits to
`NOT_READY`, and the malformed-argument check only runs once the handle
itself is known good, still returning `ALP_ERR_INVAL`. `include/alp/peripheral.h`'s
doc comment for `alp_gpio_write` is corrected to state the NULL-or-closed
case explicitly instead of attributing `ALP_ERR_NOT_READY` solely to a pin
not configured as output.

`src/yocto/peripheral_i2c.c`, `peripheral_spi.c`, and `peripheral_uart.c` gated
the same way and returned `ALP_ERR_INVAL` for a NULL-or-closed handle too --
named in ADR-0002's amendment alongside the GPIO case. That divergence is
resolved separately by #1834 (landed independently on `dev`); with both
changes in, all four Yocto peripheral families now match the Zephyr
convention.
