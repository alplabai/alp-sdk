### Fixed — E1M-AEN801's BRD_I2C is SoC I2C0, not the slave-only LPI2C0; unblocks the on-module `rv3028c7` RTC (#1848, unblocks #1814)

`BRD_I2C` (the on-module housekeeping bus carrying the RV-3028-C7 RTC, the
OPTIGA Trust M secure element, and the TMP112 temperature sensor) was
documented, and wired nowhere, on the assumption that it sat on the Alif
LPI2C0 (`P7_4`/`P7_5`) -- a bus the SoC can only be a *slave* on (TRM
§3.17.4, hardcoded slave address `0x40`), so those three parts were treated
as Tier-3 SE-mediated and unreachable as an ordinary I2C master.

That routing was wrong. `BRD_I2C_SCL`/`BRD_I2C_SDA` land on SoC pins
`P7_1`/`P7_0` (the `E1M-AEN-2626-R2` netlist, balls B3/B8); Alif's
`ADTS0013` v1.2 Table 3-16 gives those pads the alternate function
`I2C0_SCL_C`/`I2C0_SDA_C` -- **SoC I2C0**, one of the four shared-peripheral
I2C modules the HWRM (§15.4.1) documents as master-or-slave capable, not
LPI2C0. The M55 masters BRD_I2C directly, the same as any Tier-1 upstream
`i2c_dw` bus.

**What changed:**

- `zephyr/dts/alif/ensemble_e8_peripherals.dtsi` -- corrects the LPI2C0/i2c0
  comment blocks; no behavior change to the SoC-level node population.
- `examples/aen/aen-secure-element-sign`'s board overlay -- adds the
  `pinctrl_i2c0` group (`I2C0_SCL_C`=P7_1, `I2C0_SDA_C`=P7_0), enables
  `&i2c0`, and aliases it to **portable bus 2** (`alp-i2c2`, not 0) --
  0 and 1 are already the E1M edge I2C buses (`BOARD_I2C_SENSORS` /
  `EVK_I2C_BUS_DSI_CSI`), and this SoM's own board files already default
  `alp-i2c0` to the EVK sensor bus in other projects (e.g.
  `aen-eeprom-manifest`), so BRD_I2C could not reuse bus 0 without
  silently repointing the stock `i2c-scanner`/`i2c-master` examples at a
  bus carrying a secure element. Only the HE overlay wires it -- HP never
  touches `&i2c0`, so the two cores never race the same controller. The
  generated E1M-AEN801 SoM board files are UNCHANGED: this SoM's on-module
  buses are wired per-example, matching the existing I2C2/EEPROM
  convention, not baked into the shared board file.
- No `bias-pull-down` (deliberately High-Z instead): the R2 components CSV
  shows this net's pull-up jumpers (R93/R94) DNP, unlike I2C2/EEPROM's
  (R95/R96, stuffed) -- a pull-down here would park the bus low through the
  pad's own ~50 kOhm Rpd. Whether that even matters is an open question the
  datasheet and the HWRM disagree on (open-drain needing a pull-up vs.
  push-pull by design); see the overlay's pinctrl comment and the ADR
  amendment. Do not add a bias without a bench answer.
- `metadata/e1m_modules/E1M-AEN801.yaml` -- `on_module.i2c_devices.brd_i2c`
  now carries `bus_master: alif-ensemble` and a corrected, cited comment.
  The five sibling AEN presets (301/401/501/601/701) share this SoM PCB but
  keep `bus_master` OMITTED, pending a per-part datasheet check that their
  Alif silicon variant backs `I2C0_SCL_C`/`I2C0_SDA_C` the same way --
  their stale "SE masters it" comments are corrected without asserting the
  routing for them.

**Not done here, and said plainly:** this is bus plumbing, not RTC-source
selection. The AEN calendar backend (`src/backends/rtc/lprtc_calendar_shim.c`,
selected by `silicon_ref` on `alif:ensemble:e8`) still wins dispatch over the
now-reachable `rv3028c7` -- wiring the RTC dispatcher to prefer the external
part when BRD_I2C is present, with the internal LPRTC as documented fallback,
is a separate, larger change and is not part of this fix.

**Verification status: R2-sourced, NOT bench-verified.** Every routing fact
above comes from the `E1M-AEN-2626-R2` netlist + `ADTS0013` v1.2. No R1
netlist is available, and the only AEN801 bench unit on hand identifies as
r1 (`alp board` -> `E1M-AEN801 r1`, serial `2617-0001`). Probe `P7_0`/`P7_1`
on that unit before treating BRD_I2C as confirmed there -- both the pad
routing and the pull-up question above it are open until that probe runs.
`OPTIGA` also lives on this bus at `0x30` -- do not blind-scan it; probe
known addresses only.

**Bench-settled 2026-08-31** on the r1 module (`E1M-AEN801`, serial `2617-0001`),
`i2c0` at 100 kHz, read-only `i2c_write_read` of register `0x00`:

| pad bias | result on `0x48` (TMP112), `0x52` (RV-3028-C7), `0x30` (OPTIGA) |
|---|---|
| High-Z, no bias | `rc=-116` (`-ETIMEDOUT`) with `E: User Abort on i2c@49010000` |
| same build + internal pull-up (~50 kΩ) | `rc=-5` (`-EIO`), no abort |

A bias-only edit changing the error class proves the pinctrl is correct and the
controller reaches the wire, and that the net has **no usable pull-up**. It also
settles the open-drain question against the HWRM's push-pull note: had these pads
driven push-pull, the High-Z run would have worked. The I2C IP tri-states for the
high phase, so an **external pull-up is required**. Nothing ACKed under the internal
pull-up either, which is expected — ~50 kΩ is far too weak for 100 kHz rise time.

**So this bus is not usable as built.** It needs `R93`/`R94` stuffed — bridging
BRD_I2C into the segment the carrier already pulls up via `R137`/`R144` — or
dedicated pull-ups on the net. That is a board change, not a firmware one, which is
why #1814 stays open.
