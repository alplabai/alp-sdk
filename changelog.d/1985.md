### Fixed — `cc3501e_wifi_ap_start()`'s role-confirmation loop now bounds by wall time, not a manual sleep-only budget (part of #1985)

Follow-up to #1953, which fixed the identical antipattern in
`poll_by_repeat()` (`chips/cc3501e/cc3501e_core.c`) but deferred two call
sites that ran the same pre-fix shape. This lands one of the two:
`cc3501e_wifi_ap_start()`'s GET_DIAG_INFO role-confirm loop in
`chips/cc3501e/cc3501e_wifi.c`. The loop tracked a `uint32_t remaining`
budget by hand: a successful-but-not-yet-AP read debited only the 50 ms
`CC3501E_WIFI_STATUS_POLL_GAP_MS` gap it slept for, and a *failed* read
debited a defensive ESTIMATE of the attempt's worst-case cost
(`CC3501E_REQ_TMO_MS`, 100 ms) instead of what the attempt actually took —
`cc3501e_request()` does not itself bound an attempt to `CC3501E_REQ_TMO_MS`,
so nothing capped how long a genuinely hung attempt could run. Same false "a
read either costs nothing or costs its declared worst case" premise #1953
disproved for `poll_by_repeat()` itself.

**Converted to the `alp_uptime_ms()`-deadline shape** `poll_by_repeat()`
already uses: a deadline read once at entry (`alp_uptime_ms() + timeout_ms`),
a real-time check after every attempt (`now_ms >= deadline_ms`), and the
final back-off gap clamped to whatever's left before the deadline — no more
`attempt_cost` estimate. The loop keeps its existing fixed 50 ms cadence
(`CC3501E_WIFI_STATUS_POLL_GAP_MS`); it did not grow the exponential
back-off `poll_by_repeat()` itself uses, since that constant already existed
specifically to duplicate `poll_by_repeat()`'s cadence for a *different*
opcode (GET_DIAG_INFO) than the one it bounds (WIFI_AP_START).

**Quantified, not just asserted, what changes:** the old manual accounting
deliberately over-charged every failing iteration relative to real wall
time — 100 ms phantom `attempt_cost` plus the real 50 ms gap = 150 ms
debited per iteration, against the ~50 ms that (in this repo's own
fake-clock host harness, where a failed attempt costs 0 simulated time)
actually elapsed — so it converged to `ALP_ERR_TIMEOUT` faster than real
time, making fewer GET_DIAG_INFO attempts than a real deadline permits for
the same declared `timeout_ms` against a permanently wedged transport.
Measured directly (both directions of a mutation test: the converted loop
reverted to its pre-fix shape, run, then restored) against
`tests/zephyr/cc3501e_host_driver`'s fake-clock harness, `timeout_ms = 200`,
`CC3501E_REQ_TMO_MS = 100`, gap = 50 ms:

| | GET_DIAG_INFO attempts | budget accounted per iteration |
|---|---|---|
| pre-fix (manual `remaining -=`) | 2 | 150 ms (100 ms phantom + 50 ms real) |
| post-fix (`alp_uptime_ms()` deadline) | 5 | 50 ms (real gap only) |

This loop makes no read before entering the loop, so the post-fix count has
a clean closed form: exactly `ceil(timeout_ms /
CC3501E_WIFI_STATUS_POLL_GAP_MS) + 1` every time (200 -> 5, 10000 -> 201).
This does not change how long `timeout_ms` bounds the call to (both models
still return `ALP_ERR_TIMEOUT` no later than the caller's declared budget),
only how many GET_DIAG_INFO frames land on the wire while getting there.

**No accounting difference on a healthy poll:** the pre-fix code already
charged a successful-but-non-AP read nothing extra, and the deadline model
preserves that — a healthy multi-poll AP role-up still spends only its real
gap time either way.

**Tests:** added `test_wifi_ap_start_bounds_diag_attempts_on_wedged_
transport_1985` to `tests/zephyr/cc3501e_host_driver/src/test_host_driver.c`,
against a new `g_diag_io_down_remaining` / `slave.diag_info_attempt_count`
fixture pair (the GET_DIAG_INFO analogue of the existing
`g_status_io_down_remaining` / `slave.wifi_status_attempt_count` used for
WIFI_STATUS), asserting the exact `== 5u`. Mutation-proven: reverting the
loop to its pre-fix `remaining -=`/`attempt_cost` shape drops the count to
2 and reddens the assertion; restoring the fix turns it green again at 5.

**`cc3501e_wifi_connect()`'s identical WIFI_STATUS antipattern is NOT
touched by this change** — it is being converted separately, on real
E1M-AEN801 silicon, on `feat/2035-cc3501e-wedge-and-throughput`. That
branch's derivation independently confirms the same `alp_uptime_ms()`
approach and the same category of off-by-one this change ran into on the
ap_start side (an unconditional pre-loop read that adds one to the closed
form). #1985 is not fully closed until that half lands too.

**Bench-owed:** this touches `chips/cc3501e/cc3501e_wifi.c`, held per #1937.
The CC3501E is activated only on `e1m-aen-evk-01`, which is not among the
boards reservable for this work this session — no silicon measurement backs
the attempt-count table above, which is native_sim / host-harness only, same
caveat #1953 already carries for `poll_by_repeat()` itself.
