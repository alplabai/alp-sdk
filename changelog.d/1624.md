### Fixed — GD32 bridge PWM backend never resolved the "use DT default" period, so every non-zero duty on V2N/V2M failed `ALP_ERR_INVAL` (#1624)

`src/backends/pwm/gd32_bridge.c`'s `br_open()` wrote `cfg->period_ns`
verbatim into both its private channel state and the dispatcher-owned
`struct alp_pwm::period_ns` field that `alp_pwm_set_duty()` bounds-checks
`pulse_ns` against. `include/alp/pwm.h` documents `period_ns == 0` as "use DT
default" — the value `ALP_PWM_CONFIG_DEFAULT()` produces — but the bridge has
no devicetree to resolve it against, so a caller using the canonical default
config still ended up with `period_ns == 0` and every non-zero duty request
on E1M-V2N101/102 and E1M-V2M101/102 was rejected as out of range.

`br_open()` now resolves `period_ns == 0` to 1 kHz before writing it to
either field, matching the fallback the `sw_fallback` and `yocto_drv` PWM
backends already use.

Regression test: `tests/unit/pwm_gd32_bridge_period/`.
