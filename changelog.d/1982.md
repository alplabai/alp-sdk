### Fixed — the orchestrator no longer emits `bitbake alp-image-edge` for a MACHINE that cannot build (#1982)

Five SoM presets declare the A32 cluster's stock app as the `STOCK_IMAGE_APP` token
(`alp-image-edge`): `metadata/e1m_modules/E1M-AEN{501,601,701,801,803}.yaml`. Every one of them,
`scripts/alp_orchestrate/orchestrator.py` turned straight into a `bitbake alp-image-edge` /
`MACHINE = "<machine>"` build-plan command — silently, because the stock-image token is
deliberately exempt from the `recipe:` requirement that would otherwise flag an app-only Yocto
slice. All five MACHINEs are known-non-buildable, split into two failure classes (do not conflate
them): `e1m-aen801-a32` / `e1m-aen701-a32` ship a `meta-alp-sdk/conf/machine/*.conf` whose `require`
is either broken (#1968: names a file absent from every branch of the public meta-alif-ensemble) or
commented out pending that layer being vendored at all; `e1m-aen501-a32` / `e1m-aen601-a32` /
`e1m-aen803-a32` ship **no conf at all**, strictly more unbuildable since BitBake fails before it
can parse a single `require`. All five sit on a meta-alif-ensemble base that is Yocto-series-
incompatible with this repo's Scarthgap baseline regardless (#1971) — so every project naming any
of these five SoMs' A32 cluster received a confidently-emitted command that could not have
succeeded. E1M-AEN803 is the bench module #1982 itself names.

`_slice_command` now refuses all five MACHINEs before considering `image:`/`app:`/`recipe:` at
all, raising a new `UnbuildableYoctoMachineError` that `emit_build_plan` turns into a
`command: null` slice plus a `yocto-machine-unbuildable` warning naming the blocking issues and
#264 — the same "carry the slice, never emit a broken command" convention `board-tree-missing`
and `command-unrooted` already use. The `STOCK_IMAGE_APP` exemption comment now says explicitly
that it assumes the image recipe is buildable for the slice's MACHINE. A new self-cleaning CI gate,
`scripts/check_yocto_machine_tree_parity.py`, consults this SAME denylist (`YOCTO_MACHINE_UNBUILDABLE`)
so a sixth SoM with a still-missing conf can never fall through undeclared.

The two `tests/parity/oracle/*.build-plan.json` fixtures affected (`multicore_rpmsg-aen`,
`audio_i2s-tone`, both via `E1M-AEN801`) are re-frozen at their `a32_cluster` slice's `command` ->
`null` plus the new warning — the same class of hand-reviewed oracle correction alp-sdk#999 made
for `board-tree-missing`, recorded in `tests/parity/oracle/ORACLE-PROVENANCE.txt` — rather than a
seam-1 comparator allowance, per ADR-0020's own post-mortem of why that shortcut is the failure
mode to avoid. Every emit-snapshot fixture and unit test whose plan included an AEN801 A32-cluster
slice (no shipped example uses the other four SKUs) was regenerated/updated to reflect the new
`command: null` + warning shape.

**This does not close #1968 or #1971** (the underlying layer/machine-conf defects, owned by #264's
rebuild) — it only stops the planner from handing out a command it already knows cannot succeed.
