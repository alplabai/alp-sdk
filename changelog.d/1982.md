### Fixed — the orchestrator no longer emits `bitbake alp-image-edge` for a MACHINE that cannot build (#1982)

`metadata/e1m_modules/E1M-AEN801.yaml` and `E1M-AEN701.yaml` declare the A32 cluster's stock app as
the `STOCK_IMAGE_APP` token (`alp-image-edge`), which `scripts/alp_orchestrate/orchestrator.py`
turned straight into a `bitbake alp-image-edge` / `MACHINE = "e1m-aen801-a32"` build-plan command —
silently, because the stock-image token is deliberately exempt from the `recipe:` requirement that
would otherwise flag an app-only Yocto slice. Both `e1m-aen801-a32` and `e1m-aen701-a32` are
known-non-buildable MACHINEs, for related but distinct proximate reasons (#1968 for AEN801's
active `require` on a file absent upstream; AEN701's own `require` is already commented out
in-tree pending the layer being vendored at all) and one shared structural reason regardless
(#1971) — so every project naming either SoM's A32 cluster received a confidently-emitted command
that could not have succeeded.

`_slice_command` now refuses these two MACHINEs before considering `image:`/`app:`/`recipe:` at
all, raising a new `UnbuildableYoctoMachineError` that `emit_build_plan` turns into a
`command: null` slice plus a `yocto-machine-unbuildable` warning naming the blocking issues and
#264 — the same "carry the slice, never emit a broken command" convention `board-tree-missing`
and `command-unrooted` already use. The `STOCK_IMAGE_APP` exemption comment now says explicitly
that it assumes the image recipe is buildable for the slice's MACHINE.

Every emit-snapshot fixture and unit test whose plan included an AEN801 A32-cluster slice (no
shipped example uses AEN701) was regenerated/updated to reflect the new `command: null` + warning
shape.

**This does not close #1968 or #1971** (the underlying layer/machine-conf defects, owned by #264's
rebuild) — it only stops the planner from handing out a command it already knows cannot succeed.
