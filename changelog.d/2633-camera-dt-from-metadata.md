### Changed — the V2N/V2M Linux camera devicetree and kernel config are generated from metadata (#2633)

`scripts/gen_camera_dt.py` writes `meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-x-evk-<connector>-<module_id>.dtsi` for every carrier camera connector x camera module that fits it, plus `camera-sensors.cfg`, from `metadata/camera_modules/*.yaml`, each chip's `drivers.linux`, the board's `camera_connectors`, the SoM `pad_routes` and the SoC `linux_dt` (`--check` exits 1 on drift). Adding a camera is now a metadata-only change plus a regeneration. `scripts/check_camera_parity.py` (registered as `camera-parity`, run by `pr-metadata-validate.yml`) fails when a committed generated file drifts, is missing, or outlives its module. The SoC JSON gains `linux_dt.CSI0.kconfig` (the receiver and capture drivers), which the schema documents.

The bbappend's per-sensor switches are gone: `ALP_ENABLE_CAM0_IMX219` and `ALP_ENABLE_CAM0_OV9281` are replaced by one `ALP_CAMERA_CAM0 = "<module_id>"` (declared at `meta-alp-sdk/recipes-kernel/linux/linux-renesas_%.bbappend:418` ("ALP_CAMERA_CAM0 ??=")), which an unknown id rejects at parse time and lists the valid ids. The hand-written `e1m-x-evk-cam0-imx219.dtsi` and `e1m-x-evk-cam0-ov9281.dtsi` and the opt-in `camera-csi.cfg` are deleted. `camera-sensors.cfg` is merged unconditionally on every V2N/V2M machine and builds the CSI-2 receiver, the CRU and every module's sensor driver in (the images install no kernel-modules), so no per-sensor kernel config line is kept by hand.

Behaviour differences from the hand-written fragments, all read from metadata: the sensor `*-supply` properties bind to a fixed always-on 3.3 V regulator node (the connector's `supply: fixed-3v3`) instead of logging dummy regulators; every module on CAM0 gets the connector's `lane-polarities` (`lane_polarity: [1, 1, 1]`, bench-proven only with the OV9281 module, so the IMX219 path is more exposed to that assumption than before); the OV9281 node keeps the chip's `compatible = "ovti,ov9282"` and its gated clock lane (`clock-noncontinuous`). The CAM0 enable and reset stay unmodelled because their SoM routes are `TBD`; each fragment's header says so. `clock-noncontinuous` is ignored by the native 6.1 driver (it always writes the gated clock, `0x4800 = 0x20`) and required by the v6.6 backport of patch `0030`. A module gets a fragment, and its sensor driver a `camera-sensors.cfg` line, only when `metadata/os/linux-kernel-drivers.yaml` says the kernel can serve it (driver native, or its patch file present), so `ALP_CAMERA_CAM0` only offers modules the kernel can serve: the IMX296 (`raspberry_pi_global_shutter_camera`, patch `0028`) and the 2-lane IMX335 (patch `0029`) are offered because those patches are present. The IMX296 fragment names `sony,imx296lq` (new optional `linux_compatible` in the camera-module schema), which is the bench-proven node on E1M-V2M103 CAM0/J5 (IMX296LQ, 60 fps, `SBGGR10_1X10` 1456x1088, zero CSI/CRU errors over 300 frames; colour / AWB not tuned) and does not depend on the auto-identify settle delay patch `0028` adds. Because `camera-sensors.cfg` is merged unconditionally, the default V2N/V2M kernel now builds the CSI-2 receiver, the CRU and every listed sensor driver even on images with no camera selected. The OV9281 bench proof on V2M103 predates the generated fragment, which adds the supply nodes and `clock-noncontinuous`; that path needs a re-bench. Every generated fragment compiles with dtc against both cam0 wrapper dts; bitbake was not run and no hardware was available. The project `cameras:` to `ALP_CAMERA_CAM0` emit is not part of this change.
