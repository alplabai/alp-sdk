### Fixed — AEN examples no longer cycle the supply of a running CC3501E on bring-up (#2797)

The shared `cc3501e_bridge_bringup()` template (`examples/aen/aen-cc3501e-bringup/src/cc3501e_bridge.c` and every synced copy) ended with `cc3501e_reset()`, which drops `WIFI_EN` (P15_5) for 50 ms. Re-running or warm-resetting any example on an activated unit (`vendor_sbl_container_enable=1`) therefore cold-cycled the CC3501E supply, a path that may never relaunch its firmware. The template now carries the warm-aware bring-up first written for `aen-power-domains`: it latches `WIFI_EN` high in the GPIO data register before the direction change, so the pad cannot glitch low; when `WIFI_EN` reads high and the chip answers a PING it resets through nRESET only (`cc3501e_hard_reset()`); it uses `cc3501e_reset()` only from `WIFI_EN` low, or as a last resort for a chip that stays silent after an nRESET-only reset. `aen-power-domains` is no longer a declared divergent copy in `scripts/check_cc3501e_bridge_copies.py`, and the trace-runner sound copy carries the same logic. `examples/peripheral-io/alp-console` keeps its own cold-boot soak and is unchanged.
