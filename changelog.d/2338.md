### Fixed — ISP-Pico camera backend forwards the requested fps to every sensor, not just OV5647 (#2338)

`src/backends/camera/alif_isp_pico.c`'s `alp_camera_open()` forwarded the
caller's `alp_camera_config_t::fps` request to a hardcoded
`DEVICE_DT_GET(DT_NODELABEL(ov5647))` sensor device. For every other sensor
behind the ISP-Pico (IMX296, IMX335) the request was silently dropped and the
sensor free-ran at its driver's own default rate: bench run 333, IMX335 ran
at its upstream driver's default 30 fps regardless of the 15 fps
`examples/connectivity/camera-mjpeg-stream` requests on its shared 1280x960
path.

Fixed generically, with no per-sensor DT nodelabel list: `isp_pico.c` gains
`.get_frmival`/`.set_frmival` (forwarding to `config->controller`),
`video_alif.c`'s `alif_cam_set_frmival()` forwards to its endpoint (matching
its existing `alif_cam_get_frmival()`), and `video_csi_dw.c`'s
`csi2_dw_set_frmival()` forwards to the same
`config->sensor[data->current_sensor]` its own `.get_frmival` already reads
— so a 2-sensor CSI node's AE (which reads the rate back through
`.get_frmival`) sees the rate this sets. The backend now just calls
`video_set_frmival(dev, ...)` once on the ISP device itself, which walks the
whole isp -> cam -> csi -> sensor chain through those forwarders and lands on
whichever real sensor is wired. `cfg->fps == 0` still means "backend
default" (10 fps), unchanged. A sensor whose `set_frmival()` can't actually
change the rate (IMX296's all-pixel-scan mode has exactly one fixed 60.3
frame/s — `imx296_set_frmival()` always reports that fixed rate back rather
than erroring) or that returns `-ENOSYS`/`-ENOTSUP` outright (e.g. TPG mode,
no controller wired) now just keeps running at its existing rate, logged at
`INF`, not treated as a failure. The settled rate is still only logged, not
reported back to the caller — `<alp/camera.h>` has no settled-fps field yet
(#2279).

This surfaced a real consequence for IMX335: its `imx335_framerates[]`
(`{25, 30, 50, 60}`) has no 15 fps entry, so `examples/connectivity/
camera-mjpeg-stream`'s shared 1280x960 path would now round that request up
to 25 fps — a rate hal_alif patch 0014's AE envelope (calibrated at exactly
30 fps) was never derived against. Fixed by splitting the requested fps out
of that example's resolution-select Kconfig into its own
`CONFIG_CAMERA_MJPEG_STREAM_FPS` symbol, which the `aen_imx335` scenario in
`testcase.yaml` overrides to 30 via `extra_configs` — no sensor `#if` in the
portable example itself. OV5647 and IMX296 keep the unaffected 15 fps
default: OV5647 reaches it exactly (unchanged), IMX296 stays at its fixed
60.3 frame/s regardless of the request (also unchanged). `isp_pico.c`'s
`isp_apply_ae()`'s existing `CONFIG_VIDEO_ISP_VSI_AE_EXP_TIME_MAX_US_CAP`
backstop (33207 us for IMX335) now also covers this app-level path, not just
a direct `video_set_frmival()` caller bypassing the backend.

Also updated: `docs/camera-shields.md`'s Frame rate section,
`examples/connectivity/camera-mjpeg-stream/README.md`, and
`include/alp/camera.h`'s `fps` doc comment (generalized the OV5647-specific
example, since the behaviour is now sensor-generic).
