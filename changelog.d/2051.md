### Fixed — `sdhc_dwc_reset()` left the DWC SDHC controller unconfigured after a SW_RST_ALL, masking SD enumeration (#2051)

**Partial fix.** This removes a driver-level bug that masked every other SD
enumeration fix on the E1M-AEN803 EVK (E1M EVK 2626-R2); it does **not** close
`SW_RST_R` staying stuck at `0x02` (`SW_RST_CMD`), which is a separate
clock-domain question still under bench investigation and untouched here — no
SoC clock enable, clock-source mux, CGU register, or pinmux was changed.

`sdhc_dwc_reset()` (`zephyr/drivers/sdhc/sdhc_dwc.c:691-743`) issued
`SW_RST_ALL` and returned, with nothing re-running
`sdhc_dwc_set_def_config()` (`zephyr/drivers/sdhc/sdhc_dwc.c:1228-1282`)
afterward. `SW_RST_ALL` resets `NORMAL_INT_STAT_EN`, `ERROR_INT_STAT_EN`,
`HOST_CTRL2`, `PWR_CTRL` and `CLK_CTRL` to POR (`0`); with the interrupt-enable
registers at `0` the controller can never latch a command-complete event, so
every `sdhc_dwc_wait_cmd_complete()` (`zephyr/drivers/sdhc/sdhc_dwc.c:446-479`)
times out and `disk_access_init()` fails with `-116` before it reaches a real
card access. Confirmed on the bench and already documented in the example's own
diagnostics
(`examples/aen/aen-sdcard-readout/src/main.c:341-350`
("a bare SW_RST_ALL (sdhc_dwc_reset()) does NOT re-run set_def_config(), so
calling sdhc_hw_reset() from main() wiped both STAT_EN registers for
nothing")).

`sdhc_dwc_reset()` now re-runs `sdhc_dwc_set_def_config()` whenever the
`SW_RST_ALL` poll actually completes, matching the Alif DFP reference model
(`SW_RST_ALL` immediately followed by re-configuring
power/timeout/interrupts/DMA/clock). This is within the Zephyr
`sdhc_hw_reset()` API contract (upstream Zephyr's own
`include/zephyr/drivers/sdhc.h` — not vendored into this repo, so cited
without a `path:line` here — documents that resetting "should clear all
errors ... but does not necessarily reset I/O settings to boot"). Because
`sdhc_dwc_set_io()`
(`zephyr/drivers/sdhc/sdhc_dwc.c:935-1043`) only reprograms a field when it
differs from the driver's cached `data->ios`, and the Zephyr SD stack itself
never calls `sdhc_hw_reset()` (so it has no reason to re-supply an io struct
that "changed"), the cache is now explicitly invalidated on reset
(`zephyr/drivers/sdhc/sdhc_dwc.c:728-740`) so the next `sdhc_set_io()` actually
reprograms the hardware instead of silently no-op'ing against a stale cache.

Also ported the vendor Linux quirk for this same IP: `sdhc_dwc_hw_reset()`
(`zephyr/drivers/sdhc/sdhc_dwc.c:542-586`) now clears a stale Command Complete
in `NORMAL_INT_STAT_R` after any reset that includes `SW_RST_CMD`, matching
vendor Linux's `ensemble_sdhci_reset()` (`drivers/mmc/host/sdhci-of-dwcmshc.c`
in the vendor tree, not part of this repo, so cited without a `path:line`
here — it clears the response-complete status "after CMD reset") — without
it, a later command's `sdhc_dwc_wait_cmd_complete()` could return success on
the old, stale event instead of waiting for its own. A reset-poll timeout now
also names which `SW_RST_R` bit(s) are still set
(`zephyr/drivers/sdhc/sdhc_dwc.c:554-568`) instead of a bare "SDHC reset
timeout", so a stuck `SW_RST_CMD` (this issue's symptom) is distinguishable
from a stuck `SW_RST_ALL` or `SW_RST_DAT`.

`examples/aen/aen-sdcard-readout/src/main.c` keeps its PROBE 2
`sdhc_hw_reset()` diagnostic call as-is; a new comment
(`examples/aen/aen-sdcard-readout/src/main.c:356-368`) records that with this
driver fix the call no longer strips the interrupt-enable configuration
`disk_access_init()` depends on when the reset itself succeeds, while still
correctly leaving the controller unconfigured on a genuine reset timeout (its
state is not trustworthy either way in that case) — so the probe remains a
fair test of the still-open clock-domain theory.

No `tests/` target exercises `sdhc_dwc` (no native_sim/ztest harness for this
driver exists); a fake-register harness for the DWC SDHC controller would be a
large new test fixture on its own and was not built here.
