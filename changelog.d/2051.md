### Fixed — the SD peripheral clock gate was never enabled; hardened the DWC SDHC reset path (#2051)

**Card enumeration is out of scope here and cannot pass on the E1M-EVK
2626-R2.** The maintainer confirmed (2026-09-13) that board's SDIO mux stage
(74LVC157, `U38`/`U39`) is hardware-defective, and its netlist
(`metadata/boards/e1m-evk/netlists/E1M-EVK-2626-R2_pinmap.csv`) shows every
mux OUTPUT drives a SoC-facing net (`E1M_D3/D2/D1/D0`, `E1M_SDIO_RST`,
`E1M_CLK`, `E1M_CMD`). With `MUX_EN` asserted, a mux stuck driving those
outputs fights the SoC's own drivers on the same pads. So
`examples/aen/aen-sdcard-readout` and `examples/aen/aen-evk-demo`'s SD phase
no longer assert `MUX_EN` or drive `SD_RST` at all on this board, and never
reach `disk_access_init()`
(`examples/aen/aen-sdcard-readout/src/main.c:1037-1050` ("do NOT assert the SDIO mux ENABLE on this"),
`examples/aen/aen-evk-demo/src/main.c:2775-2778` ("do NOT assert the SDIO mux ENABLE on this board, and")).
Both examples' READMEs are updated to match.

**Root cause: `CLKCTL_PER_MST.PERIPH_CLK_ENA` bit 16 (`SDC_CKEN`) was never
gated on**, so the DWC SDHC block was entirely unclocked — every register,
including read-only `CAPABILITIES1`, read `0x00000000`. Fixed by moving the
`sdhc0` node (previously duplicated identically in both example overlays)
into the shared SoC dtsi with a `clocks = <&clockctrl ALIF_SDC_CLK>;`
property
(`zephyr/dts/alif/ensemble_e8_peripherals.dtsi:653-660` ("sdhc0: sdhc@48102000 {")),
a new clock id
(`zephyr/include/zephyr/dt-bindings/clock/alif-ensemble-clocks-ext.h:70-88` ("SD/SDMMC peripheral clock gate")),
and a `clock_control_on()` call as the first action in `sdhc_dwc_init()`
(`zephyr/drivers/sdhc/sdhc_dwc.c:1349-1380` ("Step 0 -- the peripheral clock")),
using the same `alif,clockctrl` mechanism other Alif peripherals in this
tree already use. Does **not** touch CGU (`0x1A602014`, Secure-Enclave-owned).
**This explains the all-zero evk-03 readback only** — it does not close the
original open question, a `SW_RST_CMD`=1 reading on a block this file's own
earlier samples show was clocked
(`examples/aen/aen-sdcard-readout/src/main.c:393-412` ("the PROPOSED MECHANISM above is not the")).
**Nothing in this fix has been run on real hardware as of this head** —
expected, not bench-confirmed; the ext-header entry says so explicitly.

**Reset-path hardening**, found while chasing the symptom before the clock
gate was identified: `sdhc_dwc_hw_reset()` now polls only the reset bit(s)
it wrote (`& reset_mask`) and names which bit is stuck on a timeout
(`zephyr/drivers/sdhc/sdhc_dwc.c:551-588`); `sdhc_dwc_reset()` reconfigures
and syncs its `data->ios` cache even on a timeout, now under `data->lock`,
and on either failure zeroes the cache (instead of leaving it stale, or
guessing an unsettled register's value) and returns whichever failure is
more fundamental
(`zephyr/drivers/sdhc/sdhc_dwc.c:693-789` ("static int sdhc_dwc_reset(const struct device *dev)"));
`sdhc_dwc_set_io()` now takes the same lock for its whole read-modify-write
(`zephyr/drivers/sdhc/sdhc_dwc.c:981-1108` ("static int sdhc_dwc_set_io(const struct device *dev, struct sdhc_io *ios)")).
Net effect versus `dev`: `sdhc_dwc_init()` calls `sdhc_dwc_reset()` once, as
it always did; the difference is that `reset()` itself now also runs
`set_def_config()`, so there is exactly one reconfigure pass at boot, not
two — an earlier revision of this fix briefly had, and removed, a genuine
duplicate call, and a stale-Command-Complete-clear that turned out to fix
nothing here; neither shipped and neither is described further.

**Also:** `zephyr/dts/bindings/sdhc/snps,dwc-sdhc.yaml` documents the new
optional `clocks` property (`:56`); `zephyr/kconfigs/vendor-alif-peripherals.kconfig`
makes `SDHC_DWC` `select CLOCK_CONTROL` only when a node declares one
(`:431`); `.github/workflows/pr-twister-aen.yml`'s path filters gained
`zephyr/dts/alif/**` and `zephyr/include/zephyr/dt-bindings/clock/**`
(`:89-90`, `:107-108`).

No `tests/` target exercises `sdhc_dwc`; a fake-register harness for the DWC
SDHC controller would be a large new test fixture on its own and was not
built here.
