### Fixed — the SD peripheral clock gate was never enabled, so the DWC SDHC block was entirely unclocked (#2051)

**This does not make a card enumerate on the E1M-EVK 2626-R2.** The
maintainer confirmed (2026-09-13) that board's SDIO mux stage (74LVC157,
`U38`/`U39`) has a hardware defect and needs a component change before it
will pass the SD signals at all — separate from, and on top of, everything
below. Everything in this fix is real and independently verifiable up to the
controller (`SDC_CKEN` set, `CAPABILITIES1` non-zero, reset bits self-clear,
interrupt enables armed), but a `-116` from `disk_access_init()` or a
`DISK_STATUS_NOMEDIA` on a 2626-R2 EVK past that point is the mux hardware,
not a controller or driver defect this fix (or any other software change)
can close.

**Root cause, found on the bench.** evk-03 (E1M-AEN803, 2026-09-13) readback:
`CLKCTL_PER_MST.PERIPH_CLK_ENA` at `0x4903F00C` read `0x00000000`, and with bit
16 (`SDC_CKEN`) clear, EVERY SDHC register — including read-only
`CAPABILITIES1` at `0x48102040` — read back `0x00000000` too. Neither this
driver nor this SoC's devicetree ever set that bit. The Alif DFP always does,
first thing, before touching the controller at all: `enable_sd_periph_clk()`
(alif-dfp-ref's `sd.c`, line 161), defined as `CLKCTL_PER_MST->PERIPH_CLK_ENA
|= PERIPH_CLK_ENA_SDC_CKEN` (`sys_ctrl_sd.h` line 30, "Enable clock supply for
SDMMC"; the `|=` is at line 40). Fixed by adding an `ALIF_SDC_CLK` id
(`zephyr/include/zephyr/dt-bindings/clock/alif-ensemble-clocks-ext.h:70-84`
("SD/SDMMC peripheral clock gate")), wiring `clocks = <&clockctrl
ALIF_SDC_CLK>;` onto the example's `sdhc0` overlay node
(`examples/aen/aen-sdcard-readout/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay:166-181`
("the real root cause behind")), and calling `clock_control_on()` as the very
first action in `sdhc_dwc_init()`
(`zephyr/drivers/sdhc/sdhc_dwc.c:1309-1340` ("Step 0 -- the peripheral clock")),
using the existing `alif,clockctrl` mechanism
(`clock_control_alif.c`) other Alif peripherals in this tree already use
(e.g. `ALIF_ETHERNET_CLK`) rather than a new one. This does **not** touch CGU
(`0x1A602014`, Secure-Enclave-owned) — that gate (the 100 MHz source select)
was already measured on and is untouched here.

**Secondary hardening in the reset path**, found while chasing the symptom
before the clock gate was identified — real defects, but not what was masking
enumeration on this bench:

- `sdhc_dwc_reset()`
  (`zephyr/drivers/sdhc/sdhc_dwc.c:693-768` ("static int sdhc_dwc_reset(const struct device *dev)"))
  now reconfigures via
  `sdhc_dwc_set_def_config()` and syncs its `data->ios` cache even when the
  `SW_RST_ALL` poll times out, matching both references — the DFP's
  `sd_host_init()` never checks `hc_reset()`'s return before continuing, and
  Linux's `sdhci_reset()` is `void`, used the same fire-and-forget way. The
  cache sync writes the exact fields `sdhc_dwc_set_def_config()` programs
  (`SDMMC_CLOCK_400KHZ`, `SDHC_BUS_WIDTH1BIT`, `SD_VOL_3_3_V`,
  `SDHC_TIMING_LEGACY`) instead of an all-`0xff` sentinel, and re-powers the
  rail off if the caller had it off (`sdhc_dwc_set_power(regs,
  SDHC_POWER_OFF)`), matching the model vendor Linux's `sdhci.c` uses (around
  line 209).
- `sdhc_dwc_hw_reset()`
  (`zephyr/drivers/sdhc/sdhc_dwc.c:551-588` ("static int sdhc_dwc_hw_reset(const struct device *dev, uint8_t reset_mask)"))
  now polls only the reset bit(s) it wrote (`& reset_mask`), matching the DFP's
  `hc_reset()` (alif-dfp-ref's `sd_host.c`, line 246) and vendor Linux's
  `sdhci_reset()` (`sdhci.c`, line 222, `& mask`), and a reset-poll timeout
  now names which `SW_RST_R` bit(s) are stuck instead of a bare "SDHC reset
  timeout".
- `sdhc_dwc_init()`
  (`zephyr/drivers/sdhc/sdhc_dwc.c:1391-1402` ("Software reset all. sdhc_dwc_reset() (#2051) already runs"))
  no longer calls
  `sdhc_dwc_set_def_config()` a second time — `sdhc_dwc_reset()` already runs
  it — removing a double `power_delay_ms` sleep and double
  `sdhc_dwc_set_power()` VDD1 toggle at boot (the same defect class as
  `#2058` defect 3). **Boot-path change:** two fewer register-config passes
  and one fewer 5&nbsp;ms `k_msleep` at `POST_KERNEL` init; behaviourally
  equivalent otherwise, since both calls always programmed the same values.
- An earlier revision of this fix added a stale-Command-Complete clear
  (matching a vendor Linux quirk for this IP) to `sdhc_dwc_hw_reset()`; review
  found it fixes nothing here — `sdhc_dwc_send_cmd()` already clears status
  and the CC event before every command it issues — so it was deleted rather
  than kept as dead code.
- `sdhc_dwc_reset()` now takes `data->lock` around the reset/reconfigure/sync
  sequence, serializing it against `sdhc_dwc_request()` (the only other
  holder); confirmed neither of `sdhc_dwc_reset()`'s two callers
  (`sdhc_dwc_init()`, and the public `sdhc_hw_reset()` syscall from app code)
  can run from inside an already-locked `request()`, so this cannot deadlock.

**Example.** `examples/aen/aen-sdcard-readout/src/main.c`'s PROBE 2 used to
WRITE `CLKCTL_PER_MST` bit 16 to test a (vendor-Linux-derived)
clock-source-mux theory against the Alif DFP's plain-enable model — clearing
the very bit this issue's root cause needed set. Bench evidence settled that
question (see above), so PROBE 2 is now READ-ONLY
(`examples/aen/aen-sdcard-readout/src/main.c:788-801` ("confirm the SD peripheral clock gate, READ-ONLY")):
it reads the gate back (expected set now
that `sdhc_dwc_init()` sets it) and still exercises a real `sdhc_hw_reset()` +
CMD0 afterward. The file's own `#2035` investigation comments are updated in
place rather than deleted
(`examples/aen/aen-sdcard-readout/src/main.c:386-405` ("the PROPOSED MECHANISM above was never it")),
preserving the history of what was ruled out and why. The file header and
`examples/aen/aen-sdcard-readout/README.md`'s Status section are also updated
with the mux-hardware note above — the README previously implied the
remaining gap to a card enumerating was purely a controller/driver question,
which is no longer accurate.

No `tests/` target exercises `sdhc_dwc` (no native_sim/ztest harness for this
driver exists); a fake-register harness for the DWC SDHC controller would be a
large new test fixture on its own and was not built here.
