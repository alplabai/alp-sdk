### Fixed — SD peripheral clock gate was never enabled; SD is now disabled entirely on the E1M-EVK 2626-R2 (#2051)

**Renamed:** `examples/aen/aen-sdcard-readout` is now
`examples/aen/aen-sdhc-probe` — the maintainer's call, so the name says
what the app actually is (register-level SD controller probes, inert
until the EVK's SD mux is reworked) rather than implying a working
card-readout path. Every live reference (docs, `testcase.yaml` ids, the
bench app list, the app's own `CMakeLists.txt` project name) moved with
it; only already-released/historical mentions of the old name (e.g. in
other closed issues' own changelog fragments) were left as-is.

**SD is disabled entirely on the E1M-EVK 2626-R2 — a hardware defect, not a
firmware gap.** The 74LVC157 SDIO mux (`U38`/`U39`) has **no
high-impedance state**: with its `/E` ENABLE input HIGH, its Y outputs are
FORCED LOW, not released — this part's datasheet gives no Hi-Z condition
in its function table at all. `U38`/`U39`'s outputs are the **SoC-facing**
nets (`E1M_CLK`, `E1M_CMD`, `E1M_D3..D0`, `E1M_SDIO_RST`), so those nets
are held low by the mux whenever it is powered, **regardless of ENABLE**.
Two in-tree comments previously claimed the opposite (`/E = 1` → Hi-Z,
"isolated, safe-default") — corrected in
`include/alp/boards/alp_e1m_evk.h` and `docs/cc3501e-bridge.md`. Given
that, leaving the SD host controller enabled and merely avoiding the mux
ENABLE write (an earlier revision of this fix) was not enough: applying SD
pinctrl and starting the identification clock at `POST_KERNEL` would still
fight the mux's held-low outputs. `sdhc0` now stays
`status = "disabled"` (the shared SoC dtsi's own default) on both
`examples/aen/aen-sdhc-probe` and `examples/aen/aen-evk-demo`'s board
overlays for this board, so no SD pinctrl is applied and no SDCLK is ever
emitted.

**Pins the firmware now leaves untouched, on both examples:** `P14_1`
(`SD_CLK`), `P14_0` (`SD_CMD`), `P13_0..P13_3` (`SD_D0..D3`), `P14_2`
(`SD_RST`), and E1M `IO20` (the mux ENABLE, → CC3501E `GPIO_26`). In
`aen-sdhc-probe` specifically, the CC3501E inter-chip SPI1 link
(`P14_4..P14_7`), `WIFI_EN`/`E_WIFI.NRST` (LP-GPIO) and `READY` (`P2_6`)
are ALSO untouched now — removed from the overlay entirely, not merely
undriven, once the bridge bring-up they existed for was dropped from
`main()` (see above). **Still muxed to a peripheral:** `aen-evk-demo`'s
other thirteen phases are unaffected, including its own use of the same
CC3501E bridge (phase 8) for Wi-Fi/BLE.

**Root cause, still real and still fixed independent of the above:**
`CLKCTL_PER_MST.PERIPH_CLK_ENA` bit 16 (`SDC_CKEN`) was never gated on, so
the DWC SDHC block was entirely unclocked — every register, including
read-only `CAPABILITIES1`, read `0x00000000`. Fixed by declaring `sdhc0`
once, in the shared SoC dtsi with `clocks = <&clockctrl ALIF_SDC_CLK>`
(`zephyr/dts/alif/ensemble_e8_peripherals.dtsi:653` ("sdhc0: sdhc@48102000 {")),
and calling `clock_control_on()` as the first action in `sdhc_dwc_init()`
(`zephyr/drivers/sdhc/sdhc_dwc.c`). **This explains the all-zero
readback on E1M-AEN803 serial 2026W36-0002 only** — it does not close the original open question, a
`SW_RST_CMD`=1 reading on a block this app's own earlier diagnostics show
was clocked. **Nothing here has been run on real hardware as of this
head.**

**Reset-path hardening**, found while chasing the symptom before the clock
gate was identified: `sdhc_dwc_hw_reset()` polls only the reset bit(s) it
wrote and names which bit is stuck on a timeout; `sdhc_dwc_reset()`
reconfigures and syncs its `data->ios` cache even on a timeout, under
`data->lock`, and on failure now sets the cached clock to `UINT32_MAX`
rather than `0` — `0` is itself a real, requestable "disable the clock"
value, so leaving it there could make a later real request for `0` compare
equal to the invalidated cache and skip reprogramming
(`zephyr/drivers/sdhc/sdhc_dwc.c:772-786`); `sdhc_dwc_set_io()` takes the
same lock for its whole read-modify-write.

**Example rework.** Both examples' overlays drop the now-pointless `P14_2`
GPIO mux group, the `gpio14` enable, and (in `aen-sdhc-probe`) the
`alp,pin-array` `SD_RST` slot. `aen-sdhc-probe`'s probes are now
compile-time conditional on `sdhc0` being enabled
(`examples/aen/aen-sdhc-probe/src/main.c:319` ("int main(void)")) — with
it disabled (as on this board), `main()` compiles down to the clock-gate
proof below rather than the full probe set. The CC3501E bridge bring-up,
PING wait, meta handshake, and SE clock-cycle diagnostic are removed
entirely from this app: nothing downstream needs the bridge once the mux
is never touched.

**Clock-gate proof, added after review, still pad-free.** The fix above
(`clock_control_on()` in `sdhc_dwc_init()`) had not been run on real
silicon on any previous head of this branch, and `sdhc0` staying disabled
means the normal probe set never reaches it either. `main()`'s disabled-
board branch
(`examples/aen/aen-sdhc-probe/src/main.c:478` ("int main(void)")) now
reads `CLKCTL_PER_MST` (`0x4903F00C`) and `CAPABILITIES1`
(`0x48102040`), calls `clock_control_on()` for `ALIF_SDC_CLK` against the
`clockctrl` device directly, re-reads both registers, and prints an
explicit, grep-able verdict on whether bit 16 (`SDC_CKEN`) went clear to
set and whether `CAPABILITIES1` went `0x00000000` to non-zero. Neither
register access nor the `clock_control_on()` call applies SD pinctrl or
touches a single SD pad: `CLKCTL_PER_MST` is a SoC-level system-control
register, gating the block's internal clock only, and pinctrl is applied
solely by the SDHC driver's own init, which is never built while `sdhc0`
stays disabled. No expected capability word is asserted anywhere in this
code -- the silicon's own value is printed and left to stand as the
evidence, so a guessed constant never masquerades as a real measurement.
This proves the controller becomes addressable; it does **not** prove a
card enumerates, and says so in its own printed output and in
`examples/aen/aen-sdhc-probe/README.md`.
`examples/aen/aen-sdhc-probe/prj.conf` gains `CONFIG_CLOCK_CONTROL=y`
(the `clockctrl` device is otherwise only pulled in via `CONFIG_SDHC_DWC`
itself, which never selects while `sdhc0` is disabled), and
`sdhc-build-coverage.overlay` gains an explicit, spelled-out hazard
comment (SoC driving HIGH into `U38`/`U39` driving LOW on six pads at
once) so the build-only, never-flashed status of that overlay cannot be
missed. `sdhc0` stays `status = "disabled"` on both real board overlays;
nothing flashable enables it.

**Driver build coverage.** With `sdhc0` disabled in both examples' real
overlays, neither build reaches `CONFIG_SDHC_DWC` any more, so the #1097
orphan-section link regression (`CONFIG_SDHC_DWC_ADMA`'s descriptor table
landing in an empty-named linker section) lost its only coverage. Restored
via a second, build-only twister scenario,
`alp_sdk.examples.aen.sdhc_probe.aen.sdhc_build_coverage`
(`examples/aen/aen-sdhc-probe/testcase.yaml`), which layers a new
`sdhc-build-coverage.overlay` on top of the real board overlay to
re-enable `sdhc0` for that scenario only — never the app's real
configuration, never flashed. Verified locally: this scenario builds and
links clean with `CONFIG_SDHC_DWC=y`.
