### Fixed — carve-out refusal told the reader to make an edit it would still refuse (#2009)

`scripts/alp_orchestrate/carveout.py`'s IPC-eligibility refusal told the
reader to "Add a region whose resolved base sits outside the ... aperture
(or, if inside it, one that resolves `write_authority: customer_runtime`)".
The parenthetical was false: `_region_ipc_eligibility()`'s `cls == "flash"`
branch refuses a region CONTAINED in the SoC's declared on-die MRAM aperture
unconditionally — `write_authority` is consulted only on the unclassified
(outside-aperture) branch. A region inside the aperture could never be made
IPC-eligible by adding `write_authority: customer_runtime`, exactly what the
remedy instructed. `docs/board-config-features.md` carried the same
inversion in prose.

Both now say what actually unblocks the case: outside the aperture, and —
only for a region the SoM preset authors itself — carrying
`write_authority: customer_runtime`. A contained region is flash-class and
refused regardless of `write_authority`.

Re-baselined the four affected golden snapshots
(`tests/fixtures/emit-snapshots/{mproc-mailbox,rpmsg-aen}.{build-plan,system-manifest}.snap`)
— the reason text changed, `status: blocked` did not. Added
`TestContainedRegionWriteAuthorityNeverRescues` to
`tests/scripts/test_orchestrate_carveout_aperture_ordering.py`, pinning the
behaviour rather than the wording: a region matching the issue's exact
repro (contained, `write_authority: customer_runtime`) still refuses, a
`mram_main`-shaped end-to-end case simulating a customer following the old
remedy stays blocked, and a region matching the corrected remedy (outside
the aperture, preset-authored, `write_authority: customer_runtime`) does
resolve eligible.

Found by a post-merge review of #1983 (#1365 split B, merged as
`2fd045411`); the reviewed text moved and this repo has advanced since,
so file/line references in the original finding no longer match `dev`
verbatim.
