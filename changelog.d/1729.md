### Fixed — the ORT and DEEPX inference backends silently truncated a rank > 4 tensor to rank 4 (#1729)

`alp_inference_tensor_t` ([ABI-STABLE] `include/alp/inference.h`) carries a
fixed `uint16_t shape[4]`. `get_input`/`get_output` in both
`src/yocto/inference_ort.cpp` and `src/yocto/inference_deepx.cpp` used to
clamp a tensor's real rank to 4 and copy only its first 4 dims, returning
`ALP_OK` with a plausible-looking but wrong shape for any caller that
computes dimensions or strides from `shape[]`. A caller that only reads
`size_bytes` was unaffected either way — that field was always sized
correctly from the real (untruncated) element count.

Per ADR-0002's error-code convention, this is a capability gap, not a
best-effort guess: both backends now refuse a rank > 4 tensor with
`ALP_ERR_NOSUPPORT` instead of truncating it (Option 1 from the issue —
widening `shape[8]` would break the `[ABI-STABLE]` header for an arbitrary
new width; an out-of-band accessor is the largest surface; documenting the
truncation without fixing it still hands the caller a wrong shape).

- `src/yocto/inference_tensor_shape.h` (new): `alp_inference_shape::fill_fixed_shape()`
  (`src/yocto/inference_tensor_shape.h:50`) — the shared rank decision,
  copy-or-refuse, no dependency on the ONNX Runtime C API or dx_rt. Mirrors
  the `src/yocto/drpai_deploy_shapes.h` (#1635) precedent of splitting a
  vendor-independent decision into its own header specifically so it is
  unit-testable without the vendor SDK.
- `alp_inference_ort_get_input()` and `alp_inference_ort_get_output()` each
  now call `fill_fixed_shape()` and return `ALP_ERR_NOSUPPORT` on a false
  return, in place of the old `(info.shape.size() > 4) ? 4 :
  info.shape.size()` clamp -- `src/yocto/inference_ort.cpp:649` and
  `src/yocto/inference_ort.cpp:679`.
- `fill_tensor_descriptor()`, shared by both `get_input` and `get_output`,
  now returns `bool` — `false`, with `*out` left untouched, on a rank > 4
  tensor (`src/yocto/inference_deepx.cpp:145`); both call sites propagate
  that as `ALP_ERR_NOSUPPORT` (`src/yocto/inference_deepx.cpp:245` and
  `src/yocto/inference_deepx.cpp:277`).
- `tests/yocto/inference_tensor_shape.cpp` (new): five cases against
  `fill_fixed_shape()` directly (rank 4 copies through, rank < 4 zero-fills
  the remainder, rank 0 is not refused, rank 5 is refused with `*out` left
  untouched — not truncated to its first 4 dims — and rank 8 is refused the
  same way). Registered in `tests/yocto/CMakeLists.txt` as a first-class
  ctest target, `alp_test_inference_tensor_shape`, built and linked with no
  vendor SDK.
- The `rank`/`shape[4]` field comments (`include/alp/inference.h:143`) and
  the `@return` lists of `alp_inference_get_input`/`alp_inference_get_output`
  (`include/alp/inference.h:292` and `include/alp/inference.h:313`) now
  document the `ALP_ERR_NOSUPPORT` refusal. Doc-comment-only — `python3
  scripts/abi_snapshot.py --version v0.16 --output docs/abi/v0.16-snapshot.json`
  reports the snapshot unchanged.

Neither `inference_ort.cpp` nor `inference_deepx.cpp` is compiled by any
local or CI gate today: both are gated by a CMake option
(`ALP_SDK_USE_ORT_CPU`, `ALP_SDK_USE_DEEPX_DXM1`) that defaults `OFF` in
`src/yocto/CMakeLists.txt`, and no workflow in `.github/workflows/` turns
either on — CI's yocto leg configures a bare `-DALP_OS=yocto`. That gap is
unchanged by this fix; `alp_test_inference_tensor_shape` covers the shared
rank decision, not either vendor TU's use of it.

**A sibling of the same defect, found while fixing this one and fixed with it.**
The rank cap is not the only place a real dimension was quietly reshaped to fit
the descriptor: `alp_inference_tensor_t.shape[]` is `uint16_t`, and
`inference_deepx.cpp` cast each `int64_t` extent straight into it with no bounds
check. A dim above 65535 wrapped (100000 became 34464) and a symbolic/dynamic
`-1` became 65535 -- in both cases a plausible-looking wrong extent, exactly the
failure mode this issue is about. `inference_ort.cpp` already refused such dims
at load time in `_gather_tensor_info`, with the note "reject here instead of
lying to the caller"; its sibling never got that check.

The shared helper now refuses any extent it cannot represent (`< 0` or
`> UINT16_MAX`), before writing anything to the descriptor, so both backends are
covered rather than one being fixed and the other left (the #1646 defect class).
`UINT16_MAX` itself is representable and still passes. It deliberately does not
copy ORT's "pin a non-positive dim to 1" behaviour: that is a documented
load-time choice ORT makes for symbolic dims, and silently inventing an extent
on a backend that never made that choice would be the same kind of lie in a new
place.
