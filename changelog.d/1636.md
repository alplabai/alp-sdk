### Fixed — hardware facts had drifted back out of `metadata/` into hand-written board headers (#1636)

Every hardware fact in this SDK is supposed to have one source under `metadata/`,
with headers generated from it. Two blocks had drifted back the other way.

**The five E1M-X EVK INA236 current-shunt monitors** — addresses, shunt
resistances and max currents — existed **only** in the hand-written
`include/alp/boards/alp_e1m_x_evk.h`. `grep -n "i2c_devices"
metadata/boards/e1m-x-evk.yaml` returned nothing, while the sibling E1M carrier's
identical data was already generated into
`include/alp/boards/alp_e1m_evk_routes.h` by `scripts/gen_board_header.py`. They
now live in `metadata/boards/e1m-x-evk.yaml` and are generated the same way, along
with the five remaining on-board sensor addresses (`BMI323`, `ICM42670`,
`BMP581`, `TCAL9538`, `EEPROM`) — leaving that header carrying prose only.

This is the shape of drift that does not announce itself. `XEVK_INA236_SHUNT_3V3_OHMS`
is `0.020f`: a **scaling factor** consumed by `ina236_init()`, not an identifier.
A board respin that changes a shunt desynchronises it into plausible-but-wrong
current readings rather than a build break.

**The eleven E1M EVK `EVK_PIN_OVERLAY_BASE + N` pad indices** were hand-maintained
in `include/alp/boards/alp_e1m_evk.h`, absent from the YAML that generates the
rest of that header. The audit did not distinguish whether these are independent
hardware facts or derivations, and the right fix differs — putting a derived
value in metadata creates two sources of truth for one fact, which is the same
defect in different clothes.

**They are derivations.** `zephyr/dts/bindings/alp,pin-array.yaml` states that
`pin_id` is the index into the `gpios` property, and no in-tree `alp,pin-array`
node comes near 52 entries — the largest is 44, then 42 — so `N` has no external
hardware anchor at all. The real per-entry hardware fact, which E1M/Alif pad was
repurposed, was already captured in prose. So the **generator** computes `N` by
position and the YAML stores ordering only; that ordering is pinned by a test
which goes red if two entries are swapped.

**A comment is a second source of truth exactly like a `#define` is.** The first
cut of this change moved the duplication rather than removing it — the X-EVK
header still listed the whole INA236 table in prose (`U21 INA236A 3V3 rail
A0 = GND -> 0x40 (20 mOhm)` and so on), and the E1M header still carried all
eleven per-pad paragraphs verbatim. Nothing syncs prose and no gate checks it.
Both are now deleted, and the per-device A0 strap facts moved into the YAML
`doc:` strings where the sibling carrier already kept them.

**Byte-identity was the acceptance test, not a green suite.** A metadata lift that
silently changes a hardware value is worse than not doing the lift, so the proof
is that every macro survives unchanged: verified with `abi_snapshot.build_snapshot`
across both trees (1025 macros each side, 27 `MOVED`, **zero** `VALUE-DIFF`) and
independently with `gcc -E -dM`, which diffs the 45 affected macro lines
identically — including `0.020f`, `0.050f`, `1.6f`, `4.0f` and two values that had
been written with line continuations.

`metadata/schemas/board-preset.schema.json`'s `overlay_pin_entry` pattern is
`^EVK_PIN_`, deliberately not `^X?EVK_PIN_`: `scripts/gen_board_header.py`
hard-codes `EVK_PIN_OVERLAY_BASE ALP_E1M_GPIO_COUNT` with no E1M-X branch, so
admitting an `XEVK_PIN_*` entry emitted a reference to `ALP_E1M_GPIO_COUNT` (52u)
into a header that only includes `alp/e1m_x_pinout.h`, where that symbol does not
exist — the E1M-X count is `ALP_E1M_X_GPIO_COUNT` (99u). A schema must not promise
what the generator cannot deliver; a test now reproduces that case and asserts the
schema rejects it.

`tests/scripts/test_abi_snapshot.py`'s #794 line-continuation guard was re-pointed
at `TPS628640_CTRL_DEFAULT`, because it had been anchored to
`XEVK_I2C_ADDR_INA236_VCAM2`/`_VCAM3` in the now-deleted hand-written location.
That is a **stronger** case, not a weaker one — a two-continuation-line macro
where the old anchors were single-continuation — and it still fails with #794's
exact symptom if the continuation joining is removed.

**Not in scope, deliberately.** Task 3 (the NPU arena envelope, zero on all nine
SoCs) is deferred: the generator gate it wants would reject every shipped SoC JSON
until real arena sizes are supplied, which is a per-SoC hardware fact. So
`src/backends/inference/alp_model_select.c` still reads a zero arena as
accept-anything and `ALP_ERR_NO_FIT` remains dead on every shipped SoM. Task 4 is
**refuted** — `include/alp/cap.h:58` is `ALP_CAP_ID_NPU_DRPAI`, an enum member that
`gen_soc_caps.py`'s `_emit_cap_h()` emits from `CAP_ALIASES`; generator and header
agree and there was no drift there.

This change transcribes `XEVK_I2C_ADDR_INA236_VCAM2` as `0x48u` **unchanged**,
which collides with `TAS2563_I2C_ADDR_BROADCAST` (`0x48u`) on the same bus
`E1M_X_I2C0`. That is a real hardware finding surfaced by this work and filed
separately as #1659; a metadata lift is not the place to silently change a
strapping.
