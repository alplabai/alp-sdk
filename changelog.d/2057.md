### Fixed — `sdhc_dwc_card_busy()` tested a five-bit CMD+DAT mask for any-bit-high, so an ordinary DAT0-low busy card reported not-busy (#2057)

`sdhc_dwc_card_busy()` (`zephyr/drivers/sdhc/sdhc_dwc.c:986-1015`) tested
`DWC_SDHC_CMD_DATA_LINE_STATUS_Msk` (`0x01F00000U` — DAT`[3:0]` Line Signal
Level at bits `[23:20]` plus CMD Line Signal Level at bit 24, SD Host
Controller Simplified Specification Present State Register, offset `024h`,
section 2.2.9 in v3.00, unchanged through v4.20) and returned "not busy" the
moment *any* of those five bits read high. SD busy signalling — an R1b
response, or write programming — is DAT0 held low while DAT1..DAT3 and CMD
sit high (SD Physical Layer Specification 4.2.4.2). That reads back as
`0x01E00000U`: non-zero, so the old check declared the card not busy while it
was busy. The five-bit group is still the correct test for the CMD11
low-phase check in `sdhc_dwc_set_voltage()` (all five genuinely go low
there); it was simply the wrong test for this function.

`sdhc_dwc.h` gains a DAT0-only accessor derived from the existing
`DWC_SDHC_DAT_LINE_LVL_Pos` field (added in #2042):

```c
#define DWC_SDHC_DAT0_LINE_LVL_Msk BIT(DWC_SDHC_DAT_LINE_LVL_Pos)
```

`sdhc_dwc_card_busy()` now tests that mask alone, and its comments name DAT0
specifically instead of "DAT lines" against a mask that also covered CMD.

**Precedent, for a reader who wants a second data point.** Linux's
`sdhci_card_busy()` masks `SDHCI_DATA_0_LVL_MASK` (`0x00100000`) — cited from
general knowledge, not read from disk; the Linux kernel is not vendored in
this tree. This repo's own `zephyr/drivers/sdhc/sam_sdmmc.c` checks a single
bit, `SDMMC_PSR_DATLL_Pos`, the same DAT0-alone convention.

**Masked, not harmless.** Upstream Zephyr's `sdmmc_wait_ready()`
(`subsys/sd/sd_ops.c`, not vendored in this alp-sdk tree) falls through to
CMD13 polling when `sdhc_card_busy()` says not-busy, so the generic write path
has a backstop and no data-corruption path is named by this fix. The sharper
consequence is the CMD11 post-switch check in `sdmmc_switch_voltage()` (upstream Zephyr
`subsys/sd/sd_ops.c`, not vendored in this alp-sdk tree, around line 397),
which would have accepted "switched successfully"
on a CMD-high/DAT-low reading — exactly the false-positive this defect could
produce. Today the only thing standing between that false success and the bus
is the driver-internal DAT`[3:0]`-all-high poll inside
`sdhc_dwc_set_voltage()`, and that poll is itself unreachable — see #2058.

**Untested on silicon.** No `PSTATE` value has ever been captured from AE822
hardware (`snps,dwc-sdhc` is instantiated by exactly two E1M-AEN801 board
overlays, and SD enumeration has never completed on either — see #2051, the
`SW_RST_CMD` self-clear defect that currently blocks `disk_access_init()`
before any command reaches the busy path). This fix is spec-and-precedent
reasoning, not a bench measurement. Whether the DWC block reports DAT0
identically to the generic SDHCI convention cited above is not established by
this change and should be labelled `untested-on-silicon` until a bench run
reads the register.

Refs #2042, #2058, #2051.
