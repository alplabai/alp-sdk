### Fixed — U-Boot `CONFIG_BOOTCOMMAND`'s kernel `Image` load was still non-fatal on both branches (#1302)

#1252's dtb fix left the vendor `sd2load`/`emmcload` env untouched (it is
patched by optional vendor feature layers, so editing it directly is not
patch-safe) — but that same env stages the kernel `Image` at `0x48080000`
with a `;`-chained, non-fatal `ext4load`, so a missing or truncated
`boot/Image` was silently followed by `booti`-ing stale or garbage RAM
content, the same failure class #1252 fixed for the dtb.

Both the `Image` and the dtb are now re-loaded fatally from
`CONFIG_BOOTCOMMAND`, in the same `if ext4load ...; then ... ; else echo ALP
FATAL: ...; fi` shape on both the SD and eMMC branches: a failed load prints
an `ALP FATAL:` message and `bootcmd` simply ends without ever calling
`bootimage`, leaving U-Boot at the interactive prompt instead of continuing
to boot on stale RAM.

This does not strand the board: the dev cmdline's interruptible autoboot
(`BOOTDELAY`/`AUTOBOOT_KEYED`) already leaves the same serial console
reachable, and `rzv2n-dev_defconfig` already carries the U-Boot USB gadget
download path (`CONFIG_USB_GADGET_DOWNLOAD` + `CONFIG_CMD_USB_MASS_STORAGE`)
for recovery — a failed autoboot returns to that same prompt, it does not
reset or loop.

Same patch as #1252:
`meta-alp-sdk/recipes-bsp/u-boot/u-boot/0003-rzv2n-dev-select-fdtfile-fatal-image-and-dtb-load.patch`.

**Verified by rebuild, not on hardware** (see #1252's entry for the build
verification). The runtime behaviour of the nested hush `if`/`then`/`else`/`fi`
— that a failed load genuinely stops at the prompt rather than resetting or
looping — is **not** bench-verified; it needs a real V2N/V2M board on the
serial console with a missing/renamed `boot/Image`, which is blocked on
V2M101's separate hardware bring-up issues.
