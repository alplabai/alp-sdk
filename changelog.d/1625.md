### Fixed — `alp_update_log_open()`'s election loop could livelock under cross-priority contention (#1625)

The OPENING/CLOSING wait loop in `alp_update_log_open()` looped straight back
on itself with no yield, reintroducing the #1114 priority-inversion hang: a
higher-priority caller that observed the elected-but-not-finished OPENING
state (or lost the UNOPENED->OPENING race) never yielded the core, so a
lower-priority initializer stuck inside `_elect_backend()`'s `ops->ready()`
call (a TF-M round trip on the HW_ENFORCED tier) could never run again on a
single-core preemptive-priority scheduler. That is a livelock, not a slow
path: the higher-priority spinner never blocks, so the lower-priority holder
of the singleton's OPENING lock never gets scheduled, and `alp_update_log_open()`
never returns for either caller.

`src/update_log_dispatch.c` now calls `alp_slot_sleep_tick()` on both
non-terminal branches of the loop, matching the sleep-poll shape #1114 already
applied to the generic close drain (`alp_handle_begin_close_blocking()`) and to
`ble_dispatch.c`'s open-time join scan.

Regression test: `tests/unit/update_log/src/test_update_log.c`'s
`test_open_election_unequal_priority_no_livelock`. A low-priority thread wins
the open election and parks, via a controllable gate, inside the HW backend's
`ready()` call; a higher-priority contender is proven — by a semaphore
rendezvous, not a timing guess — to have observed OPENING before the gate
releases.
