### Fixed - V2N/V2M reboot panicked after a `gd32_ota_host --unbind` and the board never recovered (#2734)

Bench-reproduced on E1M-V2M103 unit 0008. `gd32_ota_host --unbind` unbound `gpio-gd32-bridge` (`8-0070`); fw_devlink then force-unbound `wlan-pwrseq`, whose `reset-gpios` is gd32 line 19. Its `struct mmc_pwrseq` was devm-freed while `&sdhi2`'s `host->pwrseq` still pointed at it, so the next reboot ran `brcmf_reboot_callback` -> `mmc_hw_reset` -> `mmc_pwrseq_power_off` on freed memory and hit `Kernel panic`. `panic_timeout` was 0, so the board spun forever.

- The kernel patch `0005-gpio-add-gd32-bridge-expander-driver.patch` now sets `.suppress_bind_attrs = true` on the `gpio-gd32-bridge` driver: the sysfs `unbind` file no longer exists, and its consumers (`wlan-pwrseq`, `hci_bcm`, the panel) can never be orphaned.
- `gd32_ota_host` lost `--unbind` and all sysfs unbind/rebind code. It was never needed: every frame goes through `alp_i2c_write_read` -> `ioctl(I2C_RDWR)`, which i2c-dev allows on a bound address, and the OTA flow never calls `I2C_SLAVE`. After COMMIT it now prints `reboot required` (the GD32 resets twice, the Wi-Fi chip loses power, brcmfmac cannot recover).
- New `meta-alp-sdk` kernel fragment `panic.cfg` sets `CONFIG_PANIC_TIMEOUT=10`, so any panic reboots the board after 10 s.

Follow-up, not in this change: `watchdog.stop_on_reboot=0` still needs bench validation.
