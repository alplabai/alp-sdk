### Fixed — the CC3501E GPIO proxy route table was hand-triplicated, non-revision-aware, and routed a bridge-reserved pad (#1859)

`examples/aen/{aen-cc3501e-gpio,aen-cc3501e-bringup,aen-cc3501e-companion-tour}/src/cc3501e_gpio_routes.c`
hardcoded the r2 (production) map -- `{ALP_E1M_GPIO_IO8, 30u}`,
`{ALP_E1M_GPIO_IO10, 35u}`, no `IO21` entry -- with none of the three
`board.yaml` files setting `som.hw_rev`. On the r1 bench module `IO8` and
`IO10` are direct Alif GPIOs and `IO21` reaches the CC3501E instead, so
now that #1860 makes the table's contents actually reach the proxy
backend, a board built for r1 would have started driving the wrong
chip's pins. Separately, the table carried
`{ ALP_E1M_GPIO_IO16, 17u }` -- CC3501E `GPIO_17`, the bridge's own
READY/host-IRQ line (`metadata/e1m_modules/aen/from-cc3501e.tsv`;
`firmware/cc3501e/hal/ti/cc3501e_hw_ti_gpio.c`'s `gpio_pad_reserved()`
rejects pads 16 and 17). `IO17` (-> `GPIO_16`, the bridge's own SPI0 CS)
was correctly hand-omitted with a comment explaining why; `IO16` was not.

Both defects share a root cause: the table was hand-maintained instead of
derived from the metadata that already fully describes it. Replaced with
`scripts/gen_cc3501e_gpio_routes.py`, a generator matching this repo's
"board files are generated from YAML" convention
(`scripts/gen_board_header.py`, `--emit zephyr-board`): for every AEN
example whose `prj.conf` sets `CONFIG_ALP_SDK_GPIO_CC3501E_PROXY=y`, it
resolves `alp_project.py --input <board.yaml> --emit composed-route-table`
(which already applies `metadata/e1m_modules/aen/hw-revisions.yaml`
`pad_route_overrides:` for the board's `som.hw_rev`, falling back to the
SoM's `default_hw_rev` when unset -- `scripts/alp_project_loader.py`'s
`_hwrev_pad_route_overrides()`), filters to `dispatch: cc3501e` GPIO
rows, and excludes any row whose target pad is in
`RESERVED_CC3501E_PADS` (mirrors `gpio_pad_reserved()`'s reserved set --
the transport's own SPI0/console pads plus the bridge's own READY/CS
lines) -- as one rule applied to every row, not a per-instance hand
omission. A defensive assertion re-checks the excluded set held after
filtering, so a future change to the filter itself fails at generation
time rather than at `cc3501e_gpio_configure()` on a device.
`.github/workflows/pr-generated-files.yml` and
`scripts/test-all.sh`'s `stage_generated_files` regenerate and diff-gate
the three committed tables the same way every other single-sourced
artifact in this repo already is.

The three examples still resolve to `hw_rev=r2` (none set `som.hw_rev`,
so the SoM's `default_hw_rev: r2` applies) -- their generated tables are
unchanged in board-revision terms, just corrected (`IO16` dropped, 9
routes instead of 10) and now regenerable. A board.yaml that sets
`som.hw_rev: r1` gets the r1 map automatically; verified locally by
feeding the generator a `som.hw_rev: r1` copy of `aen-cc3501e-gpio`'s
board.yaml and confirming `IO8`/`IO10` resolve `direct` and `IO21`
resolves `cc3501e`/`30` as expected.

`fix/1854-unrouted-pad` (#1863) is unaffected: it deliberately leaves
`cc3501e_gpio_unrouted[]` unpopulated pending #1860's own-TU fix landing
first; this change does not touch that table.
