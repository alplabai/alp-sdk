### Fixed — the CC3501E GPIO proxy route table was hand-triplicated, non-revision-aware, and routed a bridge-reserved pad (#1859)

`examples/aen/{aen-cc3501e-gpio,aen-cc3501e-bringup,aen-cc3501e-companion-tour}/src/cc3501e_gpio_routes.c`
hardcoded the r2 (production) map -- `{ALP_E1M_GPIO_IO8, 30u}`,
`{ALP_E1M_GPIO_IO10, 35u}`, no `IO21` entry -- with none of the three
`board.yaml` files setting `som.hw_rev`. On the r1 bench module `IO8` and
`IO10` are direct Alif GPIOs and `IO21` reaches the CC3501E instead, so
now that #1860 makes the table's contents actually reach the proxy
backend, a board built for r1 would have started driving the wrong
chip's pins. Separately, the table carried
`{ ALP_E1M_GPIO_IO16, 17u }` -- CC3501E `GPIO_17`, the bridge's own
READY/host-IRQ line (`metadata/e1m_modules/aen/from-cc3501e.tsv`; the
bridge firmware's `gpio_pad_reserved()`, in the separate
`alplabai/cc3501e-bridge-firmware` repo, rejects pads 16 and 17). `IO17`
(-> `GPIO_16`, the bridge's own SPI0 CS) was correctly hand-omitted with
a comment explaining why; `IO16` was not.

Both defects share a root cause: the table was hand-maintained instead of
derived from the metadata that already fully describes it. Replaced with
`scripts/gen_cc3501e_gpio_routes.py`, a generator matching this repo's
"board files are generated from YAML" convention
(`scripts/gen_board_header.py`, `--emit zephyr-board`): for every AEN
example whose `prj.conf` sets `CONFIG_ALP_SDK_GPIO_CC3501E_PROXY=y`, it
resolves `alp_project.py --input <board.yaml> --emit composed-route-table`
(which already applies `metadata/e1m_modules/aen/hw-revisions.yaml`
`pad_route_overrides:` for the board's `som.hw_rev`, falling back to the
SoM's `default_hw_rev` when unset -- `scripts/alp_project_loader.py`'s
`_hwrev_pad_route_overrides()`), filters to `dispatch: cc3501e` GPIO
rows, and excludes any row whose target pad is in
`RESERVED_CC3501E_PADS`. That set is DERIVED from
`metadata/e1m_modules/aen/from-cc3501e.tsv`'s `BRIDGE_READY` /
`BRIDGE_SPI_CSN` peripheral-claim column, not hand-typed against the
firmware's `gpio_pad_reserved()` (which lives in a separate repo this
one can't see drift in) -- as one rule applied to every row, not a
per-instance hand omission. A dropped row is printed, not silently
discarded; a `dispatch: cc3501e` GPIO row with no `dispatch_pin` (a
metadata defect -- typo'd `dispatch:`, a missing pin in a
`pad_route_overrides` entry) now fails the generator outright instead of
silently delegating that pad to the platform driver, and
`metadata/schemas/hw-revisions-v1.schema.json`'s `pad_route_overrides[].dispatch`
now carries the same enum the SoM preset schema already enforces, so a
typo can't validate in the first place.
`.github/workflows/pr-generated-files.yml` and
`scripts/test-all.sh`'s `stage_generated_files` regenerate and diff-gate
the three committed tables the same way every other single-sourced
artifact in this repo already is, scoped to `examples/aen` so a future
fourth proxy-enabled example is covered without another edit here.

The three examples still resolve to `hw_rev=r2` (none set `som.hw_rev`,
so the SoM's `default_hw_rev: r2` applies) -- their generated tables are
unchanged in board-revision terms, just corrected (`IO16` dropped, 9
routes instead of 10) and now regenerable. A board.yaml that sets
`som.hw_rev: r1` gets the r1 map automatically; verified both by hand
(feeding the generator a `som.hw_rev: r1` copy of `aen-cc3501e-gpio`'s
board.yaml and confirming `IO8`/`IO10` resolve `direct` and `IO21`
resolves `cc3501e`/`30`) and by a new committed regression test,
`tests/scripts/test_gen_cc3501e_gpio_routes.py::test_r1_board_yaml_produces_the_r1_map_not_r2s`.
`tests/scripts/test_aen_cc3501e_routes.py`'s cross-check against SoM
metadata was itself pinned to `from-cc3501e.tsv` (r2-only) before this
round; it now builds its expectation from each example's own
`--emit composed-route-table`, so it can validate a per-example
`som.hw_rev` instead of only ever proving r2.

**Also added: a runtime hw_rev guard, GPIO-only** (the "stronger guard"
#1853's boot-banner fix explicitly deferred to this issue). Before this,
nothing stopped a firmware image compiled against one hw_rev's route
table from running on a module of a DIFFERENT hw_rev -- exactly the risk
above, just moved from "the table is wrong" to "the table is right for
the wrong module." `alp_gpio_cc3501e_attach()` now reads the on-module
EEPROM manifest once (via `alp_hw_info_read()` +
`alp_hw_info_build_hw_rev_mismatch()`, landed on `dev` with #1862) and
caches whether the live module's `hw_rev` disagrees with
`CONFIG_ALP_SDK_SOM_HW_REV` (the rev this build's table was generated
for); `route_lookup()` refuses to proxy anything for the rest of the run
when it does, falling through to the platform driver -- the same safe
fallback an empty/unpopulated route table already gets, instead of
driving a different physical pin than the caller asked for. Stays
inert (never refuses) when the manifest can't be read (unprovisioned
EEPROM, or -- true for all three examples today -- no
`CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BUS_ID` wired for AEN yet), matching
the boot banner's own floor: known limitation, not fixed here.

`fix/1854-unrouted-pad` (#1863) is unaffected: it deliberately leaves
`cc3501e_gpio_unrouted[]` unpopulated pending #1860's own-TU fix landing
first; this change does not touch that table, and -- unlike
`cc3501e_gpio_routes[]` -- `cc3501e_gpio_unrouted[]` is NOT covered by
`scripts/gen_cc3501e_gpio_routes.py` (different shape entirely). Whoever
populates it will be hand-writing entries the same way this table used
to be, with the same drift risk; a generator for that table is a
follow-up, not part of this fix.
