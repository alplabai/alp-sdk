### Added — `<alp/rpc.h>` link-liveness signal (issue #1643)

A far core resetting or crashing used to be invisible: nothing surfaced the
transport's own bind/unbind signal, so `alp_rpc_send()` kept returning
`ALP_OK` into a dead vring forever, indistinguishable from an idle peer.

- **`alp_rpc_link_state_t`** (`ALP_RPC_LINK_DOWN` / `_UP` / `_LOST`),
  **`alp_rpc_link_cb_t`**, **`alp_rpc_set_link_callback()`**, and
  **`alp_rpc_link_state()`** — new, purely additive `<alp/rpc.h>` surface
  (ABI-STABLE, minor bump).
- The dispatcher's internal `alp_rpc_notify_link()` hook
  (`src/backends/rpc/rpc_ops.h` / `src/rpc_dispatch.c`) enforces the header's
  documented invariant with a compare-and-swap: `ALP_RPC_LINK_LOST` is only
  ever accepted from `ALP_RPC_LINK_UP`, so a link that never bound stays
  `DOWN` rather than getting permanently poisoned by an out-of-order notify.
- `src/backends/rpc/yocto_drv.c` (Linux/A-class chardev backend) reports UP
  once `/dev/rpmsg<N>` opens — strictly **before** its rx thread starts, so
  an already-dead peer's first `poll()`/`read()` failure can't have its LOST
  clobbered back to UP by a late UP notify — and LOST on either a `poll()`
  failure or a `read()` EOF/error (both end the same thread, so both now
  report the same state; only the wake-pipe close-side branch stays silent).
- `src/backends/rpc/zephyr_drv.c` wires `ipc_service`'s `bound` + `unbound` +
  `error` endpoint callbacks (previously only `bound` + `received`), all
  three bracketed by the same `rpc_recv_enter()`/`rpc_worker_leave()`
  closing-gate `received` already used — closing a same-channel-close-from-
  inside-the-link-callback hole `bound()` had before this fix (see below).
  **However**: the ONLY `ipc_service` backend `CONFIG_ALP_SDK_RPC` permits
  (`depends on IPC_SERVICE_BACKEND_RPMSG && OPENAMP`) is the pinned Zephyr
  v4.4.1 RPMsg static-vrings backend, which invokes `bound`/`received` only
  — never `unbound`/`error` (confirmed against the pinned tree; those two
  are invoked exclusively by the ICMsg backend family, which this Kconfig
  does not select). **So in this revision, on Zephyr, `ALP_RPC_LINK_UP` is
  reliably reported but `ALP_RPC_LINK_LOST` is NOT observable at all** — the
  wiring is real, tested, and forward-compatible (it goes live the day
  upstream propagates ns-unbind through `ipc_service`, or a future backend
  swap lands), but structurally unreachable today. See
  `src/backends/rpc/zephyr_drv.c`'s `@par Link liveness` file comment.
- **Net effect for the two SoM families this issue names**: neither AEN
  (an all-Zephyr M55↔M55 pair) nor V2N's A55 (whose `silicon_ref` selects
  `src/backends/rpc/yocto_uio_drv.c`, not wired for link liveness at all —
  see below) can produce `ALP_RPC_LINK_LOST` in this revision. The only
  backend that can today is the plain Linux chardev path
  (`yocto_drv.c`) on a peer that isn't V2N's A55.
- `src/backends/rpc/yocto_uio_drv.c` (RZ/V2N's userspace-virtio path, which
  wins over `yocto_drv.c` on every V2N `silicon_ref`) is **not** wired in
  this revision — its remoteproc/virtio teardown shape has no equivalent to
  the chardev backend's poll()+read() EOF signal, and this issue is
  `needs-silicon`; tracked as follow-up. This is the primary remaining gap
  for V2N, not a footnote: it is the one backend that would let V2N's A55
  detect its CM33 peer dying.
- `src/backends/rpc/sw_fallback.c` stays DOWN forever (no synthetic peer
  under native_sim); `src/common/stub/stub_rpc.c` returns `ALP_ERR_NOSUPPORT`
  for both new functions on the bare-metal build.

**Two correctness fixes alongside the above, both covered by new/extended
tests:**
- `zephyr_drv.c`'s `rpc_ept_bound()` (the UP notify) is now bracketed by the
  same `rpc_recv_enter()`/`rpc_worker_leave()` gate `unbound`/`error` use.
  It previously ran unbracketed on the theory that `bound()` "cannot
  plausibly race a self-close" — refuted by the very next line, which
  invokes the app's registered link callback, and that callback closing its
  own channel from inside `bound()` was misclassified as an external close
  (reentrant `ipc_service_deregister_endpoint()` from inside `ipc_service`'s
  own `bound` callback) and left `bound` uncounted against a concurrent
  external close racing the same slot.
- `alp_rpc_call()` gains the same entry-only `ALP_RPC_LINK_LOST` gate
  `alp_rpc_send()` already has — a NEW call is rejected before reaching the
  backend once the link is known LOST. This does not wake a call already in
  flight (see below).

**Behaviour change on the existing surface (documented, not slipped in):**
once a channel has observed `ALP_RPC_LINK_LOST`, `alp_rpc_send()` and a NEW
`alp_rpc_call()` now fail with `ALP_ERR_NOT_READY` instead of accepting into
the dead queue — the SAME return value the header already documented for a
NULL/closed channel, now also covering a known-dead link. An
ALREADY-in-flight `alp_rpc_call()` is unaffected: it keeps its own
`timeout_ms` defense and is not woken early by a link-loss notification
(unblocking an in-flight call from a transport callback crosses the
GHSA-xhm8-7f87-93q5 close-protocol's handle-lifetime rules and needs its
own, separately-reviewed change).

Bench-gated (`needs-silicon`): whether `yocto_drv.c`'s rx thread reports
`ALP_RPC_LINK_LOST` within a bounded time against a real peer's chardev EOF,
without a false positive on a merely-busy link, has not been attempted on
real hardware. (Whether Zephyr's `unbound` vs `error` fires for a far-core
reset is *not* a needs-silicon question in this revision — neither is
reachable under the pinned RPMsg static-vrings backend; see above.)
