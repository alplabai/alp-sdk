### Fixed — the GD32 bridge fuzz harness did not link, and now follows the firmware if it moves (#1370)

Two things, both prerequisites for extracting the GD32 bridge firmware into its own
repository.

**The harness was broken.** `alp_fuzz_gd32_bridge_frame` failed to link on `dev` with
`undefined reference to ota_dispatch` — `firmware/gd32-bridge/src/bootloader/bootloader.c:22` calls it, but `src/ota.c`, which
defines it, was never in the target's source list. Nothing caught this because
`ALP_BUILD_FUZZ` is opt-in and no CI job builds it. Adding `ota.c` fixes the link; with OTA
off (the default) `ota_dispatch()` only returns `STATUS_NOSUPPORT`, so this adds no
behaviour. The harness now builds and completes 20000 runs clean.

That matters more than a normal broken test: this harness fuzzes the bridge frame parser,
which consumes **peer-supplied data**, and it cross-checks its own reference CRC against
the firmware's `crc16_ccitt_false` on every iteration so a silent divergence between the
two implementations becomes a fuzz failure. None of that was running.

**The firmware path is now configurable.** The three test builds that compile firmware
sources — the fuzz harness plus `tests/unit/gd32_bridge_transport` and
`tests/unit/gd32_bridge_ota` — reach them through `ALP_GD32_BRIDGE_FIRMWARE_DIR` instead of
a hardcoded in-tree path. The default is the in-tree copy, so this is a **no-op today**;
after the extraction it becomes a one-line repoint per build rather than an edit to each.

The fuzz harness stays in alp-sdk after the split (maintainer decision on #1370) precisely
because of the peer-supplied-data surface, so it gains a loud `FATAL_ERROR` if
`ALP_GD32_BRIDGE_FIRMWARE_DIR` has no `protocol.c` under it — a harness that guards that
surface must never be dropped silently by a mis-set path.

**And CI now builds them.** `ALP_BUILD_FUZZ` is opt-in and no workflow set it, so *none* of
the ten harnesses under `tests/fuzz/` were compiled by CI — which is how this link failure
survived. `pr-fuzz-build` now builds every harness and gives each a short smoke run on any
PR touching `src/`, `chips/`, `firmware/`, `include/alp/` or `tests/fuzz/`.

Deliberately a build+smoke gate, not a fuzzing campaign: it catches "does not compile",
"does not link" and "crashes on the first input" — the failure modes that silently disable a
harness — while staying fast enough to be a PR gate. Long corpus runs belong in a scheduled
job.

It also refuses to pass vacuously. `tests/fuzz/CMakeLists.txt` *returns early* (with a
warning, not an error) under a non-clang compiler, which is precisely how the directory went
unbuilt; the workflow therefore asserts at least one `alp_fuzz_*` target was configured and
that at least one binary was produced, rather than reporting green on a build of nothing.

All ten harnesses build and smoke clean with the `ota.c` fix in place: `ble_adv_parser`,
`cc3501e`, `eeprom_manifest`, `gd32_bridge_frame`, `iot_mqtt`, `mproc_frame`, `optiga_apdu`,
`swd_packet`, `tls_handshake`, `update_log_entry`.
