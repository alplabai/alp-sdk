### Changed — the bridge firmwares live in their own repositories, and alp-sdk's security scope now says so (#1370)

Both bridge firmware trees are extracted, with history preserved, into
`alplabai/cc3501e-bridge-firmware` and `alplabai/gd32-bridge-firmware`. Each is
public and now carries its own CI, `SECURITY.md`, `CONTRIBUTING.md`,
`CODEOWNERS` and a protected `main` — none of which existed at the moment they
became separate repositories.

**`SECURITY.md` was actively wrong, not merely stale.** It declared
`firmware/cc3501e/` and `firmware/gd32-bridge/` in scope for vulnerability
reports, so a reporter following the published policy filed against a repo whose
maintainers no longer own that artifact. It now scopes the HOST halves
(`chips/cc3501e/`, `chips/gd32g553/`) and points at the two firmware repos by
name, with the boundary stated by artifact rather than by subject: a defect in
how the host *parses* a reply is alp-sdk's, the same defect in how the companion
*builds* it is the firmware repo's. Unsure cases are asked to come here rather
than be filed twice in public.

**ADR 0015** ("CC3501E bridge firmware is embedded in alp-sdk") was still
`Status: Accepted` while the tree contradicted it. It is superseded by
**ADR 0031**, which records what actually changed and — more importantly — what
did not: the wire contract stays single-sourced. Neither firmware mirrors the
protocol header; each compiles alp-sdk's canonical one through an explicit
`ALP_SDK_ROOT`, and firmware-side CI fails on drift (cc3501e compares
`protocol-version.txt` against `ALP_CC3501E_PROTOCOL_VERSION`; gd32 regenerates
`tests/protocol_vectors.txt` and diffs it). Vendoring a copy of the header into
each repo was the obvious way to split and was rejected for exactly the reason
0015 existed: a mirrored header that is merely *stale* still compiles.

### Removed — the firmware trees themselves, and the two unit suites that linked them (#1370)

The deletion that the extraction deliberately deferred is now done:
`firmware/cc3501e/` and `firmware/gd32-bridge/` are gone, and every consumer the
extraction listed has been repointed — `tests/fuzz/` takes the GD32 sources from
an `ALP_GD32_BRIDGE_FIRMWARE_DIR` checkout and **`FATAL_ERROR`s** when it is
absent rather than silently dropping the target, the AEN SoM presets no longer
pin `firmware/cc3501e/prebuilt/` as `helper_firmware`, and the doc links,
`Doxyfile`, `check_cross_platform.py`, `check_doc_drift.py`, `.vscode/tasks.json`
and `chips.kconfig` references are updated.

**Three test suites go with them.** `tests/unit/gd32_bridge_ota`,
`tests/unit/gd32_bridge_transport` and `tests/zephyr/cc3501e_bridge_transport`
all deliberately linked the **real** firmware sources rather than mocks, so with
the firmware removed they did not fail an assertion — they failed to configure
at all:

```
alp.unit.gd32_bridge_ota on native_sim/native/64 error
  (CMake Error at CMakeLists.txt:13 (target_sources): Cannot find source file:)
alp_sdk.cc3501e.bridge_transport on native_sim/native/64 error
  (CMake Error at CMakeLists.txt:32 (file): file STRINGS file)
```

They were **moved, not deleted**. Each now runs in its own firmware repository
as a host-only `ctest` job against a small ztest shim, with the suite sources
byte-identical to the originals —
[gd32-bridge-firmware#32](https://github.com/alplabai/gd32-bridge-firmware/pull/32)
and
[cc3501e-bridge-firmware#27](https://github.com/alplabai/cc3501e-bridge-firmware/pull/27).
The CC3501E suite keeps compiling alp-sdk's canonical
`<alp/protocol/cc3501e.h>` through `ALP_SDK_ROOT`, so single-sourcing of the
wire contract survives the move.

Keeping them here and repointing them at an optional external checkout — the way
`tests/fuzz/` now does — would have produced a suite that silently stops running
whenever that checkout is absent. The fuzz harness gets away with that pattern
because it can hard-fail on a missing directory; a twister suite has no
equivalent, so a required shard would simply go green while covering nothing.

Host-side GD32 coverage here is unaffected: `tests/zephyr/chips/gd32g553/` still
exercises the driver against the committed wire vectors, whose regeneration is
now checked by the firmware repo's own CI.
