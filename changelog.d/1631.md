### Fixed — an fd-flagged frame on a classic-mode CAN handle could overflow the Zephyr backend's on-stack frame (#1631)

`alp_can_send()`'s `payload_len` bound check let a frame with `fd = true`,
`payload_len = 64` through even on a handle opened `ALP_CAN_MODE_CLASSIC` — 64
is not greater than the CAN-FD max, and the classic-only bound check is
skipped because `frame->fd` is true. On a Zephyr build without
`CONFIG_CAN_FD_MODE`, the backend's on-stack `struct can_frame.data[]` is only
8 bytes (Zephyr's `CAN_MAX_DLEN`), so `src/backends/can/zephyr_drv.c`'s
`z_send()` copied up to 56 bytes past it.

`src/can_dispatch.c`'s `alp_can_send()` now rejects an fd-flagged frame on a
handle not opened `ALP_CAN_MODE_FD` with `ALP_ERR_NOSUPPORT`, once, for every
CAN backend — `<alp/can.h>`'s `alp_can_send()` doc now lists this case.
`z_send()` keeps its own bound check as defense-in-depth regardless of what
the dispatcher already validated.

Two related gaps closed in the same backend:

- `_rx_trampoline()`'s RX decode clamped the copy length only against the
  destination (the alp frame's 64-byte `data[]`), not the source (Zephyr's
  `struct can_frame.data[]`, 8 bytes without `CONFIG_CAN_FD_MODE`) — a classic
  frame reporting a wire DLC of 9–15 (`can_dlc_to_bytes()` maps that to
  12–64 bytes) could read past the source buffer. The copy is now bounded by
  both.
- `z_open()` only rejected `ALP_CAN_MODE_FD` on a `CONFIG_CAN_FD_MODE=n` build
  when `cfg->bitrate_data_hz > 0`; a caller passing `bitrate_data_hz == 0`
  fell through and opened successfully in normal mode while the handle's
  `cfg.mode` stayed `ALP_CAN_MODE_FD`, contradicting `alp_can_open()`'s
  documented contract. It now rejects unconditionally.
