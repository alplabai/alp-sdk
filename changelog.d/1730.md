### Fixed — GD32 bridge silently clamped an over-long PWM period to 65.536 ms and reported success (#1730)

`firmware/gd32-bridge/hal/gd32/pwm.c`'s `bridge_hw_pwm_set()` rounds the caller's
period to the bridge's fixed 1 us tick (the timer is prescaled 216:1 off the
216 MHz `CK_TIMER`, per `firmware/gd32-bridge/hal/gd32/gd32_common.h`) and
programs it into a 16-bit `ARR` register. A period beyond `0xFFFF` ticks
(65,536 ticks x 1000 ns = 65.536 ms) used to be silently truncated to that
ceiling — both for the edge-aligned path and the center-aligned half-period
path — while the call still returned `BRIDGE_HW_OK`. A caller asking for a
100 ms period got a pad running at 65.536 ms with no error anywhere, and
every subsequent duty request was scaled against the period it *asked for*,
not the one the hardware actually ran.

An unrepresentable period is a capability the silicon cannot express, not a
malformed argument, so it is now refused with `BRIDGE_HW_ERR_NOTIMPL` (wire
`STATUS_NOSUPPORT`, `ALP_ERR_NOSUPPORT` on the host) instead of clamped —
matching the convention this same file already uses for other
hardware-capability gaps (`bridge_hw_pwm_configure`'s non-zero
`dead_time_ns`/`break_cfg` on an unsupported channel) and ADR-0002's amended
error-code convention ("a capability the backend or silicon lacks").
`firmware/gd32-bridge/src/protocol.c`'s `handle_pwm_set` gained the matching
`BRIDGE_HW_ERR_NOTIMPL` -> `STATUS_NOSUPPORT` mapping every other bridge
handler already has.

The host-side caches this issue named (`src/backends/pwm/gd32_bridge.c`'s
`br_set_period()` and `src/pwm_dispatch.c`'s `alp_pwm_set_period()`) already
only write their cached `period_ns` when the backend op returns `ALP_OK`, so
refusing the firmware side is sufficient on its own to stop the host from
recording a period that was never programmed.

Regression test: `tests/unit/pwm_gd32_bridge_period_refusal/`.
