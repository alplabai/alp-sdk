### Added — a gate flags a closed issue cited as an open driver-status blocker (#1950)

`metadata/chips/gd32g553.yaml`'s `driver_status: partial` comment named #495,
#494 and #496 as the open reasons the driver wasn't `complete`. All three had
closed months earlier -- #494/#495 via #730, #496 via #764 (#1949) -- and the
six chip-status gates (`check_stub_issues.py`, `check_stub_symbol_matrix.py`,
`check_driver_status_backing.py`, `check_chip_header_status.py`,
`check_sw_fallback_tags.py`, `check_vendor_ext_tags.py`) all stayed green
throughout: every one of them binds a status *word* to a source artefact,
never the free prose explaining it. A reader who follows a citation like
that into a closed issue either wrongly concludes the entry is done, or
re-does analysis the closing comment already has.

New `scripts/check_issue_citations.py` harvests `#NNNN` citations out of two
narrow, by-construction-a-claim-about-what-remains locations -- a
`<...>driver_status:` field's trailing YAML comment block
(`metadata/**/*.yaml`) and an `@par Driver status:` Doxygen paragraph
(`include/alp/chips/*.h`) -- and fails when a cited number resolves to a
closed/merged state while its own `.`/`;`-delimited clause reads as a
blocker claim. A citation whose clause carries a historical marker (`via`,
`closed`, `closing`, `landed`/`lands`, `fixed`, `resolved`, `merged`,
`shipped`, `done`, `already`) is skipped, not flagged -- "#494, #495 and #496
all closed (#494/#495 via #730, #496 via #764)" must not trip the gate the
day #1949 lands. Everywhere else (`changelog.d/`, `CHANGELOG.md`, ADR prose,
a `notes:` block, any other field's comment) is deliberately out of scope for
this first cut: those are full of legitimate historical references, and a
blanket `#NNNN` harvest over them is noise from day one. Widening there is
left for a follow-up if it turns out to be cheap.

The gate is offline by design -- a live `gh` call inside every PR run would
make it a network-flake gate on every metadata/** PR. It reads a committed
snapshot, `metadata/issue-state-snapshot.json`, refreshed by a human running
`python3 scripts/refresh_issue_state_snapshot.py`. There is no scheduled
workflow: an earlier draft ran it weekly and opened a PR via `gh pr create`
authenticated with `${{ github.token }}`, but GitHub does not start
`pull_request` workflows for events raised by `GITHUB_TOKEN`, so `dev`'s
required status checks (`twister-shard 1/4`..`4/4`, `clang-format · diff-only`,
`distro install · all`) would never report and that PR could never enter the
merge queue -- unmergeable by design, so the workflow was dropped rather than
shipped broken. Because refresh is manual, an ageing snapshot is the normal
case, not a rare cron miss: a stale-but-present snapshot still enforces every
citation it has a record for and prints one loud warning naming the refresh
command; only an entirely missing/unparsable snapshot, or a cited number the
snapshot has never seen, degrades that citation to a non-blocking warning
instead.

Registered in `metadata/quality-tasks-v1.json` (`issue-citations`, `pr` /
`full` / `release` profiles) and wired into
`pr-metadata-validate.yml:validate`, per the four-site rule in
`adding-a-ci-gate`.

Run against the real tree, the gate found six pre-existing instances of the
exact defect it exists to catch, not just the `gd32g553.yaml` case described
above: `metadata/chips/dp83825.yaml:4` citing the now-closed #1241/#1244, and
`include/alp/chips/pca9451a.h:10` citing the now-closed #474. All three
files' prose is fixed in this same change (`gd32g553.yaml` independently
again in #1949, which was still open as of this change and fixes the same
lines) -- a new gate that ships pointing at findings it doesn't itself
resolve would land red.
