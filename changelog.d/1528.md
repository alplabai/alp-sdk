### Fixed — `cross-platform-zephyr.yml` would have hung the merge queue the moment `python-smoke` becomes a required context (#1528)

The whole-directory sweep `pytest tests/scripts/` runs in exactly two
workflows — `cross-platform-zephyr`'s `python-smoke` (3-OS matrix) and
`pr-metadata-validate`'s `validate` (`ubuntu-latest`, `paths:` include
`tests/scripts/**`) — and NEITHER is a required status context on `dev` or
`main` today, confirmed live against both branches'
`required_status_checks.contexts`. A newly added `tests/scripts/` regression
gate (most recently the #1475 Actions template-injection guard and the
#1488 bench flash-verify guard) is therefore picked up only by those two
sweeps and posts an advisory, non-blocking red instead of gating the merge —
unless it is *also* named individually in a workflow with a required
context, which is the pattern a gate must opt into today to be enforced:
`pr-twister.yml`'s required `twister-shard` job names
`test_tier_a_workflow_step_timeouts.py` and `test_hil_blocks_coverage.py`
explicitly, so those two files do block on `dev` right now even though the
directory sweep that also runs them does not.
`test_workflows_are_loadable.py`'s own module docstring records how exactly
the non-required directory sweep let two unparseable workflows reach `dev`
before.

Promoting `python-smoke` to required is a live branch-protection setting
change, not a file, and stays a separate maintainer decision (the issue
itself flags an open question — whole matrix vs. `ubuntu-latest`-only — that
this change does not resolve). What this change fixes is a prerequisite bug
that would otherwise turn that promotion into a repeat of the #1474 incident:
`dev` runs an active merge-queue ruleset ("dev merge queue", confirmed via
`gh api repos/alplabai/alp-sdk/rulesets`), and GitHub raises `merge_group` —
not `push` or `pull_request` — for a queued entry. `cross-platform-zephyr.yml`
carried no `merge_group:` trigger, so once `python-smoke` became required, a
queued PR would wait forever on a check this workflow could never raise on
the queue's speculative ref (#1415) — the same trap `pr-twister.yml` and
`pr-static-analysis.yml` already document and guard against for their own
required contexts. Added the same bare `merge_group:` trigger here, with no
`paths:` filter (that event doesn't support the same filtering
`pull_request`/`push` get above). Since `merge_group` can't be `paths:`-
scoped, it would otherwise run the full 3-OS matrix (macOS billed 10x,
Windows 2x) on every `dev` merge-queue entry for both jobs even though only
the `ubuntu-latest` leg is a candidate for the eventual required context —
`python-smoke` and `loader-smoke` each scope their own
`strategy.matrix.os` down to `["ubuntu-latest"]` on `merge_group` (a
job-level `if:` can't do this: `matrix` isn't in the context list
`jobs.<job_id>.if` gets, only `jobs.<job_id>.strategy` does) while leaving
`pull_request`/`push` running all three legs unchanged.

Also corrected a stale claim in this same workflow's header comment: it
asserted `gh api repos/alplabai/alp-sdk/rulesets` returns `[]`, which is no
longer true now that the merge-queue ruleset exists. The comment now records
the real prerequisites still outstanding before promotion is safe — the
`merge_group` gap this change closes, and the separate `paths:`-filter gap it
does not: `pull_request`/`push` above still restrict this workflow to a
fixed path list, so a PR touching none of them never runs it at all, which
would reproduce #1474's permanently-blocked-PR failure mode the moment
`python-smoke` is required without also widening or removing that filter.
