### Added — V2N/V2M Linux DT: SSIU/I2S wiring reaches the TAS2563 codec pair (#1171)

`e1m-x-evk.dtsi` now carries a `rcar_sound` audio-graph playback path for
the carrier's two TAS2563 smart amps (U27 left, U28 right): two
`ti,tas2563` codec nodes on `&i2c0` (0x4D/0x4E), two independent
audio-graph ports (SSI1 -> left amp, SSI2 -> right amp, the R-Car "SSI
parallel mode" pairing that shares BCK/WS), and a `sound_card` joining
them. `CONFIG_SND_SOC_RCAR` and `CONFIG_SND_SOC_TAS2562` are both already
`y` in the vendored linux-renesas 6.1.141-cip43 build (confirmed against a
prior real bitbake `.config` for `e1m-v2m101-a55`, not just the mainline
defconfig), and `tas2563-audio.cfg`'s `CONFIG_SND_SOC_TAS2562=y` fragment
now has a DT consumer.

dtc-clean (zero new warnings vs. baseline) for both `e1m-v2n101-x-evk` and
`e1m-v2m101-x-evk` against the vendored linux-renesas source tree, with
every phandle in the new nodes resolved and hand-checked against the
decompiled `.dtb`. Not bench-verified -- no audible output claimed.

The `ssi1_pins`/`ssi2_pins` pinmux (port 4, pins 4-7) collided with the
existing `i2c6_pins`/`i2c7_pins`, which claimed the same four physical
pins with `&i2c6`/`&i2c7` both `status = "okay"`. Resolved: neither i2c6
nor i2c7 is in `metadata/boards/e1m-x-evk.yaml`'s `carrier: buses:` list
or in `renesas-peripheral-map.tsv`, while SSIU1/SSIU2 on those same pins
are, so `&i2c6`/`&i2c7` are now `status = "disabled"` and their pinctrl
groups are removed -- the audio path owns those four pads.

An earlier revision of this change wired the MCLK pinctrl group to
`RZV2N_PORT_PINMUX(9, 7, 8)` (AUDIO_CLKOUT), carried over unmodified from
the RZ/V2N EVK reference dts. That pad is P97 -- `GD32_SPI.CS0`, CM33-owned
across the AMP split -- and would have clobbered the supervisor SPI's CS
framing at every Linux boot, the same clobber class as the SD1_CD/P94
lesson already documented in this file. It is also architecturally wrong
for this carrier regardless of ownership: the TAS pair's MCLK comes from
an off-chip Renesas/IDT 5L35023B clock generator
(`metadata/chips/clk_5l35023b.yaml`) driving board net Audio_CLKB into SoC
pad P10, gated by an Audio_CLKB_OE GPIO on P67 -- not an SoC AUDIO_CLKOUT
function at all. Fixed by dropping the P97 claim; P10/P67 are NOT
CM33-owned, but `metadata/pinmux/v2n.yaml` has no verified SoC
alternate-function number for them (`e1m_function: "TBD"`, true for every
Renesas pad in this SoM today), so the corrected pinctrl group is left as
a TODO rather than inventing a function number -- `&rcar_sound` ships with
no MCLK pin claim; `clock-frequency` is descriptive only until it lands.

Still open, not silently fixed:
- Amp `shutdown-gpios` / `interrupts` (shared `\SD_N` / `IRQ_N`) and
  IV-sense capture are not wired -- playback-path DT only.
- The MCLK pinctrl group itself (P10/P67), pending the R9A09G056
  pin-function table.

The CM33/Zephyr half of #1171 is out of scope: no SSI/SSIU driver exists
in this tree, `hal_renesas`, or upstream.

**Two open questions flagged independently on `dev` while this was in
flight, neither answered here:** whether the RZ/V2N SSIU IP actually
answers to the `rcar_sound` (R-Car) binding used above, rather than a
different compatible this repo has not identified -- dtc-clean and
phandle-resolved is not the same claim as binding-correct-for-this-SoC;
and whether a kernel `ti,tas2563` codec node claiming I2C `0x4D`/`0x4E`
conflicts with the SDK's own userspace `chips/tas2563` driver, which
reaches those same addresses over `alp_i2c_*` (the nodes use the
per-strap addresses, not the `0x48` broadcast address `chips/tas2563.c`
exposes, so they do not collide on the wire, but the kernel driver vs.
userspace-`alp_i2c_*` ownership question -- who binds first, whether one
has to yield -- is unresolved). Both need a bench answer, not a guess.

### Removed — the TAS2562 kernel codec driver was enabled on V2N/V2M with no device-tree node to bind to (#1171)

`meta-alp-sdk/recipes-kernel/linux/linux-renesas/tas2563-audio.cfg` set
`CONFIG_SND_SOC_TAS2562=y` for `e1m-v2m101` and `e1m-v2n101`, pre-staging the
mainline ASoC driver that covers the carrier's two TAS2563 smart amps. Nothing
instantiated it. Each of those machines builds exactly one device tree —
`KERNEL_DEVICETREE = "renesas/e1m-v2n101-x-evk.dtb"` and
`"renesas/e1m-v2m101-x-evk.dtb"`, with V2N102/V2M102 reusing the V2N101 one —
and no `compatible` string starting `ti,tas` appears in any `.dts`/`.dtsi`
under `meta-alp-sdk/recipes-kernel/linux/linux-renesas/`. The fragment's own
comment admitted it: the driver "loads with no DT consumer (harmless no-op)".

The fragment and its two `SRC_URI:append` lines are gone. The BSP defconfig
(linux-renesas 6.1.141-cip43) does not set the symbol, so removing the
fragment returns the kernel to not-built rather than needing an explicit `=n`.
`display.cfg`, `trim-unused-storage-net-fs.cfg` and `no-kernel-audit.cfg` are
untouched.

Everything the fragment knew is now in the audio TODO block at the top of
`meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-x-evk.dtsi`, where the
implementer of the codec nodes will be reading, together with one fact that
was not recorded anywhere: landing a kernel codec node claims I2C `0x4D`/`0x4E`
away from the SDK's own userspace `chips/tas2563` driver, which reaches those
addresses over `alp_i2c_*`. That ownership call has to be made in the same
change as the nodes, not discovered afterwards.

### Notes — the missing SSIU/I2S device-tree node on V2N/V2M stays data-gated (#1171)

The other half of #1171 — no SSI/SSIU node on either core, so
`<alp/i2s.h>` falls through to `src/common/stub/stub_i2s.c` and returns
`ALP_ERR_NOSUPPORT` (lines 22, 28, 33, 41, 50) — is **not** fixable from this
repo, and no node was written.

On the Cortex-M33 side the blocker is upstream: Zephyr v4.4.0's
`dts/arm/renesas/rz/rzv/r9a09g056.dtsi`, which the generated M33 board trees
include, contains no SSI or I2S node at all, and the tree's only Renesas I2S
driver is `drivers/i2s/i2s_renesas_ra_ssie.c` behind the
`renesas,ra-i2s-ssie` binding — the RA-family SSIE, not the RZ/V SSIU+SSI. A
node here would need a new driver plus a fabricated register base, interrupt
and clock.

On the Linux side four SoC-side values are absent from this repo: the SSI/SSIU
node label the linux-renesas 6.1.141-cip43 `r9a09g056` dtsi exposes, its
binding (a comment in `e1m-x-evk.dtsi` said `rcar_sound`, an R-Car binding,
unverified for this SoC — now marked as such), the PFC function for the SSIU
pads, and the MCLK source and rate. The pad routing is not assigned either:
`metadata/pinmux/v2n.yaml:126-133` still carries `e1m_pad: "TBD"` and
`e1m_function: "TBD"` on all eight SSIU rows (`SSIU1_SSI1_SCK` on `P44`
through `SSIU4_SSI4_SDATA` on `P15`), and
`metadata/e1m_modules/E1M-V2N101.yaml:190-191` declares both `i2s0` and `i2s1`
with `driver_status: none`. Generating DT/pinctrl from that layer is #655.

The catalog's `peripherals.i2s: true` is left alone: it is derived from
`metadata/socs/renesas/rzv2n/n44.json:59` (`"i2s": 10`), a silicon fact that
is true whether or not a driver binds. Narrowing it to a
driver-availability claim is a catalog-semantics change across every SKU and
peripheral, not a V2N audio fix.
