### Fixed — an unverified AEN update-log image was booted before the verify could gate it (#1526)

`flash-update-log-firewall-probe.sh` and `flash-update-log-dual.sh` put `loadbin`,
`verifybin`, `RSetType 2`, `r` and `g` into **one** JLinkExe CommanderScript. JLinkExe
finished the whole script before the shell could read the verify result, so the SE had
already pin-reset and booted the image. The gate that followed could only suppress the
false "flash complete" report and the beacon read-back — it could not stop an unverified
image being booted, and the booted image is what appends to (or overwrites)
`alp_ulog_partition`.

Both scripts now use **two** CommanderScripts: `loadbin` + `verifybin` + `exit`, then the
shell evaluates the result, and only on success a second script carrying
`RSetType 2` / `r` / `g`. The gate is load-bearing rather than advisory.

The MRAM write itself still happens before the verify — that *is* `loadbin`, and it cannot
be otherwise. What is now prevented is **acting** on an image that failed to verify: with
`"flags": ["load", "boot"]` on the ATOC entry, not booting is exactly what keeps the HE
probe (firewall-probe) or the HP owner and the HE client it releases (dual) from running
and touching the update-log partition.

The exit-3 messages said "DATA LOSS: the board was already pin-reset and released ...
alp_ulog_partition may ALREADY have been overwritten". That is no longer true and would
now send an operator to re-verify a partition that is intact, so both copies in each
script are rewritten to say the board was not booted and the partition is untouched — the
correct remaining action being to reflash before booting. The "does NOT and CANNOT prevent
the write, or the boot" comment blocks are likewise corrected rather than left to rot.
