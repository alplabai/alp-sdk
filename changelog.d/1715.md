### Fixed — 10 of `CHANGELOG.md`'s 11 pre-existing `path:line` citation errors, ahead of extending `check_changelog_citations.py` to scan it (#1715)

`scripts/check_changelog_citations.py` only ever scanned `changelog.d/*.md`;
`CHANGELOG.md` itself — the merged history the gate exists to protect — was
never checked, so its citations rotted silently. Running the gate's own
`_check_one()` against `CHANGELOG.md` by hand found 11 pre-existing errors:
4 anchor-drift citations whose quoted anchor text no longer sat within the
cited line range because the code had moved, 5 bare filenames (no directory
component, so never path-checked before the gate existed) whose line numbers
had also never been verified, and 2 citations into files that no longer exist
in this tree.

Fixed 10, each re-verified against the real file rather than guessed (old
citation on the left, corrected one on the right):

```
include/alp/protocol/cc3501e.h:447                -> include/alp/protocol/cc3501e.h:534
firmware/cc3501e/hal/ti/cc3501e_hw_ti_wifi.c:715   -> firmware/cc3501e/hal/ti/cc3501e_hw_ti_wifi.c:781
src/zephyr/console/alp_console_companion_wifi.c:348 -> src/zephyr/console/alp_console_companion_wifi.c:416
```

The anchor-drift trio moved because the code moved: `ALP_CC3501E_WIFI_FAIL_KICK`'s
doc comment shifted 87 lines down `cc3501e.h`, the `wifi_conn_set(DISCONNECTED,
FAIL_NONE)` call shifted 66 lines down the TI HAL, and the console's
`fail_reason` print shifted 68 lines up. The bare-filename five had never been
path-checked at all before this gate existed, so their line numbers were never
verified either — `e1m-v2n102-a55.conf`'s old `:36` never pointed at the
hardcoded `KERNEL_DEVICETREE` line the prose actually describes; the TODO and
the hardcoded filename live at 44-48. `alp_project_loader.py`'s
`SDK_VERSION_FILE` had moved two lines. Both workflow citations are re-pointed
at the actual `pytest tests/scripts/` run step in each file.

The two dead-path citations are rewritten rather than line-shifted, preserving
the historical claim without pointing at something that doesn't exist:
`alp_cli/new_som.py` was deleted outright by #1727's `alp_cli` retirement (not
renamed within this repo), so the sentence now says so instead of citing a
line number nothing backs any more; the `Overview.md` citation was never an
alp-sdk path to begin with — it names the Alif DFP's own `Overview.md`, an
external vendor document this tree doesn't carry a copy of — reworded to say
that plainly instead of formatting it as if it were repo-relative.

The last one, `docs/abi/README.md:157`, had no honest line to re-point at:
its anchor quotes the phrase "no final `v0.15.0` tag exists yet", which #1622
(2026-08-25) removed from the file entirely when that note was rewritten to
reflect that the tag has since shipped for real. The text is not at a
different line -- it no longer exists anywhere in the file. Since the
`CHANGELOG.md` sentence is making a claim about what the tree recorded AT THE
TIME, it is reworded to say so explicitly ("`docs/abi/README.md`, which then
read ... (that note was rewritten in #1622 once v0.15.0 was actually tagged)")
rather than fabricating a line number or dropping the historical claim.

One gate bug is fixed here rather than deferred, because the citation work
above would otherwise have made coverage WORSE. `_CITATION`'s path group began
`[A-Za-z0-9_]`, requiring the first character to be alphanumeric or `_`, so a
citation whose path starts with a dot -- every `.github/workflows/*.yml:NNN` --
never matched the regex at all and was silently unchecked rather than reported.
Two of the bare filenames fixed above -- the `cross-platform-zephyr.yml` and
`pr-metadata-validate.yml` workflow citations -- DID match the regex while they
were bare; rewriting them to their real repo-relative `.github/...` paths would
have removed them from the gate's view entirely. The path group now accepts an optional leading dot. The regex is
anchored on backticks at both ends, so this cannot widen it into prose. Effect
on `CHANGELOG.md`: 81 citations resolved with 0 errors, up from 76 -- the three
`.github/...` citations that had already shipped unchecked all resolve
correctly. Two unit tests pin the dotted and undotted forms.

With those out of the way the gate now SCANS `CHANGELOG.md` itself -- the hole
this issue was filed for. It does NOT apply one verdict to the whole file:

* The `[Unreleased]` section is content still being written for a release that
  has not shipped. A citation there is cheap to fix and should be correct
  against `HEAD`, so it HARD-FAILS exactly like a `changelog.d/` fragment.
* Everything below it is the shipped historical record. Those entries describe
  the tree as it stood at THAT release, and ordinary refactoring moves the lines
  they cite through no fault of the entry. Hard-failing them would redden this
  gate on every unrelated PR that happens to move a cited line, and "fixing" one
  by re-pointing it at today's code silently changes what the entry historically
  claimed. They are reported as WARNINGS -- visible and actionable, never
  blocking.

Because the 11 errors above were fixed first, the scan lands GREEN on arrival
rather than failing immediately on `dev`, which is the order #1715 asked for:
104 citations resolved across 47 fragments + `CHANGELOG.md`, 0 errors, 0
warnings. Fixing a latent bug found by its own test: `main()` returned early
when `changelog.d/` was empty, which would have skipped the `CHANGELOG.md` scan
entirely in that state.
