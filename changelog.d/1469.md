### Proposed — ADR-0028: tan should own the model engine; alp-sdk keeps the NPU truth

`docs/adr/0028-tan-owns-the-model-engine.md` (Status: Proposed) records the
case for eventually moving `scripts/alp_model/` (13 modules, 1,029 lines) and
`scripts/alp_cli/model.py` to `python/tan/model/` in `alplabai/tan-cli`, so
tan becomes the single implementation of the host-side model pipeline. That
migration is NOT enacted by this change — `scripts/alp_model/` and
`scripts/alp_cli/model.py` are untouched and still live in this repo.

What this change lands now is the half of ADR-0028's decision alp-sdk is
uniquely authoritative for regardless of where the model engine ends up:
`metadata/npu_ops/`, `metadata/schemas/npu-ops-v1.schema.json`, the
`inference_arena_sram_kib` / vela-profile budgets, and the on-device
`.alpmodel` reader (`src/common/alp_model.c`). The `.alpmodel` container
format is the cross-repo seam and is unchanged.

This applies ADR-0026's principle — hardware truth stays in the repo that
owns the hardware; a consumer of it does not — to the second duplicated
surface. The measured trigger for the *proposal* (not yet enacted): `tan
model build` hand-ports 108 lines of this repo's board.yaml and
compile-option logic, that copy never received the alp-sdk#1271
`_PATH_OPT_KEYS` fix, and it currently corrupts DRP-AI's `input_shape`
(`"1,3,224,224"`), `input_name` (`"images"`) and `product` (`"V2N"`) by
resolving them as filesystem paths. The sha256 pin over
`scripts/alp_cli/model.py` could not see it: a pin proves the upstream file is
unchanged, never that the downstream port is equivalent.

No alp-sdk build path is affected — no CMake, Yocto recipe or example imports
the Python package. The migration itself is not enacted by this change; see
`docs/adr/0028-tan-owns-the-model-engine.md` for the full decision record.
