### Fixed — IMX335 full-resolution mode's `Y_OUT_SIZE` overrun, width bench-confirmed, line count not directly measured (#2334)

Upstream Zephyr's `drivers/video/imx335.c` all-pixel mode table
`imx335_bin_none` wrote `Y_OUT_SIZE` (`0x3056`) = `0x07ac` (1964 lines) for
a 2592x1944 format -- the same overrun class `zephyr/patches/zephyr/
0004-imx335-2lane-link-freq-and-binning.patch` already fixed for the
2x2-binned path (#2327). Both this driver's own `imx335_init_params`
(`Y_OUT_SIZE` `0x0798` = 1944) and the mainline Linux imx335 driver's
full-resolution mode table (`raspberrypi/linux`, branch `rpi-6.12.y` --
register value carried as a hardware fact, no GPL code copied) agree on
1944; `imx335_bin_none` is corrected to match. Patch 0004 extended (sha256
updated in `zephyr/patches.yml`), applies clean against a pristine Zephyr
v4.4.1 checkout.

No corresponding `HNUM`/`WINMODE` change was needed: unlike `imx335_bin_2x2`
(which set an explicit, bench-derived `HNUM` this driver had no formula
for), `imx335_bin_none`'s `HNUM` (restored to `0x0a20` = 2592 by #2327's own
fix) already matches both `imx335_init_params` and the Linux full-resolution
table, and its `AREA2_WIDTH_1`/`AREA3_WIDTH_1` pair (40 / 3928) already
matches the Linux table too.

**Bench runs 335-337 (E1M-AEN803 2026W36-0001), scratch-only diagnostics**:

- Run 335: the CPI's `CAM_INTR_VSYNC`/`CAM_INTR_HSYNC` interrupts do NOT
  fire while `CAM_CTRL_START` (the write-DMA arm bit) is left clear --
  DMA-free line counting, the plan this fragment originally proposed, is
  not possible on this hardware. The same run read the sensor's registers
  back in all-pixel mode and confirmed the patch's writes: `WINMODE 0x00`,
  `HTRIMMING_START 0x003c`, `HNUM 0x0a20`, `Y_OUT_SIZE 0x0798`.
- Run 336 (2x2-binned): the CPI's `CAM_VIDEO_FCFG` register's `ROW` field
  bounds a capture to exactly `ROW` lines in hardware, confirmed 4/4 -- a
  real, safe bounding mechanism. The originally proposed software fallback
  (an `INTR_HSYNC` handler calling `hw_cam_cpi_only_stop()` to cut the DMA
  after a couple of lines) does NOT work -- this run found the software
  stop does not actually halt the DMA in time. Filed as issue #2342; that
  fallback is now removed from `docs/camera-shields.md`'s recipe text.
- Run 337 (full-resolution 2592x1944, `CAM_VIDEO_FCFG`-bounded to 3 and 8
  rows): 2592 samples/line (5184 bytes, RAW10-packed), stride
  autocorrelation peak at exactly 5184 (= 2x2592, no row-to-row shear),
  canary intact both times, 4/4 identical. **Width is confirmed exactly
  2592 at full resolution**, matching `HNUM`. Caveat: the DW CSI-2 host's
  Camera-mode `hact` was itself set to 2592 for this capture, so a sensor
  line longer than 2592 samples truncated to `hact` is not excluded by
  this measurement alone.
- **Lines/frame (1944 vs. 1964) was NOT measured** -- HSYNC/VSYNC counting
  needs the DMA armed (run 335), and a full ~10 MB frame can't be written
  to prove the line count directly. This fix is still justified without
  that direct measurement: `CAM_VIDEO_FCFG`'s `ROW` field bounds the CPI's
  write to a fixed row count in hardware regardless of the sensor's own
  `Y_OUT_SIZE` value (run 336's finding), so upstream's buggy 1964 could
  never have overrun an `FCFG`-bounded capture buffer either way -- the
  memory-safety concern that motivated this diagnostic is independently
  covered by `FCFG` bounding. The `Y_OUT_SIZE` register fix itself remains
  justified by the two reference tables above, not by a bench measurement
  of the disputed line count.

See `docs/camera-shields.md`'s "Full-resolution mode: bench results (issue
#2334)" section for the full writeup. `metadata/chips/imx335.yaml` gains a
matching note.
