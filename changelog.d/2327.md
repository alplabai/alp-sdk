### Added — Sony IMX335 camera Stage A: link-frequency fix + INNO-MAKER CAM-IMX335-5MP shield (#2327)

Stage A only: raw first-light capture through `<alp/camera.h>`, no
ISP/AE/streaming. Unlike OV5647/OV9281/IMX296, this sensor's driver is
**not vendored into alp-sdk** — it reuses upstream Zephyr v4.4.1's own
`drivers/video/imx335.c` (`CONFIG_VIDEO_IMX335`, `compatible =
"sony,imx335"`) directly (ADR 0017 Tier 0), carrying one small repo patch
on top.

**`zephyr/patches/zephyr/0004-imx335-link-freq.patch`** (registered in
`zephyr/patches.yml`, applied via `west patch apply` the same way the
existing mcuboot/zephyr patches are — no in-repo mechanism was invented for
this): the upstream driver registers `VIDEO_CID_PIXEL_RATE` only, at a
value (396 MHz) matching none of its own INCK/lane-mode register tables
(24 MHz INCK, 2-lane 10-bit mode select a real 594 MHz link clock, 1188
Mbps/lane). `video_get_csi_link_freq()` (`video_common.c`) falls back to
approximating the D-PHY link frequency from `PIXEL_RATE` whenever a sensor
reports no `VIDEO_CID_LINK_FREQ` control; with the uncorrected 396 MHz that
approximation lands the DW CSI-2 host on 990 MHz (1980 Mbps/lane) instead
of 594 MHz — the same `ERRSOTSYNCHS`/`PHY_FATAL` storm signature OV5647
hit before its own fix (#2248). The patch corrects `PIXEL_RATE` to
237600000 (the value the driver's own register tables actually produce)
and registers `VIDEO_CID_LINK_FREQ` directly as a READ_ONLY int-menu
`{594000000}`, the same shape `imx296.c`'s own `link_freq` control already
uses, so `video_get_csi_link_freq()` never needs the `PIXEL_RATE` fallback
for this sensor. This correction is carried from the datasheet's own MIPI
output timing table — **not bench-measured**.

**`csi-pixclk-hz`** (new optional property, `zephyr/dts/bindings/video/
snps,designware-csi.yaml`; wiring in `struct csi2_dw_config` /
`csi2_dw_validate_data()`, `zephyr/drivers/video/video_csi_dw.{c,h}`):
Controller mode's own bare-derived IPI pixel-clock request (no bandwidth
margin) exceeds `alif_pixclk_set_rate()`'s 200 MHz ceiling for this 2-lane
sensor (237.6 MHz bare, 285.12 MHz margined) — unlike IMX296's single-lane
case, where the bare rate (118.8 MHz) fits and happens to land near the
sensor's own line rate. When present, `csi-pixclk-hz` REPLACES that
derived request with the shield's own explicitly stated IPI pixel clock;
absent (the default, 0), behaviour is byte-identical to before this
property existed — verified below by an unaffected IMX296 build. IMX296's
own shield does not set it.

**`zephyr/boards/shields/innomaker_cam_imx335/`** (new shield, same
file set as `innomaker_cam_ov9281`/`raspberry_pi_global_shutter_camera`:
`shield.yml`, `Kconfig.shield`, the overlay, `doc/index.rst`): 24 MHz
`fixed-clock`, CCI address 0x1A, 2 MIPI CSI-2 data lanes, Controller-mode
IPI timing (`csi-pixclk-hz = <133333333>`, `csi-hsa = <3>`, `csi-hbp =
<10>`, `csi-hline = <1972>`, `csi-vsa = <1>`, `csi-vbp = <254>`,
`csi-vtotal = <2250>`) derived in the overlay's own comment from the
sensor's read-back HMAX/VMAX register values and an ASSUMED 2x2-binned-mode
2H output-line pacing — **INFERRED, not a datasheet MIPI-timing-table
citation** (unlike the IMX296 shield's own derivation, which cites one).
Build with `SHIELD="e1m_evk_rpi_csi innomaker_cam_imx335"`.

`examples/aen/aen-camera-firstlight` gets a matching IMX335 `#elif`
requesting the sensor's 2x2-binned 1296x972 mode *explicitly* (the driver
boots at its native 2592x1944) plus a `testcase.yaml` scenario
(AEN801+AEN803, build-only — same as the other three sensors). `metadata/
chips/imx335.yaml` catalogues the part (`driver_status: none`, same
catalogue-only shape as `imx296.yaml`, allowlisted in
`scripts/check_chip_manifest_parity.py`'s `KNOWN_MANIFEST_NO_DRIVER`). See
`docs/camera-shields.md` for the full driver/shield derivation and the
decision NOT to add a `tests/zephyr/video_sensors` emulator+ztest (Tier 0
upstream driver, no alp-sdk-owned identity/init logic to re-prove) or a
`csi-pixclk-hz` unit test (`video_csi_dw.c` has zero existing test coverage
in this tree to extend, same as `csi-hline`/`csi-vtotal` before it).

**Bench-verified on E1M-AEN803 2026W36-0001, I2C identity ONLY**: the
module answers at CCI `0x1A`, the only device on the E1M-EVK's J5 camera
bus, and `STANDBY` (`0x3000`), `VMAX` (`0x3030`-`0x3032`), `HMAX`
(`0x3034`) and `LANEMODE` (`0x3a01`) all read back at their power-on-reset
defaults (`0x01`, `0x001194` = 4500, `0x0226` = 550, `0x03` respectively).
The module self-powers — CAM_EN (J5 pin 11) is untouched.

**NOT bench-verified — do not claim any of the following happened on
silicon**: CSI-2 D-PHY lock at 1188 Mbps/lane through the E1M SoM R2
pinout adapter (the highest measured link rate on any sensor on this bus
to date is 875 Mbps, on a different sensor); the shield's 2H output-line
pacing assumption and the Controller-mode IPI timing it produces; LP-11
clock-lane-park behaviour (`no-lp11-clock-lane-park` left unset pending a
bench result); and any frame ever captured through this shield, at any
resolution. The corrected `VIDEO_CID_PIXEL_RATE`/new `VIDEO_CID_LINK_FREQ`
values are carried from the datasheet, not measured.
