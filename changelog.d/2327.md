### Added — Sony IMX335 camera: raw capture bench-verified + INNO-MAKER CAM-IMX335-5MP shield (#2327)

Raw capture only, no ISP/AE/streaming. This sensor's driver is **not
vendored into alp-sdk** — it reuses upstream Zephyr v4.4.1's own
`drivers/video/imx335.c` (`CONFIG_VIDEO_IMX335`, `compatible =
"sony,imx335"`) directly (ADR 0017 Tier 1, upstream-native), carrying one
repo patch on top. Bench runs 316-331 on E1M-AEN803 2026W36-0001
root-caused three real upstream-driver bugs at this sensor's
2-lane/10-bit/1188 Mbps-per-lane configuration; all three are fixed by the
patch below and the fix is bench-verified end to end: **6/6 consecutive
clean 1296x972 RAW10 raw captures (run 330), 0 CSI CRC errors, 0 IPI-fatal
events, correct stride, no overrun.**

**`zephyr/patches/zephyr/0004-imx335-2lane-link-freq-and-binning.patch`**
(registered in `zephyr/patches.yml`, applied per-module by
`scripts/bootstrap.sh` via `west patch apply`, checked by
`scripts/verify_west_patches.py`):

1. **No `VIDEO_CID_LINK_FREQ`.** The driver registers `VIDEO_CID_PIXEL_RATE`
   only. `video_get_csi_link_freq()` (`video_common.c`) falls back to
   approximating the D-PHY link frequency from `PIXEL_RATE` whenever a
   sensor reports no `VIDEO_CID_LINK_FREQ` control; for this sensor's 396
   MHz `PIXEL_RATE` (a v4l2 pixel-array-clock convention value, unrelated to
   the per-lane D-PHY bit rate) that approximation lands the DW CSI-2 host
   on 990 MHz (1980 Mbps/lane) instead of the sensor's real 594 MHz link
   clock (24 MHz INCK, 2-lane 10-bit mode: 1188 Mbps/lane, link_freq =
   per-lane bit rate / 2) — the same `ERRSOTSYNCHS`/`PHY_FATAL` storm
   signature OV5647 hit before its own fix (#2248). The patch registers
   `VIDEO_CID_LINK_FREQ` directly as a READ_ONLY int-menu `{594000000}`, the
   same shape `imx296.c`'s own `link_freq` control already uses.
   `PIXEL_RATE` itself stays **untouched** — 396 MHz is the correct v4l2
   pixel-array-clock value per `<video-controls.h>`'s own convention, and
   `VIDEO_CID_LINK_FREQ` alone is what `video_get_csi_link_freq()` reads
   once registered.

2. **No SYSMODE / MIPI output-timing registers.** The driver never writes
   `SYSMODE` (`0x319e`) or the `0x3a18`-`0x3a28` MIPI output-timing block
   for ANY lane/rate combination — bench run 318 found this produces a
   payload-checksum/CRC error storm on the CSI-2 receiver at 1188
   Mbps/lane, even with LINK_FREQ fixed above. Writing the values the
   mainline Linux imx335 driver (`raspberrypi/linux`, branch `rpi-6.12.y`)
   programs for this exact lane count and bit rate (`SYSMODE=1` plus nine
   `REG16` values — register values carried as hardware facts, no GPL code
   copied) eliminated it — 0 CSI CRC errors (runs 319-330), including 6/6
   consecutive clean 1296x972 captures through the E1M SoM R2 pinout
   adapter (run 330): **this VERIFIES 2-lane CSI-2 D-PHY lock at 1188
   Mbps/lane on E1M-AEN803 2026W36-0001 + this E1M-EVK.** An 891 Mbps/lane
   alternative timing set also gave 0 CSI CRC errors on the link (run 320,
   a different `IMX335_INCKSEL`/INCK selection — that run still had bug 3's
   buffer overrun below, so no clean frame resulted at 891 Mbps, only a
   clean link) but is not carried in the product — this driver is
   hardcoded to its own 2-lane/10-bit mode, which this repo's shield feeds
   at 24 MHz INCK, i.e. the 1188 Mbps/lane path only.

3. **2x2-binned mode overruns its own buffer.** `imx335_bin_2x2` leaves
   `HNUM` at the full-resolution `0x0a20` (2592) and sets `Y_OUT_SIZE` to
   `0x03d8` (984) — the sensor then transmitted a 1308x984 frame into this
   driver's own 1296x972 buffer, a 12-pixel/12-line overrun corrupting
   memory past the buffer. Bench-derived model (run 322, `HNUM` swept until
   the transmitted width matched exactly): binned width = HNUM/2 + 12, so
   `HNUM` must be `0x0a08` (2568). `Y_OUT_SIZE` corrected to the exact 972
   lines (`0x03cc`, bench run 321); `OPB_SIZE_V` (`0x304c`) cleared to 0
   (the mainline Linux imx335 driver's own binned-mode value). `HNUM` is
   restored to `0x0a20` when switching back to full resolution
   (`imx335_bin_none`). **Not fixed**: `imx335_bin_none`'s own `Y_OUT_SIZE`
   (`0x07ac` = 1964) — both upstream Zephyr's own `imx335_init_params`
   (`Y_OUT_SIZE` `0x0798` = 1944) and the mainline Linux driver's
   full-resolution mode use 1944, so `0x07ac` is the same overrun class as
   bug 3 above for any full-resolution caller. Full-resolution mode is
   UNBENCHED (only the 2x2-binned mode is exercised) — tracked as issue
   #2334.

If bootstrapping against a Zephyr checkout that already has alp-sdk's
0001-0003 patches applied, re-running the whole patch list fails
re-applying 0001 (`west patch` is not idempotent against an already-patched
tree) — apply 0004 by hand (`git apply` from the Zephyr repo root) or start
from a clean checkout.

**`csi-pixclk-hz` extended to Camera mode** (`zephyr/dts/bindings/video/
snps,designware-csi.yaml`; `struct csi2_dw_config` / `csi2_dw_validate_data()`,
`zephyr/drivers/video/video_csi_dw.{c,h}`) — originally Controller-mode
only, now effective in EITHER `ipi-mode`. Bench measurement (runs 329/330)
found this sensor's ACTUAL binned-mode line period (29.63 us, ~4H at HMAX
550, 972 HSYNC/frame) could not be matched by a Controller-mode
`csi-hline`/`csi-vtotal` pair the way IMX296's could — this driver never
surfaces that measured line period as a register read or control, so a
Controller-mode DT constant can't be derived from it reliably. The shield
below uses Camera mode instead, and Camera mode's own margined request
(285.12 MHz) *and* bare request (237.6 MHz) both exceed
`alif_pixclk_set_rate()`'s ~200 MHz practical ceiling for this 2-lane
sensor — so `csi-pixclk-hz` needed the same integer-pass-through override
Controller mode already had. An explicit `csi-pixclk-hz` that the clock
controller cannot reach now fails loudly (`LOG_ERR`) in EITHER mode, no
silent fallback to the derived request. Camera mode with an explicit
`csi-pixclk-hz` also switches the driver's legacy HSD derivation
(`csi2_dw_validate_data()`'s CAM branch) to a lanes-aware formula (divides
by `(pll_fin<<1)*num_lanes` instead of the legacy `(pll_fin<<1)` alone,
which OV5647/OV9281 remain bench-proven against and is therefore
UNCHANGED when this property is absent). A separate same-day fix
(commit before this one) corrected `csi-pixclk-hz`'s Controller-mode
pass-through from `float` to a direct integer (a `float`'s 24 mantissa
bits rounded `133333333` up to `133333336`, landing the wrong clock
divisor) — carried forward unchanged here.

**`zephyr/boards/shields/innomaker_cam_imx335/`** (new shield, same file
set as `innomaker_cam_ov9281`: `shield.yml`, `Kconfig.shield`, the overlay,
`doc/index.rst`): 24 MHz `fixed-clock`, CCI address 0x1A, 2 MIPI CSI-2 data
lanes, **Camera mode** with `csi-pixclk-hz = <200000000>`. Bench
measurement (runs 329/330) established the sensor's real binned-mode line
period (~4H, 29.63 us) and found Controller mode (a fixed
`csi-hline`/`csi-vtotal` pair) could not be made to match it — see the
overlay's own comment for the full reasoning. Build with
`SHIELD="e1m_evk_rpi_csi innomaker_cam_imx335"`.

`examples/aen/aen-camera-firstlight` gets a matching IMX335 `#elif`
requesting the sensor's 2x2-binned 1296x972 mode *explicitly* (the driver
boots at its native 2592x1944) plus a `testcase.yaml` scenario
(AEN801+AEN803, build-only), a `Kconfig` buffer-sizing override
(`ALP_SDK_CAMERA_ZEPHYR_VIDEO_VBUF_COUNT`/`VIDEO_BUFFER_POOL_NUM_MAX` = 1,
`VIDEO_BUFFER_POOL_HEAP_SIZE` = 2.75 MiB for `VIDEO_IMX335` — the
2x2-binned frame, 2,519,424 bytes, does not fit the plain 2-buffer/2-MiB
defaults every other shield uses), and discards the first captured frame
after stream start for this sensor (bench runs 329-331: the first
post-STANDBY frame was bad every time it was checked — darkened lower
rows, all-zero rows, or near-black rows, in three different runs — while
the second capture was clean every time; bench-justified, though the root
cause is still not confirmed). `metadata/chips/imx335.yaml` catalogues the
part (`driver_status: none`, same catalogue-only shape as `imx296.yaml`,
allowlisted in `scripts/check_chip_manifest_parity.py`'s
`KNOWN_MANIFEST_NO_DRIVER`). See `docs/camera-shields.md` for the full
driver/shield derivation and the decision NOT to add a
`tests/zephyr/video_sensors` emulator+ztest (this patch's fixes are already
bench-verified directly against real silicon, a stronger proof for this
specific hardware than an emulator ztest would add) or a `csi-pixclk-hz`/
Camera-mode-HSD unit test (`video_csi_dw.c` has zero existing test coverage
in this tree to extend, same reasoning as `csi-hline`/`csi-vtotal` before
it).

**Bench-verified on E1M-AEN803 2026W36-0001 (bench runs 316-331)**: 2x2-binned
1296x972 RAW10 raw capture through `<alp/camera.h>` — 6/6 consecutive clean
captures (run 330), 0 CSI CRC errors, 0 IPI-fatal events, correct stride,
no overrun. **This VERIFIES 2-lane CSI-2 D-PHY lock at 1188 Mbps/lane on
E1M-AEN803 2026W36-0001 + this E1M-EVK through the SoM R2 pinout adapter**
(runs 319-330). The module answered at CCI `0x1A` (the only device on the
E1M-EVK's J5 camera bus) with `CAM_EN` (J5 pin 11) untouched, and
`STANDBY`/`VMAX`/`HMAX`/`LANEMODE` all read back at their power-on-reset
defaults before the patch's config writes. D-PHY Stop-state check
(`STOPSTATE 0x00010003` before stream start) passed normally once the
patch's MIPI-timing registers were written — no
`no-lp11-clock-lane-park`-style skip property was needed. **That E1M-EVK
carries the J5 pin-11 pull-up rework** (`docs/boards/e1m-evk.md`,
originally fitted for OV5647) — `CAM_EN` being untouched proves nothing
about whether this module self-enables on a *stock* carrier; that remains
unestablished, and IMX335 is not added to that doc's self-enables list.

**Run 331 — PRODUCT-CODE confirmation**: the committed tree (`fbf9c8de3`)
with ONLY patch 0004 applied on a pristine Zephyr v4.4.1 checkout (sha256
matches the committed patch file), no diag-only code. The kept (second)
frame was clean: 0 IPI/CRC error lines, only one `FRAME_SEQ` event at
start, correct stride, 0 near-black rows, nothing written past the buffer,
a clean close, and `CSI_PIXCLK_CTRL` read back `0x00020001` (divisor 2 =
200 MHz, matching this shield's `csi-pixclk-hz`). `csi-halt-en` was left at
its default — no IPI-halt/"nohalt" DT override was needed. The discarded
first frame was bad in both loads this run checked: near-black rows
466-583 in one, all-zero rows 759-778 in the other.

**NOT bench-verified — do not claim any of the following happened on
silicon**: frame rate/fps (not measured); the module self-enabling on a
stock, non-reworked carrier (the J5 pin-11 rework is a module-enable
concern, unrelated to D-PHY lock); D-PHY lock on any unit/carrier other
than E1M-AEN803 2026W36-0001 on this specific E1M-EVK; the 891 Mbps/lane
alternative timing set (bench-confirmed clean on the link but not carried
in the product); ISP/AE/colour (no ISP path exists for this sensor); and
the sensor's full-resolution (non-binned) mode.
