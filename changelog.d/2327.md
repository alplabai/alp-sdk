### Added — Sony IMX335 camera Stage A: link-frequency fix + INNO-MAKER CAM-IMX335-5MP shield (#2327)

Stage A only: raw first-light capture through `<alp/camera.h>`, no
ISP/AE/streaming. Unlike OV5647/OV9281/IMX296, this sensor's driver is
**not vendored into alp-sdk** — it reuses upstream Zephyr v4.4.1's own
`drivers/video/imx335.c` (`CONFIG_VIDEO_IMX335`, `compatible =
"sony,imx335"`) directly (ADR 0017 Tier 1, upstream-native), carrying one
small repo patch on top.

**`zephyr/patches/zephyr/0004-imx335-link-freq.patch`** (registered in
`zephyr/patches.yml`, applied per-module by `scripts/bootstrap.sh` at
`west update` time via `west patch apply`, checked by
`scripts/verify_west_patches.py`): the upstream driver registers
`VIDEO_CID_PIXEL_RATE` only, and no `VIDEO_CID_LINK_FREQ`.
`video_get_csi_link_freq()` (`video_common.c`) falls back to approximating
the D-PHY link frequency from `PIXEL_RATE` whenever a sensor reports no
`VIDEO_CID_LINK_FREQ` control; for this sensor's 396 MHz `PIXEL_RATE` (a
v4l2 pixel-array-clock convention value, unrelated to the per-lane D-PHY
bit rate) that approximation lands the DW CSI-2 host on 990 MHz (1980
Mbps/lane) instead of the sensor's real 594 MHz link clock (24 MHz INCK,
2-lane 10-bit mode: 1188 Mbps/lane, link_freq = per-lane bit rate / 2) —
the same `ERRSOTSYNCHS`/`PHY_FATAL` storm signature OV5647 hit before its
own fix (#2248). The patch registers `VIDEO_CID_LINK_FREQ` directly as a
READ_ONLY int-menu `{594000000}`, the same shape `imx296.c`'s own
`link_freq` control already uses, so `video_get_csi_link_freq()` never
needs the `PIXEL_RATE` fallback for this sensor. `PIXEL_RATE` itself is
left **untouched** — 396 MHz is the correct v4l2 pixel-array-clock value
per `<video-controls.h>`'s own convention, not a D-PHY-derived value
needing correction (an earlier draft of this patch also "corrected"
`PIXEL_RATE`; dropped on review as unnecessary and unlikely to survive
upstream). The link frequency itself is carried from the datasheet's own
MIPI output timing table — **not bench-measured**.

If bootstrapping against a Zephyr checkout that already has alp-sdk's
0001-0003 patches applied, re-running the whole patch list fails
re-applying 0001 (`west patch` is not idempotent against an already-patched
tree) — apply 0004 by hand (`git apply` from the Zephyr repo root) or start
from a clean checkout. Without 0004 applied, this shield's D-PHY runs at
990 MHz instead of 594 MHz and the CSI-2 receiver logs an
`ERRSOTSYNCHS`/`PHY_FATAL` error storm.

**`csi-pixclk-hz`** (new optional property, `zephyr/dts/bindings/video/
snps,designware-csi.yaml`; wiring in `struct csi2_dw_config` /
`csi2_dw_validate_data()`, `zephyr/drivers/video/video_csi_dw.{c,h}`):
Controller mode's own bare-derived IPI pixel-clock request (no bandwidth
margin) exceeds `alif_pixclk_set_rate()`'s ~200 MHz practical ceiling for
this 2-lane sensor (237.6 MHz bare, 285.12 MHz margined) — unlike IMX296's
single-lane case, where the bare rate (118.8 MHz) fits and happens to land
near the sensor's own line rate. When present, `csi-pixclk-hz` REPLACES
that derived request with the shield's own explicitly stated IPI pixel
clock; absent (the default, 0), behaviour is byte-identical to before this
property existed — verified below by an unaffected IMX296 build. IMX296's
own shield does not set it. An explicit `csi-pixclk-hz` that the clock
controller cannot reach now fails loudly (`LOG_ERR`, no silent fallback to
the bare derived rate — a silent fallback would run different, undocumented
timing than what the shield's own comment claims); setting it outside
Controller mode now logs a `LOG_WRN` (it has no effect there). Neither
`csi-hline`/`csi-vtotal`'s own `hsd`/`vfp` derivation (computed purely from
DT + the format's `hact`/`vact`, unaffected by this property) changed.

**`zephyr/boards/shields/innomaker_cam_imx335/`** (new shield, same
file set as `innomaker_cam_ov9281`: `shield.yml`, `Kconfig.shield`, the
overlay, `doc/index.rst`): 24 MHz `fixed-clock`, CCI address 0x1A, 2 MIPI
CSI-2 data lanes, Controller-mode IPI timing (`csi-pixclk-hz =
<133333333>`, `csi-hsa = <3>`, `csi-hbp = <10>`, `csi-hline = <1972>`,
`csi-vsa = <1>`, `csi-vbp = <254>`, `csi-vtotal = <2250>`) derived in the
overlay's own comment from the sensor's read-back HMAX/VMAX register
values and an ASSUMED 2x2-binned-mode 2H output-line pacing — **INFERRED,
not a datasheet MIPI-timing-table citation** (unlike the IMX296 shield's
own derivation, which cites one). A large `csi-vbp` anchored at Frame
Start delays the first active IPI line by an UNVERIFIED ~3.77 ms with zero
FIFO margin left in the derivation; a second file,
`innomaker_cam_imx335-vbp4.overlay` (same directory, selectable via
`-DEXTRA_DTC_OVERLAY_FILE`), carries IMX296's own bench-proven
`csi-vbp=4`/an alternative `csi-vtotal=2000` as the first bench comparison
point — neither combination is claimed correct. Build with
`SHIELD="e1m_evk_rpi_csi innomaker_cam_imx335"`.

`examples/aen/aen-camera-firstlight` gets a matching IMX335 `#elif`
requesting the sensor's 2x2-binned 1296x972 mode *explicitly* (the driver
boots at its native 2592x1944) plus a `testcase.yaml` scenario
(AEN801+AEN803, build-only — same as the other three sensors), and a
`Kconfig` buffer-sizing override (`ALP_SDK_CAMERA_ZEPHYR_VIDEO_VBUF_COUNT`/
`VIDEO_BUFFER_POOL_NUM_MAX` = 1, `VIDEO_BUFFER_POOL_HEAP_SIZE` = 2.75 MiB
for `VIDEO_IMX335`) — the 2x2-binned frame (2,519,424 bytes) does not fit
the plain 2-buffer/2-MiB defaults every other shield uses, same
one-buffer-plus-margin shape as IMX296's own override. `metadata/
chips/imx335.yaml` catalogues the part (`driver_status: none`, same
catalogue-only shape as `imx296.yaml`, allowlisted in
`scripts/check_chip_manifest_parity.py`'s `KNOWN_MANIFEST_NO_DRIVER`). See
`docs/camera-shields.md` for the full driver/shield derivation and the
decision NOT to add a `tests/zephyr/video_sensors` emulator+ztest (Tier 1
upstream driver, no alp-sdk-owned identity/init logic to re-prove) or a
`csi-pixclk-hz` unit test (`video_csi_dw.c` has zero existing test coverage
in this tree to extend, same as `csi-hline`/`csi-vtotal` before it).

**Bench-verified on E1M-AEN803 2026W36-0001, I2C identity ONLY**: the
module answered at CCI `0x1A`, the only device on the E1M-EVK's J5 camera
bus, with CAM_EN (J5 pin 11) untouched, and `STANDBY` (`0x3000`), `VMAX`
(`0x3030`-`0x3032`), `HMAX` (`0x3034`) and `LANEMODE` (`0x3a01`) all read
back at their power-on-reset defaults (`0x01`, `0x001194` = 4500, `0x0226`
= 550, `0x03` respectively). **Correction to this bench result's framing**:
that E1M-EVK carries the J5 pin-11 pull-up rework (`docs/boards/e1m-evk.md`,
originally fitted for OV5647) — CAM_EN being untouched proves nothing about
whether this module self-enables on a *stock* carrier; that remains
unestablished, and IMX335 is not added to that doc's self-enables list.

**NOT bench-verified — do not claim any of the following happened on
silicon**: CSI-2 D-PHY lock at 1188 Mbps/lane on a 2-lane sensor through
the E1M SoM R2 pinout adapter — 1188 Mbps/lane itself IS bench-proven, but
only on data lane D0 (IMX296, 1 lane, run 292); D1 through the adapter is
untested; the shield's 2H output-line pacing assumption, the
Controller-mode IPI timing it produces, and which of the two `csi-vbp`
candidates (if either) is correct; LP-11 clock-lane-park behaviour
(`no-lp11-clock-lane-park` left unset pending a bench result); and any
frame ever captured through this shield, at any resolution. The new
`VIDEO_CID_LINK_FREQ` value is carried from the datasheet, not measured.
