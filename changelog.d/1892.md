### Changed — ADR 0026 §C and §D decided: alp-sdk keeps the configure-time call and stays canonical for rendered bytes (#1892)

ADR 0026's 2026-08-30 amendment raised §C and §D as open questions and stopped
short of answering them — §C ends "Decide which, here, before step 3", and §D
warned that leaving the render-artefact owner implicit "recreates the #320 →
#485 drift class one layer down, now undetected." Both are now decided and
recorded in the ADR.

**§C — who answers `alp_project.py --emit zephyr-conf --core <id>` at
cmake-configure time: alp-sdk does, via a surviving emitter core. The call is
not repointed at `tan`.** Alp Lab ships SoMs; a customer running a plain
`west build` must not thereby acquire a hard dependency on a second tool that
was nowhere in their loop, and repointing the call at `tan` would do exactly
that for every user project build, including ones already shipped to
customers that no repo-side change can reach. This is the same direction
ADR-0017 and ADR-0020 already set: the SDK ships with the hardware, the build
CLI is optional convenience layered above it.

**§D — single owner for rendered-artefact bytes: alp-sdk's emitters are
canonical.** `tan` consumes plan-embedded bytes instead of re-implementing the
renderers. Rendering `alp.conf` / sysbuild / kconfig / headers / secure bytes
is hardware-truth generation from `metadata/`, and the producer and renderer
of hardware truth belong in the same repo. The 19-of-20 `--emit` modes
currently re-implemented in tan against alp-sdk's raw metadata are what goes
away under this decision; the parity apparatus shrinks to a render-envelope
gate rather than being deleted with the planner axis. That gate's
implementation is not decided here.

Neither decision reverses the ADR: `tan` still owns the planner outright and
alp-sdk still stops being a second plan producer. Only the renderers — the
`alp.conf` / sysbuild / kconfig / headers / secure emitters and the
configure-time `--emit zephyr-conf` call — stay in alp-sdk. §G's replacement
migration sequence is updated to match: step 3 now repoints only the
plan-producer consumers at `tan`, leaving every renderer-owned emit-registry
entry resolving to alp-sdk's surviving core, and step 6 clarifies that
deleting the planner parity axis in tan does not touch the separate
render-envelope gate §D requires.

One concrete consequence, named so it does not need rediscovering: tan-cli's
eleven vendored `CMakeLists.txt` templates that spawn
`${ALP_SDK_ROOT}/scripts/alp_project.py --emit zephyr-conf` at build time
(tan-cli#1079) are correct as written under this decision and stay unchanged.

Docs only; no code, schema or metadata change.
