### Added — synthetic SoM preset fixture covers the unresolved-base routing #2053/#2102 removed (#2096)

`mram_main.base` resolves to `0x80000000` on all seven AEN presets (#2053,
#2102), so no shipped preset authors an unresolved `memory_map:` base any
more. That was the only shipped-preset producer of that shape anywhere in the
tree, so it was also the only end-to-end path through
`scripts/alp_orchestrate/memory.py::_resolved_row()`'s unresolved-base leg
and `scripts/alp_orchestrate/carveout.py::_region_ipc_eligibility()`'s
`cls == "unresolved"` tail. The tests that cover those legs are direct calls
into the private helpers, which keep the legs green in isolation but prove
nothing about the WIRING that routes an unresolved row into them in the
first place -- a change that filtered unresolved rows out earlier (say in
`carveout.py::_candidate_regions()`, before `_region_ipc_eligibility()` is
ever called) would leave every direct pin green while the live guard went
dead.

`tests/scripts/_orchestrate_support.py` gains
`_synthetic_aen_unresolved_base_root()`, a sibling of the existing
`_synthetic_nx9101_root()`: a scratch metadata root carrying a synthetic
`E1M-AEN899` preset (not a real SKU) under `alif:ensemble:e3` -- an Alif SoC
that DOES declare an on-die MRAM aperture, so the aperture-dependent branches
are reached rather than short-circuited by `aperture is None`. Its
`memory_map:` is a verbatim copy of `metadata/e1m_modules/E1M-AEN301.yaml`'s
seven rows as they stood before #2053/#2102, `mram_main`'s `base: "TBD"`
included. Two new tests drive it through the full `load_board_yaml` ->
`resolve_memory_regions()` / `resolve_carve_outs()` pipeline rather than
calling the private helpers directly, so the routing into both legs stays
covered end to end alongside (not replacing) the direct-call pins.
