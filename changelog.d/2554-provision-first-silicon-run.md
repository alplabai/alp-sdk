### Fixed — provisioning tool fixes from the first V2M103 silicon run (#2554)

The first real-hardware pass of `scripts/provision_som.py` surfaced four defects and one missing option, each now covered by a test under `tests/scripts/test_provision_*.py`.

`scripts/provision/linux_target.py:417` ("if [ $n -ge {poll_ms} ]; then exit 3; fi; done") fixes the EEPROM write-cycle ACK poll: the old `[ $n -ge N ] && exit 3` body was a false test after any retry, so the `until` loop exited 1 and every real write reported failure after a good write.

`scripts/provision/steps.py:1285` ("Steps finished in EARLIER invocations") makes `record` merge the evidence of steps already `done`/`skipped` in the state file, with this run's facts winning, so `--only`/`--from` runs still fill the ledger. `Gd32Flash` now records `gd32_fw_version` from `<gd32-fw>/VERSION`, and `census` records `dtb_name` from `/proc/device-tree/{model,compatible}`.

`scripts/provision_som.py` gains `run --hw-rev rN`, applied after the bundle hash so earlier steps stay valid when a batch mixes module revisions. Target SSH ignores host keys (`StrictHostKeyChecking=no`, `UserKnownHostsFile=/dev/null`; units reuse DHCP addresses and the SD and eMMC images carry different keys) and uses `ConnectTimeout=5`, and unit identity is checked instead: `Ctx.need_linux`, the gateway of every Linux-mutating step, reads the eMMC CID over SSH fresh on each call (never cached) and refuses (naming host, seen CID, expected CID and serial) when it differs from the `emmc_cid_raw` recorded for that serial, and `secure_page_lock` calls it again right before the irreversible write. The recorded CID is looked up in the state (including `superseded` steps), then in the committed `<serial>.unit.yaml`; first contact with no recorded CID is unchecked (bootstrap's `EM_DCID` records it on the normal blank-unit path). `run --accept-cid-change REASON` adopts the SSH-seen CID and records an `emmc_cid_change` override (blocks shipping) only when a recorded CID existed and differed. MID..MDT are compared with the reserved bits 119:114 masked, not the last byte: the writer prints the CRC, but `scripts/provision/linux_target.py` "cid_identity" notes `scif_writer.parse_cid` rebuilds the register (reserved bits cleared, end bit forced) and host drivers differ on the last byte sysfs returns. `--hw-rev` is validated against the family's `hw-revisions.yaml` and refuses (exit 2) an unknown, wrong-case or non-`production` key. Output is forced to `errors="replace"` at startup so a U+FFFD from serial text no longer crashes a cp1252 Windows console.

**BEHAVIOUR CHANGE.** V2N101/102/103 and V2M101/102/103 are one physical PCB, and every current module is board `2625-R2`. `metadata/e1m_modules/v2n/hw-revisions.yaml` now declares `board_datecode: "2625"` like `v2n-m1`, `r2` is a `production` revision (`board_rev: "R2"`), and all six V2N/V2M SKU presets default to `default_hw_rev: r2`. The EEPROM `hw_rev` field and `CONFIG_ALP_SDK_SOM_HW_REV` for a default V2N/V2M build therefore change from `r1` to `2625-r2`. Units provisioned earlier with a bare `r1` mismatch the new build (fatal with `CONFIG_ALP_SDK_HW_REV_MISMATCH_FATAL`) until they are re-provisioned. The composed string is limited to 7 characters (`2625-r2` fits, `2625-r10` does not).
