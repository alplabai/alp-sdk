### Fixed — LVGL could draw onto a recycled display handle (#1698)

`alp_gui_lvgl_attach()` caches the `alp_display_t *` in LVGL's user-data and has no
matching detach, so `_flush_cb()` reads it back on every frame forever.

**The filed diagnosis was that this dereferences a closed handle. It does not, and the
real hazard is worse.** `alp_display_blit()` already gates on the lifecycle byte and
returns `ALP_ERR_NOT_READY`, and the handle pool is `static`, so a closed display yields a
silently dropped frame and never a use-after-free. What actually bites is **slot reuse**:
`alp_display_close()` followed by `alp_display_open()` hands the same address to a
*different* display, whose lifecycle reads `OPEN` — so the blit **succeeds, against
somebody else's screen**. Silent wrong-display corruption, not a crash.

A raw pointer therefore cannot identify a display across a close/open pair. `struct
alp_display` gains an `epoch` generation counter, bumped on every fresh claim and placed
*after* `in_use` so the allocator's `memset(..., offsetof(..., in_use))` cannot reset it.
`attach()` snapshots the epoch alongside the pointer and `_flush_cb()` re-compares before
blitting, skipping the frame on a mismatch — `lv_display_flush_ready()` is still called
either way, so the render loop never wedges, matching the existing failed-blit contract.

This needs **no new public API**, which sidesteps the decision the issue was blocked on:
its three options were adding `alp_gui_lvgl_detach()` (new surface on an `[ABI-STABLE]`
contract), refusing the close (impossible — `alp_display_close()` returns `void`), or
documenting the footgun. The corrected diagnosis makes a fourth option available that none
of the three required.

Also closes a leak on the new `NOMEM` path: the render buffer is freed when the binding
allocation fails, since a bind-up that never completed has no "persistent for the process
lifetime" claim on it.
