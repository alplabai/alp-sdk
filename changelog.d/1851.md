### Documented — ADR 0033: the SDK declares support policy as data, and exactly one normative evaluator applies it (#1851)

The SDK refuses builds on grounds it presents as facts about silicon, and some of them are
not. `board.yaml` setting the other class's runtime -- `zephyr` on a Cortex-A, `yocto` on a
Cortex-M -- is refused at `scripts/alp_orchestrate/validate.py:270-282`, reached from
`scripts/alp_orchestrate/loader.py:910`, with an error telling the customer its runtime "is
determined by the core class". Upstream Zephyr at the pinned v4.4.1 ships
`arch/arm/core/cortex_a_r/`, so Zephyr does run on Cortex-A: alp-sdk **chose** to carry two
OSes and pair one to each core class, which is a product decision, not physics.
`scripts/alp_orchestrate/topology.py:92`'s "A Cortex-A can't run Zephyr" states it as
impossibility and is inaccurate as written.

`docs/adr/0033-support-policy-is-declared-data-with-one-normative-evaluator.md` records the
shape: support policy is declared as versioned, schema-backed data; exactly **one** normative
evaluator turns a declared policy into a verdict; consumers call it or carry a hash-pinned
audited port rather than re-deriving it from prose. The evaluator stays in alp-sdk `scripts/`
because 251 configure-time `CMakeLists.txt` invocations of
`${ALP_SDK_ROOT}/scripts/alp_project.py --emit zephyr-conf --core <id>` and the four
`west alp-*` commands reach `load_board_yaml` with no tan in the process -- so a plain
`west build` keeps every refusal it has today. Declared policy is constrained (exact values
only, derived closed codomain, `required` + `additionalProperties: false` + `schemaVersion`,
no catch-all entry, totality proved by a gate rather than by ordering, normative miss
semantics) so the evaluator stays a small total lookup and a second-language port is provable
rather than trusted. And a refusal that enforces a support decision must say so.

Three measurements motivate it. The rule is restated three times
(`scripts/alp_orchestrate/topology.py:28-43`, `scripts/alp_orchestrate/topology.py:80-87`, `tan-cli` `python/tan/core/os_class.py`) and the
copies have **already diverged**: on an unresolved core type alp-sdk `_allowed_os_for_core("")`
returns `["baremetal", "off"]` while tan returns `[]`, and `_default_os_from_core_type(5)`
raises `AttributeError` where tan normalises -- tan took the tan-cli#914 / tan-cli#957 fix and
alp-sdk did not (#1852). The field built to carry the decision is unused: all **26**
`topology.<core>` entries across the twelve `metadata/e1m_modules/*.yaml` presets omit `os`,
and `som-preset-v1.schema.json` `$defs.topology_entry` has `required: []`, so
`scripts/alp_orchestrate/loader.py:555`'s preference for the declared value has never once been exercised. And
`metadata/` already carries decisions alongside hardware truth (`emit-registry-v1.json`,
`quality-tasks-v1.json`, `toolchains.json`, `bootstrap.json`, `library-aliases-v1.json`,
`registries/`), which is why "policy metadata" has been naming two different things.

`docs/board-config-schema.md`'s "OS inference from core type" section is rewritten for
customers: the refusal is kept, but named as a support boundary with the exact error text, and
the previous claim that the runtime is "mapped to the silicon class, not chosen" is corrected.
The seam spec records the same correction plus the distinction the earlier draft blurred --
prong (b) can mean "the SDK evaluates at emit time and stamps the outcome" or "the decision is
authored once and read back", and only the second removes evaluation from the build path.

ADR 0033 narrows ADR 0026 clause 2's *justification*, not its decision: clause 2 keeps
`metadata/` in alp-sdk because "Those are hardware truth", which describes only half the
directory. Docs only; no schema, metadata or code change -- `docs/README.md`'s ADR count moves
30 -> 31.
