### Fixed — `docs/gd32-bridge-protocol.md` documented `STATUS_NOMEM` for DSP chain-pool exhaustion; the firmware returns `STATUS_NOSUPPORT` (0x06) (#1496)

`CMD_ADC_DSP_CHAIN_OPEN`'s doc text claimed pool exhaustion returns `STATUS_NOMEM` (`0x07`), but
`bridge_hw_adc_dsp_chain_open()` returns `BRIDGE_HW_ERR_NOTIMPL`, which `status_from_hw()` maps to
`STATUS_NOSUPPORT` (`0x06`) — the same document's own §6 status table already lists `0x07` as
`Reserved`. A host built against the old doc text would branch on a status code it can never
receive, and misread the real `0x06` reply as "opcode unknown to this firmware build" instead of
"pool full, retry". Corrected the doc to `STATUS_NOSUPPORT` (`0x06`) with a note on why (no
NOMEM-equivalent `BRIDGE_HW_ERR_*` exists yet for this path).

Also fixed the stale in-code comments this drifted from: `adc_stream.c`'s pool-exhaustion comment
claimed `STATUS_NOMEM` "doesn't exist on the wire yet" (it does — 18 `reply_cap` guards in
`protocol.c` return it); and `bridge_hw.h`'s `bridge_hw_adc_dsp_chain_open()` doc comment claimed
real builds return a NOMEM-equivalent mapped to `STATUS_NOMEM`, which they don't. Both now say
what's actually missing: a NOMEM-equivalent `BRIDGE_HW_ERR_*` in `hal/bridge_hw.h`.
