### Documented — `helper_firmware` said the GD32 bridge was covered by "the customer's flash flow"; it is factory-programmed by Alp Lab (#1349)

`metadata/e1m_modules/E1M-V2N101.yaml`'s `helper_firmware:` header comment said
`gd32_bridge` was registered into the system manifest "so the customer's flash
flow covers them." That is the opposite of the product decision (maintainer,
2026-08-09: *"Gd32 is not a customer path. It should be programmed by us at the
factory and we should supply the api interface details to the customers."*) and
of the entry's own body, which already documented the factory-programmed,
`flash_policy: recovery_only` reality in detail.

Nothing behavioural changes: `firmware_path` was already deliberately absent, so
`tan flash` already declines this helper cleanly rather than spawning a flasher
against a nonexistent path (`python/tan/core/flash_plan.py::helper_flash_gate`).
Only the stale framing comment is corrected, to say the registration is for
Alp Lab's factory/production flash flow and that customers are given the
bridge's command-frame API (SPI + I2C, `docs/gd32-bridge.md`), not a way to
reflash it. `E1M-V2N102.yaml`, `E1M-V2M101.yaml`, and `E1M-V2M102.yaml` never
carried this comment — only `E1M-V2N101.yaml` did.

`alp.lock`'s `digests.metadata` regenerated to match.

Not addressed here: the issue's optional suggestion of an explicit
`audience: factory` field on `helper_firmware` entries so tooling can
distinguish factory-only helpers mechanically instead of by prose. That is a
schema change the issue itself flags as "worth discussing" rather than a
straightforward correction, and is left for a maintainer call.
