### Fixed — `check_emit_snapshots` failed on any checkout that had the release tag (#1738)

Four scaffold goldens (`scaffold.minimal/peripheral/sensor-v2n101`,
`scaffold.multicore-mailbox-aen801`) failed the gate on a clean `dev`, with no code
change in sight. The cause was not stale goldens — it was that the emitted bytes
depend on the **checkout**, not the commit.

A scaffolded README pins its doc links to a ref chosen by `alp_template._docs_ref()`:
`v<version>` when `metadata/sdk_version.yaml` says `status: released` **and** that tag
resolves locally, else `main`. `_tag_resolves()` is a local `git rev-parse`, so a clone
that fetched origin's tags emits `blob/v0.16.0/` while a shallow, `--no-tags`, or
tarball checkout of the same commit emits `blob/main/`. The goldens were written from a
tagless checkout, so every tagged checkout failed — unwinnable either way, since fixing
it for one host breaks the other.

That is the same machine-specific class this module already tokenises (`<SDK_ROOT>`,
`<PYTHON_EXECUTABLE>`, `<SDK_COMMIT>`), so the ref is now tokenised as `<DOCS_REF>` and
the goldens pin the link *shape* — which is what the gate is for. `main`, `v0.16.0`,
`v1.0.0` and `v0.16.0-rc1` all collapse to the same token, so this also stops the
goldens re-drifting at every release tag; non-`blob` GitHub links are left alone.

This gate runs **only** inside `scripts/test-all.sh`, never as a PR workflow, which is
why it sat red on `dev` unnoticed while every branch inherited the failure.
