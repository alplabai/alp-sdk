### Fixed — the DRP-AI Yocto inference backend now has CI compile coverage; ORT and DEEPX already gained it as a side effect of #1900 (#1747)

`src/yocto/inference_ort.cpp`, `inference_deepx.cpp`, and `inference_drpai.cpp`
default OFF (`ALP_SDK_USE_ORT_CPU` / `ALP_SDK_USE_DEEPX_DXM1` /
`ALP_SDK_USE_DRPAI_V2N`) because their real vendor SDKs (ONNX Runtime,
DEEPX dx_rt, the EdgeCortix MERA2/DRP-AI TVM runtime) are license- or
account-gated and unobtainable in CI — so none of the three was compiled by
any PR gate, and a change to any of them could ship broken straight into a
release with nothing to catch it.

`#1900` already closed the gap for ORT and DEEPX incidentally, adding
`tests/yocto/inference_ort_regression.cpp` and
`inference_deepx_regression.cpp`, which compile those two backends' real
`.cpp` bodies against clean-room stand-in vendor headers
(`tests/yocto/fakes/onnxruntime/`, `tests/yocto/fakes/dxrt/`) and are wired
into `tests/yocto/CMakeLists.txt` as ctest targets — reachable by
`pr-plain-cmake.yml`'s existing `yocto` (and `strict-warnings`) jobs on
every PR touching `src/**`, no vendor SDK required.

This closes the same gap for DRP-AI: `tests/yocto/inference_drpai_regression.cpp`
compiles `src/yocto/inference_drpai.cpp` against a new
`tests/yocto/fakes/drpai/` (a clean-room stand-in for
`MeraDrpRuntimeWrapper.h`, plus a fake `linux/drpai.h` for the DRP-AI
driver uapi struct/ioctl this file also hard-`#include`s), also wired into
`tests/yocto/CMakeLists.txt`. Unlike ORT/DEEPX, DRP-AI's `open()` resolves
its reserved-memory arena via a real `::open("/dev/drpai0", ...)` +
`::ioctl()` before ever touching the vendor C++ API, so no CI runner (there
is no such device) ever reaches `LoadModel()`/`GetInputInfo()`/`Run()` —
these tests instead cover what IS host-independent: the `model_data`/
`model_size` input-validation guard, the documented "device absent ->
`ALP_ERR_IO`, not a guess" contract, and the NULL-`be_state` guards on
every other hook. All three backends now fail a PR's build the moment a
change to them breaks compilation, closing the "ships unbuilt" risk this
issue named even though full behavioral coverage of the DRP-AI vendor
surface still requires real silicon.
