### Fixed — `alp_i3c_open()`'s `@return` list in `<alp/i3c.h>` didn't match its dispatcher (#1518)

The `@return` block named `ALP_ERR_NOSUPPORT` among the four codes `alp_i3c_open()` can set via
`alp_last_error`, and omitted two codes `src/i3c_dispatch.c` actually sets: `ALP_ERR_NOMEM` (the
handle-pool-exhausted path, already described in prose but not tied to its code) and
`ALP_ERR_NOT_IMPLEMENTED` (the `ops == NULL || ops->open == NULL` path).

`ALP_ERR_NOSUPPORT` is not a corner case in the doc, either: `src/backends/i3c/zephyr_drv.c`'s
`#else /* !CONFIG_I3C_CONTROLLER */` branch -- taken whenever a build lacks
`CONFIG_I3C_CONTROLLER` (either `CONFIG_I3C=n`, or `CONFIG_I3C=y` with
`CONFIG_I3C_TARGET_ROLE_ONLY` selected, per upstream `choice I3C_MODE` in
`zephyr/drivers/i3c/Kconfig`) -- registers the backend with every op, including `open()`,
hard-wired to return `ALP_ERR_NOSUPPORT`. Since `I3C_CONTROLLER` defaults to `n` unless a board
opts into `CONFIG_I3C_DUAL_ROLE` or `CONFIG_I3C_CONTROLLER_ROLE_ONLY`, this branch -- and hence
`ALP_ERR_NOSUPPORT` from `open()` -- is the DEFAULT outcome on every alp-sdk Zephyr build except
the ones that explicitly enable the controller role (e.g. examples/aen/aen-i3c-regcheck), not an
edge case. The Yocto and sw_fallback backends never return it from `open()`, but the Zephyr
backend does by default, so it stays in the list with that caveat instead of being dropped.

The `@return` block now enumerates all six codes against the specific dispatcher/backend branch
each comes from, mirroring the `@ref CODE (reason)` style already used in `<alp/counter.h>`.
