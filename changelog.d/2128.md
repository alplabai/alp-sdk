### Added — AEN803-qualified board overlays backfilled across the AEN example set (Refs #2128)

`scripts/bench/aen/build.sh` (#2094) now refuses a build whose app ships
`boards/` overlays but none matching the resolved board target, and every
module on the bench farm is an E1M-AEN803. But `_qualified_target_to_stems()`
(`scripts/check_example_board_overlay_parity.py:334-349`) keeps the SKU
verbatim in both the full and short overlay stem, so a single filename cannot
serve both `alp_e1m_aen801_*` and `alp_e1m_aen803_*` — repointing
`bench-env.sh`'s `AEN_BOARD` default to AEN803 (#2094, still open) would have
stranded ~18 of 23 `apps.txt` entries behind an explicit `AEN_BOARD=` export.

71 example directories that shipped an `alp_e1m_aen801_*`-qualified overlay
or `.conf` now also ship the `alp_e1m_aen803_*` counterpart — 77 `.overlay`
files (66 single-core dirs + 6 dual-core dirs' HE+HP pair:
`aen-alp-rpc`, `aen-dualcore-doorbell`, `aen-dualcore-he-master`,
`aen-dualcore-ipc`, `aen-dualcore-master`, `aen-rpc-pingpong`) and 3
`.conf` files (`aen-analog-validate`, `aen-dualcore-he-master`,
`aen-jpeg-regcheck`), 80 new files total.

Body content is SoC-level, not SKU-level, so it copies across unchanged; only
each banner's board-target name and SKU digit were updated. Two banner
sentences were corrected rather than propagated, since they were tied to a
specific bench run on an actual AEN801 unit, not a generic SoC-pad fact:
`examples/aen/aen-rtc-alarm/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:51`
("BENCH-PROVEN 2026-09-05 on E1M-AEN801 2626-R2") and
`examples/aen/aen-cc3501e-gpio/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:17`
("SPI1 DATA PATH BENCH-VALIDATED 2026-06-20 (E1M-AEN801, M55-HE)") both keep
naming the AEN801 unit that was actually bench-run and now say the SoC-pad
behavior is expected to carry to AEN803's identical die but has not itself
been separately bench-proven there.

**Excluded: `examples/aen/aen-ospi-regcheck`.** It is the only app whose
overlay substantively touches `&ospi0`, and the board tree's own banners
diverge exactly there —
`zephyr/boards/alp/e1m_aen801_m55_he/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.dts:14-16`
says OSPI0 NOR + HyperRAM "are not populated, so there is no external XIP /
flash device", while
`zephyr/boards/alp/e1m_aen803_m55_he/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.dts:14-18`
says they "are populated; neither is used for XIP boot here ... #915" — so
its regcheck pass/fail semantics may assume a floating bus that stops
floating on AEN803. That needs a human call and is deliberately left out of
this PR; the issue stays open. `examples/aen/aen-adc-regcheck` was also
skipped — it already ships both `alp_e1m_aen803_m55_he_*` and
`alp_e1m_aen803_m55_hp_*` overlays.

None of these new overlays have been bench-built or run on real AEN803
silicon as of this PR — the AEN803 bench gate run is what first compiles
them.
