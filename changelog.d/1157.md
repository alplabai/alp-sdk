### Changed — pinmux `owner` can now name the core that claims a pad, not just the vendor (#1157)

`metadata/pinmux/v2n.yaml` distinguished only `renesas` from `gd32`, so every
RZ/V2N-side pad read `owner: "renesas"` uniformly. V2N is an AMP part: the A55
cluster runs Linux and the CM33 runs Zephyr, and they own different pads. A pad
claimed by one core was therefore invisible to the other's generator, and a
cross-core conflict could only be found on a bench.

That is not hypothetical — `docs/errata-e1m-x-v2n.md:56-111` records the USB
over-current hog regressing when the CM33-owned GD32 supervisor SPI took
`P96`/`SCK7` on 2026-06-03, a collision the metadata had no way to express.

Pads may now carry a `core` alongside `owner`, and the schema enforces the pair:
a row with `core` must have `owner: "renesas"`, since a GD32-side pad has no
RZ/V2N core to attribute. The rule is validated by execution rather than by
reading — mutating the `PA9` row to carry `core: "m33"` produces exactly one
error, and a bogus core value is rejected by the enum.

**Deliberately incomplete, and that is the point.** A core assignment is a
hardware fact per pad, and only the ones this repo establishes are set — `sci7`
(CM33-owned), `gpio9` `P97` (the M33's GD32 chip-select, `..._cm33.dts:110-112`)
and `i2c8`/BRD_I2C (reachable from both, itself the coordination hazard the
issue names). Every other pad is left explicitly unassigned. Guessing an owner
would defeat the purpose of the change, which is to make a conflict a validation
error instead of a bench surprise; a wrong owner produces a confident wrong
answer, which is worse than an honest unknown.
