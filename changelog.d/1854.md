### Fixed — an unrouted E1M pad can now be modelled and is refused loudly, not opened silently as a normal GPIO (#1854)

`metadata/schemas/som-preset-v1.schema.json`'s `pad_routes:` block had exactly
two states: routed through a SoM-side mediator chip, or the implicit `direct`
default. A pad that is physically open on a given hardware revision -- wired to
neither the mediator nor the main silicon -- had no way to say so, so it fell
into the `direct` default and emitted as an ordinary, openable GPIO. The
concrete instance: `metadata/e1m_modules/aen/hw-revisions.yaml` records that AEN
r2 leaves `E1M_GPIO_IO21` unrouted (it was CC3501E `GPIO_30` on r1, moved to
`IO8` on r2), yet `--emit composed-route-table` for r2 emitted
`{ "e1m": "E1M_GPIO_IO21", "dispatch": "direct" }` with no marker at all -- the
revision where the pad is dead looked identical to a working one.

`pad_route_entry.dispatch` gains a third value, `unrouted`, and the schema's
`pad_routes:` description (the exact prose the issue quoted) now says so:
pads not listed still default to `direct`, but a dead pad MUST carry an
explicit `unrouted` entry -- there is no implicit `unrouted`. An `unrouted`
entry requires a `doc:` (schema `allOf`, mirroring the existing
`mailbox.driver_status: partial` -> `notes:` pattern), so the model can't just
say "dead" without saying why. `metadata/e1m_modules/E1M-AEN{301,401,501,601,
701,801}.yaml` each gain the one new row recording IO21 on r2; r1's existing
`pad_route_overrides` (`dispatch: cc3501e, dispatch_pin: 30`) is untouched, so
`--emit composed-route-table` still differs correctly between the two
revisions -- confirmed by diffing the full composed table before/after for
both AEN r1/r2 and a V2N SKU: the ONLY change anywhere is IO21 on r2.

The runtime side closes the loop where every caller actually meets it: the
CC3501E GPIO proxy backend (`src/backends/gpio/cc3501e_proxy.c`) is the single
chokepoint every `alp_gpio_open()` call on an AEN target passes through
(it registers above the platform GPIO backend and fans out per-pin
internally), so the check lives there, not in one example. A new
board-provided `cc3501e_gpio_unrouted[]` list (WEAK empty default, same
pattern as the existing `cc3501e_gpio_routes[]` table) is checked in
`px_open()` before the route/delegate decision; a listed pin_id now returns
`ALP_ERR_NOSUPPORT` instead of falling through to the platform driver and
silently opening a pin that reaches nothing. `include/alp/chips/cc3501e/gpio.h`
declares the new table and `aen-cc3501e-bringup` / `aen-cc3501e-companion-tour`
/ `aen-cc3501e-gpio` populate it with `ALP_E1M_GPIO_IO21` to match their target
revision's real wiring. A new `tests/unit/gpio_cc3501e_unrouted` ztest suite
(native_sim) proves both directions: with the check reverted,
`alp_gpio_open(ALP_E1M_GPIO_IO21)` genuinely succeeds against a real emulated
`alp,pin-array` node (not an accidental failure from a missing DT node); with
the check in place, the same call returns `NULL` and `alp_last_error() ==
ALP_ERR_NOSUPPORT`, and an ordinary pin (`IO20`) is unaffected.

The mechanism is schema-general -- any SoM family (V2N/V2M's GD32 bridge
included) can now record a genuinely dead pad the same way -- but only AEN's
concrete IO21 fact is recorded here, per the no-inventing-values rule; no
V2N/V2M pad is known to need it today.
