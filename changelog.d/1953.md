### Added — `alp_uptime_ms()`: a portable monotonic clock, and `poll_by_repeat()` now bounds by wall time instead of flooring it (#1953)

`chips/cc3501e/cc3501e_core.c`'s `poll_by_repeat()` — the retry wrapper every
worker-routed CC3501E op goes through (Wi-Fi, BLE, sockets, the GPIO proxy,
OTA) — charged only its own back-off sleeps against `timeout_ms`. The time
spent inside `cc3501e_request_locked()` on each attempt (up to four SPI
transfers, plus whatever the transport waits on a stalled link) was free, so
`timeout_ms` was a **floor** on wall time, not a bound, and the skew grew
with the number of attempts: gaps ramp 1 ms to 50 ms, so a 30 s budget is
roughly 610 attempts, and every millisecond an attempt costs became another
~610 ms of overrun.

A correct fix needs a monotonic millisecond clock read at entry and a loop
bound to a deadline — and `chips/cc3501e/*.c` has none available: it is
deliberately OS-agnostic (builds into both the Zephyr module and the plain-
CMake / Yocto `libalp_chips.a`; per `CMakeLists.txt`, none of the
`chips/<id>/<id>.c` cores include a Zephyr/vendor header), and
`<alp/peripheral.h>` exposed `alp_delay_ms()` but no clock.

**New portable API:** `alp_uptime_ms()` in `<alp/peripheral.h>` —
milliseconds since an arbitrary fixed epoch (usually boot), monotonic and
unaffected by wall-clock/RTC changes. Returns `uint64_t`; a millisecond
count at that width wraps after roughly 584 million years, so callers
compare two readings directly instead of needing wraparound-safe unsigned
subtraction. Three backends:

- Zephyr (`src/zephyr/delay_zephyr.c`): `k_uptime_get()`.
- Yocto (`src/common/stub/stub_core.c`, `__linux__` branch, also covers the
  plain-CMake baremetal build on the CI host): `clock_gettime(CLOCK_MONOTONIC)`.
- The clockless baremetal fallback (`src/common/stub/stub_core.c`,
  non-`__linux__` branch — dormant today; no non-Linux target builds this
  file yet): a running total of every `alp_delay_us`/`alp_delay_ms` wait
  this backend itself performed. Monotonic and internally consistent, but
  cannot see time spent outside those calls — a real vendor HAL bring-up
  should replace it with a cycle-counter read (SysTick / DWT->CYCCNT / core
  timer), same upgrade path the delay spin already notes.

`alp_delay_ms()`'s own contract is unchanged.

**`poll_by_repeat()` now loops on a deadline** (`alp_uptime_ms() +
timeout_ms`, computed once at entry) instead of decrementing a sleep-only
budget: each attempt is followed by a real elapsed-time check, and the
final back-off gap is clamped to whatever's left before the deadline. Still
always makes at least one attempt, including for `timeout_ms == 0`, since
the first attempt runs unconditionally before the deadline is ever checked.
The remaining, unavoidable slack is bounded by one attempt's own cost (SPI
transfers + any transport wait), not by the number of attempts made — a
world apart from the old unbounded-with-attempt-count overrun.

**Behaviour change at `timeout_ms == 0`:** the old sleep-budget form set
`remaining = (timeout_ms > 0) ? timeout_ms : 1u`, so a still-busy first
attempt always bought one more 1 ms back-off gap before `remaining` hit
zero — i.e. exactly two attempts. The deadline form's `deadline_ms ==
alp_uptime_ms()` at entry means the post-attempt check `now_ms >=
deadline_ms` is true as soon as any wall time has elapsed, so a still-busy
first attempt returns `ALP_ERR_TIMEOUT` immediately — exactly one attempt.
Both honour "`timeout_ms == 0` still tries once"; only the retry count for
an immediately-busy peer changes.

**Round-18 correction:** the paragraph above previously claimed "no caller in
this tree passes `timeout_ms == 0` today". That was false, and was flagged
false in round 16 without being corrected in round 17.
`examples/aen/aen-cc3501e-bringup/src/main.c` calls
`cc3501e_ota_status(fw, &bs/&ps, 0u)` at two sites in `cc3501e_demo_ota()`
(the BEGIN-attempt diagnostic probe, and the per-chunk window-flush hold-off
poll), and `chips/cc3501e/cc3501e_ota.c:436`'s `cc3501e_ota_status()`
forwards `timeout_ms` straight into `poll_by_repeat()` — so this example DID
observe the difference: reproduced on a host harness, a still-busy peer got
two attempts (6 `alp_spi_transceive` calls) under the old sleep-budget form
and exactly one (3 calls) under the deadline form, a silently dropped retry
in a shipped example.

**Decision:** keep the deadline form's one-attempt-at-zero as the correct,
now regression-locked behaviour of `poll_by_repeat()` itself (an honest
"instant, no-budget poll", not the old form's accidental one-more-attempt
floor — re-adding that floor would reintroduce a version of the exact
unbounded-slack problem this issue exists to fix, just narrowed to the
`timeout_ms == 0` case). Instead, fixed the two call sites: both now pass
`CC3501E_OTA_BENCH_FLUSH_POLL_TIMEOUT_MS` (200 ms) instead of a bare `0u`.
That constant already existed in the example, already documented as "cap
each STATUS frame so the hold-off budget above is REAL", and mirrors
`chips/cc3501e/cc3501e_ota.c`'s own `CC3501E_OTA_BLACKOUT_POLL_TIMEOUT_MS`
(also 200 ms) — it was simply never wired into the two call sites that
needed it, leaving them to rely on `poll_by_repeat()`'s old zero-timeout
floor by accident. A real, intentional per-poll budget restores retry room
for a transient BUSY/IO without reintroducing an unbounded wait.

Regression-locked by a new native_sim suite,
`tests/zephyr/cc3501e_poll_deadline`, with a stub clock that advances only
on demand (via the test's own `alp_delay_ms`/`alp_spi_transceive` seams) so
the deadline logic is exercised without any real sleeping or hardware.

**Coverage caveat:** `check_test_coverage.py` counts `alp_uptime_ms` as
covered, but every one of `tests/zephyr/cc3501e_*`'s eight suites defines
its OWN fake `alp_uptime_ms()` for link purposes (`cc3501e_poll_deadline`'s
on-demand stub clock, six sibling suites' shared fake-clock counter, and
`cc3501e_transport_lock`'s direct `k_uptime_get()` call) — under `tests/`,
that is the only place the symbol is ever CALLED, and it is always a test
double, never one of the three PRODUCTION backends.

COMPILED and EXECUTED are different questions, though, and neither real
backend is absent from a build: `src/common/stub/stub_core.c` (the Yocto
`clock_gettime` wrapper, `#if defined(__linux__)`-gated — true on the Linux
CI host regardless of `ALP_OS`) is unconditionally part of `alp::sdk` for
the Yocto and baremetal backends (`src/yocto/CMakeLists.txt:141`,
`src/baremetal/CMakeLists.txt:30`), so it is compiled into every Yocto host
test that links `alp::sdk`, plus 13 further `tests/yocto/CMakeLists.txt`
targets that `#include` a production `.c` file directly (dispatcher or
backend, to avoid a duplicate-definition link against `alp::sdk`) and add
`stub_core.c` alongside it for the same reason (e.g. `:171`
`alp_test_inference_latency`, `:1288` `alp_test_peripheral_gpio_self_close`).
`src/zephyr/delay_zephyr.c`'s `k_uptime_get()` wrapper is compiled into the
alp Zephyr module, and hence into every native_sim suite whose `prj.conf`
sets `CONFIG_ALP_SDK=y` (23 `*.conf` files today). What's actually true is
narrower than "not compiled": no test source under `tests/` CALLS `alp_uptime_ms()`
directly except the eight cc3501e_* fakes above, and none of those eight
sets `CONFIG_ALP_SDK=y` or links a Yocto build of `alp::sdk` — they
override the symbol rather than exercise it, so the real Zephyr and Yocto
backends sit in the linked binary unexercised. Only the clockless baremetal
accumulator (the non-`__linux__` branch) is genuinely uncompiled anywhere
today, per its own header comment: no non-Linux target builds this file
yet. The green coverage signal says nothing about whether the Zephyr or
Yocto backend is correct.
