### Added — RZ/V2N Cortex-M33 watchdog (WDT0) behind `<alp/wdt.h>`, bench-unverified (#2660)

The E1M-X V2N and V2M CM33 boards now declare `wdt0` (R_WDT0_BASE `0x41C00400`) and the alias `alp-wdt0`, `disabled` by default because an expiry resets the whole SoM; a product enables it with `&wdt0 { status = "okay"; }` and `alp_wdt_open()` reaches it through the existing Zephyr backend with no new public API. Upstream's `renesas,rz-wdt` driver cannot bind RZ/V2N (hal_renesas has no rzv `r_wdt`; its two builds are the RZ/A overflow timer and the RZ/T2M + RZ/N2L ICU path), so alp-sdk carries the rzt `r_wdt` adapted for WDT0 under `zephyr/drivers/watchdog/r_wdt/` and a thin glue driver for the new `renesas,rzv-wdt` compatible, the same way it carries the MHU-B port. Reset-only: interrupt-only expiry, `ALP_WDT_RESET_CPU`, a window and pause-on-debug answer `ALP_ERR_NOSUPPORT`, since hal_renesas names no WDT0 interrupt line for the CM33. The WDT0 base and 24 MHz counting clock come from the SoC spec (`m33_sm` `watchdog` block, hardware manual Table 4.4-2); the divider table is the manual's WDTCR.CKS set (/1 /16 /32 /64 /128 /256, longest period 174.8 ms; a longer `timeout_ms`, such as the 1000 ms `ALP_WDT_CONFIG_DEFAULT`, runs a software keeper: the hardware is armed at a fixed 87.4 ms period and a 20 ms `k_timer` refreshes it only until the application's own deadline passes, so a missed deadline resets the SoM between `timeout_ms` and `timeout_ms` + 87.4 ms, and a kernel or IRQ lockup still resets within 87.4 ms) and the reset is the CPG_ERRORRST_SEL2 error system reset with WDTRCR.RSTIRQS = 0.  `alp_sdk.wdt.rzv_cm33` was built by hand on both boards with the node enabled and `alp.unit.wdt_rzv_timeout` covers the timeout selection and the keeper decision on native_sim; nothing has run on silicon, and the measured counting clock and the CM33 clock hold (`renesas,cm33-owned-clocks`, on the unmerged `feat/v2n-assignable-ownership` branch) are open. Ordered bench steps are in `docs/bench/rzv-wdt0-cm33.md`.
