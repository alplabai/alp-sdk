### Added — E1M-X V2N/V2M: enable on-module CAN-FD (TCAN1044 x2) for Linux (#2332)

The RZ/V2N-family SoM's two on-module TCAN1044 CAN-FD transceivers
(U15/U16, SoM rev 2625-R2) are now wired up for Linux/A55:

- `meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-v2n-som.dtsi`:
  `canfd_pins` pinctrl, `&canfd` enabled with `channel2`/`channel3`
  live, and a `gd32_gpio` gpio-hog driving the shared CAN_STBY line
  (bridge GPIO bit 20, GD32 PB13) low at boot so both transceivers
  leave standby. Transceiver-to-channel mapping is schematic-sourced:
  U15 (CANFD3, P86/P87) is carrier `E1M_X_CAN0`; U16 (CANFD2, P84/P85)
  is `E1M_X_CAN1`.
- `0005-gpio-add-gd32-bridge-expander-driver.patch`: the Linux
  `gpio-gd32-bridge` driver's pad map grows to 21 lines (bit 20 =
  `can-stby`), resolved from the same `GET_VERSION` poll as the
  existing bt-reg-on/wl-reg-on gate (bits 18/19) and requiring bridge
  protocol MINOR >= 13. Line 20's `.request()` deliberately does NOT
  defer the way 18/19 do: its only consumer is a gpio-hog on the same
  gpiochip, and gating a hog's own request would fail that gpiochip's
  entire registration (taking bt-reg-on/wl-reg-on/RTC/Display-1 down
  with it) whenever the bridge is merely slow to boot -- the same
  class of bug Refs #2297 fixed for the rest of this driver. Wire-level
  safety (never sending `GPIO_WRITE` for an unconfirmed bit) still
  holds via the existing gate/replay machinery.
- `metadata/e1m_modules/v2n/core-ownership.yaml`: the four CANFD pads
  attributed to `a55`, marked `BENCH-PENDING` (dtc-checked, not yet
  flashed on real hardware).
- `metadata/boards/e1m-x-evk.yaml`: `CAN_STBY` dropped from the
  `partial_hw_config` TBD list (resolved: GD32 PB13); `CAM1_RST`
  remains TBD.
- Companion `gd32-bridge-firmware`: CAN_STBY exposed as bridge GPIO
  bit 20 (protocol 0.11 -> 0.13, firmware 0.2.12 -> 0.2.16, stacked on
  the open bt-reg-on/wl-reg-on PR), boot default OUTPUT HIGH (standby)
  until a host commands it low.

No TCAN1044 PHY binding is added: this kernel's `ti,tcan104x-can.yaml`
only allows `ti,tcan1042`/`ti,tcan1043`, and claiming one of those
compatibles for the populated TCAN1044 would misrepresent the part —
the gpio-hog is used instead. TCAN1044 EN is not driven from Linux
(strap unconfirmed from this repo).

Deliberately unchanged / operator steps:

- No `bitrate` or other bit timing in the device tree: set it per
  interface with `ip link set can_e1m<N> type can bitrate ... dbitrate
  ... fd on` (the interfaces stay down until then); see
  `docs/build-yocto-v2n.md` "CAN-FD bring-up".
- No `board_alias` for `E1M_X_CAN1` (only `E1M_X_CAN0` has one in
  `metadata/boards/e1m-x-evk.yaml`).
- `soc_peripheral_instances[].driver_status` for `canfd2`/`canfd3`
  stays `none` in all six SoM presets (that field tracks Zephyr/CM33
  driver maturity, which is unchanged — see #2332 for the full list of
  deliberate follow-ups, including cross-repo bridge-GPIO-bit numbering
  coordination with the open `gd32-bridge-firmware` REG_ON/OTA PR family).
