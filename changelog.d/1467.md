### Fixed — `docs/branching-and-merge-policy.md` described merges into `dev` as `--no-ff` merge commits; the live "dev merge queue" ruleset squashes them all (#1467)

Confirmed on the actual `origin/dev` tip: the `main`→`dev` back-merge commit `e9aea71bf`
(PR #1462) has a single parent and a tree identical to the un-merged source commit
`6fd857df8d`, which is *not* an ancestor of `dev` — a squash, not a merge, so the back-merge
recorded no ancestry. The same is true of ordinary feature PRs (e.g. #1703, 2 commits,
landed on `dev` as one single-parent commit) — a GitHub ruleset ("dev merge queue", id
`20781492`, live since 2026-08-13) forces `merge_method: SQUASH` for every PR merging into
`dev`, with no bypass actor configured, overriding the documented `--no-ff` policy for the
whole branch, not just the back-merge.

For the `main`→`dev` back-merge this defeats the point of back-merging: a squashed commit
carries no ancestry, so a later `dev`→`main` diff can re-propose commits `main` already has.
Fixing that needs a repository-settings decision (change the ruleset's `merge_method`, or
add a bypass actor scoped to the back-merge PR) — tracked as open in #1467, not resolved by
this change. `docs/branching-and-merge-policy.md`'s "Merge method" and "Branch protection
settings" sections now describe the live ruleset instead of the aspirational `--no-ff`
policy, so the runbook stops contradicting what `gh pr merge` actually does on `dev`.
