### Fixed — AEN E8 OSPI/HexSPI `core_clk` fell back to `bus-speed`, silently disabling OSPI_SCLK instead of driving it at the real 400 MHz core clock (#1831)

`zephyr/drivers/flash/flash_ospi_alif.c`'s `OSPI_ALIF_INIT` macro fed `core_clk` from `DT_INST_PROP_OR(inst, clock_frequency, DT_INST_PROP(inst, bus_speed))` — the node never set `clock-frequency`, so `core_clk` fell back to `bus-speed` (100 MHz). `alif_hal_ospi_initialize()` writes the whole `OSPI_BAUDR` register from `core_clk / bus_speed`, so `core_clk == bus_speed` wrote `OSPI_BAUDR = 1`. HWRM `AHRM0012NDA v0.3` §16.1.5.3.5 defines `OSPI_BAUDR[SCKDV]` as bits 15:1 (bit 0 is RESERVED and forced to 0 on every write): "If this field is set to all 0s, the serial output clock (OSPI_SCLK) is disabled." A written value of 1 leaves `SCKDV` all zero — **the old fallback disabled `OSPI_SCLK` entirely. It was a dead bus, not an overclock.** (An earlier revision of this PR, its changelog fragment, and both touched header comments claimed the old fallback would overclock an external device past its rating; that claim was wrong and is corrected here. HWRM §16.1.4.2 also makes `SCLK ≤ OSPI_CLK/2` a hardware property of Master mode, so an overclock past the core clock was structurally impossible regardless.) Latent on this batch only because no such part is populated on the E1M-AEN801 (bench module is board rev r1, `2617-0001`; the Macronix part is on the R2 BOM only, #915).

The file's own header comment justified the placeholder as "must come from the Alif Ensemble E8 TRM, not be invented" — stale: HWRM Table 16-2 sources HEXSPI0's internal core clock (OSPI0_CLK) from "SYST_ACLK or 266M_CLK", selected by `MISC_CLK_CTRL[SEL_OSPI_CLK]` (`zephyr/drivers/flash/flash_ospi_alif.c:48-53`); HWRM §8.3.2.3.7 gives that bit's silicon reset value 0x0 as "400 MHz (SYST_ACLK)" (`AHRM0012NDA v0.3`). `zephyr/dts/alif/ensemble_e8_peripherals.dtsi` now declares `clock-frequency = <400000000>` (`zephyr/dts/alif/ensemble_e8_peripherals.dtsi:739`), and the driver macro now reads it with a plain `DT_INST_PROP(inst, clock_frequency)` (`zephyr/drivers/flash/flash_ospi_alif.c:502`) — no fallback: a board/SoM that omits `clock-frequency` on its `ospi0` node now fails to build instead of silently programming a disabled clock. Worked through: `400000000 / 100000000 = 4`, `SCKDV = 2`, `BAUDR = SCKDV × 2 = 4`, `SCLK = 400/4 = ` **100 MHz** — exactly the node's `bus-speed`, and half the §10.5 200 MHz HEXSPI controller cap. The example that independently exercises this same call, `examples/aen/aen-ospi-regcheck/src/main.c`, carried the identical `DT_PROP_OR` fallback one file over from the driver fix; it is corrected the same way (`examples/aen/aen-ospi-regcheck/src/main.c:225`).

`zephyr/drivers/flash/flash_ospi_alif.c:481` adds `OSPI_ALIF_CHECK_SCLK()`, three `BUILD_ASSERT`s beside the macro so a *present but wrong* `clock-frequency`/`bus-speed` ratio fails the build the same way a *missing* `clock-frequency` now does: the effective divider (`clock-frequency / bus-speed`, HAL-truncated, bit 0 forced to 0 by `OSPI_BAUDR[SCKDV]`) must be ≥ 2 (else `SCKDV` is all zero and `OSPI_SCLK` is disabled, per §16.1.5.3.5 above), the raw ratio must be even (else the bit-0 truncation rounds the divider **down**, so `SCLK` silently **overshoots** the requested `bus-speed` -- e.g. a ratio of 3 becomes a divider of 2), and the resulting `SCLK` must stay ≤ 200 MHz (HWRM §10.5).

**Not addressed here.** The driver still does not program `MISC_CLK_CTRL[SEL_OSPI_CLK]` itself, so 400 MHz is correct only for as long as whatever boot stage runs before it (ROM/SE) leaves that mux at its documented reset value; HWRM §8.3.2.3.7 also documents a 0x1 selection (266 MHz from `266M_CLK`/PLL). Making `core_clk` unconditionally correct means the driver owning that selection itself — a distinct change to a system-level clock-mux register (`MISC_CLK_CTRL` is not OSPI-instance scoped) that needs bench confirmation of its placement relative to the existing `CLKCTL_PER_SLV->OSPI_CTRL` clock-enable sequence in the same file, which this change does not attempt. **Not verified on silicon and cannot be on the current bench**: board rev r1 (`2617-0001`) has no OSPI memory assembled to clock.
