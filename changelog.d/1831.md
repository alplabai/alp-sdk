### Fixed — AEN E8 OSPI/HexSPI `core_clk` fell back to `bus-speed`, programming the SCLK divider as if the 400 MHz core clock were 100 MHz (#1831)

`zephyr/drivers/flash/flash_ospi_alif.c`'s `OSPI_ALIF_INIT` macro fed
`core_clk` from `DT_INST_PROP_OR(inst, clock_frequency, DT_INST_PROP(inst,
bus_speed))` — the node never set `clock-frequency`, so `core_clk` fell
back to `bus-speed` (100 MHz). `alif_hal_ospi_initialize()` derives the
SCLK divider from `core_clk / bus_speed`; `core_clk == bus_speed` yields the
minimum divider, i.e. SCLK programmed at or near the full core clock. Had
the real core clock been higher (it is), the controller would have been
programmed to drive whatever external octal-NOR/HyperBus part is on the bus
far past its rating — a device-overclock, not a degraded feature. Latent on
this batch only because no such part is populated on the E1M-AEN801 (bench
module is board rev r1, `2617-0001`; the Macronix part is on the R2 BOM only,
#915).

The file's own header comment justified the placeholder as "must come from
the Alif Ensemble E8 TRM, not be invented" — stale: HWRM Table 16-2 sources
HEXSPI0's internal core clock (OSPI0_CLK) from "SYST_ACLK or 266M_CLK",
selected by `MISC_CLK_CTRL[SEL_OSPI_CLK]` (`zephyr/drivers/flash/
flash_ospi_alif.c:41`); HWRM 8.3.2.3.7 gives that bit's silicon reset value
0x0 as "400 MHz (SYST_ACLK)" (AHRM0012NDA v0.3). `zephyr/dts/alif/
ensemble_e8_peripherals.dtsi` now declares `clock-frequency = <400000000>`
on the `ospi0` node, and the driver macro now reads it with a plain
`DT_INST_PROP(inst, clock_frequency)` (`zephyr/drivers/flash/
flash_ospi_alif.c:454`) — no fallback: a board/SoM that omits
`clock-frequency` on its `ospi0` node now fails to build instead of
silently programming a wrong divider.

**Not addressed here.** The driver still does not program
`MISC_CLK_CTRL[SEL_OSPI_CLK]` itself, so 400 MHz is correct only for as
long as whatever boot stage runs before it (ROM/SE) leaves that mux at its
documented reset value; HWRM 8.3.2.3.7 also documents a 0x1 selection (266
MHz from `266M_CLK`/PLL). Making `core_clk` unconditionally correct means
the driver owning that selection itself — a distinct change to a
system-level clock-mux register (`MISC_CLK_CTRL` is not OSPI-instance
scoped) that needs bench confirmation of its placement relative to the
existing `CLKCTL_PER_SLV->OSPI_CTRL` clock-enable sequence in the same
file, which this change does not attempt. **Not verified on silicon and
cannot be on the current bench**: board rev r1 (`2617-0001`) has no OSPI
memory assembled to clock.
