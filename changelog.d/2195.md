### Added — `check_cross_platform.py` flags implicit text-encoding calls under `scripts/**`/`tests/**` (#2195)

Python resolves the default text encoding from the platform locale — UTF-8 on
our Linux/Mac hosts, cp1252 on the `windows-latest` CI runner — so a
`Path.read_text()`/`open()`/`subprocess.run(..., text=True)` call with no
explicit `encoding=` works on every host the author tested on and raises
`UnicodeDecodeError` the moment non-ASCII content reaches Windows. Not
hypothetical: this is what turned PR #2194's curly-quote fixtures into a red
Windows leg while `bash scripts/test-all.sh` (Linux-only) stayed green
throughout.

`scripts/check_cross_platform.py` (`scripts/check_cross_platform.py:18`,
"IMPLICIT-ENCODING -- a Python text-IO call with no explicit") gains a sixth
finding category, alongside `LINUX-ONLY-IDIOM` and `BASH-ONLY-SHEBANG`. It
flags, when no `encoding=` keyword is present: `Path.read_text()`/
`Path.write_text()`; bare `open()` or `Path.open()` in text mode; and
`subprocess.run`/`check_output`/`Popen` with `text=True` or
`universal_newlines=True`. Binary-mode IO and any call already passing
`encoding=` (including `encoding=locale.getpreferredencoding()`) are correct
and never flagged.

The check is AST-driven (`scripts/check_cross_platform.py:515`, "def
scan_python_encoding"), not regex-driven like the existing five
`LINUX-ONLY-IDIOM` patterns: the flagged calls routinely spread their keyword
arguments across several lines, and "does this Call node have an `encoding=`
keyword anywhere" is exactly what `ast.parse` answers for free. It's scoped
to `scripts/**` and `tests/**` (`scripts/check_cross_platform.py:227`,
"PY_SCAN_ROOTS"), the SDK's own tooling and test surface — an explicit
`--path` still scans any `.py` file regardless of that default-walk scope.

`tests/scripts/conftest.py:47` (`encoding=`) — this rule's known
live site, `subprocess.run([exe, "--version"], capture_output=True,
text=True, check=True)` with no `encoding=` — fixed in the same change so
the rule ships clean; it was the only implicit-encoding call left in the
`pytest tests/scripts/` surface.

A wider repo sweep with the new rule found 478 further implicit-encoding
sites across 139 files (overwhelmingly `write_text`/`subprocess.run` calls in
test fixtures under `tests/scripts/`); those are deliberately left for a
follow-up rather than folded into this change, so this fragment ships the
rule + its two mandated fixes (`tests/scripts/conftest.py`, and this rule's
own test-harness `_run` helper), not a sprawling mechanical diff.

Those 478 sites are not left unenforced, though: `scripts/check_cross_platform.py:345`
(`IMPLICIT_ENCODING_BASELINE: frozenset[str] = frozenset({`) grandfathers them
by file — a **file-level**, not site-level, allowlist deliberately shaped
after the existing `INTENTIONALLY_DISCUSSES_OS_PATHS` allowlist rather than a
line-numbered one, because a line-numbered baseline rots on the next
unrelated edit to a listed file and this repo has been bitten by exactly
that kind of silent drift before. The tradeoff is real and is spelled out in
a comment at `scripts/check_cross_platform.py:314`
(`What this is: the day`): touching a baselined file does not force a fix of
its other pre-existing findings, and a genuinely new implicit-encoding call
added to a baselined file is still only a warning
(`scripts/check_cross_platform.py:801`, `baselined: bool = False`) — printed,
not silenced, but not `--fail-on-warning`-failing either
(`scripts/check_cross_platform.py:1320`, `not f.baselined`). New files, and
every file not on the list, are gated from day one. The baseline is
temporary and may only shrink; draining it is tracked in #2197, not here.

`tests/scripts/test_check_cross_platform.py`'s
`test_linter_fail_on_warning_against_real_repo_passes` now asserts the thing
that is actually true post-baseline — zero findings *outside*
`IMPLICIT_ENCODING_BASELINE` against the live tree — instead of the
now-false "zero findings" it asserted before this fragment; three new cases
cover the baseline mechanism itself (a baselined file doesn't fail, a
non-baselined file does, a brand-new finding in an already-baselined file
still prints as a warning without failing).
