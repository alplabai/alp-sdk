### Fixed — AEN803 example overlays had drifted from their AEN801 siblings, re-enabling SD against the 2626-R2 mux; content-parity and stranded-overlay gates now catch it (#2198)

`df628b6ab` (#2176) backfilled every AEN801 example overlay to AEN803 by
copy. Three AEN801 fixes merged after it and never reached the copies, so
four AEN803 overlays now take the AEN801 content, SKU name aside:

- **`aen-evk-demo` — `sdhc0` disabled, the hazard half.** The AEN803 file
  still declared its own `sdhc0: sdhc@48102000` with `status = "okay"` and
  `pinctrl-0 = <&pinctrl_sdmmc>`. The 74LVC157 SDIO mux (U38/U39) has no
  Hi-Z state and holds `E1M_CLK`, `E1M_CMD`, `E1M_D3..D0` and
  `E1M_SDIO_RST` low whenever powered, so `sdhc_dwc_init()` starting the
  400 kHz ID clock at `POST_KERNEL` would fight it before `main()` runs —
  the contention #2051 removed from the AEN801 file. No AEN803 module has
  run that overlay in a 2626-R2 carrier, so the fight is inferred from
  #2051, not measured. Now
  `examples/aen/aen-evk-demo/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:452` ("&sdhc0 {")
  keeps it disabled with #2051's rationale, and the `pinctrl_sdmmc` state is
  gone because nothing applies it any more.
- **`aen-evk-demo` + `aen-pdm-mic-alif` — MP34DT05TR-A PDM clock bounds
  (#2133).** `clk-frequency-min = <1200000>` / `clk-frequency-max =
  <3250000>` at
  `examples/aen/aen-evk-demo/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:805` ("clk-frequency-min = <1200000>;")
  and
  `examples/aen/aen-pdm-mic-alif/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:68` ("clk-frequency-min = <1200000>;"),
  so an out-of-spec mic clock fails `alp_audio_in_open()` with `-EINVAL`
  on AEN803 instead of silently under-clocking the mic.
- **`aen-qenc-readout` — the AEN803 target did not compile (#2104).** Its
  overlay lacked the `gpio-qdec` node now at
  `examples/aen/aen-qenc-readout/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:170` ("qdec_sw: qdec-sw {"),
  the `&gpio3` enable and two binding includes, while
  `examples/aen/aen-qenc-readout/src/main.c:211` ("INPUT_CALLBACK_DEFINE(DEVICE_DT_GET(DT_NODELABEL(qdec_sw))")
  references that node unconditionally. Building `dc12826a1` (the `dev`
  this branch is cut from) for `alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he`
  fails with `'__device_dts_ord_DT_N_NODELABEL_qdec_sw_ORD' undeclared`.
- **`aen-sdhc-probe` — stranded overlay moved.** #2051 renamed
  `aen-sdcard-readout` to `aen-sdhc-probe` while #2176 was adding
  `examples/aen/aen-sdcard-readout/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay`;
  both merged, leaving that file alone in a directory with no app, still
  enabling `sdhc0`. It is deleted, and `aen-sdhc-probe` gets the AEN803
  copy of its own overlay, `sdhc0` disabled at
  `examples/aen/aen-sdhc-probe/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:56` ("&sdhc0 {").

**`aen-ospi-regcheck` now covers E1M-AEN803 too.** #2176 left it out,
because its pass/fail might have assumed a floating OSPI0 bus that stops
floating on AEN803, where the HyperRAM (SS0) and NOR (SS1) are fitted. The
app does no device I/O at all. It binds the node, checks the rc of
`alif_hal_ospi_initialize()` and reads `CTRLR0` back against its reset
value, `examples/aen/aen-ospi-regcheck/src/main.c:162` ("#define OSPI_CTRLR0_RESET_VALUE 0x00C00407U").
It sends no transfer, pulses no reset on `P15_6`/`P15_7`, enables no XIP and
writes nothing. It has also already run on AEN803 silicon:
`docs/verification-status.md:478` ("Bench-verified 2026-09-13 on two E1M-AEN803 modules")
records serial `2026W36-0001` and serial `2026W36-0002` giving
`alif_hal_ospi_initialize() rc=0`, `CTRLR0=0x00c00407` and
`RESULT PASS: OSPI/HexSPI node BINDS` through the AEN801 board target. The
AEN803 overlay is the AEN801 one with the SKU changed, and
`alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he` is in `platform_allow`.
The app's `CMakeLists.txt` no longer pins the AEN801 overlay with
`DTC_OVERLAY_FILE`. That pin would have handed the AEN801 file to the
AEN803 build; Zephyr now picks each target's own overlay.

**Six more AEN examples no longer pin the AEN801 overlay.** `aen-aipm-read`,
`aen-isp-regcheck`, `aen-power-iwic`, `aen-se-crypto`, `aen-se-service-info`
and `aen-se-service-query` each set `DTC_OVERLAY_FILE` to the AEN801 overlay
unconditionally, so every build for the AEN803 target applied the AEN801
file and never read its own. The pins date from 2026-06-18, when these
overlays were named `alp_e1m_aen801_m55_he.overlay` and Zephyr's
board-qualified lookup could not find them. #834 renamed the files to the
fully-qualified stem Zephyr does find, but re-pointed the pins instead of
removing them. No app declared an HP target that could have been borrowing
the HE overlay (each declared only
`alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he`), and each ships an overlay
for both SKUs, so the pins are gone, as at
`examples/aen/aen-aipm-read/CMakeLists.txt:24` ("No DTC_OVERLAY_FILE: Zephyr applies").
`aen-jpeg-regcheck` guarded its pin on `BOARD MATCHES "^alp_e1m_aen801_m55_he"`,
so it was SKU-correct, but its comment pointed at the `aen-isp-regcheck` note
removed here and restated the same stale premise; its pin is removed too.

Every touched AEN803 target builds against this tree: `aen-evk-demo`,
`aen-qenc-readout`, `aen-pdm-mic-alif`, `aen-sdhc-probe`, `aen-ospi-regcheck`
and the seven un-pinned apps. So does every target those apps declare: the
AEN801 HE target of all eight CMake-touched apps, and `native_sim/native/64`
for `aen-jpeg-regcheck`, which reads no board overlay. Each generated
`zephyr.dts` names exactly one overlay as its source, the one for its own
SKU. Nothing here has run on hardware.

**CI now builds twelve of these apps for AEN803.** Every bench EVK carries an
E1M-AEN803 by the maintainer's account, recorded at
`metadata/e1m_modules/E1M-AEN803.yaml:203` ("so it rests on the maintainer's word").
The SKU cannot be read from silicon, because both SKUs use the same part.
Until now the AEN803 bench runs on record were built for the AEN801 target
anyway. `aen-ospi-regcheck`, the seven un-pinned apps and the four whose
AEN803 overlays this change repairs (`aen-evk-demo`, `aen-pdm-mic-alif`,
`aen-qenc-readout`, and the `aen-sdhc-probe` base scenario) now declare
`alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he` next to their AEN801 target,
as at `examples/aen/aen-aipm-read/testcase.yaml:23` ("alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he").
`pr-twister-aen.yml` already hands that platform to twister at
`.github/workflows/pr-twister-aen.yml:179` ("-p alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he"),
but twister builds a scenario there only if its `platform_allow` names it, so
until now CI never compiled these AEN803 overlays. A twister `--dry-run` over
`examples/aen` now selects 14 AEN803 scenarios: these twelve on the HE target
plus `aen-adc-regcheck`'s existing HE and HP ones. All are
`build_only: true`. The AEN803 board has no simulator and no workflow runs
device tests, so CI compiles them and runs nothing. The workflow's own
comments now say so. Each app's `sample.description` now names both SKUs.

The other 50 AEN scenarios that ship an AEN803 overlay but declare only the
AEN801 target are not extended here, because the job's time budget cannot
absorb them. The twister step took 697–1220 s across the last eight runs, at
about 80 builds, against its 30-minute cap at
`.github/workflows/pr-twister-aen.yml:404` ("timeout-minutes: 30").
This change takes it to 92 builds. Adding the other 50 takes it to about 140
and, scaled linearly, a worst case near 2,100 s, past the cap. #2209 splits
the job per SKU first. Two more scenarios, `aen-sdhc-probe`'s
`.sdhc_build_coverage` and `aen-ethernet-link`'s `.mdio_managed`, list the
AEN801 overlay in `extra_dtc_overlay_files`, so an AEN803 entry there would
build the AEN801 file for AEN803. Each needs its own AEN803 twin instead.

**New gate — `scripts/check_example_board_overlay_content_parity.py`.**
`check_example_board_overlay_parity.py` checks that an overlay exists for
each target, not what it says, so it passed throughout. The new gate diffs
every pair of `examples/**/boards/alp_e1m_<sku>_*` files that differ only by
SKU, where both SoM presets declare the same `family` and `silicon_variant`:
today that means E1M-AEN801/803, E1M-V2N101/102 and E1M-V2M101/102, and 82
pairs. Comments are stripped first, because a bench result measured on one
SKU is not a claim about the other. Kconfig's `# CONFIG_FOO is not set` is
kept, because it is an assignment. Each file's own SKU name is normalised,
and only its own, so an AEN803 overlay still naming `aen801` in real content
fails:
`scripts/check_example_board_overlay_content_parity.py:154` ("re.sub(re.escape(sku)").
A SKU with no preset is an error rather than a skip, so a moved preset cannot
leave the gate passing on zero pairs. Any remaining line fails unless it is
listed in
`scripts/check_example_board_overlay_content_parity.py:102` ("ALLOWED_DELTAS: dict[tuple[str, str], str] = {}"),
which is empty: those SKUs differ only by BOM population (E1M-AEN803's
OSPI0 HyperRAM + NOR), and the one paired overlay that touches OSPI0 is
controller-only. Run on `origin/dev`, it flags exactly the `aen-evk-demo`,
`aen-pdm-mic-alif` and `aen-qenc-readout` pairs.

The same gate also fails an app `CMakeLists.txt` that names one SKU's paired
file outside an `if()` whose condition names that SKU, at
`scripts/check_example_board_overlay_content_parity.py:207` ("def _pin_problems(root: Path"),
because the sibling SKU's build would read that file instead of its own. Run
on the tree before the six pins were removed, it flags exactly those six. Only
a positive `BOARD MATCHES` or `STREQUAL` on one literal naming the SKU counts
as a guard. `NOT`, `AND`/`OR`, a `|` alternation, `else()`, or an `elseif()`
on anything else fails closed. The same check covers twister: a scenario whose
`extra_dtc_overlay_files`, `extra_conf_files`, `extra_overlay_confs` or
`extra_args` names one SKU's file while its `platform_allow` reaches the
sibling SKU fails, at
`scripts/check_example_board_overlay_content_parity.py:255` ("def _testcase_pin_problems(root: Path").
Adding the AEN803 target to `aen-sdhc-probe`'s `.sdhc_build_coverage` now
fails it. The check does not see a pin reached through an `include()`d
`.cmake` file, a filename built from variables, or `file(GLOB)`.

Twenty-two AEN app `CMakeLists.txt` headers told users to build with
`-DEXTRA_DTC_OVERLAY_FILE=<this-dir>/boards/alp_e1m_aen801_…overlay`. On an
AEN803 build that layers the AEN801 file over the AEN803 one. The instruction
is replaced with a note that Zephyr applies
`boards/<fully-qualified-board>.overlay` by itself.

**Stranded `boards/` directories now fail CI.** Closes #2207.
`check_example_board_overlay_parity.py` also fails any `examples/**/boards/`
directory whose parent holds no `CMakeLists.txt`, at
`scripts/check_example_board_overlay_parity.py:543` ("def _stranded_boards_dir_problems(root: Path)").
That is the class the `aen-sdcard-readout` file above belonged to. Neither gate
could see that file: it had no build target and no SKU sibling. Only
git-tracked files count, so a local `west build` inside an example is not
reported. `<app>/sysbuild/<image>/boards/`, sysbuild's per-image
configuration directory, is accepted when `<app>/CMakeLists.txt` exists.
