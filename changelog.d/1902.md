### Fixed — a prerelease tag declared itself as its GA version, so an rc checkout was indistinguishable from the release (#1902)

`scripts/bump_version.py --to <X.Y.Z-rcN>` already parsed a SemVer
pre-release suffix (`SEMVER_RE`'s `(?:-([\w.]+))?` group) and
`scripts/alp_lock/__init__.py`'s version regex already tolerated one too --
but nothing actually let the suffix reach a build. `.github/workflows/release.yml`'s
"Parse tag + verify against metadata" step compared `metadata/sdk_version.yaml`'s
`version:` against the TAG's core (stripped-of-suffix) version with no
stripping on the metadata side, so a `version:` carrying `-rc1` failed the
release outright -- the only way to pass was to bump metadata to the bare
GA version and let just the git tag carry `-rcN`, which is exactly why an rc
checkout's `ALP_VERSION_STRING`, `alp_version_string()`, `alp.lock`'s
`sdk.version`, and the build plan's `sdkVersion` all read identically to the
eventual GA build. (This is what forced the manual CHANGELOG retitle in the
v0.15.0 window, #1292: the metadata never distinguished the rc from the GA
it never shipped.)

Fixed at the root: `release.yml` now strips DECLARED's own suffix
(`DECLARED_CORE="${DECLARED%%-*}"`) before comparing to the tag's core, so
`metadata/sdk_version.yaml` can legitimately carry the SAME suffix as the
tag being cut. A second guard closes the gap that alone would have opened:
a GA tag (no suffix of its own) now REFUSES a metadata `version:` that
still carries a leftover rc suffix -- otherwise a forgotten final bump
after the last rc would ship a GA build silently reporting itself as an
rc, #1902 in the other direction. `scripts/bump_version.py --to 1.0.0-rc1` now writes the FULL
`1.0.0-rc1` into `metadata/sdk_version.yaml`'s `version:` and
`include/alp/version.h`'s `ALP_VERSION_STRING` (`ALP_VERSION_MAJOR/MINOR/PATCH`
stay the plain core integers) -- SemVer's own pre-release syntax, not a new
field. `pyproject.toml`'s `[project]` version and the `alp_banner.c` sample
line stay pinned to the core triple (PEP 440 doesn't accept a bare `-rc1`
suffix, and neither is the self-identification surface -- the banner's
*code* always prints the live `ALP_VERSION_STRING`). `CHANGELOG.md` is left
untouched by a pre-release bump: an rc has no GA section of its own yet, and
slicing one would starve `release.yml`'s documented `## [Unreleased]`
fallback of content; the later GA bump (`--to 1.0.0`, no suffix) does the
real slice.

Two more consumers had the same `\s*$`-anchored regex and would have
silently broken (or gone blind) the first time this was actually exercised:
`scripts/check_version_doc_sync.py`'s `declared_version()` now accepts the
suffix and checks `ALP_VERSION_STRING` against the FULL declared string
(`declared_version_full()`) while every other copy -- pyproject.toml,
alp_banner.c, VERSIONS.md -- still checks the core triple only; and
`scripts/abi_snapshot.py`'s `_SDK_VERSION_RE` (used by
`current_snapshot_version()` / `--print-current-version`, which
`scripts/test-all.sh`'s `abi_current_snapshot()` and `pr-abi-snapshot.yml`
both call) now tolerates the suffix too -- pre-fix it returned `None`
("can't verify"), silently skipping `stage_abi_strict` for the whole rc
window instead of running it.

`status: released` in `metadata/sdk_version.yaml` is deliberately left
alone: overloading it for this was already proposed and rejected once
(this CHANGELOG's v0.15.0 entry and #1508, both citing alp.lock churn) --
the pre-release suffix is the narrower, additive fix `scripts/alp_lock/__init__.py`,
`scripts/alp_orchestrate/sdk_compat.py`, `scripts/alp_orchestrate/buildplan.py`
and `scripts/alp_cli/__init__.py` already tolerated with zero code changes.
