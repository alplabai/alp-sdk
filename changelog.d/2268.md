### Fixed — Hantro JPEG driver: output-buffer overrun, a permanently-leaked import slot, and stale-completion races on error paths (#2268)

Found in review of the camera-mjpeg-stream example (#2265), before real
usage exposed any of these, and hardened further by a dev-review pass on
the first fix.

**1. Output overrun.** `jpeg_start_encode()`'s output pointer at
`zephyr/drivers/video/jpeg_hantro_vc9000e.c:481` ("uint8_t *output_ptr = (uint8_t *)buf->buffer + data->header_size;")
points the SWREG8 output-stream base `header_size` bytes into `buf->buffer`
(`CONFIG_VIDEO_JPEG_HANTRO_VC9000E_HEADER_SIZE`, default 623), but the
SWREG9 size-limit register was programmed with the full `buf->size` — SWREG9
bounds writes starting at the SWREG8 base, not at `buf->buffer` itself, so
the hardware could write up to `header_size` bytes past the end of the
caller's output buffer before tripping `JPEG_BUFFER_FULL`. There is no
datasheet in this tree to cite for that register semantics directly; the
evidence is `jpeg_hantro_vc9000e_isr()`'s completion path, which computes
`data->encoding_size = jpeg_read_reg(dev, JPEG_SWREG9_OFFSET) + data->header_size`
— treating the HW-overwritten SWREG9 as the PAYLOAD size excluding the
header, consistent only with SWREG9 being relative to SWREG8. The fix is
conservative either way: if this reading is wrong, the failure mode of
using the smaller limit is at worst a spurious `-ENOSPC`/`JPEG_BUFFER_FULL`
on a tightly-sized buffer, never an overrun. Fixed by programming
`buf->size - header_size` instead, at
`zephyr/drivers/video/jpeg_hantro_vc9000e.c:571` ("jpeg_write_reg(dev, JPEG_SWREG9_OFFSET, output_limit);"),
and rejecting a buffer too small to hold the header before that subtraction
can underflow — both now live in a new pure helper,
`jpeg_hantro_vc9000e_output_limit()` at
`zephyr/drivers/video/jpeg_hantro_vc9000e_limit.h:44` ("if (buf_size <= header_size) {"),
split out specifically so this guard is host/native_sim unit-testable
without the jpeg0 hardware — see `tests/unit/jpeg_hantro_output_limit`
(this unit test covers ONLY that pure size-limit helper; the stale-completion
and quiesce-poll fixes below have no host harness and are unverified beyond
the AEN803 builds and the Flow C bench image link listed at the bottom).

**2. Leaked video-buffer-pool import slot, and a wedged encoder after a
timeout.** `hantro_encode()` (`src/backends/jpeg/alif_hantro.c`) imports the
caller's output buffer via `video_import_buffer()`, then enqueues and
dequeues it. On a `video_dequeue()` error it previously returned without
ever releasing that slot. Ownership map, verified by reading
`jpeg_hantro_vc9000e_dequeue()`:

- `-ENOSPC` (`JPEG_BUFFER_FULL`) / `-EIO` (bus error): the driver's own
  dequeue path already clears `data->current_buf` before returning these, at
  `zephyr/drivers/video/jpeg_hantro_vc9000e.c:663` ("data->current_buf = NULL;")
  — ownership is unambiguously back with the caller. Un-fixed, this is
  inferred (not bench-observed) to have leaked one pool slot per such
  error and, after enough of them, made every subsequent
  `video_import_buffer()` fail `-ENOBUFS`, stopping encoding for good.
- `-EAGAIN` (completion-wait timeout): the driver's dequeue returns BEFORE
  touching `data->current_buf` — it may still be mid-DMA into the buffer.

The v1 fix released the slot on the first case but PARKED it forever on
`-EAGAIN`, reasoning that the pool slot might still be a live DMA target.
Dev review caught that this protected nothing: the pool slot is
`VIDEO_MEMORY_EXTERNAL` bookkeeping only — `video_buffer_release()` never
touches `out_buf` itself for an imported buffer (it frees memory only for
`VIDEO_MEMORY_INTERNAL`, per `video_buffer_release()` in
`drivers/video/video_common.c`) — so parking it protected the caller's
`out_buf` not at all, while still starving the POOL one slot per timeout
until it, too, wedged. The slot is now released unconditionally, at
`src/backends/jpeg/alif_hantro.c:475` ("(void)video_buffer_release(&vbuf);"),
on every dequeue-error path — `-ENOBUFS` from pool exhaustion can no longer
be caused by a run of timeouts.

What `-EAGAIN` actually needed was the encoder stopped and, as far as this
driver can tell, quiesced, before that release:

- `video_stream_stop()` is called first, at
  `src/backends/jpeg/alif_hantro.c:464` ("(void)video_stream_stop(st->dev, VIDEO_BUF_TYPE_OUTPUT);"),
  which needed a companion driver fix: `jpeg_hantro_vc9000e_set_stream()`'s
  disable branch never cleared `data->current_buf`, so even after stopping,
  the next `jpeg_hantro_vc9000e_enqueue()` would hit its
  `if (data->current_buf != NULL) return -EBUSY;` guard forever —
  permanently wedged, not just leaked. It now clears the reference on stop,
  at `zephyr/drivers/video/jpeg_hantro_vc9000e.c:760` ("data->current_buf = NULL;"),
  V4L2 STREAMOFF-style.
- A bounded quiesce poll follows the stop, at
  `src/backends/jpeg/alif_hantro.c:460` ("if (err == -EAGAIN) {") through
  `:467` ("deadline = k_uptime_get() + HANTRO_QUIESCE_POLL_TIMEOUT_MS;"),
  reading a new read-only volatile control, `VIDEO_CID_JPEG_ENC_BUSY`,
  defined at `zephyr/include/zephyr/drivers/video/video_alif.h:27`
  ("#define VIDEO_CID_JPEG_ENC_BUSY               (VIDEO_CID_JPEG_CLASS_BASE + 5)"). It is
  backed by `jpeg_hantro_vc9000e_get_volatile_ctrl()` reading SWREG5's
  `JPEG_ENC_ENABLE` bit straight from hardware, at
  `zephyr/drivers/video/jpeg_hantro_vc9000e.c:845` ("case VIDEO_CID_JPEG_ENC_BUSY:"),
  for up to `HANTRO_QUIESCE_POLL_TIMEOUT_MS` (5 ms, not a datasheet
  number). A cleared `ENC_ENABLE` bit is NOT proof any AXI write already in
  flight has drained -- there is no datasheet in this tree to confirm that
  is instantaneous -- so the slot is still released once the bound expires
  regardless of what the poll observed; this narrows the unsafe window, it
  does not close it. `<alp/jpeg.h>`'s `alp_jpeg_encode()` now documents
  that consequence explicitly: `include/alp/jpeg.h:197` ("@note On @ref ALP_ERR_TIMEOUT from a hardware-accelerated backend, the")
  and the matching `@return` line at `include/alp/jpeg.h:223`
  ("- @ref ALP_ERR_TIMEOUT -- (hardware backends only) the engine did") --
  `out_buf` contents are undefined after `ALP_ERR_TIMEOUT` until a later
  successful `alp_jpeg_encode()` or `alp_jpeg_close()`. Doc-only change, no
  signature change, no ABI break.

**3. Stale-completion races.** Two related hazards, both from the same
root cause: `jpeg_hantro_vc9000e_isr()` gives `data->encode_sem` and writes
`data->encoding_size`/`data->encoding_error` without anything ever
discarding a completion nobody collected.
- Path A: the ISR gives the semaphore for an abandoned request AFTER a
  caller has already given up waiting (timeout) but BEFORE the stop path
  runs. A later `jpeg_hantro_vc9000e_dequeue()`'s `k_sem_take()` for a NEW
  request could then return immediately on that stale count, reporting the
  old job's size/error as the new one's.
- Path B: a status bit latched in hardware before `JPEG_IRQ_EN_MASK` is
  re-enabled fires as soon as the IRQ is re-armed, reading whatever is
  currently in SWREG9 for whichever buffer happens to be current.

Both are now closed by discarding any latched completion, under
`irq_lock()` against a concurrently-firing ISR, in two places: the
`set_stream()` disable branch, at
`zephyr/drivers/video/jpeg_hantro_vc9000e.c:754` ("key = irq_lock();"), and
at the top of `jpeg_start_encode()`, before arming any new encode, at
`zephyr/drivers/video/jpeg_hantro_vc9000e.c:458` ("key = irq_lock();"). Each
clears SWREG1's status bits the same way the
ISR does (read, then write back what was read — W1C on the status bits,
a no-op on the enable bits) and calls `k_sem_reset(&data->encode_sem)`.
Unverified beyond a clean build and the ownership reasoning above -- there
is no bench or host harness that can exercise this ISR race.
