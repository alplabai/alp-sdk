### Fixed — Hantro JPEG driver: output-buffer overrun and a permanently-leaked import slot on an encoder error (#2268)

Found in review of the camera-mjpeg-stream example (#2265), before real
usage exposed either defect.

**1. Output overrun.** `jpeg_start_encode()`'s output pointer at
`zephyr/drivers/video/jpeg_hantro_vc9000e.c:471` ("uint8_t *output_ptr = (uint8_t *)buf->buffer + data->header_size;")
points the SWREG8 output-stream base `header_size` bytes into `buf->buffer`
(`CONFIG_VIDEO_JPEG_HANTRO_VC9000E_HEADER_SIZE`, default 623), but the
SWREG9 size-limit register was programmed with the full `buf->size` — SWREG9
bounds writes starting at the SWREG8 base, not at `buf->buffer` itself, so
the hardware could write up to `header_size` bytes past the end of the
caller's output buffer before tripping `JPEG_BUFFER_FULL`. Fixed by
programming `buf->size - header_size` instead, at
`zephyr/drivers/video/jpeg_hantro_vc9000e.c:556` ("jpeg_write_reg(dev, JPEG_SWREG9_OFFSET, output_limit);"),
and rejecting a buffer too small to hold the header before that subtraction
can underflow — both now live in a new pure helper,
`jpeg_hantro_vc9000e_output_limit()` at
`zephyr/drivers/video/jpeg_hantro_vc9000e_limit.h:44` ("if (buf_size <= header_size) {"),
split out specifically so this guard is host/native_sim unit-testable
without the jpeg0 hardware — see `tests/unit/jpeg_hantro_output_limit`.

**2. Leaked video-buffer-pool import slot.** `hantro_encode()`
(`src/backends/jpeg/alif_hantro.c`) imports the caller's output buffer via
`video_import_buffer()`, then enqueues and dequeues it. On a
`video_dequeue()` error it previously returned without ever releasing that
slot. Ownership map, verified by reading `jpeg_hantro_vc9000e_dequeue()`:

- `-ENOSPC` (`JPEG_BUFFER_FULL`) / `-EIO` (bus error): the driver's own
  dequeue path already clears `data->current_buf` before returning these, at
  `zephyr/drivers/video/jpeg_hantro_vc9000e.c:647` ("data->current_buf = NULL;")
  — ownership is back with the caller, so the slot must be released or it
  leaks permanently. After a handful of such errors every subsequent
  `video_import_buffer()` failed with `-ENOBUFS` and encoding stopped for
  good. Now released at `src/backends/jpeg/alif_hantro.c:431` ("if (err != -EAGAIN) {").
- `-EAGAIN` (completion-wait timeout): the driver's dequeue returns BEFORE
  touching `data->current_buf` — it may still be mid-DMA into the buffer, so
  releasing the slot here would risk handing a live DMA target back to the
  pool. Ownership is ambiguous, so the slot is deliberately NOT released;
  instead `video_stream_stop()` is called to force the encoder off, at
  `src/backends/jpeg/alif_hantro.c:434` ("(void)video_stream_stop(st->dev, VIDEO_BUF_TYPE_OUTPUT);"),
  so a FUTURE encode on the same handle isn't wedged. This depends on a
  companion fix to `jpeg_hantro_vc9000e_set_stream()`'s disable path, which
  previously left `data->current_buf` set after a stop — any later
  `jpeg_hantro_vc9000e_enqueue()` would then reject every buffer with
  `-EBUSY` forever. It now clears the reference on stop, at
  `zephyr/drivers/video/jpeg_hantro_vc9000e.c:726` ("data->current_buf = NULL;"),
  V4L2 STREAMOFF-style. The one slot behind the timed-out request itself
  still stays parked — ENC_ENABLE=0 quiescing any in-flight AXI write is not
  datasheet/bench-confirmed instantaneous, so reclaiming that specific
  memory is not provably safe. ponytail: a bounded, one-time cost per
  timeout, not an accumulating one; upgrade path is a bench-proven abort
  sequence or a DFP-documented "encoder idle" poll.
