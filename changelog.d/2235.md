### Fixed — the board-qualified preflight now catches near-miss names, stem conflicts and .conf mismatches too, and AEN803 gets its own twin for alp-console, blink, pwm-led-fade and drone-autopilot (#2235)

The unlanded remainder of closed PR #2232, itself the follow-up to #2094's
board-qualified overlay preflight in `scripts/bench/aen/build.sh`.

**The guard now checks `.conf` exactly like `.overlay`, and accepts
Zephyr's own SHORT stem, not only the FULL one.** Zephyr computes two
candidate filenames for both extensions -- the FULL stem (board + every
qualifier segment, `/` -> `_`) and a SHORT stem dropping the FIRST
qualifier segment (the SoC id), legal only for a single-SoC board -- both
AEN803 HE and HP declare exactly one SoC, so both stems are live targets
here, at
`scripts/bench/aen/build.sh:67` ("single-SoC board").
One shared function,
`scripts/bench/aen/build.sh:203` ("bench_build_require_board_qualified() {"),
is now called once per extension rather than duplicating the overlay-only
check #2094 shipped.

**User-visible effect of the rescoping to `alp_e1m_*_rtss_h[ep]`.** On
`origin/dev`, `build.sh`'s unscoped overlay loop refused (exit 2) on
every AEN target any app whose `boards/` ships overlays but none
`alp_e1m_*_rtss_h[ep]`-qualified -- 35 examples on this tree are in that
shape: 34 with no `alp_e1m_*` overlay at all (e.g.
`examples/peripheral-io/gpio-button-led`, `i2c-master`, `uart-echo`, each
shipping only `boards/native_sim_native_64.overlay`), plus the V2N-only
`examples/connectivity/iot-connected-camera`. The preflight no longer
refuses them, matching `check_example_board_overlay_parity.py`'s own
policy that an example whose `boards/` ships zero `alp_e1m_*`-qualified
overlays "IS legitimately board-agnostic" for that SoM family. (This
change does not claim they build for AEN -- only the four examples
below were built.)

**Three more refusal shapes, matched against Zephyr v4.4.1
(`cmake/modules/extensions.cmake`, `cmake/modules/boards.cmake`):**

- A file misnamed for THIS board specifically -- the bare board name, or
  board+SoC with the trailing RTSS qualifier dropped -- is invisible to
  the guard's `alp_e1m_*_rtss_h[ep]` scoping glob, itself new in this
  change: that glob only proves an app ships SOME real board-qualified
  file, not one shaped for this board. Zephyr auto-applies neither name
  (both accepted stems require the RTSS qualifier).
  `origin/dev`'s own unscoped `boards/*.overlay` loop already refused a
  bare-name overlay -- any `.overlay` present but not the exact
  `${BOARD//\//_}.overlay` match tripped it -- so the new `_rtss_h[ep]`
  scoping keeps refusing this board's own bare and board+SoC names too,
  for both kinds now: `.overlay` (matching what `origin/dev` already
  caught) and, newly, `.conf` (never checked there at all).
  `BOARD_BARE`/`BOARD_BOARD_SOC` name both, at
  `scripts/bench/aen/build.sh:185` ("BOARD_BARE="), and are folded into
  the same "have a file of this kind" check the generic glob already fed,
  at
  `scripts/bench/aen/build.sh:265` ("near_bare").
  They cannot collide with the `_firewall_probe`/`_firewall_proven`
  `EXTRA_CONF_FILE` fragments `examples/connectivity/firmware-update-log`
  ships: those always carry that suffix past the full stem, never a bare
  board or board+SoC filename.
- Both accepted stems present for the same extension passed the guard
  silently, and Zephyr's own `zephyr_file(CONF_FILES ...)` then
  FATAL_ERRORs ("Conflicting file names discovered. Cannot use both
  ${filename_0} and ${filename_1}...", `cmake/modules/extensions.cmake`
  line 2950 for `.overlay` / line 2997 for `.conf`) with a message
  `build.sh`'s own grep-based output filter drops. The guard now refuses
  this pair itself, naming both files and
  recommending the full stem -- the same one Zephyr's own error
  recommends -- at
  `scripts/bench/aen/build.sh:224` ("ships BOTH the full and short board-qualified").
- A malformed `$AEN_BOARD` -- a leading `/`, a trailing `/` (which
  `IFS='/' read -a` silently drops, so the stems would look well-formed
  and the bad target would reach `west build -b`), or an empty qualifier
  segment -- is now refused early (exit 2).
  `$AEN_BOARD` with an empty qualifier segment (`board//rtss_he`) is legal
  Zephyr shorthand for a single-SoC board -- upstream `boards.cmake` lines
  271-272 (not vendored in this tree) resolve the omitted SoC during
  Zephyr's OWN board lookup -- but that
  resolution never runs in this preflight, so a bare `/` -> `_`
  substitution on it produced a double-underscore stem no real file
  matches, and a false refusal. The guard now refuses early instead of
  guessing, asking for the board fully qualified, at
  `scripts/bench/aen/build.sh:152` ("empty qualifier segment ('//').").

`scripts/bench/aen/bench-env.sh`'s own `AEN_BOARD` note is reworded to
match -- each kind is checked SEPARATELY, and the scope is AEN
board-qualified `alp_e1m_*_rtss_h[ep]` names plus same-board near-misses,
not every board-qualified file -- at
`scripts/bench/aen/bench-env.sh:102` ("checks overlay and .conf files SEPARATELY -- exit 2 -- scoped to AEN").
`build.sh`'s own header comment is corrected too: Zephyr does NOT also
apply a bare `app.overlay` "by name automatically" once a board overlay is
picked up -- it only falls back to `app.overlay` when no `boards/` (or
`socs/`) overlay matched in the first place (upstream
`configuration_files.cmake` lines 76-84, v4.4.1, also not vendored here).
That fallback is not moot for every app this script builds: six
`examples/aen/*` apps (`aen-uart-ns16550-loopback`, `aen-spi-regcheck`,
`aen-npu-ethosu-regcheck`, `aen-npu-ethosu55-regcheck`,
`aen-can-regcheck`, `aen-dualcore-probe`) ship an `app.overlay` and no
`boards/` overlay at all, and get their `app.overlay` applied by exactly
this fallback; an app that ships BOTH gets only the board overlay,
at
`scripts/bench/aen/build.sh:17` ("(Zephyr only falls back to a bare app.overlay when no boards/ (or").

over three `$AEN_BOARD` shapes** -- HE and HP (the real 3-segment
board/soc/rtss shape) plus a synthetic 2-segment "one qualifier" shape
exercising the `<=2`-segment fallback a real AEN803 board never takes --
at
`tests/scripts/test_build_sh_board_qualified_guard.py:250` ("class TestBuildShBoardQualifiedGuard:"),

`tests/scripts/test_build_sh_board_qualified_guard.py:325` ("def test_both_full_and_short_stems_present_is_refused("),
and the malformed-board refusals, at
