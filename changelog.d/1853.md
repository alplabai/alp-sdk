### Fixed — the boot banner now warns when the compiled SoM `hw_rev` disagrees with the live EEPROM manifest (#1853)

Every build resolves a `hw_rev` (`board.yaml`'s `som.hw_rev`, falling back to
the SKU preset's `default_hw_rev`), and separately the SDK reads the SoM's
*actual* revision from the on-module EEPROM manifest at boot — but nothing
compared the two. On the AEN family, three E1M pads (`E1M_GPIO_IO8`,
`E1M_GPIO_IO10`, `E1M_GPIO_IO21`) physically sit on a *different chip*
depending on which revision is right, and `alp_hw_info_assert_matches_build()`
existed to catch exactly this — but had zero call sites in the tree, so a
build could disagree with its module silently. (It still has zero call
sites: this fix adds a boot-time check, not a caller of that function — see
`alp_hw_info_build_hw_rev_mismatch()` below.)

The boot banner (`CONFIG_ALP_SDK_BANNER`, on by default) now compares the
live manifest's `hw_rev` against the newly-emitted
`CONFIG_ALP_SDK_SOM_HW_REV` (`scripts/alp_orchestrate.py`, the same `hw_rev`
the build resolved — not a derived pad-routing table; nothing in a compiled
firmware image derives one from `pad_routes`/`pad_route_overrides` today,
that data is read only by the debug/BOM `--emit composed-route-table` /
`--emit carrier-netlist` surfaces) via the new, independently-testable
`alp_hw_info_build_hw_rev_mismatch()`, and prints a loud warning on a
disagreement. This is a warning, not a boot refusal, by default: a
factory-fresh module with no EEPROM manifest yet (`ALP_ERR_NOT_PROVISIONED`)
is an expected state and never trips it, and bricking a developer's board
over a revision string is a worse failure mode than a possibly-wrong pin. A
production build that would rather halt closed opts in via the new
`CONFIG_ALP_SDK_HW_REV_MISMATCH_FATAL`.

Not implemented here: refusing to *dispatch* only the specific pads whose
route actually differs between hw_revs (the issue's "stronger guard"). No
peripheral-class dispatcher consults any pad-route table today, so there is
nothing to retrofit — filed as **#1859** instead: generate a per-hw_rev
`cc3501e_gpio_routes[]` from the composed route table, plus one `hw_rev`
guard in the GPIO proxy (GPIO-only, much smaller than a dispatch-layer
change). #1859 is also why this fix, by itself, does not close the loop on
the bench module that reported #1853: `examples/aen/aen-cc3501e-gpio/src/
cc3501e_gpio_routes.c` (and the same table duplicated in
`aen-cc3501e-bringup` and `aen-cc3501e-companion-tour`) hardcodes the r2 map
— `{ALP_E1M_GPIO_IO8, 30u}` / `{ALP_E1M_GPIO_IO10, 35u}`, no IO21 entry — with
no `hw_rev` awareness at all. On the r1 bench module, this fix's banner
prints the warning correctly, but the hardcoded GPIO table is still wrong;
nothing here changes what pin actually gets driven.
`CONFIG_ALP_SDK_HW_REV_MISMATCH_FATAL` is today's coarser mitigation for
that gap: it halts before any pad is ever dispatched.

Bench-gated: verified against a crafted manifest under native_sim
(`tests/zephyr/hw_info`); not yet re-verified against the physical bench
module (`E1M-AEN801 r1`, serial `2617-0001`) that reported the original
mismatch.
