### Added — declare the on-die flash aperture and each memory region's write authority (#1365, split A)

Two optional metadata fields, authored data only: `soc_spec-v1`'s
`soc_flash_base` (the base address of the on-die non-volatile aperture --
`2147483648` / `0x80000000` on `metadata/socs/alif/ensemble/e3.json`..
`e8.json`) and `som-preset-v1`'s `memory_map[].write_authority` (WHO may
write a region: `customer_image`, `vendor_image`, `customer_runtime`,
`secure_enclave`, `none`, or `composite`), authored on all seven rows of
all six `metadata/e1m_modules/E1M-AEN{301,401,501,601,701,801}.yaml`
presets.

This exists to close a real hazard, found on the bench and previously
distinguishable only in a prose comment: `storage` (`0x80560000`, 96 KiB)
and `atoc` (`0x80578000`, 32 KiB) were the same shape in the data --
same `carveout: false`, no other differentiator -- even though one is
customer-mountable at runtime and the other is written by the Secure
Enclave at provisioning, and corrupting the latter can leave the part
unbootable. Bench-observed 2026-08-08: ATOC magic `ckBS` (`0x53426B63`)
read back **intact** at `0x8057EA50` while an app erased `0x80560000`,
which at that time fell inside the SAME `storage` partition -- an erase
of customer storage could reach the boot table, because one partition
spanned both. `atoc` has had its own declared region since; what was
still missing, and is what this change adds, is any machine-readable
statement of the difference between the two.

**Split A changes no allocator behaviour and no emitted bytes.** Both
fields are additive metadata; `scripts/alp_orchestrate/carveout.py`'s
`resolve_carve_outs()` still reads only `carveout:`, and no DTS,
partition table, or other generated artefact moves. `write_authority`
exists so the flash/RAM class can be derived and gated against
`carveout:` in CI (split B), not to change what the allocator does
today.

`mram_main`'s `base:` is deliberately left as the literal string `"TBD"`
and is NOT filled by this change. It is the whole-window alias over the
six fine-grained regions above (`write_authority: composite`), it is the
only authored row on E1M-AEN501/601/701/801 that lists `a32_cluster`, and
it carries no `carveout:` key at all -- and `resolve_carve_outs()` treats
an absent `carveout:` as eligible (`scripts/alp_orchestrate/carveout.py`
reads `if region.get("carveout") is False:`). The unresolved base is
therefore the only thing standing between the allocator and that window
today: the allocator seeds each region's high-water mark from
`base + size` alone and allocates **top-down**, with no knowledge that
six sibling partitions live inside the same extent, so an `ipc:` entry
naming an `a32_cluster` endpoint would place its first carve-out at the
TOP of the window -- inside `atoc` at `0x80578000`..`0x80580000`.

Filling that base is safe only once split B's derived-flash-class
refusal exists to reject the region first. The order is: **derived-kind
refusal first, then the base fill.** Never the reverse.
