### Fixed — mid-playback I2S underrun stopped the TAS2563 bit clock and left the amps in SHUTDOWN while `alp_audio_out_write()` kept returning `ALP_OK` (#2149)

**Measured** on `e1m-aen-evk-03` (E1M-AEN803, `alif:ensemble:e8` M55-HE, bench
test branch `test/u46-i2s-tas2563-on-reworked-mux` @ `094570cc4`, dev plus the
unmerged #2132/#2137 @ `36bc7f03a`, #2146 @ `bf77cb961`, and #2133): a
`aen-i2s-tas2563-probe` run wrote a continuous 1 kHz tone (16 kHz, S16
stereo, 256 frames/block, volume 128) on I2S3, then stopped calling
`alp_audio_out_write()` for a gap the log timestamps at ~4.6 s (`TONE 1/6 ON`
`15:20:23.769199Z` to `TONE 1 mic peak` `15:20:29.164074Z` = 5.395 s, minus
the ~800 ms 50-block tone-plus-mic-measure window itself = ~4.6 s) without
ever calling `alp_audio_out_stop()`. Across that gap both TAS2563 amps
(`0x4d`, `0x4e`) went `PWR_CTL` (`0x02`) `0x0c` → `0x0e` (MODE `00b` ACTIVE →
MODE `10b` SHUTDOWN) with `INT_LTCH0=0x04` (TDM_CLOCK) latched; `INT_LTCH4`
(power-down) is corroborated from run D of the same bench session:
`INT_LTCH4` `0x00` at `15:20:57.539884Z` → `0x80` at `15:21:03.146125Z`,
alongside `INT_LTCH3` `0x11` → `0x51` — bit 3 (`DC_DETECT`, `0x08`) is clear
in both reads, the bench baseline for the SDO-idle precondition noted below
(run A's own `INT_LTCH4=0x80/0x80` read at "after resume",
`15:20:23.766088Z`, was already latched on both sides and is not cited
here), while every subsequent `alp_audio_out_write()` kept
returning `ALP_OK` (0 write failures the whole run) and the PDM mics went
from measuring the tone at 1000 Hz, 63.9 dB above the in-band median, to
noise-floor at that frequency after the gap, with no self-heal observed
within ~1.2 s of continuous post-gap writes.

**Inferred mechanism**, confirmed by code reading at that base: when the TX
queue empties mid-playback, `i2s_tx_irq_handler()` moves the stream to
`I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:627` ("stream->state = I2S_STATE_ERROR;")) and
fell into `tx_stream_disable()`, which ended in `i2s_clock_disable()` —
clearing `CER.CLKEN` and stopping the master SCLK/WS generator entirely.
TAS2563 reads that bit-clock loss as its own cue to latch software SHUTDOWN
(`TDM_CLOCK`/`INT_LTCH0` bit 2). Issue #2137's transparent ERROR recovery —
a retried `i2s_write()` after its own `I2S_TRIGGER_PREPARE`
(`src/backends/i2s/zephyr_drv.c:703` ("err == -EIO && h->cfg.direction == ALP_I2S_DIR_TX")), then a deferred `_start_trigger()` once a block is
genuinely queued
(`src/backends/i2s/zephyr_drv.c:794` ("alp_status_t start_rc = _start_trigger(dev, h->cfg.direction);")) — re-enables the clock and
resumes the I2S stream, but nothing in that path re-arms the amp, so
playback resumes silently muted.

**Fixed** at the ISR underrun exit only, the narrow form: the queue-empty
branch that sets `I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:743` ("tx_stream_park_keep_clock(stream, dev);")) now calls
`tx_stream_disable_ex(stream, dev, /*keep_clock=*/true)` instead of the
plain `tx_stream_disable()`
(`zephyr/drivers/i2s/i2s_dw.c:629` ("tx_stream_disable_ex(stream, dev, true);")), which still disables the TX channel/block/interrupt and
still sets `I2S_STATE_ERROR` exactly as before — it only skips the final
`i2s_clock_disable()`
(`zephyr/drivers/i2s/i2s_dw.c:1490-1501` ("if (!keep_clock) {")). Every other
teardown path keeps gating the clock unconditionally: STOP/DRAIN/DROP
(`i2s_dw_trigger()`) all route through the `stream->stream_disable` function
pointer, wired to the `tx_stream_disable()` wrapper
(`zephyr/drivers/i2s/i2s_dw.c:1509-1512` ("static void tx_stream_disable(struct stream *stream, const struct device *dev)")),
itself wired as `.stream_disable = tx_stream_disable` in the
`i2s_dw_data_##index` initializer
(`zephyr/drivers/i2s/i2s_dw.c:1692-1694` ("static struct i2s_dw_data i2s_dw_data_##index")),
which always calls `tx_stream_disable_ex()` with `keep_clock=false` — and
the ISR's own already-`I2S_STATE_ERROR` and `last_block` exits call the
same shared body directly with `keep_clock=false` too, so PM suspend's
`i2s_disable_controller()` remains the only other TX-side path (unchanged)
that clears `CER.CLKEN` directly — `rx_stream_disable()` also clears it, on
the RX side. `I2S_TRIGGER_PREPARE` is the only trigger valid
from `I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:521-528` ("PREPARE trigger: invalid state"))
and moves straight to `I2S_STATE_READY` without touching the clock at all —
so a recovering stream keeps the clock alive exactly through the #2137
recovery window, unchanged in shape. `I2S_TRIGGER_DROP` is the other
trigger `i2s_dw_trigger()` accepts from `I2S_STATE_ERROR` (`STOP`/`DRAIN`
both require `I2S_STATE_RUNNING` and refuse `ERROR`, so those two are not
reachable from it at all) and calls the SAME `tx_stream_disable()` wrapper
with `keep_clock=false` via the `stream->stream_disable` function pointer,
so an abandoned errored stream still has its clock gated, not left running
forever.

**Clock state after every `I2S_STATE_ERROR` exit:**
- `I2S_TRIGGER_PREPARE` (ERROR → READY): clock **stays on** (unchanged by
  this fix; `tx_stream_disable()`/`_ex()` is never called on this path).
- `I2S_TRIGGER_DROP` (ERROR → READY, abandon): clock **gated off**, same
  as before this fix.
- `I2S_TRIGGER_STOP` / `I2S_TRIGGER_DRAIN` from ERROR: not reachable — both
  require `I2S_STATE_RUNNING` and refuse otherwise; no change.
- A second ISR entry while already `I2S_STATE_ERROR`
  (`zephyr/drivers/i2s/i2s_dw.c:646-650` ("Stop transmission if there was an error")),
  or the `last_block` exit
  (`zephyr/drivers/i2s/i2s_dw.c:652-656` ("Stop transmission if we were requested")):
  both still call the shared body with `keep_clock=false` — clock gated
  off, same as before this fix.

**Restart-glitch guard.** `tx_stream_start()` re-runs
`clock_control_set_rate()` and writes `CCR` (`i2s_configure_clock()`, whose
own doc comment says it "Should be called with Clock disabled" —
`zephyr/drivers/i2s/i2s_dw.h:441-446` ("Should be called with Clock disabled.")).
Note that `CER.CLKEN` has been `1` from `i2s_dw_initialize()` onward (it
calls `i2s_enable_controller()`, which calls `i2s_clock_enable()`), so in
practice CCR has always been written with the clock already live, on every
first start since boot — not only on a restart following the keep-clock
underrun path. What actually changes here is narrower: **skip**
`clock_control_set_rate()`/`i2s_configure_clock()` specifically to avoid
RE-touching the divider during underrun recovery, since re-deriving the
same divider gains nothing and a live CCR rewrite is not something to do
without silicon proof it's glitch-free.

Round 1 of this fix tracked that via a remembered sample rate
(`clk_frame_freq_configured`) compared against the stream's current
`cfg.frame_clk_freq`. **Round-2 review finding 1:** that cache was never
invalidated on `rx_stream_start()` (which reprograms the SAME shared
divider unconditionally), `rx_stream_disable()`, `i2s_suspend()`,
`i2s_resume()`, or a `tx_stream_disable_ex()` teardown that actually gates
the clock — so a TX restart could find `CER.CLKEN` set by an unrelated
RX/PM transition and wrongly skip reprogramming onto a divider that was
never actually programmed for its own rate. Fixed by replacing the cache
with a one-shot flag, `clk_restart_skip_ok`
(`zephyr/drivers/i2s/i2s_dw.c:238-252` ("bool      clk_restart_skip_ok;")):
set ONLY by the ISR's keep-clock underrun exit
(`zephyr/drivers/i2s/i2s_dw.c:628` ("stream->clk_restart_skip_ok = true;")),
consulted and unconditionally cleared by `tx_stream_start()`
(`zephyr/drivers/i2s/i2s_dw.c:1363-1367` ("clk_needs_reprogram = !stream->clk_restart_skip_ok")),
and also cleared by every other path that can invalidate it before that
restart happens: `rx_stream_start()`, `rx_stream_disable()`,
`tx_stream_disable_ex()` when `!keep_clock`, `i2s_suspend()`, `i2s_resume()`,
and `i2s_dw_configure()` when the TX rate actually changes. Paired with the
existing `i2s_clock_is_enabled()` helper
(`zephyr/drivers/i2s/i2s_dw.h:436-439` ("__STATIC_INLINE bool i2s_clock_is_enabled")).
`i2s->cfg.wss_len`/`sclkg` (CCR's other inputs) are fixed device-config
constants no `i2s_dw_configure()` call ever changes, so the flag being set
already implies `frame_clk_freq` is unchanged; a rate change between
PREPARE and this START (not exercised by the #2137 recovery flow) clears
the flag and reprograms normally.
**BENCH-VERIFY:** confirm no BCLK/WS glitch on the restart path that DOES
still reprogram.

**Known remaining gap, NOT fixed here:** `rx_stream_start()` reprograms
`clock_control_set_rate()`/CCR unconditionally on every RX start, including
while the shared clock may already be running (e.g. a TX stream left it on
via this fix's own keep-clock underrun exit), and `rx_stream_disable()`
still unconditionally clears `CER.CLKEN` on every RX overrun
(`zephyr/drivers/i2s/i2s_dw.c:1451` ("i2s_clock_disable(i2s);")) —
either one on a controller sharing this clock with an active TX stream
would reprogram or kill the TX bit clock out from under it. This driver is
half-duplex in practice (`dev_data->dir` is a single field, not
per-direction state), which narrows but does not eliminate the exposure,
since the two directions can still be reconfigured back to back on the same
physical clock. Refs #2150 (tracking issue already filed); out of scope for
this fix.

**Not yet verified on silicon** that this restores audio. `i2s_dw.c` is not
compiled by either default example build (`aen-evk-demo`, `aen-i2s-amp-alif`
build with I2S3 disabled by default) — the actual compile evidence is the
`-DEXTRA_DTC_OVERLAY_FILE=i2s3-enable-post-u46-rework.overlay` builds of
`examples/aen/aen-evk-demo` and `examples/aen/aen-i2s-amp-alif`, which do
enable I2S3 and were confirmed to build `i2s_dw.c.obj` with no warnings on
the AEN801 `rtss_he` target. That, plus the native_sim regression suites
below, is all that has re-run since this fix landed — nothing has been
re-run on `e1m-aen-evk-03` yet.

**Bench precondition, check before any long stall:** this fix intentionally
leaves `CER.CLKEN` set with `TER.TXCHEN=0` during the underrun window.
What the DesignWare I2S core drives on SDO while `TXCHEN=0` and the clock
keeps toggling is **not established from the TRM/source excerpts read for
this fix** — if it holds the last transmitted (non-zero) sample rather than
forcing 0, that is DC into the amp for the whole gap, which is a distinct
failure mode from the SHUTDOWN latch this fix targets and needs checking
before a long stall is left running unattended. Verify with SHORT stalls
first (seconds, not the ~4.6 s repro's actual duration) and watch
`INT_LTCH3` bit 3 (`DC_DETECT`, `0x08`) — clear in both bench reads cited
above, but that predates this fix and does not by itself prove SDO's idle
level under it. Also check:
- No `TDM_CLOCK` (`INT_LTCH0` bit 2) latch across a gap-then-resume cycle.
- A tone is audible after a stall WITHOUT calling `tas2563_resume()`
  (distinguishing this fix from #2146's explicit-restart case, which still
  needs it).

**Regression harness built (round-2 review finding 4).** Round 1 of this
fix argued a native_sim unit compiling `zephyr/drivers/i2s/i2s_dw.c` itself
against a RAM-backed register block was infeasible — that turned out to be
wrong on both cited blockers. `tests/unit/i2s_dw_underrun/` now does
exactly that: `src/test_i2s_dw_underrun.c` `#include`s `i2s_dw.c` directly,
with NO `snps,designware-i2s` DT node anywhere in the test, so
`DT_INST_FOREACH_STATUS_OKAY(I2S_DW_INIT)`
(`zephyr/drivers/i2s/i2s_dw.c:1719` ("DT_INST_FOREACH_STATUS_OKAY(I2S_DW_INIT)"))
expands to nothing — neither `i2s_dw_initialize()` nor a
`DEVICE_DT_INST_DEFINE()` instance is ever wired up, side-stepping round 1's
first cited blocker (`device_is_ready(i2s->clk_dev)`) entirely, since that
call site is simply never reached. The second blocker (`DT_INST_REG_ADDR()`
needing a DTS-compile-time literal address backed by real memory) does not
apply either, for the same reason: with zero DT instances, that macro is
never expanded. What actually makes every other static function
(`tx_stream_start()`, `i2s_tx_irq_handler()`, `i2s_suspend()`/`i2s_resume()`,
...) directly callable is that `#include`-ing the `.c` file puts them in the
SAME translation unit as the test — no linkage, no fake device driver
needed. The test manually builds an `i2s_dw_cfg` whose `paddr` points at a
plain `static struct I2S_Type` in test BSS (the `__IOM` register accessors
just read/write it like any other struct) and whose `clk_dev` points at a
fake `clock_control` device with a counting `.set_rate`/`.on`/`.off`/
`.configure` — the ONLY genuinely hardware-specific pieces the driver
touches; everything else (`k_mem_slab`, `k_sem`, `irq_lock()`, the ring
buffer) is real Zephyr kernel code, unchanged, running normally on
native_sim. The CMSIS macros (`__IOM`/`__OM`/`__IM`/`__STATIC_INLINE`/
`_VAL2FLD`/`_FLD2VAL`) and `CONFIG_I2S_DW_{RX,TX}_BLOCK_COUNT` (gated by
`CONFIG_I2S_DW`, which itself depends on
`DT_HAS_SNPS_DESIGNWARE_I2S_ENABLED` — deliberately absent here) are
predefined by the test ahead of the `#include` for the same reason.

Eight tests drive `i2s_dw_configure()`/`i2s_dw_write()`/`i2s_dw_trigger()`
and `i2s_tx_irq_handler()` directly, matching finding 4's list: (a) a
queue-empty underrun leaves `state == I2S_STATE_ERROR`, `CER` bit 0 `== 1`,
`TER` bit 0 `== 0`, and the TX interrupt masked; (b) `PREPARE` then a
same-rate restart does not call `set_rate`; (c) `DROP` clears `CER` bit 0;
(d) `STOP`/`DRAIN` (two tests) gate the clock; (e) the finding-1
stale-divider sequence (TX underrun arms the skip flag → `PREPARE` → RX
starts on the SAME shared clock at a DIFFERENT rate → TX restarts at the
ORIGINAL rate) DOES call `set_rate`, proving `rx_stream_start()`'s flag
invalidation; (f) suspend then resume then start reprograms; (g) the
finding-1 invalidation site in `i2s_dw_configure()` itself — TX underrun
arms the skip flag → `PREPARE` → `i2s_dw_configure()` at a DIFFERENT rate →
TX restarts — also reprograms, proving the rate-change clear at
`zephyr/drivers/i2s/i2s_dw.c:406` ("stream->clk_restart_skip_ok = false;").
