### Fixed — mid-playback I2S underrun stopped the TAS2563 bit clock and left the amps in SHUTDOWN while `alp_audio_out_write()` kept returning `ALP_OK` (#2149)

**Measured** on `e1m-aen-evk-03` (E1M-AEN803, `alif:ensemble:e8` M55-HE, bench
test branch `test/u46-i2s-tas2563-on-reworked-mux` @ `094570cc4`, dev plus the
unmerged #2132/#2137 @ `36bc7f03a`, #2146 @ `bf77cb961`, and #2133): a
`aen-i2s-tas2563-probe` run wrote a continuous 1 kHz tone (16 kHz, S16
stereo, 256 frames/block, volume 128) on I2S3, then stopped calling
`alp_audio_out_write()` for a gap the log timestamps at ~4.6 s (`TONE 1/6 ON`
`15:20:23.769199Z` to the next `after tone` readout `15:20:31.373458Z`,
minus the ~5.4 s tone-plus-mic-measure window itself) without ever calling
`alp_audio_out_stop()`. Across that gap both TAS2563 amps (`0x4d`, `0x4e`)
went `PWR_CTL` (`0x02`) `0x0c` → `0x0e` (MODE `00b` ACTIVE → MODE `10b`
SHUTDOWN) with `INT_LTCH0=0x04` (TDM_CLOCK) and `INT_LTCH4=0x80`
(power-down) latched, while every subsequent `alp_audio_out_write()` kept
returning `ALP_OK` (0 write failures the whole run) and the PDM mics went
from measuring the tone at 1000 Hz, 63.9 dB above the in-band median, to
noise-floor at that frequency after the gap, with no self-heal observed
within ~1.2 s of continuous post-gap writes.

**Inferred mechanism**, confirmed by code reading at that base: when the TX
queue empties mid-playback, `i2s_tx_irq_handler()` moves the stream to
`I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:571` ("stream->state = I2S_STATE_ERROR;")) and
fell into `tx_stream_disable()`, which ended in `i2s_clock_disable()` —
clearing `CER.CLKEN` and stopping the master SCLK/WS generator entirely.
TAS2563 reads that bit-clock loss as its own cue to latch software SHUTDOWN
(`TDM_CLOCK`/`INT_LTCH0` bit 2). Issue #2137's transparent ERROR recovery —
a retried `i2s_write()` after its own `I2S_TRIGGER_PREPARE`
(`src/backends/i2s/zephyr_drv.c:696` ("err == -EIO && h->cfg.direction == ALP_I2S_DIR_TX")), then a deferred `_start_trigger()` once a block is
genuinely queued
(`src/backends/i2s/zephyr_drv.c:787` ("alp_status_t start_rc = _start_trigger(dev, h->cfg.direction);")) — re-enables the clock and
resumes the I2S stream, but nothing in that path re-arms the amp, so
playback resumes silently muted.

**Fixed** at the ISR underrun exit only, the narrow form: the queue-empty
branch that sets `I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:571-579` ("Keep CER.CLKEN")) now calls
`tx_stream_disable_ex(stream, dev, /*keep_clock=*/true)` instead of the
plain `tx_stream_disable()`
(`zephyr/drivers/i2s/i2s_dw.c:588` ("tx_stream_disable_ex(stream, dev, keep_clock);")), which still disables the TX channel/block/interrupt and
still sets `I2S_STATE_ERROR` exactly as before — it only skips the final
`i2s_clock_disable()`
(`zephyr/drivers/i2s/i2s_dw.c:995-997` ("if (!keep_clock) {")). Every other
teardown path keeps gating the clock unconditionally: STOP/DRAIN/DROP
(`i2s_dw_trigger()`) and the ISR's own already-`I2S_STATE_ERROR` and
`last_block` exits all call the same shared body with `keep_clock=false`
(`zephyr/drivers/i2s/i2s_dw.c:965-977` ("keep_clock is true for exactly one")), and PM suspend's `i2s_disable_controller()` clears `CER.CLKEN`
directly, unchanged. `I2S_TRIGGER_PREPARE` is the only trigger valid from
`I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:384-390` ("PREPARE trigger: invalid state"))
and moves straight to `I2S_STATE_READY` without touching the clock at all —
so a recovering stream keeps the clock alive exactly through the #2137
recovery window, unchanged in shape. `I2S_TRIGGER_DROP` is the other
trigger `i2s_dw_trigger()` accepts from `I2S_STATE_ERROR` (`STOP`/`DRAIN`
both require `I2S_STATE_RUNNING` and refuse `ERROR`, so those two are not
reachable from it at all) and calls the SAME `tx_stream_disable()` wrapper
with `keep_clock=false` via the `stream->stream_disable` function pointer,
so an abandoned errored stream still has its clock gated, not left running
forever.

**Clock state after every `I2S_STATE_ERROR` exit:**
- `I2S_TRIGGER_PREPARE` (ERROR → READY): clock **stays on** (unchanged by
  this fix; `tx_stream_disable()`/`_ex()` is never called on this path).
- `I2S_TRIGGER_DROP` (ERROR → READY, abandon): clock **gated off**, same
  as before this fix.
- `I2S_TRIGGER_STOP` / `I2S_TRIGGER_DRAIN` from ERROR: not reachable — both
  require `I2S_STATE_RUNNING` and refuse otherwise; no change.
- A second ISR entry while already `I2S_STATE_ERROR`
  (`zephyr/drivers/i2s/i2s_dw.c:482-486` ("Stop transmission if there was an error")), or the `last_block` exit
  (`zephyr/drivers/i2s/i2s_dw.c:488-492` ("Stop transmission if we were requested")): both still call the shared body with `keep_clock=false` —
  clock gated off, same as before this fix.

**Restart-glitch guard.** `tx_stream_start()` re-runs
`clock_control_set_rate()` and writes `CCR` (`i2s_configure_clock()`, whose
own doc comment says it "Should be called with Clock disabled" —
`zephyr/drivers/i2s/i2s_dw.h:399` ("Should be called with Clock disabled.")); a restart following our new keep-clock underrun path finds
`CER.CLKEN` already set, so reprogramming that live register is not
something to do without silicon proof it is glitch-free. Chosen: **skip**
both calls when `CER.CLKEN` is already set for the SAME sample rate this
stream last programmed
(`zephyr/drivers/i2s/i2s_dw.c:906-907` ("clk_needs_reprogram =")), guarded
via the new `i2s_clock_is_enabled()` helper
(`zephyr/drivers/i2s/i2s_dw.h:392-394` ("return (i2s->paddr->CER & I2S_CER_CLKEN_Msk) != 0;")). `i2s->cfg.wss_len`/`sclkg` (CCR's other
inputs) are fixed device-config constants no `i2s_dw_configure()` call ever
changes, so `frame_clk_freq` is the only input that can genuinely differ; a
rate change between PREPARE and this START (not exercised by the #2137
recovery flow) still reprograms normally.
**BENCH-VERIFY:** confirm no BCLK/WS glitch on the restart path that DOES
still reprogram.

**Known remaining gap, NOT fixed here:** `rx_stream_disable()` still
unconditionally clears `CER.CLKEN` on every RX overrun
(`zephyr/drivers/i2s/i2s_dw.c:962` ("i2s_clock_disable(i2s);")), so an RX
overrun on a controller sharing this clock with an active TX stream would
still kill the TX bit clock the same way a TX underrun used to. Out of
scope for this fix; a follow-up issue is warranted.

**Not yet verified on silicon** that this restores audio (the fix compiles
and passes the existing regression suites but has not been re-run on
`e1m-aen-evk-03` yet). Bench checks for that follow-up:
- SDO idles at logic 0 with `TER.TXCHEN=0` and the clock still running —
  a held non-zero sample would put DC into the amp; the register tell is
  `INT_LTCH3` bit 3 `DC_DETECT`.
- No `TDM_CLOCK` (`INT_LTCH0` bit 2) latch across a gap-then-resume cycle.
- A tone is audible after a stall WITHOUT calling `tas2563_resume()`
  (distinguishing this fix from #2146's explicit-restart case, which still
  needs it).

**Also updated:** the recovery-path comment in
`src/backends/i2s/zephyr_drv.c` that used to say an underrun's clock loss
leaves the amp un-re-armed by this layer now reflects that the clock
itself no longer drops on the TX underrun path
(`src/backends/i2s/zephyr_drv.c:153` ("As of issue #2149, i2s_dw.c's underrun ISR path keeps")), while still calling out the two paths that ARE
unaffected by this fix: an explicit stop()/start() cycle
(`I2S_TRIGGER_STOP`/`DROP` still gate the clock, same as issue #2146
documents) and the RX-overrun gap noted above.

**Prose still describing the pre-fix behaviour, for a #2146 follow-up**
(not touched here — `include/alp/audio.h` and `include/alp/chips/tas2563.h`
conflict with the unmerged #2146 branch and are updated after it merges):
`include/alp/audio.h:206-208` ("that shut itself down when the bit clock stopped is not re-armed by") — still true for an explicit stop()/start()
and for the RX-overrun path, but no longer true for a plain TX underrun
gap.

**Regression harness evaluated, not built.** A real
`tests/unit/i2s_dw_underrun` compiling `zephyr/drivers/i2s/i2s_dw.c` itself
against a RAM-backed register block was the stated goal — the existing
fakes (`tests/unit/i2s_start_defer/src/fake_i2s.c`,
`tests/unit/audio_out_start_defer/src/fake_i2s.c`) model the Zephyr I2S
trigger/state-machine contract, not `CER`, so neither can fail without this
fix regardless of how the ISR/backend logic around them changes. Building
the real driver on `native_sim` hits two compounding blockers past the
~300-line/no-upstream-edits budget: (1) `i2s_dw_initialize()`
hard-requires `device_is_ready(i2s->clk_dev)` and a working
`clock_control_configure()`/`_on()` pair — no fake `clock_control` driver
exists anywhere in this tree today, native_sim included, so that alone is
new scaffolding; (2) `DT_INST_REG_ADDR(index)`
(`zephyr/drivers/i2s/i2s_dw.c:1155` ("DT_INST_REG_ADDR(index)")) must be a
DTS-compile-time LITERAL address that, at runtime, is a validly mapped
`struct I2S_Type` the test controls — native_sim is a hosted POSIX process
with no MMU-trapped peripheral address space, so making a hand-picked
literal address back a real C struct needs either a custom linker
MEMORY-region + `mmap`-based hw-model (the same plumbing native_sim's own
flash/UART simulators use, not something a ~300-line test file can bolt
on) or relying on the linker coincidentally placing a global at that exact
address, which is not a reliable CI mechanism. The proof for this fix is
therefore the bench step above, not a native_sim unit test.

**Existing regressions re-run, unaffected:** `tests/unit/i2s_start_defer`
and `tests/unit/audio_out_start_defer` both stay green (`twister -p
native_sim`, 29/29 test cases) — expected, since neither exercises `CER`.
