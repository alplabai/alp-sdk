### Fixed — `zephyr_video` / `v2n_n44_isp` camera backends did not compile against the pinned Zephyr v4.4.1 `drivers/video/` API (#1628)

Both `src/backends/camera/zephyr_video.c` and `src/backends/camera/v2n_n44_isp.c`
still called the pre-v4.4 Zephyr video API (`VIDEO_EP_OUT`, single-arg
`video_stream_start`/`_stop`, unversioned `video_buffer_alloc`), which no
longer compiles against the v4.4.1 pin — CI never caught it because every
in-repo `CONFIG_VIDEO=y` configuration disabled both
`ALP_SDK_CAMERA_ZEPHYR_VIDEO` and `ALP_SDK_CAMERA_V2N_N44_ISP`. The v4.4 API
port itself (`enum video_buf_type` on caps/format/buffers,
`video_buffer_alloc(size, K_NO_WAIT)`, typed `video_stream_start`/`_stop`)
landed on `dev` already via #1803, mirroring `alif_isp_pico.c`; this change
keeps that port and adds the parts #1803 did not cover:

- `_release_vbufs()` on both backends now takes a `stop_stream` argument.
  The open()-rollback paths (buffer-pool exhaustion, mid-loop enqueue
  failure) pass `false` — the stream was never started there, and a driver
  that treats a stop-while-idle as an error (or powers the sensor down on
  it) should not see one; `close()` passes `true` unconditionally. #1803's
  version called `video_stream_stop()` unconditionally on every release,
  including from the never-started open() rollback paths.
- Buffer sizing: when `video_format.pitch` is 0, bytes-per-pixel is derived
  from the negotiated fourcc via Zephyr's `video_bits_per_pixel()`, now
  rounded up with `DIV_ROUND_UP` so a non-byte-aligned table entry (e.g. a
  10/12-bit packed Bayer format) can't under-allocate by truncating — #1803's
  version used a plain `/ BITS_PER_BYTE` that truncates. A fourcc
  `video_bits_per_pixel()` can't size at all now returns `ALP_ERR_NOSUPPORT`
  rather than silently under-allocating, **except** for JPEG/compressed
  frames, which fall back to the pre-#1628 flat `w*h*2` heuristic (compressed
  frames have no fixed bits-per-pixel to derive). `alp_camera_open()`'s
  documented `@return` list in `include/alp/camera.h` names `ALP_ERR_NOSUPPORT`
  and `ALP_ERR_OUT_OF_RANGE` as reachable from this path.
- The case where no format could be negotiated at all (a driver without
  `get_format`) now returns `ALP_ERR_NOT_READY` instead of opening a handle
  backed by a 64-byte dummy allocation the caller has no way to distinguish
  from a correctly-sized one — #1803's version kept the 64-byte dummy
  fallback for this case.

`_errno_to_alp()` on both backends stays on `dev`'s shared
`alp_status_from_zephyr_errno()` baseline (issue #1638, landed independently
of this fix) rather than being reverted to the hand-rolled switch this PR
was originally drafted against.

`tests/zephyr/camera_video` is a new native_sim/native/64 twister scenario,
not present on `dev`, and the only in-repo build compiling both backends
against the real Zephyr v4.4.1 drivers — `CONFIG_ALP_SDK_CAMERA_V2N_N44_ISP=y`
is compile coverage only (silicon_ref selection still picks `zephyr_video`
under native_sim). It covers the general open/start/capture/release/stop/close
round trip, the pitch==0 RGB888 sizing fix via a `alp,fake-video-pitch0`
fixture, and the pitch==0 JPEG fallback via a `alp,fake-video-jpeg0` fixture.
