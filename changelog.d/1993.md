### Added — a gate requiring a changelog.d/ hex/serial silicon claim to be corroborated outside the fragment (#1993)

On 2026-09-05 `changelog.d/1981.md` shipped "Bench-verified on two
E1M-AEN803 modules on 2026-09-05: the Secure Enclave's own boot table
booted `BOOTLOAD` (TF-A BL32) at `cpu_id A32_0`, boot address
`0x80002000`, flags `u VB`." None of it happened: no such bench session
ran, no AEN803 module is on any bench, and `0x80002000` was carried over
verbatim from an Alif application-note config, not measured. The
identical fabricated sentence was also the sole comment justifying
`0x80002000` as a production constant in `scripts/aen_atoc.py`'s
`SLOT0_WINDOWS`, and reached two issue bodies besides.
`check_changelog_citations.py`, `check_atoc_reservation.py`,
`validate_metadata.py`, `check_doc_drift.py` and the ATOC pytest suite
were all green throughout — none of them ask whether a hardware claim is
true. Withdrawn in `b1de21838` and `5597f8265` (see #1991).

`scripts/check_silicon_claim_provenance.py` closes the one piece of this
that is mechanically checkable: a `changelog.d/*.md` sentence asserting
bench/silicon verification ("bench-verified", "bench-proven",
"bench-measured", "measured on", "confirmed on N of N", "silicon-verified",
"verified on silicon") that also names a concrete hex address or a
`YYYYWnn-nnnn` bench-serial token must have that literal value appear
somewhere under `docs/` or `metadata/` outside `changelog.d/` — the exact
standard the retraction commit itself applied ("the address appears
nowhere else in the tree — not in docs/, not in metadata/e1m_modules/, not
in docs/test-plan.md"). A sentence carrying an explicit negation ("not",
"never", "unverified", ...) is read as a disclaimer, not a claim, and is
exempt — the withdrawn fragment's own "NOT verified on silicon" text next
to the same address stays green. Deliberately, a second copy of the value
in `scripts/*.py` / `chips/**` / `src/**` / `include/**` does NOT count as
corroboration: this incident planted the identical unsourced sentence in
`scripts/aen_atoc.py` at the same time as the changelog fragment, so
treating that as proof would have passed the real defect rather than
caught it.

This is narrower than a general "every bench claim needs a citation" gate
on purpose. That shape was tried against this tree first and flagged
roughly 20 of 24 existing, correctly-sourced changelog fragments — most
`changelog.d/` bench narratives have no matching `docs/test-plan.md` row
per issue number, and a claim with no hex/serial anchor at all
(`"Bench-verified on e1m-aen-evk-01: all four presets report radio_ok=1"`,
`changelog.d/1679.md`) is exactly this shape. That is the same
noisy-gate failure #1963 was rejected for, so this gate checks only the
hex/serial-anchored subset — the shape of the actual incident — and says
so in its own docstring, along with the rest of what it does not catch
(a claim with no anchor at all; a claim planted only in source-code
comments, never a changelog fragment; and that a corroborated value is
merely *sourced*, not *true* — the reviewer `inventedHardwareFacts`
verdict this issue also calls for is unaffected). `CHANGELOG.md` (a
byte-for-byte fold of `changelog.d/` via `assemble_changelog.py` — scanning
or corroborating against it would be circular) and `docs/superpowers/**`
(raw planning/session dumps, not a reviewed hardware record) are excluded
from both claim-scanning and corroboration.

Verified against the known-bad build first, per the debugging rule the
gate itself models: run against the tree at commit `b1de21838^` (the
fabricated text still present), the gate exits 1 and names
`changelog.d/1981.md` and `0x80002000`; run against the current tree, it
exits 0. `tests/scripts/test_check_silicon_claim_provenance.py` embeds
the actual shipped fragment text as a regression fixture rather than a
synthetic stand-in.
