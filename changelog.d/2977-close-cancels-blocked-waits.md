### Changed — `close()` wakes camera, hwsem, audio and BLE GATT calls blocked in another thread (#2977)

**`alp_camera_close()`, `alp_hwsem_close()`, `alp_audio_in_close()`, `alp_audio_out_close()` and `alp_ble_disconnect()` no longer wait out a blocked call's timeout; the blocked call returns `ALP_ERR_NOT_READY` and the close completes.** Before, `alp_camera_capture()`, `alp_hwsem_lock()`, `alp_audio_in_read()`, `alp_audio_out_write()` or `alp_ble_gatt_read()`/`alp_ble_gatt_write()` with `UINT32_MAX` made a concurrent close spin on its in-flight count forever. The dispatchers now mark the handle closing, call a new backend `cancel` op that only wakes waiters, and then drain as before. Zephyr backends whose driver call has no cancel API (`video_dequeue()` in `zephyr_video`, `alif_isp_pico` and `v2n_n44_isp`, `dmic_read()` and `alp_i2s_write()` in the audio backend, the shared hwsem `k_sem`, the GATT read/write semaphore) now wait in 50 ms slices and re-check the closing flag, so a cancelled call returns within one slice and a blocked call wakes 20 times a second. The Yocto camera and audio backends poll an eventfd alongside the device descriptors. The CC3501E BLE bridge backend checks the closing flag between bridge polls (#3103), so there too a blocked GATT call returns `ALP_ERR_NOT_READY` within one bridge attempt plus one poll gap (<= 50 ms). One exception remains: on the Zephyr audio backend a write already blocked handing a buffer to the I2S transmit queue is not interruptible. The `@retval` of each affected call in `<alp/camera.h>`, `<alp/mproc.h>`, `<alp/audio.h>` and `<alp/ble.h>` now says so; no <alp/*.h> portable symbol changed (see #3103 for the CC3501E chip API change).
