### Fixed — AEN Ethernet: pin GMAC descriptor rings + net_buf pools to SRAM0 without moving all of main RAM (#2260)

On Alif E8 (E1M-AEN801/803), the GMAC DMA cannot reach the M55 DTCM: the descriptor
rings and the net_buf packet pool must live in the global on-chip SRAM0
(`0x02000000`). The fix so far was `chosen { zephyr,sram = &sram0; }` in
`examples/aen/aen-ethernet-link`'s board overlays, which moves **all** of main
RAM off DTCM to SRAM0 — slower than DTCM for everything that is not Ethernet-DMA
traffic, and it intermittently broke the ISP.

Build-verified: pin only the Ethernet-owned buffers to SRAM0 and leave main RAM
on DTCM. The same placement idea was prototyped on silicon in scratch bench run
200, but that scratch used a different app-level relocation of net_pkt.c and the
glue file, `CONFIG_NOCACHE_MEMORY=y`, and different ring addresses — this exact
mechanism has not itself run on silicon yet.

`zephyr/dts/bindings/ethernet/alif,ethernet.yaml` gains an optional
`memory-region` phandle property (precedent:
`zephyr/dts/bindings/display/tes,cdc-2.1.yaml:98`, "memory-region:").
`zephyr/dts/alif/ensemble_e8_peripherals.dtsi`'s
`ethernet` node sets `memory-region = <&sram0>;`. `zephyr/drivers/ethernet/eth_dwmac_alif_ensemble.c`
places `dwmac_tx_descs`/`dwmac_rx_descs` in that DT region via
`Z_GENERIC_SECTION(LINKER_DT_NODE_REGION_NAME(DT_INST_PHANDLE(0, memory_region)))`
when the node carries `memory-region`, falling back to the previous
(`zephyr,sram`-inherited) placement when it does not; the `BUILD_ASSERT` that
`CONFIG_DCACHE` stays off is unconditional now (the E8 D-cache maintenance loop
hangs on this silicon, see `scripts/bench/aen/aen-bench-shared.conf`) — there is
no more `__nocache` arm, since with `memory-region` set that would conflict with
the section the DT region already gives the rings and fail to build when
`CONFIG_NOCACHE_MEMORY=y`.

`zephyr/kconfigs/vendor-alif-peripherals.kconfig` drops `ETH_DWMAC_ALIF`'s
`select NOCACHE_MEMORY if ARCH_HAS_NOCACHE_MEMORY_SUPPORT` (its nocache section
lands in DTCM, which the DMA cannot see) and adds
`ETH_DWMAC_ALIF_NET_BUF_IN_DMA_REGION` (default y, depends on `ETH_DWMAC_ALIF` +
`NETWORKING`), selecting `CODE_DATA_RELOCATION`. `zephyr/CMakeLists.txt` resolves
the region the same way the driver resolves the node — `dt_comp_path(...
COMPATIBLE "alif,ethernet" INDEX 0)`, then the `memory-region` phandle, then
that node's `zephyr,memory-region` string (single phandle properties export as
node paths) — and calls `zephyr_code_relocate(FILES ${ZEPHYR_BASE}/subsys/net/ip/net_pkt.c
LOCATION <REGION>_DATA / _BSS / _NOINIT)`; `net_pkt.c`'s net_buf pools are
`__noinit`. Both the Kconfig help and the CMake comment now say this prints a
CMake `WARNING` (not a silent no-op) when the Kconfig is on but no usable region
resolves. LIMIT, called out in the binding, the Kconfig help and the README:
only `net_pkt.c`'s own pools are relocated — an application's own net_buf pool
(e.g. `NET_PKT_DATA_POOL_DEFINE` via `net_context_setup_pools`) still lands on
DTCM and the DMA would silently fail against it.

`examples/aen/aen-ethernet-link`'s board overlays (both AEN801 and AEN803, kept
content-identical) drop `zephyr,sram = &sram0` — main RAM now stays on DTCM.
`docs/aen-bench-bringup.md` and the example README are updated to describe the
new placement, without pairing the 2026-06-17 DHCP-lease bench evidence (which
used the whole-RAM-move mechanism) with the new narrower one.

Because the ethernet node's `memory-region` is now set at the SoC-dtsi level,
it also applies to `examples/aen/aen-evk-demo`, which shrinks `&sram0`'s linker
region to a 64 KiB window shared with phase 13's JPEG buffers: the GMAC
descriptor rings and the relocated net_buf pools now land in that same window
too (measured 20800/65536 B, 31.7%, both AEN801 and AEN803), and `jpeg_out`
moved from `0x02000000` to `0x02001940`. Several of that example's comments
described a stale state — the "no narrower fix available to an application ...
so system RAM moves" claim, the address-map table, and a `prj.conf` comment
about `eth_dwmac_alif`'s BUILD_ASSERT being an OR that `select NOCACHE_MEMORY`
satisfied unconditionally — and are corrected in this change. `sram0_sys` (the
separate 512 KiB system-RAM window) is left in place; whether it could now be
dropped in favour of the generated `zephyr,sram = &dtcm` default is an open
question this change does not answer.

Verified: `aen-ethernet-link` builds clean for both
`alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he` and
`alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he`, 0 new warnings. `nm` confirms
`net_buf_data_rx_bufs`, `net_buf_data_tx_bufs`, `dwmac_rx_descs` and
`dwmac_tx_descs` land at `0x02xxxxxx` (SRAM0) while `_kernel`/`z_main_stack`
land at `0x20xxxxxx` (DTCM), identically on both boards. `aen-evk-demo` builds
clean on both boards, 0 new warnings, fits its 64 KiB SRAM0 window at 31.7%.
`aen-isp-ov5647-viewfinder` (non-network, `alif,ethernet` disabled) builds
unaffected.
