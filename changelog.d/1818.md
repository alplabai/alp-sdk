### Reverted — a #1818 follow-up briefly programmed the reduced DMA burst length into DMATDLR instead of the unreduced FIFO default; that write is now back to the unreduced default (#1818)

A pass over `spi_dw_dma_setup_tx_channel()` (`zephyr/drivers/spi/spi_dw_alif.c`)
found that DMATDLR (the DW_SSI TX DMA watermark register) got the raw,
unreduced half-FIFO default while the PL330 `dma_cfg` burst length —
computed separately — could be smaller, for a dummy-TX chunk or for
`ALP_CC3501E_OTA_MAX_CHUNK` (4092, not a multiple of the default burst of 8).
A first pass made the two match by writing the reduced burst length into
DMATDLR as well. That is reverted here: DMATDLR is a **low watermark**, not a
burst count — it asserts `dma_tx_req` once the TX FIFO holds `<= DMATDLR`
entries, and the only hardware constraint is `DMATDLR + burst <= fifo_depth`.
With `fifo_depth = 16` (`zephyr/dts/alif/ensemble_e8_peripherals.dtsi:624`)
the existing `DMATDLR = 8` with `burst <= 8` already satisfied that, so the
mismatch this closed was never a correctness bug by that measure. Moving
DMATDLR to 4 (the OTA tail) or 1 (a dummy-TX chunk) instead makes the PL330
refill in much smaller increments against a DW_apb_ssi master that gates
SCLK on TX underrun — an unproven, potentially-regressive behavioural change
with no bench evidence either way, so it is not made.

`write_dmatdlr(dev, dw_spi_txftlr_dflt)` (`zephyr/drivers/spi/spi_dw_alif.c`)
is back to the unreduced default. The extracted, host-tested burst-length
helper (`zephyr/drivers/spi/spi_dw_alif_dma_burst.h`,
`tests/unit/spi_dw_alif_dma_burst`) is kept: it still supplies the PL330
`dma_cfg` burst length for both directions, which does need to match the
actual burst, unlike DMATDLR.

Still open, and not resolvable from source reading alone: `spi_dw_dma_enable_channels()`
leaves `SSIENR = 1`, so every `write_dmatdlr()` / `write_dmardlr()` call runs
with the controller already enabled, and whether the DW_apb_ssi honours a
watermark-register write in that state is unverified. See the
`CONFIG_SPI_DW_ALIF_DMA_MIN_LEN` comment in
`examples/aen/aen-cc3501e-bringup/prj.conf` for the full note and the
one bench read-back (`read_dmatdlr()`/`read_dmardlr()`) that would settle it.
