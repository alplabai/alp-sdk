### Fixed — Flow D MRAM writes sector-pad neighbours and prove themselves with a fresh-session read-back, not `verifybin` (#2233)

Two defects measured on real hardware during the #2067 persistence proof made
every Flow D MRAM writer unsafe as written. SEGGER's built-in
`AE822FA0E5597LS0_M55_HE` loader always erases and reprograms WHOLE 16 KiB
sectors and never reads a sector's prior contents first, so a `loadbin` that
does not start and end on a sector boundary silently turned every other byte
in its first/last sector to `0xFF`. Separately, `verifybin` was comparing
against J-Link's own in-process flash cache, never a fresh chip read — a
`Verify successful.` proved nothing about what MRAM actually held.

`scripts/bench/aen/flowd_sector_pad.py:65` (`class FlowdSectorPadError(Exception):`)
is a new, pure host-side helper: given the blob(s) a write touches, it merges
their sector-aligned ranges, overlays the blob bytes on a pre-read sector
image, and refuses on a blob outside the MRAM window, a non-power-of-two
sector size, or two blobs overlapping with different bytes. It also pre-reads
and proves a GUARD sector immediately before/after each padded range, so
collateral damage just outside the intended write is visible, not just damage
inside it. `scripts/bench/aen/bench-env.sh:1808` (`bench_flowd_proof() {`) is
the shared bash orchestration — plan, read the touched sectors, build the
padded images, and a FRESH read-only J-Link session that `savebin`s each
range (and its guards) back and `cmp`s it against the padded image, which
proves both that the blob landed and that its immediate neighbours survived
THIS write.

Every affected writer — flash-jlink.sh, flash-jlink-hp.sh,
flash-jlink-mramxip.sh, flash-update-log-dual.sh,
flash-update-log-firewall-probe.sh, and the #1430 provisioning
erase-storage.sh — now gates on `bench_flowd_proof()` instead of `verifybin`,
and each write session also `savebin`s its own touched sectors immediately
before the load line(s) so a host-side compare against the original pre-read
can catch (not prevent — the pre-read is not halted) a write racing this
one between the read and the load. `FLOWD_DRY_RUN=1` is a THREE-layer
guarantee, not a flag with one effect: every writer exits right after
printing its would-be write CommandFile, `bench_jlink_run()` independently
refuses any `loadbin`/`erase` CommandFile while it is set, and
`bench_flowd_proof()` itself never reports success in this mode — an earlier
version of this fix only did the first of the three, so the write session
still ran for real underneath a "dry run" label.

`erase-storage.sh` additionally now resolves where the RESIDENT ATOC package
actually starts before erasing (`scripts/bench/aen/atoc_trailer.py`,
bench-measured on one real E1M-AEN803 board, serial 2026W36-0001,
2026-09-19) and refuses outright if the erase window would overlap it — on
that board the live package started well inside the nominal customer storage
window this script erases, which a metadata-window-only erase would have
zeroed part of. `--sku`/`ALP_AEN_SKU` picks which module preset a run
targets (previously hard-coded to E1M-AEN801), and every pre-write sector
read is copied to `$BENCH_ROOT/flowd-backup/<timestamp>-erase-storage/`
before any write, printed at run time — the only restore source on a board
with no SE-UART.

None of this is a persistence proof across a power cycle: the fresh-session
read-back proves the write landed and its neighbours survived within the
SAME power cycle, not that it survives one. flash-jlink-mramxip.sh's own
"ACCEPTANCE ON THIS PATH IS A COLD-CYCLE READBACK" requirement is unchanged
and still stands on top of this proof, not replaced by it.
