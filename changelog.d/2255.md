### Fixed — E8 ISP-Pico: 4:2:0 output chroma was vertically wrapped, corrupting real-scene colour (#2255)

Bench-proven on E1M-AEN803 + OV5647 (runs 176/186/187): the ISP core always
produces 4:2:2 chroma internally, and neither `VSI_MPI_ISP_SetScaleAttr()`
(closed VSI lib) nor `zephyr/drivers/video/isp_pico.c` ever programmed the
main resizer's (MRSZ) vertical chroma downscaler — `MRSZ_CTRL`, `SCALE_VC`,
and `FORMAT_CONV_CTRL` all read back 0 at stream start. For a 4:2:0 MI
output (`VIDEO_PIX_FMT_YUV420`/`NV12`/`NV21`) this meant the MI wrote a
full-height chroma plane (e.g. 480 lines) into a half-height buffer sized
for the format's own subsampling, wrapping the Cb/Cr write address ("Main
picture Cb/Cr address wrap" in the MI ISR) and leaving the bottom half of
each frame's chroma corrupted. Luma was unaffected and vertical colour bars
looked correct, which is why this was not caught by the bar-pattern
regression; a real scene lost or misplaced colour.

`isp_stream_start()` now programs MRSZ directly right after `isp_vsi_start()`
succeeds: for a 4:2:0 output it computes `SCALE_VC` from the actual output
height (`((height/2 - 1) * 65536) / (height - 1)`), zeroes `PHASE_VC`, sets
`FORMAT_CONV_CTRL` to 4:2:0, and enables the scaler with `CFG_UPD`/
`AUTO_UPD`; any other output format bypasses MRSZ (`CTRL=0` with `CFG_UPD`,
so a previous 4:2:0 stream's config cannot persist into a 4:2:2/raw one).
