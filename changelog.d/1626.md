### Fixed — `alp_power_profile_set()` accepted any `rail_mv` and forwarded it straight to the Alif SE DC-DC mailbox (#1626)

The Alif SE aiPM DC-DC rail (`run_profile_t.dcdc_voltage` / `off_profile_t.dcdc_voltage`,
`modules/hal/alif/se_services/include/aipm.h`) only accepts 750-850 mV. `alif_profile_set()`
in `src/backends/power/alif_se_profile.c` copied a caller's `rail_mv` into that field
unchecked for both `ALP_POWER_PROFILE_RUN` and `ALP_POWER_PROFILE_STANDBY`, so a caller
typo such as `8000` (an mV/uV slip) or any other out-of-window value reached the SE mailbox
verbatim instead of being rejected.

`alif_profile_set()` now validates `rail_mv` against the 750-850 mV window before writing
either profile and returns `ALP_ERR_INVAL` on an out-of-range value, on both the RUN and
STANDBY call sites — the SE mailbox setter is never invoked for a bad value.
`include/alp/power.h` documents the per-SoM window on the `rail_mv` field and the new
refusal on `alp_power_profile_set()`'s `@return`.

Regression test: `tests/unit/power_alif_dcdc_bounds/`. It compiles the real
`src/backends/power/alif_se_profile.c` translation unit against a fake `<se_service.h>`
(the same technique `tests/unit/se_cryptocell_hash_bounds/` uses for the same
Alif-SE-gated situation) and calls the shipped `alif_profile_set()` through the backend's
own vtable, asserting both that an out-of-range `rail_mv` returns `ALP_ERR_INVAL` on RUN
and STANDBY *and* that the fake `se_service_set_run_cfg()` / `se_service_set_off_cfg()`
were never called for those inputs — proving the SE mailbox itself was never written, not
just that an error code came back.
