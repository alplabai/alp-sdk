### Added — provisioning caches payloads on the SD it boots, not over the console or SSH (#2624)

- **Payload store.** A directory, `/var/lib/alp-payload/<bundle sha256>/`, on the provisioning SD's root filesystem; used only when Linux runs from the SD, on by default, `--no-payload-store` turns it off, never used in `plan`. `gd32_flash` (console path), `dxm1_npu_flash`, `write_rootfs`, `write_xspi` and `write_emmc_boot` use a stored file only after its hash, computed on the board, matches the signed bundle; a miss or mismatch pushes as before and caches the file (free space of size + 20 % + 64 MiB checked with `df -k` first, then `sync`). Evidence records `payload_source: sd-store|pushed`. No partition, no `prepare-sd`, no mount handling. Not yet benched.
- **Internal only.** The provisioning SD carries the license-gated DEEPX binaries and must never ship with a unit.
- **bmap write on the board.** `write_rootfs` pushes `bmap_writer.py` and runs it with the board's `python3` (`zlib` stream, `pwrite` per range, `fsync`; fails on a short or truncated stream), replacing the `dd iflag=fullblock` loop that BusyBox `dd` rejects. Without `python3`, or without a bmap, it writes the full image. Evidence always records `rootfs_write_mode` (`bmap-python` or `full-image`), `rootfs_bytes_written`, `rootfs_image_bytes` and, for the full image, `rootfs_bmap_fallback`. Not yet benched.
- **Ethernet diagnosis.** `boot_sd_linux` no longer assumes a blank GD32 explains a missing IP: the stmmac dmesg check and the single extra cold cycle run regardless of the GD32 state. If there is still no IP while a GD32 flash is pending the step continues on the console and records `network: none (gbeth DMA reset failed on <ports>)` or `none (no carrier)`.
- **Console and bmap hardening.** A flash write over the console is never Ctrl-C-ed or re-sent; an rc=127 is re-sent only when the command did not run; `bmap` refuses an image whose unmapped blocks are not zero; a non-block-aligned image is padded the same way on the host-stream and store paths.
- **Boot ROM `Address Error!!!`.** `load_writer` now names the cause (the SoC is probably not booting on the CA55) instead of timing out.
- **Clean shutdown before every power cut.** A hard cut under a Linux running from the provisioning SD corrupted its ext4 journal. Before every tool-driven power cut (`detect`, `bootstrap`, `boot_to_linux` and so `boot_sd_linux`, `eeprom_manifest`, `gd32_flash` and each `cold_boot_test` cycle, `poweroff_and_cold_boot`, and the operator prompts of `dsw1_emmc_insert_sd` and `dsw1_xspi_remove_sd`) the tool sends `poweroff` over this boot's console shell, or over SSH once the host has proved on the console that it is this unit, and waits up to 120 s for `reboot: Power down` or `System halted`. A console of unknown state gets a Ctrl-C probe (no Enter until a U-Boot prompt has been ruled out for 2 s). Each cut is recorded as the step evidence `power_cut`: `clean` (halted, first sync rc 0), `clean (sync rc=<n>)`, `fallback`, `blind` (Linux may be up, hard cut) or `not-needed`. The OFF dwell and the 3 cold cycles are unchanged. A kernel still booting is not covered. Not yet benched.
- **Census and I2C.** `i2cget` retries 3 times, 0.5 s apart; a read that still fails is recorded as `unread (<error>)` instead of dropping the key. Census adds `eth<i>_phy_id_raw` (MII registers 2/3), `eth_phy_id_mismatch`, `eth_dma_reset_failed`, and, with SCPI power, `psu_current_a` and `psu_current_state` (a reading above 0.40 A warns in the step detail, never fails). Not yet benched.
- **SCIF fallback banner.** The refusal for `SCI Download mode (Due to parameter error)` now says the boot ROM fell back because the selected boot source has no valid image, and to set DSW1 to mode 3. Behaviour unchanged.
