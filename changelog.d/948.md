### Documented — ADR 0032: vendor data under its own terms gets a segregated subtree, not a `library-v1` allowlist entry (#948)

#948's acceptance list made "add `LicenseRef-Alif` to `metadata/schemas/library-v1.schema.json`
`license.enum`" its first item and the hardest prerequisite for shipping the Alif Ensemble SVDs.
Checked against the tree, that enum is the wrong gate: it governs `metadata/libraries/*.yaml` — the
35 library manifests a project pulls through a `libraries:` selection — and its own description says
why it exists, "so a copyleft surprise cannot ride in through a `libraries:` selection (ADR 0018
non-goal)". An SVD is not west-pulled, is not selectable, and `soc-spec-v1.schema.json` carries no
`license` field at all. Admitting `LicenseRef-Alif` there would widen 0018's guard to authorise
something that never travels that path.

The second finding is that the carve-out is bigger than a new directory. The root `NOTICE` already
states, as a published claim, that "Silicon-vendor BSPs and SDK binaries (Alif Ensemble, Renesas
RZ/V2N, NXP i.MX93, DEEPX DX-M1) are NOT redistributed in this repository" — so vendoring an Alif
file amends a representation this repo has already made, rather than filling a blank.

`docs/adr/0032-vendor-data-under-its-own-terms.md` records the mechanism: the curated-library
allowlist stays permissive-only; vendor data the vendor permits us to redistribute lands in its own
subtree — `metadata/svd/<vendor>/` for vendor register descriptions and
`vendors/<name>/` for vendored source — with the vendor's
unmodified licence file beside it, a README naming the upstream repository and commit and the
field-of-use restriction, and a matching root `NOTICE` entry; and the `NOTICE` amendment lands in
the same change as the first file it describes, never ahead of it. It records the mechanism, not an
authorisation — whether Alp Lab redistributes any given vendor's files stays a per-vendor maintainer
decision, and nothing in it is legal advice.

Consequence for the two coupled issues: #948's stated blocker is **proposed** to be
withdrawn — the ADR is `Status: Proposed`, and acceptance items 1 and 2 remain a
maintainer/legal decision, the remaining one being the per-vendor redistribution
call. #383 would be decoupled if the ADR is accepted — memfault-firmware-sdk genuinely is a
curated library, so its `LicenseRef-Memfault` question stands on its own and still needs the legal
review ADR 0018 requires.

Docs only; no schema, metadata or code change. `docs/README.md`'s ADR count moves 30 -> 31.

### Added — `variants[].debug.svd`: declare where a Cortex Peripherals SVD comes from, gated, with no file shipped (#948)

`cortex-debug`'s Cortex Peripherals view is driven entirely by `svdFile`, and the SDK gave a
consumer nothing to resolve — alp-sdk-vscode's field is still the literal `"<resolved-svd>"`
placeholder. This ships the resolution *mechanism* and deliberately not the files.

`metadata/schemas/soc-spec-v1.schema.json`'s `$defs/variant/properties/debug` gains an optional
`svd` string beside `pyocd_target`, `jlink_device`, `jlink_flash_device`, `expect_dpidr` and
`openocd_config`. It is a **bare relative path** — never absolute, never containing `..`, never
a URL — resolved **repository directory first, then `ALP_SVD_DIR`**, the same shape
`SETOOLS_DIR` already has for genuinely licence-gated vendor tooling. Absence semantics match
the rest of that block: an unresolvable path is not an error, the consumer omits `svdFile` and
the session runs without a register pane. Substituting another variant's SVD is called out as
worse than omitting one, because a register map from the wrong part reads plausibly.

`_check_soc_debug_svd_shape` in `scripts/validate_metadata.py` enforces it, and it cannot be a
single rule: **shape** is checked always, because an absolute path bakes one machine's layout
into published metadata, a `..` escapes whichever root resolved it, and a URL is not a path a
debugger can open. **Existence** is checked only for a value under `metadata/svd/` — the
subtree ADR 0032 designates — because anything else names a file on the customer's machine
that no build host can see, and failing it would break a correctly-configured project on a
host with no vendor SDK installed. The discriminator is that declared prefix, not the
filesystem: a first draft keyed it on "does the parent directory exist", which inverted the
check, letting a value that names a subtree nobody has created yet — the first mistake a
vendoring PR would make — pass silently. That case is now a test.

**No SoC declares the key**, and a test pins that absence so it fails loudly the day it
changes. Whether Alp Lab redistributes Alif's SVDs under Alif's terms is still a per-vendor
maintainer decision: ADR 0032 records the mechanism, not an authorisation, and the root
`NOTICE` currently publishes the opposite claim, which the first vendored file would have to
amend in the same change. Until then the supported source is a customer-supplied file reached
through `ALP_SVD_DIR` — which is enough for alp-sdk-vscode to stop shipping a placeholder.

Schema, gate, tests and docs only; no vendor file, no `NOTICE` change, no `metadata/socs/**`
data change.
