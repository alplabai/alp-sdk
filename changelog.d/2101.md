### Added — a gate catching a testcase.yaml platform_allow entry with no matching boards/ overlay (#2101)

`scripts/check_example_board_overlay_parity.py` already caught a `board.yaml`-declared core with a missing overlay (#1009); it now also catches the sibling case #2101 reported: a `testcase.yaml` `platform_allow` entry for a real E1M SoM board target (`alp_e1m_*`) with no matching `boards/<target>.*`, while `boards/` ships an `alp_e1m_*`-qualified overlay for a different target in the same file. Zephyr's board-overlay auto-apply resolves a qualified target to its overlay filename by joining the board name and every `/`-separated qualifier with `_`, and separately accepts a SHORT form that drops the SoC-id segment (confirmed against `cmake/modules/configuration_files.cmake` and `cmake/modules/extensions.cmake` in a real Zephyr v4.4 checkout, not inferred from this repo's filenames); a target with no matching file in either form silently builds with no board overlay at all — no error, no warning. The precondition for "does this example use per-target overlays" is keyed off `boards/` content on disk, not off which `platform_allow` entries happen to be declared — the declaration-keyed form misses the defect's own fully-declared shape (`aen-brd-i2c-scan` on the AEN803 branch: `platform_allow` swapped to the AEN803 target, the AEN801 overlay left in place, zero declared-entry matches).

Measured on the AEN803 board-tree branch (counting directories, not files): 81 example directories under `examples/aen/`, 73 ship an `alp_e1m_aen801*` overlay, 1 (`aen-adc-regcheck`) ships `alp_e1m_aen803*`, 72 ship 801-but-not-803. This gate covers **0** of those 72 — none of them declares an AEN803 `platform_allow` entry at all, so a `platform_allow`-keyed check has nothing to compare against for them; closing those needs the overlays themselves (owned by #2100/#2103) or a broader repo-state-keyed check (below). On `origin/dev` today the check also finds 0 problems, but that means "nobody has declared a second SKU's `platform_allow` entry yet," not that this class is absent — `zephyr/boards/alp/` already ships preliminary `e1m_aen401_m55_hp` / `e1m_aen601_m55_hp` trees with no sibling overlay across the 12 examples that ship an `alp_e1m_aen801_m55_hp` one, reachable the moment any of those 12 declares an AEN401/AEN601 `platform_allow` entry. This gate is scoped to `alp_e1m_*` targets only, so an example whose only `boards/` content is a `native_sim` overlay/conf for a vendor reference-board `platform_allow` entry (a real, common, legitimate pattern) is never flagged — with one known exception outside this scope, filed separately: `examples/peripheral-io/drone-autopilot` ships a real `alp_e1m_aen801_m55_hp` overlay but declares only `ensemble_e8_dk` for its hardware scenario, so its build silently drops the overlay's `alp-i2c0`/`alp-uart1`/`alp-pwm0..3` aliases today.

`pr-metadata-validate.yml` is not among `dev`'s required merge-queue contexts (those are the `twister-shard` jobs, `clang-format · diff-only`, and `distro install · all`), so this gate does not hold the queue.

A broader, deferred alternative that would close all 72 plus the AEN401/AEN601 gap: key off `zephyr/boards/alp/` tree membership instead of `testcase.yaml` declarations — for every `boards/<SKU>_<quals>.overlay` an example ships, if a sibling SKU's board tree names the same core in its own `metadata/e1m_modules/<SKU>.yaml` `topology.<core>.board:`, require the sibling overlay or an explicit allow-list entry. Fully computable from committed metadata, but red on `dev` today (the 12 HP examples above), so deferred rather than landed here.
