### Added — a gate catching an example's testcase.yaml naming a board target with no matching boards/ overlay (#2101)

`scripts/check_example_board_overlay_parity.py` already caught a `board.yaml`-declared core with a missing overlay (#1009); it now also catches the sibling case #2101 reported: a `testcase.yaml` `platform_allow` entry for a real E1M SoM board target (`alp_e1m_*`) with no matching `boards/<target>.overlay`, while a *different* `alp_e1m_*` target in the same file does have one. Zephyr's board-overlay auto-apply resolves a qualified target to its overlay filename by joining the board name and every `/`-separated qualifier with `_` (confirmed against `cmake/modules/boards.cmake` and `cmake/modules/extensions.cmake` in a real Zephyr v4.4 checkout, not inferred from this repo's filenames); a target with no matching file silently builds with no board overlay at all — no error, no warning. Filed on the AEN803 board-tree branch, where 80 of 82 `examples/aen/*` apps are in exactly this state; on `origin/dev` today the check finds nothing, since no example yet declares a second SKU's `platform_allow` entry — it exists so that the moment one does, the drop is loud instead of silent. Scoped to `alp_e1m_*` targets only, so an example whose only `boards/` content is a `native_sim` overlay/conf for a vendor reference-board `platform_allow` entry (a real, common, legitimate pattern) is never flagged.
