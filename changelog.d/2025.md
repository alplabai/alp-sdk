### Fixed — Flow D's `flash-jlink*.sh` write a replacing ATOC with no way to warn what it delisted (#2025)

`app-write-mram -p` and a J-Link `loadbin` of a hand-authored ATOC both
REPLACE the resident ATOC rather than merging it — any boot entry not
named in the config being written is silently delisted, and the SES
prints `[SES] ATOC ok` afterwards with nothing to say otherwise. On
2026-09-07 this destroyed a diagnostic BL32 (md5
`94aa473453271b58160146ceaa828a5f`) plus an A32 Linux boot chain on
`e1m-aen-evk-01`.

PR #2026 guards the four SE-UART (Flow A) scripts with
`bench_atoc_replace_guard()`, which queries the resident TOC via SETOOLS
`maintenance -c $SE_UART -opt gettoc` before writing and refuses (exit 5)
unless `--replace-atoc` is passed. Flow D has no `SE_UART` dependency at
all — that is the point of Flow D, and on `e1m-aen-evk-03` (no SE-UART
resource) it is the only load path — so it cannot run that same query.

**Interim step only** (this change): `flash-jlink.sh`, `flash-jlink-hp.sh`
and `flash-jlink-mramxip.sh` now require an explicit `--atoc-unqueryable`
flag before writing anything; without it they abort (**exit 8**, chosen
to collide with none of these scripts' existing 1–7) with a message
naming the replace, the missing SE-UART channel, and the class of entry
that would be delisted (an A32 chain, an HP app). This is a deliberately
DIFFERENT flag from Flow A's `--replace-atoc`, not merged or aliased to
it: an operator on a no-SE-UART slot passes `--atoc-unqueryable` on every
single run, and that habit must never also unlock `--replace-atoc` on a
board where the resident TOC genuinely can be read.

**Open question, blocking the full (query-based) guard on Flow D:** does
`maintenance -c $SE_UART -opt gettoc` itself reset the target? If it
does, `AP[3] (APAddr 0x00300000)` — the AHB-AP carrying the M55 debug
domain — disappears (per `flash-jlink-mramxip.sh`'s own `#1902` notes:
0 of 8 post-reset scans found it), and that script's pre-programming `h`
halt gate (exit 5, unrelated to this change's exit 8) would then fail on
every run regardless of SE-UART availability. Reading the ATOC over
SWD/J-Link instead was assessed and rejected: MRAM reads on this part can
return an uncommitted shadow (a `loadbin` that verifies but does not
persist, so a same-power-cycle read shows the just-written package while
persisted MRAM holds a different, foreign one) and the debug-AP read path
has also returned a flatly false `Verify successful.` against data never
written (2026-09-05, 5/5 `verifybin` calls). Wiring the SE-UART `gettoc`
guard into Flow D needs the reset question answered on silicon first.
