### Changed — stop committing `alp.lock`; generate it on demand (#1576)

`alp.lock`'s `digests.metadata` (`scripts/alp_lock/__init__.py:158-166`) is a
single sha256 over the entire `metadata/**` tree, so any two PRs touching
*different* metadata files rewrote the same JSON line from different bases
and conflicted by construction, sharing no other file. Measured: #1576's body
recorded four PRs simultaneously DIRTY, three sharing no other file; in a
2026-08-25 merge campaign, #1676, #1678 and #1694 were each ejected from the
`dev` merge queue with `alp.lock` as the ONLY conflicting file — #1678 twice,
once per predecessor merge. Precedent: `sdk.revision` was retired in #1615
for exactly this conflict class. A `.gitattributes` merge driver can't fix
it either — the executable it names lives in local `git config`, which never
lives in the repo, and GitHub's server-side merge can't run it.

`alp.lock` is now generated on demand and no longer tracked. `build_lock` is
a pure function of tracked files, so any consumer regenerates the identical
document from the commit it needs it for:

- `git rm alp.lock`; `.gitignore` keeps a locally-regenerated `/alp.lock` out
  of any future commit.
- `west alp-lock --check` (`scripts/west_commands/alp_lock.py`) no longer
  diffs against a committed copy — there isn't one. It now builds a lock in
  memory and schema-validates it against `metadata/schemas/alp-lock-v1.schema.json`,
  still failing on a broken generator or a local/abs-path leak
  (`_reject_local`). Both `.github/workflows/pr-metadata-validate.yml`'s
  "alp.lock generator self-check" step and `scripts/test-all.sh`'s
  `stage_alp_lock` call the same unchanged CLI invocation, so only its
  internal behaviour moved.
- `scripts/check_sbom.py` builds the lock in memory (`alp_lock.build_lock`)
  instead of reading a committed `alp.lock` from disk.
- `.github/workflows/release.yml` generates `alp.lock` before packaging the
  source tarball and appends it into the tarball (`tar --append` after
  `git archive`, since `git archive` only knows tracked files) so a consumer
  with only the tarball -- not a git checkout -- still gets one; `gen_sbom.py`
  reads it from there for the SBOM step, unchanged.
- `scripts/bump_version.py` no longer regenerates `alp.lock` on a version
  bump (`regenerate_alp_lock` removed) -- nothing to keep in sync in a
  tracked file that no longer exists.
- `scripts/resolve_generated_conflicts.py`'s `REGENERATORS` no longer carries
  an `alp.lock` entry -- an untracked file can't appear in a merge conflict.
- `docs/getting-started.md` "Reproducing a build with alp.lock" no longer
  says to commit it or re-run-and-commit on a metadata change; it now
  documents the generate-and-validate model and that the release tarball
  carries one.
