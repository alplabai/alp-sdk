### Fixed — `wifi ap-stop` reported an unknown outcome as a definite failure (#1553)

`cmd_companion_wifi_ap_stop()` printed `ap stop failed (-4)` whenever
`cc3501e_wifi_ap_stop()` did not return `ALP_OK`. Against CC3501E firmware
protocol v4 that is the **expected** status regardless of what actually
happened: `WIFI_AP_STOP` sends no acknowledgement the driver can confirm on, so
`poll_by_repeat` exhausts its down-window and returns `ALP_ERR_TIMEOUT`. This
is the same missing-confirmation gap `wifi ap` already documents for
`WIFI_AP_START` (#1385), which is why `ap start` says "unconfirmed" rather than
"failed".

The driver cannot distinguish a teardown that did not happen from one that did,
so reporting a definite failure stated more than was known. The console now
says:

```
ap stop unconfirmed (-4) -- firmware v4 has no AP-stop acknowledgement
(#1553, same gap as #1385); confirm the SSID is gone out of band
```

It still returns an error — the status is *inconclusive*, not success.

`cc3501e_wifi_ap_stop()`'s declaration is corrected to match. It claimed
"`ALP_OK` once the firmware acknowledged the AP stop", implying an
acknowledgement protocol v4 does not send; it now carries the same `@warning`
shape as `cc3501e_wifi_ap_start()` and states that `ALP_OK` is not currently
reachable. Doc comment only — no signature or ABI change.

#### What the bench did and did not establish

Measured on E1M-AEN801 (2026-08-18) using a second, independent radio as the
observer (the host's Intel AX200 via `netsh wlan show networks`, validated
against known APs before being trusted — it saw the same neighbours the CC3501E's
own scan reported).

Established:

- **`ap start` really does start the AP despite its own `-4`.** A soft-AP
  started from the console was confirmed broadcasting on the independent radio.
  #1385's "unconfirmed" wording is accurate, not pessimistic.

Observed once, **not** established, and deliberately not relied on by this
change:

- With the link healthy and the AP confirmed visible, `ap-stop` returned `-4`
  and the SSID stopped being advertised ~45 s later (visible at 0.1 s / 15.2 s /
  30.3 s, gone at 45.4 s). That run had **no stability control** — the AP was
  never held untouched to prove it would not have dropped on its own — and the
  attempt to repeat it properly failed, because of the next item.

Open, and worth its own issue:

- **`wifi ap` frequently does not bring an AP up at all**, on a link confirmed
  healthy (`alp companion ver` → `CC3501E protocol v4`) immediately before. Three
  separate attempts saw no SSID appear across 90 s, 133 s and 121 s of polling,
  including the first `ap start` after a warm reset. An earlier `ap start` in the
  same session did come up. Whatever gates this is unknown; it is the reason the
  teardown measurement could not be repeated under control.
