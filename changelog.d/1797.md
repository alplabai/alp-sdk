### Fixed — `docs/aen-se-services.md` listed a second AEN bench board that does not exist (#1797)

ADR 0030 sets the supported SERAM floor for E1M-AEN at **v110** and says a board
below it "is updated before it is trusted to produce evidence". The per-board
table this doc added to record that
(`docs/aen-se-services.md:150` ("SERAM version, per physical board (#1797)"))
carried two rows: the bench unit, and "the second AEN bench board (on the
internal board farm)" marked `TBD` / **Unverified**.

There is no second board. The board-farm place `e1m-aen-evk-01` is a stale
definition — every resource on it reports `avail: False` with `port: None` and
`path: None`, the exporter host has no `/dev/ttyUSB*` attached at all, and the
exporter's own udev match rules name `ID_SERIAL_SHORT` `BG01028C` and
`BG04503B`, which are the same two FTDI adapters the bench enumerates as its
SE-UART and app-console ports. One board, moved off the farm.

The remaining row is now identified by module revision and serial rather than by
which host it happens to be plugged into, and re-confirmed on a cold power-on
reset: `SEROM v1.105.65 0x000002A0`, `SES A0 v1.110.0 Mar  4 2026`, both SERAM
banks `1.110.0`, `LCS=1`
(`docs/aen-se-services.md:159` ("The AEN bench unit")).

**v110 meets the floor exactly**, so every AEN board in existence is above it and
no SE-touching result is taken on a pairing ADR 0030 calls untriageable.

The same cold-POR capture also settled #1702, which had recorded that the SERAM
offset record at `0x805ffff0` does not survive a cold power-on and that the unit
must therefore be run warm-reset only. It survived a full 20 s power-off: SEROM
handed off to a valid SERAM bank, `ATOC ok`, and slot0 booted in 31.09 ms. That
constraint is not in force, which matters because it was written into every AEN
and CC3501E bench harness.
