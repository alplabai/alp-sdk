### Fixed — the provisioning example no longer records a real module under the wrong SKU (#2001)

`examples/aen/aen-eeprom-provision/` used the real allocated serial
`2026W36-0001` with `mfg 2026-09-04`, alongside `sku=E1M-AEN801` taken from the
example's own `board.yaml`. Both the command block and the expected-output
transcript did it, so the file read as a record that the module with that serial
had been provisioned as an `E1M-AEN801`.

It has not. **The maintainer confirmed the unit is an `E1M-AEN803`** — which is
what `changelog.d/1974.md:3`, `metadata/boards/e1m-evk.yaml:278` and
`src/zephyr/alp_banner.c:204` already say. Those three were corrected when #1977
landed; this example was the last place on `dev` still pairing that serial with
`E1M-AEN801`.

The SKU here is **not** changed to `E1M-AEN803`, deliberately. It comes from
`som.sku` in the example's `board.yaml`, and the per-example overlay filename is
required to be the fully-qualified Zephyr board id
(`alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay`). No `E1M-AEN803`
board tree exists under `zephyr/boards/alp/` — only the SoM preset
`metadata/e1m_modules/E1M-AEN803.yaml` — so renaming the SKU would break the
example's build to fix a documentation defect.

Instead the unit identity is now `<SERIAL>` / `<MFG-DATE>`, which is what a
worked example should have carried in the first place: step 1 of the same README
already says *"The serial must come from the allocation ledger, not from your
head."*

**Bench-owed, and not claimed here:** whether the physical module was ever
actually written with `sku=E1M-AEN801` is unverified. The transcript was
illustrative, but if that provisioning run really happened against
`2026W36-0001`, its EEPROM holds the wrong SKU and `alp_banner.c` will print it.
Reading the manifest back off that unit settles it in one line; nothing in this
change asserts either way.

Closes #2001.
