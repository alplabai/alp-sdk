### Added — the six Alif Ensemble variants the vendor declares and this repo did not

`metadata/socs/alif/ensemble/{e4,e5,e6}.json` each listed a subset of the
devices Alif actually ships. Measured against the vendor pack
(`alifsemi/alif_ensemble-cmsis-dfp`, `AlifSemiconductor.Ensemble.pdsc`), the
gap was e4 1-of-3, e5 1-of-4, e6 1-of-2. All six missing devices are now
carried:

```
e4.json  AE402FA0E5597BE0  WLCSP216  extended  5.5 MB   9984 KiB  flash_device: null
e4.json  AE402FA0D5597BS0  WLCSP216  standard  5.5 MB   9984 KiB  flash_device: null
e5.json  AE512F80F5582LS   FBGA194   standard  5.5 MB   8448 KiB  AE512F80F5582_HE
e5.json  AE512F80F5582AS   WLCSP208  standard  5.5 MB   8448 KiB  AE512F80F5582_HE
e5.json  AE512F80F55D5AS   WLCSP208  standard  5.5 MB  13824 KiB  AE512F80F55D5_HE
e6.json  AE612FA0E5597BS0  WLCSP216  standard  5.5 MB   9984 KiB  AE612FA0E5597BS0_M55_HE
```

**Every field is read per device out of the vendor pack, not decoded from the
order code.** `package` comes from the device's own
`<feature type="BGA"|"CSP" n=...>` element; `mram_mb` and `sram_kb` from its
resolved memory regions, `sram_kb` being the sum of the non-MRAM, non-TCM
regions.

That extraction was validated before it was trusted: re-deriving all **13
previously-shipped** Ensemble variants the same way reproduces their declared
`package` / `mram_mb` / `sram_kb` with **zero mismatches**. The first attempt
did not — it read E7 as 15616 KiB against the corpus's 13824. The corpus was
right: the 1792 KiB delta is exactly `ITCM_HP 256 + ITCM_HE 256 + DTCM_HP 1024
+ DTCM_HE 256`, core-private TCM that this corpus has never counted as SRAM.
E4/E6 only appeared to agree because their pack entries name the same banks
`SRAM2..SRAM5` with no `TCM` in the string. Fixing the extractor rather than
the metadata is what turns the round-trip into evidence.

`temperature_grade` is the one field the pack does not carry, so it remains the
order-code suffix decode (`E` = extended, `S` = standard) that holds across
every shipped variant.

`optional_features` is likewise per-device, and it discriminates.
`AE402FA0D5597BS0` — the `D5597` generation code, not `E5597` — is annotated
with **43 features against 52** for its siblings, and the block it drops is
display/imaging: GLCD, both Camera interfaces, the ISP Acceleration Unit, the
JPEG Encoder. It therefore carries `isp: false, jpeg_encoder: false` while the
two `E5597` variants in the same file carry them true. `npu_hg` stays true —
the Ethos-U85 is still annotated. No E5 variant declares `optional_features`:
the pack gives all four E5 devices an identical feature set (2x Ethos-U55, no
U85, no ISP, no JPEG), so there is nothing per-variant to toggle.

### Fixed — #1295's E4 Flow D gap is subfamily-wide, not one odd variant

Both new E4 devices also take `jlink_flash_device: null`, and that settles the
question #1295 left open with a sample of one. SEGGER's DLL V9.46 table holds
exactly two E4 entries — `AE402FA0E5597LS0` and `AE402FA0E5597BS0`, indices
93/94 — and Alif declares **neither**. Alif's three E4 devices are
`AE402FA0E5597LE0`, `AE402FA0E5597BE0` and `AE402FA0D5597BS0`. The intersection
is empty.

So no Alif-declared E4 part is flashable over Flow D until SEGGER ships a
profile, and all three now say so loudly instead of silently degrading to the
Linux-only SE-UART path. `BE0` is not `BS0`; substituting the nearest string
would point a flash algorithm at a part the vendor does not declare.

The four other additions do resolve, including an exact-match entry for the E6
WLCSP part (`AE612FA0E5597BS0_M55_HE`, index 104).

### Verification

Every `jlink_flash_device` string in the corpus — all 19 variants, not just the
six added — was round-tripped through the live DLL: `JLINKARM_DEVICE_GetIndex`
to resolve, then `JLINKARM_DEVICE_GetInfo` to read the canonical name back.

```
19 variants declared, 0 name mismatches, 0 unresolved
19 variants cross-checked against the DFP, 0 fact mismatches
validate_metadata.py: 9 SoC file(s) ... 0 failure(s)
```

Reading back rather than trusting the index is the point: SEGGER registers
order-code spellings as aliases, so a non-negative index proves a name
*resolves*, not that it is the entry — the error #1295 was opened to correct.

No gate is added here. The regression this guards against is drift from the
vendor pack, which cannot be checked offline; #1295's `validate_metadata.py`
check already fails any variant that omits the field entirely.

`AE101F4071542LH` and `AE1C1F4051920PH0` remain uncarried — E1 and E1C are
subfamilies with no file in this corpus, which is a different change from
completing the ones that exist.
