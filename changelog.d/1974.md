### Fixed — the E1M-EVK I2C map asserted three addresses that a bench sweep contradicts (#1974, #1975)

Read-only I2C censuses on **two** E1M-EVKs (carrying `E1M-AEN803` serials
`2026W36-0001` and `2026W36-0003`) found three of
`metadata/boards/e1m-evk.yaml`'s recorded addresses silent on **both**, with one
part answering somewhere else entirely:

* **Neither TCAL9538 GPIO expander answered.** `0x72` (U35 main) and `0x71`
  (U37 PCIe) were both clean `-EIO` NACKs, and so was the `0x20` TCA6408A
  alternative strap. Exactly one PCA9538-register-compatible expander replied,
  at **`0x73`** (`A1=1, A0=1`), at power-on defaults — `OUTPUT=0xFF`,
  `POL=0x00`, `CFG=0xFF`, `INPUT=0xFB` (bit 2 low, a live input). Since U37
  drives the PCIe slot RST/WAKE/CLKREQ lines and the I2C-mux SEL, this is the
  first thing to suspect when those misbehave.
* **One INA236 did not answer on each board — but not the same one.** On
  `2026W36-0001` it was `0x4A` (U30, +5V); on `2026W36-0003` it was `0x41`
  (U31, +1V8), while that board's `0x4A` answered and fingerprinted correctly.
  Every responding part gave `MFG_ID 0x5449` ("TI"). So "five of six respond"
  is batch-wide, while *which* one is missing is per-unit — and "U30
  unpopulated" cannot explain both boards. Power characterisation on either
  board silently omits one rail.

**Resolved: U35 is at `0x73`, and U37 is not fitted on this revision.** The
maintainer's EVK I2C schedule gives `TCAL9538RSVR U35 = 1110011` = `0x73`
(`A1=1, A0=1`), matching both boards — so this file was wrong on the address
*and* on the strap it recorded (`A1=1, A0=0` → `0x72`). The schedule lists only
one TCAL9538, and the maintainer has confirmed this EVK revision, built for
Alif, does not need the second expander: **U37 is not assembled**. That is why
`0x71` never answered, and why `0x20` (the TCA6408A alternative, bench-confirmed
on an earlier revision) does not appear either.

U35's address is corrected. U37 is marked `assembled: false` rather than
deleted — the footprint is real and other revisions populate it — which needed
a new `assembled` key on `i2c_device_entry` in
`metadata/schemas/board-preset.schema.json`, mirroring the one SoM presets
already have. Note the limitation recorded there: `gen_board_header.py` does not
read the key, so it still emits the address macro for an unfitted part.

Three entries initially looked like schedule-vs-silicon conflicts and none of
them were. BMP581 U14 (schedule `0x46`, boards `0x47`) is `0x47`: SDO is
connected to VIO on this EVK, which is that strap. TAS2563 U27 and U28 (schedule
`0x4C`/`0x4F`, boards `0x4D`/`0x4E`) are `0x4D`/`0x4E`. All three schedule
entries were slips, confirmed by the maintainer; the addresses in this file were
already right and are unchanged. Recorded because anyone comparing the schedule
against this file will hit the same three and should find the answer here rather
than re-deriving it on a bench.

**One hypothesis was tested and failed.** `EVK_PIN_IO_EXP_RST`
(SPI0_CS1 pad, E1M `N1`, Alif `P3_6`) was driven HIGH (reset deasserted) and then
pulsed LOW 10 ms → HIGH, on both boards. The I2C2 ACK set was byte-identical
across all three phases on both units — nothing appeared, nothing vanished. So
this is **not** a "deassert `IO_EXP_RST` before using the expanders" firmware
requirement.

The addresses are **deliberately unchanged**, but the reason has narrowed. It is
no longer "one board's strap is not the contract" — 2 of 2 units agree, so this
looks like a design/documentation mismatch rather than a per-unit assembly
defect. They stay as designed because what `0x73` physically **is** remains
unknown, so there is nothing verified to change them to. Each entry records what
was observed, when, and the issue tracking it.

One earlier claim needed qualifying rather than deleting: the `0x20` entry said
`BENCH-CONFIRMED 2026-06-16: read back config=0xFF + a live input port`. That
still stands for the board it was taken on, but it is not a property of every
EVK — on the 2026-09-05 board `0x20` was silent and that exact signature
appeared at `0x73`.

Which physical part sits at `0x73` is deliberately left unresolved: telling U35
from U37 requires driving an output, and writing to an unidentified expander on
a bus that also carries the identity EEPROM can move PCIe reset or display
control lines.

One of the two unexplained responders is now explained. `0x48` is the TAS2563's
**global address** per the datasheet, so it ACKs on any board with an amp
fitted. The census evidence already fitted: `MFG_ID(0x3E)=0x1000` ruled out an
INA236, and `REVID(0x7D)=0x10` at `0x48` was byte-identical to both fitted amps
at `0x4D`/`0x4E`. It is recorded so a future I2C census does not re-report it as
an undocumented device.

`0x58` remains genuinely unidentified — it is in neither the schedule nor this
file, and a pointer-free read returns all `ff` (alp-sdk#1976).
