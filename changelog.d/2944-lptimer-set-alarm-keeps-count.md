### Fixed — `counter_alif_lptimer` `set_alarm()` no longer loses the running count (#2944)

**`counter_get_value()` stays continuous across `counter_set_channel_alarm()`, the alarm firing and `counter_cancel_channel_alarm()`.** Arming an alarm reloads the single LPTIMER channel (one `LOADCOUNT`, no compare register), which discarded the count, left the channel cycling in the alarm period after the alarm fired, and made `counter_get_top_value()` return the alarm period. The driver now folds the elapsed count into a software base before each reload, the alarm ISR and `cancel_alarm()` restore free-run (`LOADCOUNT` `0xFFFFFFFF`), and the top value stays `0xFFFFFFFF`. `cancel_alarm()` with nothing armed no longer stops the counter, and `stop()` drops a pending alarm. Residual error: the few ticks between reading `CURRENTVAL` and the reload taking effect are lost on each `set_alarm()`/`cancel_alarm()`; ISR latency is not lost.

**After `cancel_alarm()` the channel keeps free-running (it used to be left disabled).** `alif_se_hw_wake_timer_disarm()` therefore leaves LPTIMER ch0 counting after a STOP cycle; that is harmless on the always-on 32 kHz domain, and `counter_stop()` is the way to halt it. After every reload the driver waits (bounded, about 100 us) for `CURRENTVAL` to show the new segment, because the register keeps the previous count (or 0) for about one LF clock after a `LOADCOUNT` write. A 1- or 2-tick alarm is only exact while the ISR runs within one alarm period.
