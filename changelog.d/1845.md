### Added — CI gate: no two chips may claim the same 7-bit I2C address, including a chip's broadcast address (#1845, folds in #1675)

`scripts/check_i2c_address_collisions.py` groups every declared I2C device by bus and by
7-bit address across `metadata/e1m_modules/*.yaml`'s `on_module.i2c_devices.<bus>.devices[]`
and `metadata/boards/*.yaml`'s flat top-level `i2c_devices:` list plus `audio.codecs[]`
(merged into one address space per board file — see below), and fails on any address
claimed by more than one chip on the same declared bus. `assembled: false` devices are
excluded; `assembled: optional` devices are NOT — a part fitted only on some board variants
still occupies its address when it is fitted.

**Two gaps closed relative to the gate's first cut (#1675).**

A board file's flat `i2c_devices:` list and its `audio.codecs[]` list are now checked as
ONE address space instead of two separate ones. `metadata/boards/e1m-x-evk.yaml` documents,
in its own leading comment, that the flat list and the audio codecs sit on the same
physical bus ("On-board sensors + I/O expander + ID EEPROM, all on the same
XEVK_I2C_BUS_SENSORS bus"), and its `audio.codecs` entries declare `i2c_bus: E1M_X_I2C0` —
the same bus by the board's own account.
(`metadata/boards/e1m-evk.yaml` has no `audio.codecs:` block at all — its TAS2563 rows are
already flat `i2c_devices:` entries — so this join only applied to e1m-x-evk.yaml.) A board
that ever puts devices on two genuinely different I2C buses will need a per-device bus field
before this join stays correct; the gate's docstring says so.

A chip's I2C *broadcast* address — a fixed address a part answers on regardless of its
strap, declared in its own `metadata/chips/<id>.yaml` under `i2c.addresses[]` with a `scope`
naming it (e.g. `{ addr_7bit: 0x48, scope: "global broadcast (write-only)" }` for the
TAS2563) — is now expanded onto every bus where that chip is already claimed and checked
for collisions like any other claim. Bus attribution still comes entirely from the instance
table (an unattributed chip-manifest address is still not read for anything but broadcast
rows); the manifest only supplies "this part also answers here" once the bus is already
known from an instance claim on it. A chip's own broadcast claim never collides with that
SAME chip's ordinary strap claim, only with a different chip at the same address.

Running this on the real tree finds two open, needs-silicon collisions, both recorded in
`WAIVERS` (keyed by `(relative_path, bus, address_int)`, valued with the exact excused
claimant multiset plus the tracking issue) so the gate stays green without hiding them:
`metadata/e1m_modules/E1M-V2M101.yaml` / `E1M-V2M102.yaml`, `brd_i2c` `0x48` (TMP112 vs
TPS628640 `deepx_lpddr_0v85`, #1163), and `metadata/boards/e1m-x-evk.yaml`, `0x48` (INA236
U32 `+VCAM2` vs the TAS2563 broadcast address, #1659). A waived collision still prints a
`NOTE:` line on stdout so it stays visible in CI logs instead of vanishing into a silent
exemption. A `WAIVERS` entry whose EXACT excused claimant set no longer collides — the
address freed, a device removed, a claimant swapped for a different part, or a third
claimant appearing at the address (even one whose label duplicates an already-excused one —
compared as a multiset, not a set, so duplicates can't hide a new claimant) — fails instead
of staying silently stale or silently absorbing the new claimant.

Wired into `pr-metadata-validate.yml`'s `validate` job; `metadata/**` was already in that
workflow's `paths:` filter so both `metadata/e1m_modules/**` and `metadata/boards/**`
already retrigger it, and `scripts/check_i2c_address_collisions.py` itself is added to the
filter too.

**Hardening carried forward from #1675's review history**, none of it lost in the rename:
a `WAIVERS`/`ALLOWLIST` entry excuses one known claimant set, not the address forever (keying
on address alone let a brand-new claimant slip through at rc=0 in an early cut; keying on a
`frozenset` of that set let a THIRD claimant whose label duplicated an excused one slip
through the same way one level down — both are covered by regression tests that mutate the
comparison and confirm it goes red). A declared address above `0x77` is not treated as a
distinct address (the schema's pattern allows up to `0xFF`, so a device entered in 8-bit
write-address form — `0xD0` for the 5L35023B, the form its own chip YAML quotes — would
otherwise compare unequal to the real `0x68` claimant and never collide with it). A
partially-declared `audio.codecs[]` entry (an address but no `i2c_bus`, or vice versa) is
reported instead of silently dropped, since `audio:` is a wholly open object in
`board-preset.schema.json` and this gate is one of its few readers. The failure summary
says "problem(s) ... (collisions, uncomparable entries, and/or stale waivers)" rather than
calling every reported line a collision.
