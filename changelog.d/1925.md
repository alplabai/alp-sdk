### Added — listening sockets on the CC3501E, so a host can serve over the soft-AP (#1925)

The CC3501E socket API was client-only — `cc3501e_sock_open` / `_connect` /
`_send` / `_recv` / `_close`, opcodes `0x20`-`0x24`. A product could not
terminate an inbound TCP connection over the module's own soft-AP even though
the bridge firmware already runs lwIP with `bind`/`listen`/`accept` available:
the AP path starts a DHCP server through that same stack. This is the host half
of cc3501e-bridge-firmware#104 — serving an embedded web console over the
module's AP so the product needs no Ethernet PHY.

Wire protocol **8 → 9** (`ALP_CC3501E_PROTOCOL_VERSION`):

| Opcode | Name | Payload |
|---|---|---|
| `0x25` | `ALP_CC3501E_CMD_SOCK_BIND` | `alp_cc3501e_sock_bind_t` — the `SOCK_CONNECT` layout with the LOCAL endpoint |
| `0x26` | `ALP_CC3501E_CMD_SOCK_LISTEN` | `alp_cc3501e_sock_listen_t` |
| `0x2c` | `ALP_CC3501E_EVT_SOCK_ACCEPTED` | `alp_cc3501e_sock_accepted_evt_t`, async |
| `0x17` | `ALP_CC3501E_CMD_WIFI_GET_IP` | gains an optional `alp_cc3501e_wifi_iface_t` byte |

New host API in `<alp/chips/cc3501e/sockets.h>`: `cc3501e_sock_bind()`,
`cc3501e_sock_listen()` and `cc3501e_sock_accepted_decode()`.

**There is deliberately no accept opcode.** `accept()` blocks, and the firmware
worker holds READY low across a worker body, so an accept opcode would black the
whole bridge out — every opcode, not just sockets — for as long as no client
connected. An inbound connection arrives instead as an entry on the existing
polled event queue (`cc3501e_poll_events`), carrying a handle the host uses with
the ordinary `SOCK_RECV` / `SOCK_SEND` / `SOCK_CLOSE`.

The accepted-connection event is a compact 12-byte IPv4 form, not a 20-byte
`alp_cc3501e_sock_addr_t`: the firmware event ring caps a per-entry payload at
`ALP_CC3501E_EVENT_PAYLOAD_MAX` (16) and **clamps** anything longer, i.e.
silently truncates it on the wire, so `_Static_assert`s pin the size against
that cap (`include/alp/protocol/cc3501e.h:1481`
(`sock_accepted must fit ALP_CC3501E_EVENT_PAYLOAD_MAX`)). Use
`cc3501e_sock_accepted_decode()` rather than casting the callback's payload
pointer — it aims into the driver's event buffer at whatever offset the entry
landed on, so the cast is unaligned.

**Breaking:** `cc3501e_wifi_get_ip()` takes the interface as a parameter
(`cc3501e_wifi_get_ip(ctx, iface, ip)`), rather than gaining a second entry
point beside a permanently-STA one. Pass `ALP_CC3501E_WIFI_IFACE_STA` to keep
existing behaviour; `ALP_CC3501E_WIFI_IFACE_AP` reports the module's own
soft-AP address — the bind address a serving application needs before any
client has associated.

`alp companion sock serve <port> [seconds]` is the worked reference: it binds,
listens, and answers inbound HTTP, printing the AP-side address to aim a client
at.

Bench-verified on an E1M-AEN801 (2026-09-03, firmware GPE `0.149.83.0`,
`GET_VERSION` → protocol v9): an associated client holding a DHCP lease from the
CC3501E's own server received `HTTP/1.0 200 OK` on 16/16 requests across 5 serve
runs at ~0.45 s each, each connection arriving as `opcode 0x2c (len 12)`, with
the bridge still answering `GET_VERSION` afterwards.

Not fixed here and not caused here: socket operations in AP mode are unreliable
when they race radio activity — back-to-back **client** ops, and `bind`/`listen`
issued while a client is still associating. The first shape reproduces
identically on the pre-change protocol-8 firmware with no listening socket in
play; both are cc3501e-bridge-firmware#106. The send direction is also unbounded
(cc3501e-bridge-firmware#107).
