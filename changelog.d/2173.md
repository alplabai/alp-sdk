### Fixed — the connectivity examples build for AEN again: mbedTLS' PSA core is now on wherever mbedTLS is (#2173)

`mqtt-telemetry`, `iot-fleet-ota` and `production-deployment` did not compile
for an AEN target at all, and the same break is why each carried a
`CONFIG_MBEDTLS=n` workaround on `native_sim`. Root cause, now established: the
`mbedtls` library manifest emits `CONFIG_MBEDTLS=y` +
`CONFIG_MBEDTLS_BUILTIN=y` and nothing else, which builds the library's SSL
sources with PSA crypto off. The pinned mbedTLS does not survive that — its own
internal `library/ssl_misc.h` declares `extern const mbedtls_error_pair_t
psa_to_ssl_errors[7]` unconditionally, while `mbedtls_error_pair_t` itself is
inside `#if defined(MBEDTLS_PSA_CRYPTO_CLIENT)` in tf-psa-crypto's
`psa_util_internal.h`, so every translation unit that pulls in `ssl_misc.h`
fails with `unknown type name 'mbedtls_error_pair_t'`. It is an alp-sdk
integration gap, not an upstream bug and not a Zephyr one: upstream has no
non-PSA TLS path left to fall back to.

The fix is one Kconfig rule rather than a per-example knob
(`zephyr/Kconfig.alp-libraries:365` ("config ALP_SDK_MBEDTLS_PSA_CRYPTO")):
whenever `MBEDTLS` is on and TF-M is not building the crypto partition, the SDK
selects `MBEDTLS_PSA_CRYPTO_C`. `MBEDTLS_PSA_CRYPTO_CLIENT` — the symbol the
header actually tests — is not directly assignable; it is a non-prompt bool
defaulting y on `BUILD_WITH_TFM || MBEDTLS_PSA_CRYPTO_C`, and
`MBEDTLS_PSA_CRYPTO_C` itself `depends on !BUILD_WITH_TFM`, hence the condition
on the default (`zephyr/Kconfig.alp-libraries:368`
("default y if !BUILD_WITH_TFM")) rather than an unconditional select.

Verified by building each app end to end on this change (arm-none-eabi 13.2 +
picolibc, Zephyr v4.4.1): `mqtt-telemetry` and `iot-fleet-ota` link for
`alp_e1m_aen801_m55_hp/ae822fa0e5597ls0/rtss_hp`, and `mqtt-telemetry`,
`iot-fleet-ota`, `iot-dashboard` and `production-deployment` all build for
`native_sim/native/64` with mbedTLS ON. `mqtt-telemetry` still reaches its
`[mqtt] done` marker when run on `native_sim` with TLS enabled.

Because the workaround is no longer needed, the two `native_sim.conf` files
that existed only to carry it are deleted, `production-deployment`'s keeps just
its littlefs block, `iot-dashboard`'s keeps just its panel wiring, and
`iot-dashboard` now builds MQTT over TLS rather than forcing `MQTT_LIB_TLS=n`.
The `EXTRA_CONF_FILE=native_sim.conf` arguments those two deleted files needed
are gone with them, so the `native_sim` scenarios now build the same
TLS-enabled configuration the SoM does — that is the point of the change, not a
side effect: these apps' whole subject is a TLS transport.

The reason a break this total went unnoticed is that nothing built these apps
for AEN. `iot-fleet-ota`'s AEN scenario named `ensemble_e8_dk/...` — Alif's own
DevKit board, which no `-p` flag in this repo selects — and `mqtt-telemetry`
had no AEN scenario at all. Both now name the target their own `board.yaml`
describes (`examples/connectivity/mqtt-telemetry/testcase.yaml:51`
("alp_e1m_aen801_m55_hp")), and both are added as bounded testsuite roots of
the AEN twister job (`.github/workflows/pr-twister-aen.yml:411`
("alp-sdk/examples/connectivity/mqtt-telemetry")), build_only, so the next regression
in this path fails a PR instead of a bench session.

**Not fixed, and not silently left implicit.** Two things this does not do:

- `iot-dashboard` still does not build for AEN, for an unrelated reason: LVGL
  requires a `zephyr,display` chosen node and no panel is wired for this app on
  the E1M EVK. The EVK solders no panel at all; its documented default is an
  SSD1306 over the I²C/Qwiic header, the app declares an ST7789, and per the
  2626-R2 netlist SPI1 terminates on the on-module CC3501E while every SPI0 pad
  is repurposed (IO-expander reset, amplifier fault/enable, Arduino DIO3/DIO4).
  The one real AEN display path in the tree is the MIPI-DSI chain
  `examples/aen/aen-dsi-display` drives on the M55-HE core. Which panel this
  demo targets is a hardware decision, so it is left open rather than guessed
  at; the app's AEN scenario still names `ensemble_e8_dk/...` and still runs
  nowhere.
- `iot-dashboard`'s AEN scenario is unchanged and still runs nowhere, now said
  so in its own `testcase.yaml` rather than looking like coverage.

### Added — a build that would ship TLS on a predictable RNG is now refused (#2192)

Turning the PSA core on selects `CSPRNG_NEEDED`, and Zephyr satisfies that with
a generator it documents as not random whenever no true entropy driver is
bound. There is no Alif Ensemble entropy driver in this tree or upstream, so
every AEN target was in exactly that state: TLS linked, ran, negotiated, and
derived key material from a predictable source, with a boot-log `WARNING:
Using a test - not safe - entropy source` as the only thing between that and a
shipped product.

A warning does not stop that shipping, so the build refuses it. A new
non-prompt result symbol is y when the PSA core is compiled against
randomness that is not cryptographically secure
(`zephyr/Kconfig.alp-libraries:400` ("config ALP_SDK_MBEDTLS_WEAK_RNG")), and
CMake turns that into a hard failure naming the board and the fix
(`zephyr/CMakeLists.txt:1579` ("CONFIG_ALP_SDK_MBEDTLS_WEAK_RNG AND NOT")).
Kconfig cannot refuse a configuration, hence the CMake half.

The check is `CSPRNG_ENABLED` — Zephyr's own "a true entropy driver is in this
build" signal — plus two terms for the drivers that set `ENTROPY_HAS_DRIVER`
while stating they are not real entropy sources, so `native_sim`'s
`FAKE_ENTROPY_NATIVE_SIM` does not read as a pass.

Acknowledging it is one visible line,
`CONFIG_ALP_SDK_ALLOW_TEST_ENTROPY=y`, and it is legal only where the build
never ships: a twister scenario's `extra_configs`, a `native_sim.conf`, or
`tests/`. It is deliberately **not** in any example's `prj.conf`, because
`tan init --from-example` copies `prj.conf` into a customer's tree and
`testcase.yaml` stays behind — so a scaffolded product built for a real SoM
gets the refusal rather than the acknowledgement. A test enforces that
containment (`tests/scripts/test_weak_rng_optin_is_not_shippable.py:69`
("test_optin_is_only_enabled_where_the_build_never_ships")).

The policy reaches further than TLS, because it asks whether the PSA core is
compiled at all rather than whether a handshake happens. That blast radius was
measured rather than assumed: a configure-only twister sweep of every `tests/`
and `examples/` scenario on `native_sim` (257 configurations) and on the four
AEN targets (167) finds exactly three other builds in the tree that compile the
PSA core with no cryptographically secure random source. Each now says so, in
the place that cannot travel to a customer.

Two are `native_sim`-only ztest suites, where the acknowledgement goes in
`prj.conf` because `tan init --from-example` does not copy anything under
`tests/`: `tests/zephyr/ble_gatt_server/prj.conf:26`
("CONFIG_ALP_SDK_ALLOW_TEST_ENTROPY=y"), where `CONFIG_BT` brings in Zephyr's
own PSA provider (`PSA_CRYPTO_PROVIDER_MBEDTLS` selects
`MBEDTLS_PSA_CRYPTO_C`), and `tests/zephyr/security_mbedtls/prj.conf:34`
("CONFIG_ALP_SDK_ALLOW_TEST_ENTROPY=y"), which exists to exercise the real PSA
AEAD path.

The third is the interesting one. `examples/aen/aen-se-crypto` runs its own
TRNG demo through the Secure Enclave, but that source is not bound as a Zephyr
entropy driver, so the MbedTLS-PSA fall-through the same image builds — for the
algorithms the SE declines — would draw from Zephyr's non-cryptographic
generator. Its `build_only` bench scenario acknowledges that
(`examples/aen/aen-se-crypto/testcase.yaml:29`
("CONFIG_ALP_SDK_ALLOW_TEST_ENTROPY=y")) while the app's `prj.conf` does not,
so someone scaffolding this example for a shipping product still meets the
refusal. It is also the clearest evidence that #2192 has a hardware answer
waiting: exposing that same SE TRNG as an entropy driver would retire this line
here and on every other AEN target.

Verified four ways by hand on this change (arm-none-eabi 13.2 + picolibc,
Zephyr v4.4.1), since twister cannot assert a build failure: `mqtt-telemetry`
for `alp_e1m_aen801_m55_hp` is refused without the opt-in and links with it,
and the same app on `native_sim` is refused without it and builds with it.
The AEN and `native_sim` scenarios therefore carry the opt-in; the apps do
not.

Both halves of the decision are also locked down in CI, evaluated over the
real Kconfig and CMake text rather than restated: a truth table covers the
refuse path (AEN with no entropy driver, `native_sim` behind its fake one)
and the allow path (the same two with the acknowledgement, a target that
binds a real driver, and a TF-M build where the secure partition owns
crypto) — `tests/scripts/test_weak_rng_policy_paths.py:167`
("test_refuse_and_allow_paths_both_decide_correctly").

The real fix stays open silicon work: an entropy driver over the Secure
Enclave TRNG, filed as #2192.

- `ALP_SDK_MBEDTLS_PSA_CRYPTO` is also now scoped to `MBEDTLS_BUILTIN`. The
  break is a property of the mbedtls sources Zephyr vendors; a build selecting
  a custom implementation supplies its own headers and must not inherit
  Zephyr's PSA policy from this SDK.
