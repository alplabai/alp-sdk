### Fixed — `alif_pdm.c`'s per-channel gain (`0x0D`) made E1M-EVK mic captures ~40 dB too quiet, then a corrected `0x800` default clipped (#2143)

A mid-capture register readback during a round 4d silicon session on `e1m-aen-evk-03` found `CH0 GAIN=0x0000000D` -- `PDM_DEFAULT_CH_GAIN` (`zephyr/drivers/audio/alif_pdm.c`, before this fix). `PDM_CH_GAIN`'s `GAIN` field is bits `[11:0]`, unsigned 8.4 fixed-point, reset `0x10` = 1.0x (Alif SVD `AE822FA0E5597BS0_CM55_HP_View.svd`, `PDM_CH_GAIN` register, `GAIN` field, lines ~19081-19092: "Gain in unsigned 8.4 format"; matches the Alif DFP's `PDM_MAX_GAIN_CTRL 0xFFFU`, alif-dfp-ref drivers/include/pdm.h:99, not vendored in this tree) -- so `0x0D` = 0.8125x, confirmed ~40 dB too quiet. That value is Alif's own register-level driver test value (`sdk-alif tests/drivers/pdm/src/alif_test_pdm.h:88-123`, and sdk-alif samples/drivers/audio/dmic_alif/src/main.c:22), never an audio-tuned one.

**Round 4d fixed the default to `0x800` (128x); round 4e's silicon run found that clips.** `alif_kws`'s `AudioBackend.cpp` (`0x00000F00`) was cited as Alif precedent for a 48 kHz default, but its shipped model runs at 16 kHz (`g_AudioRate = 16000`, `generated/kws/kws_micronet_m_vela_H128.tflite.cc:38`), which selects mode 4 (`PDM_MODE_HIGH_QUALITY_1024_CLK_FRQ`), not the 48 kHz mode 7 this driver defaults to -- `0xF00` was never Alif-validated at this rate. The value actually used for the `0x800` default, `mic_listener.c` from the GitHub-hosted `alifsemi/alif_ml-embedded-evaluation-kit` (not vendored locally, so not a `path:NNN` citation), fared no better on silicon: a round 4e run at gain `0x800` (quiet room, no controlled stimulus, `e1m-aen-evk-03`, image built from `7e2535d63`) found `GAIN` read back `0x800` on CH0/1/4/5 as expected, the quiet-window p2p median jumped from 3/3/2/2 (at `0x0D`) to 384/512/384/384, every unclipped sample was a multiple of `0x80` (the gain is a saturating multiply applied AFTER the datapath quantizes, so a coarser gain step adds no resolution -- it only moves the clip point), and the start block plus the first window after each restart pinned at +/-32767 (decimator settling, not signal). Two overruns also occurred during that run, suspected (not proven) to be console load from raw hex-dump printing.

Per an advisory analysis of that data: the estimated pre-gain full scale is roughly 900-1000 LSB, uncalibrated and derived only from the uncontrolled start transient -- hardware gain only moves where clipping starts, it does not add resolution. `0x800` clips a close clap or any start transient at that estimated full scale. Fixed with a **provisional default of `0x200`** (32x, +30.1 dB) -- chosen only as "clearly below the observed clip point", pending a calibrated full-scale measurement; it brackets BLE Audio's voice-tuned `ALIF_BLE_AUDIO_PDM_MICROPHONE_GAIN` Kconfig range (`0x140`-`0x320` in this register's units, `range 1 256` left-shifted by 4). `zephyr/dts/bindings/audio/alif,alif-pdm.yaml`'s `channel-gain` property description carries the full reasoning and cites the SVD directly. `pdm_apply_channel_defaults()` applies `cfg->channel_gain` to every enabled hardware channel instead of the old hardcoded `PDM_DEFAULT_CH_GAIN` constant (`zephyr/drivers/audio/alif_pdm.c:555` ("pdm_set_ch_gain(dev, hw_ch, cfg->channel_gain);")). Phase (`0x1F`) and FIR (`pdm_default_fir_voice512`) are unchanged and match Alif's own audio-capture examples; the IIR coefficient (`0x4`) does too, but whether it filters at all depends on the board's `bypass_iir_filter` DT property -- every current overlay bypasses it. No example overlay sets a non-default `channel-gain`.

**`PDM_INIT`'s `BUILD_ASSERT` range is now `0x001..0xFFF`, the register's own 12-bit hardware range** -- not `0x10..0x1000` as round 4d had it. `0xFFF` (4095) is the largest value the 12-bit `GAIN` field can hold; `0x1000` and above OVERFLOW the field and wrap to 0, which MUTES the channel (round 4d's upper bound was silently invalid). The lower bound is `0x001`: `0x000` is 0.0x, silently indistinguishable from a dead channel, and never a plausible DT value. Re-proved: a temporary `channel-gain = <0x0>;` and, separately, `<0x1000>;` on `examples/aen/aen-pdm-mic-alif`'s board overlay both failed the build with the expected `_Static_assert` message; `<0xFFF>;` built clean. All three overlay edits were then deleted (`git diff` against this change shows no overlay edit).

Mic liveness is **NOT** established by any of this data -- issue #2133's round 4d "clap test" was not attended (nobody clapped), so the bursts it recorded (at the old `0x0D` gain) are unidentified room sound or interference, not proof of acoustic liveness; see `changelog.d/2133.md`'s round 4e finding for the correction. What round 4e's `0x800` silicon run DOES establish: the datapath quantizes before the gain multiply (every unclipped sample a multiple of `0x80`), the start/restart transient reads full-scale, and two overruns occurred (cause unconfirmed). A silicon re-run with the corrected `0x200` default, and a controlled acoustic stimulus, has not been done yet.

New host-testable coverage: none added specifically for the gain-value change itself -- the DT-to-`BUILD_ASSERT` wiring has no pure-function surface to extract (compile-time devicetree validation, proved with the scratch-overlay red/green above, not a runtime decision `tests/unit/alif_pdm_trigger_state`'s pattern would fit), and `pdm_apply_channel_defaults()`'s `cfg->channel_gain` read is a one-line change to an existing, already-covered call site.
