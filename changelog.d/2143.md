### Fixed — `alif_pdm.c`'s per-channel gain (`0x0D`) made E1M-EVK mic captures ~40 dB too quiet (#2143)

A mid-capture register readback during issue #2133 round 4d's attended clap test on `e1m-aen-evk-03` found `CH0 GAIN=0x0000000D` -- `PDM_DEFAULT_CH_GAIN` (`zephyr/drivers/audio/alif_pdm.c`, before this fix). That value traces to Alif's own register-level driver test (`sdk-alif tests/drivers/pdm/src/alif_test_pdm.c`), which exercises the register path, not audio quality -- it was never an audio-tuned value. Alif's own audio-capture applications use a much larger gain for this same class of capture: `alif_kws`'s `AudioBackend.cpp` uses `0x00000F00` (including for 48 kHz mode 7, the mode this driver now defaults to), and the `ml-embedded-evaluation-kit`'s `mic_listener.c` uses `0x00000800`. `subsys/bluetooth/le_audio`'s `ALIF_BLE_AUDIO_PDM_MICROPHONE_GAIN` Kconfig (`range 1 256`, default `20`) left-shifts its value by 4 before writing this same `PDM_CH_GAIN` register. No source available documents the register's bit width or dB scale, so none of these values can be independently verified as "correct" -- but `0x0D` is two orders of magnitude below all three.

Fixed with a new, per-instance, devicetree-configurable `channel-gain` property (`zephyr/dts/bindings/audio/alif,alif-pdm.yaml:71`), defaulting to `0x800` (2048) -- the ML evaluation kit's value, chosen over the KWS sample's larger `0xF00` as the more conservative of the two documented-in-source options. `pdm_apply_channel_defaults()` now applies `cfg->channel_gain` to every enabled hardware channel instead of the old hardcoded `PDM_DEFAULT_CH_GAIN` constant (`zephyr/drivers/audio/alif_pdm.c:506` ("pdm_set_ch_gain(dev, hw_ch, cfg->channel_gain);")). Phase (`0x1F`), FIR (`pdm_default_fir_voice512`), and IIR (bypass) are unchanged -- they already match Alif's own audio-capture examples; only the gain was ever wrong. No example overlay sets a non-default value; the DT default covers the EVK's fitted MP34DT05TR-A mics until a silicon re-run says otherwise.

`PDM_INIT`'s new `BUILD_ASSERT` bounds `channel-gain` to `0x10..0x1000` -- taken from the one place a range IS documented for this register at all, BLE Audio's `ALIF_BLE_AUDIO_PDM_MICROPHONE_GAIN` (`1..256`) shifted left by 4 the same way that subsystem shifts it before writing the register. Proved with a temporary out-of-range (`0x2`) `channel-gain` on `examples/aen/aen-pdm-mic-alif`'s board overlay: the build failed with the expected `_Static_assert` message; the overlay change was then deleted (`git diff` against this change shows no overlay edit). ADR 0017 divergence (9) (`zephyr/drivers/audio/alif_pdm.c`) documents the change alongside issue #2133 round 4d's other two findings.

A silicon re-run with the corrected `0x800` default has not been done yet -- the attended clap test that found the `0x0D` shortfall ran at the OLD gain; this fix is not itself re-verified on hardware.

New host-testable coverage: none added specifically for this fix -- the DT-to-`BUILD_ASSERT` wiring has no pure-function surface to extract (it is compile-time devicetree validation, proved with the scratch-overlay red/green above, not a runtime decision `tests/unit/alif_pdm_trigger_state`'s pattern would fit), and `pdm_apply_channel_defaults()`'s new `cfg->channel_gain` read is a one-line change to an existing, already-covered call site.
