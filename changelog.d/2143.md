### Fixed — `alif_pdm.c`'s per-channel gain (`0x0D`) made E1M-EVK mic captures 31.9 dB quieter than the corrected default; no calibrated default exists yet (#2143)

A mid-capture register readback during a silicon session on E1M-AEN803 serial 2026W36-0002 found `CH0 GAIN=0x0000000D`. On `dev`, `examples/aen/aen-pdm-mic-alif` hardcoded `CH_GAIN 0x0000000D` and called `pdm_set_ch_gain()` directly from app code; this issue moves gain-setting into the driver itself, applied from a new DT `channel-gain` property by `pdm_apply_channel_defaults()` (`zephyr/drivers/audio/alif_pdm.c:608` ("pdm_set_ch_gain(dev, hw_ch, cfg->channel_gain);")). `PDM_CH_GAIN`'s `GAIN` field is bits `[11:0]`, unsigned 8.4 fixed-point, reset `0x10` = 1.0x (Alif SVD `AE822FA0E5597BS0_CM55_HP_View.svd`, `PDM_CH_GAIN` register, `GAIN` field: "Gain in unsigned 8.4 format"; matches the Alif DFP's `PDM_MAX_GAIN_CTRL 0xFFFU`, alif-dfp-ref drivers/include/pdm.h:99, not vendored in this tree) -- so `0x0D` = 0.8125x (-1.8 dB vs unity). That value is Alif's own register-level driver test value (`sdk-alif tests/drivers/pdm/src/alif_test_pdm.h:93` ("CH1_GAIN 0x0000000D"), and `sdk-alif samples/drivers/audio/dmic_alif/src/main.c:22`), never an audio-tuned one, and 31.9 dB below the corrected provisional default (`0x200`) below.

As evidence, a `0x800` (128x) gain run on E1M-AEN803 serial 2026W36-0002 (quiet room, no controlled stimulus) found `GAIN` read back `0x800` on every enabled channel as expected, every unclipped sample a multiple of `0x80` (the gain is a saturating multiply applied AFTER the datapath quantizes, so a coarser gain step moves only the clip point, never resolution), and the start-of-capture block plus the first window after every restart pinned at `+/-32767` (decimator settling reading as clipped, not a calibrated full-scale figure). Fixed with a **provisional default of `0x200`** (32x, +30.1 dB), added as a new DT-configurable `channel-gain` property on the `alif,alif-pdm` binding, default `0x200`, bounds documented and cross-referenced against the register's own hardware range. Full-scale headroom at `0x200` is UNMEASURED, and `0x200` does not bracket a documented "voice-tuned" BLE Audio range either: `ALIF_BLE_AUDIO_PDM_MICROPHONE_GAIN`'s Kconfig (`range 1 256`, left-shifted by 4 before writing this register) carries three DIFFERENT values in the same codebase, none described as tuned for anything -- `0x140` is its Kconfig DEFAULT (20), `0x320` is a DIFFERENT `#ifndef` fallback (50, `sdk-alif subsys/bluetooth/le_audio/audio_source_pdm.c`), and `sdk-alif samples/bluetooth/le_audio/unicast_initiator`'s `prj.conf` ships a THIRD value, 100 (`0x640`).

**`PDM_INIT`'s `BUILD_ASSERT` bounds `channel-gain` to `0x001..PDM_CH_GAIN_MAX`** -- the register's own 12-bit hardware range, not an arbitrary Kconfig-style range (`zephyr/drivers/audio/alif_pdm.c:1736` ("BUILD_ASSERT(DT_INST_PROP_OR(n, channel_gain, 0x200) >= 0x001 && \")): `PDM_CH_GAIN_MAX` (`0xFFF`, 4095) is the largest value the 12-bit `GAIN` field can hold -- a value above it truncates to bits `[11:0]` (`0x1000` exactly truncates to 0, muting the channel); the lower bound is `0x001`, since `0x000` is 0.0x, silently indistinguishable from a dead channel. A runtime write above the bound (from a caller-supplied value, not just DT) is independently clamped through `pdm_ch_gain_clamp()` rather than written unclamped -- see issue #2133's fragment for that fix and its host test. Phase (`0x1F`) and FIR (`pdm_default_fir_voice512`) are unchanged and match Alif's own audio-capture examples; the IIR coefficient (`0x4`) does too, but whether it filters at all depends on the board's `bypass_iir_filter` DT property -- every current overlay bypasses it. No example overlay sets a non-default `channel-gain`.

New host-testable coverage: none added specifically for the gain VALUE change itself -- the DT-to-`BUILD_ASSERT` wiring has no pure-function surface to extract (compile-time devicetree validation); a temporary `channel-gain = <0x0>;` and, separately, `<0x1000>;` on `examples/aen/aen-pdm-mic-alif`'s board overlay both failed the build with the expected `_Static_assert` message, and `<0xFFF>;` built clean -- all three overlay edits were then discarded. `pdm_apply_channel_defaults()`'s `cfg->channel_gain` read is a one-line change to an existing, already-covered call site. The clamp itself (`pdm_ch_gain_clamp()`) IS host-tested -- see issue #2133's fragment.

**Silicon evidence, E1M-AEN803 serial 2026W36-0002.** Mic liveness was NOT established by the `0x0D`/`0x800` data above -- both runs were register-level/quiet-room observations, neither a controlled acoustic test. What the `0x800` run DID establish: the datapath quantizes before the gain multiply, and the start/restart transient reads full-scale (decimator settling, not calibrated headroom evidence). A speaker-to-mic loopback -- the `PROBE_LOOPBACK` mode of `examples/aen/aen-i2s-tas2563-probe` on branch `test/u46-i2s-tas2563-on-reworked-mux` (commit `56631094d`), 2026-09-15 14:49Z -- separately confirms real, frequency-correct audio reaches mic ch0/ch1 (PDM controller 0) at 48 kHz with gain `0x200` (readback-confirmed): the 1 kHz Goertzel bin went from 9.3/0.1 dB in silence to 43.4/48.8 dB at volume 16 and 57.8/57.6 dB at volume 48; peak-to-peak (per channel, 960 ms window, after `zephyr_drv.c`'s `dc_block_s16()` high-pass, hence not a multiple of 32) went from 128/128 in silence to 266/292 at 1 kHz/volume 16 and 651/652 at 1 kHz/volume 48. The D2 pair (HW 4/5) is register-level verified only, never acoustically tested. **What is STILL unmeasured: full-scale headroom at `0x200`** -- the loopback used a fixed speaker level, not a calibration sweep; see issue #2133's fragment for the full loopback account.
