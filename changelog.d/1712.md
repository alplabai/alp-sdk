### Fixed — `--emit scaffold --template multicore-rpmsg` emitted a tree that could not build standalone (#1712)

Materialising the catalog's `multicore-rpmsg` template (`tan init`/`alp_project.py
--emit scaffold --template multicore-rpmsg --sku <SKU>`) produced a project
that failed immediately: `metadata/templates/catalog-v1.json`'s
`files.user_owned` list for the record was missing the project root's own
`CMakeLists.txt` (the multi-slice marker directing a customer at `linux/` and
`m55_hp/`) and `linux/src/main.c` — a file `linux/CMakeLists.txt`'s
`add_executable(rpmsg_aen_consumer src/main.c)` already required. `cmake -S .
-B build` at the scaffold root failed with "does not appear to contain
CMakeLists.txt"; configuring `linux/` past that failed again at
`add_executable` with "Cannot find source file: src/main.c". Both paths are
added to the record now (`board.yaml`, `CMakeLists.txt`, `m55_hp/prj.conf`,
`m55_hp/CMakeLists.txt`, `m55_hp/src/main.c`, `linux/CMakeLists.txt`,
`linux/src/main.c`, `README.md`).

Separately, `examples/multicore/rpmsg-aen/linux/CMakeLists.txt`'s
`ALP_GENERATED_DIR` fallback resolved
`${CMAKE_CURRENT_SOURCE_DIR}/../../build/generated` — two levels up from
`linux/`, landing in the scaffold's *parent* directory, outside the project
entirely, instead of the project root's own `build/generated/` one level up.
Fixed to `../build/generated`; verified by resolving both forms against a
materialised scaffold path.

Reproduced by emitting the template, materialising the JSON envelope to disk,
and running `cmake` against both the project root and `linux/` — see
`tests/scripts/test_alp_project_scaffold_emit.py::
test_scaffold_via_cores_selects_multicore_rpmsg`, whose pre-fix assertion
pinned exactly the missing-file set this fixes.
