### Fixed — CC3501E reply-header gate is now sized by the real expected byte count, not a flat 200 us or the caller's rx_cap (#2107)

The host used to wait a fixed, blind 200 us (`cc3501e_reply_gate(ctx, 200u)`)
before clocking the CC3501E bridge's reply header on every request, regardless
of how much reply data that request expected back or how much request data it
just sent. Two bench findings show 200 us is too short for a large exchange
either direction:

- **Reply side (measured for this fix).** `dispatch_frame` composes a large
  reply (ring copy, a CRC over ~4100 bytes, a ~4100-byte memcpy) inside the
  CC3501E's SPI transfer-complete ISR before it re-arms the reply-header
  phase. A `SOCK_RECV` asking for 512 bytes (`want` = 512, wire reply =
  `sizeof(alp_cc3501e_sock_recv_resp_t)` (24 B) + 512 = 536 B) was clean 3/3 at
  200 us; the SAME op asking for 4071 bytes wedged the link on the very first
  call, 2/2 runs at both 1 MHz and 25 MHz. Widening only that gate to 2000 us
  made the 4071 B `want` succeed 3/3, including a streamed 262144 B download
  with a matching CRC. The want=4071 reply is NOT 24 + 4071 = 4095 B: a bridge
  command handler's writable capacity is the 4100 B frame minus its own 5 B
  header minus the 2 B CRC trailer = 4093 B, so the actual wire reply the
  firmware produced was capped at 4093 B.
- **Request side (inferred, not directly measured for this fix).**
  `dispatch_frame` runs in the SAME ISR the instant the request PAYLOAD phase
  finishes -- it CRCs up to ~4094 request bytes and runs the opcode's handler
  before arming the reply header, so a large REQUEST should pay the same
  composition cost even when its reply is tiny.
  `examples/aen/aen-cc3501e-socket-throughput/README.md` (~159-165) records a
  512 B `STREAM_WRITE` request clean 4/4 at the old flat 200 us gate, while
  1024 B and 4092 B requests both failed `rc=-5`, 3/3 each. No run has
  measured what gate value actually fixes the request side -- this fix's
  `max(expected_reply, wire_tx_len)` is CONSISTENT WITH that failure boundary
  (a 1024+ B request now gets more than 200 us), not proven to close it the
  way the reply-side fix was proven on `SOCK_RECV`.

**The key is not `rx_cap`.** `cc3501e_sock_recv()` always passes
`rx_cap == sizeof(ctx->sock_buf) == ALP_CC3501E_MAX_PAYLOAD` (4096 B)
regardless of the `want` it actually asked the peer for -- rx_cap is a fixed
local staging buffer, and the bridge sizes its reply from the wire request,
not from how big a buffer the host happens to have allocated. An earlier
version of this fix keyed the gate on rx_cap directly, which would have put
every `SOCK_RECV` -- including the 512 B one proven fine at 200 us -- at the
2000 us ceiling, taxing every small read for no reason.

`cc3501e_expected_reply_bytes()` (`chips/cc3501e/cc3501e_core.c`)
reconstructs the real expected reply size per opcode from `(cmd, tx_payload,
tx_len)` instead of trusting rx_cap:

- `SOCK_RECV`: `sizeof(alp_cc3501e_sock_recv_resp_t)` (24 B) + `want` (the
  wire `max_len` field the request actually carries) -- EXCEPT `want == 0`,
  which the bridge treats as "no limit" (it clamps the reply to `max_len`
  only when `max_len != 0`), not "expect nothing back". A caller-supplied
  `cap` of 0 reaches the wire as literally that "no limit" value, so `want ==
  0` falls back to rx_cap instead of computing a tiny 24 B reply.
- `SPI1_TRANSFER`: `sizeof(alp_cc3501e_spi1_transfer_resp_t)` (4 B), plus the
  request's own `len` unless it set `ALP_CC3501E_SPI1_XFER_NO_RX` (reply is
  then the bare 4 B header).
- Every other opcode, `GET_PENDING_EVENTS` included: `rx_cap`, unchanged.

**`GET_PENDING_EVENTS` was NOT special-cased**, though its firmware-side
event ring is a documented fixed 16 entries (288 B worst case) well under
this rx_cap (`sizeof(ctx->evt_buf)`, 4096 B). An earlier version of this fix
keyed it to that 288 B ring so every poll stayed at the 200 us floor; that
case was removed because it depends on a firmware-internal constant
(cc3501e-bridge-firmware `src/event_ring.h`) this driver has no way to verify
stays 16 -- a silent ring-depth change on the firmware side would silently
under-gate this poll again, exactly the class of bug this fix exists to
close. `cc3501e_poll_events()` now pays the full ~2000 us ceiling every call:
measured at roughly 1.8 ms added per poll, about 0.36% additional
transport-lock hold at a realistic 2 polls/s cadence -- accepted as the cost
of not trusting a number this file cannot verify, rather than risking a
silent wedge if the ring ever grows.

`cc3501e_reply_header_gate_us()`'s input is then `max(expected_reply,
wire_tx_len)` -- whichever side of the exchange is larger -- so a large
REQUEST (`STREAM_WRITE`, `OTA_WRITE`, a big `SPI1_TRANSFER` TX, or a large
`SOCK_SEND`/`BLE_GATT_REGISTER`/`BLE_GATT_NOTIFY`/`BLE_GATT_WRITE` payload)
gates just as long as a large reply does -- these are NOT unchanged from the
old 200 us floor when their payload is large; see the table below. The
proven 200 us floor holds at or below 536 B (the measured `SOCK_RECV`
`want`=512 point); the gate grows linearly to the proven 2000 us at
`ALP_CC3501E_MAX_PAYLOAD - ALP_CC3501E_HEADER_BYTES` (4092 B) -- the largest
single-frame byte count any opcode in this driver can ever present in either
direction, 1 byte short of the measured 4093 B ceiling, which only ever hands
out the proven 2000 us slightly sooner, never less delay than a naive
interpolation would. Only those two points (536 B at 200 us, 4093 B at
2000 us) were bench-measured; every byte count strictly between them is
linearly interpolated, not separately measured.

Per-op-class worst-case added latency (vs. the old flat 200 us):

| Class | Bytes | Gate | Added latency |
|---|---|---|---|
| `PING`, `GET_VERSION`/`GET_CAPABILITIES`, `GET_DIAG_INFO`/`DIAG_GET_STATS`, most BLE control, `SOCK_OPEN`/`BIND`/`LISTEN`/`CLOSE`, `GET_MAC`, `WIFI_GET_RSSI`/`GET_IP`/`STATUS`, most `OTA_*` control, `GPIO_CONFIGURE`/`SET_INTERRUPT`, `POWER_POLICY`, camera control | <= 536 B | 200 us | none |
| `SOCK_RECV` with `want` near its 4071 B protocol ceiling or `want == 0` ("no limit"), a near-max `SPI1_TRANSFER`, `GET_PENDING_EVENTS` (rx_cap 4096 B, no longer floored), or a near-max `STREAM_WRITE`/`OTA_WRITE`/`SOCK_SEND`/`BLE_GATT_REGISTER`/`BLE_GATT_NOTIFY`/`BLE_GATT_WRITE` payload | >= 4092 B | 2000 us | +1800 us |
| Anything strictly between | 536-4092 B | interpolated | up to +1800 us |

Two documented, deliberately-unfixed limits remain, both pre-existing and
both left alone rather than special-cased:

- **`BLE_GATT_READ` can be OVER-gated.** `src/backends/ble/cc3501e.c` (~324)
  passes the portable API caller's own `out_cap` straight through as rx_cap,
  and a caller sized generously for "any GATT value" pays the large-reply
  gate even though most real attribute values are a few bytes.
- **A raw `WIFI_SCAN_START`/`BLE_SCAN_START` call with `(NULL, 0)` can be
  UNDER-gated.** rx_cap bounds only how much the driver copies into the
  caller's buffer, not what the firmware actually sends back on the wire --
  a cached scan result can still return a large reply even when the caller
  asked to copy out nothing.

**Caveat.** On `dev` without alp-sdk#2105, a READY pin that reads CONSTANT
HIGH -- a stuck-high pad, not a genuinely wired-and-idle one -- proves itself
on the very first read and then bypasses this fallback gate entirely via the
level-gated READY path. This fix only changes behaviour on the fixed-wait
fallback path (every CS-less r1 board, and any board whose READY pin never
proves itself); it does nothing for a board already misbehaving on the READY
path #2105 addresses.

Does not touch `CC3501E_PHASE_SETTLE_US` (the request-header, request-payload,
and reply-payload phases' own settle) or the READY-line edge-wait path --
both stay exactly as they were; only the reply-header phase's blind-fallback
computation changed.
