### Fixed — CC3501E reply-header gate is now sized by the real expected byte count, not a flat 200 us or the caller's rx_cap (#2107)

The host used to wait a fixed, blind 200 us (`cc3501e_reply_gate(ctx, 200u)`)
before clocking the CC3501E bridge's reply header on every request, regardless
of how much reply data that request expected back or how much request data it
just sent. Two independent bench findings show 200 us is too short for a large
exchange either direction:

- **Reply side.** `dispatch_frame` composes a large reply (ring copy, a CRC
  over ~4100 bytes, a ~4100-byte memcpy) inside the CC3501E's SPI
  transfer-complete ISR before it re-arms the reply-header phase. A `SOCK_RECV`
  asking for 512 bytes (`want` = 512, wire reply = `sizeof(alp_cc3501e_sock_recv_resp_t)`
  (24 B) + 512 = 536 B) was clean 3/3 at 200 us; the SAME op asking for 4071
  bytes (reply 4095 B) wedged the link on the very first call, 2/2 runs at both
  1 MHz and 25 MHz. Widening only that gate to 2000 us made the 4071 B `want`
  succeed 3/3, including a streamed 262144 B download with a matching CRC.
- **Request side.** `dispatch_frame` runs in the SAME ISR the instant the
  request PAYLOAD phase finishes -- it CRCs up to ~4094 request bytes and runs
  the opcode's handler before arming the reply header, so a large REQUEST pays
  the same composition cost even when its reply is tiny. `examples/aen/aen-cc3501e-socket-throughput/README.md`
  (~159-165) already documents this independently: a 512 B `STREAM_WRITE`
  request was clean 4/4 at the old flat 200 us gate, while 1024 B and 4092 B
  requests both failed `rc=-5`, 3/3 each, and the link did not recover for the
  rest of that run.

**The key is not `rx_cap`.** `cc3501e_sock_recv()` always passes
`rx_cap == sizeof(ctx->sock_buf) == ALP_CC3501E_MAX_PAYLOAD` (4096 B)
regardless of the `want` it actually asked the peer for -- rx_cap is a fixed
local staging buffer, and the bridge sizes its reply from the wire request,
not from how big a buffer the host happens to have allocated. An earlier
version of this fix keyed the gate on rx_cap directly, which would have put
every `SOCK_RECV` -- including the 512 B one proven fine at 200 us -- at the
2000 us ceiling, taxing every small read for no reason.

`cc3501e_expected_reply_bytes()` (`chips/cc3501e/cc3501e_core.c`)
reconstructs the real expected reply size per opcode from `(cmd, tx_payload,
tx_len)` instead of trusting rx_cap:

- `SOCK_RECV`: `sizeof(alp_cc3501e_sock_recv_resp_t)` (24 B) + `want`
  (the wire `max_len` field the request actually carries).
- `SPI1_TRANSFER`: `sizeof(alp_cc3501e_spi1_transfer_resp_t)` (4 B), plus the
  request's own `len` unless it set `ALP_CC3501E_SPI1_XFER_NO_RX` (reply is
  then the bare 4 B header).
- `GET_PENDING_EVENTS`: a fixed 288 B (the firmware's real 16-entry event ring
  ceiling, `ALP_CC3501E_EVENT_HDR_BYTES` + `ALP_CC3501E_EVENT_PAYLOAD_MAX` per
  entry), NOT the oversized `evt_buf` rx_cap (4096 B) -- this op stays at the
  200 us floor.
- Every other opcode: `rx_cap`, unchanged and already a tight bound for the
  many small, fixed-shape replies (`GET_VERSION`, `GET_DIAG_INFO`, the
  BLE/GPIO/power control acks, ...).

`cc3501e_reply_header_gate_us()`'s input is then `max(expected_reply,
wire_tx_len)` -- whichever side of the exchange is larger -- so a large
REQUEST (`STREAM_WRITE`, `OTA_WRITE`, a big `SPI1_TRANSFER` TX) gates just as
long as a large reply does. The proven 200 us floor holds at or below 536 B
(the measured `SOCK_RECV` `want`=512 point); the gate grows linearly to the
proven 2000 us at `ALP_CC3501E_MAX_PAYLOAD - ALP_CC3501E_HEADER_BYTES` (4092
B) -- the largest single-frame byte count any opcode in this driver can ever
present in either direction, 3 bytes short of the measured 4095 B ceiling,
which only ever hands out the proven 2000 us slightly sooner, never less delay
than a naive interpolation would. Only those two points (536 B at 200 us,
4095 B at 2000 us) were bench-measured; every byte count strictly between them
is linearly interpolated, not separately measured.

Per-op-class worst-case added latency (vs. the old flat 200 us):

| Class | Bytes | Gate | Added latency |
|---|---|---|---|
| `PING`, `GET_VERSION`/`GET_CAPABILITIES`, `GET_DIAG_INFO`/`DIAG_GET_STATS`, BLE control + `GATT_REGISTER`, `SOCK_OPEN`/`BIND`/`LISTEN`/`SEND`/`CLOSE`, `GET_MAC`, `WIFI_GET_RSSI`/`GET_IP`/`STATUS`, all `OTA_*` control, `GPIO_CONFIGURE`/`SET_INTERRUPT`, `POWER_POLICY`, camera control, `GET_PENDING_EVENTS` (288 B ring, not its 4096 B rx_cap) | <= 536 B | 200 us | none |
| `SOCK_RECV` with `want` near its 4071 B protocol ceiling, a near-max `SPI1_TRANSFER`, or a near-max `STREAM_WRITE`/`OTA_WRITE` request | >= 4092 B | 2000 us | +1800 us |
| Anything strictly between | 536-4092 B | interpolated | up to +1800 us |

`BLE_SCAN_START` and `WIFI_SCAN_START` still key off rx_cap (their reply size
genuinely varies with how many APs/peripherals are visible, unlike
`GET_PENDING_EVENTS`'s fixed ring), so they still see the large-reply gate at
their full 4096 B scratch-buffer capacity -- unchanged from an rx_cap-keyed
design, and conservative for the same reason PING's rx_cap-keyed default is.

**Caveat.** On `dev` without alp-sdk#2105, a READY pin that reads CONSTANT
HIGH -- a stuck-high pad, not a genuinely wired-and-idle one -- proves itself
on the very first read and then bypasses this fallback gate entirely via the
level-gated READY path. This fix only changes behaviour on the fixed-wait
fallback path (every CS-less r1 board, and any board whose READY pin never
proves itself); it does nothing for a board already misbehaving on the READY
path #2105 addresses.

Does not touch `CC3501E_PHASE_SETTLE_US` (the request-header, request-payload,
and reply-payload phases' own settle) or the READY-line edge-wait path --
both stay exactly as they were; only the reply-header phase's blind-fallback
computation changed.
