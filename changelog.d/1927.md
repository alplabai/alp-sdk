### Changed — the CC3501E wire protocol is versioned MAJOR.MINOR, and features are discovered by capability (#1927)

The wire protocol went **v5 to v9 in a single week**, and every bump forced a
lockstep reflash of both halves, because the host refused the link on any
mismatch. Sorted by the only question that matters — would an *unchanged host*
be **misread**? — only two of those four bumps qualify:

| Bump | Change | Old host misread? |
|---|---|---|
| v6 | SPI1 passthrough opcodes `0x55`..`0x57` | No — additive |
| v7 | `alp_cc3501e_sock_send_t::reserved` → retry seq | **Yes** |
| v8 | frame-header flags bits 3..7 → retry seq | **Yes** |
| v9 | `SOCK_BIND`/`SOCK_LISTEN`/`EVT_SOCK_ACCEPTED` | No — additive |

Two real breaks presented as four. The cause was one integer doing two jobs — a
compatibility gate *and* a feature marker — tested with exact equality, so the
feature half kept firing the gate half.

Per **ADR 0033**:

- `ALP_CC3501E_PROTOCOL_MAJOR` / `ALP_CC3501E_PROTOCOL_MINOR` replace the flat
  integer. `CMD_GET_VERSION` carries `(MAJOR << 8) | MINOR` in the same 2-byte LE
  reply. Retroactively v5=`1.0`, v6=`1.1`, v7=`2.0`, v8=`3.0`, v9=`3.1` — and the
  current wire `3.1` is **byte-identical** to what shipped as "v9".
- `cc3501e_reset()` refuses on **MAJOR only**
  (`chips/cc3501e/cc3501e_core.c:251` (`if (fw_major != (uint8_t)ALP_CC3501E_PROTOCOL_MAJOR)`)).
  A differing MINOR now connects, which is safe *because* MINOR is defined as
  additive: the host never sends an opcode it does not know, and the firmware
  never emits an event nobody armed.
- `MAJOR 0` is reserved, so a firmware predating the scheme — answering with its
  raw v1..v9 integer — stays distinguishable from one that disagrees about frame
  layout. `cc3501e_t::fw_proto_major` / `::fw_proto_minor` are recorded on both
  the accept and the refuse path.
- New `CMD_GET_CAPABILITIES` (`0x06`) and `cc3501e_get_capabilities()` report
  which opcode families a **build** implements, composed from the same
  compile-time switches that decide which HAL bodies link. That is something a
  version number cannot express: a build without Wi-Fi still carries every socket
  opcode and answers `NOTIMPL` to all of them.
- `alp companion ver` now leads with the release version — `fw 0.6.0 (wire 3.1)`.
  That line is how the raw wire integer leaked into customer-facing threads.
- `scripts/check_protocol_version_policy.py` fails a MAJOR bump with no justified
  row in ADR 0033's machine-readable ledger. The failure it prevents is social:
  a MAJOR bump is never technically *wrong*, costs the person shipping it
  nothing, and spends a customer's reflash.

**Breaking:** this is one final bump by construction — a v9 host and a `3.1`
firmware do not interoperate even though their frames are identical. Taken now,
at one customer on the protocol, rather than later at ten.

It also repaired two gates that would have gone quietly green: the firmware
repo's "protocol version parity" job greps for digits after
`ALP_CC3501E_PROTOCOL_VERSION`, which now matches nothing (the macro is a
composed expression) and would have compared empty to empty; and this repo's own
version-mismatch test used `PROTOCOL_VERSION + 1`, which under the composed
encoding only bumps MINOR — an accepted case — so it would have kept passing
while testing nothing.

Paired firmware change: `cc3501e-bridge-firmware` (`protocol-version.txt` → `3.1`,
`CMD_GET_CAPABILITIES` handler, honest stub-build bitmap via a new
`CC3501E_HAL_STUB` define).
