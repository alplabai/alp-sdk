### Fixed — `rv3028c7_dispatch_irq()` could silently swallow a one-shot RTC event that fired mid-dispatch (#1623)

`rv3028c7_dispatch_irq()` read `STATUS`, ran the registered handlers, then wrote
`STATUS = 0x00` unconditionally to acknowledge -- clearing every write-0-to-clear
flag, including any one-shot source (`RV3028C7_SRC_ALARM`, `RV3028C7_SRC_EXT_EVENT`,
`RV3028C7_SRC_BSF`) that latched during the handlers' own I2C work. A one-shot
source has no "next event" to re-latch it, so the flag -- and its handler
invocation -- was lost with no error returned and no trace in `status_seen`.

The acknowledge is now a write-0x00-then-re-read step
(`rv3028_status_ack()`, `chips/rv3028c7/rv3028c7.c`) shared by
`rv3028c7_init()`, `rv3028c7_alarm_check_and_clear()` and
`rv3028c7_dispatch_irq()`: a bit that races the acknowledge comes back on the
re-read instead of being silently dropped. `rv3028c7_dispatch_irq()` loops
(bounded to 3 passes) re-dispatching anything that races its own acknowledge;
`rv3028c7_alarm_check_and_clear()` folds a raced `AF` into `*fired` without
looping -- a raced bit it can't fully drain self-heals on the next call
instead of being lost.

This intentionally does **not** assume anything about what writing a `1` to a
`STATUS` bit that reads `0` does on real silicon (no cited RV-3028-C7
Application Manual table settles that); it relies only on the driver's
existing "write 0 clears" contract. An earlier version of this fix wrote back
`~status & 0x7F` (setting unobserved bits to `1` to "preserve" them), which
would have needed that unverified fact to actually be correct -- replaced
before merge.

Regression test: `tests/unit/rv3028c7_dispatch_ack/`. It links the real
`chips/rv3028c7/rv3028c7.c` against a small in-TU fake I2C register file
(the driver's only bus dependency is `alp_i2c_write()` /
`alp_i2c_write_read()`) so it exercises the actual dispatch/ack code path,
including the exact race from this issue.
