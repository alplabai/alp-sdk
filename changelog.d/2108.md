### Changed — CC3501E `SOCK_RECV` gets its own request-seq counter, ahead of a pending firmware fix (#2108)

Bench evidence: one run downloaded 262144 B over 4071 B `cc3501e_sock_recv()`
calls, every call returned `ALP_OK`, and exactly one 4069 B block never
arrived -- a GAP, not a duplicate -- sitting exactly on a reply boundary.
Root cause: the bridge firmware commits its receive-ring advance EAGERLY,
before the host has actually received anything, so a reply that then fails
CRC on the wire has already consumed that chunk firmware-side. Today's
firmware cannot tell a retry of that exact request apart from a brand-new
one, so `poll_by_repeat()`'s identical re-issue gets answered with the NEXT
chunk instead of the lost one.

The real fix is firmware-side and is **not yet merged**
(`cc3501e-bridge-firmware`, branch `fix/sock-recv-retry-safe`): the ring
advance becomes lazy, keyed on (header seq, socket handle) recorded on every
`SOCK_RECV` dispatch -- a request whose seq and handle match the immediately
preceding dispatch is a replay, the ring does not advance again; any other
request commits and serves the next chunk. That mechanism only works if the
key it reads is unambiguous.

This change is the host-side groundwork for that key: `cc3501e_sock_recv()`
now allocates its wire-header retry seq (proto v8, 5 bits, 1..31) from its
own dedicated `ctx->sock_recv_seq`, not the shared `ctx->req_seq` every other
worker-routed opcode also draws from. One counter per ctx, shared across
every socket handle, is enough -- the firmware records its key on every
`SOCK_RECV` dispatch regardless of handle and compares only against the
single most recent entry, never against history, so two recvs that are
adjacent in the `SOCK_RECV` stream can never carry the same seq regardless of
which handles they're on. Drawing from the shared `req_seq` instead would not
have that property: unrelated opcode traffic can land between two recvs
without ever touching a dedicated counter, so two recvs that are adjacent in
the firmware's `SOCK_RECV`-only view could still end up exactly 30 unrelated
commands apart in `req_seq`'s cycle and numerically identical -- exactly the
bench failure above.

`cc3501e_sock_recv()` also only commits its candidate seq into
`ctx->sock_recv_seq` once its own call reaches `ALP_OK` with the reply fully
decoded -- never after `ALP_ERR_TIMEOUT`, `ALP_ERR_IO`, or a short header. A
caller whose call fails keeps the SAME candidate on its next attempt, so once
`fix/sock-recv-retry-safe` ships, an immediate retry of the SAME handle will
recover the chunk that call's lost or corrupted reply already committed,
instead of the bridge treating the retry as a new request and skipping past
it. Recovery holds only for an immediate retry of the same handle: a
different handle called first also gets that same candidate, but with its
own handle, so it correctly starts fresh rather than colliding with the
failed call's entry -- and once that different-handle call commits, the
original handle's next retry gets a genuinely new seq and can no longer
recover the original lost chunk.

`poll_by_repeat()`'s retry loop is unchanged in behaviour; its body moved to
a new `poll_by_repeat_seq()` that takes the seq as an explicit parameter,
letting `SOCK_RECV` supply its own while every other caller still goes
through `poll_by_repeat()`, which allocates from `ctx->req_seq` exactly as
before.

Harmless against firmware without the pending replay logic: it ignores the
seq bits for `SOCK_RECV` exactly as it already does for every opcode that
never checks them.
