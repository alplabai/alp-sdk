### Documentation — refresh remaining stale CC3501E bridge firmware claims (#2141)

`docs/cc3501e-bridge.md`'s Versioning section still named SemVer 0.4.0 / wire
protocol 5 / stamp `0.4.0.0` as the current release, and only distinguished
two firmware states (merged vs. shipped). There are three: nine fixes merged
to `cc3501e-bridge-firmware:main`; **v0.9.0** (firmware PR #151), cut
carrying all nine but not yet bench-verified or published; and **v0.8.0**
(wire protocol 4.0, GPE `0.254.5.0`, `prebuilt/cc3501e-v0.8.0.bin`), what
`prebuilt/` actually publishes today and what every bench unit still runs,
carrying none of them. The doc now says so plainly.

`include/alp/chips/cc3501e/sockets.h`'s `cc3501e_sock_recv()` doc described a
zero-length result as always ambiguous ("no data, or the peer closed —
poll again"). That is only true against v0.8.0;
`cc3501e-bridge-firmware#140` (merged to `main`, cut into the unreleased
v0.9.0) makes EOF sticky on the worker path, so a zero-length result against
a `#140` bridge is unambiguous. The doc now covers both. `aen-cc3501e-
socket-throughput`'s `SOCKTP_ZERO_STREAK_DONE` host-side workaround for the
ambiguity stays in the code — v0.8.0 still needs it — with its comment
updated to say so and to note it is bench-validated 5 of 5 against a `#140`
build too, so it is correct against both firmware generations.

Most of the audit's other stale-claim candidates (the connect-budget/DHCP
family across the console and every `aen-cc3501e-*` example, the
"not-yet-merged" framing in `chips/cc3501e/cc3501e_sockets.c`) turned out to
already be correct on `dev`, fixed by #2111/#2113/#2115 — left untouched.
