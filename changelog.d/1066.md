### Fixed — a swapped AEN board would have re-swapped forever: MCUboot's scratch magic is never cleared on a 0x00-erase MRAM (#1066)

`boot_swap_image()` hands `copy_size` to MCUboot's scratch-algorithm
`swap_run()` unconditionally. `copy_size == 0` makes `find_last_sector_idx()`
return `-1`, so `swap_run()`'s loop body — the only call site of
`boot_swap_sectors()`, where the scratch-trailer erase lives — never runs.
On a flash device whose reported erase value is `0x00` (Alif Ensemble
on-die MRAM, `FLASH_MRAM_ERASE_VALUE` in
`zephyr/drivers/flash/flash_mram_alif.c`), that erase value is
bit-for-bit identical to a genuine `swap_size` of `0`. `boot_read_swap_size()`
is a raw, unchecked read, so a stale trailer field reads back as
`copy_size == 0` while the scratch magic still reads `GOOD`, and
`boot_status_source()` keeps selecting `BOOT_STATUS_SOURCE_SCRATCH` on
every following boot — the board resumes the same no-op swap forever,
never moving a byte and never clearing the magic that put it there.
Confirmed on real silicon (E1M-AEN801) 2026-07-31, source-level root cause
pinned by reading the vendored MCUboot directly.

Carried as `zephyr/patches/mcuboot/0002-loader-clear-scratch-trailer-on-degenerate-copy-size-zero.patch`
(registered in `zephyr/patches.yml`): guard `copy_size == 0` at the
`boot_swap_image()` call site and clear the scratch trailer directly
instead of resuming. No-op for the ordinary case (a real
swap-in-progress trailer never carries `copy_size == 0`); scoped to
`MCUBOOT_SWAP_USING_SCRATCH`, so move/offset-strategy builds are
unaffected. Verified to apply cleanly, forward and reverse, against the
pinned upstream `mcuboot` revision (Zephyr v4.4.1's pin,
`6d3b3d2c38ab20c242e5b9abb04d050086383eb2`), and to stack cleanly on top
of the existing `0001-flash_map_extended-alif-mram-base.patch`.

**Not bench-verified**, and it cannot be from this tree today: #1100 and
#1445 removed the AEN family's scratch/slot1 partitions to fit the
disjoint dual-core slot0 budget, so no AEN board target currently builds
the scratch-swap path this patches. This closes the underlying defect
ahead of a secondary slot being reintroduced, so the swap-path work does
not have to be redone from scratch before OTA can be re-enabled — see the
amended note in `docs/adr/0006-secure-boot-secure-ota.md`.
