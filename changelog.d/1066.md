### Fixed — MCUboot could read an ambiguous swap_size of 0 off a 0x00-erase MRAM trailer and either loop forever or crash (#1066)

The self-perpetuating re-swap this issue reported — a completed swap that
never clears its scratch magic and so keeps resuming forever — was
**confirmed on real silicon** (E1M-AEN801, 2026-07-31). The mechanism
behind it was pinned down by reading the vendored MCUboot source, and is
**not itself measured on silicon**: `boot_read_swap_size()`
(`bootutil_misc.c`) is a raw, unchecked `flash_area_read()`. On a flash
device whose reported erase value is `0x00` (Alif Ensemble on-die MRAM,
`FLASH_MRAM_ERASE_VALUE` in `zephyr/drivers/flash/flash_mram_alif.c`),
that erase value is bit-for-bit identical to a genuine `swap_size` of
`0` — unlike the obviously-invalid `0xffffffff` a 0xFF-erase device would
read back for the same not-really-written field. A stale or torn-written
`swap_size` then reads back as `0` instead of as clearly erased, and both
of the function's callers degenerate silently: `swap_run()`'s scratch
algorithm (`swap_scratch.c`) never clears the scratch trailer, so a
swapped board resumes the same no-op swap forever; `find_swap_count()`
(the same file, a second, earlier call site not covered by an initial
draft of this fix) returns `0` too, and `boot_read_image_header()`
substitutes the **wrong slot's** header for the one requested.

Fixed at the shared choke point: `boot_read_swap_size()` now treats an
erased-value `swap_size` as a read failure (`BOOT_EBADSTATUS`, via the
same `bootutil_buffer_is_erased()` helper `boot_read_flag()` already uses
for `image_ok`/`copy_done`) instead of handing out a meaningless `0`.
Both callers already fail safely on that with no further change —
`loader.c`'s existing `assert(rc == 0)` propagates up to
`boot_read_image_headers()` failing, which declines the swap outright
(primary slot left untouched) rather than proceeding on a `0`;
`swap_scratch.c` already turns any nonzero return here into `BOOT_EFLASH`
before it can substitute the wrong slot. **An earlier version of this fix
guarded `copy_size == 0` at the `loader.c` call site alone and
force-cleared the scratch trailer there directly — this was caught on
review and replaced**: that guard could destroy an in-flight swap's only
surviving copy of a sector and then report success, converting a
harmless reboot loop into a bootloader that signs off on a corrupted
image, and it left the `find_swap_count()` call site unguarded. Carried
as `zephyr/patches/mcuboot/0002-bootutil_misc-reject-erased-swap_size-trailer.patch`,
touching no flash on the failure path.

**Regression-verified on the mcuboot host simulator** (`sim/`, cargo + a
C compiler, no embedded toolchain needed) — `zephyr/patches/mcuboot/0003-sim-swap-size-erased-collision-regression-test.patch`
adds a case that force-writes an interrupted, genuinely in-progress
swap's `swap_size` field to the device's erase value and asserts the
primary slot is never left stamped complete over a corrupted image.
Against the pinned upstream revision
(`6d3b3d2c38ab20c242e5b9abb04d050086383eb2`): pre-fix, this scenario
**segfaults** inside `boot_read_image_header()`'s wrong-slot
substitution — a worse failure mode than the reboot loop originally
measured; post-fix, all 26 simulator cases pass (25 pre-existing plus
this one), across every device/alignment/`erased_val` (`0x00` and
`0xff`) combination the harness sweeps. Both patches verified to apply
cleanly forward and reverse, and to stack disjointly on top of the
existing `0001-flash_map_extended-alif-mram-base.patch`, using this
repo's own `scripts/verify_west_patches.py` against a freshly-applied
checkout.

**Not bench-verified on AEN silicon, and cannot be from this tree
today**: #1100 and #1445 removed the AEN family's scratch/slot1
partitions to fit the disjoint dual-core slot0 budget, so no AEN board
target currently builds the scratch-swap path this patches. This closes
the mechanism ahead of a secondary slot being reintroduced, so the
swap-path work does not have to be redone from scratch before OTA can be
re-enabled — see the amended note in
`docs/adr/0006-secure-boot-secure-ota.md`. It does **not** close #1066's
second finding (a clean, valid PERM upgrade request that produced no
swap at all), which was never root-caused and still gates the
revert-on-bad-image security claim.
