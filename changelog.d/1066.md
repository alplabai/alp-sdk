### Fixed — MCUboot's scratch-swap trailer could survive a completed swap forever on a no-explicit-erase device, plus a separate ambiguous-swap_size crash (#1066)

The self-perpetuating re-swap this issue reported — a completed swap that
never clears its scratch magic and so keeps resuming forever — was
**confirmed on real silicon** (E1M-AEN801, 2026-07-31). Two independent
bootutil defects were found while root-causing it, and both are fixed
here; only one of them is the actual re-swap mechanism.

**The real re-swap mechanism, now fixed:** `swap_scratch.c`'s
`boot_swap_sectors()` writes a full temporary trailer — magic included —
to the scratch area while the primary slot's own trailer is rebuilt. The
comment right after it, *"Erase the temporary trailer from the scratch
area"*, is meant to remove that magic once it is no longer needed, but on
a flash device that does not require an explicit erase before rewrite
(Alif Ensemble on-die MRAM), that call is a **documented no-op**:
`boot_erase_region()` (`bootutil_area.c`) takes its
`device_requires_erase(fa) == false` branch, logs `"device without
erase"`, and returns success without touching flash. The GOOD magic
survives, and on the next boot `boot_status_tables[]`'s scratch-source
entry matches on that magic alone — regardless of the primary slot's own
`image_ok` — resuming the same completed swap forever. A second,
independent bug compounds this class of fix: `boot_scramble_region()`'s
backwards branch never wrote the block at its own range boundary (an
off-by-one in the loop guard), which for a trailer-scoped scramble is the
trailer's first status entry. Both are fixed in
`zephyr/patches/mcuboot/0004-scramble-scratch-trailer-and-backward-scramble-off-by-one.patch`:
the no-op erase is replaced with a trailer-scoped scramble (not a
whole-area one, to avoid an unnecessary MRAM endurance cost), and the
backwards loop is split so it writes its boundary block.

**`0002`'s own contribution is a separate, real, reproduced defect on
the `find_swap_count()` path — not the re-swap mechanism above.**
`swap_status_init()` (`swap_misc.c`) writes `swap_size` before magic
within the same call, so a GOOD scratch magic implies a
genuinely-written, nonzero `swap_size`; the re-swap mechanism above
never involves an erased `swap_size` field. `0002` closes a different,
narrower crash: `swap_size == 0`
also feeds `find_swap_count()` (`swap_scratch.c`), which
`boot_read_image_header()` uses to decide whether to substitute a
different slot's header — an ambiguous `0` there makes it substitute the
**wrong slot's** header, and the unpatched read segfaults inside that
substitution on the mcuboot host simulator. Fixed at the shared choke
point: `boot_read_swap_size()` now treats an erased-value `swap_size` as
a read failure (`BOOT_EBADSTATUS`, via the same `bootutil_buffer_is_erased()`
helper `boot_read_flag()` already uses for `image_ok`/`copy_done`) instead
of handing out a meaningless `0`. Both callers already fail safely on
that with no further change — `loader.c`'s existing `assert(rc == 0)`
propagates up to `boot_read_image_headers()` failing, which declines the
swap outright (primary slot left untouched) rather than proceeding on a
`0`; `swap_scratch.c` already turns any nonzero return here into
`BOOT_EFLASH` before it can substitute the wrong slot. **An earlier
version of this fix guarded `copy_size == 0` at the `loader.c` call site
alone and force-cleared the scratch trailer there directly — this was
caught on review and replaced**: that guard could destroy an in-flight
swap's only surviving copy of a sector and then report success,
converting a harmless reboot loop into a bootloader that signs off on a
corrupted image, and it left the `find_swap_count()` call site unguarded.
Carried as
`zephyr/patches/mcuboot/0002-bootutil_misc-reject-erased-swap_size-trailer.patch`,
touching no flash on the failure path.

**Regression-verified on the mcuboot host simulator** (`sim/`, cargo + a
C compiler, no embedded toolchain needed), against the pinned upstream
revision `6d3b3d2c38ab20c242e5b9abb04d050086383eb2`:

- `0003-sim-swap-size-erased-collision-regression-test.patch` (companion
  to `0002`) force-writes an interrupted, genuinely in-progress swap's
  `swap_size` field to the device's erase value and asserts the primary
  slot is never left stamped complete over a corrupted image. Pre-`0002`,
  this **segfaults** inside `boot_read_image_header()`'s wrong-slot
  substitution.
- `0005-sim-scratch-trailer-no-erase-device-regression-test.patch`
  (companion to `0004`, covering BOTH of its fixes) adds two tests.
  `scratch_trailer_cleared_after_swap` runs a real, uninterrupted,
  permanent upgrade to completion on a device that does not require an
  explicit erase, and asserts the scratch area's temporary trailer never
  reads back a GOOD magic afterwards — this covers fix (i). Pre-`0004`,
  it **fails on the very first device/align/erased_val combination it
  tries**. Getting there needed a small maker of its own
  (`ImagesBuilder::make_image_undersized()`): every existing maker fills
  its slot to capacity by design, which keeps the swap on the
  `bs->use_scratch == true` path `0004`'s fix (i) does not touch, so the
  no-op-erase mechanism was unreachable by ANY existing sim test — not
  just an untested one. `scramble_region_backwards_boundary` calls
  `boot_scramble_region()`'s backwards branch directly instead, over an
  arbitrary sub-range of the scratch area, and asserts the write-block
  boundary at the low end of that range was written and nothing below it
  was touched — this covers fix (ii), which the first test's own
  end-to-end shape (every real caller's off/size sums to the flash
  area's own size) cannot distinguish from a no-op: with fix (i) applied
  but fix (ii)'s `bootutil_area.c` hunk alone reverted, **27 passed and
  only the new direct test failed**.

Post-`0004`+`0005`: `cargo test --release --test core` — **28 passed, 0
failed** (26 pre-existing cases plus these two), across every
device/alignment/`erased_val` (`0x00` and `0xff`) combination the harness
sweeps. All five patches verified to apply cleanly, in order, on the
pinned upstream revision.

**Not bench-verified on AEN silicon, and cannot be from this tree
today**: #1100 and #1445 removed the AEN family's scratch/slot1
partitions to fit the disjoint dual-core slot0 budget, so no AEN board
target currently builds the scratch-swap path either fix touches. This
closes the mechanism ahead of a secondary slot being reintroduced, so the
swap-path work does not have to be redone from scratch before OTA can be
re-enabled. It does **not** close #1066's second finding (a clean, valid
PERM upgrade request that produced no swap at all), which was never
root-caused and still gates the revert-on-bad-image security claim. That
finding's own trace runs through a stale non-`0x00` primary status byte
surviving into the next boot, not the scratch-magic mechanism `0004`
fixes; `0004`'s off-by-one fix (ii) plausibly removes that stale byte's
source, but that link is a **hypothesis, not proven here**.
