### Fixed — scope the OSPI0 NOR's identity, population, and chip-select claims to the SKU each is actually true for (#2062)

The true count, from `git grep -n 'R2 BOM'`, `git grep -n MX25UM25645`, and
`git grep -n W958D8NB` against `origin/dev` before this fix (the "Five
sites" in an earlier draft of this fragment and in commit `332c8a4b2` was a
written-list undercount, not a grepped one): **fifteen distinct sites across
thirteen files** stated in the present tense that the E1M-AEN OSPI0 NOR is a
Macronix `MX25UM25645GXDI00` populated (`DNP = 0`) on "the R2 BOM," that its
HyperRAM sibling is a Winbond `W958D8NBYA5I`, or both. Measured contradiction
(issue #2041): on `E1M-AEN803` serial `2026W36-0002`, Flow C ITCM RAM-run,
the NOR answered a JEDEC ID read on OSPI0 **CS1** with `9d 5b 19 10` at
`BAUDR=20` (20 MHz), repeated on the alternate ISSI ReadID opcode `0x9E`.
`0x9d` is the ISSI manufacturer ID; `5b 19` is the `IS25WX256` type/capacity
pair -- matching `metadata/e1m_modules/E1M-AEN803.yaml:59-72`'s
`IS25WX256-JHLE` NOR and `:75-94`'s `S80KS5122GABHM02` (Infineon/Cypress)
HyperRAM. Macronix's manufacturer ID is `0xc2`.

Three separate errors were mixed into these sites and are corrected
independently:

1. **Part identity.** Macronix `MX25UM25645GXDI00` -> measured ISSI
   `IS25WX256-JHLE`; Winbond `W958D8NBYA5I` -> measured
   `S80KS5122GABHM02` (Infineon/Cypress) -- cited to #2041, everywhere the
   claim named a SKU/footprint that actually populates OSPI0.
2. **Population.** `metadata/e1m_modules/E1M-AEN801.yaml:60-88` declares
   *both* external memories `assembled: false` (`memory.dram_mbit: 0`,
   `memory.flash_mbit: 0` at `:155-156`) -- E1M-AEN801 runs from the SoC's
   on-die MRAM and populates neither device on any revision as this repo
   models it. "The R2 BOM populates only OSPI0" is false for that SKU;
   every corrected site now says which SKU (E1M-AEN803) the claim is
   actually true for.
3. **Chip select.** Several sites placed the NOR on CS0. The netlist puts
   `U10` (NOR) on `OSPI0_SS1` and `U9` (HyperRAM) on `OSPI0_SS0`; metadata
   was corrected to match in `44200cab` (#1944, #1990, PR #2007); #2041
   confirmed it by distinguishing three `ser` values -- `0x00000002` (CS1)
   drains `9d 5b 19 10`, `0x00000001` (CS0) drains `00 00 00 00`,
   `0x00000000` drains 0/4 with `SR = 0x00000002`.
