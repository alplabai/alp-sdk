### Fixed — `uhc_xhci_alif` implements the full UHC API instead of a skeleton (#388)

The driver self-identified as a "SKELETON" with 16 `TODO(aen401-bench)`
markers, and `examples/peripheral-io/usb-host-storage/README.md` called it a
"compile-only skeleton" — accurate at the time, but issue #388's later triage
comments found register bring-up (`first_light`), command/event-ring
processing, and single-device root-hub enumeration had since landed; only
the transfer path, bus ops, and the event-ring IRQ were still unwritten.

`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1784` (`uhc_xhci_alif_ep_enqueue`) and
`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1853` (`uhc_xhci_alif_ep_dequeue`) now
build real TRBs on a per-endpoint ring (control over the existing EP0 ring;
bulk/interrupt on a small pool configured via a Configure Endpoint Command,
`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1281` (`uhc_xhci_alif_ep_ctx_get`) and wait for completion with the same bounded-
polling pattern `uhc_xhci_alif_enumerate()` already used. `SET_ADDRESS` on
EP0 is short-circuited to success rather than re-sent on the wire, since
Address Device already assigned it in `*_enable()`.

`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1576` (`uhc_xhci_alif_disable`) and
`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1621` (`uhc_xhci_alif_shutdown`) now
really stop the controller (clear USBCMD.R/S, poll HCH, gate the PHY/clock);
`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1638` (`uhc_xhci_alif_bus_reset`)
plus new `bus_suspend`/`bus_resume` drive real PORTSC sequences per the
xHCI spec.

`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1950` (`IRQ_CONNECT(DT_INST_IRQN(n),`)
wires a real `IRQ_CONNECT` (IRQ 101);
`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:1236`
(`uhc_xhci_alif_isr`) drains the event ring for hotplug (connect/disconnect)
notification once `*_enable()` arms `IMAN.IE`. Every synchronous
command/transfer wait (`uhc_xhci_alif_wait_event`,
`zephyr/drivers/usb/uhc/uhc_xhci_alif.c:796` ("static uint8_t uhc_xhci_alif_wait_event(const struct device *dev,")) is bracketed by its caller with
`uhc_xhci_alif_irq_mask`/`uhc_xhci_alif_irq_unmask` on the controller's IRQ so
it can never race the ISR over the shared event-ring consumer state on this
single-core M55.

Added `xhci_alif_flush`/`xhci_alif_invd` (cache maintenance around every
CPU/xHC DMA handoff — rings, contexts, transfer buffers), since the
controller is an AXI-master DMA engine that bypasses the M55 D-cache.

**Unverified on silicon** (stated plainly, not bench-run): `ep_enqueue`/
`ep_dequeue`, bus suspend/resume, disable/shutdown, the event-ring ISR and
its `irq_disable`/`irq_enable` race argument, and whether the cache-
maintenance calls are the right ones for this target's D-cache
configuration. Only `first_light` plus `enable()`'s own controller bring-up
(DWC3 host-mode init, xHCI reset, the command/event-ring round trip: No-Op +
Enable Slot) was proven on an E8 EVK. `enumerate()`'s device-dependent
stages (Address Device, the GET_DESCRIPTOR control transfer) did **not**
reach completion on that same bench session — blocked on the EVK's D+/D-
signal path issue #388's triage comments describe, a separate, hardware
blocker, independent of anything below. Nothing past `first_light`/
`enable()`'s controller bring-up is silicon-verified.

A follow-up review pass (same issue) found and fixed several correctness
defects in the above, all still unverified on silicon for the same reason:

- Every synchronous command/transfer wait now masks the controller IRQ
  **before** enqueuing the TRB and ringing the doorbell, not just before the
  wait itself — the old order left a window where the event-ring ISR
  (already armed) could steal the very completion event the wait was about
  to consume.
- A short control-IN read reported the requested `wLength` instead of the
  real byte count: the Data Stage TRB now carries its own `IOC`, and its own
  Transfer Event (matched by TRB pointer) — not the Status Stage's, which
  carries no residual — is what `ep0_transfer` waits on for the byte count.
- STALL / transaction-error / babble now drive Reset Endpoint + Set TR
  Dequeue Pointer (the endpoint was left Halted with no recovery before);
  a `wait_event` timeout now drives Stop Endpoint + Set TR Dequeue Pointer
  (command-ring timeouts abort the ring via `CRCR.CA`) instead of leaving an
  armed TRB a later wait could wrongly match.
- `bus_reset()` now issues Reset Device + re-Address Device (and resets the
  endpoint-ring pool) after the port reset, instead of leaving an
  already-addressed device's slot state stale.
- `PORTSC` change bits are now RW1C'd when a Port Status Change is handled
  (ISR or a masked poll), a Port Status Change seen while waiting for
  something else is latched and reported once the mask lifts instead of
  silently dropped, and `enable()` reports a connect event up front if a
  device is already attached (`CCS=1`).
- `disable()`/`enable()` now issue Disable Slot and re-init the command ring
  + endpoint pool respectively, instead of a second `enable()` reusing stale
  software ring state against a freshly-programmed `CRCR`.
- `shutdown()` no longer re-asserts `USB_CTRL2.PHY_POR`, which directly
  contradicted `first_light()`'s own bench note about why that hangs HCRST;
  it now also masks the NVIC line before gating the clock.
- The NVIC line for this IRQ is enabled at the end of `enable()` instead of
  at `POST_KERNEL` driver init, and the ISR now bails on a software `armed`
  gate as a second line of defense.
- IN transfer buffers are now flushed (not just invalidated) before the
  doorbell, matching the OUT-side handling that was already there.
- Transfer lengths are now validated against the caller's actual buffer room
  and a 64 KiB single-TRB cap (`xhci_validate_xfer_len()`, new in
  `xhci_core.c`, host-unit-tested) before building a TRB.
- The endpoint context (`xhci_build_ep_context()`) now also fills Interval,
  CErr=3, and Average TRB Length per xHCI 1.2 §6.2.3 (it previously left
  them zero).
- `bus_suspend()` now stops endpoints first and confirms via `PORTSC.PLS`
  reading back U3, not `PLC` (not guaranteed to latch on every
  implementation).
- An interrupt endpoint now returns `-ENOTSUP` from `ep_enqueue()` rather
  than silently running through the same fully-synchronous transfer path as
  bulk: a real interrupt-IN needs periodic, asynchronous completion this
  driver doesn't implement, so the claim is dropped (Kconfig.xhci_alif /
  the example README corrected to match) instead of shipped half-true.
- `xhci_dci_for_ep()` moved into `xhci_core.c` (pure, host-unit-tested)
  alongside the new `xhci_validate_xfer_len()`; `xhci_core.h`'s Reset
  Endpoint/Stop Endpoint/Set TR Dequeue Pointer/No-Op command section
  citations were off by one (a skipped Evaluate Context subsection), fixed,
  and a new Reset Device Command TRB type constant added.
