### Fixed — the CC3501E GPIO proxy's weak route table was constant-folded at `-Os`, so a board's strong override was never read (#1860)

`src/backends/gpio/cc3501e_proxy.c` defined `cc3501e_gpio_routes[]` /
`cc3501e_gpio_route_count` as `__attribute__((weak)) const` objects in the
same translation unit that read them in `route_lookup()`'s loop bound. At
`-Os` (`CONFIG_SIZE_OPTIMIZATIONS=y`, the default on
`alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he`) the compiler could see
its own zero initializer for `cc3501e_gpio_route_count` at the read site
and folded the loop away entirely -- a board's strong override in another
translation unit (e.g. `examples/aen/aen-cc3501e-gpio`) still linked, but
nothing ever read it. Measured on the real target build: the example
object carried the strong `R cc3501e_gpio_routes` symbol, the proxy
object carried only the weak `V` definition with zero relocations
against either symbol in its disassembly, and the final ELF contained
neither symbol. Every `alp_gpio_open()` call fell through to the
platform backend, so pads that exist only on the CC3501E (`IO13`, `IO15`,
`IO18`, `IO19`, `IO20`) could not be driven at all, silently, at any
optimization level the repo ships.

Fixed by splitting the weak default into its own translation unit,
`src/backends/gpio/cc3501e_proxy_routes_weak.c` (gated the same way as
`cc3501e_proxy.c`, `CONFIG_ALP_SDK_GPIO_CC3501E_PROXY`, in
`zephyr/CMakeLists.txt`). `cc3501e_proxy.c` now only ever sees the
`extern` declaration already in `<alp/chips/cc3501e/gpio.h>`, so
`route_lookup()` always compiles a genuine indirect load through
whichever definition the linker resolves. Re-measured on the same target
build after the fix: the proxy object's disassembly now carries real
`R_ARM_ABS32` relocations against both symbols, and the final ELF
carries the strong 9-entry table (verified against the raw `.rodata`
bytes, not just symbol presence).

The same weak-array-read-in-its-own-TU shape is the bug, not this one
instance -- `#1854`'s `cc3501e_gpio_unrouted[]` table (currently parked,
unpopulated, on `fix/1854-unrouted-pad`) will need the identical
own-TU split before it can safely carry real entries.
