### Fixed — portable-C FIR read its own output as the delay line (#1629)

The portable-C `fir_apply()` in `src/backends/dsp/sw_fallback.c` read
`in[n-k]` for `k >= 1` as the FIR delay line, but every real call site runs
it in-place (`out == in`), so for `n >= k` that index is `out[n-k]` — a
sample this same loop had already overwritten on an earlier iteration. The
filter ran over its own output, a recursive and potentially unstable
response, instead of the caller's FIR, and the tail-state save at the end of
the call inherited the same aliasing bug.

`fir_apply()` now tracks the `M-1` delay-line samples from a copy of each
input sample taken before its output is written, so the kernel never reads
back through `out[]`. Every real `alp_dsp_chain_apply_samples()` /
`alp_dsp_chain_apply_samples_f32()` caller through the portable-C path was
affected — any FIR with more than one tap running in-place on a SoM without
CMSIS-DSP.

Regression test: `tests/zephyr/dsp` — a 3-tap moving-average FIR checked
against its closed form, both in one call and split across two calls to
confirm the saved delay-line state stays correct at a chunk boundary.
