### Fixed — OSPI0 pads never muxed; wrong pinctrl route in `aen-ospi-regcheck`; NOR NOT actually exercised (#2041)

`zephyr/drivers/flash/flash_ospi_alif.c` declared `pinctrl-0` on the
`ospi0` DT node (via `pinctrl-device.yaml`) but contained zero occurrences
of `pinctrl` in the driver body — the property was never applied, so the
OSPI0 pads were never muxed regardless of how correct the controller's
register program was. `examples/aen/aen-ospi-regcheck`'s overlay also
routed the Alif DevKit's OSPI0 pad set (`PIN_P3_0__OSPI0_SCLK_B`,
`PIN_P2_0..P2_7__OSPI0_Dn_B`, port 1/3), not the E1M-AEN carrier's own
route — and the example performed no device transfer at all, only
controller-register reads, so "the OSPI memories are silent" had never
actually been tested at the device level by anything in this repo.

Fixed:

- `ospi_alif_init()` now calls `pinctrl_apply_state(config->pcfg,
  PINCTRL_STATE_DEFAULT)` before `alif_hal_ospi_initialize()`, propagating
  its error; `struct ospi_alif_config` gained a `pcfg` field wired via
  `PINCTRL_DT_INST_DEFINE()` / `PINCTRL_DT_INST_DEV_CONFIG_GET()`.
- The example's board overlay now transcribes the real E1M-AEN OSPI0
  route from `metadata/e1m_modules/aen/alif-ospi.tsv` (13 pads, function 1:
  D0-D7 on P2_0/P2_1/P6_2-P6_6/P0_7, SCLK/SCLKN/RXDS on P12_0-P12_2,
  SS0/SS1 on P12_3/P12_4) instead of the DevKit's pad set, and overrides
  `cs-pin`/`bus-speed` to target OSPI0 CS1 (the NOR, per
  `metadata/e1m_modules/E1M-AEN803.yaml`
  `on_module.ospi_memories.ospi0.chip_select: 1`) at the bench-proven baud.

Measured on E1M-AEN803 real silicon: OSPI0 CS1 answers a JEDEC ID read
(opcode 0x9F, single-lane SDR, `ser`=0x00000002, `OSPI_BAUDR`=20) with
`9d 5b 19 10` — 0x9d is the ISSI manufacturer ID, `5b 19` the
IS25WX256-JHLE's type/capacity pair — through
`ospi_alif_read_jedec_id()` (see #915), reachable now that the pads are
actually muxed. This contradicts the "no OSPI memory fitted" note
previously in `aen-ospi-regcheck`'s header (maintainer, 2026-08-30, about
one physical unit at one point in time) and in the `OSPI_ALIF` Kconfig
help text — both corrected here rather than deleted, so the reversal is
traceable. A live XiP read stays unconditionally unverifiable regardless
of population: `OSPI_XIP_SER` does not exist on this die
(`SOC_FEAT_OSPI_HAS_XIP_SER=0`), an unrelated fact this change leaves
unchanged.

`chip_select` mapping in `E1M-AEN801.yaml` / `E1M-AEN803.yaml` and
`docs/bring-up-aen.md` are untouched here — the former was already correct
on `dev`, the latter is owned by a separate change in flight.
