### Fixed — `flash-jlink-mramxip.sh` no longer shadows `bench-env.sh`'s overridable `GD32_DPIDR`, but keeps the deliberate `AEN_DPIDR` safety pin (#1497)

`scripts/bench/aen/flash-jlink-mramxip.sh` re-declared both `AEN_DPIDR` and
`GD32_DPIDR` as unconditional local assignments after sourcing `bench-env.sh`
(the documented single, overridable source for both), silently discarding an
operator's `export GD32_DPIDR=...` override. #1497's own suggested fix — delete
both lines and let `bench-env.sh`'s exports stand, as `flash-update-log-dual.sh`
already does — is wrong for the `AEN_DPIDR` half: that local pin is
deliberate, and deleting it was already tried once and reverted (`27a4e756`,
during #1488) because it made the wrong-board **MRAM-write** gate
environment-overridable — `AEN_DPIDR` is the positive match
`bench_jlink_assert_aen_dpidr` gates the write on, so a stray or mistaken
`export AEN_DPIDR=...` must not be able to arm it against the wrong value.
`#1527`'s in-tree comment already over-scoped this finding onto `GD32_DPIDR`
too ("do NOT delete this pair"); `197e8264a` already corrected the changelog
record to note only the `AEN_DPIDR` half was ever implicated, but the
in-source comment still said "this pair."

`GD32_DPIDR` is different: `bench_jlink_assert_aen_dpidr` (in the sourced
`bench-env.sh`) *does* abort on a `GD32_DPIDR` match, on its own `return 4`
path — it is not cosmetic — but redundantly, because the fail-closed positive
`AEN_DPIDR` match right after it aborts on the same transcript anyway, just
with a less specific message. So a wrong or missing `GD32_DPIDR` still can't
permit a write, and it carries no gate of its own to weaken. Deleted its local
re-declaration; it now comes from `bench-env.sh`'s single, overridable export,
same as `V2N_CM33_DPIDR` already did in this file. Kept `AEN_DPIDR="4C013477"`
(verified byte-for-byte against `bench-env.sh`'s
`export AEN_DPIDR="${AEN_DPIDR:-4C013477}"`) and rewrote the surrounding
comment to state the real, verified scoping instead of "do not delete this
pair."

Review follow-up, same PR: `flash-update-log-dual.sh`'s own comment said
`AEN_DPIDR`/`GD32_DPIDR` "both" come from `bench-env.sh` — categorical, no
`AEN_DPIDR` carve-out — which read as the opposite instruction to this file's
"`AEN_DPIDR` is deliberately re-pinned here" on the exact line #1488 already
deleted-and-reverted once. Amended that comment to carve `AEN_DPIDR` out and
point back here, rather than silently re-litigating #1488.

Known gap, not closed by this PR: the safety argument for re-pinning
`AEN_DPIDR` locally (an operator's stray `export AEN_DPIDR=...` must not be
able to arm the MRAM-write gate against the wrong value) applies to all six
`bench_jlink_assert_aen_dpidr` call sites, and only this one script pins it.
The other five (`flash-jlink-hp.sh`, `flash-jlink.sh`,
`flash-update-log-dual.sh`, `flash-update-log-firewall-probe.sh`,
`ram-run.sh`) still take `AEN_DPIDR` from `bench-env.sh`'s overridable export.
Pinning at the single source instead (`scripts/bench/aen/bench-env.sh:166` ->
`readonly AEN_DPIDR="4C013477"`) would close all six at once but removes an
environment override the operator relies on across every bench script that
runs against real hardware, so it's tracked as a separate issue rather than
folded into this PR.

`shellcheck -x -S warning` and `bash -n` are both clean on both changed
scripts. Not run: the scripts themselves (they touch MRAM on real silicon;
static reasoning only, per the standing bench-safety rule).
