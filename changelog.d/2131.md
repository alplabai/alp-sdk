### Fixed — SDHC DWC R2 (CID/CSD) response realignment (#2131)

`CONFIG_SDHC_RSP_136_HAS_CRC` (`zephyr/kconfigs/vendor-alif-peripherals.kconfig:499`
("config SDHC_RSP_136_HAS_CRC")) gates the 8-bit realignment shift the DWC_mshc
R2 (CID/CSD) response needs, but nothing defined the symbol, so `IS_ENABLED()`
was always 0 and the shift never ran. Once defined, the realignment loop
(now `sdhc_dwc_realign_r2_response()`, `zephyr/drivers/sdhc/sdhc_dwc.h:351`
("static inline void sdhc_dwc_realign_r2_response")) also carried the
shifted-out byte from the wrong neighbour -- `response[i + 1]` instead of
`response[i - 1]` -- which truncated a v2 CSD's `C_SIZE` to its low 16 bits.

Bench evidence (E1M-AEN803 serial 2026W36-0002), same Samsung microSD, whose MBR ends at
sector `0x0EEC0000` = 250,347,520 sectors:

- symbol undefined (dead code): `524800` sectors reported (256 MiB).
- symbol defined, wrong carry direction: `49020928` sectors reported
  (`C_SIZE` `0x3BAFF` truncated to `0xBAFF`).
- both fixes: the correct `250347520` sectors (122240 MiB), CID/CSD read
  correctly, sector 0 read back with its `55 AA` boot signature.

The realignment is now a small `static inline` helper so it is host-testable
independent of hardware; see `tests/unit/sdhc_dwc_r2_realign` (native_sim
ztest), which builds the 4 RESP words a DWC controller would hold for a real
CSD v2 register (`CSD_STRUCTURE = 1`, `READ_BL_LEN = 9`, `C_SIZE = 0x3BAFF`)
and asserts the decode matches the same field positions Zephyr's `sd_ops.c`
v2 CSD decode uses (that file lives in the Zephyr tree, not this repo) --
including `response[0]` (the least significant word), which the old carry
direction polluted with data from the wrong neighbour even though it has no
lower word to carry from.
