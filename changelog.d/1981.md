### Fixed — the ATOC guard rejected every Cortex-A32 boot configuration (#1981)

`scripts/aen_atoc.py` looked each `mramAddress` entry's `cpu_id` up in
`SLOT0_WINDOWS`, which held `M55_HE` and `M55_HP` only, and raised on anything
else. An A32 boot chain uses `cpu_id: "A32_0"` — what the Secure Enclave
requires for the entry it boots — so the guard rejected the one configuration
that demonstrably works:

```
AtocValidationError: ATOC entry 'BOOTLOAD' has unknown cpu_id 'A32_0' for a
slot0-XIP window check -- expected one of ['M55_HE', 'M55_HP']
```

That configuration is not hypothetical. It boots: the SE's own table reports
`BOOTLOAD` as `cpu_id A32_0`, boot address `0x80002000`, flags `u VB` —
uncompressed, Verified, **Booted** (#1972).

**The fix is not an extra dictionary key**, and treating it as one would
re-open the collision #1069 exists to prevent. The A32 chain occupies one
contiguous span — BL32 at `0x80002000`, device tree at `0x80010000`, kernel
XIP at `0x80020000`, cramfs at `0x80380000` — which covers **both** M55 slot0
windows in full. That is the intended layout, not an overlap bug: an A32 Linux
system uses essentially the whole 5.5 MB MRAM, and the M55 entries in its ATOC
are `loadAddress` ITCM stubs at `0x50000000` / `0x58000000`, never MRAM
residents.

So the guard now enforces a stronger invariant than it did before: **if any
`mramAddress` entry declares an A32 `cpu_id`, no `mramAddress` entry may
declare an M55 one, and vice versa.** Mixing them would stage an M55 slot0
image into memory the A32 is executing from. `loadAddress` (ITCM) entries stay
exempt, exactly as before, so a real A32 ATOC's two M55 stubs do not trip it.

Two deliberate asymmetries with the M55 windows, both commented in the source:

- `A32_CPU_IDS` is a **separate** constant rather than a third entry in
  `SLOT0_WINDOWS`. `scripts/west_commands/runners/alif_flash.py` iterates that
  dict to map a build's reset vector back to its core, and its
  `'HE' if … else 'HP'` would have mislabelled every A32-window hit as HP — an
  A32 region spanning `0x80002000`..`0x80580000` also contains every legal
  HE/HP vector.
- The A32 check is **base-bound only**. Its ceiling is the APP Package start,
  which is not a policy constant: it moves with package size, and SETOOLS
  reports it per build in `build/app-package-map.txt`. Hardcoding today's
  `0x8057a8f0` would silently rot. `MRAM_END` still bounds it.

Four tests added, each verified to fail against the pre-change module rather
than passing vacuously: an A32 config accepted, a mixed A32+M55-slot0 config
rejected, an A32 config with ITCM M55 stubs accepted, and an A32 entry below
the BL32 base rejected. `tests/scripts/test_aen_atoc.py` goes 8 → 12; the full
`tests/scripts/` sweep is 3541 passed, 36 skipped.

Also lands `scripts/bench/aen/flash-jlink-a32.sh`, the five-blob A32 flash
flow, which calls this guard before `app-gen-toc` runs.

> **Bench-gated.** The guard change is exercised by unit tests only. The
> configuration it now accepts has been booted on silicon, but no flash path in
