### Fixed — `aen_atoc.py` rejected every valid Cortex-A32 boot config (#1981)

`scripts/aen_atoc.py`'s `SLOT0_WINDOWS` (the #1069 slot0-XIP window guard)
only recognised `cpu_id` values `M55_HE`/`M55_HP`, so any `mramAddress` ATOC
entry declaring `cpu_id: "A32_0"` — what the Alif Secure Enclave requires for
an A32 Linux boot chain — raised `AtocValidationError` unconditionally. No
in-tree flash path could stage an A32 Linux image. Bench-verified on two
E1M-AEN803 modules on 2026-09-05: the Secure Enclave's own boot table booted
`BOOTLOAD` (TF-A BL32) at `cpu_id A32_0`, boot address `0x80002000`, flags
`u VB`, the exact config the guard rejected.

Added an `A32_0` window, floor `0x80002000` (that bench-verified `BOOTLOAD`
boot address) through `0x80578000` (5592 KiB) — the base of the SE-owned
`atoc` band, verbatim from every AEN preset's `memory_map:` `atoc` region
(`metadata/e1m_modules/E1M-AEN801.yaml`, `E1M-AEN803.yaml`, and five other
AEN SKUs, all `{ base: 0x80578000, size_kib: 32 }`). This is a fixed
reservation band, not the true per-build ceiling — the signed ATOC's own
start address moves with ATOC package size (SETOOLS
`build/app-package-map.txt`) and this module has no per-build input to
re-derive it — the same #1289/#1482 decision `scripts/check_atoc_reservation.py`
already enforces for every other AEN partition table: never derive the exact
ATOC start, reserve a band whose base is a committed static value instead.
An earlier version of this window used the raw System MRAM end
(`0x80580000`) as its ceiling instead of the atoc band's base, which
silently accepted an `A32_0` `mramAddress` entry anywhere inside that 32 KiB
SE-owned band — exactly the vacuous-hardcode shape
`check_atoc_reservation.py`'s own docstring warns against. `SLOT0_WINDOWS`'s
ceiling is now derived from that band's size rather than hand-copied, and
`check_atoc_reservation.py` gained a fourth check asserting every
`SLOT0_WINDOWS` ceiling stays at or below each preset's `atoc` band base, so
this specific regression can't recur unnoticed.

An A32 Linux chain's `mramAddress` span runs from TF-A BL32 through the
kernel and so covers **both** M55 windows entirely — the A32 window above is
not a third disjoint slice, it deliberately overlaps the M55 ones.
`validate_atoc_entries()` therefore also rejects any config mixing an
`A32_0` `mramAddress` entry with an `M55_HE`/`M55_HP` `mramAddress` entry
(mixing them would stage an M55 slot0 image into memory the A32 chain is
executing from); `loadAddress` (ITCM) M55 stub entries — the shape the
issue's own example config uses for its `HP_APP`/`HE_APP` stubs — stay
exempt, as before. That mutual-exclusivity check only fires when an M55
`mramAddress` entry is present alongside an A32 one; a **pure** A32-only
config (the shipped shape) is constrained by the window bounds alone, not by
that check — worth stating plainly, since an earlier version of this
module's own comment claimed the opposite.

Fixed a second, sibling defect this window addition exposed in
`scripts/west_commands/runners/alif_flash.py::_select_app_shape()`: its
`vector_suffix = 'HE' if vector_cpu_id == 'M55_HE' else 'HP'` ternary assumed
`SLOT0_WINDOWS` held exactly two keys. With `A32_0` added, a reset vector
landing in the sliver above the old `M55_HP` ceiling (`0x80550000..0x80580000`,
inside the `A32_0` window but outside both real M55 windows) would have
silently matched `A32_0`, fallen into the `else` branch, and been mis-staged
to burn at `M55_HP`'s window base (`0x802b0000`) — a wrong address. An
earlier version of this fix special-cased `A32_0` to reject it with a
message claiming the address was "staged by a different flash path" — a
regression in its own right: this runner is Zephyr `west flash`-only and
never legitimately stages an A32 image, so a genuine M55 mis-link landing
in that sliver (e.g. `0x80560000`) got a misleading "nothing to see here"
message instead of the correct refusal. `_select_app_shape()` now excludes
`A32_0` from its window lookup entirely, so any reset vector outside the two
real M55 windows gets the plain "outside every declared slot0 window —
refusing to burn" diagnostic.

Also fixed: the mutual-exclusivity check itself tested `cpu_id != 'A32_0'`
to decide "is this an M55 entry", which would mislabel a future second
A32-cluster key (the Alif E8's A32 cluster is dual-core) as an M55 entry and
wrongly trip mutual exclusion against `A32_0`. It now tests membership
against an explicit `{M55_HE, M55_HP}` set instead.
