### Fixed — an RX-only path could still stop or reprogram the shared I2S bit clock out from under a live TX stream (#2150 phase 1)

**Not full duplex.** #2150 itself is filed as a full-duplex feature request.
This is phase 1 only: the shared bit-clock ownership gap the driver's own
file header already named as a known remaining hazard after #2149. Refs
#2150; `i2s_dw_configure()` still maps `I2S_DIR_BOTH` to `-ENOSYS` and
`dev_data->dir` is still a single field
(`zephyr/drivers/i2s/i2s_dw.c:170-175` ("struct i2s_dw_data {")), both
deliberately unchanged.

**Why now.** #2149 made the TX underrun ISR exit deliberately leave
`CER.CLKEN` set so a TAS2563 on the same bus does not read bit-clock loss as
its own cue to latch SHUTDOWN. `rx_stream_disable()` and `rx_stream_start()`
were the two remaining places that could still pull that clock out from
under a transmitting stream, reopening the exact bug #2149 just closed —
this driver has one CGU-derived bit clock shared by both directions, not one
per direction.

**Fixed.** A new helper, `tx_clock_is_live()`
(`zephyr/drivers/i2s/i2s_dw.c:899-903` ("static bool tx_clock_is_live(const struct i2s_dw_data *dev_data)")),
decides whether TX is depending on the shared clock right now:
`I2S_STATE_RUNNING` always qualifies; `I2S_STATE_ERROR` qualifies only when
`tx.clk_restart_skip_ok` is still set, since that flag's own contract (see
`struct stream`) is exactly "`CER.CLKEN` is deliberately left set" — armed
only by #2149's keep-clock underrun exit and cleared by every path that
actually gates the clock. Checking `RUNNING` alone would miss that ERROR
window and reopen the #2149 bug; an `ERROR` state with the flag already
clear means some other exit already gated the clock, so there is nothing
left for RX to disturb.

- `rx_stream_disable()` — the single shared body reached from
  `STOP`/`DRAIN`/`DROP` (via `stream->stream_disable`) and both RX-ISR error
  exits — now skips `i2s_clock_disable()` when TX is live
  (`zephyr/drivers/i2s/i2s_dw.c:1111-1119` ("if (!tx_live) {")), and
  deliberately leaves `tx.clk_restart_skip_ok` untouched in that case, since
  the clock never actually stopped. When TX is not live, behaviour is
  unchanged from before this fix.
- `rx_stream_start()` now skips reprogramming
  `clock_control_set_rate()`/CCR when TX is live at the SAME
  `frame_clk_freq`
  (`zephyr/drivers/i2s/i2s_dw.c:949-966` ("clk_needs_reprogram = !tx_live;")),
  mirroring the `clk_needs_reprogram` shape #2149 already established in
  `tx_stream_start()`. If TX is live at a DIFFERENT rate, RX cannot silently
  retune the one shared divider without also retuning TX's stream out from
  under it, so it now returns `-EBUSY`
  (`zephyr/drivers/i2s/i2s_dw.c:913-925` ("return -EBUSY;")) instead of
  pretending to succeed, before touching any hardware state or allocating a
  block. `-EBUSY` was chosen over `-ENOTSUP` (this is not a permanent
  incapability) or `-EINVAL` (the RX config is fine on its own; the conflict
  is with the CURRENT shared clock state) — retrying once TX stops, or
  reconfigures to the same rate, succeeds. When TX is not live, behaviour is
  unchanged from before this fix.

**Known remaining gap, out of scope for phase 1:** `rx_stream_start()` and
`tx_stream_start()` each still unconditionally disable the OTHER
direction's channel-enable bit (`i2s_tx_channel_disable()` /
`i2s_rx_channel_disable()`) on every start — a genuinely concurrent RX+TX
session would still have one direction's channel silenced by the other's
(re)start, clock ownership aside. That is full-duplex territory and stays
with #2150's later phase(s). The narrow window between an underrun's
`I2S_TRIGGER_PREPARE` (`ERROR` → `READY`, clock left on but
`tx_clock_is_live()` now reads false since only `RUNNING`/`ERROR` count) and
the next TX restart is also not covered by this phase — an RX start or stop
landing in exactly that window still reprograms/gates as before. Both are
explicitly bounded by phase 1's scope: clock-ownership safety for the
`RUNNING` and keep-clock-`ERROR` states only.

**Not verified on silicon.** No hardware access for this change. The bench
check still owed: on `e1m-aen-evk-03`, an RX overrun during active TX must
leave `CER=0x00000001` and both TAS2563 amps at `PWR_CTL=0x0c`.

**Tests.** `tests/unit/i2s_dw_underrun` — the suite that compiles
`zephyr/drivers/i2s/i2s_dw.c` directly against a RAM-backed register block —
gains four cases: RX `STOP` with TX `RUNNING` leaves `CER.CLKEN` set
(mutation-proven: reverting `rx_stream_disable()`'s `if (!tx_live)` guard to
unconditional gating turns it RED); RX `STOP` with no TX stream configured
still gates the clock, unchanged; RX `START` with TX `RUNNING` at the same
rate does not call `set_rate`; RX `START` with TX `RUNNING` at a different
rate returns `-EBUSY` and does not touch `set_rate`
(`tests/unit/i2s_dw_underrun/src/test_i2s_dw_underrun.c` new
`test_rx_stop_with_tx_running_keeps_clock`,
`test_rx_stop_with_tx_idle_gates_clock`,
`test_rx_start_with_tx_running_same_rate_skips_reprogram`,
`test_rx_start_with_tx_running_different_rate_fails`). `twister -p
native_sim/native/64 -T tests/unit/i2s_dw_underrun`: 12/12 test cases pass.
