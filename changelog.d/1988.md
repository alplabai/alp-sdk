### Fixed — the RTC-alarm port-15 register-layout warning was family-scoped, not part-scoped, and would have misdirected non-E8 AEN SKUs (#1988)

`metadata/e1m_modules/aen/on-module-links.yaml` carries `families: [aen]` —
it is the single on-module-pad authority shared
by every AEN SKU (E1M-AEN301/401/501/601/701/801/803). Its `rtc_alarm.risk`
string, though, was evidenced against exactly one document:
`metadata/e1m_modules/aen/on-module-links.yaml:148` ("The AE822 DFP warns for port 15").
AE822 is the E8's own part number — there is no citation against the
E3/E4/E6/E7 DFPs, and `scripts/gen_zephyr_board.py`'s `_aen_brd_i2c_dts()`
(`scripts/gen_zephyr_board.py:1144`, "def _aen_brd_i2c_dts") emitted that
string into every AEN SKU's generated `.dts` unconditionally — the function
took no part parameter at all.

Nothing had shipped wrong yet only because every non-E8 AEN SKU is refused
earlier in the pipeline, for one of two reasons. E1M-AEN301, E1M-AEN501 and
E1M-AEN701 (E3/E5/E7) are driven out at `_board_naming()`: none of their SoC
JSONs' `m55_hp`/`m55_he` core entries declares `zephyr_cpucluster` at all, so
board naming itself raises before this code is ever reached. E1M-AEN401 and
E1M-AEN601 (E4/E6) clear that guard but are then refused by
`_aen_peripherals_dtsi()`, since neither `e4.json` nor `e6.json` declares
`zephyr_peripherals_dtsi`. Either way, none of the five reaches this code
path today. The moment any of E3/E4/E5/E6/E7 clears its own guard, its
generated devicetree would carry AE822-specific register-layout guidance for
silicon whose port-15 layout was never checked — actively misdirecting a
bring-up engineer toward suspecting the wrong register on a fault they
cannot attribute to that DFP.

Fixed by scoping the DATA, not by hardcoding a part check in the generator:
`rtc_alarm.risk` is now a map keyed by the SoC's own `part` designator
(`metadata/e1m_modules/aen/on-module-links.yaml:140`, "Keyed by the SoC")
with a single `E8:` entry carrying the existing AE822 text.
`_aen_brd_i2c_dts()` now takes `part` and looks up `risk.get(part)`
(`scripts/gen_zephyr_board.py:1204`, "risk_text = (alarm.get(") — a part
with no entry gets no risk paragraph at all, silence rather than a hedged
restatement, because no DFP has been checked for it. `docs/soms/aen.md`'s
own prose already scoped this section "E1M-AEN801 only", so no doc change
was needed there — only the generator was unconditional.

`tests/scripts/test_gen_zephyr_board.py`'s
`test_rtc_alarm_risk_is_scoped_to_the_part_it_was_evidenced_against` forces
E1M-AEN801 down this same emit path with its SoC JSON's `part` mutated to
`E4` (the narrowest stand-in for onboarding E1M-AEN401, which is refused
earlier for lacking `zephyr_peripherals_dtsi`) and asserts the AE822 sentence
is absent from that `.dts` while still present in the genuine, unmutated
E1M-AEN801 build. Every committed AEN board file is byte-identical after
this change (E1M-AEN801 is genuinely E8, so its own generated `.dts` is
unaffected). `_load_aen_on_module_links()` also now shape-checks
`rtc_alarm.risk` itself (a bare string, the pre-#1988 shape, used to reach
the `.get(part)` lookup and crash with an uncaught `AttributeError` instead
of the file-naming `ZephyrBoardEmitError` its sibling checks already raise).

NOT closed by this fix: the SAME family-vs-part shape survives, unattributed,
in `_aen_i2c_pinctrl_group()`'s "Alif's own DFP sets PADCTRL_READ_ENABLE on
{sda} AND {scl}" comment (`scripts/gen_zephyr_board.py:1098`, "Alif's own
DFP sets") — it is evidenced only against the AE822 DFP but is emitted into
every AEN SKU's `-pinctrl.dtsi` unconditionally, taking no `part` parameter
at all. `test_part_designator_is_read_from_the_soc_json` now also asserts
`"AE822 DFP"` is absent from a part-mutated board (pinning the CLASS, not
just the one string this fix scopes), so this residue will fail loudly the
day a non-E8 board is onboarded rather than silently inheriting E8 wording;
scoping the pinctrl comment itself is left as a follow-up.
