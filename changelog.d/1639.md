### Added — `alp_uart_config_t` gains hardware/software flow control (#1639)

`alp_uart_config_t` carried baud rate, data bits, stop bits and parity but no
flow-control field, so RTS/CTS was unreachable through the portable UART API
even though the Zephyr and Linux backends both sit on top of a real
mechanism (`uart_config.flow_ctrl`, termios `CRTSCTS`) that neither one wired
up. Anyone attaching a UART radio, modem or GNSS receiver above roughly
230400 baud, or against any peer with a shallow FIFO, had no way to prevent
the peer overrunning and silently dropping bytes -- `alp_uart_write()`
returned `ALP_OK` for data the far end never saw.

- **New `alp_uart_flow_t` enum** (`include/alp/peripheral.h`):
  `ALP_UART_FLOW_NONE` (default) / `ALP_UART_FLOW_RTS_CTS` (4-wire hardware
  flow control) / `ALP_UART_FLOW_XON_XOFF` (in-band software framing). New
  `flow_control` field on `alp_uart_config_t`, appended after `parity` so
  every existing designated-initialiser call site in the tree (examples,
  tests) keeps compiling unchanged and defaults to `ALP_UART_FLOW_NONE`.
  `ALP_UART_CONFIG_DEFAULT(id)` now also sets `.flow_control =
  ALP_UART_FLOW_NONE`.
- **The field cannot be silently dropped -- three in-tree backends fixed.**
  `src/backends/uart/zephyr_drv.c` used to hardcode `.flow_ctrl =
  UART_CFG_FLOW_CTRL_NONE` regardless of the caller's request, and its
  `uart_configure()` call tolerated `-ENOSYS`/`-ENOTSUP` unconditionally on
  the theory that the devicetree-provided params were good enough;
  `vendors/alif/uart.c` (the bare-metal Ensemble CMSIS-Driver wrapper) had
  the identical `ARM_USART_FLOW_CONTROL_NONE` hardcode. Both now map
  `flow_control` onto the real backend field, and `alp_uart_open()` returns
  `ALP_ERR_NOSUPPORT` -- instead of a silent `ALP_OK` with no flow control
  -- when the caller asked for `ALP_UART_FLOW_RTS_CTS` and the controller
  can't attempt `uart_configure()` at all (`-ENOSYS`/`-ENOTSUP`); a driver
  that rejects the request outright surfaces whatever status it actually
  returned (e.g. `ALP_ERR_INVAL` for `-EINVAL`), not necessarily
  `ALP_ERR_NOSUPPORT`.
- **Accepted-but-ignored is also closed, on both backends.** A driver can
  report success from `uart_configure()`/`tcsetattr()` without having
  acted on the flow-control bits at all -- nothing in the Zephyr UART API
  requires a driver to reject a `flow_ctrl` it merely stores (`uart_emul`
  does exactly this), and POSIX `tcsetattr()` returns success as soon as
  ANY requested change lands, even when the specific tty driver clears
  `CRTSCTS` inside `set_termios()`. Both backends now read the
  configuration back after a reported success (`uart_config_get()` /
  `tcgetattr()`) and turn a mismatch on the requested bits into
  `ALP_ERR_NOSUPPORT`.
- **`ALP_UART_FLOW_XON_XOFF` has no Zephyr or CMSIS-Driver USART
  equivalent.** `enum uart_config_flow_control` carries only `NONE` /
  `RTS_CTS` / `DTR_DSR` / `RS485`; CMSIS-Driver USART has no in-band
  software framing mode either. The Zephyr backend refuses it before
  calling `uart_configure()` at all; the CMSIS backend still has to run
  `Initialize()`/`PowerControl(ARM_POWER_FULL)` first (CMSIS-Driver
  requires that before any `Control()` call), then refuses it -- both
  return `ALP_ERR_NOSUPPORT`/`NULL` without ever handing the request to
  `Control()`.
- **The Linux/Yocto backend** (`src/yocto/peripheral_uart.c`) gets a real
  mapping for *both* enumerators, since termios has no such gap: `CRTSCTS`
  in `c_cflag` for `ALP_UART_FLOW_RTS_CTS`, `IXON|IXOFF` in `c_iflag` for
  `ALP_UART_FLOW_XON_XOFF`. The mapping lives in a new pure helper,
  `apply_flow_control()`, unit-tested directly against a scratch `struct
  termios` (`tests/yocto/peripheral_uart_flow_control.c`) without needing a
  real `/dev/tty*`.
- **The sw_fallback and testing (`alp_testing`) UART backends stay
  unchanged, deliberately.** Neither drives a real line: `sw_open` is a
  64-byte in-process ring buffer and `t_open` is a test double documented
  to always succeed regardless of config, so the flow-control
  refusal/readback guarantee in `<alp/peripheral.h>` -- scoped to backends
  that drive actual hardware -- does not cover them; both already ignore
  every line-config field in `alp_uart_config_t` (`sw_open`/`t_open` never
  read `cfg->parity`/`cfg->baudrate` either), so they compile against the
  wider struct with no behaviour change.

**Not wired up by this change, and deliberately so:** which E1M/carrier pads
actually carry RTS/CTS is per-SoM metadata that does not exist in the tree
today -- no board currently routes those lines. Emitting Zephyr's
`hw-flow-control` devicetree property or the corresponding pinmux
(`scripts/alp_project.py`) needs that real pad data first; inventing it would
violate this repo's "never invent hardware facts" rule. A caller drives
`flow_control` through the portable API today only on a board whose own
`boards/*.overlay` already routes and pin-muxes RTS/CTS for the target UART
node.

Labelled `needs-silicon`: proving flow control actually prevents overrun
needs a real run at a high baud rate against a real peer, which `native_sim`
cannot show and this change was not bench-verified against. Failure-path and
mapping coverage lands with the code (native_sim ztest for the
`ALP_UART_FLOW_XON_XOFF` NOSUPPORT-on-Zephyr path; a pure-function unit test
for the Linux termios bit mapping); the RTS/CTS overrun-prevention claim
itself remains a bench-gated follow-up.
