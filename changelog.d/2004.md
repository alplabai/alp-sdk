### Added — `metadata/catalog.json` publishes each SoM's single-slot boot fact (#2004)

`scripts/alp_orchestrate/secure.py::_boot_target_is_single_slot` already
computed, per project, whether a target's MCUboot chain is single-slot
(no `slot1`/scratch partition to swap into) — but the answer was computed
in-process at `emit_sysbuild_conf` time and published nowhere. A consumer
outside this repo (the VS Code Configurator, via `tan`) had no way to
know a given SoM would reject `boot.swap_algorithm: move` until the build
itself raised `OrchestratorError`.

Every `soms[*]` entry in `metadata/catalog.json` now carries:

```json
"boot": {
  "single_slot": true,
  "default_swap_algorithm": "none",
  "allowed_swap_algorithms": []
}
```

(the second of the two shapes weighed in the issue — the resolved default
plus the legal set, not just the bare boolean). On a two-slot target this
reads `single_slot: false`, `default_swap_algorithm: "scratch"`,
`allowed_swap_algorithms: ["scratch", "move", "overwrite"]` — mirroring
`scripts/alp_orchestrate/secure.py:239-269`'s `swap_algorithm` →
`SB_CONFIG_MCUBOOT_MODE_*` mapping exactly, the sole owner of that rule.

**What the field means for a SoM, not just a project.** The real predicate
answers a per-project, per-core question (does THIS project's chosen
`m55_he`/`m55_hp` core have its own `<role>_slot0` region?), and a catalog
entry has no project, only a SoM preset. `scripts/gen_catalog.py`'s new
`_boot()` answers the SoM-level version of the same question: does EVERY
m55 role this SoM's own `topology:` declares have a `<role>_slot0`
`memory_map:` region? On the current corpus this is never a mixed answer —
each dual-M55 AEN SoM's preset declares disjoint `he_slot0`/`hp_slot0`
windows or neither (#1069/#1445) — so `single_slot` is never a lie by
omission. A `memory_map:` authored for one m55 role but not its sibling
would be a half-authored preset; `gen_zephyr_board._aen_role_slot0_map`
raises for that state instead of guessing, and `_boot()` checks EVERY
declared m55 role (not just the first, unlike `_boot_target_is_single_slot`'s
short-circuit) so a future half-authored preset fails the regen loudly
instead of resolving to an order-dependent answer.

**No second implementation of the predicate.** `_boot()` calls the SAME
`gen_zephyr_board._aen_role_slot0_map` resolver `_boot_target_is_single_slot`,
`_aen_dts`, `_aen_flash_partitions` and `loader._resolve_slot0_load_address`
already share — never a scan of `memory_map:` region names for the
substrings `slot1`/`scratch`, which `secure.py`'s own docstring documents
as disagreeing with the real resolver in general.

**Corpus result**, verified against a direct call into
`alp_orchestrate.secure._boot_target_is_single_slot` (not just re-derived):
single-slot — `E1M-AEN301`, `E1M-AEN401`, `E1M-AEN501`, `E1M-AEN601`,
`E1M-AEN701`, `E1M-AEN801`, `E1M-AEN803`; two-slot (no `m55_he`/`m55_hp`
core, so the predicate never fires and explicit `boot.swap_algorithm`
values are accepted) — `E1M-NX9101`, `E1M-V2M101`, `E1M-V2M102`,
`E1M-V2N101`, `E1M-V2N102`.

`metadata/catalog.json` carries no JSON Schema in `metadata/schemas/`
today (only `metadata/templates/catalog-v1.json` has one, a different
file) — none was extended, since none exists.

The downstream leg — `tan` forwarding this field to the extension — is
tracked separately; this closes only the SDK-side publication the issue
asked for.
