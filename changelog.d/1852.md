### Fixed — an unresolved `cores[].type` no longer crashes or gets guessed at; alp-sdk now answers what tan answers (#1852)

alp-sdk and tan carry the same core-class-to-runtime rule in two repos, and they had diverged
on the one input neither schema constrains: a `cores[].type` that is absent, empty, or not a
string. tan took the fix (tan-cli#914 / tan-cli#957 / tan-cli#962); alp-sdk did not, in the one
direction `test_planner_relocation_freshness.py` cannot see -- tan's copy lives at
`python/tan/core/os_class.py`, outside `tan/planner/` and outside `HAND_PORT_SOURCES`, so the
hash pin never looked at it.

Measured on `dev` before this change:

```
alp-sdk  _allowed_os_for_core("")       -> ["baremetal", "off"]      tan -> []
alp-sdk  _default_os_from_core_type(5)  -> AttributeError            tan -> "off"
alp-sdk  _runtime_class(5)              -> AttributeError            tan -> "other"
```

Two failure modes, not one. `AttributeError: 'int' object has no attribute 'lower'` aborts
`--emit os-topology` with a bare traceback rather than a diagnostic; and `["baremetal", "off"]`
for a core whose class nobody established is a plausible-but-wrong answer that tan's own
docstring rejects by name.

The bare `(core_type or "").lower()` idiom was in **three** functions in
`scripts/alp_orchestrate/topology.py` -- `_default_os_from_core_type`, `_runtime_class` and
(via `_cross_class_os`) `_allowed_os_for_core` -- reached from one caller,
`core_os_topology`, whose `soc_types` comprehension took `c.get("type", "")` unvalidated
against `soc-spec-v1.schema.json`'s own `"type": {"type": "string"}`. That value also went
verbatim into the emitted `core_type` field, so a non-string was a wire leak into the
document as well as a crash. All four sites are fixed: the caller normalises to the same `""`
unresolved sentinel a missing `type` already produces, and each helper keeps an `isinstance`
backstop so a future caller does not inherit the same crash-or-leak choice.

`_cross_class_os` is deliberately left unguarded, matching tan. It feeds the REFUSAL at
`scripts/alp_orchestrate/validate.py::_enforce_os_matches_core_class`, where declining both
real runtimes for an unclassified core is the conservative answer. Only the *advertised*
`allowed_os` set was wrong.

The distinction the fix preserves is **unresolved** versus **unclassified**: a real type
string matching neither `cortex-a*` nor `cortex-m*` (a future RISC-V companion, say) still
resolves to `off` with `["baremetal", "off"]` on offer, in both repos. Collapsing those two is
what produced the wrong answer in the first place.

No emitted bytes change for any shipping SoM -- every `cores[].type` in all nine
`metadata/socs/**` files is `cortex-a*` or `cortex-m*`, and both `os-topology` emit snapshots
are byte-identical after the change.
