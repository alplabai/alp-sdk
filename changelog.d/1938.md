### Fixed — the PUBLISH-payload drain now resumes across `alp_mqtt_loop()` calls instead of ignoring the caller's `timeout_ms` or aborting a healthy link (#1938)

`alp_mqtt_evt_cb()`'s `MQTT_EVT_PUBLISH` handling stamped a fixed 5 s
deadline and blocked inside the event callback -- itself invoked from
`mqtt_input()`, itself invoked from `alp_mqtt_loop()` -- until the whole
payload was off the wire or that deadline passed, ignoring the caller's own
`timeout_ms` entirely. `include/alp/iot.h` documents `timeout_ms` as "max
wait per call"; `alp_mqtt_loop(m, 10)` -- the exact call
`examples/connectivity/iot-connected-camera/src/main.c` teaches -- could
therefore block roughly 500x its documented budget on a payload split
across TCP segments.

The drain is now resumable across calls instead of blocking inside one.
`struct mqtt_be` carries the pending drain's progress (bytes still owed, how
much has already landed in `rx_buf`, the QoS/msg-id needed to finish
delivery) plus a spanning lifetime deadline stamped once when the drain
first becomes pending. Each `alp_mqtt_loop()`/`alp_mqtt_connect()` call
drains only what the socket has ready within its OWN `timeout_ms` and then
returns -- never aborting a healthy connection just because that one call's
budget ran out. Only the drain's spanning lifetime (still 5 s, now measured
from when the drain started rather than reset on every call) tears the
connection down, so a peer that goes permanently silent mid-payload still
can't wedge the client forever.

Also fixed while replacing the drain:

- `alp_mqtt_loop()` returned `ALP_OK` on the very call that tore the
  connection down: after a drain gives up and calls `mqtt_abort()`,
  `mqtt_input()` still answers 0 and `mqtt_live()` answers `-EAGAIN`
  whenever no keepalive is due, so nothing surfaced the loss.
  `docs/tutorials/11-mqtt-tls-publish.md` already documents the intended
  contract -- a broker disconnect surfaces as `ALP_ERR_IO`, since there is
  no separate is-connected query -- so `z_loop()` (and `z_connect()`'s
  drain-resume path) now compare the connected flag before and after and
  return `ALP_ERR_IO` the moment it flips, whether the loss was a graceful
  `MQTT_EVT_DISCONNECT` or our own `mqtt_abort()`.
- The drain's `zsock_poll()` call ignored its return value entirely, so a
  torn-down/invalid socket would have `mqtt_read_publish_payload()` answer
  `-EAGAIN` forever while `zsock_poll()` kept returning immediately --
  hot-spinning at 100% CPU for the rest of the deadline. Zephyr reports a
  torn-down/invalid fd as `POLLNVAL`/`POLLERR` in `revents` with a POSITIVE
  return, never `-1`, so a bare `rc < 0` guard would not have caught it
  either. The drain now inspects `revents` for `POLLNVAL`/`POLLERR` and
  treats `EINTR` as retryable rather than a failure.
- `timeout_ms` is now clamped to `INT32_MAX` before
  `k_uptime_get_32() + timeout_ms`, so the `(int32_t)(deadline - now)`
  comparisons this file uses throughout can't be fooled by a caller passing
  a timeout near `UINT32_MAX`.

`examples/connectivity/iot-connected-camera/src/main.c`'s
`alp_mqtt_loop(g_mqtt, 10)` teaching comment and
`docs/tutorials/11-mqtt-tls-publish.md`'s `ALP_ERR_IO`-on-disconnect contract
both already documented the intended behaviour; this change makes the code
honor it rather than needing either updated.
