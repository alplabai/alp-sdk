### Fixed — the PUBLISH-payload drain now resumes across `alp_mqtt_loop()` calls instead of silently wedging the connection when a payload spans TCP segments (#1938)

`mqtt_drain_remaining()` (added by #1645 to stop an oversized PUBLISH from
wedging the connection) drained the leftover payload in a single
non-blocking pass: it kept reading only while `mqtt_read_publish_payload()`
returned a positive count, and gave up the instant that call answered
anything else -- including a plain `-EAGAIN` because the rest of the
payload simply hadn't arrived on the wire yet. A payload split across TCP
segments therefore reproduced the exact wedge #1645 set out to close:
Zephyr's `mqtt_client::internal.remaining_payload` stayed non-zero, and
every later `mqtt_input()` answered `-EBUSY` forever, with nothing in
`alp_mqtt_loop()`'s return value ever saying so. There was no deadline, no
`zsock_poll()`, and no `mqtt_abort()` anywhere in this path -- the drain
just gave up in silence and left the connection dead.

The drain is now resumable across calls instead of one blind pass.
`struct mqtt_be` carries the pending drain's progress (bytes still owed, how
much has already landed in `rx_buf`, the QoS/msg-id needed to finish
delivery) plus a spanning lifetime deadline stamped once when the drain
first becomes pending. Each `alp_mqtt_loop()`/`alp_mqtt_connect()` call
resumes the drain, spending only what the socket has ready within its OWN
`timeout_ms` (via `zsock_poll()`) before returning -- never aborting a
healthy connection just because that one call's budget ran out. Only the
drain's own spanning lifetime (`ALP_MQTT_DRAIN_TIMEOUT_MS`, 5 s, measured
from when the drain started rather than reset on every call) tears the
connection down with `mqtt_abort()`, so a peer that goes permanently silent
mid-payload still can't wedge the client forever -- the gap #1645's fix
left open.

Also fixed while replacing the drain:

- Neither `alp_mqtt_loop()` nor `z_connect()` surfaced the drain's own
  `mqtt_abort()` (or a peer-initiated `MQTT_EVT_DISCONNECT`) as anything
  but `ALP_OK`: `mqtt_input()` still answers 0 and `mqtt_live()` answers
  `-EAGAIN` whenever no keepalive is due, so nothing told the caller their
  connection was gone. `docs/tutorials/11-mqtt-tls-publish.md` already
  documents the intended contract -- a broker disconnect surfaces as
  `ALP_ERR_IO`, since there is no separate is-connected query -- so
  `z_loop()` (and `z_connect()`'s drain-resume path) now compare the
  connected flag before and after and return `ALP_ERR_IO` the moment it
  flips, whether the loss was graceful (`MQTT_EVT_DISCONNECT`) or the
  drain's own `mqtt_abort()`.
- The drain's new `zsock_poll()` call inspects `revents` for
  `POLLNVAL`/`POLLERR` rather than trusting a bare `rc < 0`: Zephyr reports
  a torn-down/invalid fd as `POLLNVAL`/`POLLERR` with a POSITIVE return,
  never `-1`; missing that would have `mqtt_read_publish_payload()` answer
  `-EAGAIN` forever while `zsock_poll()` kept returning immediately --
  hot-spinning at 100% CPU for the rest of the deadline.
- `timeout_ms` is now clamped to `INT32_MAX` before
  `k_uptime_get_32() + timeout_ms`, so the `(int32_t)(deadline - now)`
  comparisons this file uses throughout can't be fooled by a caller passing
  a timeout near `UINT32_MAX`.

`examples/connectivity/iot-connected-camera/src/main.c`'s
`alp_mqtt_loop(g_mqtt, 10)` teaching comment and
`docs/tutorials/11-mqtt-tls-publish.md`'s `ALP_ERR_IO`-on-disconnect contract
both already documented the intended behaviour; this change makes the code
honor it rather than needing either updated.

**Bench-gated:** the resumable drain is logic-reviewed and confirmed against
a host harness (a synthetic 300 B PUBLISH split into a 100 B then a 200 B
segment 150 ms apart, drained across two `alp_mqtt_loop()` calls with the
connection surviving), not against a real broker. `tests/zephyr/iot`'s new
`alp_sdk.iot.mqtt_build` scenario compiles this file's
`CONFIG_ALP_SDK_IOT_MQTT` arm under `native_sim` -- closing the compile-only
gap `changelog.d/1645.md` recorded for this same file -- but it is
build-only: `native_sim` has no MQTT-capable network stack to run a live
client against, so a real-broker round trip still needs the AEN-Zephyr bench
(`docs/ci/HW-IN-LOOP.md`).
