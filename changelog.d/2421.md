### Changed — one shared, committed MCUboot development key for pre-provisioned AEN modules (#2421)

The docs told customers to generate a random per-clone
`keys/mcuboot_dev_ecdsa_p256.pem` and sign with it. A module's factory MCUboot
can only trust a key that existed when that MCUboot was built, so images
signed that way would have been rejected by a pre-provisioned module
(`docs/aen-provisioning.md` §0.5 Option B).

The SDK now commits a shared development key,
`keys/mcuboot_shared_dev_ecdsa_p256.pem`, and `zephyr/sysbuild/aen/sysbuild.conf`
signs with it by default. Alp Lab builds the factory MCUboot with the same
key, so an image built from a fresh clone boots on a pre-provisioned module
with no key setup. This is the same model as MCUboot's own published
`root-ec-p256.pem`. The key is public and gives no security, which matches the
DM lifecycle the modules ship in; a product re-provisions MCUboot with its own
key. `keys/generate_dev_key.sh` still makes your own key, now documented as
requiring that re-provisioning.

Updated: `keys/README.md`, `keys/.gitignore`, `keys/generate_dev_key.sh`,
`docs/aen-provisioning.md`, `docs/secure-boot.md`, `docs/threat-model.md`,
`docs/tutorials/10-secure-boot-signing.md`, `docs/test-plan.md` (and the
generated `docs/verification-status.md`), `zephyr/sysbuild/aen/README.md`,
`examples/aen/aen-mcuboot-smoke/`, and the `iot-fleet-ota` /
`production-deployment` `board.yaml` `key_file` (plus its emit snapshot).
Verified by a sysbuild build of `aen-mcuboot-smoke`: the MCUboot image embeds
the shared key's public half, and `imgtool verify` accepts the signed slot0
app against it.
