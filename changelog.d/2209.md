### Fixed — `pr-twister-aen.yml` split per SKU, and the AEN803 target declared for the ~50 scenarios #2198 held back (#2209)

**Every bench EVK carries an E1M-AEN803 module, but CI never compiled most
of its board overlays.** #2198 declared the AEN803 target for 12
scenarios and held back ~50 more because the single combined `twister-aen`
job had no time budget left: the last run before it took 24m21s against
the twister step's 30-minute cap. Declaring the rest would have pushed
that past the cap.

**`twister-aen` is now a 2-way SKU matrix.** Each leg selects only its own
SKU's two platforms via `matrix.platform_flags`, at
`.github/workflows/pr-twister-aen.yml:165` ("platform_flags: >-"), and the
two legs run in parallel. Neither is a required branch-protection context on
`dev` (the required contexts are `twister-shard 1/4`..`4/4`, `clang-format
· diff-only` and `distro install · all`, verified against the branch's
own protection rules), so the split blocks nothing, at
`.github/workflows/pr-twister-aen.yml:86` ("building all four board targets, so the two SKUs build in parallel and").
The `--testsuite-root` list stays a single
block shared by both matrix legs rather than duplicated per SKU, at
`.github/workflows/pr-twister-aen.yml:341` ("here. The --testsuite-root list below is scoped to examples/aen --").
The per-SKU report artefact is renamed to avoid an upload collision between
the two legs now running in the same workflow run, at
`.github/workflows/pr-twister-aen.yml:419` ("name: twister-out-${{ matrix.sku }}").

A local `--dry-run` against this tree (examples/aen + firmware-update-log +
drone-autopilot) counts 153 configurations total: 78 AEN801, 75 AEN803 (up
from the pre-split 92). Scaling the 1461s/92-build #2198 measurement
linearly, AEN801 projects to about 1240s/20.7min and AEN803 to about
1195s/19.9min -- both comfortably under the unchanged 30-minute
twister-step cap and 41-minute job ceiling, so neither is tightened per
leg. `examples/connectivity/firmware-update-log` and
`examples/peripheral-io/drone-autopilot`, the two non-examples/aen roots
this job also builds, are unchanged: neither ships an AEN803 overlay at
all under `boards/`, so declaring AEN803 for either would be the exact
silent-overlay-drop hazard this issue exists to close, not a safe
addition.

**Two scenarios get an AEN803 twin scenario instead of a `platform_allow`
line.** `aen-sdhc-probe`'s `.sdhc_build_coverage` and `aen-ethernet-link`'s
`.mdio_managed` both name the AEN801 board overlay explicitly in
`extra_dtc_overlay_files`, which REPLACES rather than supplements Zephyr's
own board-default-overlay auto-discovery -- adding AEN803 to their
`platform_allow` alone would have built the AEN801 overlay for an AEN803
target, the exact #2198 hazard. Each gets its own scenario naming its own
SKU's file instead, at
`examples/aen/aen-sdhc-probe/testcase.yaml:85` ("alp_sdk.examples.aen.sdhc_probe.aen803.sdhc_build_coverage:")
and
`examples/aen/aen-ethernet-link/testcase.yaml:84` ("alp_sdk.examples.aen.ethernet_link.aen803.mdio_managed:").
A grep across `examples/aen/*/testcase.yaml` for `extra_dtc_overlay_files`
naming an AEN801 file found no other scenario shaped this way.

**New guard -- `check_example_board_overlay_parity.py` extended, not a new
script.** A narrower, declaration-triggered relative of the "broader,
deferred alternative" that file's own docstring filed as a follow-up when
#2101 landed (that fuller alternative -- keying off `boards/` content with
NO platform_allow declaration required at all -- is still not
implemented; see the docstring for why it would still be red today). This
one requires a real `platform_allow` declaration to trigger: a scenario
declares SKU A's core target while `boards/` ships the same-PCB SKU B's
file for that same core (same `family` + `silicon_variant`, the pairing
`check_example_board_overlay_content_parity.py`'s `_pcb_key` already
uses), undeclared anywhere that scenario's own build reaches, at
`scripts/check_example_board_overlay_parity.py:644` ("def _same_pcb_sibling_undeclared_problems(root: Path) -> list[str]:").
Unlike the plain #2101 check, this one DOES catch the ~50 scenarios #2209
declared the AEN803 target for.

A scenario is "pinned" -- cannot declare its own sibling target this way
by design -- only when it sets `extra_dtc_overlay_files`, or an
`extra_args` entry starting `DTC_OVERLAY_FILE=`/`CONF_FILE=`: those are
the only twister keys that actually REPLACE (not supplement) Zephyr's
board-default-overlay auto-discovery (verified against
`zephyr/cmake/modules/configuration_files.cmake`'s `if(NOT DEFINED
DTC_OVERLAY_FILE)` guard); `extra_conf_files` and `extra_overlay_confs`
only ADD files and must not be treated as pinned. A pinned scenario is
satisfied only by another PINNED scenario in the same testcase.yaml
declaring the sibling SKU's own target for the same core -- its twin --
not by a coincidental declaration in an unrelated non-pinned scenario
elsewhere in the file. `platform_allow` is read as Twister actually
resolves it: a scenario's own value MERGES with the file's `common:`
default (a `set`-type field) rather than replacing it.

That second guard the issue asked for -- a scenario's extra board files
naming SKU A's paired file while its `platform_allow` reaches SKU B --
already existed from #2214
(`scripts/check_example_board_overlay_content_parity.py:255` ("def _testcase_pin_problems(root: Path")),
so no second gate was added for it. Both guards are green on this tree
with no allowlist, and both are wired into `pr-metadata-validate.yml`
already, no CI/registry changes needed (neither is a new `check_*.py`
script).

Mutation-proof: removing the AEN803 `platform_allow` line from
`aen-brd-i2c-scan/testcase.yaml` reproduces the exact #2101/#2209 class and
fails `check_example_board_overlay_parity.py`; restoring it passes again.

testcase.yaml`, with nothing else in the file pinning AEN803's own
overlay, now fails the same gate (its base scenario declaring both SKUs
does NOT save it, since only another PINNED scenario counts) -- restoring

`extra_dtc_overlay_files` reproduces the #2198 class and fails
`check_example_board_overlay_content_parity.py`'s `_testcase_pin_problems`;
restoring it passes again. Both scripts gained regression tests for their
respective mutations, including the reverse-direction pin case
`_testcase_pin_problems` itself already checked but nothing previously
exercised.

**One real, previously-unbuilt compile break found and fixed, and 29 SKU
board-macro sites corrected.** `aen-dualcore-he-master`'s HP-peer role
select hardcoded the AEN801 board symbol, so an AEN803 HP build silently
took the HE-master branch instead, reaching `#include <alp/mproc.h>` in a
role that never enables `CONFIG_ALP_SDK` (by this example's own asymmetric
design) -- `error: alp/mproc.h: No such file or directory`. The exact
#2198 class, only reachable once this issue's twister invocation actually
compiled the target. On review, the same class turned out to be
widespread: 29 sites across `examples/` gated on the AEN801-specific
`CONFIG_BOARD_ALP_E1M_AEN801_M55_H[EP]` when what they actually depend on
is the SoC core (both SKUs select the identical
`CONFIG_SOC_AE822FA0E5597LS0_RTSS_H[EP]` symbols) -- most seriously the 17
`examples/**/cc3501e_bridge.c` copies, where the WIFI_EN/nRESET LP-pad mux
compiled OUT entirely on AEN803, so the CC3501E companion would never
power. All 29 now gate on the SoC-core symbol instead, at
`examples/aen/aen-dualcore-he-master/src/main.c:108` ("#if defined(CONFIG_SOC_AE822FA0E5597LS0_RTSS_HP)")
and
`examples/aen/aen-cc3501e-bringup/src/cc3501e_bridge.c:10` ("#if defined(CONFIG_SOC_AE822FA0E5597LS0_RTSS_HE)").
clang-format-22 diff-only: clean.
