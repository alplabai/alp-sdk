### Fixed — `pr-twister-aen.yml` split per SKU, and the AEN803 target declared for the ~50 scenarios #2198 held back (#2209)

**Every bench EVK carries an E1M-AEN803 module, but CI never compiled most
of its board overlays.** #2198 declared the AEN803 target for 12
scenarios and held back ~50 more because the single combined `twister-aen`
job had no time budget left: the last run before it took 24m21s against
the twister step's 30-minute cap at
`.github/workflows/pr-twister-aen.yml:384` ("timeout-minutes: 30"), at
~92 builds. Declaring the rest would have pushed that past the cap.

**`twister-aen` is now a 2-way SKU matrix.** Each leg selects only its own
SKU's two platforms via `matrix.platform_flags`, at
`.github/workflows/pr-twister-aen.yml:165` ("platform_flags: >-"), and the
two legs run in parallel. Neither is a required branch-protection context on
`dev` (the required twister contexts are `twister-shard 1/4`..`4/4` plus
`clang-format · diff-only`), so the split blocks nothing. The
`--testsuite-root` list stays a single block shared by both matrix legs
rather than duplicated per SKU, at
`.github/workflows/pr-twister-aen.yml:340` ("here. The --testsuite-root list below is scoped to examples/aen --"),
so open PR #2193's two additional roots land as a trivial textual merge
conflict there, not a semantic one, whichever of the two PRs lands second.
The per-SKU report artefact is renamed to avoid an upload collision between
the two legs now running in the same workflow run, at
`.github/workflows/pr-twister-aen.yml:405` ("name: twister-out-${{ matrix.sku }}").

A local `--dry-run` against this tree (examples/aen + firmware-update-log +
drone-autopilot) counts 144 configurations total: 78 AEN801, 66 AEN803 (up
from the pre-split 92). Scaling the 1461s/92-build #2198 measurement
linearly, AEN801 projects to about 1240s/20.7min and AEN803 to about
1050s/17.5min -- both comfortably under the unchanged 30-minute twister-step
cap and 41-minute job ceiling, so neither is tightened per leg.

**The AEN803 target is now declared for 44 of the held-back scenario
files (50 platform_allow additions -- some declare both HE and HP
targets).** Only where the example's `boards/` already ships the matching
AEN803 overlay for that core, re-derived from the tree rather than trusted
from #2198's own held-back list (#2214 may have already covered some), for
example at
`examples/aen/aen-wdt-feed/testcase.yaml:23` ("alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he")
and, for a dual-core scenario declaring both cores, at
`examples/aen/aen-dualcore-doorbell/testcase.yaml:29` ("alp_e1m_aen803_m55_hp/ae822fa0e5597ls0/rtss_hp").

**Two scenarios get an AEN803 twin scenario instead of a `platform_allow`
line.** `aen-sdhc-probe`'s `.sdhc_build_coverage` and `aen-ethernet-link`'s
`.mdio_managed` both name the AEN801 board overlay explicitly in
`extra_dtc_overlay_files`, which REPLACES rather than supplements Zephyr's
own board-default-overlay auto-discovery -- adding AEN803 to their
`platform_allow` alone would have built the AEN801 overlay for an AEN803
target, the exact #2198 hazard. Each gets its own scenario naming its own
SKU's file instead, at
`examples/aen/aen-sdhc-probe/testcase.yaml:85` ("alp_sdk.examples.aen.sdhc_probe.aen803.sdhc_build_coverage:")
and
`examples/aen/aen-ethernet-link/testcase.yaml:83` ("alp_sdk.examples.aen.ethernet_link.aen803.mdio_managed:").
A grep across `examples/aen/*/testcase.yaml` for `extra_dtc_overlay_files`
naming an AEN801 file found no other scenario shaped this way.

**New guard -- `check_example_board_overlay_parity.py` extended, not a new
script.** The "broader, deferred alternative" that file's own docstring
filed as a follow-up when #2101 landed is now implemented: a scenario that
declares SKU A's core target while `boards/` ships the same-PCB SKU B's
file for that same core (same `family` + `silicon_variant`, the pairing
`check_example_board_overlay_content_parity.py`'s `_pcb_key` already uses),
undeclared anywhere in that scenario, now fails at
`scripts/check_example_board_overlay_parity.py:623` ("def _same_pcb_sibling_undeclared_problems(root: Path) -> list[str]:").
A scenario that pins one literal board file via `extra_dtc_overlay_files`/
`extra_conf_files`/`extra_overlay_confs`/`extra_args` is skipped -- that
shape (the two twin scenarios above) is deliberately single-SKU per
scenario by design, and is
`check_example_board_overlay_content_parity.py`'s `_testcase_pin_problems`
to govern instead. That second guard the issue asked for -- a scenario's
extra board files naming SKU A's paired file while its `platform_allow`
reaches SKU B -- already existed from #2214
(`scripts/check_example_board_overlay_content_parity.py:255` ("def _testcase_pin_problems(root: Path")),
so no second gate was added for it; it is mutation-proven below instead.
Both guards are green on this tree with no allowlist, and both are wired
into `pr-metadata-validate.yml` already, no CI/registry changes needed
(neither is a new `check_*.py` script).

Mutation-proof: removing the AEN803 `platform_allow` line from
`aen-brd-i2c-scan/testcase.yaml` reproduces the exact #2101/#2209 class and
fails `check_example_board_overlay_parity.py`; restoring it passes again.
Adding an AEN803 `platform_allow` entry to `aen-ethernet-link`'s
`.mdio_managed` scenario without changing its `extra_dtc_overlay_files`
reproduces the #2198 class and fails
`check_example_board_overlay_content_parity.py`'s `_testcase_pin_problems`;
restoring it passes again. Both scripts gained regression tests for their
respective mutation.

**One real, previously-unbuilt compile break found and fixed.**
`aen-dualcore-he-master`'s HP-peer role select hardcoded the AEN801 board
symbol -- `#if defined(CONFIG_BOARD_ALP_E1M_AEN801_M55_HP)` -- so an AEN803
HP build silently took the `#else` (HE-master) branch instead, reaching
`#include <alp/mproc.h>` in a role that (by this example's own asymmetric
design, no `boards/*_hp*.conf` ever sets `CONFIG_ALP_SDK=y` for either
SKU's HP target) never enables `CONFIG_ALP_SDK`, so the header is never on
the include path: `error: alp/mproc.h: No such file or directory`. The
exact #2198 class -- an AEN803-vs-AEN801 SKU hardcode left over from before
AEN803 existed, only reachable once this issue's twister invocation
actually compiled the target. Fixed by adding the AEN803 board symbol to
the same `#if`, at
`examples/aen/aen-dualcore-he-master/src/main.c:108` ("#if defined(CONFIG_BOARD_ALP_E1M_AEN801_M55_HP) || defined(CONFIG_BOARD_ALP_E1M_AEN803_M55_HP)").
Rebuilt clean after the fix; the sibling AEN801 HE/HP targets, unaffected
by the change (their own macro branch is untouched), were also rebuilt to
confirm no regression.

Every newly-declared AEN803 scenario, plus the two twins, was built
locally with the same twister invocation the workflow step uses
(`ZEPHYR_BASE=/home/caner/zephyr`, `hal_alif` as an extra module): 66
AEN803 configurations selected across `examples/aen`. First pass: 65 built,
1 errored (`aen-dualcore-he-master`'s `hp_peer`, above). After the fix: 66
built, 0 failed, 0 errored.
