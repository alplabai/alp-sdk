### Fixed — AEN bench builds default to AEN803, and refuse a board overlay that would silently not apply (#2094)

Zephyr auto-applies a per-app devicetree overlay only when its filename
matches the fully-qualified board target with `/` replaced by `_`, and
`scripts/bench/aen/build.sh` never forces `EXTRA_DTC_OVERLAY_FILE`. So an app
that ships overlays for a *different* target built with **no overlay applied
at all** and said nothing about it — the operator got a binary shaped for the
wrong module, and the first symptom was a peripheral misbehaving on real
silicon. `scripts/bench/aen/bench-env.sh`'s `AEN_BOARD` note already
described this hazard; nothing enforced it.

The build now checks the app's `boards/` directory before invoking `west`
(`scripts/bench/aen/build.sh:91` ("BOARD_STEM=")) and refuses when that
directory holds overlays but not the one this board target would pick up
(`scripts/bench/aen/build.sh:115`
("ships AEN board")). The refusal prints the exact
filename it expected, every overlay that *is* present, and the
`AEN_BOARD=<fully-qualified board>` override to build anyway
(`scripts/bench/aen/build.sh:122`
("refusing to build with no $label applied")).

An app with no `boards/` overlays at all still builds: there is nothing to
miss, so only a non-empty overlay set that lacks this board's file is an
error.

### Fixed — `scripts/bench/aen/bench-env.sh` repoints the `AEN_BOARD` default to E1M-AEN803, and `build.sh` gains a symmetric `.conf` guard (#2094)

Every module on the bench farm is an E1M-AEN803, not an E1M-AEN801 —
`AEN_BOARD` defaulted to AEN801 regardless, so a default no-override bench
build produced an AEN801-shaped image on AEN803 silicon. The overlay
preflight above, plus #2176/#2214's AEN803 overlay backfill across
`examples/aen/`, made the flip safe; this change makes it
(`scripts/bench/aen/bench-env.sh`, `AEN_BOARD="${AEN_BOARD:-alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he}"`).

Four `examples/peripheral-io/` apps that still carried an AEN801-only
overlay — `blink`, `pwm-led-fade`, `alp-console` (HE, this default's
target) and `drone-autopilot` (HP-only, for symmetry when a caller
overrides to the HP target) — get AEN803 twins (same PCB, same silicon,
and each one's pads sit outside the AEN803 OSPI0 set, so the AEN801 body
carries over unchanged).

A census against the resolved guard (simulate
`bench_build_require_board_qualified()` for every `examples/*/*/boards/`
directory, for both the AEN801 and AEN803 HE stems — see
`scripts/bench/aen/bench-env.sh` for the exact one-liner) separates two
groups that must not be conflated: apps **newly** refused by this repoint
(refused under AEN803, not under AEN801) vs. apps **already** refused
before and after (unrelated to the AEN801→AEN803 flip). Only
`examples/connectivity/firmware-update-log` is newly refused (both its
overlay and its `.conf`); it is knowingly left out: its `CMakeLists.txt`
gates `DTC_OVERLAY_FILE`/`EXTRA_CONF_FILE` on a literal
`BOARD MATCHES "^alp_e1m_aen801_m55_he"`, and it is the ATOC/MRAM write
path carrying a fail-closed firewall claim — it needs a bench run before a
twin ships, not a copy-paste, so it is tracked separately. Its own README
always builds it with an explicit `-b alp_e1m_aen801_m55_he/...`, never
this default, so the repoint changes nothing about that app's documented
workflow.

`aen-hp-core-smoke`, `edgeai-vision-aen`, `iot-connected-camera` and
(before this change) `drone-autopilot` are already refused before and
after: the first two and `drone-autopilot` ship only an HP-qualified
overlay with no HE sibling of either SKU, so the HE-default guard refuses
them regardless of AEN_BOARD's SKU (build with an explicit HP override);
`iot-connected-camera` ships only a V2N-qualified overlay (a different SoM
family whose filename happens to also start with `alp_e1m_`) and no AEN
overlay of any core.

The overlay preflight itself also gained a gap it did not have: a
board-qualified `.conf` is auto-applied by Zephyr's exact-filename rule
just like an overlay, but was not guarded, so an app with an AEN803
overlay and no AEN803 `.conf` would build with that `.conf` silently
dropped (`scripts/bench/aen/build.sh`,
`bench_build_require_board_qualified()`). `build.sh` now runs the same
check for both extensions through one shared helper, scoped to
`alp_e1m_*`-prefixed stems only — the pre-existing overlay loop counted
ANY `*.overlay` file, which is a rare false-positive for `.overlay` but a
COMMON one for `.conf` (several `aen-cc3501e-*` bench apps ship only a
`native_sim_native_64.conf`, no AEN `.conf` of any kind, and must keep
building clean).

### Fixed — `scripts/check_example_portability.py`'s bare-board-name rationale contradicted its own hard-error function (#2094 review)

The module docstring's item (g), rewritten in this PR, claimed Zephyr's
board-overlay auto-apply "picks up BOTH the bare board name and the
fully-qualified one (they merge)" for a `board.yaml`-less bench dir, and
that this check was scoped to `board.yaml`-bearing examples only —
directly contradicting `check_overlay_qualified()`'s own docstring three
lines away, which says the opposite (applies to every example, a bare
name drops silently everywhere). Read against Zephyr 4.4.1's
`cmake/modules/dts.cmake` (`zephyr_file(CONF_FILES ...)`) and
`cmake/modules/extensions.cmake`'s `zephyr_build_string(... MERGE)`: with
`BOARD_QUALIFIERS` non-empty, `MERGE` only adds a revision-less variant
that still carries every qualifier segment — it never emits the bare,
unqualified board name as a candidate. So `check_overlay_qualified()` was
right and the module docstring was wrong; corrected (g) to match, and
removed the false "scoped to `board.yaml`-bearing only" distinction from
(f) — both hard errors run over all of `examples/**` and `tests/**`.
`tests/scripts/test_check_example_portability.py`'s
`test_bench_example_with_no_board_yaml_is_also_checked` docstring already
matched reality and needed no change on inspection.

### Verified — every `apps.txt` app builds identically-shaped for AEN801 and AEN803 (#2094)

Independent of the repoint above: all 23 apps in `scripts/bench/aen/apps.txt`
were built directly with `west build`, the same flags `build.sh` uses, once
for `alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he` and once for
`alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he`. All 23 build on both
targets. `aen-npu-inference-alif` needs a Vela compiler, which `build.sh`
does not supply: without one it fails the same way on both targets
(`ERROR: vela not found at vela`), and with `-DAEN_NPU_VELA=<venv>/bin/vela`
it builds on both. For every app, the pair was then compared three ways:

- **`zephyr.dts`**: after stripping the `/* in <file>:<line> */` source-location
  comments, which name the board tree each node came from, the only
  differences are the root `model` and `compatible` strings. No node,
  register value or property differs, OSPI0 included. This matches the
  issue's own prediction that a safe repoint changes nothing observable
  until #915 lands OSPI0 driver support.
- **`.config`**: only the board-identity symbols differ: `CONFIG_BOARD`,
  `CONFIG_BOARD_TARGET`, and `CONFIG_BOARD_ALP_E1M_AEN80{1,3}_M55_HE[...]`.
- **`zephyr.bin`, byte for byte**: 3 apps are identical, and the other 20
  differ in exactly one byte. That byte is the `1` to `3` of the embedded
  `alp_e1m_aen80{1,3}_m55_he` board-name string. Image sizes are equal in
  all 23.

None of `apps.txt`'s 23 apps is one of the four `examples/peripheral-io/`
apps backfilled with an AEN803 twin above, so this comparison and that
backfill are orthogonal evidence for the same repoint.
