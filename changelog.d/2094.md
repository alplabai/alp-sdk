### Fixed — AEN bench builds default to AEN803, and refuse a board overlay that would silently not apply (#2094)

Zephyr auto-applies a per-app devicetree overlay only when its filename
matches the fully-qualified board target with `/` replaced by `_` (the full
stem; #2235 found Zephyr also accepts a second, SHORT stem -- see
`changelog.d/2235.md`), and `scripts/bench/aen/build.sh` never forces
`EXTRA_DTC_OVERLAY_FILE`. So an app
that ships overlays for a *different* target built with **no overlay applied
at all** and said nothing about it — the operator got a binary shaped for the
wrong module, and the first symptom was a peripheral misbehaving on real
silicon. `scripts/bench/aen/bench-env.sh`'s `AEN_BOARD` note already
described this hazard; nothing enforced it.

The build now checks the app's `boards/` directory before invoking `west`
(`scripts/bench/aen/build.sh:274` ("$APP_DIR/boards")) and
refuses when that directory holds overlays but not the one this board target
would pick up (`scripts/bench/aen/build.sh:257`
("ships AEN board $label files, but none for")). The refusal prints the exact
filename it expected, every overlay that *is* present, and the
`AEN_BOARD=<fully-qualified board>` override to build anyway
(`scripts/bench/aen/build.sh:268`
("refusing to build with no $label applied")). #2235 later extended this
check to board-qualified `.conf` files through one shared function
called once per extension,
`scripts/bench/aen/build.sh:203`
("bench_build_require_board_qualified() {"), then refined the guard further
-- see `changelog.d/2235.md` for what changed.

An app with no `boards/` overlays at all still builds: there is nothing to
miss, so only a non-empty overlay set that lacks this board's file is an
error (of any kind, at the time -- #2235 narrowed this to
`alp_e1m_*_rtss_h[ep]`-shaped sets plus this board's own bare and
board+SoC near-miss names, so a `native_sim`-only overlay set no longer
counts; see `changelog.d/2235.md`).

**The `AEN_BOARD` default is now repointed to E1M-AEN803, closing the issue.**
Every module on the Alp Lab AEN bench farm is an E1M-AEN803. That rests on
the maintainer's account, not on anything readable from silicon (the same
part number is on both SKUs), as
`metadata/e1m_modules/E1M-AEN803.yaml:203`
("so it rests on the maintainer's word") records. The repoint
waited on the guard above landing first, then on #2214 backfilling every
`examples/aen/*` overlay that previously existed only for AEN801 with an
AEN803 twin, so the guard does not strand most of `apps.txt`. The default is
now
`scripts/bench/aen/bench-env.sh:105` ("alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he"),
confirmed a real, generated board target at
`zephyr/boards/alp/e1m_aen803_m55_he/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.yaml:4`
("identifier: alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he") since #2084;
`AEN_BOARD` still overrides for genuine AEN801 or off-default work.

**Verification: every `apps.txt` app built for both targets.** All 23 apps in
`scripts/bench/aen/apps.txt` were built directly with `west build`, the same
flags `build.sh` uses, once for
`alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he` and once for
`alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he`. All 23 build on both
targets. `aen-npu-inference-alif` needs a Vela compiler, which `build.sh`
does not supply: without one it fails the same way on both targets
(`ERROR: vela not found at vela`), and with `-DAEN_NPU_VELA=<venv>/bin/vela`
it builds on both. For every app, the pair was then compared three ways:

- **`zephyr.dts`**: after stripping the `/* in <file>:<line> */` source-location
  comments, which name the board tree each node came from, the only
  differences are the root `model` and `compatible` strings. No node,
  register value or property differs, OSPI0 included. This matches the
  issue's own prediction that a safe repoint changes nothing observable
  until #915 lands OSPI0 driver support.
- **`.config`**: only the board-identity symbols differ: `CONFIG_BOARD`,
  `CONFIG_BOARD_TARGET`, and `CONFIG_BOARD_ALP_E1M_AEN80{1,3}_M55_HE[...]`.
- **`zephyr.bin`, byte for byte**: 3 apps are identical, and the other 20
  differ in exactly one byte. That byte is the `1` to `3` of the embedded
  `alp_e1m_aen80{1,3}_m55_he` board-name string. Image sizes are equal in
  all 23.

`scripts/bench/aen/README.md` and the `build.sh` overlay-name comment are
updated to match the new default;
`scripts/bench/aen/README.md:171` ("Qualified board target.") and
`scripts/bench/aen/README.md:223` ("west build -b alp_e1m_aen803_m55_he")
now show the AEN803 target.
`scripts/bench/aen/aen-flowc-itcm.conf:21`
("boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.conf") named only the
AEN801 file at the time: `examples/peripheral-io/alp-console` had no
AEN803-qualified twin of that board-scoped `.conf`, so an app built under the
new AEN803 default without an `AEN_BOARD` override would have tripped
`build.sh`'s own overlay preflight (it also shipped only an AEN801
`.overlay`). #2235 resolved that gap: `alp-console` now ships both twins —
`boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.conf` and the matching
`.overlay` — so a build under the AEN803 default no longer trips the guard.
