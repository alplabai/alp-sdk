### Fixed — AEN bench scripts now default to AEN803, matching the real bench farm (#2094)

Zephyr auto-applies a per-app devicetree overlay only when its filename
matches the fully-qualified board target with `/` replaced by `_`, and
`scripts/bench/aen/build.sh` never forces `EXTRA_DTC_OVERLAY_FILE`. So an app
that ships overlays for a *different* target built with **no overlay applied
at all** and said nothing about it — the operator got a binary shaped for the
wrong module, and the first symptom was a peripheral misbehaving on real
silicon. `scripts/bench/aen/bench-env.sh`'s `AEN_BOARD` note already
described this hazard; nothing enforced it.

The build now checks the app's `boards/` directory before invoking `west`
(`scripts/bench/aen/build.sh:65` ("BOARD_OVERLAY=")) and refuses when that
directory holds overlays but not the one this board target would pick up
(`scripts/bench/aen/build.sh:74`
("ships board overlays, but none for")). The refusal prints the exact
filename it expected, every overlay that *is* present, and the
`AEN_BOARD=<fully-qualified board>` override to build anyway
(`scripts/bench/aen/build.sh:81`
("refusing to build with no overlay applied")).

An app with no `boards/` overlays at all still builds: there is nothing to
miss, so only a non-empty overlay set that lacks this board's file is an
error.

**The `AEN_BOARD` default is now repointed to E1M-AEN803, closing the issue.**
Every module on the AEN bench (`e1m-aen-evk-01/02/03`) is an E1M-AEN803, a
claim that `metadata/e1m_modules/E1M-AEN803.yaml:203`
("so it rests on the maintainer's word") says outright rests on the
maintainer's account, not on anything readable from silicon. The repoint
waited on the guard above landing first, then on #2214 backfilling every
`examples/aen/*` overlay that previously existed only for AEN801 with an
AEN803 twin, so the guard does not strand most of `apps.txt`. The default is
now
`scripts/bench/aen/bench-env.sh:105` ("alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he"),
confirmed a real, generated board target at
`zephyr/boards/alp/e1m_aen803_m55_he/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.yaml:4`
("identifier: alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he") since #2084;
`AEN_BOARD` still overrides for genuine AEN801 or off-default work.

**Verification: every `apps.txt` app built for both targets.** All 23 apps in
`scripts/bench/aen/apps.txt` were built directly with `west build`, the same
flags `build.sh` uses, once for
`alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he` and once for
`alp_e1m_aen803_m55_he/ae822fa0e5597ls0/rtss_he`. 22 of 23 succeeded on both
targets; for every one of those 22, `zephyr.dts` differs from its AEN801
build only in the board `model`/`compatible` strings and the source-file
comments naming which board tree a node came from -- no register value, node,
or property differs, OSPI0 included, matching the issue's own prediction that
a safe repoint changes nothing observable until #915 lands OSPI0 driver
support. `.config` differs only in the 4 board-identity `CONFIG_BOARD*`
symbols, and `zephyr.elf`'s `text`/`data`/`bss` are byte-identical between the
two targets for every app. The 23rd, `aen-npu-inference-alif`, fails
identically on both targets (`ERROR: vela not found at vela`, a missing local
Vela toolchain) -- a pre-existing environment gap unrelated to the board
target, not a regression from this change.

`scripts/bench/aen/README.md` and the `build.sh` overlay-name comment are
updated to match the new default;
`scripts/bench/aen/README.md:169` ("Qualified board target.") and
`scripts/bench/aen/README.md:218` ("west build -b alp_e1m_aen803_m55_he")
now show the AEN803 target.
`scripts/bench/aen/aen-flowc-itcm.conf:20`
("boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.conf") still names an
AEN801-only file on purpose: `examples/peripheral-io/alp-console` has no
AEN803-qualified twin of that board-scoped `.conf`, so the comment stays
accurate. That app is not in `apps.txt` and is not part of the daily bench
default; if it is ever built under the new AEN803 default without an
`AEN_BOARD` override, `build.sh`'s own overlay preflight refuses it (it also
ships an AEN801-only `.overlay`), the same loud failure the guard above was
built for.
