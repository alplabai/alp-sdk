### Fixed — `alp_template.py` refuses an inapplicable numeric bound instead of crashing with a bare `TypeError` (#1916)

`scripts/alp_template.py`'s `_check_constraints()` compared a parameter's
value against `constraints.minimum` / `constraints.maximum` without first
checking that the bound applies to the parameter's declared `type`.

`$defs/parameter` in `metadata/schemas/template-catalog-v1.schema.json` does
not cross-reference `constraints` against `type` at all: `type` is exactly
one of `string` / `integer` / `boolean` / `enum`, and `minimum` / `maximum`
are plain `"type": "integer"` bounds coupled to none of them. So a record
like

```json
{"name": "knob", "type": "string", "default": "a", "constraints": {"minimum": 5}}
```

validates clean against the shipped schema (`jsonschema` 4.26.0), and then
reached `value < constraints["minimum"]` as `"a" < 5`:

```
TypeError: '<' not supported between instances of 'str' and 'int'
```

a bare `TypeError` past every `except TemplateError` both callers of this
module declare — surfacing to the user as an internal failure on a document
nothing upstream refused.

`_check_constraints()` now raises a curated `ParameterError` naming the
template, the parameter, its value, its declared type and the inapplicable
bound, before it ever compares the two:

```
fixture-tpl: knob='a' is type 'string'; constraints.minimum (5) only applies to type 'integer'
```

`boolean` is refused alongside `string` and `enum` deliberately: `bool < int`
never raises, so there is no crash, but a bound on a boolean knob is
meaningless either way. The guard reads the DECLARED `spec["type"]` rather
than `isinstance(value, int)` — `bool` is an `int` subclass, so the
isinstance form would silently let the boolean case through.

This closes a cross-repo divergence, not just a crash. tan-cli fixed its own
copy of this function in tan-cli#1087 (PR tan-cli#1123); until now the two
implementations agreed on well-formed catalogs and disagreed on malformed
ones, which nothing on either side gated — tan-cli's planner-parity gate only
exercises well-formed catalogs.

`constraints.enum` is the same inapplicability class (the schema forces
`enum` items to strings, so a `type: integer` parameter can never satisfy
one, and the resulting error blames the value rather than the bound). It is
LEFT OPEN on purpose, matching tan-cli's own deliberate choice: it fails
loudly rather than crashing, and closing it on one side only would re-open
the divergence in the other direction.

No behaviour change for any shipped template: every constrained parameter in
`metadata/templates/catalog-v1.json` already pairs its bound with the right
type (`enum` on `enum`-typed knobs, `minimum` on `integer`-typed knobs), and
`test_no_shipped_catalog_parameter_carries_an_inapplicable_bound` locks that
in so a future catalog edit fails in the test suite with the offender named
rather than at a user's `alp generate`.

`tests/scripts/test_alp_template.py` gains, parametrized over
`string`/`enum`/`boolean` x `minimum`/`maximum`:
`test_a_numeric_bound_on_a_nonint_parameter_is_schema_valid` (asserts the
premise against the real shipped schema — if a future schema revision adds
the cross-reference, it goes red and the guard's rationale needs revisiting)
and `test_a_numeric_bound_on_a_nonint_parameter_raises_a_curated_error`. Plus
`test_a_numeric_bound_on_an_integer_parameter_is_still_enforced` (the guard
must not swallow the bound it protects) and
`test_render_refuses_an_inapplicable_bound_instead_of_crashing`, which drives
the whole `render()` path. Mutation-checked: dropping the guard turns six
cases red, and swapping `spec["type"] != "integer"` for `not isinstance(value,
int)` turns exactly the two `boolean` cases red.
