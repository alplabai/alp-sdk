### Fixed — `alp_template.py` crashed with a bare `TypeError` on a schema-valid catalog record declaring `constraints.minimum`/`maximum` on a non-integer parameter (#1916)

`_check_constraints` (`scripts/alp_template.py:267`) compared a parameter's
`default` against `constraints.minimum`/`maximum` without first checking the
bound applies to the parameter's declared `type`. A **schema-valid**
`templates[].parameters[]` record —

```json
{"name": "knob", "type": "string", "default": "a", "constraints": {"minimum": 5}}
```

— died with `TypeError: '<' not supported between instances of 'str' and
'int'`, surfacing an internal crash on input the tooling itself said was
acceptable.

`_check_constraints` now refuses `minimum`/`maximum` on any non-`integer`
type — string, enum **and** boolean (boolean deliberately: `bool < int`
never raises, so there is no crash, but the bound is still meaningless) —
and raises the same curated `ParameterError` every other check in this
function already uses (`scripts/alp_template.py:281-285`, "only applies to
type 'integer'"), matching the shape tan-cli's own fix settled on
(tan-cli#1123) so the two implementations agree on this input class again.

`metadata/schemas/template-catalog-v1.schema.json`'s `$defs/parameter` gained
an `if`/`then` pair (the same construct the record already uses for
`status: preview` requiring `note`) rejecting `constraints.minimum`/`maximum`
on a non-`integer` `type` at the schema level too, so the crashing record
above no longer validates in the first place.

`constraints.enum` on a non-`string`-coerced type (e.g. `integer` +
`constraints.enum`, unsatisfiable rather than crashing) is the same
inapplicability class the issue also flagged — left out of scope here as
lower priority; tracked in the issue for follow-up.
