### Added — `flash_ospi_alif.c` implements `read_jedec_id()`; everything else stays honestly unimplemented (#915)

`flash_driver_api` was `NULL` at this driver's `DEVICE_DT_INST_DEFINE` --
`read`, `write`, `erase`, and `get_size` were all unreachable through the
standard Zephyr flash API. With #2041's pinctrl fix landing alongside this
change, the driver's init path can now actually reach a populated part, so
this batch implements the one op with a live bench capture to write
honestly against: `ospi_alif_read_jedec_id()`, gated behind
`CONFIG_FLASH_JESD216_API` (which `OSPI_ALIF` now `select`s
`FLASH_JESD216` for). It polls `alif_hal_ospi_irq_handler()` directly
(bounded by `OSPI_ALIF_JEDEC_POLL_ITERATIONS`, failing `-ETIMEDOUT` rather
than hanging) because this driver does not wire an NVIC `IRQ_CONNECT` for
OSPI0 — safe because `alif_hal_ospi_transfer()` unmasks `OSPI_IMR`
unconditionally and `OSPI_ISR` reflects live FIFO state independent of
whether the interrupt line reaches the NVIC.
`examples/aen/aen-ospi-regcheck` now calls the standard
`flash_read_jedec_id()` and gates its `RESULT PASS` on the ISSI
manufacturer byte, printing the JEDEC bytes read back.

**Left unimplemented, on purpose, and why** (each cites what capture would
close it, per `flash_ospi_alif.c`'s own provenance block):

- **`read()`** (offset-based Read Data, opcode 0x03/0x0B): needs a live
  capture of an *addressed* transfer. `alif_hal_ospi_transfer()`'s
  `tx_total_cnt` derivation for a nonzero `addr_len` looks internally
  inconsistent (4 bytes for `OSPI_ADDR_LENGTH_24_BITS`, 2 for
  `OSPI_ADDR_LENGTH_32_BITS` — `ospi_hal.c`) and is unverified here, unlike
  the `addr_len=0` case the bench capture actually exercises.
- **`write()` / `erase()`**: need WREN (0x06) + status-poll (0x05) +
  Page-Program/Sector-Erase opcodes — none bench-proven. OSPI0 is SHARED
  with the HyperRAM device (CS0) and carries a live XiP window reservation
  at `0xA0000000`; a wrong factory-mode or erase sequence risks the shared
  bus, not just this device. Explicitly out of scope per the driving
  instructions for this change.
- **`get_size()`**: the controller binding (`snps,designware-ospi.yaml`)
  carries no DT size property — capacity is a per-populated-part metadata
  fact (`metadata/e1m_modules/E1M-AEN803.yaml`
  `on_module.ospi_memories.ospi0.capacity_mbit`), not a controller-node
  fact. Wiring it needs a new DT property, out of scope this batch.
- **`get_parameters()`**: would describe `write_block_size`/`erase_value`
  for ops this driver does not implement — publishing invented values for
  an unimplemented write/erase path is worse than leaving it `NULL`.

Also newly discovered and worth recording: `alif_hal_ospi_receive()` is an
unimplemented stub in the vendored hal_alif library
(`modules/hal/alif drivers/ospi/src/ospi_hal.c`) -- it returns
`OSPI_ERR_NONE` without touching any buffer, so it cannot be used for any
future op either; any future flash op on this driver needs
`alif_hal_ospi_transfer()` (or `_send()`) plus the polling pattern
`ospi_alif_read_jedec_id()` establishes here.
