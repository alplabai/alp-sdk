### Fixed — every AEN preset claimed 32 MiB of HyperRAM the module does not carry (`memory.dram_mbit: 256`)

No currently shipping E1M-AEN SKU populates *any* memory on the OSPI bus —
neither the Macronix `MX25UM25645GXDI00` NOR on OSPI0 CS0 nor the Winbond
`W958D8NBYA5I` HyperRAM on CS1. All six presets nevertheless carried
`memory.dram_mbit: 256`, derived from the HyperRAM's `capacity_mbit` under a
comment asserting it was "populated on every AEN BOM variant". That is a
customer-facing claim of 32 MiB of external RAM on a module that has none,
and the preset was the last place in the tree still making it: the generated
board DTS, `zephyr/kconfigs/vendor-alif-peripherals.kconfig:961`, and
`docs/bring-up-aen.md:44` ("SoM's OSPI memories are NOT populated")
all already documented MRAM-only.

Both capacities on `E1M-AEN301/401/501/601/701/801` are now `0`, and the
population of each part is stated where population belongs — `assembled:
false` on `ospi_memories.ospi0`, `.ospi1` and `hyperram`
(`metadata/e1m_modules/E1M-AEN801.yaml:60-62` (`assembled:      false`)),
replacing the `optional` ("assembled per BOM variant") that had left the
question open. `capacity_mbit` stays: it is the designed-in part's capacity,
not a capacity the module carries, so a populated variant would flip one flag
rather than re-derive the bus.

`0` is deliberately not `TBD`. `0` is a resolved fact ("this SKU populates
none"); `TBD` is an open question ("nobody has written the capacity down
yet"), which is `E1M-NX9101`'s state and must stay distinguishable from this
one — see `metadata/schemas/som-preset-v1.schema.json:120` ("is a RESOLVED fact and").
Both `dram_mbit` and `flash_mbit` therefore relax from `minimum: 1` to
`minimum: 0`.

### Schema — `on_module.hyperram` gains `assembled:`

The `hyperram` `$def` is `additionalProperties: false` and had no `assembled`
property at all, so the schema could not express an unpopulated HyperRAM even
though its `ospi_memory` sibling could. Added with the same three-state shape
(`true` / `false` / `"optional"`) that
`metadata/schemas/som-preset-v1.schema.json:320` ("Population status: true (default), false (DNI)")
already carries for OSPI memories.

### Added — `validate_metadata.py` now BINDS `memory:` to the population facts it is derived from

Every AEN preset states the derivation in prose —
`metadata/e1m_modules/E1M-AEN801.yaml`: *"dram_mbit  <- 0: on_module.hyperram
is `assembled: false`"* — and for one commit a comment was the whole of the
enforcement. Proven by mutation: setting `hyperram.assembled: true` while
leaving `dram_mbit: 0` was **fully green** — `validate_metadata.py` rc=0 AND
`pytest tests/scripts/` rc=0. `dram_mbit: 128` against an unpopulated part
left only one hardcoded string assertion red. A derivation nothing binds is
not a derivation; it is a comment that happens to be true today.

`_check_som_memory_population` closes it. `memory.dram_mbit` is decided by
`on_module.hyperram`, `memory.flash_mbit` by every
`on_module.ospi_memories[]` entry:

- every relevant part `assembled: false` ⇒ the figure MUST be `0` — not
  `TBD` (which re-opens a question the preset just closed) and not a
  capacity;
- any relevant part populated ⇒ the figure MUST NOT be `0`, and when every
  fitted part declares an integer `capacity_mbit` it must equal their sum;
- `assembled:` absent reads as **populated**, per the schema's own default
  (*"Population status: true (default)"*) — never as "unknown";
- `assembled: "optional"` is BOM-variant dependent, so only the `0`
  contradiction is decidable, not the exact capacity;
- a preset declaring neither block is **skipped**: V2N/V2M's LPDDR4X + eMMC
  and E1M-NX9101's open capacities state no population fact here, and
  inventing one to bind against would be inventing a hardware value.

JSON Schema cannot reach across `on_module` into `memory:` (nor sum a sibling
object's values), so this layer is the only one that can hold it.
`tests/scripts/test_validate_metadata_som_memory_population.py` pins the same
rules independently, so deleting the check reddens something other than the
check's own file. Mutation-proved both ways — 13 mutations of
`E1M-AEN801.yaml`, 10 RED and 3 GREEN controls. RED: the fully-green
`assembled: true` + `dram_mbit: 0`; the same for `ospi0` and for `ospi1`; a
capacity against an unpopulated part, both figures; `TBD` against an
unpopulated part, both figures; `assembled: optional` + `0`; a fitted part
whose `dram_mbit` disagrees with its own `capacity_mbit`; the `assembled:`
key deleted outright. GREEN: the pristine preset, and a fitted part matching
its capacity on either figure. The `assembled: true` + `dram_mbit: 0`
mutation now also turns `pytest tests/scripts/` red, which it did not before.

### Changed — the portability matrix distinguishes "resolved: none" from an unstated capacity, on BOTH figures

`scripts/gen_portability_matrix.py`'s `notes_for()` only tagged a positive
`dram_mbit`, so correcting the six AEN presets to `0` would have replaced a
false "256 Mbit DRAM" note with silence — indistinguishable from
`E1M-NX9101`'s genuinely-unknown `TBD`. `0` now renders `no external DRAM`;
`TBD` still renders nothing, because a Notes cell has nothing true to say
about it.

That fix landed on `dram_mbit` alone, which reproduced the very defect it
describes one column over: `notes_for()` never read `flash_mbit`, so
`E1M-AEN801` (`0`, resolved: MRAM-only) and `E1M-NX9101` (`TBD`, open)
rendered **identically** — on the figure that decides storage and MCUboot
partitioning. `flash_mbit: 0` now renders `no external flash` alongside it,
and `docs/portability-matrix.md` is regenerated: all six AEN rows gain the
tag, `E1M-NX9101` gains nothing. A *positive* `flash_mbit` stays untagged;
printing eMMC densities is an editorial addition to the cell, not a
distinction anything was collapsing.

### Fixed — the generated board DTS still hedged "BOM-optional", contradicting the corrected presets

The hedge was deleted from the presets and from `docs/bring-up-aen.md:44` but
not from the customer-facing generated devicetree: `scripts/gen_zephyr_board.py`
kept emitting *"are BOM-optional and NOT populated on the current batch"* and
*"not populated on this batch"* into both AEN801 board DTS headers, so the DTS
and the docs disagreed about the same hardware. The generator now emits *"NOT
populated on ANY AEN SKU (`assembled: false` in every
metadata/e1m_modules/E1M-AEN*.yaml, and memory.dram_mbit / .flash_mbit are 0)
… this is not a per-batch or per-BOM-variant caveat"*, and
`e1m_aen801_m55_hp` / `e1m_aen801_m55_he` are regenerated.
`zephyr/boards/alp/e1m_aen601_m55_hp/`'s DTS carried its own variant of the
hedge (*"BOM-optional and not assumed populated"*) and is corrected by hand:
that board sits in `tests/scripts/test_gen_zephyr_board.py`'s `NOT_EMITTABLE`
set (`metadata/socs/alif/ensemble/e6.json` has no `zephyr_peripherals_dtsi`),
so no generator emits it and regenerating would never have reached it.

**No behaviour change.** Nothing reads `memory.dram_mbit` or
`memory.flash_mbit` except that one Notes cell, and nothing reads
`ospi_memories[].assembled` or `hyperram.assembled` outside the new check —
the `assembled == "optional"` skip at `scripts/alp_orchestrate/slugs.py:112`
(`dev.get("assembled") == "optional"`) applies only to `i2c_devices[]`. The
one `memory` key a consumer *does* read is a DIFFERENT block: per-core
`cores.<id>.memory` (`heap_kib` / `stack_kib` / `isr_stack_kib`), copied onto
the `Slice` at `scripts/alp_orchestrate/loader.py:559`
(`memory=dict(entry.get("memory") or {}),`) and read back at
`scripts/alp_orchestrate/validate.py:238`
(`heap_kib = (slice_.memory or {}).get("heap_kib")`) and
`scripts/alp_orchestrate/kconfig.py:1300`
(`mem = slice_.memory or {}`). That
block never carries `dram_mbit` or `flash_mbit`, so it is not evidence for
the no-consumer claim and must not be cited as though the SoM-preset
`memory:` block flowed through it.

### Known hazard — `partition.py` will still size a partition against an unfitted part

`scripts/alp_orchestrate/partition.py::_resolve_flash_device` keys off
`on_module.ospi_memories[].capacity_mbit` and ignores `assembled:`. Measured
after this change: `_resolve_flash_device("ospi0", <E1M-AEN801 preset>)`
returns `size_bytes=33554432` — 32 MiB, from `capacity_mbit: 256` — on a part
whose own preset now declares `assembled: false`, and
`_known_flash_devices()` still offers `ospi0` and `ospi1` to a customer's
`storage[].flash_device:`. `assembled: false` is the declared fact a fix keys
on; `capacity_mbit` is the DESIGNED-IN part's capacity, not one the module
carries. (The earlier note that storage resolution keys off `capacity_mbit`,
*"both unchanged"*, was true but incomplete: unchanged code now contradicts
changed metadata.)

Latent, not live: no in-tree `board.yaml` names either device — the only
`flash_device:` user is
`examples/connectivity/production-deployment/board.yaml`, five entries, all
`mram_main`.

Deliberately **not** fixed here, because the fix crosses repos.
`python/tan/planner/partition.py::_resolve_flash_device` in tan-cli is a
line-for-line port of this function, and tan is the executor — a refusal
added on one side only would make alp-sdk and tan disagree about the same
`board.yaml`, which is the drift ADR-0020 exists to prevent. Both sides move
in one lockstep change (refuse on `assembled: false`, and drop the device
from `_known_flash_devices()`), or neither does. The hazard is now recorded
at the call site, so the next reader meets it before the code.
