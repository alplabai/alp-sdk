### Fixed — `e1m-aen801-a32` required `conf/machine/devkit-e8.conf`, a file no Alif layer ships (#1968)

`meta-alp-sdk/conf/machine/e1m-aen801-a32.conf` carried an active

```
require conf/machine/devkit-e8.conf       # meta-alif-ensemble @scarthgap
```

and a header describing `devkit-e8` as "the upstream-complete E8 base". There is
no such file. The public
[`meta-alif-ensemble`](https://github.com/alifsemi/meta-alif-ensemble) has one
branch, `devkit-ex-b0`, and its `conf/machine/` holds exactly
`appkit-e7.conf`, `devkit-e5.conf` and `devkit-e7.conf` — no E8 machine of any
name. So the `require` could not resolve from any branch of the layer it named,
and the MACHINE could never have parsed.

The `require` is now commented out, the same treatment the sibling
`meta-alp-sdk/conf/machine/e1m-aen701-a32.conf` already gives its own base
`require`, and the comment names the branch that actually exists rather than one
that does not:

```
#require conf/machine/devkit-e8.conf       # does not exist on meta-alif-ensemble @devkit-ex-b0 (#1968)
```

The header stops claiming an upstream-complete E8 base and says what the file
is: a **non-buildable placeholder**. That is the point of the change — the
MACHINE is not made to work, it is made honest. `bitbake` with
`MACHINE = "e1m-aen801-a32"` still does not produce an image, and the file now
says so at the top instead of reading as a working target whose one missing
piece is a layer you forgot to clone. A `require` of a missing file errors only
when that MACHINE is selected, so nothing else in the layer parses differently
before or after.

Selecting it does behave differently, though, and the conf now states that cost
in place rather than leaving it for someone to discover. With no missing file to
trip over, `e1m-aen801-a32.conf` **parses**. Nothing in it sets a tune, a
`PREFERRED_PROVIDER_virtual/kernel` or a kernel image type, and no base supplies
them, so `MACHINE = "e1m-aen801-a32"` is expected to fail later and less
legibly — in bitbake's parse / dependency resolution, on an unset tune (no
`DEFAULTTUNE`, empty `TARGET_ARCH`) and an unprovided `virtual/kernel` — instead
of on a clear "devkit-e8.conf not found". Expected, not observed: no bitbake run
has been performed against this MACHINE.

A louder failure would be better than that, but a machine conf cannot carry one.
`.conf` files are read by bitbake's ConfHandler, which accepts only assignments,
`include`, `require`, `export`, `unset` and `addpylib`; an anonymous
`python () { bb.fatal(...) }` is BBHandler syntax (`.bb` / `.bbclass`) and
ParseErrors here — pointing at a syntax error in alp-sdk's own file, a worse
misdirection than the tune error it was meant to replace. So the prose in the
conf is the record, and there is no guard.

The A32 does now boot: on 2026-09-05 Linux 6.12.6 reached a live shell on the
Alif Ensemble E8 (AE822) Cortex-A32 on two E1M-AEN803 modules, over the chain
Secure Enclave -> TF-A BL32 (SP_MIN, AArch32 Secure World) -> Linux as BL33 —
no BL1/BL2/BL31 and no U-Boot, kernel XIP from MRAM, kernel RAM in on-chip SRAM
(#1972). That first light was done with hand-built artefacts — TF-A, kernel and
a statically-linked busybox cramfs — flashed directly, not through any Yocto
layer, and the six `ALIF_CONSOLE_*` TF-A knobs it used are a local patch to the
vendor tree (#1979), so the boot is not reproducible from a clean checkout.

None of that makes this MACHINE buildable. No bitbake or Yocto build has ever
been run against `MACHINE = "e1m-aen801-a32"`; no base machine exists to supply
the cortexa32 tune, `PREFERRED_PROVIDER_virtual/kernel`, the kernel image type,
the defconfig + dtb, TF-A or the serial console (#1968, #1971); and the rootfs
that booted is a hand-rolled cramfs, not an `alp-image-*`. The file stays a
non-buildable placeholder, and the expected later failure described above stands
— still expected, not observed.
