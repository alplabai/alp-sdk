### Fixed — the SN65DSI83 bridge recovers by itself after it resets to its defaults (panel black, backlight on) (#2815)

On the bench (E1M-AEN803 + Riverdi RVT121) the panel went black with the backlight on while the SoC side stayed healthy (CDC200 scanning, DSI PHY locked, EN `P13_4` high): the bridge had reset itself (CSR `0x0D` `0x00`, `0x0A` `0x0A`, `0xE5` `0x3D`; healthy reads `0x01`, `0x81`, `0x00`) and its init ran only once at boot. The driver now health-checks the bridge every `CONFIG_SN65DSI83_RECOVERY_INTERVAL_MS` (default 1000, `CONFIG_SN65DSI83_RECOVERY`, default y) and, when PLL_EN is clear, the PLL is not locked or `HS_CLK_SRC` reads back different from the table, replays the same init from PLL off (ID check, CSR table, PLL start, `0xE5` clear), rate-limited to one re-init per 5 s, counted and reported with `printk` and the register values (the apps keep `CONFIG_LOG` off). `0xE5` error bits with the PLL fine are cleared and counted, and re-init only when they persist on 3 polls in a row or show on the first poll after a re-init; a replay that fails part-way writes `0x0D` = `0x00` so the next window retries. `sn65dsi83_recovery_count()` returns the counter. The recipe is published right after the ID check, before the CSR bank is written, so a boot init that fails half-way is recoverable too. When the display core hands I2C1 to another core after init (the Trace Runner with `-DTR_INPUT_NPU=ON`: the HE configures the bridge, the HP owns the controller for the camera), the display core never touches the bus again: the driver publishes its CSR table in shared SRAM (`recovery-recipe-address`, `0x0237FE00`, `TR_MEM_SN65_RECIPE`) and an `alp,sn65dsi83-recovery` node on the bus-owning core replays it from that core's own I2C driver on its own low-priority work queue, so the check cannot race the camera's transfers; a build that hands the bridge's bus away without the recipe address fails at compile time. Replay into a live video stream is bench-unverified.
