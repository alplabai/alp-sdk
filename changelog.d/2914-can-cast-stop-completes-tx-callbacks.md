### Fixed — CAN (`can_cast`) `can_stop()` and bus-off complete queued TX frames instead of dropping them (#2914)

**A blocking `can_send()` already queued when `can_stop()` or bus-off hits now wakes up.** `zephyr/drivers/can/can_cast.c` reset the TX callback queue without invoking the pending callbacks, so a `can_send()` with a NULL callback waited `K_FOREVER` on a semaphore only that callback could release. Every pending entry now completes with `-ENETDOWN` (stop) or `-ENETUNREACH` (bus-off), per the Zephyr CAN API. `can_stop()` marks the driver stopped and puts the core in reset before it runs the callbacks, bus-off is published before its flush, and `can_send()` re-checks started, bus-off and reset under the same `irq_lock` as the enqueue, so a send racing the flush fails with `-ENETDOWN` or `-ENETUNREACH` instead of queueing a frame nothing completes (not yet exercised on silicon). A single-shot frame that loses arbitration now reports `-EBUSY` instead of the positive status `1` (callers testing `ret < 0` counted it as sent), and `can_recover()` counts its microsecond budget down with the saturating helper so a timeout that is not a multiple of 100 us no longer wraps and polls forever. The driver API struct is declared with `DEVICE_API(can, ...)`.
