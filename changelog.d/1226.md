### Fixed — BRD_I2C (RIIC8) pinctrl on both Zephyr CM33 boards omits `bias-pull-up`, so SCL/SDA can't idle high (#1226)

Both `e1m_v2n101_m33_sm` and `e1m_v2m101_m33_sm` mux BRD_I2C (RIIC8, P06/P07)
without enabling the RZ/V2N pinctrl's internal pull-ups. The ALP carrier has
no external pull-ups on this bus, so the lines float and the bus never
reaches a valid idle-high state -- on Linux this shows up as `i2c i2c-8: SCL
is stuck low, exit recovery` with nothing ACKing, including the ACT88760 at
0x25/0x26 that powers the SoC doing the scan. The Zephyr CM33 pinctrl was the
one place this bus's pull-ups were still missing: the Linux carrier
devicetree (`meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-x-evk.dtsi`)
already enables `bias-pull-up` on its `i2c8_pins` node, and on
`i2c0_pins`/`i2c1_pins`/`i2c6_pins`/`i2c7_pins` for the same reason.

`bias-pull-up;` is added inside the inner `i2c8-pinmux` child node of both
boards' `alp_e1m_v2n101_m33_sm-pinctrl.dtsi` and
`alp_e1m_v2m101_m33_sm-pinctrl.dtsi` -- the RZ/V2N pinctrl binding's
`bias-pull-up` allowlist entry lives on the child-binding node, not the
parent `i2c8_pins` node. No other I2C pinctrl group exists in either file;
this is the only bus these two boards currently mux.

**Not bench-verified.** Both trees build and the generated devicetree
confirms the property reaches `R_IOPORT_PinCfg` (`DT_N_S_pinctrl_S_i2c8_S_i2c8_pinmux_P_bias_pull_up`
== 1), but this has not been flashed and probed on real V2N/V2M silicon. A
bench run needs to show two things: SCL/SDA on BRD_I2C actually idling high
(scope or a bus-health scan, not just a clean build), and at least one device
ACKing -- the ACT88760 at 7-bit `0x25`/`0x26` is the useful probe target,
since it powers the SoC running the scan and is unquestionably present on
every assembled unit.

**If BRD_I2C still fails to ACK after this fix, `input-enable` is the next
thing to try, not a second pass at `bias-pull-up`.** It is deliberately left
unset here. The RZ/V2N GP-port input buffer is a real, compiled-in FSP path
on this part (`BSP_FEATURE_IOPORT_SUPPORT_IEN_GP` in `bsp_feature.h`; the IEN
write in `r_ioport.c` is conditional on it and defaults to 0 when
`input-enable` is absent from the pinctrl node -- unlike `bias-pull-up`,
whose PUPD write in the same file is unconditional, which is why this fix
does not need it too). But the evidence says IEN is not what an I2C peripheral
pin needs: upstream's own `rzv2n_evk` board enables its `&i2c2` with neither
`bias-pull-up` nor `input-enable` set on the pinmux (it has external
pull-ups, which is why it omits the former; it works over I2C regardless,
which is why the latter's absence is not the blocker there). Adding
`input-enable` here without silicon evidence it is needed would be guessing
at hardware behaviour this repo does not do. The Alif E1M-AEN801 hit an
analogous omission on a different peripheral and it produced a specific,
recognisable symptom -- clean NACKs but no device ACKs at all (see
`docs/aen-bench-bringup.md`) -- which is the pattern to watch for at the
bench before reaching for `input-enable`.
