### Fixed — BRD_I2C (RIIC8) Zephyr pinctrl omitted `bias-pull-up` on both CM33 boards (#1226)

`zephyr/boards/alp/e1m_v2n101_m33_sm/alp_e1m_v2n101_m33_sm-pinctrl.dtsi` and
`zephyr/boards/alp/e1m_v2m101_m33_sm/alp_e1m_v2m101_m33_sm-pinctrl.dtsi` muxed
BRD_I2C (RIIC8, P06/P07) without `bias-pull-up`, unlike the Linux carrier DT
(`meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-x-evk.dtsi`), which
already enables the SoC internal pull-up because the ALP carrier has **no
external pull-ups** on this bus. Both Zephyr board files now match.

Confirmed before landing: the ALP carrier genuinely lacks external pull-ups
on BRD_I2C (documented in `e1m-x-evk.dtsi`'s own `i2c8_pins` comment), so
enabling the internal pull-up has no external-pull-up-in-parallel concern.
Also confirmed the Renesas RZ/V Zephyr pinctrl binding
(`renesas,rzv-pinctrl.yaml`) accepts `bias-pull-up` and the driver
(`soc/renesas/rz/common/pinctrl_rzv.h`'s `RZV_GET_PU_PD()`) programs it into
the same `pupd_reg` field the FSP/HAL layer drives — this is not a
no-op property.

**This does not resurrect BRD_I2C on the current board revision.** Bench
scanning (see issue #1226 discussion) found the bus wedged by an active sink
holding SCL low — a hardware fault confirmed by the maintainer and fixed in
the next board revision, unrelated to pull-ups. The pinctrl gap is closed on
its own merits (an I2C bus must not depend on undocumented external pulls);
it does not make BRD_I2C usable on today's boards.

**Verified:** `west build` for both
`alp_e1m_v2n101_m33_sm/r9a09g056n48gbg/cm33` and
`alp_e1m_v2m101_m33_sm/r9a09g056n48gbg/cm33` (against this tree via
`EXTRA_ZEPHYR_MODULES`) compiles clean with `bias-pull-up` present on the
`i2c8-pinmux` node in the generated `zephyr.dts`. Mutation-proofed: a
deliberate DTS syntax break in the touched line produced a `devicetree
error: ... parse error` at that exact line/file, confirming the build reads
this file; reverted before landing.
