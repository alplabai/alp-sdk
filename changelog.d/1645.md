### Fixed — six sites where a caller-, peer- or broker-controlled length was used unchecked (#1645)

The audit grouped these under "length reaches a `memcpy` or a DMA master with no
bound", which reads as six memory-corruption bugs. They are three distinct
shapes, and only some are memory-unsafe. Each is described as what it actually
is.

**Correction to the plan's own framing, worth stating because it changes
severity.** `docs/superpowers/plans/2026-08-23-unbounded-length-sweep.md` says
only one of the six is memory-unsafe and that it is unreachable in a default
build. That holds for the DEEPX site, which is behind an `OFF`-by-default CMake
option. It does **not** hold for `src/backends/jpeg/alif_hantro.c`: that backend
is added unconditionally by `zephyr/CMakeLists.txt` and registers at priority 100
for `silicon_ref = "alif:ensemble:e8"`, so it is the **active** JPEG backend on
qualified E8 boards today, with a caller-controlled stride reaching the JPEG AXI
master unchecked. The plan's own Task 1 prose says exactly that while its summary
table downgrades it.

**Unvalidated caller geometry (JPEG).** `alp_jpeg_encode()` checked only
non-NULL and non-zero width/height. A `y_stride` of `0` reached
`src/backends/jpeg/vendor/toojpeg_baseline.c`'s `yrow = y + (size_t)row *
y_stride`, aliasing every row to row 0, and emitted a structurally valid JPEG of
the wrong image with `ALP_OK`. The `max_width`/`max_height` the backends
advertise (16384 in `sw_baseline.c`) were never enforced either.
`src/jpeg_dispatch.c` now validates strides once, backend-independently —
`y_stride` non-zero and `>= width`, and for `ALP_PIXFMT_YUV420_PLANAR` with
chroma present, `u_stride`/`v_stride` `>= (width + 1) / 2` — and range-checks the
request against the selected backend's advertised maxima with
`ALP_ERR_OUT_OF_RANGE`.

`alif_hantro.c` additionally guards locally, because it is the one that reaches
hardware. Note it does **not** reject `y_stride == 0`: unlike the software
encoder, that backend correctly treats 0 as "tightly packed" through its existing
ternary. Its hazard is a non-zero but **under-sized** stride, which is used
unchecked at two separate sites — the `in_stride` derivation and the `.pitch`
assignment — and the plan cites only one of them. `_is_dma_reachable()` never
caught it because it validates only "not in TCM"; it never checks a length
against the buffer's actual allocation.

**Peer- or broker-controlled length, silently truncated — the ones a customer
actually hits.** `src/backends/rpc/yocto_uio_drv.c` clipped a peer frame over
`ALP_RPC_TX_FRAME_MAX` (1024) and dispatched it as complete; it now rejects and
drops it. `src/backends/rpc/yocto_drv.c` let `read()` truncate and left the tail
queued, misaligning every later frame; a read that fills the buffer is now
treated as a protocol error.

Worst is `src/backends/mqtt/zephyr_drv.c`. The `MIN` bounded the copy correctly —
the audit's memory-safety claim about it was rightly refuted — but the remainder
was never drained, so `remaining_payload` stayed `> 0`, every later
`mqtt_input()` returned `-EBUSY`, and the connection stopped delivering
**permanently**. The message was already PUBACKed before that happened, so the
broker will not resend it. One broker-controlled length bricks the link. The
oversized remainder is now drained off the wire, mirroring the drain the
`msg_cb == NULL` branch in the same function already performed correctly — that
asymmetry is what made this a real defect rather than an inferred one. The
truncation is reported by `LOG_WRN` rather than through the callback:
`alp_mqtt_msg_cb_t` is marked `[ABI-STABLE]` in `include/alp/iot.h`, so widening
its signature is not available here.

**Multi-input DMA over PCIe (DEEPX).** `src/yocto/inference_deepx.cpp` passed
`input_bufs[0].data()` where the struct's own comment says `Run()` needs one
pointer to the **concatenated** inputs — but `input_bufs` is
`std::vector<std::vector<uint8_t>>`, separate allocations. For any model with
more than one input, dx_rt reads `sum(size_in_bytes)` past the end of input 0 and
DMAs unrelated heap to the DX-M1. `alp_inference_deepx_open()` now refuses a
multi-input model with `ALP_ERR_NOSUPPORT`, before `input_bufs` is ever staged.

Refusing rather than writing the concatenation is deliberate: dx_rt's
concatenated layout — tensor order, per-tensor alignment, device-expected padding
— is not derivable from the headers, and nothing offline can falsify a guess, so
a hand-written concatenation would replace a loud `ALP_ERR_NOSUPPORT` with a
silent wrong-DMA indistinguishable from the bug being fixed. The comment claiming
"dx_rt concatenates multi-input models" was false and is corrected — that false
comment is why this read as intentional.

**A truncation bug found while fixing that one, and swept across its whole
class.** `shape[i]` is narrowed to the `uint16_t shape[4]` descriptor with no
bound check. `git grep -n 'shape\[i\] ='` over `src/` returns exactly three
sites: `inference_deepx.cpp`, `inference_ort.cpp` and
`src/backends/inference/tflm.cpp`. Only ORT guarded. Both others now validate at
`open()` — matching ORT's open-time gather, so a model with an unrepresentable
dimension fails at open rather than when the application later asks for a
descriptor, and `alp_inference_get_input`/`_get_output` keep their documented
status sets unchanged. `include/alp/inference.h`'s existing `ALP_ERR_NOSUPPORT`
sentence for `alp_inference_open()` is widened with the two new reasons.

The guard rejects `dim <= 0` as well as `dim > UINT16_MAX`. Checking only the
upper bound is not enough: `shape[i]` is `int64_t`, so a negative dimension
passes a `> UINT16_MAX` test and `static_cast<uint16_t>(-1)` still reports
`65535` — the caller is lied to in exactly the way the guard exists to prevent.

**Recorded, not fixed: there is no cache-maintenance primitive in this SDK.**
`alp_shmem_config_t.cacheable` offers `true` and `alp_shmem_open()` documents
that coherency is then the caller's responsibility, but the SDK gives the caller
nothing to discharge it with — no clean, no invalidate, no barrier helper — and a
tree-wide sweep of `src/` finds no `sys_cache_data_`, `arch_dcache_` or
`SCB_CleanDCache`-class call at all; every occurrence of the word "cache" under
`src/` is a dispatch-ops pointer cache. `include/alp/mproc.h` now states that
beside the field, and records that two AEN backends hand raw CPU pointers to DMA
masters with no maintenance either. Adding barriers to a DMA path without
measuring on real silicon trades a visible gap for an intermittent one, so this
needs an owner and bench time rather than a sweep commit.

**Not verified on silicon.** `alif_hantro.c` is Kconfig-gated to real E8 and
never compiles under `native_sim` — it is cross-compile-verified only. The DEEPX
path compiles nowhere in CI at all (the option is `OFF` by default and the build
only adds the file when `find_library(dxrt)` succeeds), so its fix has no
compiler behind it in either direction beyond a manual build against the real
dx_rt headers. `tests/yocto/rpc_uio_peer_length.c` is gated behind
`pkg_check_modules(open-amp libmetal)`, which is installed neither on this host
nor anywhere in CI, so it never runs — a pre-existing gap it shares with its
sibling `rpc_uio_self_close.c`, not a new one.
