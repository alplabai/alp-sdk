### Fixed — the DEEPX 0.75 V rail could stay down forever depending on P65 timing at init (#1633)

`alp_z_v2n_power_mgmt_init()` (`src/zephyr/v2n_power_mgmt.c`) armed the
`DEEPX_PWR_EN_REQ` (P65) rising-edge interrupt and registered its GPIO callback
*before* `k_work_init()` had run on the `k_work` the ISR submits to, and before
`g_pwr.initialised` was set. An edge landing between `gpio_add_callback()` and
`k_work_init()` submitted an uninitialised `k_work` (undefined behaviour); an
edge landing after `k_work_init()` but before `initialised = true` was silently
dropped by the work handler's `if (!g_pwr.initialised) return;` guard. P65 is
edge-triggered, so a dropped edge never retries and the DA9292 CH2 = 0.75 V
DEEPX rail never comes up.

`k_work_init()` and `g_pwr.initialised = true` now both complete before the
callback is registered and the interrupt is armed. Registration and arming
are themselves reordered: the callback is registered with
`gpio_add_callback()` *before* `gpio_pin_interrupt_configure_dt()` arms the
interrupt, not after. The original arm-then-register order (inherited from
before this fix, not introduced by it) left a window where the GPIO
controller could deliver an edge to a callback list that didn't contain
`v2n_pwr_irq_handler` yet — the edge is consumed by the controller and lost,
with nothing to retry it, since P65 is edge-triggered. Registering first
means the handler is always in place before the first edge can ever be
delivered, closing that window entirely.

A third failure mode neither reorder fixes: if P65 is already high when init
runs, a rising-edge interrupt never fires at all (there is no edge to see).
Init now samples the pin's level once the callback is registered and the
interrupt armed, and submits the work item directly if it is already
asserted. That submission can race a genuine edge landing at the same
instant and run the handler twice — every step it takes (programming CH2 to
a setpoint it may already hold, enabling a channel that may already be
enabled, driving P64 to a level it may already be at) is idempotent, so the
duplicate run is harmless.

`gpio_add_callback()` / `gpio_pin_interrupt_configure_dt()` failing after
`initialised` was set to `true` used to leave the module claiming to be
initialised (the top-of-function `if (g_pwr.initialised) return ALP_OK;` idempotency
check would then short-circuit every later retry) despite never having armed
the interrupt; both failure paths now reset `initialised = false` before
returning, and a `gpio_pin_interrupt_configure_dt()` failure after a
successful `gpio_add_callback()` also removes the just-added callback.

`src/zephyr/v2n_power_mgmt.c`'s guarded body (behind
`CONFIG_ALP_SDK_V2N_POWER_MGMT` + `CONFIG_ALP_SDK_V2N_SUPERVISOR` +
DT_NODE_HAS_STATUS on the two DEEPX aliases) is compiled by no board or test
in this tree today — no board.yaml/overlay in-tree publishes
`v2n-deepx-pwr-en-req`/`v2n-deepx-core-0p75-en`, so `alp_sdk.peripheral.v2n_supervisor`
(the only scenario that force-enables the V2N supervisor) still only exercises
the module's stub path. Verified this fix compiles for real via a scratch
`west build` of that native_sim app with a throwaway devicetree overlay
supplying the two aliases plus `CONFIG_ALP_SDK_CHIP_DA9292=y` and
`CONFIG_ALP_SDK_V2N_POWER_MGMT=y` (`-DCONFIG_COMPILER_WARNINGS_AS_ERRORS=y`,
matching CI) — clean build, and a deliberately injected syntax error broke
that same build with the expected `error: expected ';'` at the injected
line, confirming the harness actually compiles this code (re-verified after
the register/arm reorder, injecting at the new `gpio_add_callback()` line).
Real-silicon P65 timing (already-high vs. edge-during-init, and the
register-vs-arm window) is bench-gated; only compilation is proven here.
