### Fixed — V2N DEEPX rail: the P65 IRQ was armed before `k_work_init()` and before `initialised = true`, so the one-shot enable edge could be lost (#1633)

`alp_z_v2n_power_mgmt_init()` in `src/zephyr/v2n_power_mgmt.c` armed the
`DEEPX_PWR_EN_REQ` (Renesas pad P65) rising-edge interrupt and registered its
GPIO callback *before* the `k_work` the ISR submits to was initialised, and
before `g_pwr.initialised` was set. `DEEPX_PWR_EN_REQ` is a one-shot rising
edge driven by the A55, so an edge landing in either window was gone for good:
with `CONFIG_ASSERT=n` the system workqueue could dequeue a zero-initialised
`struct k_work` and call through a `NULL` handler, and an edge arriving during
the multi-millisecond `da9292_init` / `da9292_v2n_base_init` BRD_I2C sequence
reached the work handler only to be dropped by its
`if (!g_pwr.initialised) return;` guard. Nothing afterwards re-sampled the
*level* of P65, so a P65 already high when init ran was never observed at all.
In all three cases the DEEPX 0.75 V core rail (DA9292 VCH2) never came up, P64
(`DEEPX_CORE_0P75_EN`) stayed low for the rest of the boot, and
`alp_z_v2n_power_mgmt_init()` still returned `ALP_OK` — so the DX-M1 looked
like a PCIe fault rather than a rail fault. The realistic trigger is a CM33
restart under a running A55 (remoteproc reload), not a cold boot.

`alp_z_v2n_power_mgmt_init()` now builds the whole ISR path before anything can
fire on it: the work item at `src/zephyr/v2n_power_mgmt.c:163`
(`k_work_init(&g_pwr.work, v2n_pwr_work_handler);`), then the DA9292 base init
under the supervisor's BRD_I2C lock, then the flag at
`src/zephyr/v2n_power_mgmt.c:181` (`g_pwr.initialised = true;`), then the
callback at `src/zephyr/v2n_power_mgmt.c:186`
(`rc = gpio_add_callback(g_pwr_en_req.port, &g_pwr.cb);`), and only then the arm
at `src/zephyr/v2n_power_mgmt.c:192`
(`rc = gpio_pin_interrupt_configure_dt(&g_pwr_en_req, GPIO_INT_EDGE_RISING);`).
Callback-before-arm matches what the portable GPIO backend already does at
`src/backends/gpio/zephyr_drv.c:229-235`
(`gpio_remove_callback(s->spec.port, &s->zcb);`), including the same unwind. The
two `gpio_remove_callback()` calls that used to unwind the I2C-failure paths are
gone: no callback is registered at that point any more.

With the edge path live, P65 is level-sampled once at
`src/zephyr/v2n_power_mgmt.c:206` (`if (gpio_pin_get_dt(&g_pwr_en_req) > 0) {`)
and the rail-up work submitted from the init if the A55 is already holding it
high; a negative errno from that read falls through to the edge path rather
than submitting. Because the edge and the level sample can both submit the work
for the same one-shot request, and `da9292_v2n_m1_enable_deepx_rail()` opens by
clearing `CH2_EN` — step 1 of its documented sequence,
`include/alp/chips/da9292.h:267-272`
(`VSTEP is only writable while the channel is`) — a new `g_pwr.rail_up` flag at
`src/zephyr/v2n_power_mgmt.c:89` (`if (g_pwr.rail_up) return;`) makes the CH2
sequence run at most once, so a duplicate submit cannot drop and re-ramp a rail
the DEEPX is already running on. Only the system workqueue touches that flag.

Static fix only — the **already-high P65 / CM33-restart** path is still unproven
on silicon. Confirming it needs bench time on an `E1M-V2M101` or `E1M-V2M102`:
restart the CM33 via remoteproc while the A55 holds `DEEPX_PWR_EN_REQ` high,
then check P64 goes high and DA9292 CH2 reports power-good. The issue stays
`needs-silicon` for that.
