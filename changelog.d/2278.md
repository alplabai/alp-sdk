### Fixed — `zephyr_video` and `v2n_n44_isp` camera backends silently ignored `alp_camera_config_t::fps`, and `alif_isp_pico` did too on an IMX296 shield (#2278)

`#2276` fixed `alif_isp_pico.c`'s fps handling for its OV5647 path only;
the portable `zephyr_video` backend and the V2N N44 ISP backend still
never called `video_set_frmival()` at all -- every `<alp/camera.h>`
stream through either one ran at whatever rate the sensor's default
mode happened to power up at, no matter what an app's `cfg.fps` asked
for. Separately, `alif_isp_pico.c`'s fps block was gated behind
`#if DT_NODE_EXISTS(DT_NODELABEL(ov5647))`, so an IMX296 shield build
(`camera-mjpeg-stream`, #2287/#2305) compiled that whole block out and
silently ignored `cfg.fps` too.

The fps-apply logic (request, decline, or settle) now lives once in a
shared header, `src/backends/camera/camera_frmival.h:90`
("static inline alp_status_t camera_apply_fps(const struct device"),
instead of being copied a third time. Policy --
`effective = requested_fps ?: default_fps`; if both are 0 the device is
left untouched -- is graded by WHO asked, not by the errno a
`video_set_frmival()` call returns:

  - `requested_fps == 0` (only a backend's own internal default asked)
    -- `src/backends/camera/camera_frmival.h:117`
    ("if (requested_fps == 0u) {"): ANY negative rc -- `-ENOSYS`, a
    transient I2C/SCCB NAK, anything -- is a quiet `LOG_WRN` + `ALP_OK`.
    Round-2 review caught a draft that graded purely on errno instead
    of on who asked, which would have newly broken `alif_isp_pico.c`'s
    pre-#2278 OV5647 tolerance (a transient SCCB NAK on its 10 fps
    default used to only warn, never fail `open()`).
  - `requested_fps != 0` (the CALLER explicitly asked) --
    `src/backends/camera/camera_frmival.h:126`
    ("if (rc == -ENOSYS || rc == -ENOTSUP) {"): this is the ONLY case
    that declines with `ALP_ERR_NOSUPPORT` + `LOG_ERR`; any other
    negative rc maps through the shared errno baseline (`alp_errno.h`)
    and `open()` fails with that mapped status instead.
  - On success, the settled rate is read back with `video_get_frmival()`
    and compared against a COPY of the original request --
    `video_set_frmival()` takes its argument by pointer and some
    drivers (`video_sw_generator.c`'s `set_frmival` among them)
    overwrite it in place with the clamped/settled value, so comparing
    the readback against that overwritten value instead of the
    original request made every "settled differently" case compare
    equal to itself and never log the `LOG_INF` line (round-2 review
    finding). A failed readback, or one reporting a zero interval --
    `src/backends/camera/camera_frmival.h:143`
    ("if (get_rc != 0 || actual.numerator == 0u || actual.denominator == 0u) {")
    -- falls back to reporting the original request as settled.

All three camera backends now call it:
`src/backends/camera/zephyr_video.c:278`
("fps AFTER format, never before:"),
`src/backends/camera/v2n_n44_isp.c:284`
("fps AFTER format, same ordering rationale as zephyr_video.c (#2278)."),
and `src/backends/camera/alif_isp_pico.c`, which is refactored onto the
shared helper AND generalised to resolve whichever supported sensor
node the stacked shield actually defines -- OV5647
(`#if DT_NODE_EXISTS(DT_NODELABEL(ov5647))`, unchanged, default 10 fps)
or IMX296, no default worth forcing --
`src/backends/camera/alif_isp_pico.c:420` ("#elif DT_NODE_EXISTS(DT_NODELABEL(imx296))") --
instead of only ever looking for OV5647. A nonzero `cfg.fps` with
NEITHER sensor node present now declines with `ALP_ERR_NOSUPPORT` --
`src/backends/camera/alif_isp_pico.c:449` ("fps requested but no known sensor node exists on this ") --
rather than silently no-op'ing. The fps-AFTER-format ordering matters throughout:
`ov5647_set_fmt()` (`zephyr/drivers/video/ov5647.c`) re-derives its
stored frame-interval request from the just-negotiated mode and would
silently overwrite an earlier one.

`imx296_set_frmival()` (`zephyr/drivers/video/imx296.c`) always
overwrites the request with the sensor's one fixed all-pixel-scan rate
(10/603 = 60.3 fps) and returns success regardless of what was asked,
so `camera-mjpeg-stream`'s IMX296 scenario (`FRAME_FPS` 30) now settles
(logs `LOG_INF`, since 30 != 60.3) instead of declining -- confirmed by
reading `imx296_set_frmival()`'s body, not benched (needs-silicon, see
below).

`video_alif.c` and `video_csi_dw.c` (the CPI / CSI-2 endpoint forwarders
that sit between `zephyr_video.c`/`v2n_n44_isp.c` and a real sensor on
AEN silicon) previously forwarded only `.get_frmival` to the endpoint
device -- `.set_frmival`/`.enum_frmival` were missing, so
`camera_apply_fps()` would have hit `-ENOSYS` on every AEN board
regardless of what the sensor itself supports. Both now forward all
three, mirroring the existing `.get_frmival` shape exactly:
`zephyr/drivers/video/video_alif.c:953` ("#2278: same forwarding shape as alif_cam_get_frmival() above -- set/enum") and
`zephyr/drivers/video/video_csi_dw.c:939` ("#2278: same forwarding shape as csi2_dw_get_frmival() above -- set/enum").

**Behaviour changes for existing callers:**

  - `ALP_CAMERA_CONFIG_DEFAULT`'s `fps` field changes from `30` to `0`
    (`include/alp/camera.h:118` ("fps = 0u, .format = ALP_PIXFMT_RGB565"))
    -- any caller that left `cfg.fps` unset and relied on the implicit
    30 now gets "backend default" instead. `0` means "let the backend
    pick its own default" per the field's own doc.
    `tests/zephyr/peripheral/src/config_defaults.c:176`
    ("0 = let the backend pick its own default (#2278)") and
    `examples/aen/aen-isp-ov5647-viewfinder`'s file-header + inline
    comments (no longer assuming the default is 30) are updated to
    match. `docs/abi/v0.16-snapshot.json` is regenerated for the
    macro's new value.
  - A CALLER-requested nonzero `cfg.fps` against a sensor with no
    frame-rate control at all now fails `open()` with
    `ALP_ERR_NOSUPPORT` instead of silently ignoring the request (or,
    for `alif_isp_pico.c` specifically, instead of only warning as it
    did before this change). Audited every `examples/**` use of
    `.fps` / `cfg.fps` / `ALP_CAMERA_CONFIG_DEFAULT` for this risk:
    `ai-object-detection-realtime`, `ai-camera-viewer`,
    `visual-defect-detection`, `edgeai-vision-aen`, and
    `iot-connected-camera` all set a nonzero fps but none of their
    `prj.conf`s enable `CONFIG_VIDEO` at all, so only `zephyr_stub`
    links and `alp_camera_open()` already returns
    `ALP_ERR_NOT_IMPLEMENTED` regardless of fps (three of the five
    already say so in their own source comments, "skip (v0.2
    deliverable)" / "so alp_camera_open returns NULL") -- no behaviour
    change. `aen-camera-firstlight` leaves `cfg.fps` at its new 0
    default (never set explicitly) -- no behaviour change.
    `camera-mjpeg-stream` and `aen-isp-ov5647-viewfinder` request a
    nonzero fps against a real OV5647 or IMX296 sensor, both of which,
    per the two paragraphs above, always settle a request rather than
    decline it -- neither example was changed. No example needed an
    fps=0 edit.

New `tests/unit/camera_zephyr_video` ztest suite covers the policy
against three DT devices: upstream's `zephyr,video-sw-generator` (a
real frame-interval-capable device) at fps 0/15/200 (untouched / exact
settle / clamped-to-ceiling), a test-local `alp,test-video-no-frmival`
fake with no `.set_frmival` at all (fps 30 declines with
`ALP_ERR_NOSUPPORT`, fps 0 opens, and a pool-size-plus-one run of
declines followed by a reopen proves the state-pool slot is released on
EVERY decline, not merely tolerated by one spare slot -- round-2 review
found the original single-decline regression test still passed under a
mutation that deleted the `_free_state()` call it was meant to guard),
and a test-local `alp,test-video-frmival-err` fake whose `.set_frmival`
always returns `-EIO` (a non-`ENOSYS` error), called directly against
`camera_apply_fps()` to cover the backend-default-tolerates-any-error
and caller-request-maps-through-errno branches that `alp_camera_open()`
alone can't reach cheaply --
`tests/unit/camera_zephyr_video/src/test_camera_zephyr_video.c:243`
("test_apply_fps_backend_default_tolerates_non_enosys_error") --
directly. A suite `before`/`after` hook pair resets the generator's rate and
closes any handle a failed assertion left open before each case runs,
since ztest runs cases in NAME order rather than declaration order and
a rate-changing case (e.g. the 200 fps clamp) can otherwise leak into
whichever case follows it alphabetically (also a round-2 finding).
