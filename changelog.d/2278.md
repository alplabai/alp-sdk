### Fixed — `zephyr_video` and `v2n_n44_isp` camera backends silently ignored `alp_camera_config_t::fps` (#2278)

`#2276` fixed `alif_isp_pico.c`; the portable `zephyr_video` backend and
the V2N N44 ISP backend still never called `video_set_frmival()` at all
-- every `<alp/camera.h>` stream through either one ran at whatever
rate the sensor's default mode happened to power up at, no matter what
an app's `cfg.fps` asked for.

The fps-apply logic (request, decline, or settle) now lives once in a
shared header, `src/backends/camera/camera_frmival.h:76`
("static inline alp_status_t camera_apply_fps(const struct device"),
instead of being copied a third time.  Policy:
`effective = requested_fps ?: default_fps`; if both are 0 the device is
left untouched; `video_set_frmival()` returning `-ENOSYS`/`-ENOTSUP` is
a loud `ALP_ERR_NOSUPPORT` + `LOG_ERR` when the CALLER asked for a
nonzero rate, but only a `LOG_WRN` + `ALP_OK` when it was the backend's
own default that couldn't land -- see the `@return` doc at
`src/backends/camera/camera_frmival.h:72`
("ALP_OK, or ALP_ERR_NOSUPPORT when @p requested_fps is nonzero and").
All three camera backends now call it:
`src/backends/camera/zephyr_video.c:278` ("fps AFTER format, never before:"),
`src/backends/camera/v2n_n44_isp.c:284` ("fps AFTER format, same ordering rationale as zephyr_video.c (#2278)."), and
`src/backends/camera/alif_isp_pico.c:416` ("camera_apply_fps(sensor_dev, cfg->camera_id, cfg->fps, 10u,"),
which is refactored onto the shared helper rather than hand-rolling its
own copy a third time. The ordering note matters:
fps must be set AFTER `video_set_format()`, never before, because
`ov5647_set_fmt()` (`zephyr/drivers/video/ov5647.c`) re-derives its
stored frame-interval request from the just-negotiated mode and would
silently overwrite an earlier one.

`video_alif.c` and `video_csi_dw.c` (the CPI / CSI-2 endpoint
forwarders that sit between `zephyr_video.c`/`v2n_n44_isp.c` and a real
sensor on AEN silicon) previously forwarded only `.get_frmival` to the
endpoint device -- `.set_frmival`/`.enum_frmival` were missing, so
`camera_apply_fps()` would have hit `-ENOSYS` on every AEN board
regardless of what the sensor itself supports. Both now forward all
three, mirroring the existing `.get_frmival` shape exactly:
`zephyr/drivers/video/video_alif.c:953` ("#2278: same forwarding shape as alif_cam_get_frmival() above -- set/enum") and
`zephyr/drivers/video/video_csi_dw.c:939` ("#2278: same forwarding shape as csi2_dw_get_frmival() above -- set/enum").

`ALP_CAMERA_CONFIG_DEFAULT`'s `fps` field changes from `30` to `0`
(`include/alp/camera.h:111` ("fps = 0u, .format = ALP_PIXFMT_RGB565")) -- a behaviour change for
any caller that left `cfg.fps` unset and relied on the implicit 30. `0`
means "let the backend pick its own default" per the field's own doc,
which is what every backend now honors explicitly instead of two of
the three quietly ignoring the number that used to be there.
`tests/zephyr/peripheral/src/config_defaults.c:176`
("0 = let the backend pick its own default (#2278)") and
`examples/aen/aen-isp-ov5647-viewfinder`'s file-header + inline comments
(no longer assuming the default is 30) are updated to match.
`docs/abi/v0.16-snapshot.json` is regenerated for the macro's new value.

New `tests/unit/camera_zephyr_video` native_sim ztest suite covers the
policy against two real DT devices: upstream's
`zephyr,video-sw-generator` (a real frame-interval-capable device) at
fps 0/15/200 (untouched / exact settle / clamped-to-ceiling), and a
test-local `alp,test-video-no-frmival` fake with no `.set_frmival` at
all, at fps 0 (opens) and fps 30 (`ALP_ERR_NOSUPPORT`, then a same-`camera_id`
re-open at fps 0 to prove the state-pool slot wasn't leaked). Coverage is
native_sim only -- the `video_alif.c`/`video_csi_dw.c` forwarder path and
the OV5647-through-`zephyr_video` path are **not** bench-verified on AEN
silicon (needs-silicon); `alif_isp_pico.c`'s own fps path was already
silicon-proven under #2276 and is unchanged in behavior here, only in
implementation.

Refs #2276. Refs #2279 (still open: the settled rate is latched into
each backend's per-handle state -- e.g. `zephyr_video.c`'s
`alp_z_video_state_t::frmival` -- but no public getter reads it back
yet).
