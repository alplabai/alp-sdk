### Fixed — apt steps bounded each download but not the operation, so a slow mirror blocked merges (#1595)

Every apt step in `.github/workflows` carried per-request bounds and a job cap:

```yaml
timeout-minutes: 20
run: |
  sudo apt-get update  -o Acquire::http::Timeout=30 ... -o Acquire::Retries=3
  sudo apt-get install -o Acquire::http::Timeout=30 ... -o Acquire::Retries=3 -y ...
```

`Acquire::Retries=3` retries a single stuck **download**; it never restarts the
**operation**, and every retry targets the same backend that is already
struggling. Against a mirror that is slow rather than dead, a dozen-odd packages
each creeping toward the 30 s ceiling walk the install past 20 minutes inside one
attempt, and the job is killed with no second try.

Measured 2026-08-19 — five install steps blew their caps in a single afternoon,
and **re-running did not clear it**:

| step | consequence |
|---|---|
| `Install cppcheck` | ran in the **merge queue's own** job and evicted a green PR (#1564, 19 passing / 0 failing) from the queue **twice** |
| `Install host build tools (dtc, ninja, ccache, gperf, libffi)` | failed twice, blocking #1589 outright |
| `Install arm-none-eabi toolchain` | red PR |
| `Install Yocto-side runtime deps` | red PR |

Other jobs the same afternoon installed fine, so the mirror was degraded, not
down — which is exactly the case the old shape handles worst.

New `.github/scripts/apt-install.sh` bounds and retries the **whole** operation:
each attempt is killed at `APT_ATTEMPT_TIMEOUT` (default 240 s) and retried with
a growing backoff, so a slow attempt costs seconds instead of the entire budget,
and the fresh attempt re-resolves DNS — usually onto a healthier backend. apt's
own per-request options are kept, since they still cap a single stuck download
*inside* an attempt.

Converted the seven call sites in the four workflows that demonstrably failed:
`pr-twister.yml`, `pr-static-analysis.yml`, `pr-cc3501e-bridge-build.yml`,
`pr-plain-cmake.yml` (×4). The remaining 20 sites across 8 workflows keep the old
shape for now — deliberately incremental, because a workflow change cannot be
verified except by running it, and these four are the ones with evidence. They
also exercise the new path on this very PR (`pr-twister` and `pr-static-analysis`
both run on it), so the fix proves itself before the sweep.

The script is unit-tested locally against a stubbed `apt-get`: succeeds first
try; **retries** and then succeeds when the first two attempts fail; exhausts to
exit 1 naming the packages; rejects an empty package list with exit 2; and — the
case that matters — a hung mirror is **killed at the attempt cap and retried**
(14 s across two 2 s-capped attempts, versus 60 s of hanging under the old shape).

The failure message says plainly that this is a degraded-mirror condition and not
a repo defect, so the next person reads it correctly instead of hunting a
phantom regression. Three separate reds today were all this one fault, which is
how teams learn to wave through red CI.

Two defects in this change's own first CI run, both mine, both caught by the PR
exercising the script on a real runner:

- The script was committed **non-executable** (`100644`): `chmod +x` on a Windows
  checkout does not reach the index, so every converted step died instantly with
  `Permission denied` / exit 126. My local tests all invoked it as `bash <script>`,
  which works regardless of the mode — so the one property CI depended on was
  precisely the one they bypassed.
- `pr-twister.yml` checks the repo out into a **subdirectory** (`path: alp-sdk`),
  so a repo-root-relative path resolved to nothing there (exit 127). Anchored to
  `$GITHUB_WORKSPACE/alp-sdk`. The other three converted workflows check out at
  the root, which is why `cppcheck` passed on the same run.

The first CI run also exposed a design flaw: the per-attempt cap was applied to
`apt-get update` and `apt-get install` **separately**, so one "240s" attempt
actually ran 5m10s and three attempts could exceed the job's own
`timeout-minutes` — reintroducing the killed-mid-operation failure this script
exists to prevent, just later. The cap now wraps the whole attempt, verified by a
test that fails against the old shape.

Finally, an honest limit: on the run that exposed these, the retry loop worked
exactly as designed (three bounded attempts, then a clear diagnosis) and the
install **still failed**, because the mirror was genuinely bad for that package
set. This change turns "hang for the whole cap, die with no information" into
"bounded attempts, then a message naming the cause". It cannot make a degraded
mirror serve packages.

A third defect, and the one that made the retry useless in practice: when
`timeout` fired, **`apt-get` survived as an orphan still holding the dpkg lock**,
so both remaining attempts died in seconds with

```
E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 2599 (apt-get)
```

The retry could never have worked. Two causes, both introduced by the previous
iteration's own fix: wrapping the attempt in `sudo sh -c` to make the cap cover
the whole attempt meant `timeout` killed the wrapper shell while `apt-get` ran
on, and nothing cleaned up afterwards. The wrapper is gone (`timeout … sudo
apt-get …` lets sudo relay the signal), the attempt total is still bounded by
recomputing the remaining budget between the two commands, and a cleanup step
now clears stray `apt-get`/`dpkg` processes, stale lock files and half-configured
packages between attempts. That cleanup is scoped to ephemeral CI runners and
says so — it must not be lifted onto a developer machine.
