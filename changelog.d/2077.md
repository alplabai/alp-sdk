### Fixed — `tas2563_init()`'s connectivity probe discarded the real bus status, and the EVK demo issued its first amp I2C access with no post-SDZ-release settle time (#2077)

`tas2563_init()`'s I2C connectivity probe (`chips/tas2563/tas2563.c`) remapped
every bus failure to a hardcoded `ALP_ERR_NOT_READY`, throwing away the status
`alp_i2c_write()`/`alp_i2c_write_read()` actually returned. A NACK is
documented to return `ALP_ERR_IO` ("NACK / bus fault",
`include/alp/peripheral.h:436-437`), but a failure on any of the three bus
calls inside `tas2563_init()` -- `select_book0_page0()`
(`chips/tas2563/tas2563.c:194-195`), the REVID read
(`chips/tas2563/tas2563.c:197-198`), and the shutdown-mode `reg_update()`
(`chips/tas2563/tas2563.c:210-211`) -- surfaced identically as
`ALP_ERR_NOT_READY` regardless. On two bench boards the EVK demo printed
`tas2563_init(0x4d) -> -2` for what reads elsewhere as a NACK; the driver had
swallowed the distinction. All three call sites now `return s;` instead,
propagating whatever the bus call returned. `addr_is_valid()`'s
`ALP_ERR_INVAL` path (`chips/tas2563/tas2563.c:163-171`) is unchanged, and
`tas2563_init()` has no genuine "answered but not in a usable state" case of
its own -- it reads REVID but never validates it against an expected
identity -- so there is no remaining use for a driver-invented
`ALP_ERR_NOT_READY` on this path. `include/alp/chips/tas2563.h`'s `@return`
block is updated to match: an `(other)` arm now documents that the probe's
status passes through verbatim, typically `ALP_ERR_IO` (NACK / bus fault),
`ALP_ERR_NOT_READY` (bus handle closed), or `ALP_ERR_NOSUPPORT`.

Both real callers of `tas2563_init()` -- `examples/aen/aen-evk-demo/src/main.c`
and `examples/peripheral-io/i2c-device-hub/src/main.c` -- only ever branched
on `== ALP_OK`, never on `ALP_ERR_NOT_READY` specifically, so neither needed a
behavioural change beyond this fix. A new host test,
`test_tas2563_init_propagates_bus_status_on_probe_failure`
(`tests/zephyr/chips/src/test_audio.c`), arms the fake TAS2563 emulator's
existing `fake_tas2563_fail_write_at()` fault-injection hook to NACK the very
first bus write `tas2563_init()` issues (the `PAGE = 0` write inside
`select_book0_page0()`) and asserts `ALP_ERR_IO`, not `ALP_ERR_NOT_READY`.
Mutation-checked: reverting the fix (restoring the hardcoded remap) turns
this test red; re-applying the fix turns it green again.

**Second, datasheet-confirmed defect found while reading `tas2563_init()`'s
callers.** TI SLASET3D (April 2019, revised January 2024) §7.3.11.1 states
that while the part is in Hardware Shutdown, "I2C communication is
disabled," and §9.2 "Power Supply Sequencing" states that once SDZ is
released, "additional commands to the device should be delayed for 100 uS to
allow the OTP to load" before any I2C operation. That floor applies to BOTH
places this driver can release SDZ, and the fix covers both:

- **Driver-owned `sd_n`.** When a caller passes a non-NULL `sd_n`,
  `tas2563_init()` drives SDZ high itself (`chips/tas2563/tas2563.c:180-184`)
  and, until this fix, probed the bus immediately afterwards with no delay --
  the same violation, just inside the driver instead of at a call site, and
  one the driver itself is in a position to know about: it just drove the
  pin. `tas2563_init()` now calls `alp_delay_us(TAS2563_RESET_SETTLE_US)`
  (`chips/tas2563/tas2563.c:191`) in that branch, after the GPIO write and
  before the connectivity probe.
- **Caller-owned `sd_n` (the `sd_n == NULL` case).**
  `examples/aen/aen-evk-demo/src/main.c`'s sound phase drives `AMP_ENABLE`
  (SD_N/SDZ, P5_2) itself via raw `gpio5`, then calls `tas2563_init()` on
  both amps with `sd_n = NULL` -- here the driver has no way to know when an
  externally-owned pin went high, so the wait belongs at the call site. The
  demo now calls `k_usleep(TAS2563_RESET_SETTLE_US)`
  (`examples/aen/aen-evk-demo/src/main.c:4024`) immediately before the
  `tas2563_init()` loop.

The wait constant went through two names in review. It started as
`TAS2563_SDZ_RELEASE_WAIT_US`, scoped to the hardware-reset case only; once
`tas2563_init()` gained its own unconditional software reset (below) with the
identical §9.2 floor, one constant covering BOTH reset kinds read better than
two, so it is now `TAS2563_RESET_SETTLE_US` (200 us, deliberately above the
100 us datasheet floor), defined exactly once, in
`include/alp/chips/tas2563.h:188`, and used by every placement below -- not a
demo-local constant re-exported for the driver to ignore.
`include/alp/chips/tas2563.h`'s `tas2563_init()` `@pre`
(`include/alp/chips/tas2563.h:348-355`) documents both cases: with `sd_n`
non-NULL the function applies the wait itself; with `sd_n` NULL, the caller
must have already waited that long since releasing SDZ.

A host test,
`test_tas2563_init_settles_sdz_before_first_access_when_sd_n_owned`
(`tests/zephyr/chips/src/test_audio.c`), covers the driver-owned branch. The
fake TAS2563 I2C-emul target does not model bus timing (the same limitation
already documented above
`test_bmi323_init_honours_suspend_mode_communication_idle` for
`fake_bmi323.c`), so it cannot assert either wait's POSITION relative to a
bus access -- only that `tas2563_init()`'s real wall-clock time, with `sd_n`
owned, is at least the combined floor. `k_uptime_ticks()` proved too coarse
to see a 200 us spin land inside one system tick (it measured 0 us elapsed
and the test failed against the passing driver); the test instead reads
`k_cycle_get_32()` / `k_cyc_to_us_floor64()`, the same HW cycle counter
`k_busy_wait()` itself spins against on native_sim, before and after the
`tas2563_init()` call. Once the software reset below added a SECOND
unconditional wait on this same path, the test's threshold was tightened
from `>= 1x TAS2563_RESET_SETTLE_US` to `>= 2x` -- at 1x, a regression that
dropped either wait alone would still pass; mutation-testing confirmed this:
deleting only the hardware-reset-branch wait left the suite otherwise green
and failed only this test, exactly the case 1x could not have caught.

`examples/peripheral-io/i2c-device-hub/src/main.c` never drives SD_N itself
(it always passes `sd_n = NULL` and relies on the pin being tied or managed
elsewhere), so it has no "just released SDZ" event to wait after and needed
no change. No other caller of `tas2563_init()` in this tree drives SD_N
immediately beforehand. This defect was found by reading, from the
datasheet sections above; it has not been verified against silicon.

**Third: `tas2563_init()` now performs the software reset TI recommends,
independent of `sd_n`.** TI SLAA954 "TAS2563 End System Integration Guide"
§3.1 Case 1 recommends BOTH a hardware reset and a software reset before
initialization "for reliable operation." Nothing in this driver ever wrote
`SW_RESET` (0x01) -- `tas2563_load_tuning()` only referenced it to REFUSE a
tuning record that targets it. `tas2563_init()` now writes `SW_RESET = 1`
(SLASET3D §7.5.3, p.65: bit 0, self-clearing, resets every register to its
POR default) right after book 0 / page 0 selection is valid
(`chips/tas2563/tas2563.c:199-216`) and before anything else the function
configures -- ordering matters because the reset wipes whatever came before
it. The same `TAS2563_RESET_SETTLE_US` wait follows, since §9.2's 100 us
floor applies "after a hardware OR software reset" equally. Nothing in
SLASET3D calls out special ACK handling for this write; it is a normal
single-byte write like every other one in this driver. The pre-existing
"park in software shutdown" write immediately after (unchanged in behaviour)
is now largely redundant -- the software reset already restores `PWR_CTL` to
its POR default, which is software shutdown -- and its comment says so; it
stays as cheap, explicit insurance.

Two new host tests cover this, both in `tests/zephyr/chips/src/test_audio.c`:

- `test_tas2563_init_issues_sw_reset_before_other_configuration`
  (`tests/zephyr/chips/src/test_audio.c:331`) pins the exact write sequence a
  clean init issues via the fake's ordered write log -- `PAGE=0`, `BOOK=0`,
  `SW_RESET=1`, then the `PWR_CTL` park write -- proving `SW_RESET` lands
  strictly between the paging writes and the park write, not after it.
  Mutation-checked: deleting the `SW_RESET` write turned this test (and the
  two below) red; restoring it turned the suite green again.
- `test_tas2563_init_settles_after_sw_reset_when_sd_n_not_owned`
  (`tests/zephyr/chips/src/test_audio.c:373`) proves the settle wait itself
  runs even with `sd_n == NULL`, where -- before this change -- init issued
  its first bus access with no wait at all. Same `k_cycle_get_32()` technique
  as the sd_n-owned test above, floor `>= 1x TAS2563_RESET_SETTLE_US` (only
  one wait runs on this path).

Mutation-checked as a group: deleting the whole software-reset block
(`chips/tas2563/tas2563.c:202-216`) turned exactly these three tests red --
the two above plus the sd_n-owned settle test, now at its tightened `>= 2x`
threshold -- with the rest of the suite (279 other cases) staying green;
restoring the block turned all three green again (282/282 total). Isolating
just the hardware-reset-branch wait (leaving the new software-reset wait in
place) turned ONLY the sd_n-owned settle test red, confirming its `>= 2x`
threshold, not the `>= 1x` it started at, is what catches that specific
regression.

**Fourth: the driver-invented `sd_n` glitch theory didn't hold up, and the
real defect on this board is different.** `alp_gpio_configure(sd_n,
ALP_GPIO_OUTPUT, ...)`'s Zephyr backend (`src/backends/gpio/zephyr_drv.c:111`)
passes bare `GPIO_OUTPUT`, documented upstream as "Enables pin as output, no
change to the output state" -- so `tas2563_init()`'s own
configure-then-write sequence should not itself glitch SD_N low (documented
in a new `@par`, `include/alp/chips/tas2563.h:91-101`). What the
authoritative E1M-EVK carrier netlist DOES establish is a real, different
defect: `AMP.ENABLE` (SD_N) and `AMP.FAULT` (IRQZ) are each ONE net shared
between U27 and U28 (U27 pin 7 + U28 pin 7 + Alif P5_2 for SD_N; U27 pin 18 +
U28 pin 18 + Alif P5_0 for IRQZ), unlike TI's stereo reference design
(SLAA920 Figure 22), which keeps each amp's shutdown independent. `SD_N`
also carries a 10 kOhm pull-up (R138, fitted) to `+VIO`, so both amps leave
hardware shutdown on their own at power-up. Consequences already present in
the driver: `tas2563_deinit()` and `tas2563_set_hw_enable()` both toggle
`sd_n` directly, so calling either on one amp's context resets or shuts down
BOTH amps if they share the net; a fault on a shared `IRQZ` cannot identify
which amp faulted without reading each instance's own
`tas2563_read_faults()` over I2C. This driver models ONE physical chip per
`tas2563_t` and has no cross-instance registry to detect sharing across two
independent contexts, so the fix is documentation, not a runtime guard: a new
"Shared SD_N / IRQZ nets" `@par` block
(`include/alp/chips/tas2563.h:72-88`) states the contract plainly -- pass
`sd_n` to at most one instance per physical net, leave every other instance
on that net at `sd_n = NULL`, and disambiguate a shared fault pin by reading
each instance's registers -- with cross-reference notes added to
`tas2563_deinit()`, `tas2563_set_hw_enable()` and
`tas2563_configure_fault_pin()`'s doc comments. The hardware facts are
recorded once, in `metadata/boards/e1m-evk.yaml` (the `EVK_I2C_ADDR_TAS2563_LOW`
and `EVK_PIN_AMP_ENABLE` entries), and regenerated into
`include/alp/boards/alp_e1m_evk_routes.h` via `scripts/gen_board_header.py`.
The demo's own SD_N sequence (`examples/aen/aen-evk-demo/src/main.c`, phase
11) already matches this contract -- it owns `AMP_ENABLE` once, at board
level, and passes `sd_n = NULL` to both `tas2563_init()` calls -- and its
`GPIO_OUTPUT_INACTIVE` step now carries a teaching comment explaining that,
because `SD_N` is pulled high by R138, that step is a deliberate hardware
reset of BOTH amps (SLAA954 §3.1 Case 1), not an incidental side effect of
configuring the pin.

**Fifth: three documentation-only corrections, no behaviour change.**

- `tas2563_load_tuning()`'s doc comment claimed the datasheet's "multi-byte
  write section does not state the register address auto-increments." That
  conflated two different sections: SLASET3D §7.3.7 (p.33), titled
  "Multiple-Byte Write and Incremental Multiple-Byte Write," indeed never
  restates it -- it only describes the electrical ACK framing -- but §7.3.5
  "Single-Byte and Multiple-Byte Transfers" (p.32), the section immediately
  before it, does: "the register issued then serves as the starting point,
  and the amount of data subsequently transmitted... determines to how many
  registers are written." The comment
  (`include/alp/chips/tas2563.h:698-708`) now cites §7.3.5 and frames the
  single-byte-write choice as deliberate conservatism pending silicon
  confirmation, not an undocumented behaviour. `changelog.d/2040-tas2563-v03x-tuning-i2s-faults.md`,
  still unreleased, repeated the same imprecise §7.3.7-only framing in its
  own prose and is corrected in place rather than left to ship a
  self-contradicting release note next to this one.
- `tas2563_set_amp_level()`'s doc now notes (per TI SLAA953 §1.9, p.9, not
  SLASET3D itself) that "Amplifier Level cannot be changed in Smart
  Amp/Tuning Mode. In order to change it, user must enter ROM mode" -- and
  that this driver cannot enforce or detect that restriction: SLASET3D's
  register map names no field for ROM vs Smart Amp/Tuning mode. The one
  register whose title suggests it, `DSP Mode & TDM_DET` (0x11, §7.5.19,
  p.73), is read-only TDM clock-detection readback (`FS_RATIO`/`FS_RATE`)
  despite its name, with no mode-select field. `tas2563_init()`'s doc gained
  the matching note: it does not select, and cannot report, which of the two
  modes the part is in.
- `tas2563_load_tuning()`'s doc gained a "Write verification" `@par`
  (`include/alp/chips/tas2563.h:729-741`) explaining why this driver does
  NOT implement TI's `I2C_CKSUM` (0x7E) post-write checksum verification
  (shown in SLAA765 §16, p.25): SLASET3D §7.5.61 (p.93) documents the
  register exists and is "updated on writes to other registers on all books
  and pages," but never specifies the algorithm -- not what it sums, not
  whether `PAGE`/`BOOK` select writes count as "other registers," not an
  initial value beyond POR `0h`. Without the algorithm, an expected value
  can only be guessed, not computed, so this driver does not attempt it.

Register defaults already established in this driver's testing
(`PWR_CTL.MODE[1:0]` reset `2'b10` = software shutdown, `ISNS_PD`/`VSNS_PD`
both powered down at reset -- both SLASET3D §7.5.4 Table 7-104, p.66) are now
also stated in the file-level "Safe by default" overview
(`include/alp/chips/tas2563.h`), not only near the functions that touch
them. Per-unit speaker calibration provisioning remains explicitly
out-of-scope, noted where `tas2563_load_tuning()`'s doc already discusses
what it does not do -- this driver only replays whatever tuning array a
caller's own provisioning step produced.

**Everything in this entry is paper analysis against SLASET3D (TI, Rev. D,
January 2024), cross-referenced with SLAA954, SLAA953, SLAA920 and SLAA765
where cited by section; none of it has been run on silicon, and no bench
was used for this round.**
