### Fixed — `tas2563_init()`'s connectivity probe discarded the real bus status, and the EVK demo issued its first amp I2C access with no post-SDZ-release settle time (#2077)

`tas2563_init()`'s I2C connectivity probe (`chips/tas2563/tas2563.c`) remapped
every bus failure to a hardcoded `ALP_ERR_NOT_READY`, throwing away the status
`alp_i2c_write()`/`alp_i2c_write_read()` actually returned. A NACK is
documented to return `ALP_ERR_IO` ("NACK / bus fault",
`include/alp/peripheral.h:436-437`), but a failure on any of the three bus
calls inside `tas2563_init()` -- `select_book0_page0()`
(`chips/tas2563/tas2563.c:194-195`), the REVID read
(`chips/tas2563/tas2563.c:197-198`), and the shutdown-mode `reg_update()`
(`chips/tas2563/tas2563.c:210-211`) -- surfaced identically as
`ALP_ERR_NOT_READY` regardless. On two bench boards the EVK demo printed
`tas2563_init(0x4d) -> -2` for what reads elsewhere as a NACK; the driver had
swallowed the distinction. All three call sites now `return s;` instead,
propagating whatever the bus call returned. `addr_is_valid()`'s
`ALP_ERR_INVAL` path (`chips/tas2563/tas2563.c:163-171`) is unchanged, and
`tas2563_init()` has no genuine "answered but not in a usable state" case of
its own -- it reads REVID but never validates it against an expected
identity -- so there is no remaining use for a driver-invented
`ALP_ERR_NOT_READY` on this path. `include/alp/chips/tas2563.h`'s `@return`
block is updated to match: an `(other)` arm now documents that the probe's
status passes through verbatim, typically `ALP_ERR_IO` (NACK / bus fault),
`ALP_ERR_NOT_READY` (bus handle closed), or `ALP_ERR_NOSUPPORT`.

Both real callers of `tas2563_init()` -- `examples/aen/aen-evk-demo/src/main.c`
and `examples/peripheral-io/i2c-device-hub/src/main.c` -- only ever branched
on `== ALP_OK`, never on `ALP_ERR_NOT_READY` specifically, so neither needed a
behavioural change beyond this fix. A new host test,
`test_tas2563_init_propagates_bus_status_on_probe_failure`
(`tests/zephyr/chips/src/test_audio.c`), arms the fake TAS2563 emulator's
existing `fake_tas2563_fail_write_at()` fault-injection hook to NACK the very
first bus write `tas2563_init()` issues (the `PAGE = 0` write inside
`select_book0_page0()`) and asserts `ALP_ERR_IO`, not `ALP_ERR_NOT_READY`.
Mutation-checked: reverting the fix (restoring the hardcoded remap) turns
this test red; re-applying the fix turns it green again.

**Second, datasheet-confirmed defect found while reading `tas2563_init()`'s
callers.** TI SLASET3D (April 2019, revised January 2024) §7.3.11.1 states
that while the part is in Hardware Shutdown, "I2C communication is
disabled," and §9.2 "Power Supply Sequencing" states that once SDZ is
released, "additional commands to the device should be delayed for 100 uS to
allow the OTP to load" before any I2C operation.
`examples/aen/aen-evk-demo/src/main.c`'s sound phase drove `AMP_ENABLE`
(SD_N/SDZ, P5_2) high and called `tas2563_init()` on both amps with no delay
between the two. The demo now waits `TAS2563_SDZ_RELEASE_WAIT_US` (200 us,
`examples/aen/aen-evk-demo/src/main.c:3926`, deliberately above the 100 us
datasheet floor; `k_usleep()` is tick-rounded and may sleep longer) via
`k_usleep(TAS2563_SDZ_RELEASE_WAIT_US);` at
`examples/aen/aen-evk-demo/src/main.c:4022`, immediately before the
`tas2563_init()` loop. The wait was added at the call site, not inside
`tas2563_init()` itself: the driver has no way to know when a caller who
owns SD_N externally (the `sd_n == NULL` case) actually released it, and a
fixed sleep inside the driver would silently tax every caller that had
already waited. `include/alp/chips/tas2563.h`'s `tas2563_init()` doc comment
now states this precondition explicitly (`include/alp/chips/tas2563.h:280-289`).
`examples/peripheral-io/i2c-device-hub/src/main.c` never drives SD_N itself
(it always passes `sd_n = NULL` and relies on the pin being tied or managed
elsewhere), so it has no "just released SDZ" event to wait after and needed
no change. No other caller of `tas2563_init()` in this tree drives SD_N
immediately beforehand. This defect was found by reading, from the
datasheet sections above; it has not been verified against silicon.
