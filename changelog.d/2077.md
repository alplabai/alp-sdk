(`:10-16`, matching `metadata/chips/tas2563.yaml`'s `driver_status: partial`)
and a `@par Why an in-tree driver, not the upstream one` note (`:18-27`):
an upstream Zephyr TAS2563 driver exists
(`zephyrproject-rtos/zephyr#103148`, merge commit `95bcb74aa`, merged

(`west.yml:221` pins `v4.4.1`, tagged 2026-06-10, which is AFTER the merge

(`git merge-base --is-ancestor 95bcb74aa v4.4.1` fails; the commit object

Neither line existed before this issue, on top of everything below.

`tas2563_init()`'s I2C connectivity probe remapped every bus failure to a
hardcoded `ALP_ERR_NOT_READY`, discarding the status `alp_i2c_write()`/
`alp_i2c_write_read()` actually returned (`chips/tas2563/tas2563.c:251-284`).
A NACK is documented to return `ALP_ERR_IO` (`include/alp/peripheral.h:436-437`).
All three probe/park bus calls now `return s;`, propagating the real status;
`include/alp/chips/tas2563.h`'s `@return` block documents the `(other)` arm.
Neither real caller (`examples/aen/aen-evk-demo/src/main.c`,
`examples/peripheral-io/i2c-device-hub/src/main.c`) branched on
`ALP_ERR_NOT_READY` specifically, so neither needed a behavioural change.

**Reset sequence.** SLAA954 "TAS2563 End System Integration Guide" §3.1 Case
1 recommends both a hardware and a software reset before init; SLASET3D
§9.2 requires a 100 us settle after either, before any I2C access
(`TAS2563_RESET_SETTLE_US`, 200 us, `include/alp/chips/tas2563.h:261`, one
constant for both cases). `tas2563_init()` now issues a software reset
(`SW_RESET`, SLASET3D §7.5.3) after book 0/page 0 selection and before any
other configuration (`chips/tas2563/tas2563.c:251-269`) — the part had never
written this register before. This runs unconditionally, whether or not the
function owns `sd_n`; when it does own `sd_n`, driving SD_N high only
*releases* hardware shutdown (it is not itself a hardware reset unless SDZ
was actually low beforehand) — an explicit hardware reset is the caller's
job, not this function's, since it may not own the pin exclusively (see
below). The pre-existing "park in software shutdown" write after the probe
is now redundant given the unconditional software reset, and says so in its
comment (`chips/tas2563/tas2563.c:276-284`).

**SD_N glitch, found by reading `drivers/gpio/gpio_dw.c` (the AEN801 `gpio5`
backend, `snps,designware-gpio`).** `dw_pin_config()` switches a pin's
direction to output BEFORE touching its data register, and only touches
that register for `GPIO_OUTPUT_INIT_HIGH`/`_LOW` — flags `alp_gpio_configure()`
never passes. Configuring SD_N as output before writing it therefore exposed
the data register's reset-time level as an output the instant direction
flipped — an unplanned pulse on a net shared with U28 (see below). That
reset-time level is NOT verified as `0` on this board's actual AE822 silicon
— the DesignWare IP's data-register reset value is a synthesis-time
parameter, so it is possible for it to reset `1` instead; the fix does not
depend on which. Fixed by writing high BEFORE configuring
(`chips/tas2563/tas2563.c:224-230`): `alp_gpio_write()` has no dependency on
the pin already being configured, and `gpio_dw_port_set_bits_raw()` writes
the register unconditionally regardless of direction — but only if `sd_n` is
declared `GPIO_ACTIVE_HIGH` in its devicetree pin-array entry, since Zephyr
only applies a `GPIO_ACTIVE_LOW` entry's inversion inside
`gpio_pin_configure()` itself, not before; documented as a precondition
(`include/alp/chips/tas2563.h:159-174`). Not a live bug today: no in-tree
board declares `P5_2` in `alp,pin-array` at all, and both real callers pass
`sd_n = NULL`. That first write alone is not sufficient on every backend:
Zephyr's `gpio_emul` (this test suite) masks a write against the pins
*currently* configured as output, so a write issued before configure is
silently dropped there if the pin was not already an output — order-dependent
across test cases, and confirmed by mutation (below). `tas2563_init()`
therefore writes high a SECOND time, after configuring, so the final state
lands correctly on both kinds of backend. Verified against Zephyr/DesignWare
and `gpio_emul` only; the `sw_fallback`/`testing` GPIO backends have no real
pin either way, and the CC3501E GPIO proxy's behaviour on a pre-configure
write is unverified — all documented in `include/alp/chips/tas2563.h:116-157`.

**Shared SD_N/IRQZ — an E1M-EVK hardware fact, not a driver defect.** The
authoritative carrier netlist shows `AMP.ENABLE` (SD_N) and `AMP.FAULT`
(IRQZ) are each ONE net shared between U27 and U28 (unlike TI's stereo
reference design, SLAA920 Figure 22, which keeps each amp's shutdown
independent); SD_N carries a 10 kOhm pull-up (R138) to `+VIO`, IRQZ a 10 kOhm
pull-up (R124). This driver models one physical chip per `tas2563_t` and
keeps no cross-instance registry, so the fix is a documented caller contract
(`include/alp/chips/tas2563.h:91-114`): pass `sd_n` to at most one instance
per net, initialise that instance first, and disambiguate a shared fault pin
by reading each instance's own faults. `metadata/boards/e1m-evk.yaml`'s
`EVK_I2C_ADDR_TAS2563_LOW` (line 300-301), `EVK_PIN_AMP_FAULT` (line 344) and
`EVK_PIN_AMP_ENABLE` (line 346) entries record the facts once; regenerated
into `include/alp/boards/alp_e1m_evk_routes.h` via `scripts/gen_board_header.py`.

**Demo (`examples/aen/aen-evk-demo/src/main.c`).** The sound phase's
microsecond-scale `GPIO_OUTPUT_INACTIVE`-then-`gpio_pin_set(1)` pulse was not
GUARANTEED to reach Hardware Shutdown: with SDZ_MODE at its default 00b
("Normal Shutdown with Timer", SLASET3D §7.3.11.1 Table 7-6), asserting SDZ
low starts a graceful ramp-down/power-down sequence that reaches Hardware
Shutdown once it completes; `SDZ_TIMEOUT` (Table 7-7:
2/4/6(default)/23.8 ms — whichever this part's register currently holds,
unknown to the demo) is only a backstop that forces it if that sequence
hasn't finished in time, not the sole path there — and that guarantee itself
assumes `SDZ_MODE`'s default; `SDZ_MODE = 10b` ("Normal Shutdown", no timer
at all) has no time bound whatsoever. SD_N is now held low for
`AMP_ENABLE_RESET_HOLD_MS` (24 ms,
`examples/aen/aen-evk-demo/src/main.c:3942`), at or above the
worst-case 23.8 ms, before release — an actual hardware reset, unverified on
real silicon. `TAS2563_RESET_SETTLE_US` is still waited afterward, separately
(`main.c` phase 11).

**The demo's tone reached neither speaker.** Phase 11 configured both amps
with `TAS2563_RX_SLOT_FROM_ADDR`
(`examples/aen/aen-evk-demo/src/main.c:3862` ("Explicit TAS2563_RX_LEFT"),
old call site) on a 2-channel-wide I2S frame. SLASET3D §7.4.2 (p.42): the
default source is "mono from the time slot equal to the I2C base address
offset"; Table 7-3 (p.29): the offset is `address - 0x4C`, so U27 (0x4D) is
offset 1 and U28 (0x4E) is offset 2. A 2-slot frame only has slots 0
(left) and 1 (right): U27 landed on the RIGHT slot, and U28's slot 2 fell
"either partially or fully beyond the frame boundary," which SLASET3D
§7.4.2 (p.42) again states returns "a null sample equivalent to a digitally
muted sample" -- U28 was permanently muted by construction. U27 fared no
better: the demo's I2S config was mono (`.channels = 1`), and the Alif DW
I2S driver's mono TX path (`zephyr/drivers/i2s/i2s_dw.c`, vendored in this
tree) writes the sample to the LEFT slot and a hardcoded `0` to the RIGHT
slot -- so the RIGHT slot U27 was listening to carried nothing but zeros
regardless of what `TAS2563_RX_*` it was configured for. Both speakers were
silent even when every earlier phase (mux routing, `tas2563_init()`,
`ACTIVE` mode) succeeded.

now request `.channels = 2`
(`examples/aen/aen-evk-demo/src/main.c:4100`, `:4159`), and the tone buffer
(`:4196`) is interleaved `[L0,R0,L1,R1,...]` with the identical sample
written to both channels -- the DW driver's stereo TX path writes both
slots for real once the stream is genuinely 2-channel, so downmix was not

`TAS2563_RX_LEFT` for U27, `TAS2563_RX_RIGHT` for U28, per the

hardcoded with no citable source. `SOUND_VOL_START`/`SOUND_VOL_CEILING`

`examples/aen/aen-evk-demo/src/sound_verdict.h`'s PDM-energy ratio/floor

**Documentation-only corrections**, each citing the exact section rather
than the loose earlier claim, none change behaviour:
- Multi-byte writes: SLASET3D §7.3.5 "Single-Byte and Multiple-Byte
  Transfers" (p.32) DOES document sequential-address auto-increment in
  prose; §7.3.7 (p.33), a different, later section, merely doesn't restate
  it. `tas2563_load_tuning()`'s doc now cites §7.3.5 and frames single-byte
  writes as deliberate conservatism pending silicon, not an undocumented gap
  (`include/alp/chips/tas2563.h:822-829`). The same imprecise framing in the
  still-unreleased `changelog.d/2040-tas2563-v03x-tuning-i2s-faults.md` is
  corrected in place rather than left to ship self-contradicting notes —
  this does not close any part of #2040 otherwise.
- `tas2563_set_amp_level()`: SLAA953 §1.9's full note — "Amplifier Level
  cannot be changed in Smart Amp/Tuning Mode. In order to change it, user
  must enter ROM mode in Test and Measurement panel in the Device Home
  page" — is a PPC3-GUI workflow note, not a register rule; SLASET3D itself
  never mentions ROM mode. No register in SLASET3D's map selects or reports
  ROM vs Smart Amp/Tuning mode (searched exhaustively); documented, not
  gated in code (`include/alp/chips/tas2563.h:549-566`).
- `tas2563_load_tuning()`: TI's `I2C_CKSUM` (0x7E) write-verification CRC
  (SLASET3D §7.3.2, p.29, not just SLAA765's command-syntax examples) is
  documented but its algorithm is never specified — not what it sums, not
  whether `PAGE`/`BOOK` writes count, not an initial value beyond POR `0h` —
  so a host-side expected value cannot be computed, only guessed; not
  implemented (`include/alp/chips/tas2563.h:850-867`).
- Calling `tas2563_init()` again now visibly wipes any loaded tuning/I2S/
  IV-sense configuration (the software reset above is unconditional);
  documented on both `tas2563_init()` and `tas2563_load_tuning()`.

**Close-before-assert, precisely scoped.** The shared `tas_init()` helper
(`:224`), which roughly 15 tests call, now closes the bus on its own
init-failure path before asserting, fixing the leak for every one of its
callers on that path. Two tests needed a SECOND fix beyond that: `:246` and
`:324` both still had a later assertion, reading `fake_tas2563_get_reg()`/
`fake_tas2563_cur_book()` (not the bus handle), positioned before their
final `alp_i2c_close(bus)` -- a failure there, after `tas2563_init()` had
already succeeded, would still have leaked. Both now close right after
`tas2563_init()` returns, before any later assertion, since nothing either
test does afterward touches the bus handle itself. The four newly-added
tests follow the same pattern from the start.

**The SD_N-glitch test needed two attempts.** `gpio_emul_pin_configure()`
fires every registered callback synchronously on every `configure()` call,
even with no interrupt armed (upstream Zephyr's `drivers/gpio/gpio_emul.c`,
not vendored in this tree, `gpio_emul_pin_configure()`) — the first version
of the new test used that to capture `gpio_emul_output_get()` at the
instant `tas2563_init()`'s own `configure()` ran, expecting the
pre-configure write to have already landed. It passed against BOTH the
fixed driver and a configure-then-write-once mutation, because
`gpio_emul_port_set_bits_raw()` (the write path) ALSO fires the same
callback on every successful write ("for output-wiring, so the user can
take action based on output," the driver's own comment on that call) — so
the capture-only-the-latest
approach was overwritten by the trailing write's own (always-correct)
callback regardless of ordering. The test now logs EVERY firing, in order,
and requires all of them to read high, not just the last one — see the
test's own comment for the full reasoning.

Mutation-checked: reverting the status-propagation fix, deleting the whole
software-reset block, isolating either settle wait, and swapping SD_N's
write order back to configure-then-write-once were each tried. All turned
exactly their target test(s) red; each was then restored and the suite
re-confirmed green. The write-order mutation specifically: 282/283 passed,
with `test_tas2563_init_writes_sd_n_before_configuring_it` failing on
"SD_N read 0 at configure/write event #0" — the FIRST logged event being
low is exactly what identifies the bug.

**Silicon-open, recorded rather than guessed at:** whether the `SW_RESET`
write itself ACKs (a NACK would surface as `ALP_ERR_IO` on every boot);
whether 200 us is enough on real parts; whether a 24 ms SD_N low pulse
actually reaches Hardware Shutdown; P5_2's data-register level at first
configure on a real EVK; and what the CC3501E proxy's `configure()` does to
output level. Nothing in this entry has been run on silicon.
