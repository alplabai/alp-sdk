### Fixed — the Zephyr RPC backend's async dispatch read the subscribe table with no lock while subscribe/unsubscribe wrote it with none either (#1632)

`src/backends/rpc/zephyr_drv.c`'s `rpc_ept_recv()` runs on the ipc_service
worker thread; its async dispatch block read `sub->cb`/`sub->user` straight off
the per-channel subscribe table and called `sub->cb(...)` with no lock held.
`z_subscribe()` and `z_unsubscribe()` mutate the same table from the
application thread, also lock-free. A subscribe/unsubscribe racing an in-flight
dispatch could hand the callback a torn `(cb, user)` pair, or a concurrent
unsubscribe could clear the entry out from under the dispatch mid-read and
silently drop the callback entirely -- worse than an error, since nothing
observed it.

The channel already has `be->lock` (a `k_spinlock`, used by the close protocol
for GHSA-xhm8-7f87-93q5): holding it across the callback call itself would
deadlock, since the callback may call `alp_rpc_close()` on its own channel
(self-close), and `alp_rpc_close()` -> `z_shutdown()` also takes `be->lock`.
The fix is snapshot-under-lock, invoke-outside: `rpc_ept_recv()` takes the
lock, finds the subscribe-table entry, copies `cb`+`user` into locals, releases
the lock, then invokes through the locals. `z_subscribe()`/`z_unsubscribe()`
now take the same lock around every table read/write.

This closes the write/write and write/read races on the table itself. It does
**not** close every race a caller might assume: once the snapshot is taken and
the lock released, a concurrent `alp_rpc_unsubscribe()` can still complete
before the callback actually runs -- the callback fires once more for a
message that was already in flight, exactly as if the unsubscribe had landed a
moment later. This residual window is documented at the call site; a caller
needing a hard "no callback after unsubscribe returns" guarantee must
serialise on its own.

Regression test: `tests/unit/rpc_zephyr_backend/` scenario 5
(`test_1632_dispatch_vs_unsubscribe_snapshot_is_coherent`), added alongside the
four existing GHSA-xhm8-7f87-93q5 scenarios in the same file. It drives a
genuinely concurrent, higher-priority `z_unsubscribe()` against an in-flight
`rpc_ept_recv()` dispatch, timed via a new test-only hook
(`g_rpc_dispatch_test_sync_hook`) fired from inside the fix's `be->lock`
critical section -- mirroring the file's existing
`test_defect1_recv_vs_timed_out_call_race` technique. Reverting only the lock
(keeping the hook call site at the equivalent unlocked position) reproduces the
defect exactly: the higher-priority unsubscribe preempts before the dispatch
reads `sub->cb`, clears the entry, and the callback is silently never invoked.
