### Decided — `new-som`'s `alif:ensemble` `ospi_memories`/`hyperram` scaffold stays out of alp-sdk (#1944)

PR #1470 carried an enhancement to the `new-som` scaffold that emitted
`ospi_memories:`/`hyperram:` skeletons for `alif:ensemble` parts, plus two
dedicated tests. It was dropped mid-rebase because `210e9fedc` had already
retired the whole `scripts/alp_cli/` CLI surface on `dev` — `new-som` now
lives only in tan-cli, and there is no alp-sdk file left for that hunk to
land in. Confirmed on this pass: `scripts/alp_cli/` keeps only its
non-CLI library modules (`_workspace.py`, `diagnostic.py`,
`diagnostic_format.py`, `validator.py`, `yaml_pos.py`, `__init__.py`); no
`new_som.py`/`main.py` and no other alp-sdk file emits either field.

**Decision: do not port the hunk into alp-sdk. `new-som` scaffolding is a
tan-cli concern.** Filed as
[tan-cli#1220](https://github.com/alplabai/tan-cli/issues/1220) for a native
port — not merely asserted as "tracked", since no such issue existed before
this pass (`gh issue list --repo alplabai/tan-cli --search "new-som ospi
hyperram scaffold"` returned none).

**Engaging ADR-0026, not just citing it.** §D's own words are "the producer
of hardware truth and the renderer of hardware truth belong in the same
repo" — read broadly, a scaffold that writes an `ospi_memories:`/`hyperram:`
skeleton into `metadata/e1m_modules/*.yaml` looks like a hardware-truth
*producer*, which clause 2 keeps in alp-sdk. That reading does not survive
contact with what §D is actually scoped to: its "producer" is the
already-authored metadata `clause 2` protects (`metadata/`,
`metadata/schemas/`) and what a *renderer* derives from it at
configure/build time (`alp.conf`, sysbuild, kconfig, headers, secure bytes)
— both are read-then-emit pipelines over metadata that already carries
schema-validated facts. `new-som`'s scaffold is neither: it writes
`TBD`/placeholder text a human still has to replace with a real MPN, CS
index and population state, and the result is not "hardware truth" until
`validate_metadata.py` (which *does* stay in alp-sdk, unmoved by any of
this) accepts it. It is authoring tooling, not a truth pipeline — the same
category as the `new-som` SoC/SoM-YAML skeleton generation that already
moved to tan-cli in full (`210e9fedc`, 2026-08-27), eight days before
ADR-0026 §C/§D was decided (2026-09-04). §C/§D discuss the configure-time
CMake call and the renderer axis by name and do not mention scaffolding at
all; reopening an already-shipped, working placement on an ADR that does
not address it would be the drift, not honoring it.

The metadata *schema* already has correct homes for both fields
(`ospi_memory`/`hyperram` in `som-preset-v1.schema.json`), and every shipped
AEN preset *declares* them — populated where fitted (explicit
`assembled: true` on the five family SKUs corrected in
`changelog.d/1990-aen-ospi-chip-select.md`; `E1M-AEN803.yaml`'s hyperram
still relies on the same implicit-default omission, out of scope for this
pass since that file's own values were never inverted) and marked DNI where
not (`E1M-AEN801.yaml`'s `assembled: false`) — so the scaffold gap is a
generation-time convenience, not a validation gap.
`docs/porting-new-som.md` now carries the gap + the tan-cli#1220 pointer
inline, so the next person filling in a new Ensemble SoM's
`ospi_memories:`/`hyperram:` by hand does not rediscover this in PR history.
