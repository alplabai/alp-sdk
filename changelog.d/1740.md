### Fixed — an idle CC3501E delivered ~5.8 phantom events per second (#1740)

Every `cc3501e_poll_events()` on an **empty** event ring dispatched three events with
opcode `0x00`, length 0 — continuously, with no Wi-Fi or BLE activity at all. `0x00` is
not a defined `ALP_CC3501E_EVT_*` opcode.

Reply padding added in #1610/#1655 pads a reply up to an 8-byte multiple for DMA burst
alignment and folds the pad **into the declared payload length**. Its own comment states
the invariant it breaks: *"The pad bytes are never interpreted: every reply carries its
own length"* — true only for a self-delimiting payload. `GET_PENDING_EVENTS` returns a
packed `{opcode(1) | len(1) | payload[len]}` list with no count and no terminator, so the
pad is indistinguishable from entries. An empty ring produced `reply_payload = 1`,
`rem = 1`, `pad = 7`, declared 8 — the host then walked 7 zero bytes as three
`{opcode 0, len 0}` entries. Measured on an E1M-AEN801: `[evtdbg] got=7 raw=00 00 00 00`
every poll.

`#1724`'s fan-out meant every subscriber received each phantom. Fixed-size replies
(`GET_VERSION`, `GET_MAC`) were unaffected because the host reads a known byte count.

The walk now stops at a zero opcode, treating it as the padding it is — no wire-format
change, and the DMA-alignment win is kept. Bench A/B on AEN801: 117 phantom events per
20 s before, **0** after, with the padding still arriving unchanged (`got=7`).

Not a regression from #1721/#1724 — the walk loop is byte-identical before #1724.

Also noted while tracing, not changed here: `cc3501e_request()` writes `*rx_len` only when
`data_len > 0`, so a caller that does not pre-initialise its length variable reads stale
stack on a bare-OK reply. `cc3501e_poll_events()` initialises `got = 0`, so it was not the
cause, but it is a live trap for the next caller.
