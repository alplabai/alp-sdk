### Added — TLS transport for the AWS IoT and Azure IoT SDK glue (#2581)

`<alp/cloud_transport.h>` (`CONFIG_ALP_CLOUD_TRANSPORT=y`, `[ABI-EXPERIMENTAL]`) is a TLS-over-TCP client transport on Zephyr sockets and mbedtls: `alp_cloud_transport_connect()` / `_send()` / `_recv()` / `_close()` on a caller-owned `alp_cloud_transport_t`. With `CONFIG_ALP_AWS_IOT=y`, `vendors/aws-iot/` adds a coreMQTT `TransportInterface_t` over it (`alp_cloud_transport_coremqtt()`). Until now both SDKs built but neither could reach a broker, because the transport was left to the application.

The peer certificate is always verified, against `server_name` or, when that is NULL, `host`; there is no option to turn verification off. TLS with no security tag returns `ALP_ERR_INVAL` rather than falling back to plain TCP, and plain TCP has to be requested with `plaintext = true`. `recv` returns 0 on a timeout and `ALP_ERR_IO` when the peer has closed, which is what coreMQTT's process loop needs to stop instead of spinning. `last_errno` in the transport keeps the socket errno of the last failure, so a refused connection (`ECONNREFUSED`) can be told from a failed handshake (`ECONNABORTED`).

For Azure this provides the TLS socket only. The hub client has no MQTT stack, so the application still brings the MQTT client that runs over it.

`tests/zephyr/cloud_transport/` runs on `native_sim` over loopback, in three scenarios: argument checks, lifecycle and the receive contract over plain TCP; a real TLS handshake against Zephyr's bundled test certificates, where a wrong CA, a wrong server name and an ALPN mismatch are each refused; and the coreMQTT adapter under a real `MQTTContext_t`. The coreMQTT scenario needs the `extras-cloud` AWS checkout and runs in `nightly-cloud-sdks.yml`.

Not verified: a connection to a live AWS IoT Core or Azure IoT Hub endpoint, mutual TLS with a client certificate, DNS resolution, and a send timeout or partial send. IPv4 only.
