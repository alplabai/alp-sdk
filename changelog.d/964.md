### Added — `cores.<core>.toolchain` lets a project declare a non-default toolchain variant (#964)

`board.yaml` had no input for the toolchain a slice builds with, even though the
system manifest and build-plan already carry a `slices[].toolchain` field —
until now it was always the SoM preset's derived default (`arm-zephyr-eabi` for
Zephyr, `poky-glibc` for Yocto), never customer-declared. This blocked
alp-sdk-vscode#314's toolchain picker: there was no input to write to.

`metadata/schemas/board.schema.json`'s `core_entry` now accepts an optional
`toolchain:` string per core, e.g.:

```yaml
cores:
  m55_hp:
    os: zephyr
    app: ./src
    toolchain: llvm
```

Omitting it keeps today's default unchanged — additive, and no existing
`board.yaml` changes behaviour. The value flows through the already-existing
`Slice.toolchain` plumbing (`scripts/alp_orchestrate/loader.py`'s per-core
merge already let a project override any SoM `topology.<core>` field; only
the schema was missing the key) into `--emit build-plan`'s
`slices[].toolchain.id`/`targetTriple`/`compiler` and
`system-manifest.yaml`'s `slices[].toolchain`, unchanged surfaces the same
`_slice_toolchain` derivation already populates from the SoM-preset default.

Deliberately out of scope (open questions the issue itself raises, not
resolved here): a validated enum vs. free-form value set, and a
host-local path for a vendor toolchain (`GNUARMEMB_TOOLCHAIN_PATH`-style) —
a maintainer call, not a schema addition.
