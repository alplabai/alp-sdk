### Fixed — `_dxcom_version()`'s failure fallback no longer renames the vendor, so a probe-failure perf point stays matchable (#1923)

`scripts/alp_model/adapters/deepx.py`'s `_dxcom_version()` returned
`DX-COM <ver>` on success but the lowercase `dxcom` whenever the
`dxcom -v` probe raised or its banner did not parse. `compiler_version`
is part of a perf point's measurement identity — `scripts/validate_metadata.py`
folds `str(target.get("compiler_version", ""))` into the point key — so a
measurement taken while the probe failed was filed under a vendor string no
success-path point ever uses. It could never match, rather than merely
lacking its version digits, and the measurement was silently lost.

Both fallbacks now return `DX-COM`. This restores the invariant the two
sibling adapters already held across the same boundary:
`scripts/alp_model/adapters/ethos_u.py`'s `_vela_version()` returns
`vela <ver>` / `vela`, and `scripts/alp_model/adapters/drpai.py`'s
`_compiler_version()` returns `drp-ai_tvm <ver>` / `drp-ai_tvm`. Only the
version digits are ever unknown when a probe fails — never the vendor.

`tests/scripts/test_alp_model_adapters.py` gains
`test_dxcom_version_fallback_keeps_the_vendor_token` (both failure routes:
the probe raising `OSError`, and a banner the version regex cannot parse)
and `test_every_adapter_version_fallback_shares_its_success_vendor_token`,
which states the invariant once for the two probe-based adapters. Both were
mutation-checked: restoring the `dxcom` literal turns them red.
