### Fixed — `_dxcom_version()`'s probe-failure fallback carried a different vendor token than its success path (#1923)

`scripts/alp_model/adapters/deepx.py`'s `_dxcom_version()` returned
`"DX-COM <version>"` on the success path but the bare lowercase
`"dxcom"` (the console-script name) when the version probe failed, so a
perf point published during a probe failure carried a different
`target.compiler_version` vendor token than one published during a
successful probe -- for the same compiler, on the same backend. tan-cli
matches a bench perf point to a build by that token, case-folded, so the
mismatched fallback silently produced "no bench data for this build"
instead of a match.

`_dxcom_version()`'s fallback is now `"DX-COM <unknown>"` -- the token
stays `DX-COM` on every path; only the version segment varies. Checked
both sibling adapters for the same shape: `ethos_u.py`'s `_vela_version()`
falls back to the bare `"vela"` (no version suffix) and
`drpai.py`'s `_compiler_version()` falls back to the bare `"drp-ai_tvm"`
-- both already share their first token with their success-path string,
so neither had this divergence.

Added `tests/scripts/test_alp_model_adapters.py::test_dxcom_version_fallback_matches_success_vendor_token`
(probes a simulated `dxcom` failure and asserts the token) and
`::test_vela_and_drpai_version_fallback_already_matches_success_token`
(pins the two sibling adapters' existing, already-correct behaviour so a
future edit can't reintroduce the split).
