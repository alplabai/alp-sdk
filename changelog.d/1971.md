### Documented — `meta-alif-ensemble` is a zeus-era layer and cannot run on meta-alp-sdk's Scarthgap baseline (#1971)

Documentation of a known blocker, not a code fix. With the clone command
corrected (#1967), the AEN A32 Yocto path still does not build, and the reason
is structural rather than a matter of patching a recipe or two.

`meta-alif-ensemble` declares

```
LAYERSERIES_COMPAT_meta-alif-ensemble = "warrior zeus"
```

against meta-alp-sdk's Scarthgap 5.0.11 baseline — four LTS series apart. That
is not just a version string to widen: the layer is written in pre-honister
override syntax (`SRC_URI_append`, `do_compile_prepend`), which BitBake on
Scarthgap no longer parses as overrides at all, and it pins
`LINUX_VERSION ?= "5.4.25"`.

The TF-A side has drifted the same distance. The layer passes TF-A build knobs
`UART`, `HYPRAM_EN`, `FLASH_EN`, `MODEM_SRAM` and `RAM_PRELOADED_DTB_BASE`,
none of which current `trusted-firmware-a_alif` still defines; its `platform.mk`
uses `ALIF_BL32_XIP_BASE`, `ALIF_TRUSTED_SRAM_BASE`, `PRELOADED_BL33_BASE`,
`ALIF_SOC_E8`, `ISSI_HYPERRAM_EN`, `AP_HYPERRAM_EN` and `MX_FLASH_EN` instead.
So even a layer forward-ported to Scarthgap syntax would configure the
bootloader with knobs the bootloader ignores.

Recorded as a blocker rather than silently left in the tree as an
apparently-working dependency. A reader who saw the layer listed in
`meta-alp-sdk/conf/layer.conf`'s recommended set had no way to know that
adding it cannot produce a booting image, and would have spent the debugging
budget on symptoms.

Nothing here was built or booted. The A32 cluster remains un-run on silicon.
