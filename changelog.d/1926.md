### Fixed — gd32-bridge protocol spec said the frame CRC is MSB first; both implementations transmit it LSB first (#1926)

`docs/gd32-bridge-protocol.md:796` claimed the CRC-16/CCITT-FALSE trailer is
transmitted MSB first. Verified against `chips/gd32g553/gd32g553.c`'s four
CRC sites (`:213-214` SPI request, `:255-256` SPI reply parse, `:275-276`
short-error-envelope parse, `:366-367` I2C write) -- all four store the low
byte at the lower index, confirming LSB first, silicon-verified and matching
the gd32-bridge-firmware side. The spec sentence was the deviant party, and
it had already caused a downstream defect twice: the firmware's wire-vector
generator followed this sentence and emitted every vector big-endian
(gd32-bridge-firmware#68, fixed by gd32-bridge-firmware#88).

The doc now states the CRC is LSB first, with the worked example from the
issue -- CRC-16/CCITT-FALSE over the PING request body `A5 00` is `0xFF84`,
which goes on the wire as `84 FF` -- and a note that this is the one
little-endian field in an otherwise big-endian envelope, which is what made
the mistake easy. Grepped the repo for every other site repeating an
MSB-first claim for this protocol's CRC; found none (`docs/gd32-bridge.md`,
`docs/adr/0016-cross-core-peripheral-proxy-wire-schema.md`, and the other
gd32-bridge docs don't state a byte order for the CRC at all). Neither
implementation changed.
