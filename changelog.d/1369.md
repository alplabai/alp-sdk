### Fixed — `gd32_swd.yaml`'s wrong-board guard armed with an unattested value; the V2N/V2M `expect_dpidr` stance now applies to it too (#1369, #1440)

`metadata/chips/gd32_swd.yaml`'s `target_expected_idcode` carried
`0x6BA02477`. Neither circulating GD32 SW-DP IDR candidate is a
measurement taken on a GD32 with a probe attached:

- `0x6BA02477` is the **generic** ADIv5 expectation for any Cortex-M33
  r0p1 SW-DPv2 part — its own comment said so — and separately is
  `CHANGELOG.md`'s record of a *different* target on the same board: the
  V2N CM33 DAP measured on `e1mx-v2n-m1-01` (`Found SW-DP with ID
  0x6BA02477`, `Found Cortex-M33 r0p4`).
- `0x0BE12477` has no attribution at all — no bench transcript, no
  datasheet reference, no commit message.

A guard armed at a wrong ID is worse than an unarmed one: if the wrong
value happens to match the other board, it passes on exactly the board
it exists to exclude — and `0x6BA02477` is exactly that other board's
own measured value.

The GD32 V2N/V2M helper-firmware presets already deliberately leave
`debug.expect_dpidr` unset for this same reason (#1355). This change
brings `gd32_swd.yaml` into line with that stance instead of inventing
a new policy: `target_expected_idcode` is now absent, not repopulated
with either candidate.

**Mechanism check before removing it:** `gd32_swd_connect()`
(`chips/gd32_swd/gd32_swd.c`) reads the SW-DP IDR into `ctx->idcode` and
never compares it against anything — it is not a gate in the driver.
The manifest field itself has no code consumer: it is not read by any
generator or by `validate_metadata.py`, and it is optional in
`metadata/schemas/chip-v1.schema.json` (absent from `required`). The
only place a comparison happens at all is
`examples/v2n/v2n-gd32-swd-flash/src/main.c`, against the *header*
macro `GD32_SWD_EXPECTED_IDCODE` (`include/alp/chips/gd32_swd.h`), and
that comparison already only logs and continues on a mismatch — it was
never fatal. So removing the manifest field breaks no consumer, and no
code anywhere gates a wrong-board decision on either unattested value.

`GD32_SWD_EXPECTED_IDCODE` itself is unchanged (still `0x6BA02477`,
still carrying its existing `@warning UNVERIFIED on a GD32G553`) —
it stays only as the informational generic-architecture reference the
driver comment and the example log, and its manifest header comment no
longer describes it as mirroring a manifest field, since that field no
longer exists.

Also corrected, all still without picking a winner between the two
candidates: the `v2n-gd32-swd-flash` example's README and `src/main.c`
stated `0x6BA02477` as "the GD32G553's documented value" and something
"we expect" on real silicon — both overstated it as attested when the
header it uses already disclaimed it; and `metadata/e1m_modules/README.md`
and `docs/gd32-bridge.md` said the manifest "expects" / "currently
arms" its guard with `0x6BA02477`, which is no longer true now that the
field is absent.

`docs/glossary.md`, `docs/bring-up-aen.md`, `docs/test-plan.md` /
`docs/verification-status.md` (generated from it), `docs/_aen-runbook-section.md`,
and `docs/tutorials/07-recovering-a-bricked-bridge.md` already correctly
hedged this from earlier work (#1512, #1999) and needed no further
change; none of them describe the manifest as arming a guard.
`scripts/bench/aen/bench-env.sh` and
`scripts/bench/aen/flash-jlink-mramxip.sh` also carry `0x0BE12477`
(a *different*, AEN-Flow-D wrong-board rejection gate, not this
manifest field) and are deliberately left untouched here — both are
mid-rewrite on the open #2032/#2064 branch.

Not settled by this change, and not settleable without one: which of
`0x0BE12477` / `0x6BA02477` (if either) a GD32 actually answers. That
needs a probe on a GD32G553, which no authorized bench place currently
provides. `alplabai/tan-cli#610` covers only that a `tan flash`
consumer must degrade cleanly when `expect_dpidr` is absent — it does
not settle which value is correct either, and is not sufficient to
close this on its own.
