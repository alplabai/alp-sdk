### Added — a single-pass bench runbook for the measurements v0.17.0 is blocked on (#1369)

Several v0.17.0 issues are not blocked on analysis. They are blocked on four
numbers nobody has read off the hardware, and each was filed as "needs a bench"
without saying what to measure — so a bench session spent its time
rediscovering the question.

`scripts/bench/v2n/measure-blocked-issues.sh` runs them in one read-only pass:
the GD32 SW-DP IDR (#1369, #1440), the V2M DRAM/flash sizes (#1230), and the
BRD_I2C `0x48` identity (#1163). It writes nothing to flash, fuses or
devicetree, holds a labgrid reservation for the duration, and **refuses to touch
the board if the reservation is not actually held** rather than assuming the
acquire succeeded.

It also encodes the two preconditions that were false on 2026-08-28, because
either one silently invalidates the results:

- **The V2N-M1 was physically disconnected from its DPS-150 output.** The supply
  read `power: on, voltage: 15.0, current: 0.0` while SWD independently reported
  `VTref=0.000V`. The script prints the current draw and says plainly that zero
  current with a live output means nothing is attached — the `power` field alone
  will happily tell you the board is on.
- **The GD32 probe was not attached.** Only one J-Link was present (USB `3-4.1`,
  serial `000600107451`, the V2N CM33 DAP), so the GD32-side DPIDR could not be
  read at all — which *is* #1369's blocker.

For the DPIDR it uses OpenOCD pinned by USB path rather than `JLinkExe`,
because the GD32 probe enumerates with the same OEM-cloned serial `603000869` as
the AEN E8 probe and `JLinkExe` selects only by serial — a bare
`-SelectEmuBySN` can land on a different board entirely.

The `0x48` step is gated on #1226: `i2c-8` is electrically wedged on the current
board revision, and an empty `i2cdetect` grid there is a bus fault rather than
evidence of absence. The script says so instead of inviting the misreading.
