### Added — `examples/connectivity/camera-mjpeg-stream`: camera → JPEG → MJPEG HTTP stream (#2265)

New connectivity example: capture a frame with `<alp/camera.h>`, JPEG-encode it
with `<alp/jpeg.h>`, and serve it over a plain Zephyr BSD TCP socket on port
8080 — `GET /stream` (multipart/x-mixed-replace, one boundary per frame) and
`GET /snapshot.jpg` (a single JPEG with `Content-Length`). No host tool ships;
point a browser, VLC (`vlc http://<ip>:8080/stream`), or ffmpeg at the printed
URL. See `examples/connectivity/camera-mjpeg-stream/README.md`.

The encoder is opened first and its `alp_jpeg_caps_t::pixfmt_mask` decides the
source layout everything downstream builds against — `ALP_PIXFMT_NV12` when
the won backend advertises it (the Hantro VC9000E hardware encoder on the
E1M-AEN family), `ALP_PIXFMT_YUV420_PLANAR` otherwise (the portable software
encoder, everywhere else including native_sim). The camera path is gated on
`alp_has(ALP_CAP_ID_HW_MIPI_CSI)`, not on SoC identity, and falls back to a
synthetic test-pattern frame when there is no camera capability or no camera
actually attached — no `#ifdef` on which SoC this is. Requested at 640×480.
The camera-capture/JPEG-encode loop (the app's main thread) never touches a
socket: it encodes directly into one of two SRAM0 ping-pong buffers
`src/mjpeg_http.c` owns (`mjpeg_http_claim_write_buffer()` /
`mjpeg_http_publish_frame()` — zero-copy, no `memcpy` on either side), which
swap under a mutex on publish unless a client is mid-send of the current
`front` buffer, in which case the new frame is dropped rather than tearing
the one in flight. `zsock_recv`/`zsock_send` on every accepted socket carry
`SO_RCVTIMEO`/`SO_SNDTIMEO` (`CONFIG_NET_CONTEXT_RCVTIMEO`/`_SNDTIMEO`), so an
idle or stalled client can't wedge the single server thread. A failed capture
is logged (rate-limited), backs off with `k_msleep`, and falls back to the
synthetic frame after 10 consecutive failures — an unbacked-off error loop at
the capture thread's priority would otherwise starve the (lower-priority)
HTTP thread outright. DHCP is fired once at boot and negotiates concurrently
in Zephyr's own net-stack thread; a `net_mgmt` event callback prints the
lease IP plus the stream/snapshot URLs once bound, off the capture loop's own
critical path.

`src/mjpeg_http.c` and the native_sim-only `src/selftest.c` call the
`zsock_*`-prefixed socket API (`CONFIG_NET_SOCKETS`) rather than the plain
POSIX names: on native_sim the example links as an ordinary host executable
against the host's own libc, and depending on archive link order the plain
POSIX socket names can silently resolve to the HOST's `socket()` instead of
Zephyr's — every call then fails immediately with `EPROTONOSUPPORT` because
the host interprets Zephyr's `AF_INET` (1) as its own `AF_UNIX`. `zsock_*` has
no libc counterpart, so there is nothing to collide with.

On the E1M-AEN family the JPEG source/output buffers are placed in the global
on-chip SRAM0 bank (`section("SRAM0")`, gated on
`CONFIG_ALP_SDK_JPEG_ALIF_HANTRO`) — the Hantro VC9000E is an external AXI
bus master and cannot reach the M55's local TCM, the same constraint
`examples/aen/aen-jpeg-regcheck` and `examples/aen/aen-evk-demo` document. The
AEN board overlays carry two pieces of DT graph wiring, each mirroring the
example it's drawn from: the ISP capture path from
`examples/aen/aen-isp-ov5647-viewfinder` (routes the camera shield's sensor
port through the ISP-Pico), and an INTERIM Ethernet bring-up from
`examples/aen/aen-ethernet-link` (RMII pin group + PHY power/reset GPIOs;
board generation doesn't grow real Ethernet routing yet). The PHY MDIO/refclk/
power sequence lives in the AEN-only `src/aen_eth_phy.c`, compiled in only for
`alp_e1m_aen*` targets and never referenced by the portable `main.c`.

native_sim streams the synthetic frame through the portable software JPEG
encoder (`CONFIG_NET_LOOPBACK`, no camera, no Ethernet) and proves the server
end to end with an in-app loopback selftest: `GET /snapshot.jpg`'s JPEG
SOI/EOI markers, and `GET /stream`'s multipart framing (boundary line,
`Content-Type`/`Content-Length` header pair, blank line, trailing CRLF), over
127.0.0.1 (`\[camera-mjpeg-stream\] selftest ok`). Two board-conf files
(`native_sim.conf` and `native_sim_native_64.conf`) are needed, not one --
Zephyr's board-conf auto-apply resolves a different filename per qualifier
string, and there is no single name that matches both `native_sim` (32-bit)
and `native_sim/native/64`. The E1M-AEN801/AEN803 scenario now also runs in
`pr-twister-aen.yml` (build-only — no camera/Ethernet hardware in the
runner); it did not before. Bench run 204 (E1M-AEN803 + OV5647, 320×240,
before this example's resolution was raised to its intended 640×480): a
valid 15571 B `/snapshot.jpg`, `/stream` at 17 fps / ~12.8 KB/frame over
255 parts in 15 s, with a 1536 B Ethernet net_buf data size (at the 128 B
default, run 203, frames over 896 B were dropped and no JPEG body arrived
at all). Run 205 (640×480, dark scene): 10 fps, ~37 KB/frame — both AEN
board confs now set `CONFIG_NET_BUF_DATA_SIZE=1536` explicitly, ahead of
the matching default landing on the Alif Ethernet Kconfig itself
separately. The captured frame content is dark (AWB) and its bottom two
rows render solid green (a known ISP resizer off-by-one) — both under
separate investigation, neither an issue in this example's own code; see
the README's Limits section. Repeat-encode stability is bench-proven, not
unverified: runs 204/205 encoded 255+/300+ frames back-to-back with no
encoder error.

Second pass, addressing review + bench findings on the first: raised
`MJPEG_HTTP_MAX_JPEG` to 128 KiB (bench run 205 measured ~37 KB/frame at
640×480 on a dark scene; a lit scene compresses worse) and, until a
separate Hantro driver fix lands for a header-size buffer overrun, reserve
`CONFIG_VIDEO_JPEG_HANTRO_VC9000E_HEADER_SIZE` bytes of that capacity as
margin in what `main.c` tells `alp_jpeg_encode()` it may use (the physical
buffer stays full-size). `wait_and_claim()` (the `/stream` frame wait) now
times out after `IDLE_TIMEOUT_S` instead of blocking `K_FOREVER` — a
stalled capture loop can no longer wedge the server thread through a
`/stream` client that never sees a send failure. `GET /stream`/
`GET /snapshot.jpg` on an idle-timeout `zsock_recv()` (no request line
ever arrives) now close quietly instead of replying 404. The AEN video
buffer pool math was corrected: only 3 ISP buffers actually exist (2
queued to the ISP MI, 1 converting) — a previous pass over-counted this as
5 and sized the heap accordingly; `CONFIG_VIDEO_BUFFER_POOL_HEAP_SIZE` is
now sized for the real 3×460,800 bytes (`NUM_MAX` keeps one spare
descriptor slot above that, which costs no heap bytes). `src/aen_eth_phy.c`'s
MDIO read now returns the "nothing here" sentinel when the post-transaction
wait times out too (not just the pre-transaction one), and `phy_find()`
aborts its whole scan on the first MDIO timeout rather than retrying all
32 addresses against a bus that is not coming back. `src/selftest.c` now
also verifies `Content-Length` against the real body length (both
endpoints) and guards a `size_t` underflow in the `/stream` body-length
computation that a malformed response could have driven far out of
bounds; its response-buffer caps are derived from `MJPEG_HTTP_MAX_JPEG`
instead of separately hand-picked numbers that could fall out of sync
with it.
