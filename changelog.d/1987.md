### Fixed — `cores.<id>.app:` no longer crashes the orchestrator on an unresolvable path (#1987)

`scripts/alp_orchestrate/orchestrator.py` resolved a user-supplied
`cores.<id>.app:` with a bare `(Path(base_dir) / p).resolve()`, and
`_zephyr_app_dir()` then called `.is_file()` twice on the result with no
`try` at all. That is the third instance of the antipattern #1961 closed
for `extra_libraries.<name>.profile:` in `validate.py` and for the
`--input` board.yaml in `loader.py`: a `board.yaml` whose `app:` reaches
a symlink loop crashes the CLI with an unhandled exception instead of a
clean `OrchestratorError`.

All three call sites now catch `(OSError, RuntimeError)` and re-raise
`OrchestratorError` naming the offending `app:` value.

Both platform shapes are covered, because they are genuinely different
and one test cannot see both:

* POSIX -- a symlink loop makes `Path.resolve()` raise `RuntimeError`
  (ELOOP).
* Windows -- `.resolve()` returns *without* raising and `.is_file()`
  raises a plain `OSError` (`WinError 1920`, "The file cannot be
  accessed by the system"), which is neither `RuntimeError` nor
  `PermissionError`.

Mutation-proven, one mutant per guard, each killed by exactly one test:

* deleting the `try`/`except` around `_resolve_app_path()`'s `.resolve()`
  fails `test_resolve_app_path_posix_symlink_loop_clean_error` with the
  raw `RuntimeError` escaping, and leaves the Windows test green;
* narrowing `_zephyr_app_dir()`'s first `except (OSError, RuntimeError)`
  back to `(RuntimeError, PermissionError)` fails
  `test_zephyr_app_dir_windows_symlink_loop_clean_error` with
  `OSError: [WinError 1920] The file cannot be accessed by the system`,
  and leaves the POSIX test green.

Closes #1987.
