### Added — per-project Linux core-ownership fragment (#2660)

`alp_project.py --emit linux-ownership-dts` renders the Linux devicetree fragment (node `status` of the assignable instances plus the CPG `renesas,cm33-owned-clocks` hold) from a project's resolved `ownership:`, using the same renderer as the committed SoM-default `e1m-v2n-ownership.dtsi` (`scripts/alp_orchestrate/linux_ownership.py`, shared with `scripts/gen_linux_ownership_dt.py`). An instance owned by the M33 is now explicitly `status = "disabled"` for Linux (the default fragment is unchanged: every instance is `a55`). The linux-renesas bbappend renders the project fragment itself in `do_configure` from the `ownership:` of the system-manifest (`ALP_SYSTEM_MANIFEST_PATH`, the variable and default `../alp-sdk/build/system-manifest.yaml` that `alp-dts-reservations` uses). With no manifest the committed SoM-default fragment (which carries the `renesas,cm33-owned-clocks` RSCI7 hold) is kept and a `bbwarn` says so, so existing builds keep working; pass the manifest (a project build from `tan build` / `alp_project` emit) to render the project fragment: `gen_linux_ownership_dt.py --manifest M --output F` renders it and `--vendor-dtsi` checks every node (including `channelN` children) against `r9a09g056.dtsi`. The fragment is only as fresh as the manifest (the last `tan build`); `do_configure` re-runs when the manifest, the generator, the renderer, `core-ownership.yaml`, `supervisor-links.yaml` or the SoC JSON change. The ownership fragment is now included last in the V2N/V2M board dts so a carrier node cannot re-enable an M33-owned instance. `resolve_ownership` no longer rejects a non-default `board.yaml` override outright: it is accepted when the instance lists `m33` in `candidates` and carries an `m33:` block (so the CM33 overlay and the Linux fragment can both follow), still refuses `hw_blocked` instances, and refuses handing a node to `a55` without `linux_enable`. `check_amp_pad_claims.py --project <board.yaml>` (default: every V2N-family `examples/**/board.yaml`, so the CI gate and `test-all.sh` cover them) runs the full Linux-DT-vs-CM33-pad pass over the SoM dtsi, carrier dtsi and the generated fragment with the project's resolved ownership. No instance lists `m33` as a candidate yet, so no shipped project changes; the per-project path is covered by tests and is not bench-verified.
