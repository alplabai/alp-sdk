### Fixed — one subsystem's `alp_wdt_close()` silently removed another subsystem's watchdog protection (#1637)

`alp_wdt_open()` validated `timeout_ms` and picked a backend but never compared
`cfg->wdt_id` against a live handle, so two subsystems could each open
`ALP_E1M_WDT0` and both believe they were protected. They were not: the backend
close path used to disable the whole watchdog **device**, not the handle's
channel — `src/backends/wdt/zephyr_drv.c`'s `z_close()` called
`wdt_disable(dev)` and cast the result to `(void)` — so the first close
disarmed the second owner's deadline. No error surfaced on any path, in either
caller's return value or `alp_last_error()`. A device that believes it is
watchdog-protected and is not is worse than one with no watchdog at all,
because nobody is looking.

A watchdog instance is now **exclusive**. The dispatcher's handle pool is
indexed by `wdt_id` rather than being a free list, which makes the existing
atomic slot claim (`alp_slot_try_claim`, #1115) *be* the exclusivity check: one
compare-exchange, no scan of the pool, and no TOCTOU window between "is this
instance taken?" and "take it". A second `alp_wdt_open()` on a live `wdt_id`
returns NULL with `ALP_ERR_BUSY` until the owner calls `alp_wdt_close()`, after
which the instance is claimable again.

Two consequences worth knowing:

- `cfg->wdt_id` is now bounded by the dispatcher (`ALP_ERR_INVAL` above the
  portable instance count) instead of only by whichever backend was selected.
  `src/backends/wdt/yocto_drv.c` previously passed any id straight into
  `/dev/watchdog%u`. The portable ID space is exactly `{0, 1}` —
  `ALP_E1M_WDT0..1` / `ALP_E1M_X_WDT0..1` are `0u` and `1u`.
- Two subsystems that both need a deadline must use two instances or share one
  handle. `include/alp/wdt.h` documents the rule on `alp_wdt_open()`.

Regression test: `tests/unit/wdt_exclusivity/`. It deliberately builds with
`CONFIG_WATCHDOG=n` so the `sw_fallback` backend is selected and
`alp_wdt_open()` actually succeeds under `native_sim` — with `CONFIG_WATCHDOG=y`
the priority-100 `zephyr_drv` wins selection, finds a NULL device (`native_sim`
has no `alp-wdt0` DT alias) and fails every open, so the test could only skip
and would prove nothing. The rule under test is pure dispatcher code, so
exercising it over `sw_fallback` is faithful.

Exclusivity closed the *concurrent*-owner half of this defect but not the
close-time one: `z_close()` still called `wdt_disable(dev)` on the way out, so
while another `alp_wdt_t` handle can no longer coexist on the same `wdt_id`, a
non-SDK Zephyr consumer sharing the same underlying device (e.g.
`CONFIG_TASK_WDT`) still had its channel silently pulled out from under it by
every alp-owned close. `z_close()` no longer calls `wdt_disable()` at all — it
only releases the handle. Zephyr's `wdt_*` driver class has no per-channel
disable or uninstall, so there was no way to scope the call to just this
handle's channel; removing it entirely is the only way to stop it reaching
outside this handle's own state. `alp_wdt_close()`'s Doxygen now spells out,
per backend, what close does and does not disarm; `alp_wdt_disable()` is the
explicit, documented way to get a best-effort SoC-wide disable before closing.

One consequence of dropping the automatic disable: Zephyr's
`wdt_install_timeout()` refuses a second install on a device that is already
`wdt_setup()` and was never disabled, so a bare `alp_wdt_open()` right after a
`close()` that didn't call `alp_wdt_disable()` first would otherwise never
succeed again on the Zephyr backend. `z_open()` now detects exactly that case
— an `-EBUSY` from `wdt_install_timeout()` on a `wdt_id` the dispatcher's own
exclusivity check just confirmed has no live SDK owner — and reclaims the
device with one `wdt_disable()` + retry before giving up, so a `wdt_id` is
never permanently stranded by an ordinary close.

`ALP_WDT_INTERRUPT_ONLY` had the same "protection nobody can see" shape as the
close-time bug above: the Zephyr backend selected `WDT_FLAG_RESET_NONE` with a
hardcoded `.callback = NULL`, so a missed deadline fired into nothing — no
reset, no notification, strictly worse than not offering the mode.
`alp_wdt_config_t` gains `on_expire` + `user`; `alp_wdt_open()` rejects
INTERRUPT_ONLY with `ALP_ERR_INVAL` when `on_expire` is NULL, and the Zephyr
backend wires a real ISR trampoline (Zephyr's `wdt_callback_t` carries no
user-data cookie of its own, unlike `counter_alarm_cfg`'s, so `open()`
registers `(dev, channel_id) -> owner` in a small backend-local table and
`close()` clears it — a deadline that fires after `close()` finds no owner and
delivers nothing, by design, rather than touching a freed handle). The Yocto
backend now returns `ALP_ERR_NOSUPPORT` for INTERRUPT_ONLY instead of silently
accepting a mode the Linux watchdog ABI has no ioctl to deliver.

**Needs-silicon, not verified on a bench.** `native_sim` has no `alp-wdt0` DT
alias, so `zephyr_drv`'s `z_open()` always returns `ALP_ERR_NOT_READY` before
reaching `wdt_install_timeout()` -- the `-EBUSY` reclaim path and the ISR
trampoline are compiled and linked (`twister -p native_sim/native/64`, host
toolchain: `alp.unit.wdt_exclusivity` 3/3, the wdt cases in
`tests/zephyr/peripheral/src/wdt.c` + `config_defaults.c` 9/9,
`alp_sdk.conformance.portable_api` 11/11, and the `wdt-feed` example all pass
locally) but never executed at runtime by any of that. Whether the reclaim
actually reopens a still-armed device, whether the ISR trampoline actually
fires, and how wide the close-vs-latched-interrupt race window is, all need an
E1M-AEN801 or E1M-V2N101 bench run.
