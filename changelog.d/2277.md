### Fixed — OV5647 AE calibration envelope was pinned to the sensor's 10 fps VTS regardless of the active frame rate (#2277)

`zephyr/patches/hal_alif/0011-isp-ov5647-ae-calib-envelope.patch`'s
`ov5647_ae_envelope.h` (the shared header `isp_param_conf.h`'s compiled-in
OV5647 `.ae` calibration block and `sensor_attributes.h`'s reference table
both route through, patches 0011/0006) previously fixed
`OV5647_AE_MAX_INT_LINE` at `3145` — the sensor's 10 fps VTS minus a 4-line
margin — no matter which frame rate the app actually requested via
`<alp/camera.h>`'s `alp_camera_config_t::fps`. Issue #2276 stopped the
ISP-Pico camera backend from hard-coding 10 fps in its own frame-interval
request, but left this calibration ceiling untouched: at the SDK's own
default of 30 fps (`ALP_CAMERA_CONFIG_DEFAULT`, VTS 1049 lines) or 60 fps
(VTS 524 lines) AE was still free to command an exposure far past that
mode's own frame period, stretching the frame and dropping the effective
capture rate in a dim scene instead of holding it.

`OV5647_AE_MAX_INT_LINE_AT_FPS(fps)` now derives the ceiling from whichever
rate it is asked about, using the same VTS formula (`pixel_rate / (hts *
fps)`) `ov5647.c`'s own `ov5647_frmrate_to_vts()` uses. `isp_param_conf.h`'s
calibration block is a compile-time-only static initializer, so it can
still carry only one ceiling per build — its `OV5647_AE_FPS` now reads a
new Kconfig, `CONFIG_VIDEO_ISP_VSI_CALIB_OV5647_FPS` (default 30, matching
the SDK's own default fps), instead of a hardcoded 10; a board whose
default camera config asks for a different fixed rate sets this Kconfig to
match. `isp_pico.c`'s `isp_apply_ae()` already separately re-derives and
pushes a sensor-agnostic, per-apply ceiling from `video_get_frmival()` on
every stream (re)start, generic across whatever rate the app negotiates at
runtime; this Kconfig only governs the calibration's compiled-in initial
value.

`tests/unit/ov5647_ae_envelope` (a host-buildable native_sim mirror of the
formula, kept in sync with the vendored patch by
`tests/scripts/test_ov5647_ae_envelope_patch_mirror.py`, mirroring
`isp_ae_ctrl_clamp`'s pattern from #2271) asserts the commanded exposure
ceiling stays at or under each mode's own VTS-minus-margin at 10, 30, and
60 fps, and pins the old bug as a regression case (the pre-fix 3145-line
constant exceeds both the 30 fps and 60 fps frame periods). All 5 test
cases fail without the fix (2 of them, the 30/60 fps checks, against the
pinned constant) and pass with it; `west twister -T
tests/unit/ov5647_ae_envelope -p native_sim` and the existing `tests/zephyr/
video_sensors` OV5647 suite (39 cases) both stay green.

Build-verified: `examples/connectivity/camera-mjpeg-stream` (the AEN803
target, `SHIELD="e1m_evk_rpi_csi raspberry_pi_camera_module_1"`) links clean
with `-DCONFIG_COMPILER_WARNINGS_AS_ERRORS=y` and 0 compiler warnings, with
`CONFIG_VIDEO_ISP_VSI_CALIB_OV5647_FPS=30` resolved in the generated
`.config`. Unverified on silicon in a dim scene at 30/60 fps — bench run
220 (E1M-AEN803 + OV5647, 30 fps) never exercised this path because the
scene was bright daylight (intLine settling 331-351, well under either
ceiling).
