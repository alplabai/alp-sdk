### Fixed — OV5647 AE calibration envelope was pinned to a compile-time fps, not the app's actual active rate (#2277)

`zephyr/patches/hal_alif/0011-isp-ov5647-ae-calib-envelope.patch`'s
`isp_param_conf.h` OV5647 `.ae` calibration block used to fix
`OV5647_AE_MAX_INT_LINE` at the sensor's 10 fps VTS (3145 lines) regardless
of the frame rate an app actually requested. A first attempt at fixing this
made the compiled-in ceiling a function of a Kconfig-selected fps
(`VIDEO_ISP_VSI_CALIB_OV5647_FPS`, default 30, matching
`ALP_CAMERA_CONFIG_DEFAULT`) instead — still ONE compile-time value, and
every app in this repo that actually drives the OV5647 (this backend's own
10 fps fallback, `src/backends/camera/alif_isp_pico.c`, plus both
`examples/aen/aen-isp-ov5647-*` apps) pins `cfg.fps = 10`, not 30, so a
30 fps compiled-in default left a real 10 fps app's calibration ceiling at
roughly a third of its actual entitlement — the opposite bug, still a
mismatch between the compiled-in value and the ACTIVE rate.

The real fix drops that Kconfig: `ov5647_ae_envelope.h`'s macros go back to
being a fixed 10 fps BOOT-TIME default only (the sensor's own floor rate,
the most exposure headroom of any mode, so never worse than a real 10 fps
app needs). `isp_api_wrapper.c`'s `isp_vsi_set_param()` now mirrors the
exposure/gain RANGE `isp_apply_ae()` (`isp_pico.c`) already derives from
`video_get_frmival()` — the sensor's own reported ACTIVE frame period, on
every stream (re)start — into `isp_calib_param.modules.ae.autoAttr`
directly, the SAME struct `VSI_MPI_ISP_SetCalib()` reprograms the library
from on any later reload (PM resume, a second `isp_open()` after a full
close/reopen). So the compiled-in default only governs the brief window
before the first stream start; from there on, the calibration stays correct
for whatever fps the app is actually running, not a rate guessed at compile
time.

`isp_pico.c`'s frame-period-to-microseconds derivation was pulled out into
its own pure function, `isp_ae_int_time_max_us_from_frmival()`, so it could
be exercised directly rather than only as inline code inside
`isp_apply_ae()`. `tests/unit/isp_ae_calib_envelope_sync` (native_sim, 5
cases) mirrors that function AND the new calibration-sync field-copy and
tests the REAL runtime path this time, not just self-consistent macro
arithmetic (the deleted `tests/unit/ov5647_ae_envelope` only proved a
formula matched itself): it asserts the derived ceiling at 10/30/60 fps
(matching the review round's own bench-cited 30 fps figure, 32667 us),
pins e263820a8's actual bug as a regression case (an unsynced calibration
struct stays at its compiled-in default even when the active fps differs),
and proves the fix holds across a 30→10→30 fps switch, not just one push.
2 of the 5 cases fail if the sync mirror is reduced to a no-op (i.e.
e263820a8's actual behavior); the other 3 (the pure frmival-derivation
sanity checks) are unaffected by that specific bug and pass either way.
Two `tests/scripts/` drift checks keep both test mirrors honest against
their real sources (`isp_pico.c` directly, and the vendored patch).

Build-verified with the fix's own hal_alif patch set applied end-to-end
(confirmed via each build's `zephyr_modules.txt`):
`examples/connectivity/camera-mjpeg-stream` and
`examples/aen/aen-isp-ov5647-viewfinder` (both the AEN803 target,
`SHIELD="e1m_evk_rpi_csi raspberry_pi_camera_module_1"`) link clean with
`-DCONFIG_COMPILER_WARNINGS_AS_ERRORS=y` and 0 compiler warnings (the DTS
`simple_bus_reg`/`unique_unit_address_if_enabled` notices in both builds are
pre-existing and unrelated to this change). A bench image
(`camera-mjpeg-stream`, 30 fps, `scripts/bench/aen/aen-bench-shared.conf` +
`scripts/bench/aen/aen-flowc-itcm.conf`/`.overlay`) also exposes two new
diagnostic globals in `isp_pico.c`,
`isp_ae_diag_applied_int_time_max_us`/`isp_ae_diag_frame_period_us`
(readable over SWD, and LOG_INF'd at most once per second), reporting the
AE integration ceiling the LIBRARY actually holds (via the existing #2271
readback) and the active frame period it was derived from. Unverified on
silicon.

**Third cut (the actual root cause) -- bench run 244**: the "real fix"
above shipped and did NOT change the reported symptom. Bench run 244
(E1M-AEN803, OV5647, `camera-mjpeg-stream`, 30 fps requested) confirmed
`isp_apply_ae()` pushed the correct 30 fps ceiling
(`int_time_max_us=32667`) into `isp_calib_param.modules.ae.autoAttr`, but
the ISP library's own "VSI AE INFO" console trace showed `intLine` ramping
straight past that push's line-equivalent (~1029) and PINNING at exactly
3145 -- `sensor_attributes.h`'s `AE_SNS_DEFAULT_S.maxIntLine`, the fixed
10 fps boot-time default (patch 0006), never touched by either #2277 cut
above. Root cause: `VSI_MPI_ISP_InitAeSnsFunc()` (`isp_vsi_init()`)
registers `aeSnsFunc` -- whose `pfnGetAeDefault` callback
(`vsi_get_ae_default()`) hands the library `sensor_attributes` verbatim --
exactly ONCE, at device boot, well before any app has negotiated a frame
rate; `isp_calib_param.modules.ae.autoAttr` (this patch's earlier mirror)
is a DIFFERENT struct the library does not appear to enforce its
per-frame `intLine` ceiling from.

Real fix: a new `isp_vsi_sync_ae_sns_default(init_cfg, full_lines,
max_int_line)` (hal_alif patch 0011) updates `sensor_attributes.fullLines`/
`fullLinesStd`/`maxIntLine` and re-registers `aeSnsFunc` via
`VSI_MPI_ISP_InitAeSnsFunc()` so the library re-pulls it -- the only lever
found that actually reaches the ceiling bench run 244 observed. The
`full_lines`/`max_int_line` values (VTS at the active frame period, minus a
4-line margin) come from a new pure function in `isp_pico.c`,
`isp_ae_sns_full_lines_from_frmival()` (OV5647's own pixel_rate/HTS facts,
same convention as this file's existing `int_time_max_us` fallback
constant), called from `isp_apply_ae()` on every stream (re)start alongside
the existing `isp_calib_param` mirror (kept -- not proven dead: no bench
evidence isolates whether it affects anything besides the hard ceiling).

Two more diagnostics: `isp_ae_diag_sns_int_line` (hal_alif
`isp_api_wrapper.c`'s `vsi_int_time_update()`, 1 Hz `LOG_INF`) mirrors the
LAST `intLine` the library actually pushed to the sensor -- exactly the
value bench run 244's console trace showed pinning; `isp_pico.c`'s
`isp_ae_diag_sns_full_lines`/`isp_ae_diag_sns_max_int_line` mirror the
ceiling this sync call last pushed.

`tests/unit/isp_ae_calib_envelope_sync` gained 4 more cases (9 total)
mirroring `isp_ae_sns_full_lines_from_frmival()` and the new sync call's
field-copy; `tests/scripts/test_isp_ae_calib_envelope_sync_patch_mirror.py`
gained 2 more drift checks. Both new drift checks fail against 4990322ee
(the function doesn't exist in that commit's `isp_pico.c`; that commit's
patch 0011 makes no `sensor_attributes.*` assignment at all), pinning this
as a genuine regression test, not just a self-consistency check.
Re-built end-to-end against a scratch hal_alif copy carrying the updated
patch (both example targets, same flags as above, 0 warnings, confirmed
via `zephyr_modules.txt`). Bench re-run not yet performed as part of this
change.
