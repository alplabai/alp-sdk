### Added — `<alp/temperature.h>`, a portable read of the on-module ambient-temperature sensor (issue #2066)

The on-module TMP112 had no `<alp/*>` entry point — an app could reach it
only through the upstream Zephyr sensor API directly against a vendor
compatible string, same as the on-module RTC still does (repointing
`alp_rtc_open()` at that part is the separate #1814).

- **`alp_temperature_read_milli_c(int32_t *milli_c)`** — new, handle-less,
  index-less (`[ABI-EXPERIMENTAL]`).  Implemented as a single plain
  function per OS, the same no-registry/no-ops-header/no-handle-pool/
  no-conformance-array-entry shape as `alp_hw_info_read()` — but, unlike
  hw_info's EEPROM reader (built from already-portable `alp_i2c`
  primitives, so genuinely one shared translation unit), this class binds
  through Zephyr's own devicetree/sensor API with no portable equivalent
  to fall back to.  So it is a real per-OS split:
  `src/zephyr/temperature_zephyr.c` (Zephyr-only, gated internally on
  `CONFIG_SENSOR` + the `alp-temp0` DT alias's own status) plus
  `src/common/stub/stub_temperature.c` (baremetal/Yocto, unconditional
  `ALP_ERR_NOSUPPORT`) — the same split every other Zephyr-specific class
  uses (`stub_rtc.c`, `stub_wdt.c`, ...).  An earlier draft tried to keep
  it as one `_zephyr`-suffixed file compiled everywhere behind
  `#if defined(__ZEPHYR__)` guards; that broke both native_sim (a DT
  macro referenced outside a `__ZEPHYR__`-gated `#include` is a
  preprocessor syntax error, not a false condition — `&&` doesn't protect
  later terms of an `#if`) and, one line lower, the baremetal/Yocto builds
  for the identical reason. The stub is the more robust shape.
- Zephyr backend binds the metadata-emitted `alp-temp0` devicetree alias
  through the upstream sensor API — deliberately **not** by opening
  `chips/tmp112` over `alp_i2c_open()`.  AEN's BRD_I2C is standard-mode
  with no external pull-up, and `alp_i2c`'s `z_open` re-runs
  `i2c_configure()` with the caller's bitrate with no exclusivity check;
  a portable open at `alp_hw_info`'s 400 kHz would both silently
  reconfigure the bus under an app's own handle and be a real electrical
  fault on this board. The DT-bound path inherits the bus's own
  `clock-frequency` instead.
- Presence is a SoM fact, not a SoC one: it is **not** exposed through
  `<alp/cap.h>` / `<alp/soc_caps.h>` (those are generated per-SoC and
  would wrongly claim the sensor for every SoM sharing that die — RZ/V2N
  n44 already declares 2 on-die `temp_sensor`s of its own). No new
  `hw_info_build.h` macro either — that lands the first time an example
  needs to `#if` on presence.
- The generator's device alias is renamed `ambient-temp0` → **`alp-temp0`**,
  joining the existing `alp-`prefixed portable-alias namespace
  (`alp-i2cN`, `alp-lprtc-counter`); the two committed E1M-AEN801 board
  trees (`m55_he`/`m55_hp`) are regenerated to match.
- `src/zephyr/alp_banner.c`'s housekeeping line migrates onto the new
  call — its old `DT_HAS_COMPAT_STATUS_OKAY(ti_tmp112) &&
  defined(CONFIG_TMP112)` gate was a second, vendor-bound truth about
  presence that could disagree with the metadata-derived one; net
  deletion. The RTC half of housekeeping is untouched (still #1814).
- `metadata/chips/tmp112.yaml`'s `0x48` "default on E1M-AEN" address was
  stale — every AEN preset, `on-module-links.yaml`, the generated dts and
  the bench all say `0x40` (measured 2026-09-12 at 0x40, reg 0x00 = `1c
  10` = 28.0625 degC; `0x48` a clean NACK on 3 of 3 modules — the same
  class of bug that kept the stock `CONFIG_TMP112` driver from binding,
  #1978). Corrected, with a separate, still-unverified `0x48` entry kept
  for E1M-V2N.

**Coverage today**: AEN-Zephyr only. V2N/V2M are unproven end to end — no
V2N board devicetree carries a tmp112 node yet, and `E1M-V2N101.yaml`'s
own `0x48` is still "bench verification pending" — so every non-AEN
target returns `ALP_ERR_NOSUPPORT`, not silently claimed as "every SKU".
`examples/aen/aen-temp-sensor` is left on the upstream API unchanged — it
is documented as teaching the ADR 0017 layering; folding it together with
`examples/v2n/v2n-temp-sensor` is a natural follow-up, not this change.

**Not bench-run in this change.** The AEN path will be exercised by the
banner on the next bench session; this PR is native_sim/build-only.
