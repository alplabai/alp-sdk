### Fixed — cc3501e READY gate trusted a level read as proof the slave had re-armed, clocking phases into a stuck-HIGH pad near-instantly (#2105)

**Before:** `cc3501e_reply_gate()` (`chips/cc3501e/cc3501e_core.c`) read
`ctx->ready_pin` once per phase and, on HIGH, skipped its fixed inter-phase
settle outright — a HIGH read was trusted as proof the slave's SPI slave was
armed+idle. On an R2 AEN EVK bench module, the pad AEN example bridges
opened for this (Alif P2_6) is not the CC3501E's GPIO17 READY net at all: it
is E1M pad AH7 / I2S1_SCLK, which the EVK carrier maps to the Arduino
header's `CK_RST` (`metadata/boards/e1m-evk.yaml`) — a reset line that idles
HIGH — while the real READY net lands on E1M pad G3 / IO16 instead
(`metadata/e1m_modules/aen/from-cc3501e.tsv`, `from-alif.tsv`). Reading
`CK_RST`'s constant HIGH as "armed" produced near-zero settles on every
phase; with the gate trusting it, station connect never associated in 4 of 4
bench boots (run8), against 5 of 7 with the gate disabled.

**After this commit:** the line may only ever ADD delay, never remove it.
When `ctx->ready_pin` is populated, `cc3501e_reply_gate()` waits (bounded by
`CC3501E_READY_WAIT_US`) for the pin to read HIGH, and then **always** pays
the same fixed `fallback_us` settle a `NULL` `ready_pin` pays with no wait at
all — a HIGH read decides only how much *extra* time to wait before that
unconditional settle, so however wrong the read is, the worst case is
"waited a bit longer than necessary", never "clocked early". A stuck-HIGH
pad is found on the very first, zero-delay poll, so it costs exactly the
`ready_pin == NULL` timing and can never make a gate faster than gate-off; a
noisy or glitching pad cannot shorten a settle either; a genuinely
slower-than-the-fixed-settle slave (e.g. mid radio op) is the one case READY
still helps, by waiting out the real re-arm instead of guessing a fixed
number.

A new `CC3501E_READY_STUCK_LOW_STREAK` (3) bounds the cost of a genuinely
stuck-LOW (or disconnected) `ready_pin`: after 3 consecutive gates each burn
the full `CC3501E_READY_WAIT_US` without ever seeing HIGH, this process
stops *waiting* on it (`g_ready_ignored`, file-global — not per-`ctx`, and
`cc3501e_ready_line_was_stuck()` latches for diagnostics) and falls back to
paying only the fixed settle from then on. **The latch recovers:** firmware
can legitimately hold READY LOW across an entire radio op spanning several
gates, so once latched, each gate still takes one zero-wait read; a HIGH
there clears the latch and the streak so the next gate resumes the real
bounded wait. Each time the latch sets, the number of consecutive timeouts
needed to set it again doubles (3, 6, 12, then capped at 24, never reset), so
a line that is mostly LOW with an occasional HIGH read cannot keep re-buying
3 full waits under the transport lock. This can only ever remove a wasted *wait* — the settle itself
is always paid unconditionally, so none of this can make a gate return
early.

`ctx->ready_pin` is opt-in and left `NULL` by default on every AEN example
bridge on the R2 module: a board (or hand-reworked unit) that genuinely
wires GPIO17 to some Alif pin sets `fw->ready_pin` in its own
`cc3501e_bridge_bringup()`. Doing so while holding a stale assumption about
the wiring is safe for *link timing* (READY can never clock a phase early),
but not free: the wait runs while `cc3501e_request()` holds its internal
transport lock, so a wrong or slow `ready_pin` can make another caller see
`ALP_ERR_BUSY` after `CONFIG_ALP_SDK_CC3501E_REQUEST_LOCK_TIMEOUT_MS` —
documented on `ready_pin` itself (`include/alp/chips/cc3501e/core.h`), the
Kconfig (`zephyr/kconfigs/chips.kconfig`), and every example's opt-in
comment.

`tests/zephyr/cc3501e_host_driver` coverage asserts plain delay accounting,
never wall-clock time: stuck-HIGH pays exactly the 3 fallbacks (700 us);
stuck-LOW pays the bounded wait plus fallback on each of the first 3 gates,
then fallback only once the latch trips, recovering back to the full bounded
wait the moment a read comes back HIGH; a HIGH between two shorter runs of
timeouts resets the streak instead of letting it accumulate across the gap;
a noisy (flips-every-read) pad and a slower-to-arm slave both pay AT LEAST
the fallback total, never less. Mutation-verified: an early return on HIGH
(the pre-fix bug shape) turns the stuck-HIGH, noisy, and slow-to-arm cases
red; deleting the stuck-LOW latch turns the stuck-LOW case red; deleting the
streak reset on HIGH turns the timeout/HIGH/timeout/timeout case red;
reverting the latch-recovery read turns the latch-clears-on-HIGH case red;
disabling the threshold doubling turns the re-latch hysteresis case red —
each mutation turns exactly its own regression(s) red and nothing else.

**Out of scope for this fix, noted for follow-up:** on the E1M EVK, CC35
GPIO17 (the CC3501E's real READY output) is wired out to E1M pad G3 / IO16,
which the EVK carrier also exposes as `EVK_PIN_W_DISABLE2` — the M.2 E-key
slot's Bluetooth-disable line (`metadata/boards/e1m-evk.yaml`). READY
toggling (and the separate async-event attention pulses, `#1721`/`#130`)
may therefore also toggle that M.2 signal on a board with an M.2 E-key card
fitted; this was not investigated further here.
