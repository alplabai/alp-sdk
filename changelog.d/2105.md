### Fixed — cc3501e READY gate could return early and clock into an un-rearmed slave; it can now only ADD delay, never remove it (#2105)

`cc3501e_reply_gate()` (`chips/cc3501e/cc3501e_core.c`) used to try to
**prove** `ctx->ready_pin` trustworthy from the GPIO reads themselves, so a
proven line could skip its fixed inter-phase settle outright. Three
successive designs here each tried a different proof and each was defeated
in turn: a bare level HIGH proved it on the very first read (a stuck-high
pad reached that in one call); requiring a single raw difference between
two reads still let pure per-read noise accumulate enough coincidental
agreement to be trusted eventually (proving around ping 265 of a 5000-ping
run, after which most gates returned short); and even several DEBOUNCED,
agreeing edges gated to "busy-expected" call sites could still return on a
stale HIGH once proven, clocking into a slave that had not actually
re-armed (100 of 100 back-to-back PINGs did exactly that once a line got
proven that way). Trying to prove anything from this pin was the wrong
move.

**The line may now only ADD delay, never remove it.** When `ctx->ready_pin`
is populated, `cc3501e_reply_gate()` waits (bounded by the existing
`CC3501E_READY_WAIT_US`) for the pin to read HIGH, and then **always** pays
the same fixed `fallback_us` settle a `NULL` `ready_pin` pays with no wait
at all. A HIGH read decides only how much *extra* time to wait before that
unconditional settle, so however wrong the read is, the worst case is
"waited a bit longer than necessary" — never "clocked early". Consequences:
a stuck-HIGH pad is found on the very first, zero-delay poll, so it costs
exactly the `ready_pin == NULL` timing and can never make a gate faster
than gate-off; a noisy or glitching pad cannot shorten a settle either,
whatever it reads; a genuinely slower-than-the-fixed-settle slave (e.g.
mid radio op) is the one case READY still helps, by waiting out the real
re-arm instead of guessing a fixed number. The old LOW-before-HIGH spin
that existed specifically to dodge a stale HIGH is gone and not missed:
since the fixed settle now always runs after any HIGH, stale or not, the
slave gets its settle regardless of which HIGH ended the wait.

A new `CC3501E_READY_STUCK_LOW_STREAK` (3) bounds the cost of a
genuinely stuck-LOW (or disconnected) `ready_pin`: after 3 consecutive
gates each burn the full `CC3501E_READY_WAIT_US` without ever seeing HIGH,
the ctx stops waiting on it entirely (`cc3501e_ready_line_was_stuck()`
latches) and falls back to paying only the fixed settle from then on —
this can only ever remove a wasted *wait*, the settle itself is still paid
unconditionally either way, so it cannot make a gate return early.

Bench evidence review corrected the pin-routing claim along the way:
`ctx->ready_pin` is not wired by AEN example bridges by default any more on
the R2 module `e1m-aen-evk-01` holds, because Alif P2_6 there is E1M pad
AH7 / I2S1_SCLK — the EVK's Arduino CK_RST net (`metadata/boards/e1m-evk.yaml`)
— not the CC3501E's GPIO17 READY signal, which lands on E1M pad G3 / IO16
instead (`metadata/e1m_modules/aen/from-cc3501e.tsv`, `from-alif.tsv`). A
separately hand-reworked r1 unit did once have READY genuinely working —
its own serial was never recorded, and it is a DIFFERENT unit than the one
measured for the phase-settle timing bench notes elsewhere in this file
(`cc3501e_sockets.c`'s `SOCK_RECV` cap comment, `changelog.d/1799.md`). The
`CC3501E_BRIDGE_PIN_READY` macro is removed from all 13 affected example
headers along with the now-pointless fixed index; a board where the READY
net really is routed to the host opts in by setting `fw->ready_pin`
directly in its own `cc3501e_bridge_bringup()`, documented in one place per
app. The 13 affected board overlays no longer mux, input-enable, or
declare an `alp_pins` entry for P2_6 by default (`aen-cc3501e-bringup`
keeps its own `gpio2`/P2_6 wiring, relabelled, since its separate
`alp,cc3501e-attn` node still needs the pad); `aen-sdcard-readout`'s
`SD_RST` moved from index `[3]` to `[2]` (`SD_RST_PIN_ID` updated in
`src/main.c`).
`examples/peripheral-io/alp-console/src/cc3501e_bridge.c`'s dead
`cc3501e_bus_ready()` / `bodge_ready_raw()` / `aen_bodge_init()` — a P2_6
pinctrl mux nothing ever read back — are removed, along with its overlay's
now-unused `&gpio2` node.

`tests/zephyr/cc3501e_host_driver` coverage now asserts plain delay
accounting instead of trying to test a proof: stuck-HIGH pays exactly the
3 fallbacks (700 us); stuck-LOW pays the bounded wait plus fallback on each
of the first 3 gates, then fallback only once the latch trips; a noisy
(flips-every-read) pad and a slower-to-arm slave both pay AT LEAST the
fallback total, never less. Mutation-verified: an early return on HIGH (the
pre-fix bug shape) turns the stuck-HIGH, noisy, and slow-to-arm cases red;
deleting the stuck-LOW latch turns the stuck-LOW case red — each mutation
turns exactly its own regression(s) red and nothing else.

**Out of scope for this fix, noted for follow-up:** on the E1M EVK, CC35
GPIO17 (the CC3501E's real READY output) is wired out to E1M pad G3 / IO16,
which the EVK carrier also exposes as `EVK_PIN_W_DISABLE2` — the M.2 E-key
slot's Bluetooth-disable line (`metadata/boards/e1m-evk.yaml`). READY toggling
(and the separate async-event attention pulses, `#1721`/`#130`) may therefore
also toggle that M.2 signal on a board with an M.2 E-key card fitted; this
was not investigated further here.
