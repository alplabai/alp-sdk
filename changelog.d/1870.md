### Fixed — the three CC3501E examples never enabled `i2c2`, so the EEPROM manifest read structurally could not succeed (#1870)

`alp_hw_info_read()` opens `bus_id = 0`, which resolves through the
`alp-i2c0` alias to the SoC's `i2c2` (the on-module EEPROM manifest bus,
disabled by default in the base dtsi). `examples/aen/aen-cc3501e-gpio`,
`aen-cc3501e-bringup` and `aen-cc3501e-companion-tour` never enabled that
node or declared the alias — zero references in all three, versus two in
`examples/peripheral-io/alp-console`'s bench-validated overlay — so the
manifest read failed for a *configuration* reason on modules that are
otherwise fully provisioned. The banner fell back to the raw board target
instead of the SoM identity, and, more importantly, the hw_rev-mismatch
guard added for #1853/#1859 keys off exactly this read: with it inert, a
compiled-vs-actual revision mismatch on these examples — which carry the
CC3501E GPIO proxy route table, i.e. exactly where a mismatch drives the
wrong chip's pins — went undetected.

Each of the three real-board overlays now carries the same `i2c2` pinctrl
group, `&i2c2 { status = "okay"; ... }` and `alp-i2c0` alias as
`alp-console`'s overlay, byte-for-byte the same pad config (SCL `P5_6`
/ SDA `P5_7`, input-enable, bias-pull-down — the pad DSC value Alif's
reference uses, do not "correct" to pull-up). `i2c2` is the EEPROM/manifest
bus that exits at the connector and is pulled up on the carrier
(`R95`/`R96` populated); it is a different bus from the on-module BRD_I2C
housekeeping bus (#1848), whose pull-ups are absent.

Verified with `west build` (`alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he`)
for all three: the resolved `zephyr.dts` shows `i2c2` `status = "okay"`
with `pinctrl-0 = <&pinctrl_i2c2>` and the `alp-i2c0` alias resolving to it.
`aen-cc3501e-bringup`'s `CONFIG_MAIN_STACK_SIZE=32768` is unchanged by the
new bus. Bench-gated: not yet re-verified against a physical E1M-AEN801.
