### Fixed — a timed-out GATT read/write left the BT host holding a dead stack frame (#1620)

`z_gatt_read()` / `z_gatt_write()` handed Zephyr's BT host an **automatic**
`ble_read_ctx` / `ble_write_ctx` and, on the `k_sem` timeout path, returned
without cancelling the outstanding ATT procedure. When the peer's response
eventually arrived on the BT RX thread, the completion callback cast `params`
back to that dead stack frame and wrote through it — a use-after-return into
another thread's stack, from a path the caller had no way to see.

Zephyr offers no general "cancel this ATT procedure" call, so the fix is an
ownership change rather than a cancel: the contexts move into
`_read_ctx_pool` / `_write_ctx_pool`, claimed with the existing
`alp_slot_try_claim()` and released by whichever side wins a one-byte
`alp_lifecycle_cas()`. A timeout marks its slot `ABANDONED` and returns; the
late callback loses the CAS, touches nothing, and frees the slot itself. The
issue's own suggestion — putting the context inside `struct ble_conn_be` — was
rejected on inspection, because `_conn_be_free()`'s memset would then clear a
context a live registration still points at.

Three caller-visible consequences, all now documented on the public
declarations in `include/alp/ble.h` rather than left for someone to discover:

- **`ALP_ERR_BUSY` is a new return code** for both functions, returned when
  every concurrent-procedure slot is held. It was previously impossible.
- **A timeout does not cancel anything.** `ALP_ERR_TIMEOUT` now means "not
  answered in time", not "abandoned", and the slot stays held until the peer
  answers or the link drops. `timeout_ms == 0` is the pathological case: each
  such call burns a slot, and the default
  `CONFIG_ALP_SDK_BLE_MAX_GATT_PROCS` is 4.
- **A procedure completing just after the deadline now returns its real
  result** instead of `ALP_ERR_TIMEOUT`.

`alp_ble_gatt_write()` additionally documents that the host may re-read the
caller's `data` buffer after the call returns. In upstream Zephyr's BT host, a
long write goes out as a prepare-write sequence (`gatt_prepare_write()`), and
`att_req_retry()` re-encodes the request on an encryption-change retry under
`CONFIG_BT_SMP` even for a **short** write — wider than the long-write case the
issue named. Both re-read `params->data`, which the caller owns.

**Not closed by this change:** the issue's regression test for the abandon path
is still owed. `native_sim` has no BLE controller, so the late-callback race
cannot be driven by a real peer; it needs a test seam in the backend, and the
existing `tests/zephyr/ble_gatt_server` cases only ever exercise the
`LIVE -> DONE` win. The abandon path, the CAS loss, and the `ALP_ERR_BUSY`
branch are unexecuted code.
