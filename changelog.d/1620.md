### Fixed — a timed-out GATT read or write left a dead stack frame registered with the Bluetooth host (#1620)

`z_gatt_read` and `z_gatt_write` in `src/backends/ble/zephyr_drv.c` built their
completion context as an **automatic** object, handed its `.params` to
`bt_gatt_read()` / `bt_gatt_write()`, and returned on a finite `k_sem_take`
timeout without cancelling — which Zephyr offers no way to do. `params` must stay
valid until the callback fires or the connection drops.

When the peer's response finally arrived on the BT RX thread, `ble_read_cb` cast
`params` back to the returned-from frame and wrote through it — `memcpy(ctx->out,
data, n)`, `*ctx->out_len = n`, `ctx->result = ALP_OK` — then gave a semaphore in
recycled memory, corrupting the kernel wait queue. `ble_write_cb` had the
identical shape. A slow or unresponsive peer is normal BLE, not an exotic fault.

The comment above both contexts asserted the opposite, which is what made the bug
look deliberate to a reader:

> "the ctx must remain valid until then, which the `k_sem_take()` call below
> guarantees for an on-stack instance"

A `k_sem_take` with a finite `K_MSEC(timeout_ms)` guarantees no such thing. That
comment is replaced with what is now true.

Both contexts now live in `struct ble_conn_be`, so their lifetime is the
connection's rather than the calling frame's, and each connection carries a
`read_in_flight` / `write_in_flight` flag. On timeout the op returns
`ALP_ERR_TIMEOUT` but deliberately leaves the flag **set** and the context live —
the host has not finished with it just because this side stopped waiting — and
the completion callback clears the flag when the late response lands. A second
read or write on a connection whose slot is still claimed returns `ALP_ERR_BUSY`.

The guard is checked **before** `c->bt`, and before anything is handed to the
host. That ordering is the point: it is what makes leaving a pool-owned context
live across a timeout safe.

Sibling audit, so this does not read as a spot fix: `bt_gatt_notify`
(`gatt_notify`) is synchronous and holds no params across a wait;
`bt_gatt_service_register` registers out of `_gatt_svc_pool[]`, already
pool-owned; and this backend has no discovery or subscribe path. `z_gatt_read`
and `z_gatt_write` were the only two sites of this shape.

Regression tests: `test_gatt_read_refuses_while_a_read_is_in_flight` and
`test_gatt_write_refuses_while_a_write_is_in_flight` in
`tests/zephyr/ble_gatt_server/`, driving the real ops through two new
`CONFIG_ZTEST`-only seams. They pass a non-NULL **sentinel** `bt` that is never
dereferenced because the guard returns first — so if the guard is ever reordered
after `bt_gatt_read()`, the tests fault instead of quietly passing.

**Two things this does not do.** The corruption half — a late response landing
after a timeout — needs a real peer and is bench-gated on E1M-AEN801; a green
`native_sim` run is not evidence for it. And `bt_gatt_write`'s `params.data`
still points at the **caller's** buffer: Zephyr copies it into the ATT PDU
immediately for a short write, but a **long** write (`len > ATT_MTU − 3`) is sent
across later prepare-write PDUs, i.e. after a timed-out `alp_ble_gatt_write` has
returned. Closing that means either copying the payload into the context or
enforcing the `≤ ATT_MTU − 3` bound `include/alp/ble.h` already documents — the
latter would remove working long-write support, so it is left to a follow-up
rather than decided here.
