### Fixed — CPI stop paths polled a useless `BUSY` bit, and `flush(cancel)` could race the completion work item into stalling the stream (#2342)

`zephyr/drivers/video/video_alif.c` stopped the CPI at three call sites
(`hw_cam_cpi_only_stop()` for a buffer-starvation pause, #2287;
`alif_cam_stream_stop()`; `alif_cam_flush(cancel)`) with the same
`CAM_CTRL = 0` write followed by a `BUSY` poll (up to 1000 x `k_msleep(1)`)
before the soft reset. A register-level bench diagnostic (E1M-AEN803
2026W36-0001, runs 336-339) found `BUSY` reads back 0 immediately after the
`CAM_CTRL = 0` write even while the DMA is still actively overrunning the
buffer — so that poll proves nothing about whether the write took hardware
effect. `hw_cam_cpi_only_stop()`'s only caller runs after a `STOP` interrupt,
when the `SNAPSHOT` capture has already auto-stopped in hardware, and
`alif_cam_stream_stop()` stops the CSI-2 endpoint/sensor source before
touching `CAM_CTRL` — so in the paths this driver actually exercises, the
soft reset the poll was waiting to reach normally followed within
microseconds regardless. Never write `CAM_AXI_ERR_STAT` (CPI+0x18) to
"clear" it: bench-confirmed that register is not writable on this CPI — a
write bus-faults.

The three call sites now share one `hw_cam_quiesce()` helper (unconditional
soft reset, no `BUSY` poll, `CAM_INTR` cleared afterwards) instead of each
repeating the `CAM_CTRL = 0` + poll + reset sequence — `alif_cam_flush(cancel)`
previously never cleared `CAM_INTR` after its reset, unlike the other two
call sites; it now does. `alif_cam_flush(cancel)` also masks the `STOP`
interrupt before cancelling the pending AXI work-helper item (same ordering
as `isp_flush()`), instead of cancelling first: a `STOP` landing in that
window could resubmit the work item, which then ran after the quiesce had
already reset the CPI, hit the empty-IN-FIFO "Unexpected condition" branch,
cleared `is_streaming`, and stalled the stream. That work-helper item now
also checks `is_streaming` immediately after taking its lock and returns
quietly if a stop already ran, instead of logging a spurious error later in
the same function. If a `flush(cancel)` leaves the stream still marked
running, it now sets `starved` so the next `video_enqueue()` resumes capture
through the existing starved-resume path, instead of leaving the CPI parked
with `INTR_STOP` masked and nothing left to restart it. The ISR's post-`STOP`
park write no longer clears `FIFO_CLK_SEL` mid-capture if it happens to run
after the CPI has already been re-armed for the next frame. `capture-mode =
"continuous"` is now rejected at DT build time (removed from the
`alif,cam.yaml` enum) rather than at driver init — nothing in this repo's DT
overlays sets it, and none of this driver's stop paths implement a safe
mid-frame abort for a mode with no hardware auto-stop boundary.

Bench-proven on the register-level diagnostic only (E1M-AEN803
2026W36-0001, runs 336-339: the `CAM_CTRL = 0` write and the 3-step soft
reset were characterized on real silicon). The driver-level changes in this
commit — the shared helper, the flush/work-helper race fix, the ISR park
change, the DT enum change — have not themselves been re-run on silicon;
only `-Werror` builds have been verified: `camera-mjpeg-stream` (IMX335,
IMX296, OV5647), `aen-camera-firstlight` (IMX335, OV9281),
`aen-isp-capture` (IMX335), `aen-isp-regcheck`.

Closes #2342.
