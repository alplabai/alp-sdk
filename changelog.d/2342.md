### Fixed — a mid-frame `video_flush(dev, true)` on the E8 CPI no longer overruns the frame buffer or hangs the SoC (#2342)

On the CPI AXI capture path, `alif_cam_flush(cancel)` in
`zephyr/drivers/video/video_alif.c` stopped a capture in progress with
`CAM_CTRL = 0`, then a `BUSY` poll (up to 1000 x `k_msleep(1)`), then the
soft reset. On E1M-AEN803 2026W36-0001 with an IMX335 (bench run 340), a
mid-frame cancel with the old driver kept the DMA writing past the buffer
through the rest of SRAM0 — 1,543,664 B past a 128 KiB guard — with no
fault raised. The register-level diagnostic (runs 336-339) showed why:
`CAM_CTRL = 0` does not stop the DMA (about 2x frame overrun), `BUSY` reads
0 while the DMA is still writing, and only the 3-step soft reset
(`CAM_CTRL` 0, then `SW_RESET`, then 0) stops a frame mid-capture.

A soft reset issued while a frame is still being written is not safe
either: the first revision of this fix, which reset the CPI immediately on
cancel, hung the SoC in 12 of 212 mid-frame cancels (run 341). The core
stalled, SRAM0 writes never completed, and only a power cycle recovered it.
Resets at a frame boundary (0/240) or after the pixel source was stopped
(0/50) never hung.

What changed:

- `alif_cam_flush(cancel)` masks the `STOP` interrupt, cancels the pending
  completion work item, then waits (1 ms steps, 500 ms cap) for the armed
  frame's hardware `STOP` before the soft reset, so the reset never lands
  on an active AXI write burst. If the source has stopped and no `STOP`
  arrives, it logs a warning and resets after the timeout.
- `hw_cam_cpi_only_stop()`, `alif_cam_stream_stop()` and
  `alif_cam_flush(cancel)` share one `hw_cam_quiesce()` helper: mask
  interrupts, soft reset, clear `CAM_INTR`, end at `CAM_CTRL = 0`. The
  useless `BUSY` polls are gone. The helper's doxygen states the rule:
  stop the source or wait for frame end first.
- Masking `STOP` before cancelling the work item (the `isp_flush()`
  ordering) closes a window where a late `STOP` resubmitted the work item
  into an empty IN-FIFO and stalled the stream. The work item returns
  quietly once a stop has run. A cancel while streaming sets `starved`, so
  the next `video_enqueue()` restarts capture.
- The ISR's post-`STOP` write keeps `FIFO_CLK_SEL` set instead of writing
  0, so a late ISR after a re-arm clears only `START`.
- `capture-mode = "continuous"` is rejected at devicetree build time
  (removed from the `alif,cam.yaml` enum). No overlay in this repo used
  it, and no stop path here has a safe abort for a mode without a
  hardware frame-end boundary.
- Never write `CAM_AXI_ERR_STAT` (CPI+0x18): it is not writable on this
  CPI, and a write bus-faults.

Bench, this revision (E1M-AEN803 2026W36-0001, IMX335, runs 342-343):

- Mid-frame `video_flush(dev, true)`: 0 hangs and 0 overruns in 520
  events, 200 of them on the stock devicetree. The aborted buffer was
  untouched after flush returned, restart worked every time, and flush
  latency was at most 29.7 ms (one frame).
- Mid-frame `video_stream_stop()`: 0 hangs and 0 overruns in 100 events.
- Forced timeout path (sensor put in standby mid-frame, then flush): the
  timeout fired 81 times out of 85, with 0 hangs and 0 overruns, and
  restart worked every time.
- `camera-mjpeg-stream`: 2471 frames at 26 fps, no errors.

Not fixed here: restart after a mid-frame `video_stream_stop()` on the CSI
endpoint fails the same way on the base driver (#2351).

Closes #2342.
