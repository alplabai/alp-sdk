### Fixed — `<alp/inference.h>` claimed no adapter produces `ALP_INFERENCE_MODEL_EXECUTORCH` (#1517)

`ALP_INFERENCE_MODEL_EXECUTORCH`'s Doxygen said "RESERVED -- no adapter produces this format
and no backend consumes it, so a blob claiming it is rejected with `ALP_ERR_INVAL`". Two of
those three claims were false: `ExecutorchAdapter` (`scripts/alp_model/adapters/executorch.py`)
is registered in `build.py`'s default adapter list and produces `format="executorch"` for any
`.pte` source, and `_fmt_enum()` in `src/backends/inference/alp_model_select.c` explicitly
accepts the `"executorch"` string and decodes it to this enumerator instead of rejecting it.

Only "no backend consumes it" holds: none of `tflm.cpp`, `ethos_u_aen.cpp`, `ethos_u_n93.cpp`,
or `sw_fallback.c` under `src/backends/inference/` branch on `cfg->format`, so an ExecuTorch
blob still ends up handed to the CPU/TFLM backend, which tries to verify the raw `.pte` bytes
as a TFLite flatbuffer and fails that verification -- landing on `ALP_ERR_INVAL` by coincidence
of the TFLM backend's own input validation, not a deliberate format-enum rejection.

The comment now describes the real split: the write side (host-side `.alpmodel` build) is live
and produces this format; the read side (on-device execution) has no consumer yet, and the
`ALP_ERR_INVAL` a caller sees comes from the CPU/TFLM backend's flatbuffer verifier, not a
guard on the format enum itself.
