### Changed — `<alp/power.h>` mode ladder, retention, and wake-source contract settled while still `[ABI-EXPERIMENTAL]` (#1813)

`<alp/power.h>` could not express what the Alif Ensemble E8 actually offers,
and it is `[ABI-EXPERIMENTAL]` precisely so this can be fixed before an AEN
power backend freezes against it (`docs/abi-markers.md` confirmed before
touching the header — no ABI-snapshot major-bump gate applies pre-1.0 to an
experimental symbol; `docs/abi/v0.16-snapshot.json`, the CURRENT snapshot
per `metadata/sdk_version.yaml`'s still-0.16.0 `version:`, is regenerated in
place for the new symbols, following the same-week precedent set by
`bc6974d3` — see the ABI-snapshot note at the end).

- **`ALP_POWER_MODE_STOP`** — a fifth rung on `alp_power_mode_t`, below
  `STANDBY`. The E8's STOP ladder (datasheet Table 5-5) runs from a ~900 nA
  floor at STOP_5 (nothing retained) up through low-uA levels depending on
  what's retained (e.g. STOP_2 retains the 4 KB Utility SRAM at ~1.1 uA); the
  SDK had no way to name it. The two generic backends registered for the
  `power` class today, `zephyr_pm_policy.c` and `yocto_drv.c`, have nothing
  deeper than `PM_STATE_SUSPEND_TO_RAM` / `"mem"` to offer, so both now round
  STOP DOWN to that state explicitly (not through their `default:` case,
  which rounded to the SHALLOWEST state instead) and report
  `alp_power_wake_info_t::realised_mode` as `STANDBY`, never `STOP` — a
  caller is never told the backend reached a depth it never proved.
- **`alp_power_configure_retention()` + `alp_power_retain_t`** — a portable
  retention descriptor (`ALP_POWER_RETAIN_NONE` / `_UTILITY` / `_TCM` with a
  `retain_kb` field / `_FULL`), not a raw vendor bitmask, mapping onto
  `SERVICES_power_mem_retention_config`'s bitmask on a real E8 backend.
  `ALP_POWER_RETAIN_TCM` always rounds UP to the backend's own retention
  granularity — never `ALP_ERR_NOSUPPORT` for a `retain_kb` that doesn't land
  exactly, which the header's first draft contradicted itself on.
  `{ALP_POWER_RETAIN_TCM, retain_kb=0}` is rejected as `ALP_ERR_INVAL` (not a
  valid spelling of "retain nothing" — use `ALP_POWER_RETAIN_NONE`).
  Optional on the backend vtable (`alp_power_ops_t::configure_retention` may
  be `NULL`): a backend with no opinion accepts `ALP_POWER_RETAIN_NONE` as a
  no-op and returns `ALP_ERR_NOSUPPORT` for anything else. Mirrored into the
  handle only on `ALP_OK`, same reasoning as the wake bitmap below.
- **`alp_power_wake_capabilities()`** — a new dedicated accessor reporting
  which `ALP_POWER_WAKE_*` bits the active backend can arm. Deliberately
  NOT a field on `alp_power_capabilities()`'s existing `alp_capabilities_t`:
  that struct's `flags` is the cross-class `alp_instance_cap_t` bitmap every
  peripheral class shares (`cap_instance.h`), and its bit values collide
  numerically with `ALP_POWER_WAKE_*` one-for-one (`ALP_INSTANCE_CAP_DMA` ==
  `ALP_POWER_WAKE_RTC` == bit 0, `HW_OVERSAMPLE` == `WAKE_GPIO`, and so on) —
  overloading it would have made `alp_capabilities_has(caps,
  ALP_INSTANCE_CAP_DMA)` return true for a power handle that merely armed an
  RTC wake. `alp_power_ops_t::open()` gained a dedicated `wake_caps_out`
  output parameter (a separate channel from the existing `caps_out`) so
  every backend reports it without touching the shared struct.
- **`ALP_POWER_WAKE_COMPARATOR` / `ALP_POWER_WAKE_BROWNOUT`** — two wake
  bits with no earlier portable equivalent (the E8 LPCMP analog threshold
  wake and brown-out detect).
- **Reported-capability + error contract for wake sources, enforced
  centrally.** `<alp/power.h>` previously documented "unsupported bits are
  silently ignored" on the `ALP_POWER_WAKE_*` bitmap, directly contradicting
  `alp_power_configure_wake_source()`'s own already-documented
  `ALP_ERR_NOSUPPORT` return. That contradiction is resolved in the honest
  direction: `src/power_dispatch.c`'s `alp_power_configure_wake_source()`
  now rejects, for EVERY registered `power`-class backend in one guard, any
  bitmap containing a bit outside what `alp_power_wake_capabilities()`
  reports — not a per-backend duplicated check. All three backends
  registered today report accurately: `zephyr_stub` (0, the AEN-default —
  #1812), `zephyr_pm_policy` (RTC/GPIO/UART_RX/TIMER, the four sources it
  has always documented delegating to a peripheral driver — not USB/
  ETH_LINK, which it never actually could arm), and `yocto_drv` (0 — its
  bitmap parameter has no sysfs knob at all; only `wake_after_ms` drives a
  real wake via the RTC wakealarm). `src/backends/ext/renesas/power.c`
  implements no `power`-class vtable of its own (it's a vendor-ext bypass
  reading the dispatcher's mirrored bitmap directly), so it inherits the fix
  automatically once a rejected bitmap is no longer mirrored into the
  handle on failure.

**ABI-snapshot precedent.** `metadata/sdk_version.yaml` still reads
`version: 0.16.0` / `status: released`, and `v0.16.0` is tagged, so naively
regenerating `docs/abi/v0.16-snapshot.json` looked like rewriting shipped
history. It isn't: `bc6974d3` (`feat(cc3501e): host driver + console for the
SPI1 bridge passthrough (#1842)`), merged to `dev` on 2026-08-30 — a week
after the `v0.16.0` tag, with `sdk_version.yaml` unchanged — directly edited
`docs/abi/v0.16-snapshot.json` in place for its own new public symbols
("The ABI snapshot is regenerated for the new fields", per its commit
message). The tagged commit itself is untouched; the file literally named
`v0.16-snapshot.json` on `dev`'s HEAD is a rolling ledger of the CURRENT
`[ABI-EXPERIMENTAL]`+`[ABI-STABLE]` surface, not a frozen artifact of the
tag, until whatever cuts v0.17.0 renames/regenerates it. This change follows
that exact precedent rather than inventing a new one or bumping the version
file unilaterally.
