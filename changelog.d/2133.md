### Fixed — `alif_pdm.c` ignored the Zephyr `dmic` contract; `<alp/audio.h>` PDM capture returned `ALP_OK` then read nothing (#2133)

`alp_audio_in_open()` + `alp_audio_in_start()` returned `ALP_OK` on the E1M-AEN801's HP PDM mics, then every `alp_audio_in_read()` timed out with an empty FIFO. `dmic_alif_pdm_configure()` (`zephyr/drivers/audio/alif_pdm.c`) broke the standard Zephyr `dmic` API contract two ways: it read `req_chan_map_lo`'s low byte VERBATIM as the hardware channel-enable mask instead of decoding the standard `dmic_build_channel_map()` nibble encoding, and it never left the PDM clock-mode field `MICROPHONE_SLEEP` nor programmed per-channel FIR/gain — only the Alif-specific `pdm_mode()`/`pdm_channel_config()`, which a standard `dmic` consumer has no reason to call, did that. The portable `src/backends/audio/zephyr_drv.c` backend used the standard encoding correctly, so it was the one broken by the driver's divergence: for its 2-channel request the verbatim read produced `0x10` (hardware channel 4 only) instead of `0x03` (hardware channels 0 and 1, where the EVK's mics actually are). Fixed by making the driver honour the contract itself with a new dependency-free translation header, grounded in the register layout, HWRM 15.7.4.3.1's even/rising-odd/falling edge rule, and the bench-proven example's raw bitmask (`zephyr/drivers/audio/alif_pdm_chanmap.h:21` ("hw_channel = (pdm_controller * 2) + lr")); it also rejects a duplicate or out-of-order map the ISR cannot honour. **Register-level proof on `e1m-aen-evk-03`**: `PDM_CONFIG_REGISTER` read back `0x00010033` (channels 0/1/4/5, mode 1), the FIFO count moved, and every read returned a full block with `rc=0` — this proves the channel-map/driver-plumbing fix; it does NOT by itself prove real acoustic capture at that mode's rate (see the round 3 correction below).

**Round 2 correction — the rate table was wrong.** `PDM_MODE_STANDARD_VOICE_512_CLK_FRQ` was first keyed to 16000 Hz; HWRM Table 15-118 and the DFP's `ARM_PDM_MODE_AUDIOFREQ_8K_DECM_64` name both say mode 1 is 512 kHz clock / decimation 64 / **8 kHz** Fs, and the bench 1600-frame-per-~200 ms cadence agreed. The table now keys mode 1 to 8000 Hz, the register-level-proven entry (`zephyr/drivers/audio/alif_pdm.c:227` ("{ 8000U, PDM_MODE_STANDARD_VOICE_512_CLK_FRQ, 512000U },")), and adds mode 4 (`PDM_MODE_HIGH_QUALITY_1024_CLK_FRQ`, 1024 kHz clock, the SAME decimation ratio, 64, as mode 1) for 16000 Hz (`zephyr/drivers/audio/alif_pdm.c:240` ("{ 16000U, PDM_MODE_HIGH_QUALITY_1024_CLK_FRQ, 1024000U },")). Reusing `pdm_default_fir_voice512` on mode 4 is vendor-sourced — Alif's own driver test applies the same per-channel FIR tables across modes 1-9 with no FIR switch (`sdk-alif tests/drivers/pdm/src/alif_test_pdm.c`, FIR tables + mode select) — but mode 4 is still a **hypothesis**, and (see the round 3 correction below) both modes turned out to be below this EVK's mics' clock minimum regardless. `PDM_MODE_*` names encode only the clock, not Fs; every mode this round could ground against HWRM Table 15-118 now carries a rate comment (`zephyr/include/zephyr/drivers/pdm/pdm_alif.h:25` ("#define PDM_MODE_STANDARD_VOICE_512_CLK_FRQ 0x01UL /* 512 kHz clk, decim 64 -> 8 kHz Fs */")). `configure()` also now validates the resolved mode's PDM clock against the caller's `dmic_cfg.io` window, previously read by nothing (`zephyr/drivers/audio/alif_pdm.c:436` ("if (pdm_clk_hz < eff_min) {")) — both portable callers' windows were widened at this point to admit the proven 512 kHz clock (round 3 reverts the backend's widening — see below; `examples/aen/aen-pdm-mic-alif/src/main.c:153` (".min_pdm_clk_freq = 500000,") is the example's still-generic window, now superseded by the board overlay's DT range as the real constraint).

**Round 2 correction — power regression.** `configure()` used to write the clock-mode field itself, so the block started sampling — and PDM_C0/PDM_C2 stayed clocked — the instant `dmic_configure()` returned, and `DMIC_TRIGGER_STOP` never wrote `MICROPHONE_SLEEP` back, so the mics clocked forever after `alp_audio_in_stop()`/`close()`. The resolved mode is now stored in `pdm_data` and written only on `DMIC_TRIGGER_START` (`zephyr/drivers/audio/alif_pdm.c:735` ("pdm_mode(dev, pdata->clk_mode);")); `DMIC_TRIGGER_STOP` (`zephyr/drivers/audio/alif_pdm.c:702` ("pdm_mode(dev, PDM_MODE_MICROPHONE_SLEEP);")) and a `PM_DEVICE_ACTION_SUSPEND` (`zephyr/drivers/audio/alif_pdm.c:1174` ("pdm_mode(dev, PDM_MODE_MICROPHONE_SLEEP);")) both write `MICROPHONE_SLEEP` back.

**Round 2 addition — APB write spacing.** HWRM 15.7.5.3.1 warns against back-to-back `PDM_CTL0` (`PDM_CONFIG_REGISTER`) writes with no APB transactions between them; the channel-enable write in `configure()` followed by the (now START-side) clock-mode write had too little spacing. `pdm_ctl0_write_spacer()` (`zephyr/drivers/audio/alif_pdm.c:289` ("static void pdm_ctl0_write_spacer(const struct device *dev)"), ≥4 dummy reads of the read-only FIFO status register) now runs before every `PDM_CONFIG_REGISTER` write.

**Round 2 addition — stale sticky status on START.** HWRM 15.7.5.3.5: `PDM_ERROR_IRQ`/`PDM_WARN_IRQ` are edge-triggered, sticky, clear-on-read; because the mode write starts sampling immediately and the 4-bit FIFO count field overflows in ~1.9 ms at 8 kHz, a few ms of scheduling/printf delay before `enable_interrupt()` could latch an already-serviced overflow — `enable_interrupt()`'s own write would then have `pdm_error_handler()` silently clear the overflow-enable bit for the rest of the session, with block 0 starting with stale pre-clear samples followed by a gap. `DMIC_TRIGGER_START` now writes the mode, THEN read-clears both sticky status registers and pulses `FIFO_CLR`, THEN enables interrupts — the order is load-bearing (nothing to clear before the mode write; nothing latched once cleared before `enable_interrupt()`).

`examples/aen/aen-pdm-mic-alif` moves onto the standard contract and now measures the ACHIEVED sample rate instead of only checking "PCM varies" — a check that never would have caught round 1's mislabelled rate: it counts frames across `dmic_read()` calls and divides by elapsed `k_uptime_get()` time, excluding the first read as a startup-latency anchor, and requires the result within ±5% of `SAMPLE_RATE_HZ` (now a `#define` overridable via `-DEXTRA_CFLAGS`; round 3 changes the default -- see below) for `PASS` (`examples/aen/aen-pdm-mic-alif/src/main.c:250` ("bool     rate_ok = measured_rate_hz >= rate_lo && measured_rate_hz <= rate_hi;")). No app-side `pdm_mode()`/`pdm_channel_config()`/`pdm_set_ch_*()` calls remain — the driver does that setup itself. Its README's "`MICROPHONE_SLEEP`" step is updated to match; the per-channel FIR/gain defaults are the channel-4/5 set the working example applied to every channel, not the distinct channel-5-only set `sdk-alif`'s own sample and the DFP demo use elsewhere — the driver keeps that bench-proven set, not a literal "verbatim from the reference" copy of every channel's own tuning.

New host-testable regression: `tests/unit/alif_pdm_chanmap` (9 cases) locks the translation with the portable backend's exact 2-channel map, the example's 4-channel map, three single-hw-channel L/R cases (needed because the paired maps alone don't distinguish a swapped L/R formula — both request both edges), a duplicate-hw-channel rejection, an out-of-order rejection, and the pre-existing invalid-map/range cases. Round-2 red/green: an `(pdm * 2U) + (1U - lr)` L/R-swap mutant fails 6/9 cases; removing the duplicate/order guard fails exactly the 2 cases that test it; both pass 9/9 restored.

The clock-mode change itself is not unit-testable — it drives a PDM analog block with no host model — and needs a silicon bench run to confirm live PCM at the labelled rate for each mode; see the round 3 correction below for why mode 1's round-2 "bench-proven" status was downgraded.

`examples/aen/aen-evk-demo`'s phase 11 opens the HP PDM mic through `<alp/audio.h>` (`alp_audio_in_open()`, `examples/aen/aen-evk-demo/src/main.c:4320` ("mic    = alp_audio_in_open(&(alp_audio_config_t){")) — the exact portable path this issue fixes — but only when built with `AEN_EVKDEMO_SOUND_PLAYBACK=1` (playback off, the default, never opens the mic); no source change was needed there, it inherits the fix through the driver. It requests 16000 Hz for both speaker and mic from one `SOUND_SAMPLE_RATE_HZ` constant; round 3 shows that rate is below the fitted mics' minimum on this board, so with playback on the mic's `alp_audio_in_open()` now fails `-EINVAL` instead of silently under-clocking (see below). The LP PDM node (`lppdm@43002000`, same `alif,alif-pdm` compatible, disabled by default) shares `dmic_alif_pdm_configure()` and would inherit the channel-map/clock-mode fix if enabled, but `PDM_INIT`'s IRQ wiring always uses a NAMED `warning_intr` line while the `lppdm` DT node carries only one UNNAMED IRQ — enabling it fails to build for an unrelated, pre-existing reason this issue does not touch. `tests/zephyr/audio` does not reference `dmic`/`pdm` and is unaffected.

**Round 3 correction — the fitted mics have a 1.2 MHz minimum PDM clock, invalidating round 2's proof.** The EVK's mics are MP34DT05TR-A (`E1M-EVK-2626-R2_components.csv`); ST's own in-tree Zephyr driver for this family declares `MPXXDTYY_MIN_PDM_FREQ 1200000` / `MPXXDTYY_MAX_PDM_FREQ 3250000` (`drivers/audio/mpxxdtyy.h`). Both round 1's mode 1 (512 kHz) and round 2's mode 4 (1024 kHz) are BELOW that minimum — round 1's "live varying PCM" reading is consistent with an under-clocked mic's flat residual noise, not proof of real audio; its "samples vary" pass gate could not tell the two apart. The in-spec Alif modes for this mic are mode 5 (1536 kHz, decim 48 → 32 kHz) and mode 7 (3072 kHz, decim 64 → 48 kHz, the same decimation ratio as the FIR set) — HWRM Table 15-118 / the DFP's `Driver_PDM.h` names. Both are added to the table (`zephyr/drivers/audio/alif_pdm.c:249` ("{ 32000U, PDM_MODE_WIDE_BANDWIDTH_AUDIO_1536_CLK_FRQ, 1536000U },")), (`zephyr/drivers/audio/alif_pdm.c:266` ("{ 48000U, PDM_MODE_FULL_BANDWIDTH_AUDIO_3071_CLK_FRQ, 3072000U },")); mode 7's FIR reuse is the direct, same-ratio argument mode 4 had, mode 5's is less direct (different decimation, 48 vs 64). The 8000/16000 entries stay in the table — they are valid for a mic that accepts those clocks — but are now board-rejected on the EVK (see next).

**Mic clock limits are a board fact, not the driver's or the portable backend's to know.** `src/backends/audio/zephyr_drv.c:272`'s `min_pdm_clk_freq` is reverted from round 2's `500000` back to the generic `1000000` — the portable backend names no mic part number and should not encode one. Instead, the `alif,alif-pdm` binding (`zephyr/dts/bindings/audio/alif,alif-pdm.yaml`, properties at lines 39 and 48 -- its comma-bearing filename isn't a checkable `path:NNN` citation) gains optional `min-pdm-clk-freq`/`max-pdm-clk-freq` properties for the board to declare its attached mic's range (renamed in round 4a — see below), and `dmic_alif_pdm_configure()` validates the resolved mode's clock against the INTERSECTION of that DT range and the caller's `dmic_cfg.io` window (`zephyr/drivers/audio/alif_pdm.c:433` ("uint32_t eff_min = MAX(cfg->clk_frequency_min, config->io.min_pdm_clk_freq);")); an unset DT property (0 / `UINT32_MAX`) collapses the intersection to `io` alone. Both EVK overlays that enable `pdm@4902d000` (`examples/aen/aen-pdm-mic-alif` and `examples/aen/aen-evk-demo`'s phase-11 overlay) now declare that range for the fitted MP34DT05TR-A, citing `mpxxdtyy.h` and the part number in a comment. The rejection log line names which bound tripped: `"mode clock %u Hz below mic minimum %u Hz"` / `"...above mic maximum %u Hz"`.

`pdm_alif.h`'s mode-define comments fill in modes 5-7 (HWRM Table 15-118 / `Driver_PDM.h`); mode 8 (`ULTRASOUND_4800_CLOCK_FRQ`) still has no cited decimation/Fs and stays marked "not yet grounded" rather than guessed.

`examples/aen/aen-pdm-mic-alif` now defaults to `SAMPLE_RATE_HZ 48000` (`examples/aen/aen-pdm-mic-alif/src/main.c:55`) — the only table entry both in-spec on the EVK and sharing the proven decimation ratio — and gains a per-channel signal-level gate: RMS (via a single-pass Welford online mean/variance, since the raw stream can't be buffered for a two-pass calculation) and peak-to-peak (`examples/aen/aen-pdm-mic-alif/src/main.c:72-73` ("#define MIN_SIGNAL_RMS_LSB          16") / ("#define MIN_SIGNAL_PEAK_TO_PEAK_LSB 64")), each a documented order of magnitude above the "±1-2 LSB flat noise" floor round 3 traced round 1's reading to, and DC offset, all printed per channel. `PASS` now additionally requires at least one channel to clear both floors; a clean read at the right rate with no channel over them reports `INCONCLUSIVE (no acoustic signal)` (`examples/aen/aen-pdm-mic-alif/src/main.c:296`) rather than `PASS`. Built and verified to compile at both 48000 (primary) and 16000 (expected to fail `dmic_configure()` with `-EINVAL` on the EVK once the DT mic range rejects it — round 4a confirms this on real silicon, see below).

Downgraded two prior verification claims that both ran mode 1 with the old "samples vary" gate: `docs/test-plan.md:310` (AEN801 peripheral matrix — PDM mics, ✅ verified → 🟡 partial) and `docs/aen-bench-bringup.md:35` (PDM mics, ✅ PASS → 🟡 PARTIAL *(re-verification pending)*), both with the mic-clock-minimum reasoning above. `docs/verification-status.md` is regenerated from `docs/test-plan.md` via `scripts/gen_verification_status.py` (never hand-edited) to match.

**Round 4a — silicon results on `e1m-aen-evk-03` (round 3 images), and three fixes.** The 16 kHz build's guard is CONFIRMED: `dmic_configure -> -22`, and `PDM_CONFIG_REGISTER` was never written. The 48 kHz build's mode select is CONFIRMED CORRECT and held (`PDM_CONFIG_REGISTER = 0x00070033` throughout capture, 38400 B blocks = 4800 frames x 4 ch x 2 B, as configured) — but the MEASURED delivery rate was **~32 kHz in two runs**, not 48 kHz; host-side timing agreed, and per-channel `rms_ac` 6-7 / `peak_to_peak` 1011-1126 look like sparse spikes, not a clean acoustic signal. **Root cause (ISR throughput/frame drops vs clock/decimation vs block assembly) is under separate investigation and NOT fixed in this round** — `pdm_clock_modes`' mode-7 entry (`zephyr/drivers/audio/alif_pdm.c:266`) and this README's Rates table are updated to say so explicitly; 48 kHz is not claimed to work.

- **Standard DT property names.** Zephyr already ships `zephyr/dts/bindings/audio/pdm-dmic.yaml` ("dts: bindings: audio: common PDM channel configuration", `2ceda8506e7`) with `clk-frequency-min`/`clk-frequency-max`. The branch's `min-pdm-clk-freq`/`max-pdm-clk-freq` (round 3) are renamed to match, on `alif,alif-pdm.yaml` directly — no aliasing, no legacy compat (the old names never reached `dev`). `include: [pdm-dmic.yaml]` was checked and rejected: that binding also makes `clk-duty-cycle-min`/`clk-duty-cycle-max`/etc REQUIRED and describes a separate CHILD node (`zephyr,pdm-dmic`), which this driver does not yet model; a note to that effect is in the binding file. `struct pdm_config`'s fields, `PDM_INIT`'s `DT_INST_PROP_OR()` calls, and both EVK overlays are updated to the new names.
- **Inverted-range diagnosis.** A DT overlay with `clk-frequency-min > clk-frequency-max` used to make `dmic_alif_pdm_configure()` reject every mode with an opaque per-attempt bound message and never say why. `PDM_INIT` now carries a per-instance `BUILD_ASSERT`, fired only when BOTH properties are present, failing the BUILD with `"alif,alif-pdm: clk-frequency-min must not exceed clk-frequency-max (the DT range is inverted)"` rather than a confusing runtime rejection.
- **Driver init must sleep the block — new silicon finding.** `PDM_CONFIG_REGISTER = 0x00010033` (mode 1) from a PREVIOUS image survived a `loadbin` reset and was STILL set after a refused `dmic_configure()` in the NEXT image: `pdm_initialize()` only ever wrote `PDM_CTL_REGISTER`/`PDM_THRESHOLD_REGISTER`, never `PDM_CONFIG_REGISTER`, so a fresh image silently inherited whatever clock mode + channels the last one left running and kept clocking the mics for the life of the image even though the app never started a capture. A new `pdm_force_sleep()` helper (`zephyr/drivers/audio/alif_pdm.c:311`) clears the channel-enable field and the clock-mode field (through the APB write-spacing helper); `pdm_initialize()` now calls it before anything else touches the block (`zephyr/drivers/audio/alif_pdm.c:1126`, right after the clock is confirmed on), and `dmic_alif_pdm_configure()`'s validation section is refactored onto a single `goto invalid;` exit that also calls it (`zephyr/drivers/audio/alif_pdm.c:505`), so a REFUSED configure() can no longer leave a prior successful capture's clock/channels running.
