### Fixed — `alif_pdm.c` ignored the Zephyr `dmic` contract; `<alp/audio.h>` PDM capture returned `ALP_OK` then read nothing (#2133)

`alp_audio_in_open()` + `alp_audio_in_start()` returned `ALP_OK` on the E1M-AEN801's HP PDM mics, then every `alp_audio_in_read()` timed out with an empty FIFO. `dmic_alif_pdm_configure()` (`zephyr/drivers/audio/alif_pdm.c`) broke the standard Zephyr `dmic` API contract two ways: it read `req_chan_map_lo`'s low byte VERBATIM as the hardware channel-enable mask instead of decoding the standard `dmic_build_channel_map()` nibble encoding, and it never left the PDM clock-mode field `MICROPHONE_SLEEP` nor programmed per-channel FIR/gain — only the Alif-specific `pdm_mode()`/`pdm_channel_config()`, which a standard `dmic` consumer has no reason to call, did that. The portable `src/backends/audio/zephyr_drv.c` backend used the standard encoding correctly, so it was the one broken by the driver's divergence: for its 2-channel request the verbatim read produced `0x10` (hardware channel 4 only) instead of `0x03` (hardware channels 0 and 1, where the EVK's mics actually are). Fixed by making the driver honour the contract itself with a new dependency-free translation header, grounded in the register layout, HWRM 15.7.4.3.1's even/rising-odd/falling edge rule, and the example's raw bitmask (`zephyr/drivers/audio/alif_pdm_chanmap.h:21` ("hw_channel = (pdm_controller * 2) + lr")); it also rejects a duplicate or out-of-order map the ISR cannot honour. **Register-level proof on `e1m-aen-evk-03`**: `PDM_CONFIG_REGISTER` read back `0x00010033` (channels 0/1/4/5, mode 1), the FIFO count moved, and every read returned a full block with `rc=0` — this proves the channel-map/driver-plumbing fix; it does NOT by itself prove real acoustic capture at that mode's rate (see the round 3 correction below).

**Round 2 correction — the rate table was wrong.** `PDM_MODE_STANDARD_VOICE_512_CLK_FRQ` was first keyed to 16000 Hz; HWRM Table 15-118 and the DFP's `ARM_PDM_MODE_AUDIOFREQ_8K_DECM_64` name both say mode 1 is 512 kHz clock / decimation 64 / **8 kHz** Fs, and the bench 1600-frame-per-~200 ms cadence agreed. The table now keys mode 1 to 8000 Hz, the register-level-proven entry (`zephyr/drivers/audio/alif_pdm.c:443` ("{ 8000U, PDM_MODE_STANDARD_VOICE_512_CLK_FRQ, 512000U },")), and adds mode 4 (`PDM_MODE_HIGH_QUALITY_1024_CLK_FRQ`, 1024 kHz clock, the SAME decimation ratio, 64, as mode 1) for 16000 Hz (`zephyr/drivers/audio/alif_pdm.c:456` ("{ 16000U, PDM_MODE_HIGH_QUALITY_1024_CLK_FRQ, 1024000U },")). Reusing `pdm_default_fir_voice512` on mode 4 is vendor-sourced — Alif's own driver test applies the same per-channel FIR tables across modes 1-9 with no FIR switch (`sdk-alif tests/drivers/pdm/src/alif_test_pdm.c`, FIR tables + mode select) — but mode 4 is still a **hypothesis**, and (see the round 3 correction below) both modes turned out to be below this EVK's mics' clock minimum regardless. `PDM_MODE_*` names encode only the clock, not Fs; every mode this round could ground against HWRM Table 15-118 now carries a rate comment (`zephyr/include/zephyr/drivers/pdm/pdm_alif.h:25` ("#define PDM_MODE_STANDARD_VOICE_512_CLK_FRQ 0x01UL /* 512 kHz clk, decim 64 -> 8 kHz Fs */")). `configure()` also now validates the resolved mode's PDM clock against the caller's `dmic_cfg.io` window, previously read by nothing (`zephyr/drivers/audio/alif_pdm.c:702` ("if (pdm_clk_hz < eff_min) {")) — both portable callers' windows were widened at this point to admit the proven 512 kHz clock (round 3 reverts the backend's widening — see below; `examples/aen/aen-pdm-mic-alif/src/main.c:216` (".min_pdm_clk_freq = 500000,") is the example's still-generic window, now superseded by the board overlay's DT range as the real constraint).

**Round 2 correction — power regression.** `configure()` used to write the clock-mode field itself, so the block started sampling — and PDM_C0/PDM_C2 stayed clocked — the instant `dmic_configure()` returned, and `DMIC_TRIGGER_STOP` never wrote `MICROPHONE_SLEEP` back, so the mics clocked forever after `alp_audio_in_stop()`/`close()`. The resolved mode is now stored in `pdm_data` and written only on `DMIC_TRIGGER_START` (`zephyr/drivers/audio/alif_pdm.c:1074` ("pdm_mode(dev, pdata->clk_mode);")); `DMIC_TRIGGER_STOP` (`zephyr/drivers/audio/alif_pdm.c:1003` ("pdm_mode(dev, PDM_MODE_MICROPHONE_SLEEP);")) and a `PM_DEVICE_ACTION_SUSPEND` (`zephyr/drivers/audio/alif_pdm.c:1624` ("pdm_mode(dev, PDM_MODE_MICROPHONE_SLEEP);")) both write `MICROPHONE_SLEEP` back.

**Round 2 addition — APB write spacing.** HWRM 15.7.5.3.1 warns against back-to-back `PDM_CTL0` (`PDM_CONFIG_REGISTER`) writes with no APB transactions between them; the channel-enable write in `configure()` followed by the (now START-side) clock-mode write had too little spacing. `pdm_ctl0_write_spacer()` (`zephyr/drivers/audio/alif_pdm.c:530` ("static void pdm_ctl0_write_spacer(const struct device *dev)"), ≥4 dummy reads of the read-only FIFO status register) now runs before every `PDM_CONFIG_REGISTER` write.

**Round 2 addition — stale sticky status on START.** HWRM 15.7.5.3.5: `PDM_ERROR_IRQ`/`PDM_WARN_IRQ` are edge-triggered, sticky, clear-on-read; because the mode write starts sampling immediately and the 4-bit FIFO count field overflows in ~1.9 ms at 8 kHz, a few ms of scheduling/printf delay before `enable_interrupt()` could latch an already-serviced overflow — `enable_interrupt()`'s own write would then have `pdm_error_handler()` silently clear the overflow-enable bit for the rest of the session, with block 0 starting with stale pre-clear samples followed by a gap. `DMIC_TRIGGER_START` now writes the mode, THEN read-clears both sticky status registers and pulses `FIFO_CLR`, THEN enables interrupts — the order is load-bearing (nothing to clear before the mode write; nothing latched once cleared before `enable_interrupt()`).

`examples/aen/aen-pdm-mic-alif` moves onto the standard contract and now measures the ACHIEVED sample rate instead of only checking "PCM varies" — a check that never would have caught round 1's mislabelled rate: it counts frames across `dmic_read()` calls and divides by elapsed `k_uptime_get()` time, excluding the first read as a startup-latency anchor, and requires the result within ±5% of `SAMPLE_RATE_HZ` (now a `#define` overridable via `-DEXTRA_CFLAGS`; round 3 changes the default -- see below) for `PASS` (`examples/aen/aen-pdm-mic-alif/src/main.c:336` ("bool     rate_ok = measured_rate_hz >= rate_lo && measured_rate_hz <= rate_hi;")). No app-side `pdm_mode()`/`pdm_channel_config()`/`pdm_set_ch_*()` calls remain — the driver does that setup itself. Its README's "`MICROPHONE_SLEEP`" step is updated to match; the per-channel FIR/gain defaults are the channel-4/5 set the example applied to every channel, not the distinct channel-5-only set `sdk-alif`'s own sample and the DFP demo use elsewhere — the driver keeps that set, not a literal "verbatim from the reference" copy of every channel's own tuning.

**Round 4a — silicon results on `e1m-aen-evk-03` (round 3 images), and three fixes.** The 16 kHz build's guard is CONFIRMED: `dmic_configure -> -22`, and `PDM_CONFIG_REGISTER` was never written. - **Standard DT property names.** Zephyr already ships `zephyr/dts/bindings/audio/pdm-dmic.yaml` ("dts: bindings: audio: common PDM channel configuration", `2ceda8506e7`) with `clk-frequency-min`/`clk-frequency-max`. - **Inverted-range diagnosis.** A DT overlay with `clk-frequency-min > clk-frequency-max` used to make `dmic_alif_pdm_configure()` reject every mode with an opaque per-attempt bound message and never say why. `PDM_INIT` now carries a per-instance `BUILD_ASSERT` (`zephyr/drivers/audio/alif_pdm.c:1700` ("BUILD_ASSERT(!(DT_INST_NODE_HAS_PROP(n, clk_frequency_min) && \")), fired only when BOTH properties are present, failing the BUILD with `"alif,alif-pdm: clk-frequency-min must not exceed clk-frequency-max (the DT range is inverted)"` rather than a confusing runtime rejection.
- **Driver init must sleep the block — new silicon finding.** `PDM_CONFIG_REGISTER = 0x00010033` (mode 1) from a PREVIOUS image survived a `loadbin` reset and was STILL set after a refused `dmic_configure()` in the NEXT image: `pdm_initialize()` only ever wrote `PDM_CTL_REGISTER`/`PDM_THRESHOLD_REGISTER`, never `PDM_CONFIG_REGISTER`, so a fresh image silently inherited whatever clock mode + channels the last one left running and kept clocking the mics for the life of the image even though the app never started a capture. A new `pdm_force_sleep()` helper (`zephyr/drivers/audio/alif_pdm.c:552` ("static void pdm_force_sleep(const struct device *dev)")) clears the channel-enable field and the clock-mode field (through the APB write-spacing helper); the init path calls it before anything else touches the block, and `dmic_alif_pdm_configure()`'s validation section is refactored onto a single `goto invalid;` exit that also calls it (`zephyr/drivers/audio/alif_pdm.c:771` ("pdm_force_sleep(dev);")), so a REFUSED configure() can no longer leave a prior successful capture's clock/channels running. (Round 4c splits the init-path call so `PM_DEVICE_ACTION_RESUME` no longer force-sleeps -- see below.)

**Round 4b — a slow consumer, and a separate silent-drop hole; DO NOT read these as proven connected.** Root-cause analysis first suggested round 4a's "~32 kHz" mode-7 result was the CONSUMER: `chan_stats_update()` ran a double-precision Welford update (a divide per sample) on all ~19200 samples/block, and this build has no `CONFIG_FPU` -- soft-float, measured at ~150 ms/block against a 100 ms block period. Round 4c corrects this round's own framing (see below): a 1 ms timing model shows that consumer cost alone reproduces the ~32 kHz reading, whether or not the 4-block slab also exhausted on that specific run -- whether it did was NOT separately measured at the time, because the driver had no way to report a drop yet. Two fixes, one on each side, neither claimed here to be THE explanation for round 4a's specific number:

- **Example: integer-only per-sample stats, no `CONFIG_FPU`.** `struct chan_stats` (`examples/aen/aen-pdm-mic-alif/src/main.c:140` ("struct chan_stats {")) is now `int64_t sum`/`sum_sq` + `int32_t min_v`/`max_v` -- no division, no `sqrt()`, no floating point anywhere in the per-sample loop. `chan_stats_rms_ac()` (`examples/aen/aen-pdm-mic-alif/src/main.c:169` ("static double chan_stats_rms_ac(const struct chan_stats *cs)")) computes `sqrt(E[x^2] - E[x]^2)` from the sums ONCE per channel, after the capture loop -- 4 `sqrt()` calls total instead of ~19200 per-sample divides. Turning on `CONFIG_FPU` was deliberately NOT the fix: it would only make the same per-sample cost faster, not remove the design smell, and wouldn't catch the next slow thing. `sound_pdm_capture_correlated()` in `examples/aen/aen-evk-demo` (`sound_verdict.h`) was checked for the same double-per-sample pattern and does NOT have it -- it already sums `uint32_t` `|sample|` with a cross-multiply ratio check, no division or float anywhere -- so no change was needed there.
- **Driver: stop dropping audio silently.** Grepped upstream Zephyr's dmic drivers (`ZEPHYR_BASE` `zephyr/drivers/audio/`) for the prevailing precedent on surfacing a buffer overrun to `dmic_read()`: `dmic_nrfx_pdm.c`'s `event_handler()` stops the whole capture outright on a slab-alloc failure (too drastic for a driver whose ISR is designed to keep sampling through a transient exhaustion); `dmic_mcux.c` is the closer fit -- `dmic_mcux_dma_cb()` sets `drv_data->dmic_state = DMIC_STATE_ERROR` on a slab-alloc miss (and on an RX-queue-put failure), and `dmic_mcux_read()` checks that state FIRST, before its own `k_msgq_get()`, returning `-EIO` (`dmic_mcux.c`, ZEPHYR_BASE `zephyr/drivers/audio/` -- not this repo, so not a `path:NNN` citation: around lines 220/236/259 for the sets, 639-641 for the check). Followed that shape: `pdm_data` gains a `bool overrun` (`zephyr/drivers/audio/alif_pdm.c:368` ("bool overrun;")), set at both drop sites -- `get_slab()`'s existing `slab_missed++` branch (`zephyr/drivers/audio/alif_pdm.c:1266` ("pdm_data->overrun = true;")) and the ISR's "queue full, drop oldest block" branch, which didn't count anything before (`zephyr/drivers/audio/alif_pdm.c:1461` ("pdmdata->overrun = true;")) -- and `dmic_alif_pdm_read()` checks it before every `k_msgq_get()`, returning `-EIO` (`zephyr/drivers/audio/alif_pdm.c:1155` ("if (pdata->overrun) {")). `slab_missed` itself is kept as a plain counter, unchanged. (Round 4c makes this flag sticky across STOP/START instead of self-clearing in START -- see below; this round's "no new test" call for this flag is superseded by round 4c's, which extracts the actual START decision logic into a testable pure function.)
- **Example: FAIL, not just a rate mismatch, on a driver-reported drop.** The read loop checks each `dmic_read()` return for exactly `-EIO` (distinct from a plain `-EAGAIN`/`-ETIMEDOUT` timeout) and sets `overrun_detected` (`examples/aen/aen-pdm-mic-alif/src/main.c:283` ("if (rc == -EIO) overrun_detected = true;")); the verdict checks it FIRST, ahead of every other condition, and reports `RESULT FAIL` regardless of what the surviving blocks measured (`examples/aen/aen-pdm-mic-alif/src/main.c:379` ("verdict = ")).

Silicon re-verification of the 8000/16000/32000/48000 kHz images is pending on both fixes; the 48 kHz measured-rate result from round 4a is not superseded by a new silicon run in this round, only explained -- and round 4c narrows that explanation further, see below.

**Round 4c — adversarial review: three more silent-drop/state bugs, an honesty correction, and cleanup.**

1. **START without STOP defeated the overrun report and leaked a slab block.** `DMIC_TRIGGER_START` used to clear `overrun` itself without freeing the in-progress block or draining the queue (both of which only `DMIC_TRIGGER_STOP` did), so restarting straight after an errored read -- instead of stopping first -- silently erased the drop report, replayed stale queued blocks as the new session's first reads, and leaked one slab block per recovery (the 4-block slab dies after 4 recoveries). Fixed by mirroring `dmic_mcux_trigger()`'s `DMIC_TRIGGER_START` (ZEPHYR_BASE `zephyr/drivers/audio/dmic_mcux.c`, around lines 606-616): START now refuses `-EIO` when the device is unconfigured or still flagged `overrun`, forcing STOP first, and is a no-op when already running (matching mcux's `else if (state != DMIC_STATE_ACTIVE)` skip), rather than double-arming interrupts. `overrun` now clears ONLY in `DMIC_TRIGGER_STOP`, after it frees the in-progress block and drains the queue (`zephyr/drivers/audio/alif_pdm.c:1029` ("pdata->overrun = false;")). The refuse/no-op/proceed decision itself is a pure function, `pdm_decide_start()` (`zephyr/drivers/audio/alif_pdm_trigger_state.h`), called from the trigger handler (`zephyr/drivers/audio/alif_pdm.c:1039` ("enum pdm_start_decision decision = pdm_decide_start(")) and host-tested directly (`tests/unit/alif_pdm_trigger_state`, 4 cases) -- see the test section below.
2. **A hardware FIFO overflow was a third silent drop.** `pdm_error_handler()` read-cleared `PDM_ERROR_IRQ` (register offset `0x10`) without ever checking it, so a genuine overflow masked further overflow IRQs for the session and never set `overrun` -- on LPPDM instances (no named `error_intr` line) this runs on every warning ISR. Fixed: the read result is now checked before being discarded, and `overrun` is set when the relevant bit is set (`zephyr/drivers/audio/alif_pdm.c:1204` ("error_status = sys_read32(reg_base + PDM_ERROR_IRQ);")); the function is unchanged in signature so both the HP PDM's dedicated error-IRQ path and LPPDM's shared-warning-IRQ path get the fix automatically. This round's fix tested the WRONG bit of the WRONG register (`PDM_FIFO_OVERFLOW_IRQ`, bit 1 of the enable register, not the status register's bit 0) and so never actually detected a real overflow -- see round 4d finding 1 below for the correction.
3. **The round 4a/4b mechanism claim was overstated -- corrected.** A 1 ms timing model of the example's OLD double-precision stats loop: at 150 ms/block, `measured_rate_hz` comes out ~35820 with ZERO `get_slab` failures; at 170-180 ms/block (which brackets the silicon's 32142), the first slab failure lands at ~700 ms, AFTER the last read of a 4-block capture, so `eio_reads` would have been 0 even then. The ~32 kHz reading was the rate measurement tracking THIS APP's own consumption speed; whether a slab drop ALSO happened on that specific run was never measured (the driver had no way to report one before round 4c). Restated conservatively everywhere this was asserted as settled fact: `zephyr/drivers/audio/alif_pdm.c`'s mode-7 table comment, this app's file-header comment and `struct chan_stats` comment, and the README's Rates/Status sections. The two "wrong rate" / "FIFO empty" `PARTIAL` verdicts that used to guess a specific unconfirmed cause (`"wrong PDM clock mode"`, `"SE-managed HFOSCx2"`) are now `FAIL` with causes NOT named (`examples/aen/aen-pdm-mic-alif/src/main.c:388` ("verdict = ")) and (`examples/aen/aen-pdm-mic-alif/src/main.c:397` ("verdict = ")). A bench run of the `68a169977` 48 kHz image was in progress at review time; its outcome is not claimed here.
