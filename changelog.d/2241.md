### Fixed — the `iot` scaffold now carries `src/cc3501e_bridge.{c,h}`, and the template gate rejects any app-dir file the catalog forgets (#2241)

`--emit scaffold` copies exactly a template's `files.user_owned` list, and the
`iot` entry listed only `board.yaml`, `prj.conf`, `CMakeLists.txt`,
`src/main.c` and `README.md`. Its canonical example, `mqtt-telemetry`, compiles
a second source since #2112 / #2172
(`examples/connectivity/mqtt-telemetry/CMakeLists.txt:41`
("target_sources(app PRIVATE src/cc3501e_bridge.c)")), so every emitted `iot`
project referenced a `src/cc3501e_bridge.c` it did not contain and could not
link. The two bridge files are now in the list
(`metadata/templates/catalog-v1.json:546` ("src/cc3501e_bridge.c")), and
the scaffold carries them byte for byte.

`scripts/check_template_catalog.py` gains the check that would have caught
this (`scripts/check_template_catalog.py:235`
("def _check_core_files_declared(rec: dict) -> list[str]:")). Every file git
tracks in a record's `cores[].dir` app dirs must appear in
`files.user_owned`. The one exemption is a path that `test.testcase_yaml`
lists: that is SDK CI wiring, which the scaffold drops on purpose (the
`multicore-*` records' `m55_hp/testcase.yaml` and `peer/testcase.yaml`). The
check reads `git ls-files`, not the directory, so a stray untracked file such
as `.DS_Store` cannot trip it. A core whose `dir` is the example root is
skipped, because the root also holds CI-only files by design. Across the nine
current templates, `iot` was the only violation.

For tan-cli: tan's in-process `--emit scaffold` mirrors this envelope byte for
byte, and its planner re-sync (alplabai/tan-cli#1275) worked around the gap by
vendoring the two files as `NON_ENVELOPE_EXTRAS`. That workaround can be
dropped on the first re-sync that picks this up.
