### Fixed — the AEN memory-map overlap check had no whole-device-alias exception, so resolving `mram_main`'s `base` would self-overlap every partition inside it (#2073)

`scripts/gen_zephyr_board.py::_aen_check_map_overlaps()` treated every
integer-`base` `memory_map:` row as a placed partition and refused any pair
whose extents touched. `mram_main` is a deliberate whole-device alias — it
spans the same window `mcuboot`/`he_slot0`/`hp_slot0`/`reserved`/`storage`/
`atoc` subdivide — so the moment its `base` stopped being the `"TBD"`
sentinel (the only reason the check happened to pass), it was reported as
overlapping all six of them. `scripts/alp_orchestrate/aperture.py`'s
`classify_region()` already carried the correct exception (`extent ==
aperture exactly`) for this same shape; the two disagreeing was itself the
defect.

The predicate is now a single shared helper,
`whole_device_alias.is_whole_device_alias()`, used by both
`classify_region()` / `is_partition_inside_aperture()`
(`scripts/alp_orchestrate/aperture.py`) and the new
`_aen_check_map_overlaps()` exclusion, so the generator and the aperture
module can no longer drift on what counts as the device itself versus a
partition inside it. It lives in a new flat, dependency-free
`scripts/whole_device_alias.py` (the `sentinels.py` precedent), not
inside the `alp_orchestrate` package: an earlier version of this fix had
`gen_zephyr_board.py` import `alp_orchestrate.aperture` directly, which
pulled in the whole orchestrator package for one predicate (measured 53
-> 218 modules imported, roughly 6x the cumulative `-X importtime`) and
created a package-to-generator import loop with `alp_orchestrate/loader.py`
/ `secure.py`'s own (necessary) deferred import of `gen_zephyr_board`
going the other way — with `jsonschema` blocked, `gen_zephyr_board`
alone stopped importing at all (`alp_orchestrate: jsonschema is
required.`). Both are fixed by the flat module: module count is back to
baseline plus one (54 -- the extra module is `whole_device_alias`
itself), import time is back in the same ballpark, and `gen_zephyr_board`
imports again with `jsonschema` blocked. **Also
narrowing an overstated claim:** "exactly one copy" covers only the
generator and `classify_region()` / `is_partition_inside_aperture()` --
`check_atoc_reservation.py`'s own 4b/4c aperture-tiling and
flash-class-agreement checks still hand-write this same `lo == full_lo
and hi == full_hi` comparison independently rather than importing it, a
known gap left as a separate follow-up, not touched here (a rewrite of
that file is in flight on another branch). The exception itself is
narrow regardless: only a region whose resolved extent equals the App
MRAM aperture exactly is excluded from the pairwise overlap comparison
— a region that merely contains another without matching the aperture
exactly is still refused, and **more than one region matching the
aperture exactly is refused outright** rather than silently letting two
undeclared aliases coexist uncompared.

tan-cli keeps a copy of `gen_zephyr_board.py` pinned by hash
(`test_planner_relocation_freshness.py`); its next resync will pick up
this file's new `whole_device_alias` import alongside it.

SoC's declared on-die MRAM aperture) -- not safe as an IPC carve-out
