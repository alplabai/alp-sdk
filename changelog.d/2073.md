### Fixed — the AEN memory-map overlap check had no whole-device-alias exception, so resolving `mram_main`'s `base` would self-overlap every partition inside it (#2073)

`scripts/gen_zephyr_board.py::_aen_check_map_overlaps()` treated every
integer-`base` `memory_map:` row as a placed partition and refused any pair
whose extents touched. `mram_main` is a deliberate whole-device alias — it
spans the same window `mcuboot`/`he_slot0`/`hp_slot0`/`reserved`/`storage`/
`atoc` subdivide — so the moment its `base` stopped being the `"TBD"`
sentinel (the only reason the check happened to pass), it was reported as
overlapping all six of them. `scripts/alp_orchestrate/aperture.py`'s
`classify_region()` already carried the correct exception (`extent ==
aperture exactly`) for this same shape; the two disagreeing was itself the
defect.

The predicate is now a single shared helper,
`alp_orchestrate.aperture.is_whole_device_alias()`, used by both
`classify_region()` / `is_partition_inside_aperture()` and the new
`_aen_check_map_overlaps()` exclusion, so the generator and the
orchestrator can no longer drift on what counts as the device itself
versus a partition inside it. The exception is narrow: only a region whose
resolved extent equals the App MRAM aperture exactly is excluded from the
pairwise overlap comparison — a region that merely contains another
without matching the aperture exactly is still refused.

`metadata/e1m_modules/E1M-AEN801.yaml` and `E1M-AEN803.yaml` still carry
`mram_main: base: "TBD"` — resolving it to `0x80000000` passes this
overlap check and `check_atoc_reservation.py`'s top-anchor tie-break, but
also changes the `rpmsg-aen` / `mproc-mailbox` emit snapshots, so it's
left as a follow-up rather than folded in here. Measured, not assumed: no
`ipc:` entry moves off `status: blocked` and no carve-out gains an
address — `mram_main` was already disqualified by its authored
`write_authority: composite` (never `customer_runtime`) before this.
What changes is `mram_main`'s own `memory_map` row (`kind`/`status` go
from `unresolved` to `flash`/`ok` and it gains a `base:`, exactly as
`classify_region()` says it should once resolved) and the *reason text*
every blocked `ipc:` entry cites for it, from
"has an unresolved base ('TBD')" to "is flash-class (contained in the
SoC's declared on-die MRAM aperture) -- not safe as an IPC carve-out
target". Same verdict, better-worded reason.
