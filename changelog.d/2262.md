### Fixed — the `alif_flash` west runner burned a fresh ATOC without reading the resident one first, silently delisting every other app entry (#2262)

`scripts/west_commands/runners/alif_flash.py`'s `do_run` (the `west flash`
runner wired into all six `zephyr/boards/alp/e1m_aen*` boards) staged a
signed ATOC config holding only `DEVICE` + this build's own `ALP-HE`/`ALP-HP`
entry, then burned it with `app-write-mram -c <SE_UART> -p` — a write that
REPLACES the whole resident ATOC, not merges it. Every other resident app
entry (the other M55 core's own entry, an A32 Linux boot chain
`BOOTLOAD`/`A32_APP`, ...) was silently delisted the instant the write
landed, with no error and no SES warning (`[SES] ATOC ok` prints either
way). #2025 closed this exact hazard (an AEN EVK bench unit's A32 Linux boot
chain, 2026-09-07) for the bench shell helpers alone (`bench_atoc_replace_guard`
in `scripts/bench/aen/bench-env.sh`); it never reached this `west flash`
door.

`do_run` now reads the resident ATOC back over the SE-UART before burning,
with the same two documented, non-destructive SETOOLS queries the bench
guard uses (`maintenance -opt getbanner` then `-opt gettoc`), and refuses the
burn — before anything is written — when a resident entry outside this
run's own `ALP-HE`/`ALP-HP` section would be delisted, or when the read
could not be verified (a missing `maintenance` binary, a malformed/absent
SES banner, or a non-zero query exit). The new `--replace-atoc` runner
option is the explicit override, spelled identically to
`flash-run.sh`'s own Flow A flag — distinct from, and never merged or
aliased with, Flow D's `--atoc-unqueryable` (#2027). A new `--se-uart-baud`
option (default `$SE_UART_BAUD`, else `57600`) matches the bench guard's own
baud fallback.

The parse/decision logic (`compute_query_status`, `foreign_resident_entries`,
`decide_atoc_guard`) is a single shared, pure-Python port of
`bench_atoc_replace_guard`'s semantics, added to `scripts/aen_atoc.py` next
to the existing ATOC-assembly guard (#1069). A parity test
(`tests/scripts/test_atoc_guard_parity.py`) feeds fixture transcripts
through both implementations and asserts identical verdicts (bash's exit
0/5 vs. Python's richer status, and — parsing bash's own `This board also
carries: ...` line — the identical foreign-entry NAME SET, not a substring
check). Some of those fixtures are the real, bench-verified 2026-09-07 AEN
EVK captures (the 9-row A32-Linux-boot-chain table, the clean two-row
table, the leading-space SES banner); others (an ANSI-coloured 2-row table,
a CRLF-only table, a truncated/NBSP-only-name row, a non-zero `gettoc` exit
after partial rows, `No ATOC found on target device.` on its own) are
hand-written to exercise one specific parser rule and were never captured
off real hardware — this changelog and the fixtures' own comments say
which is which; **do not read every fixture here as bench-proof.**

Two review rounds against the initial version of this fix found and closed:
- **A fail-open parser bug** (a Python row with fewer than 3 `|`-delimited
  fields, or a Name cell of pure NBSP, was silently DROPPED instead of
  read as a real — if oddly-shaped — resident entry the way `awk` reads
  it; both shapes now match `awk`'s own field/trim semantics exactly, with
  unit + parity coverage for both).
- **A wrong remedy for a pre-provisioned module's factory ATOC.** Alp
  Lab's factory-provisioned MCUboot bootloader shows up as a resident
  `MCUBOOT-` entry (`zephyr/sysbuild/aen/README.md`); this guard correctly
  refuses to burn over it, but `--replace-atoc` deletes it and leaves the
  module unable to boot — the refusal message for that specific entry name
  now says so and points at the already-documented Option B (plain
  J-Link, no ATOC) path instead of inviting `--replace-atoc`.
  `docs/aen-provisioning.md`, `docs/_aen-runbook-section.md`,
  `docs/aen-bench-bringup.md`, and `zephyr/sysbuild/aen/README.md` are
  corrected to stop promising plain `west flash` works day-1 on such a
  module.
- **A stale verdict file.** A run that fails BEFORE reaching the guard
  (no SETOOLS, no `zephyr.bin`, a rejected ATOC window, ...) now removes
  any `atoc-guard.json` a PREVIOUS run left behind, so its mere absence —
  not a stale `status` field — is what tells a caller "the guard did not
  reach a verdict this attempt".
- **A wedged SE-UART query with no timeout** could hang `west flash`
  forever; `maintenance -opt getbanner`/`gettoc` now time out (120s) and
  report `unverified`, the same fail-closed shape as any other query
  failure.

Every run leaves `<build_dir>/alif_flash/atoc-before.txt` (the raw
transcript) and `<build_dir>/alif_flash/atoc-guard.json` (a
machine-readable verdict — see "The verdict contract is frozen as v1"
below for the exact field set), written before any refusal is raised so
a caller such as tan-cli's `zephyr_west_flash` backend (tan-cli#1267) can
tell this refusal apart from any other `west flash` failure without
parsing stderr.

### The verdict contract is frozen as v1

`atoc-guard.json`'s `schema` field is the literal string
`alp-sdk.alif-flash-atoc-guard.v1`. The exact field set the code writes
(`schema`, `status`, `foreign`, `transcript`, `allowed`, `query_status` —
their types, allowed values, and what "absent file" / `query_status`
mean for telling the two `replaced` shapes apart) is documented once, in
`docs/aen-provisioning.md`'s "The ATOC-replace guard verdict contract"
section, rather than duplicated here. (Second review round: this table
lived only in `docs/_aen-runbook-section.md`, an unpublished draft
fragment never actually folded into a published doc — moved to
`docs/aen-provisioning.md`, which is published, with a pointer left in the
fragment.) Any future change to that field set must bump the schema
string (`...v1` -> `...v2`), the same convention
`metadata/schemas/*-v1.schema.json` already uses elsewhere in this repo.

### Sysbuild multi-domain `west flash` is NOT supported through `alif_flash` yet (alp-sdk#2274)

Zephyr's own multi-domain flash plumbing (in its `scripts/west_commands/`:
`flash.py` passes `build/domains.yaml` to `do_run_common`; `run_common.py`
resolves every domain in flash order and its own per-domain loop
instantiates and calls the board's flash runner ONCE PER DOMAIN, not once
per `west flash` invocation -- upstream Zephyr, not something alp-sdk
ships or can cite a stable line number in) means a sysbuild AEN build
(MCUboot domain + app domain) runs `alif_flash`'s `do_run` -- and
therefore this guard -- TWICE, once per domain's own build directory.

The guard identifies a resident entry by NAME ONLY. MCUboot (ITCM
`0x58000000`) and the HE app (HE slot0) both map to the identical ATOC
section name `ALP-HE` via `_atoc_section_name`, so on the SECOND
invocation the resident `ALP-HE` entry (written by the FIRST invocation)
is already in that run's own `allowed` set — not foreign — and the guard
reports `clear`. It still burns a fresh single-entry ATOC, silently
replacing whatever the first invocation wrote: the guard only ever
detects a FOREIGN name, never a same-name overwrite by a different
domain's build. **This is not a regression** — the pre-`#2262` runner did
exactly the same thing with no check of any kind — but it is a real,
unclosed gap in what this guard can catch, tracked as alp-sdk#2274
(closing it needs either a per-domain-aware `allowed` contract or a
binary-identity check this PR does not attempt). Do not read the
`clear`/`replaced` distinction above as covering this case: a same-name
overwrite between two sysbuild domains is exactly the kind of collision
neither status can currently name. (An untested hypothesis about whether
the app-domain invocation might fail earlier, at `_reset_vector`, on a
signed image's `imgtool` header, belongs to alp-sdk#2274's own
investigation, not this changelog — it is not claimed here.)

### Second review round: closing a fail-open, tightening the guard's edges (#2262)

A second review pass against the landed fix found and closed one BLOCKER
and several smaller gaps:

- **BLOCKER — a truncated-but-rc-0 `gettoc` read as "ok" and let the burn
  proceed.** `compute_query_status` (and its bash mirror,
  `bench_atoc_replace_guard`) accepted any `gettoc` read that exited
  `rc=0`, carried a valid SES banner, and parsed >=1 resident row — a real
  9-row capture cut short after only its first four rows (the two
  `DEVICE` rows, `* SERAM0`, `SERAM1` — a serial timeout mid-download can
  still exit `rc=0`) satisfied all three and silently delisted whatever
  the cut-off tail would have shown (`BOOTLOAD`/`A32_APP`/`HP_APP`/
  `HE_APP` in that real capture): the exact 2026-09-07 hardware loss this
  guard exists to close, reproduced against the west runner itself. Fixed
  by requiring structural completeness on both legs — a boxed table (one
  carrying the `| Name |` header row) must also carry a closing `+---+`
  separator strictly after its last data row, or it reads `unverified`
  rather than `ok`. A boxless capture with neither marker at all (the
  real multi-entry dual-core fixture, which carries no header/separator
  lines) is exempt and keeps the pre-existing any-rows-parsed rule — all
  three real fixtures classify exactly as they did before this fix.
  New unit + parity fixtures cover a truncated-after-baseline-rows table,
  a table cut mid-row, and a table missing only its closing separator.
- **The abort decision was stringly-typed.** The runner branched on
  `verdict.status == 'refused-unverified' or 'refused-foreign'`, falling
  through to a silent burn for ANY status that matched neither exactly —
  even though `decide_atoc_guard` had already computed `refused=True`
  correctly, and every test in both suites asserts on `.refused`. The
  runner now branches on the boolean directly, with a fail-closed
  catch-all raise for any future refused status this method has no
  dedicated message for yet.
- **The generic foreign-entry refusal steered toward `--replace-atoc` as
  the default remedy** ("Re-run with `--replace-atoc` only once you
  can..."). This is the exact branch a pre-provisioned module falls into
  if its factory bootloader's real ATOC name ever differs from the
  `MCUBOOT-` this guard assumes (see below) — the same steer-onto-the-
  destroy-flag failure the factory-specific message was written to avoid.
  Reworded, on both legs, to lead with "capture/restore first" and
  present `--replace-atoc` only as the last resort.
- **`_FACTORY_MCUBOOT_ATOC_NAME = 'MCUBOOT-'` is unsourced.** It traces to
  exactly one sentence in `zephyr/sysbuild/aen/README.md`, itself
  documenting a SETOOLS-shipped config alp-sdk does not ship — there is no
  capture of a real pre-provisioned module's `gettoc` output anywhere in
  this repo to confirm it against; every "real" fixture is an AEN EVK dev
  board. Marked **TBD (unverified, no gettoc capture of a pre-provisioned
  module)** in the code comment and in every doc that names it
  (`docs/aen-provisioning.md`, `docs/_aen-runbook-section.md`,
  `zephyr/sysbuild/aen/README.md`). A wrong literal does not make the
  guard unsafe: an unrecognised factory name still refuses, it only loses
  its dedicated message and falls back to the (now reworded) generic one.
- **The frozen v1 verdict contract lived only in an unpublished draft.**
  Moved from `docs/_aen-runbook-section.md` (a fragment whose own header
  says it was never folded into a published doc) to
  `docs/aen-provisioning.md`, with a pointer left behind.
- **`maintenance.is_file()` where bash checks `[ -x ... ]`.** Fail-closed
  by construction already (a `PermissionError` from actually trying to
  run a non-executable file is an `OSError`, caught and treated as a
  failed read), but untested and inconsistent with the bash guard.
  Switched to `os.access(path, os.X_OK)`, with a test that isolates the
  availability check itself from that fail-closed-by-coincidence path.
- **An unwritable build_dir surfaced a bare `OSError`.** The transcript/
  verdict `write_text` calls are now wrapped and re-raise a `RuntimeError`
  naming the path — still fail-closed either way (the burn is never
  reached), but this is the one case where the guard's own "a refused run
  always leaves a verdict" contract cannot hold (there is nowhere to put
  it if the build directory itself can't be written to), now documented
  as that contract's one honest exception.
- **`transcript` was only absolute when west's own `build_dir` happened to
  be**, contradicting the contract's "absolute path" claim. `.resolve()`d
  now, with a test driving `do_run` through a relative `build_dir`.
- **`_run_maintenance` caught only `TimeoutExpired`/`OSError`.** A
  `ValueError` from `subprocess.run` (e.g. a NUL byte embedded in a
  garbled `se_uart` string) would have propagated uncaught instead of
  becoming the same rc=1 failed-read every other IO problem here becomes.
  Now caught explicitly.
- **The padded `" No ATOC found on target device."` shape** (leading/
  trailing whitespace, the way SETOOLS demonstrably pads the SES banner)
  previously matched neither leg's exact-line comparison, misreading a
  genuinely blank board as `unverified` rather than `empty` — annoying
  and fail-closed, never unsafe, but wrong. Both `is_no_atoc_found` and
  the bash guard's `grep` now tolerate it, with a parity test.
- **The runner's post-burn log line claimed "the SES has booted the
  image."** — more than `do_run` actually knows: its only write is
  `app-write-mram -p` (never an erase), and the AEN bench notes document
  the SE preferring a STALE resident slot0 image over a freshly written
  ITCM-load ATOC. Reworded to state only that the write completed; boot
  is not verified by this command. `docs/aen-bench-bringup.md`'s guard
  section now also states plainly that `west flash` is a Flow-A-class
  destructive MRAM/ATOC write (not a safe incremental update), and that
  the canonical `person_detect` slot0 restore's own `ALP-HE` entry sits
  *inside* this guard's allowed set — so a subsequent `west flash`
  correctly, silently overwrites it, by design, not as a bypass.

### Not yet verified (bench-owed before this is safe to rely on in the field, same "Bench before merge" caveat the issue itself named)

The Python port + this runner's wiring have not been run on a real AEN
EVK slot at all — the parser semantics are bench-proven only in bash.

Two specific gaps carried forward from the second review round, both
needing the bench, not a doc guess, to close:

- **Truncation reachability.** The structural-completeness fix above
  closes the fail-open in CODE on both legs, but whether a real, mid-
  table serial-read cut actually reaches this code path with `rc=0` is
  still unmeasured — the bash guard's own comment asserts "a serial
  timeout mid-read must also land here" (i.e. `maintenance` exits
  non-zero) but cites no capture. Stage 0/1 of the bench plan: capture a
  `gettoc`, cut the SE link mid-table, and record `maintenance`'s actual
  exit code. Non-zero means the structural-completeness fix is defence in
  depth for a hole that was already unreachable through the exit-code
  check alone (still worth keeping — the exit-code contract is itself
  unverified); zero means it was, and until this fix landed still would
  have been, a live fail-open on real hardware.
- **The factory `MCUBOOT-` name.** Still TBD — see above. Capturing a
  real pre-provisioned module's `gettoc` output is a Stage 2 bench task;
  until then this is a plausible, not confirmed, literal.
