### Fixed — the `alif_flash` west runner burned a fresh ATOC without reading the resident one first, silently delisting every other app entry (#2262)

`scripts/west_commands/runners/alif_flash.py`'s `do_run` (the `west flash`
runner wired into all six `zephyr/boards/alp/e1m_aen*` boards) staged a
signed ATOC config holding only `DEVICE` + this build's own `ALP-HE`/`ALP-HP`
entry, then burned it with `app-write-mram -c <SE_UART> -p` — a write that
REPLACES the whole resident ATOC, not merges it. Every other resident app
entry (the other M55 core's own entry, an A32 Linux boot chain
`BOOTLOAD`/`A32_APP`, ...) was silently delisted the instant the write
landed, with no error and no SES warning (`[SES] ATOC ok` prints either
way). #2025 closed this exact hazard (an AEN EVK bench unit's A32 Linux boot
chain, 2026-09-07) for the bench shell helpers alone (`bench_atoc_replace_guard`
in `scripts/bench/aen/bench-env.sh`); it never reached this `west flash`
door.

`do_run` now reads the resident ATOC back over the SE-UART before burning,
with the same two documented, non-destructive SETOOLS queries the bench
guard uses (`maintenance -opt getbanner` then `-opt gettoc`), and refuses the
burn — before anything is written — when a resident entry outside this
run's own `ALP-HE`/`ALP-HP` section would be delisted, or when the read
could not be verified (a missing `maintenance` binary, a malformed/absent
SES banner, or a non-zero query exit). The new `--replace-atoc` runner
option is the explicit override, spelled identically to
`flash-run.sh`'s own Flow A flag — distinct from, and never merged or
aliased with, Flow D's `--atoc-unqueryable` (#2027). A new `--se-uart-baud`
option (default `$SE_UART_BAUD`, else `57600`) matches the bench guard's own
baud fallback.

The parse/decision logic (`compute_query_status`, `foreign_resident_entries`,
`decide_atoc_guard`) is a single shared, pure-Python port of
`bench_atoc_replace_guard`'s semantics, added to `scripts/aen_atoc.py` next
to the existing ATOC-assembly guard (#1069). A parity test
(`tests/scripts/test_atoc_guard_parity.py`) feeds fixture transcripts
through both implementations and asserts identical verdicts (bash's exit
0/5 vs. Python's richer status, and — parsing bash's own `This board also
carries: ...` line — the identical foreign-entry NAME SET, not a substring
check). Some of those fixtures are the real, bench-verified 2026-09-07 AEN
EVK captures (the 9-row A32-Linux-boot-chain table, the clean two-row
table, the leading-space SES banner); others (an ANSI-coloured 2-row table,
a CRLF-only table, a truncated/NBSP-only-name row, a non-zero `gettoc` exit
after partial rows, `No ATOC found on target device.` on its own) are
hand-written to exercise one specific parser rule and were never captured
off real hardware — this changelog and the fixtures' own comments say
which is which; **do not read every fixture here as bench-proof.**

The guard also covers these edge cases:
- **Short and NBSP-only rows** (a Python row with fewer than 3 `|`-delimited
  fields, or a Name cell of pure NBSP, was silently DROPPED instead of
  read as a real — if oddly-shaped — resident entry the way `awk` reads
  it; both shapes now match `awk`'s own field/trim semantics exactly, with
  unit + parity coverage for both).
- **Pre-provisioned module's factory ATOC.** Alp
  Lab's factory-provisioned MCUboot bootloader shows up as a resident
  `MCUBOOT-` entry (`zephyr/sysbuild/aen/README.md`); this guard correctly
  refuses to burn over it, but `--replace-atoc` deletes it and leaves the
  module unable to boot — the refusal message for that specific entry name
  says so and points at the already-documented Option B (plain
  J-Link, no ATOC) path instead of inviting `--replace-atoc`.
  `docs/aen-provisioning.md`, `docs/_aen-runbook-section.md`,
  `docs/aen-bench-bringup.md`, and `zephyr/sysbuild/aen/README.md` are
  say plain `west flash` does not work day-1 on such a module.
- **No stale verdict file.** A run that fails BEFORE reaching the guard
  (no SETOOLS, no `zephyr.bin`, a rejected ATOC window, ...) now removes
  any `atoc-guard.json` a PREVIOUS run left behind, so its mere absence —
  not a stale `status` field — is what tells a caller "the guard did not
  reach a verdict this attempt".
- **Wedged SE-UART query.** `maintenance -opt getbanner`/`gettoc` now time out (120s) and
  report `unverified`, the same fail-closed shape as any other query
  failure, so `west flash` cannot hang on it.

Every run leaves `<build_dir>/alif_flash/atoc-before.txt` (the raw
transcript) and `<build_dir>/alif_flash/atoc-guard.json` (a
machine-readable verdict — see "The verdict contract is frozen as v1"
below for the exact field set), written before any refusal is raised so
a caller such as tan-cli's `zephyr_west_flash` backend (tan-cli#1267) can
tell this refusal apart from any other `west flash` failure without
parsing stderr.

### The verdict contract is frozen as v1

`atoc-guard.json`'s `schema` field is the literal string
`alp-sdk.alif-flash-atoc-guard.v1`. The exact field set the code writes
(`schema`, `status`, `foreign`, `transcript`, `allowed`, `query_status` —
their types, allowed values, and what "absent file" / `query_status`
mean for telling the two `replaced` shapes apart) is documented once, in
`docs/aen-provisioning.md`'s "The ATOC-replace guard verdict contract"
section, rather than duplicated here. (`docs/_aen-runbook-section.md`, an unpublished draft fragment,
carries only a pointer to it.) Any future change to that field set must bump the schema
string (`...v1` -> `...v2`), the same convention
`metadata/schemas/*-v1.schema.json` already uses elsewhere in this repo.

### Sysbuild multi-domain `west flash` was NOT supported through `alif_flash` — refused by `alif_flash` since alp-sdk#2274 (see `changelog.d/2274.md`)

Zephyr's own multi-domain flash plumbing (in its `scripts/west_commands/`:
`flash.py` passes `build/domains.yaml` to `do_run_common`; `run_common.py`
resolves every domain in flash order and its own per-domain loop
instantiates and calls the board's flash runner ONCE PER DOMAIN, not once
per `west flash` invocation -- upstream Zephyr, not something alp-sdk
ships or can cite a stable line number in) means a sysbuild AEN build
(MCUboot domain + app domain) runs `alif_flash`'s `do_run` -- and
therefore this guard -- TWICE, once per domain's own build directory.

The guard identifies a resident entry by NAME ONLY. MCUboot (ITCM
`0x58000000`) and the HE app (HE slot0) both map to the identical ATOC
section name `ALP-HE` via `_atoc_section_name`, so on the SECOND
invocation the resident `ALP-HE` entry (written by the FIRST invocation)
is already in that run's own `allowed` set — not foreign — and the guard
reports `clear`. It still burns a fresh single-entry ATOC, silently
replacing whatever the first invocation wrote: the guard only ever
detects a FOREIGN name, never a same-name overwrite by a different
domain's build. **This is not a regression** — the pre-`#2262` runner did
exactly the same thing with no check of any kind — but it is a real,
unclosed gap in what this guard can catch, tracked as alp-sdk#2274
(closing it needs either a per-domain-aware `allowed` contract or a
binary-identity check this PR does not attempt). Do not read the
`clear`/`replaced` distinction above as covering this case: a same-name
overwrite between two sysbuild domains is exactly the kind of collision
neither status can currently name. (An untested hypothesis about whether
the app-domain invocation might fail earlier, at `_reset_vector`, on a
signed image's `imgtool` header, belongs to alp-sdk#2274's own
investigation, not this changelog — it is not claimed here.)

**Refused by `alif_flash` since alp-sdk#2274** (`changelog.d/2274.md`): rather than attempt a
per-domain-aware `allowed` contract or a binary-identity check, `alif_flash`
now REFUSES outright, before any side effect, whenever the build being
flashed is a multi-domain sysbuild — so this same-name-overwrite gap is
never reached at all. This section is left as the historical record of
when and how the gap was found.

### Guard behaviour (#2262)

- **Structural completeness is required.** `compute_query_status` (and its bash mirror,
  `bench_atoc_replace_guard`) reads a `gettoc` result as `ok` only when it exited `rc=0`, carried a
  valid SES banner, parsed >=1 resident row, AND the boxed table carries BOTH the `| Name |` header
  row and a closing `+---+` separator strictly after its last data row; otherwise it reads
  `unverified`. A real 9-row capture cut short after four rows (a serial timeout mid-download can
  still exit `rc=0`) would otherwise silently delist the cut-off tail (`BOOTLOAD`/`A32_APP`/
  `HP_APP`/`HE_APP`), the 2026-09-07 hardware loss this guard exists to close. There is no
  exemption for a transcript with neither marker: noise can swallow the top separator and header
  while a timeout cuts the tail, a different SETOOLS build could use unseen box-drawing glyphs, and
  SES boot-banner rows interleaved by a mid-query reset carry no markers either, so a transcript
  with no recognised table structure is `unverified` on both legs. The refusal message for that
  shape says the table format was not recognised and asks for the transcript, rather than steering
  at `--replace-atoc`. Fixtures cover a truncated-after-baseline-rows table, a table cut mid-row, a
  table missing only its closing separator, and (as a negative control, in each suite) a boxless
  table without markers.
- **The abort decision is boolean.** The runner branches on `decide_atoc_guard`'s `refused`
  directly, with a fail-closed catch-all raise for any refused status it has no dedicated message
  for.
- **The generic foreign-entry refusal does not steer toward `--replace-atoc`.** Both legs lead with
  "capture/restore first" and present `--replace-atoc` only as the last resort ("...only once you
  know it is safe to lose"), naming the pre-provisioned-module factory-bootloader risk. This is the
  branch a module falls into if its factory bootloader's real ATOC name differs from `MCUBOOT-`.
- **`_FACTORY_MCUBOOT_ATOC_NAME = 'MCUBOOT-'` is unsourced.** It traces to one sentence in
  `zephyr/sysbuild/aen/README.md`, documenting a SETOOLS-shipped config alp-sdk does not ship; no
  capture of a real pre-provisioned module's `gettoc` output exists in this repo to confirm it.
  Marked **TBD (unverified, no gettoc capture of a pre-provisioned module)** in the code comment
  and in every doc that names it (`docs/aen-provisioning.md`, `docs/_aen-runbook-section.md`,
  `zephyr/sysbuild/aen/README.md`). A wrong literal does not make the guard unsafe: an unrecognised
  factory name still refuses, it only loses its dedicated message.
- **Availability check.** The maintenance binary is checked with `os.access(path, os.X_OK)`,
  matching the bash guard's `[ -x ... ]`, with a test that isolates the availability check itself.
- **Unwritable build_dir.** The transcript/verdict `write_text` calls re-raise a `RuntimeError`
  naming the path; the burn is never reached either way. This is the one case where the "a refused
  run always leaves a verdict" contract cannot hold, since there is nowhere to put it.
- **`transcript` is always absolute** (`.resolve()`d), tested through a relative `build_dir`.
- **`_run_maintenance`** catches `TimeoutExpired`, `OSError` and `ValueError` (e.g. a NUL byte in a
  garbled `se_uart` string), all becoming the same rc=1 failed-read.
- **Padded `" No ATOC found on target device."`** (leading/trailing whitespace, the way SETOOLS pads
  the SES banner) reads as `empty` on both legs (`is_no_atoc_found` and the bash `grep`), with a
  parity test.
- **Post-burn log line.** It states only that the write completed; `do_run`'s only write is
  `app-write-mram -p` (never an erase), and the AEN bench notes document the SE preferring a STALE
  resident slot0 image over a freshly written ITCM-load ATOC, so boot is not verified by this
  command. `docs/aen-bench-bringup.md`'s guard section states that `west flash` is a Flow-A-class
  destructive MRAM/ATOC write (not a safe incremental update), and that the canonical
  `person_detect` slot0 restore's own `ALP-HE` entry sits *inside* this guard's allowed set, so a
  subsequent `west flash` overwrites it silently, by design, not as a bypass.
- **Test provenance.** `_REAL_MULTI_ENTRY_ATOC` is not a `gettoc` capture: it is "trimmed from the
  alp-sdk#2025 incident report" (PR #2026), hand-assembled from prose with no header row, no
  `+---+` separators and no SERAM `Time (ms)` column. It is kept in its boxless shape as each
  suite's negative control; a `_boxed()`/`_REAL_MULTI_ENTRY_ATOC_BOXED` variant covers the
  foreign-entry-detection tests. Every synthetic "ok"/"foreign" fixture across the four test files
  carries the header+separator bookends a real capture has, via a shared `_boxed()`/
  `_boxed_bytes()` helper.

### Not yet verified (bench-owed before this is safe to rely on in the field, same "Bench before merge" caveat the issue itself named)

The Python port + this runner's wiring have not been run on a real AEN
EVK slot at all — the parser semantics are bench-proven only in bash.

Three specific gaps remain, all needing the bench, not a doc guess, to
close:

- **Truncation reachability (measured, #2538).** On an E1M-AEN803 (serial
  2026W36-0009, `SES A1 v1.110.0`) a stalled SE-UART read right after a
  complete entry makes `maintenance -opt gettoc` exit 0 with 4, 7 or 8 rows
  and no closing `+---+` line (3/3 at byte 548); a reply later than 0.5 s
  gives a header-only table, also exit 0. The closing line is printed only
  when the 0xa8 end packet arrives, so the structural-completeness rule is
  the primary defence, not defence in depth. A closed port exits 1, and a
  complete table followed by `[ERROR] ... readSerial reporting
  disconnected` is caught only by the exit code, so a non-zero exit stays
  refused.
- **The factory `MCUBOOT-` name.** Still TBD — see above. Capturing a
  real pre-provisioned module's `gettoc` output is a Stage 2 bench task;
  until then this is a plausible, not confirmed, literal.
- **Mid-table row loss or a merged line is undetectable by structure
  alone (residual gap).** The
  structural-completeness check proves the transcript's HEADER and
  CLOSING SEPARATOR both arrived; it says nothing about whether every row
  BETWEEN them arrived intact. A serial glitch that drops exactly one
  `\n` mid-table merges two rows into one (the dropped row's own name
  ends up concatenated into field >=4 of the surviving row -- an address
  or flags column, never re-parsed as a second Name), or a glitch that
  silently drops one whole row without disturbing the header/separator
  count at all, both leave a structurally "complete" table that is
  missing a resident entry the guard can no longer see to protect. This
  is not a hypothetical unique to this guard -- it is the same class of
  gap a fixed-width/line-oriented parser always has against a corrupted
  byte stream — but it is real, unclosed, and not something either
  `_is_table_structurally_complete` or its bash mirror can detect from the
  transcript text alone. No fix is proposed here; recorded as an open,
  understood limitation.
