### Fixed — the `alif_flash` west runner burned a fresh ATOC without reading the resident one first, silently delisting every other app entry (#2262)

`scripts/west_commands/runners/alif_flash.py`'s `do_run` (the `west flash`
runner wired into all six `zephyr/boards/alp/e1m_aen*` boards) staged a
signed ATOC config holding only `DEVICE` + this build's own `ALP-HE`/`ALP-HP`
entry, then burned it with `app-write-mram -c <SE_UART> -p` — a write that
REPLACES the whole resident ATOC, not merges it. Every other resident app
entry (the other M55 core's own entry, an A32 Linux boot chain
`BOOTLOAD`/`A32_APP`, ...) was silently delisted the instant the write
landed, with no error and no SES warning (`[SES] ATOC ok` prints either
way). #2025 closed this exact hazard (an AEN EVK bench unit's A32 Linux boot
chain, 2026-09-07) for the bench shell helpers alone (`bench_atoc_replace_guard`
in `scripts/bench/aen/bench-env.sh`); it never reached this `west flash`
door.

`do_run` now reads the resident ATOC back over the SE-UART before burning,
with the same two documented, non-destructive SETOOLS queries the bench
guard uses (`maintenance -opt getbanner` then `-opt gettoc`), and refuses the
burn — before anything is written — when a resident entry outside this
run's own `ALP-HE`/`ALP-HP` section would be delisted, or when the read
could not be verified (a missing `maintenance` binary, a malformed/absent
SES banner, or a non-zero query exit). The new `--replace-atoc` runner
option is the explicit override, spelled identically to
`flash-run.sh`'s own Flow A flag — distinct from, and never merged or
aliased with, Flow D's `--atoc-unqueryable` (#2027). A new `--se-uart-baud`
option (default `$SE_UART_BAUD`, else `57600`) matches the bench guard's own
baud fallback.

The parse/decision logic (`compute_query_status`, `foreign_resident_entries`,
`decide_atoc_guard`) is a single shared, pure-Python port of
`bench_atoc_replace_guard`'s semantics, added to `scripts/aen_atoc.py` next
to the existing ATOC-assembly guard (#1069). A parity test
(`tests/scripts/test_atoc_guard_parity.py`) feeds fixture transcripts
through both implementations and asserts identical verdicts (bash's exit
0/5 vs. Python's richer status, and — parsing bash's own `This board also
carries: ...` line — the identical foreign-entry NAME SET, not a substring
check). Some of those fixtures are the real, bench-verified 2026-09-07 AEN
EVK captures (the 9-row A32-Linux-boot-chain table, the clean two-row
table, the leading-space SES banner); others (an ANSI-coloured 2-row table,
a CRLF-only table, a truncated/NBSP-only-name row, a non-zero `gettoc` exit
after partial rows, `No ATOC found on target device.` on its own) are
hand-written to exercise one specific parser rule and were never captured
off real hardware — this changelog and the fixtures' own comments say
which is which; **do not read every fixture here as bench-proof.**

Two review rounds against the initial version of this fix found and closed:
- **A fail-open parser bug** (a Python row with fewer than 3 `|`-delimited
  fields, or a Name cell of pure NBSP, was silently DROPPED instead of
  read as a real — if oddly-shaped — resident entry the way `awk` reads
  it; both shapes now match `awk`'s own field/trim semantics exactly, with
  unit + parity coverage for both).
- **A wrong remedy for a pre-provisioned module's factory ATOC.** Alp
  Lab's factory-provisioned MCUboot bootloader shows up as a resident
  `MCUBOOT-` entry (`zephyr/sysbuild/aen/README.md`); this guard correctly
  refuses to burn over it, but `--replace-atoc` deletes it and leaves the
  module unable to boot — the refusal message for that specific entry name
  now says so and points at the already-documented Option B (plain
  J-Link, no ATOC) path instead of inviting `--replace-atoc`.
  `docs/aen-provisioning.md`, `docs/_aen-runbook-section.md`,
  `docs/aen-bench-bringup.md`, and `zephyr/sysbuild/aen/README.md` are
  corrected to stop promising plain `west flash` works day-1 on such a
  module.
- **A stale verdict file.** A run that fails BEFORE reaching the guard
  (no SETOOLS, no `zephyr.bin`, a rejected ATOC window, ...) now removes
  any `atoc-guard.json` a PREVIOUS run left behind, so its mere absence —
  not a stale `status` field — is what tells a caller "the guard did not
  reach a verdict this attempt".
- **A wedged SE-UART query with no timeout** could hang `west flash`
  forever; `maintenance -opt getbanner`/`gettoc` now time out (120s) and
  report `unverified`, the same fail-closed shape as any other query
  failure.

Every run leaves `<build_dir>/alif_flash/atoc-before.txt` (the raw
transcript) and `<build_dir>/alif_flash/atoc-guard.json` (a
machine-readable verdict — see "The verdict contract is frozen as v1"
below for the exact field set), written before any refusal is raised so
a caller such as tan-cli's `zephyr_west_flash` backend (tan-cli#1267) can
tell this refusal apart from any other `west flash` failure without
parsing stderr.

### The verdict contract is frozen as v1

`atoc-guard.json`'s `schema` field is the literal string
`alp-sdk.alif-flash-atoc-guard.v1`. The exact field set the code writes
(`schema`, `status`, `foreign`, `transcript`, `allowed`, `query_status` —
their types, allowed values, and what "absent file" / `query_status`
mean for telling the two `replaced` shapes apart) is documented once, in
`docs/_aen-runbook-section.md`'s "The verdict contract, frozen as
`alp-sdk.alif-flash-atoc-guard.v1`" table, rather than duplicated here.
Any future change to that field set must bump the schema string (`...v1`
-> `...v2`), the same convention `metadata/schemas/*-v1.schema.json`
already uses elsewhere in this repo.

### Sysbuild multi-domain `west flash` is NOT supported through `alif_flash` yet (alp-sdk#2274)

Zephyr's own multi-domain flash plumbing (in its `scripts/west_commands/`:
`flash.py` passes `build/domains.yaml` to `do_run_common`; `run_common.py`
resolves every domain in flash order and its own per-domain loop
instantiates and calls the board's flash runner ONCE PER DOMAIN, not once
per `west flash` invocation -- upstream Zephyr, not something alp-sdk
ships or can cite a stable line number in) means a sysbuild AEN build
(MCUboot domain + app domain) runs `alif_flash`'s `do_run` -- and
therefore this guard -- TWICE, once per domain's own build directory.

The guard identifies a resident entry by NAME ONLY. MCUboot (ITCM
`0x58000000`) and the HE app (HE slot0) both map to the identical ATOC
section name `ALP-HE` via `_atoc_section_name`, so on the SECOND
invocation the resident `ALP-HE` entry (written by the FIRST invocation)
is already in that run's own `allowed` set — not foreign — and the guard
reports `clear`. It still burns a fresh single-entry ATOC, silently
replacing whatever the first invocation wrote: the guard only ever
detects a FOREIGN name, never a same-name overwrite by a different
domain's build. **This is not a regression** — the pre-`#2262` runner did
exactly the same thing with no check of any kind — but it is a real,
unclosed gap in what this guard can catch, tracked as alp-sdk#2274
(closing it needs either a per-domain-aware `allowed` contract or a
binary-identity check this PR does not attempt). Do not read the
`clear`/`replaced` distinction above as covering this case: a same-name
overwrite between two sysbuild domains is exactly the kind of collision
neither status can currently name. (An untested hypothesis about whether
the app-domain invocation might fail earlier, at `_reset_vector`, on a
signed image's `imgtool` header, belongs to alp-sdk#2274's own
investigation, not this changelog — it is not claimed here.)

### Not yet verified (bench-owed before this is safe to rely on in the field, same "Bench before merge" caveat the issue itself named)

The Python port + this runner's wiring have not been run on a real AEN
EVK slot at all — the parser semantics are bench-proven only in bash.

Also open: the risk for a genuinely blank board is not ANSI colour (both
the Python port and the bash guard strip CSI sequences FIRST, before any
other check) — it is whether SETOOLS pads `No ATOC found on target
device.` with LEADING WHITESPACE the way it demonstrably pads the SES
banner (`" SES A1 v1.110.0 ..."`, bench-verified 2026-09-07). Neither
implementation's exact-line match tolerates that. This string has NO
in-repo source of truth: the `_NO_ATOC` fixture in
`tests/scripts/test_atoc_guard_parity.py` is SYNTHETIC (a hand-written
test vector, not a capture — see this file's own fixture-provenance
note above), and the identical risk applies equally to
`bench_atoc_replace_guard` in `scripts/bench/aen/bench-env.sh`, which
uses the same unpadded literal. Confirming (or padding) the real string
needs a genuinely blank AEN EVK board, not a doc guess.
