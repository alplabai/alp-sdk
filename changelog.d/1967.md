### Fixed — `meta-alp-sdk` documented the Alif BSP layer at a branch that does not exist (#1967)

`meta-alp-sdk/README.md` and `meta-alp-sdk/conf/layer.conf` both told the
reader to clone
[`meta-alif-ensemble`](https://github.com/alifsemi/meta-alif-ensemble) at
branch **scarthgap**, chosen to match alp-sdk's own Yocto series. That
repository has exactly one branch, `devkit-ex-b0`. So the documented step

```sh
git clone -b scarthgap https://github.com/alifsemi/meta-alif-ensemble ../meta-alif-ensemble
```

failed outright — not a subtle version mismatch discovered at `bitbake` time,
but a clone that never produces a layer at all. The README went on to explain
which machine confs "scarthgap keeps", a distinction that was never real.

Both sites now name `devkit-ex-b0`, the branch that exists. The README section
also states up front that the AEN A32 Yocto path is **blocked** rather than
reading as a working recipe: a reader who followed it to the end previously got
a broken clone and no indication that the destination was unreachable even with
the clone fixed. Why it is blocked is recorded separately (#1971).

Not documentation only. Alongside the prose, `meta-alif-ensemble` is dropped
from the bitbake-parsed `LAYERRECOMMENDS_alp-sdk` list in
`meta-alp-sdk/conf/layer.conf` — a layer that cannot be layered into a
Scarthgap build (#1971) has no business being recommended by one — and the
previously active `require conf/machine/devkit-e8.conf` in
`meta-alp-sdk/conf/machine/e1m-aen801-a32.conf` is commented out (#1968). No
recipe and no `LAYERSERIES_COMPAT` value changed.

Nothing here has been built or booted. Of the AEN A32 chain only the TF-A BL32
build is proven, and only as a build; the A32 cluster has still never run on
silicon.
