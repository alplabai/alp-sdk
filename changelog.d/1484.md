### Fixed — a `storage[].flash_device:` naming an AEN MRAM sub-region (`mcuboot`, `he_slot0`, `hp_slot0`, `reserved`, `storage`, `atoc`) resolved and decorated a Devicetree label that doesn't exist on the board (#1484)

`_resolve_flash_device()` in `scripts/alp_orchestrate/partition.py` fell back
to the `memory_map:` region's **name** as its Devicetree label whenever
neither the region nor any SoM preset declared `dt_label:` — and no preset
ever does; `grep -rn dt_label metadata/e1m_modules/*.yaml` returned nothing.
On every E1M-AEN30x/40x/50x/60x/70x/801 preset the region names `mcuboot`,
`he_slot0`, `hp_slot0`, `reserved`, `storage` and `atoc` are *partition*
labels **inside** the generated `mram_storage` flash node
(`scripts/gen_zephyr_board.py:1297`), not Devicetree node labels of their
own, so a `board.yaml` `storage:` entry targeting any of them made
`emit_dts_partitions` write `&storage { partitions { ... } }` (or `&mcuboot`,
`&atoc`, ...) against a label that appears nowhere in the board tree — a
"does not resolve" DT compile error rather than the refusal this should have
been.

Second half of the same defect: `_known_flash_devices()` unioned every
`memory_map:` region name into the "Known devices" set with no filtering, so
the loader's typo-rejection message advertised `atoc` and `mcuboot` — the
SE boot table and the MCUboot band #1289 carved out specifically to keep
customer allocation off of — as legal `flash_device:` targets. Both resolved
`status: ok, base_kib: 0` with no refusal; only `atoc` accidentally blocked,
and only when the entry was large enough to overrun its 32 KiB capacity.

Fixed at the root the schema already names: every one of those six regions
carries `carveout: false` (`metadata/schemas/som-preset-v1.schema.json`'s
`memory_region.carveout` — "a flash-class region... that base is NOT
byte-addressable shared memory a carve-out can safely land in"), which is
exactly the flag that marks a region as a sub-partition of a flash-class
node rather than a flash device. `_known_flash_devices()` now skips any
`carveout: false` region, and `_resolve_flash_device()` refuses one with a
reason (rather than fabricating a `dt_label`) as defense in depth for a
hand-built project that bypasses the loader's set. This removes `mcuboot`,
`he_slot0`, `hp_slot0`, `reserved`, `storage` and `atoc` from the AEN
`flash_device:` target set and the advertised "Known devices" list in one
move; the `on_module.ospi_memories:` branch (`ospi0`) is untouched by THIS
fix. `mram_main` itself (the actual flash-class region, `carveout`
unset/true) still resolves
today but is not a genuinely working target either — no AEN preset declares
a `dt_label:` override for it, so it falls back to a Devicetree label of
`mram_main`, and the generated board tree defines no such node (only
`mram_storage`); that gap is separate from this fix and is not closed here.

`metadata/schemas/som-preset-v1.schema.json`'s `dt_label` description no
longer presents "defaults to the region `name`" as an unconditionally safe
convention, and now states the `carveout: false` refusal explicitly.
`docs/board-config-features.md` and `docs/tutorials/09-board-yaml-deep-dive.md`
each gained the same note next to their `flash_device:` resolution-order
list.

Nothing on `dev` reached this path today — the one example declaring
`storage:` (`examples/connectivity/production-deployment/board.yaml`) targets
`mram_main`, and `dts-partitions.dtsi` is `#include`d by no committed
overlay — so this is a data/logic fix with no example or generated-file
fallout.

Third round: the reserved-region overlap remedy's "use a different
flash_device:" alternative list still leaked the same defect it was written
to close. It filtered out only the entry's own device and anything failing
`_resolve_flash_device()`, so it could (and, measured on E1M-V2N101, did)
recommend the very reserved region an entry had just been refused for
(`m33_tcm`) plus a sibling reserved region (`ocram_low`) — neither has a
Devicetree label, `_resolve_flash_device()` succeeding on a `memory_map:`
region proves only that it fabricates a `dt_label` default, not that the
default is real. The list now excludes every reserved-region name and
trusts only a `memory_map:` region with an explicit `dt_label:`
override — nothing declares one yet, so on a SoM where nothing qualifies
(every SoM today) the remedy names no alternative rather than an
undefined one. Separately, the reserved-spans WARNING that fires when a
device's capacity can't be mapped onto the SoM's addressed window is now
suppressed for an `on_module.ospi_memories:` device — an off-chip OSPI
part legitimately has no `memory_map:` presence, so sibling-only checking
isn't a degradation there, and every AEN storage build targeting `ospi0`
was printing the warning as pure noise.

Fourth round: the third round's own `_has_real_dt_label()` still trusted
an `on_module.ospi_memories:` key "by construction" — false. Measured
against the generated Zephyr board trees: `ospi0` is the ONLY `ospi<n>`
label anywhere under `zephyr/`
(`zephyr/dts/alif/ensemble_e8_peripherals.dtsi:503`), only the two
E1M-AEN801 board `.dts` files include it, and there it is the OSPI
CONTROLLER node (`status = "disabled"`, no flash-chip child) — not an
enabled flash device. E1M-AEN401/601 have a board tree with no `ospi0`
node; E1M-AEN301/501/701 have no board tree at all. The prior fix's own
`alt_devices` filter was therefore RECOMMENDING `ospi0` as a storage
`flash_device:` alternative on 5 of 6 AEN SKUs — the exact
"decorates a Devicetree label that doesn't exist on the board" defect
this issue is titled after. `_has_real_dt_label()` no longer trusts
`on_module.ospi_memories:` at all; it now trusts only a `memory_map:`
region with an explicit `dt_label:` override, which means `alt_devices`
names no alternative on any SoM today (none has that override yet).
The fully-tiled remedy's "no other flash_device: resolves for this SoM"
wording was also inaccurate for the same reason — `ospi0` DOES resolve
(`_resolve_flash_device()`), it just has no verified label — so that
branch now says "no other flash_device: on this SoM both resolves and
has a verified Devicetree label" instead, true in both cases. Corrected
the same "real DT label"/"genuine flash device" claim about `ospi0`
everywhere it had spread: `docs/board-config-features.md`,
`docs/tutorials/09-board-yaml-deep-dive.md`,
`metadata/templates/board.yaml`,
`metadata/schemas/board.schema.json`'s `flash_device:` description, and
the two test files' docstrings
(`test_orchestrate_storage_pinned_offsets.py`,
`test_orchestrate_storage_region_bounds.py`) that called E1M-AEN301's
`ospi0` "a genuine flash device" / "real external OSPI NOR" — that SKU
has no board tree at all. Added an E1M-AEN401 regression (fully-tiled
`mram_main`, mirroring the E1M-V2N101 "no alternative" case) asserting
the remedy names no alternative device.

This is still not a full close of #1484's root cause for the general
case: naming a `memory_map:` region directly (e.g.
`flash_device: mram_main`) still resolves `status: ok` with a fabricated
`dt_label` default that is never checked against the generated board
tree. alp-sdk#1556 tracks validating the resolved `dt_label` against the
generated board tree (or requiring an explicit, verified `dt_label:`)
before `resolve_storage_partitions()` returns `status: ok`.
