### Added — E1M-X EVK I2C inventory: INA228 chip manifest and a board I2C table (#2645)

Every I2C bus and fixed device on the E1M-X EVK with an E1M-V2N / E1M-V2M SoM was checked against the hardware design data and against recorded `i2cdetect` sweeps on E1M-V2M103 units. The SDK already described all but one of them.

- **`metadata/chips/ina228.yaml` (new).** The board metadata names `part: ina228` for the +5V input monitor at `0x42`, but the part had no chip manifest. The new manifest is catalogue-only (`driver_status: none`): the INA228's 20-bit register map is not `chips/ina236`'s, and the 6.1.141-cip43 `ina238` hwmon driver matches `ti,ina238` only. `scripts/check_chip_manifest_parity.py` allowlists it until a driver lands.
- **`docs/boards/e1m-x-evk.md`.** New "I²C buses and devices" section: each bus with its controller and Linux adapter number, each device with its address, strap, interrupt / reset lines and SDK driver, and a column saying whether the address was seen on a real unit.
- **`metadata/boards/e1m-x-evk.yaml`.** `XEVK_I2C_ADDR_EEPROM` (`0x50`) is now described as what it is: the SoM identity EEPROM, which shares E1M-X I2C0 with the carrier sensors. The carrier has no EEPROM of its own. The macro and its value are unchanged; only the comment in `include/alp/boards/alp_e1m_x_evk_routes.h` moves. The block's board notes also record the 2026-10-02 sweeps, in which `0x42` and `0x68` answered.

No address changed and no Linux device tree node was added. Parts with an SDK `chips/` driver stay on that driver over i2c-dev (#2339, #2335).

Still open on #2645, all needing a powered board: an ID-register read at `0x42`, `0x68` and `0x69` on `i2c-0`; which controller the display touch bus and the mikroBUS I2C reach; the enable polarity of the PCIe / M.2 I2C switch; and an INA228 driver.
