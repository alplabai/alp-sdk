### Added — E1M-X EVK I2C inventory: INA228 chip manifest and a board I2C table (#2645)

Every I2C bus and fixed device on the E1M-X EVK with an E1M-V2N / E1M-V2M SoM was checked against the hardware design data and against recorded `i2cdetect` sweeps on E1M-V2M103 units. The SDK already described all but one of them.

- **`metadata/chips/ina228.yaml` (new).** The board metadata names `part: ina228` for the +5V input monitor at `0x42`, but the part had no chip manifest. The new manifest is catalogue-only (`driver_status: none`) by design: upstream Zephyr v4.4.1 already ships a `ti,ina228` driver (`drivers/sensor/ti/ina2xx`, `CONFIG_INA228`) covering shunt, bus, die temperature, current, power, energy, charge and accumulator reset, so it is consumed as-is (ADR 0017 Tier 1) rather than reimplemented. `chips/ina236` is not reusable (16-bit registers) and the 6.1.141-cip43 `ina238` hwmon driver matches `ti,ina238` only. On the current EVK revision the device's bus pins are documented as swapped and corrected by a hand rework, so it answers at `0x42` only on carriers with that rework; no answer means the part is absent, not a fault. The driver was not run on hardware: the only bench fact is that `0x42` acknowledged on 2026-10-02, and no ID register was read. `scripts/check_chip_manifest_parity.py` allowlists the manifest.
- **`docs/boards/e1m-x-evk.md`.** New "I²C buses and devices" section: each bus with its controller and Linux adapter number, each device with its address, strap, interrupt / reset lines and SDK driver, and a column saying whether the address was seen on a real unit.
- **`metadata/boards/e1m-x-evk.yaml`.** `XEVK_I2C_ADDR_EEPROM` (`0x50`) is now described as what it is: the SoM identity EEPROM, which shares E1M-X I2C0 with the carrier sensors. The carrier has no EEPROM of its own. The macro and its value are unchanged; only the comment in `include/alp/boards/alp_e1m_x_evk_routes.h` moves. The block's board notes also record the 2026-10-02 sweeps, in which `0x42` and `0x68` answered.
- **Removed: the `0x48` camera-rail monitor (`XEVK_I2C_ADDR_INA236_VCAM2`, `XEVK_INA236_SHUNT_VCAM2_OHMS`, `XEVK_INA236_MAX_VCAM2_A`).** The INA236B strapped to `0x48` on E1M-X I2C0 is not fitted; `0x48` there is the shared address of the two TAS2563 amplifiers (recorded in `metadata/chips/tas2563.yaml`, which `scripts/check_i2c_address_uniqueness.py` reads, so nothing else can be assigned it). The `0x48` allowlist entry in that gate is gone, the three macros are recorded in `docs/abi/removed-symbols.json`, and `examples/v2n/v2n-power-monitor` and its HIL spec now read only the 3V3, 1V8 and VCAM3 monitors. The board doc, the I2C scan tutorial and the board metadata no longer describe an open BMI323 / ICM-42670 address clash: the as-built addresses are `0x68` (BMI323) and `0x69` (ICM-42670).

No other address changed and no Linux device tree node was added. Parts with an SDK `chips/` driver stay on that driver over i2c-dev (#2339, #2335).

Still open on #2645, all needing a powered board: an ID-register read at `0x42`, `0x68` and `0x69` on `i2c-0`; which controller the display touch bus and the mikroBUS I2C reach; the enable polarity of the PCIe / M.2 I2C switch; and the `ti,ina228` Devicetree node with the shunt value for the upstream driver.
