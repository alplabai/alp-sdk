### Removed — `board.schema.json`'s `ota.server.tls_ca_bundle` (#1493)

The schema declared `ota.server.tls_ca_bundle` ("Optional pinned CA bundle
for production"), but the string appeared nowhere else in this repo — no
emitter, loader, gate, test or example read it. (The public consumer
`alp-sdk-vscode` still carries three live copies of the key —
`packages/alp-core/src/board/models.ts`, `packages/alp-webview/src/types.ts`,
and `schemas/board.schema.json`, the last registered as VS Code's board.yaml
validation schema — so the editor will keep autocompleting a key this schema
now rejects; tracked separately as
[alplabai/alp-sdk-vscode#589](https://github.com/alplabai/alp-sdk-vscode/issues/589).)
`_hawkbit_server_lines()`
(`scripts/alp_orchestrate/kconfig.py`) derives TLS from `url`'s scheme alone
(`CONFIG_HAWKBIT_USE_TLS=y`, no sec-tag/CA symbol), and the Yocto/Mender
branch of the same file emits no CA variable either. The key validated and
the value silently evaporated: a customer setting it got a build that
succeeded with no trust anchor installed.

This is the same defect class `boot.anti_rollback` was removed for — a field
promising a security guarantee the SDK doesn't deliver — so it is removed
the same way: deleted from the schema, no legacy shim (no active customers),
no `schemaVersion` bump (matching the `anti_rollback` precedent — a bump is
reserved for a real `scripts/alp_migrate` migration step, and a straight
field removal isn't one).
