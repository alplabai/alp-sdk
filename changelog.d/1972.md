### Added — the Cortex-A32 (APSS) Linux boot chain is documented in `docs/bring-up-aen.md` (#1972)

The AEN bring-up doc covered the M55 side only; the A32 half of the E8 had no
written boot model at all, so the first person to attempt it would have had to
re-derive it from the vendor trees. It is now recorded.

The chain is short and unlike the V2N/NX9101 ones: the **Secure Enclave**
releases the A32, **TF-A BL32** (`SP_MIN`, AArch32) runs, and it hands off to
the preloaded payload as **BL33**. There is no BL1, no BL2, no BL31 and no
U-Boot — the SE does the job the earlier boot stages do elsewhere, and the
payload is already resident rather than loaded from boot media. A reader
carrying the RZ/V2N model over would look for a U-Boot prompt that does not
exist.

The doc records the verified upstream sources —
[`trusted-firmware-a_alif`](https://github.com/alifsemi/trusted-firmware-a_alif)
branch `alif_lts-v2.10.8` and
[`linux_alif`](https://github.com/alifsemi/linux_alif) branch `v6.12-dev` —
the exact BL32 build line, and the MRAM/SRAM layout the whole chain has to fit:

- `bl32` at `0x80002000`
- `dtb` at `0x80010000` — this one is not a defconfig value like the others
  around it: it is TF-A's own build option `ARM_PRELOADED_DTB_BASE=0x80010000`,
  which BL32 passes to the kernel in `r2`
- kernel XIP at `0x80020000`
- `cramfs` at `0x80380000`
- kernel RAM at `CONFIG_PHYS_OFFSET=0x2000000`

XIP plus a `cramfs` root is what makes the arithmetic close at all: the chain
fits inside the E8's 5.5 MB MRAM, which a conventional decompress-to-RAM Linux
would not.

**The BL32 that was built and flashed is the debug build.** On 2026-09-05, with
`PLAT=devkit_e7 ALIF_SOC_E8=1` per the branch that carries E8 support:

```sh
make -j"$(nproc)" \
  CROSS_COMPILE=arm-zephyr-eabi- ARCH=aarch32 PLAT=devkit_e7 \
  DEBUG=1 LOG_LEVEL=40 ALIF_SOC_E8=1 \
  ALIF_CONSOLE_UART_BASE=0x4901D000 \
  ALIF_CONSOLE_RX_PORT=PORT_3 ALIF_CONSOLE_RX_PIN=PIN_4 \
  ALIF_CONSOLE_TX_PORT=PORT_3 ALIF_CONSOLE_TX_PIN=PIN_5 \
  ALIF_CONSOLE_PIN_FUNC=PINMUX_ALTERNATE_FUNCTION_2 \
  ALIF_BL32_XIP_BASE=0x80002000 ALIF_BL32_XIP_SIZE=0xD000 \
  ALIF_TRUSTED_SRAM_BASE=0x027DE000 \
  ARM_LINUX_KERNEL_AS_BL33=1 ARM_PRELOADED_DTB_BASE=0x80010000 \
  PRELOADED_BL33_BASE=0x80020000 \
  bl32
```

That produces `build/devkit_e7/debug/bl32.bin`, **20621 bytes** on disk; SETOOLS
pads it to 20624 in the ATOC map. `DEBUG=1 LOG_LEVEL=40` is deliberate — it is
what makes BL32 emit `INFO` lines, where a release build prints `NOTICE` and
above only — and `ALIF_BL32_XIP_SIZE=0xD000` is what the flashed image happened to be
built with, not something the build needs: measured 2026-09-05, omitting it
links just as well and yields the same 20621 bytes, because that fits the
`0x8000` default window. The knob is compiled in and sizes the mapped XIP
region, so the images differ byte-for-byte — but nobody should carry it
forward believing the debug build required it. Earlier notes citing a 16517-byte
`bl32.bin` describe a release build that no longer exists on disk and that
carried neither the DTB handoff nor the console fix; it is not the artifact to
reproduce.

**The six `ALIF_CONSOLE_*` knobs above do not exist upstream (#1979).** They are
a local patch to the vendor tree. `trusted-firmware-a_alif` @ `alif_lts-v2.10.8`
hardcodes the console to the DevKit's UART2, in two places — the register base
in `plat/alif/board/devkit_e7/common/include/platform_def.h` and the pads in
`devkit_e7_pinmux_init()` in
`plat/alif/board/devkit_e7/sp_min/devkit_e7_sp_min_setup.c`. A reader with a
clean checkout **cannot run the command as written**; the knobs have to be
patched in first. That is what #1979 tracks.


**Linux boots to a live shell on silicon, 2026-09-05.** Observed on two
separate E1M-AEN803 modules: Linux 6.12.6 comes up on the Alif Ensemble E8
(AE822) Cortex-A32 and reaches an interactive shell on the carrier console at
115200 on UART5. This supersedes the earlier `Kernel panic - not syncing: VFS:
Unable to mount root fs on unknown-block(0,253)` result recorded here — that
panic was the no-rootfs case, not the end state.

Console evidence, observed:

```text
NOTICE:  SP_MIN: v2.10.8(debug):59a39e0-dirty
INFO:    Entry point address = 0x80020000
INFO:    SPSR = 0x1d3
Booting Linux on physical CPU 0x0
OF: fdt: Machine model: Alp E1M-AEN EVK (Alif Ensemble E8, A32 unicore)
psci: PSCIv1.1 detected in firmware.
ensemble-clk: CPU clock registered, PLL rate=800000000 Hz
4901d000.serial: ttyS0 at MMIO 0x4901d000 (irq = 54, base_baud = 6250000) is a 16550A
cramfs: linear cramfs image on mtd:physmap-flash.0 appears to be 1024 KB in size
VFS: Mounted root (cramfs filesystem) readonly on device 31:0.
Run /init as init process
```

and from the shell itself: `CPU part : 0xd01` (Cortex-A32), `Hardware : Alif
Ensemble`, and `sysfs /sys sysfs rw,relatime 0 0` in `/proc/mounts`.

**The Secure Enclave side is what makes this more than a console printing
something.** The SE's boot table, read over the SE-UART at 57600, shows the SE
itself validating the ATOC and releasing the A32:

```text
|   Name   |  CPU   | Store Addr |  Obj Addr  | Boot Addr  |   Size   |  Flags |
| BOOTLOAD | A32_0  | 0x80002000 | 0x8057A8F0 | 0x80002000 |    20621 | u VB   |
|  A32_APP | A32_0  | 0x80020000 | 0x8057B2F0 | ---------- |  2290045 | u V    |
|   HP_APP | M55-HP | 0x8057D230 | 0x8057C830 | 0x50000000 |     4480 | uLVB   |
|   HE_APP | M55-HE | 0x8057EDB0 | 0x8057E3B0 | 0x58000000 |     4480 | uLVB   |
Legend: (u)(C)ompressed,(L)oaded,(V)erified,(s)kipped verification,(B)ooted,(E)ncrypted,(D)eferred
```

`BOOTLOAD` is `cpu_id A32_0` at boot address `0x80002000` with flags `u VB` —
uncompressed, **V**erified, **B**ooted. `A32_APP` is `u V`: verified but
deliberately **not** loaded, because the kernel executes in place from MRAM and
BL32 jumps to it. Alongside it the SE prints `[SES] ATOC ok` and `[SES] LCS=1`,
with `SEROM v1.109.46 0x000002A1`, `SES A1 v1.110.0`, `[SES] SE frequency is
74.36 MHz` and `[SES] No LF XTAL`.

Getting from the panic to a shell needed three things beyond the layout above,
all of them on the payload side rather than in TF-A:

- `init=/init` in the carrier bootargs. Not because `/sbin/init` is missing —
  busybox installs it as a symlink and the kernel runs it happily. The point is
  that a cramfs root is a *real* root filesystem, not an initramfs, so the
  kernel takes its default `/sbin/init` and the image's own `/init` script —
  which mounts `/proc`, `/sys` and `/dev` and prints the banner — is never
  reached. `Run /init as init process` in the boot log is the confirmation
- `/etc/inittab` and `/etc/init.d/rcS` present in the image, so busybox `init`
  still behaves if it is ever booted *without* `init=`. Its compiled-in default
  respawns getty on `/dev/tty2`../dev/tty4`, which do not exist here, and the
  console fills with `can't open /dev/tty2: No such file or directory`
- `CONFIG_SYSFS` and `CONFIG_DEVTMPFS_MOUNT` enabled in the kernel config

**What this does not mean.** No bitbake or Yocto build has been run, at all.
`MACHINE = "e1m-aen801-a32"` and `e1m-aen701-a32` remain non-buildable
placeholders, and silicon booting does not change that: the boot used
hand-built artefacts — TF-A, kernel and cramfs assembled by hand — not a layer.
The rootfs is a hand-rolled statically-linked busybox cramfs, not an
`alp-image-*`. The `ALIF_CONSOLE_*` caveat above still stands (#1979), so the
build is not reproducible from a clean checkout. The OSPI0 chip-select
assignment is still unmeasured (#1973) and the HyperRAM capacity still disputed
(#1969).
