### Fixed — TAS2563 TDM clock fault is now armed by `tas2563_configure_fault_pin()` (#2140)

`TAS2563_FAULT_TDM_CLOCK` reads `INT_LTCH0[2]`
(`include/alp/chips/tas2563.h:346` ("TAS2563_FAULT_TDM_CLOCK")), but
`INT_MASK0`'s reset value `FCh` leaves that bit masked and a masked event
never latches at all -- nothing in the driver unmasked it, so the flag read
clear whether the TDM/I2S clock was present, stopped, or never valid.
Measured on `e1m-aen-evk-03` from `examples/aen/aen-i2s-tas2563-probe`: the
flag stayed `0x00000000` both while playing and after `alp_audio_out_stop()`,
discriminating nothing (SLASET3D §7.5.28-§7.5.31, p.77-80, already cited at
`include/alp/chips/tas2563.h:719` for the other three `INT_MASK` registers).

`tas2563_configure_fault_pin()` now clears `INT_MASK0` bit 2 as part of
binding the fault pin
(`chips/tas2563/tas2563.c:625` ("reg_update(ctx, TAS2563_REG_INT_MASK0")),
citing the register address already modelled by the fake at
`tests/zephyr/chips/src/fake_tas2563.c:96` ("INT_MASK0   §7.5.28 p.77") and the
bit position already recorded in the driver header
(`include/alp/chips/tas2563.h:721`, pre-fix, "`INT_MASK0[2]`"). A caller
binding a fault pin gets every safety-relevant latch reaching both IRQ_N and
`tas2563_read_faults()`, TDM clock loss included, rather than having to know
to write `INT_MASK0` directly. `tas2563_read_faults()`'s doc comment
(`include/alp/chips/tas2563.h:791` ("@note A masked event never latches"))
now states which faults are armed by default: over-temperature/over-current
(`INT_MASK0`), VBAT brown-out/speaker open-short (`INT_MASK1`) and VBAT POR
(`INT_MASK2`) at reset, TDM clock error once a fault pin has been configured
(#2140), and `INT_MASK3` (`FFh`) masked wholesale with nothing in this driver
unmasking it.

### Not included in this fix

The issue's other two asks -- a public accessor decoding register `0x11`
("DSP Mode & TDM_DET", SLASET3D §7.5.19) into a detected sample rate and FS
ratio or "no valid clock", and switching
`examples/aen/aen-i2s-tas2563-probe`'s TDM check to key on that live state
instead of the latch -- are **not done**. `include/alp/chips/tas2563.h:569`
("correctly documented, despite its title")
already records that register `0x11` holds `FS_RATIO`/`FS_RATE` fields, but
no in-tree citation (this driver, its tests, or `changelog.d/2040-*.md`,
which is the only other place `§7.5.19` is cited) gives those fields' bit
positions or their value encoding -- only the register's existence and
purpose. Decoding a byte into a rate/ratio without a sourced field layout
would be a fabricated silicon behaviour indistinguishable from a real one to
the next reader, so it was left undone rather than guessed. Sourcing
SLASET3D §7.5.19's actual `FS_RATIO`/`FS_RATE` bit table is a prerequisite
for both remaining asks.
