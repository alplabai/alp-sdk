### Fixed — CI trusted `west patch apply`'s exit 0, which is also what it returns after applying nothing (#1392 item 3)

`.github/workflows/pr-twister-aen.yml` ran the AEN patch carry as a bare
`west patch apply` and believed its exit status. That status is not evidence:
the pinned Zephyr v4.4.1 `scripts/west_commands/patch.py` exits 0 on two
distinct "did nothing" paths.

* `load_yml()` prints `no patches to apply: {args.patch_yml} not found` and
  returns `None`, and `do_run()` returns right after — exit 0. This is what
  the `-b`/`-l` flags produced in workspace `C:\alp\ws1380`:
  `west patch -b zephyr/patches -l zephyr/patches.yml apply` resolves both
  flags against the **manifest repo**, looked for
  `...\alp-sdk\alp-sdk\zephyr\patches.yml`, did not find it, and reported
  success. The same workspace, run from the correct cwd without the flags,
  applied **6 patches**.
* `apply()` does `mod = self.get_module_path(patch_info["module"])` followed
  by `if mod is None: continue` — a patch whose `module:` does not resolve is
  skipped with no warning and is simply absent from the final
  `{patch_count} patches applied successfully \o/` line. That is the #1076
  defect (`module: hal_alif` never matched hal_alif's own
  `zephyr/module.yml` `name: alif`), reached through a different door.

Either way the job then compiles against an unpatched workspace. On AEN that
is not cosmetic: `zephyr/patches/mcuboot/0001-flash_map_extended-alif-mram-base.patch`
is what teaches `flash_device_base()` about `alif_mram_flash_controller`.
Without it MCUboot computes the chainload vector table as
`0x0 + 0x10000 + 0x800` — an address in unused ITCM — and cannot chainload the
application from MRAM. Every layer still reports success; the first symptom is
a board that does not boot, which reads as a hardware or image problem.

New `scripts/west_patch_apply.py` replaces the bare command at that step. It
resolves `zephyr/patches.yml` itself and **fails before invoking west** if the
path does not exist, then invokes `west patch apply` with that exact resolved
path passed explicitly as `-l` (plus the sibling `patches/` directory as `-b`)
so west opens the same file that was just counted, rather than falling back to
its own default `manifest.path` resolution — a wrapper that only counted the
file without also telling west to open it could report success about a
manifest west never opened, which is the same defect class through a
different door. The wrapper then requires west to have reported that it
applied exactly as many patches as the file carries — today 6. A missing
success line fails with `applied no patches`; a short count fails with
`applied N of the 6 patches ...` and names the `module:`-resolution cause. A
west failure is propagated with west's own return code. Filtered runs (`-dm`)
can state their own expectation via `--expect-applied N`; extra arguments
after `--` are inserted before `west patch`'s `apply` subcommand, because
`-dm`/`-sm`/`-w` are `west patch`'s own parent-parser options and west's
argparse rejects them placed after `apply` (proved end to end against real
west v1.5.0). `apply`'s own `-r/--roll-back` is not reachable through this
passthrough.

Deliberately not a `scripts/check_*.py`: it mutates the workspace rather than
asserting a static repo invariant, so it is not a `metadata/quality-tasks-v1.json`
entry. Covered by `tests/scripts/test_west_patch_apply.py`, which stubs `west`
on `PATH` to reproduce both exit-0 no-op shapes and also asserts that
`pr-twister-aen.yml` still routes through the wrapper — the CI-wiring half of
the fix cannot silently regress.

Scope: this is item 3 of #1392 only. Item 1 (a gate that verifies the patched
symbols are present in a workspace) lands separately; item 2 (whether
`scripts/bootstrap.sh` should apply the patches at all, rather than leaving a
manual step CI has to replicate) is a maintainer decision and is untouched
here — `bootstrap.sh` still does not apply `zephyr/patches.yml`.
