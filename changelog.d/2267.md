### Fixed — ISP MRSZ SCALE_VC truncation dropped the last 4:2:0 chroma row (E1M-AEN803) (#2267)

`zephyr/drivers/video/isp_pico.c`'s `isp_apply_mrsz()` (added by #2258)
programmed `ISP_MRSZ_SCALE_VC` for the main resizer's 2:1 vertical-chroma
downscale (4:2:2 internal -> 4:2:0 output) as a plain
`((out_h - 1) * 65536) / (in_h - 1)`. For 480 -> 240 that truncates to
`0x7FBB` (32699), which the resizer computes back to
`floor((479 * 0x7FBB) / 65536) + 1 == 239` output lines -- one short of the
240 the 4:2:0 output needs. The last chroma row was never written.

**Silicon-confirmed, E1M-AEN803:** bench run 205 (`camera-mjpeg-stream`,
640x480 NV12 -> Hantro JPEG) showed image rows 478-479 (the last chroma
row, line 239) solid green in every frame -- the look of a never-written
chroma row; bench run 201 (`aen-isp-ov5647-capture`, I420) showed the last
U row (239) holding stale garbage.

`ISP_MRSZ_SCALE_VC` (HWRM SS17.3.4.3.169) documents only the register's
meaning, no formula, and neither the Alif DFP nor `hal_alif` programs this
register anywhere. The ISP main resizer is rkisp1-lineage silicon
(VSI/rkisp1 IP); its downscale ratio formula takes a `+1` a naive
`floor(((out-1)<<16)/(in-1))` misses:
`((len_out - 1) * RKISP1_CIF_RSZ_SCALER_FACTOR) / (len_in - 1) + 1`.

`isp_apply_mrsz()` now calls a new shared `alp_isp_mrsz_scale_vc()` helper
(`zephyr/include/zephyr/drivers/video/isp_frame_size.h`, the same header
`isp_pico.c`'s pitch/frame-size math already shares with
`tests/unit/isp_frame_size`) that applies the `+1` rounding, so the
resizer's output line count and the register formula can only drift once,
not into two independently-wrong copies. 480 -> 240 now programs `0x7FBC`.
New unit tests pin the corrected 480x240 value and the general
"produces exactly `out_lines`" property at two more sizes (360x180,
1080x540).
