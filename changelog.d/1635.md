### Fixed — five backend-parity guards from the #1635 audit: an unbounded GD32-bridge instance id, three missing vendor-ext NULL guards, a missing MQTT timeout clamp, a UART sw_fallback empty-read contract violation, and an unaligned storage erase-size (#1635)

`src/backends/qenc/gd32_bridge.c`'s `br_open()` stored `cfg->encoder_id` with
no bound of its own, then narrowed it to `uint8_t` before handing it to the
chip driver's own `GD32G553_BRIDGE_QENC_CHANNELS` check — so `encoder_id ==
256` aliased to channel 0 and opened fine, unlike every sibling GD32-bridge
backend (`counter`, `adc`, `dac`, `pwm`), which all bound the instance id at
open before any narrowing. `br_open()` now rejects an out-of-range
`encoder_id` with `ALP_ERR_INVAL` (matching the qenc `zephyr_drv.c` sibling's
convention) before the id is ever narrowed.

`src/backends/adc/alif_e8.c` and `alif_e7.c`'s
`alp_alif_adc_set_trigger_source()` checked `h == NULL` but then dereferenced
`h->backend->vendor` unchecked; `src/backends/ext/renesas/power.c`'s
`alp_renesas_power_supervisor_mode_set()` checked `handle->backend == NULL`
but not `handle->backend->vendor == NULL`. Six of the seven other vendor-ext
gates already carry the full three-part guard (`h != NULL && h->backend !=
NULL && h->backend->vendor != NULL`); these three now do too.

`src/backends/mqtt/yocto_drv.c`'s `y_connect()` passed `(int)timeout_ms`
straight to `mosquitto_loop()`, unlike `y_loop()` 65 lines below it, which
clamps at `INT_MAX` so a `UINT32_MAX`-as-forever caller doesn't roll over
into a negative timeout. `y_connect()` now applies the same clamp.

`src/backends/uart/sw_fallback.c`'s `sw_read()` ignored `timeout_ms`
entirely and returned `ALP_OK` on an empty ring with the destination buffer
untouched — a silent-failure violation of the documented contract
(`include/alp/peripheral.h`: "If the deadline is reached with zero bytes
collected, the call returns `ALP_ERR_TIMEOUT`", and for `timeout_ms == 0`,
"return immediately with `ALP_ERR_TIMEOUT` if no byte is already
available"). `sw_read()` now returns `ALP_ERR_TIMEOUT` whenever it drains
zero bytes, matching the `zephyr_drv.c` sibling.

`src/backends/storage/zephyr_flash.c`'s `z_get_info()` hardcoded
`erase_size = 1u` with a comment claiming the device API is opaque — false,
`flash_area_get_device(fa)` is already called two lines below and supports
`flash_get_page_info_by_offs()`. This contradicted `include/alp/storage.h`
("Both bounds MUST align to the device's erase_size"). `z_get_info()` now
reads the real page/sector size via `flash_get_page_info_by_offs()` when
`CONFIG_FLASH_PAGE_LAYOUT` is enabled, falling back to `1u` only if that
lookup is unavailable or fails.

Considered and reverted: a `wdt_disable(dev)` call on `zephyr_drv.c`'s
`z_open()` failure path, meant to undo the channel `wdt_install_timeout()`
installs before `wdt_setup()` can fail. It is not the right undo —
`wdt_disable()` is documented as device-wide ("automatically uninstalls all
timeouts", `zephyr/drivers/watchdog.h`), never per-channel, and in the state
this path runs in (setup just failed, instance not enabled) it returns
`-EFAULT` on `wdt_nrfx.c`, `wdt_renesas_rz.c`, and `wdt_fwdgt_gd32.c` — a
no-op on exactly the drivers where the leak is real. On `wdt_counter.c` it
*does* succeed, but as a bare `counter_stop()` with no enabled-check: it
stops the shared counter backing every installed channel and clears no
bookkeeping, disarming a running watchdog while still leaking. The channel
leak on a failed `wdt_setup()` is real but needs a per-driver-class fix, not
a device-wide disable; left open.

Left for a deliberate decision, not fixed here (each is a genuine
convention split across ≥2 backends, not an "obviously right" two-line fix):
the PWM out-of-range-channel status split (`ALP_ERR_OUT_OF_RANGE` in
`pwm/yocto_drv.c`, `ALP_ERR_INVAL` in `pwm/gd32_bridge.c`, both in
`pwm/zephyr_drv.c`); `storage_dispatch.c`'s `read_only` status split
(`ALP_ERR_NOT_READY` for write, `ALP_ERR_INVAL` for erase); and
`storage/zephyr_littlefs.c`'s hardcoded `erase_size = 1u`, which may be
deliberate given littlefs's own block abstraction rather than drift. Also
left: the two tensor-rank conventions across the three inference backends
(`src/yocto/inference_ort.cpp` and `inference_deepx.cpp` both truncate rank
at 4; `inference_drpai.cpp` reports rank `0` because the MERA wrapper
doesn't expose per-input shape — a documented capability gap, not drift);
`src/backends/counter/gd32_bridge.c`'s `ALP_ERR_NOSUPPORT` for an
out-of-range `counter_id`, a fourth status alongside the `ALP_ERR_INVAL`
`adc`/`dac`/`pwm`/`qenc` siblings use, well-argued in place (E1M-X connector
identities are a form-factor bound, not a per-SoM promise) but part of the
same convention split; and the wdt channel-leak-on-failed-setup noted above.

Not open bugs: `allow_unsafe_write` (`include/alp/storage.h`) and
`allow_modeset` (`include/alp/display.h`) are documented Yocto-only /
DRM-master-path-only by design and are ignored elsewhere on purpose — not
missing guards. The audio/i2s `timeout_ms`-forever handling
(`audio/zephyr_drv.c`'s `(int32_t)timeout_ms` cast, `i2s/zephyr_drv.c`'s
missing `UINT32_MAX` case) is a real inconsistency worth a closer look, but
narrower than previously stated here: `(int32_t)UINT32_MAX == -1 ==
SYS_FOREVER_MS`, so the exact `UINT32_MAX`-as-forever case already works.
The gap is the range `(INT32_MAX, UINT32_MAX-1]`, which casts to a negative
value other than `-1` and the underlying drivers treat as no-wait — a
~25-day timeout returns immediately instead of waiting. Neither
`alp_audio_in_read` nor `alp_i2s_write` currently promises
`UINT32_MAX`-as-forever the way `camera.h`, `mproc.h`, `peripheral.h`, and
`rpc.h` do, so this is a consistency gap against those siblings rather than
a documented-contract violation; outside this patch's assigned scope.

A `tests/zephyr/peripheral` regression
(`test_v2n_supervisor_qenc_open_out_of_range_id_rejected`) covers the
GD32-bridge qenc bound check without needing real V2N hardware — the check
now runs before the supervisor acquire, so it fires the same way whether or
not a bus is configured. A `tests/unit/uart_registry` regression
(`test_sw_fallback_empty_read_returns_timeout`) covers the UART empty-read
fix directly against the `sw_fallback` ops.

**PWM channel-id status.** `alp_pwm_open()`'s channel-id validation collapsed a real two-tier distinction into a single
status on two of the three PWM backends. `src/backends/pwm/zephyr_drv.c` already got this right
(and `src/backends/wdt/zephyr_drv.c` mirrors the same shape): `ALP_ERR_INVAL` for a channel index
outside the alp_pwm ABI's 0..7 space at all (a malformed argument, not a hardware limit), versus
`ALP_ERR_OUT_OF_RANGE` for a well-formed index the active SoC doesn't populate that many instances
of. On a board.yaml that runs the same portable app across different silicon, collapsing these to
one code destroys information a caller acts on — "fix your argument" versus "this part can't reach
that channel."

`src/backends/pwm/yocto_drv.c` returned `ALP_ERR_OUT_OF_RANGE` for every out-of-range channel_id,
including ones that aren't even in the ABI's 0..7 space. It now returns `ALP_ERR_INVAL` for those,
and reads the target pwmchip's own `npwm` sysfs attribute (`Documentation/ABI/testing/sysfs-class-pwm`)
to return `ALP_ERR_OUT_OF_RANGE` for a well-formed channel_id the running kernel's PWM controller
doesn't actually expose — the dynamic equivalent of `zephyr_drv.c`'s `ALP_SOC_PWM_COUNT`, since this
backend's `silicon_ref = "*"` gives it no static per-SoC ceiling to check at compile time. A failed
`npwm` read (chip not present yet) is not itself treated as out-of-range; that case already surfaces
as `ALP_ERR_NOT_READY` from the subsequent export write.

`src/backends/pwm/gd32_bridge.c` returned `ALP_ERR_INVAL` unconditionally. Its channel_id genuinely
has no second tier to split: `metadata/chips/gd32g553.yaml`'s `pwm_routing:` table wires all eight
E1M PWM channels to a real GD32 TIMER0/TIMER7 channel on V2N, with no partial-population case — so
`ALP_ERR_INVAL` was already the complete answer, not a collapsed one, and stays unchanged. The
backend's real hardware floor (a period the GD32 timer's 1 us prescaled tick can't represent —
`period_us == 0`, i.e. under 1 us, under 2 us center-aligned) already surfaces as
`ALP_ERR_OUT_OF_RANGE` from `br_set_duty()` / `br_set_period()` via the bridge firmware's own
`STATUS_OUT_OF_RANGE` (wire `0x08`); the comment at `br_open()` now says so instead of citing a
since-superseded "mirror the adc bridge" rationale, and instead of an earlier draft's ~303 us
"longest period" figure, which was wrong on two counts: it was the *unprescaled* 4.63 ns-core-clock
ceiling, not the firmware's actual 216:1-prescaled 1 MHz tick (real ceiling 65.536 ms, the 16-bit
ARR's full count), and an over-long period is currently silently clamped and returns `OK` rather
than surfacing `ALP_ERR_OUT_OF_RANGE` at all — filed separately as #1730, not fixed here.
`docs/gd32-bridge-protocol.md` and `metadata/chips/gd32g553.yaml` carried the same stale ~303 us
figure and are corrected too.

`include/alp/pwm.h`'s `alp_pwm_open()` Doxygen previously lumped both codes under one vague
"channel_id out of range or alias unset" bullet; it now states the `ALP_ERR_INVAL` /
`ALP_ERR_OUT_OF_RANGE` split explicitly, per `alp_last_error()`'s documented convention in
`include/alp/peripheral.h`.

**storage read-only status.** `src/storage_dispatch.c` split on `state.read_only`: `alp_storage_write()` returned
`ALP_ERR_NOT_READY`, `alp_storage_erase()` returned `ALP_ERR_INVAL` — same attribute, same
handle, same cause, two contracts. A read-only handle is a *state*, not a malformed argument:
the call is well-formed and would succeed on a writable handle. `alp_storage_erase()` now
returns `ALP_ERR_NOT_READY` too, matching `alp_storage_write()` and the convention the #1646
cluster (merged as PR #1713) settled for `alp_handle_op_enter()` failure — itself a state
problem, and already `ALP_ERR_NOT_READY` at 110 of 122 sites. ADR-0002 frames `ALP_ERR_INVAL`
as "programmer error" and a case could be made for that reading instead, but that rule is
already unimplemented at ~104 of 110 fused `op_enter` sites, so aligning storage with the real
convention beats aligning it with the aspirational one.

`include/alp/storage.h`'s `@return` docs for both `alp_storage_write()` and
`alp_storage_erase()` are updated to describe the unified behaviour — this was a documented
contract, not just an internal code path. A new `tests/unit/storage_registry` case
(`test_read_only_handle_write_and_erase_agree`) opens a read-only handle through the real
`alp_storage_open()`/`alp_storage_write()`/`alp_storage_erase()` public API and asserts both
calls surface `ALP_ERR_NOT_READY`, guarding against a regression back to `ALP_ERR_INVAL` on the
erase path.

**DRP-AI tensor shape.** `alp_inference_drpai_get_input()`/`get_output()` set `rank = 0` with an empty
`shape[]`, because `MeraDrpRuntimeWrapper::GetInputInfo()`/`GetOutputInfo()`
only report `(name, size_bytes, dtype)` — no shape. That comment was true but
irrelevant: the shape is on disk the whole time. `deploy.json`, the TVM
graph-runtime JSON `scripts/alp_model/adapters/drpai.py` tars into every
`drpai_dir` blob alongside `drp_desc.bin`/`weight.bin`, carries every graph
input's and output's shape, and lands flat in `st->model_dir` before
`open()` returns.

Both hooks now resolve real rank/shape from that file. `open()` parses
`deploy.json` once (a new file-local, dependency-free JSON scanner — alp-sdk
carries no JSON library, so this understands only the narrow TVM graph-JSON
subset it needs: nodes, `node_row_ptr`, `arg_nodes`, `heads`, and the
`attrs.shape` "list_shape" table) and correlates each entry to the existing
`in_info`/`out_info` vectors: inputs by node name (falling back to
graph-input positional order only when the counts agree), outputs
positionally (`deploy.json`'s `heads` order already matches `GetOutput(idx)`
order). Anything that doesn't resolve cleanly — the file missing or
unreadable, a schema that doesn't match, a corrupt dim — leaves that
tensor's `rank` at 0, identical to the prior behaviour; a wrong shape is
worse than no shape, so the parser bails rather than guesses.

A tensor whose real rank exceeds 4 also keeps `rank = 0`, deliberately.
`alp_inference_tensor_t.shape` is a frozen `uint16_t[4]`
(`[ABI-STABLE]`, `include/alp/inference.h`), and the sibling ORT/DEEPX
backends silently truncate a rank > 4 tensor to its first 4 dims — now
filed as #1729. DRP-AI does not add a third behaviour to that question.

Verified against the real `deploy.json` from a compiled `yolox-s-voc`
DRP-AI model (input `images` → `[1,3,640,640]`; three detection-head
outputs → `[1,25,80,80]`/`[1,25,40,40]`/`[1,25,20,20]`) plus synthetic
malformed inputs (missing file, truncated/non-object JSON, a non-integer
dim, an out-of-range node index, and a rank-5 shape) via a standalone unit
test, and by syntax-checking the modified translation unit against a
minimal local stub of the vendor `MeraDrpRuntimeWrapper.h`/`linux/drpai.h`
surface. **Code-complete and bench-unverified**: the DRP-AI runtime only
executes on V2N silicon under the MERA2/DRP-AI TVM sysroot, which does not
exist on this dev host — this change has not run on real hardware.

**Left unchanged, deliberately: `src/backends/counter/gd32_bridge.c`'s `ALP_ERR_NOSUPPORT`.** An earlier pass changed it to `ALP_ERR_INVAL` for consistency with its adc/dac/pwm siblings, and that was reverted. `include/alp/e1m_x_pinout.h` publishes COUNTER0..3 as E1M-X *connector identities* -- a form-factor bound, not a per-SoM promise (#1242) -- and the V2N/V2M bridge populates only id 0. Asking for COUNTER2 is a valid form-factor id this SoM does not serve, which is what `ALP_ERR_NOSUPPORT` means; it is not a malformed argument. `docs/portability.md` (4.5) and `e1m_x_pinout.h` both state that a published id never reports `ALP_ERR_INVAL`, and `tests/zephyr/peripheral/src/counter.c` pins it. The sibling backends returning `ALP_ERR_INVAL` for their own out-of-range ids may themselves be the drift; that is left open on #1635.
