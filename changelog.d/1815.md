### Added — promote DMA0 + EVTRTR0 into the shared E8 devicetree, add EVTRTR2 (#1815)

The E8 ships three PL330 DMA controllers and three Event Routers (AE822 HWRM §3.13.4: "EVTRTR0,
dedicated to DMA0 controller and UTIMER... EVTRTR1, dedicated to DMA1 controller... EVTRTR2,
dedicated to DMA2 controller and LPUTIMER"), but `evtrtr0`/`dma0` were declared only inside FIVE
example board overlays (`aen-cc3501e-bringup`, `aen-usb-firstlight`, `aen-cc3501e-gatt-register`,
`aen-cc3501e-companion-tour`, `aen-cc3501e-ble-gatt`) — the CC3501E bridge SPI1's only DMA
consumer — with no way for a second consumer to reach the same nodes without copy-pasting the
`ALIF_DMA_ENCODE()` cells and peripheral-request numbers by hand. `dma2` (the RTSS-HE-local
controller) already existed in `zephyr/dts/alif/ensemble_e8_peripherals.dtsi`, but its paired
event router, `evtrtr2`, did not — `alif,dma-event-router.yaml`'s own doc-comment example already
named it, unused.

`dma0` + `evtrtr0` are now declared in the shared dtsi, `status = "disabled"` like every other
block, content unchanged from the five overlays (bench-exercised there, not re-derived); the five
overlays now just flip `&dma0`/`&evtrtr0` to `status = "okay"` instead of redeclaring the nodes.
`evtrtr2` is added paired 1:1 with the existing `dma2` (`dma-controller = <&dma2>`, `dma-groups =
1`, matching the single-group LP-peripheral router the CC3501E overlay's own SPI1 routing comment
already described), at its HWRM-sourced local address `0x400E2000` (Table 10-8 M55-HE Local
Memory Map).

No separate `evtrtr1`/`dma1` node is added: per the HWRM, each M55 core's local PL330 + event
router sit at the SAME core-local register window (`0x400C0000` / `0x400E2000`) regardless of
which core reaches it — `dma2`'s own existing comment already documents that the RTSS-HP core
sees this identical address as "DMA1". A second, identically-addressed node would collide with
`dma2`/`evtrtr2`, not extend them; `evtrtr2`'s comment now states this explicitly, discharging the
"EVTRTR1 appears only in prose comments" gap without inventing a duplicate node.

Left undone: `dmas`/`dma-names` wiring onto the I2S, PDM, ADC, CPI and HexSPI nodes named in the
issue. Most of those peripheral nodes (`i2s0..3`, the main-domain `pdm`) do not exist in the
shared dtsi yet — they are declared per-example, matching this repo's established pattern that
`dmas` wiring is overlay-level (the CC3501E bridge's own `dmas` property lives in its overlay, not
on `spi0`/`spi1` in the shared dtsi) — so wiring them here would be scope creep past what a single
dtsi-file change can responsibly source. `evtrtr2`'s comment records the confirmed peripheral-
request numbers found while researching this (`DMA2_REQ[12]`/`[13]` LPSPI RX/TX, `DMA2_REQ[4]`
ADC24_DONE0) for whichever board overlay picks this up next.
