### Fixed — i2s3's pinctrl group declared TX only, leaving SDI (P9_2) unmuxed even though it is the one U46 leg wired correctly (#2196)

Both in-tree `i2s3` board overlays for the E1M-AEN801 (`ae822fa0e5597ls0`,
RTSS-HE) muxed only SDO/SCLK/WS and left `P9_2` (`I2S3_SDI_A`) undeclared.
`P9_2` is the one leg of U46 (a 74LVC157 2:1 mux) that is wired in the
*correct* direction — it feeds the amps' SDOUT/IV-sense back to the SoC —
unlike SDO/SCLK/WS, which are wired backwards against the SoC's own I2S3 TX
and are the reason this node ships `status = "disabled"` by default. The
omission was a deliberate TX-only scope decision at the time, not a hazard;
that scope has since widened.

`<PIN_P9_2__I2S3_SDI_A>` is now declared in its own `pinctrl_i2s3` group with
`input-enable` set, in all four in-tree `i2s3` board overlays -- the
E1M-AEN801 pair,
`examples/aen/aen-i2s-amp-alif/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay:70`
(`pinmux = <PIN_P9_2__I2S3_SDI_A>;`) and
`examples/aen/aen-evk-demo/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay:779`
(`pinmux = <PIN_P9_2__I2S3_SDI_A>;`), and the E1M-AEN803 pair, which carries
the identical U46 wiring and the identical stale TX-only comment,
`examples/aen/aen-i2s-amp-alif/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:70`
(`pinmux = <PIN_P9_2__I2S3_SDI_A>;`) and
`examples/aen/aen-evk-demo/boards/alp_e1m_aen803_m55_he_ae822fa0e5597ls0_rtss_he.overlay:779`
(`pinmux = <PIN_P9_2__I2S3_SDI_A>;`). `input-enable` is load-bearing, not
decoration: on this SoC a pad's input buffer is gated by a separate REN bit
that Zephyr's upstream `alif,pinctrl` binding's `input-enable` property
programs (`soc/alif/ensemble/pinctrl_soc.h` in the pinned Zephyr v4.4.1
module, outside this repo) — muxing the pin alone is necessary but not
sufficient to receive, since REN defaults off. An
earlier commit's claim that read-enable is "not in the upstream
`alif,pinctrl` binding" was true of the fork's own `read-enable = <0x1>`
property name, but the mainline binding's equivalent `input-enable` boolean
is already the established idiom elsewhere in this same repo (e.g. the PDM
data pin a few groups below in the `aen-evk-demo` overlay) and programs the
identical REN bit, so it is used here too rather than inventing anything new.

Both groups stay inert on their own: `i2s3` ships `status = "disabled"` by
default on EVK rev 2626-R2, so `pinctrl-0` is not applied until
`i2s3-enable-post-u46-rework.overlay` flips it `"okay"` — that switch-overlay
only sets `status`, and inherits `pinctrl_i2s3` from the board overlay
unchanged, so no separate edit was needed there. Neither example's app code
calls `i2s_configure()`/`i2s_read()` in the RX direction, so this change is
pinctrl-only groundwork; actually reading over I2S3 SDI still needs that
app-level RX wiring, which is out of scope here.

Bench caveat, not a reason to hold this change: U46 is a 3257-type switch
with `VCC` on `+3V3`, while `+VIO` measured 1.8 V on E1M-AEN803 serial 2026W36-0002, and a
3257 passes the amp's SDOUT level through rather than re-driving it, so the
logic level that actually lands on `P9_2` depends on the amp's IO rail and
has not been established — enabling REN here adds no contention regardless
(the SoC never drives `P9_2`, an input-only function, and U46's `4Y` drives
that net either way), but someone must check the level on hardware before
trusting a long RX run.
