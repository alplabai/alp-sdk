### Added — OSPI SecAES key provisioning over the Alif SE-service transport (#224)

Re-scoped issue #224: it was deferred years ago as "blocked on the vendor
HAL pack," but that premise was wrong. The E8 HWRM's `AES_CONTROL`
description makes `AES_CONTROL_LD_KEY` the bit the **Secure Enclave**, not
the host, arms once it has written the key -- the host never pokes raw key
bytes into an OSPI register, and no code in hal_alif's
`drivers/ospi/src/ospi.c` ever touches that bit. Alif publish the host-side
call for this instead: AUGD0014 "SE Host Services API" v1.109.0's
`SERVICES_application_ospi_write_key`, with `OSPI_WRITE_OTP_KEY_OSPI0/1`
and `OSPI_WRITE_EXTERNAL_KEY_OSPI0/1` command codes.

That symbol's body is not compiled anywhere in the pinned hal_alif v2.3.0
module (only the prototype ships; every low-level `SERVICES_*` entry point
is declared, never defined, there), so
`alp_alif_storage_secaes_key_provision()`
(`src/backends/ext/alif/storage.c`) instead builds the identical wire
packet (`ospi_write_key_svc_t`, `SERVICE_APPLICATION_OSPI_WRITE_KEY_ID`,
`OSPI_WRITE_EXTERNAL_KEY_OSPI0`) by hand and hands it to the *public*
generic transport hal_alif already exports for exactly this shape of
caller: `se_service_send_request()`, the same seam
`src/backends/security/se_cryptocell.c` rides for its CryptoCell
AES/SHA/AEAD packets, over the identical MHUv2 mailbox this SDK's
read-only SE-service path is bench-proven on
(`docs/aen-se-services.md`).

Gated behind a new `CONFIG_ALP_SDK_STORAGE_ALIF_SECAES`
(`depends on HAS_ALIF_SE_SERVICES`, **default `n`**) so
`src/backends/ext/alif/storage.c` -- which every board links
unconditionally -- keeps compiling, and the call keeps returning
`ALP_ERR_NOSUPPORT`, on any board with no hal_alif SE client linked.
Default OFF because the round-trip is unverified on silicon (below) --
about eight in-tree AEN examples already set `CONFIG_HAS_ALIF_SE_SERVICES=y`
and would otherwise get this real SE transaction on by default; unlike
`CONFIG_ALP_SDK_SECURITY_SE_CRYPTOCELL_SEND_SEAM` (default ON because that
path bench-PASSED), this one flips to ON in the same change that adds a
bench PASS row for it.

**Both wire-protocol verdict fields are checked.** `se_service_send_request()`
returns `rc==0` as soon as any response frame arrives over the mailbox --
neither it nor any `se_service_*` wrapper in hal_alif inspects
`header.hdr_error_code` or `resp_error_code` itself. `resp_error_code` is
pre-seeded to a non-success sentinel before the send (the packet's `memset`
otherwise leaves it bit-identical to `OSPI_WRITE_KEY_SUCCESS`), and
`header.hdr_error_code` is checked against `SERVICES_REQ_SUCCESS` for a
transport-layer NACK (e.g. `SERVICES_RESP_UNKNOWN_COMMAND` from an SE that
doesn't implement service 105 at all) -- so an SE that never actually loads
the key cannot report back as `ALP_OK`.

**The call brackets the SE round-trip against a concurrent close.**
`se_service_send_request()` can block for up to ~35 s (hal_alif's 15 s
`MUTEX_TIMEOUT` twice + 10 s `SERVICE_TIMEOUT`).
`alp_alif_storage_secaes_key_provision()` and `_get_status()` now enter via
`alp_handle_op_enter()` before touching the handle and leave via
`alp_handle_op_leave()` on every exit path (issue #629's open/op/close
guard) -- the same counter `alp_storage_close()` drains before it frees the
handle, so a close racing an in-flight call blocks until the call returns
instead of freeing/recycling the handle out from under it.

**Key width narrowed to 16 bytes (AES-128) only.** The header previously
documented `key_bytes` as 16/24/32 (AES-128/192/256); the vendor's
`ospi_write_key_svc_t.send_key` is a fixed `uint8_t[16]` and
`OSPI_KEY_LENGTH_BYTES == 16` -- the OSPI SecAES write-key service does not
offer a wider key. `alp_alif_storage_secaes_key_provision()` now rejects
any other `key_bytes` with `ALP_ERR_INVAL`.

**Key material never leaves the call.** `pkt.send_key` is an *inline* copy
of the key (unlike the CryptoCell AEAD packets, which only ever carry a
DMA address) -- it is the one place this call holds the key in clear. The
whole packet is zeroised with a compiler barrier immediately after
`se_service_send_request()` returns, on both the success and failure path,
and the key is never logged.

**`alp_alif_storage_secaes_get_status()` is unchanged: still
`ALP_ERR_NOSUPPORT`, unconditionally.** Alif has not published an SE
service that reads the OSPI SecAES engine's ARMED/ENGAGED/error state
back, and inventing a register-read sequence against the host-side
`ospi_aes_regs` block (the SE's own domain for the `LD_KEY` sequence)
would repeat the exact "guess the vendor timing" mistake this issue was
reopened to avoid.

**Bus scope: OSPI0 only, hardcoded.** The R2 BOM populates only OSPI0 (a
Macronix `MX25UM25645GXDI00`, `DNP=0`, per #915); no SoM in scope wires
OSPI1, so no bus selector was added to the (already-published) header
signature. Revisit if a future SoM populates OSPI1.

**UNVERIFIED ON SILICON.** No bench unit reachable at implementation time
has an OSPI SecAES-relevant part populated -- the bench module is board
rev **r1** (EEPROM manifest "E1M-AEN801 r1", serial `2617-0001`), not the
R2 BOM the Macronix part ships on. The SE-transport half of this call
reuses the identical `se_service_send_request()` path already bench-proven
for SE CryptoCell (`aen-se-crypto`: SHA-256 + AES-128-GCM MATCH); the OSPI
write-key round-trip itself has not been run against real SE firmware.
`docs/aen-se-services.md` §2.5 carries the full writeup, wire example, and
an added row in the §4 bench-execution policy table.

Docs: `include/alp/ext/alif/storage.h` doxygen updated (key width, return
codes, the ~35 s blocking note, `@par Supported silicon` narrowed to
`alif:ensemble:e8` -- e4/e6 are untried, not confirmed unsupported --
ABI-status note); `docs/aen-se-services.md` gains §2.5 (wire example, the
two-verdict-field check, the blocking/close-guard behaviour, the default-OFF
rationale); new rows in `docs/abi-markers.md` (`ext/alif/storage.h`) and
`docs/threat-model.md` (splits the previously-inaccurate single
`<alp/storage.h>` (inline-AES) row -- which claimed an OPTIGA path no
backend implements -- into the portable surface's real, still-unimplemented
status and this vendor-ext surface's actual SE-transport mechanism, and
calls out the false-`ALP_OK` risk class the two-verdict-field check closes);
`docs/test-plan.md`'s Inline-AES row updated to reflect the real
(bench-unverified) key-provision body and to say plainly that the ZTESTs
below do not reach it. `tests/unit/storage_registry` gains a regression
ZTEST covering the key/key_bytes validation and the NOSUPPORT fallback on a
build with no SE transport linked (that build has no
`HAS_ALIF_SE_SERVICES`, so `CONFIG_ALP_SDK_STORAGE_ALIF_SECAES` compiles out
there too -- this test cannot and does not exercise the real SE round-trip).
