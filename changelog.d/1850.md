### Fixed — `hw-revisions-v1.schema.json` closes its root; it was the last schema that accepted an undeclared top-level key (#1850)

`metadata/schemas/hw-revisions-v1.schema.json` carried `"additionalProperties": true` at
its root -- the only one of the 28 schemas under `metadata/schemas/` that did, with no
rationale recorded anywhere for the exception. Swept against the tree, nothing needs the
door: all four governed files (`metadata/e1m_modules/{aen,imx93,v2n,v2n-m1}/hw-revisions.yaml`)
carry exactly the three declared top-level keys `display_name`, `family` and `hw_revisions`,
and all three are already `required`, so no optional key could be hiding behind it either.
Closed to `false`.

This is narrower than it may sound, and the narrowing is worth recording because the issue
that opened it overstated the hole. A typo *inside* a revision entry was never accepted:
`$defs.hw_rev_entry` is `additionalProperties: false` over `board_rev`, `changes`,
`max_sdk_version`, `min_sdk_version`, `pad_route_overrides`, `released`, `status` and
`summary`, and `hw_revisions` constrains its own keys with
`propertyNames: {"pattern": "^r[0-9]+$"}`. Only a stray key at the top level was admitted.

Nothing downstream depended on the open root. `scripts/validate_metadata.py:82` loads this
schema and validates every `metadata/e1m_modules/*/hw-revisions.yaml` against it
(`:1466-1473`), and reports `4 hw-revisions file(s) ... 0 failure(s)` after the change. No
generator in this repo writes these files; tan reads them and touches only `hw_revisions`
(`tan-cli` `python/tan/commands/new_som_cmd.py:401-426`, `_family_hw_revisions`), and
creating a family file is a manual porting step. The customer-facing path in
`docs/porting-new-som.md` §7 appends a revision row *inside* `hw_revisions:`, which was
already strict.

Schema only; no metadata, code or generated-file change.
