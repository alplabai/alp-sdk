### Fixed — `bring-up-aen.md` called OSPI0-unpopulated a batch-wide fact; it's SKU-scoped and false for E1M-AEN803 (#1973)

`docs/bring-up-aen.md` carried a blockquote headed "This batch: the SoM's OSPI
memories are NOT populated," asserting as a present-tense property of "this
batch" that the OSPI0 NOR and HyperRAM are un-stuffed and that boot and app
storage run from on-die MRAM only. That was true of the **E1M-AEN801** SKU on
the earlier 2026-06-15 bench batch, but the maintainer confirmed on 2026-09-05
that the **E1M-AEN803** SKU now on the bench ("ospi memories are there — this
is a new Batch") fits both external memories, and the doc never said so. A
back-reference later in the same file, in the §5.1 OPTIGA note, repeated the
blanket framing ("like the un-stuffed OSPI memories") and its own header
("This bench batch (2026-06-15)") mixed a batch date into what is actually a
SKU-scoped fact.

Both are now scoped to the SKU rather than to an unqualified "this batch": on
E1M-AEN801 both `ospi_memories.ospi0.assembled` and `hyperram.assembled` are
`false` (`metadata/e1m_modules/E1M-AEN801.yaml`), so MRAM-only stands for that
SKU; on E1M-AEN803 both are `true` (`metadata/e1m_modules/E1M-AEN803.yaml`) —
the `IS25WX256-JHLE` NOR on CS1 and the `S80KS5122GABHM02` HyperRAM on CS0.
The OPTIGA note is corrected the other way: OPTIGA is `assembled: false` on
**both** SKUs (`metadata/e1m_modules/E1M-AEN801.yaml:123`,
`metadata/e1m_modules/E1M-AEN803.yaml:129`), so unlike OSPI0
that absence is not SKU-differentiated, and the paragraph no longer implies
otherwise by naming one bench date.

The chip-select question the original issue left open ("confirm before
documenting it") was previously stated backwards in this same doc (NOR on
CS0, HyperRAM on CS1) — a probe wired from that wording would have aimed a
NOR opcode at CS0 and could have misread a live NOR as dead. It is now
measured: on the **AEN803** bench module serial `2026W36-0002`, a JEDEC ID
read on OSPI0 CS1 drains `9d 5b 19 10` (ISSI, IS25WX256) at a 20 MHz test
rate (alp-sdk#2041), matching the R2 netlist (U10 -> OSPI0_SS1). `ser` is a
bitmask, not an index — `0x00000002` selects CS1. The same read at the
driver's 100 MHz DT-derived default comes back `4e ad 8c 88` with
`RISR=0x00000001` — a sampling error, not silence — so clock headroom above
20 MHz is still open; two points is not a sweep. The CS0 read in the same
session used a NOR opcode against what should be the HyperRAM and drained all
zero bytes; that is not a probe of the HyperRAM and this fragment claims
nothing about its behaviour.

The reason nothing can boot or XIP from either OSPI0 device yet is
`zephyr/drivers/flash/flash_ospi_alif.c` having no pinctrl support at all
(`grep -ci pinctrl` on that file returns `0`) — no consumer can apply OSPI0's
pad configuration. `examples/aen/aen-ospi-regcheck`'s overlay pinctrl is a
symptom of that driver gap, not the cause: its pads silently never take
effect regardless of which board's pad set it names. The doc's "target MRAM,
not OSPI" instruction for MCUboot/storage partitions is kept, re-scoped from
a population claim to this driver-readiness one, until the OSPI0 pinctrl work
tracked in alp-sdk#2041 lands.

Not touched, on purpose: `aen-ospi-regcheck`'s own PASS banner
(`examples/aen/aen-ospi-regcheck/src/main.c:284`) still prints "live XiP
HW-blocked (no part populated this batch)," and its file header
(`examples/aen/aen-ospi-regcheck/src/main.c:61-63`) still asserts "the bench
unit has NO OSPI memory fitted" — both now contradicted by the measurement
above. A parallel unit owns that file under alp-sdk#2041; this change only
flags the staleness from `docs/bring-up-aen.md`'s §0 rather than editing the
example directly.
`metadata/e1m_modules/E1M-AEN801.yaml`'s chip-select fields were already
corrected, in commit `eff266b6` (PR #1964), not in #2007 — #2007 never
touched `E1M-AEN801.yaml` and carries its own "netlist-inferred, never
probed on E3-E7" caveat that does not apply to AEN801's already-probed
values. #1969 (the HyperRAM capacity-metadata discrepancy) is CLOSED as of
2026-09-12; its residual `memory_map`/`mram_main.base` gap is tracked
separately as #2053. #1970's missing TF-A HyperRAM driver stays open. No A32
Linux boot has ever been demonstrated on any AEN module, on OSPI or
otherwise.
