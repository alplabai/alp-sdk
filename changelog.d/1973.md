### Fixed — `bring-up-aen.md` called OSPI0-unpopulated a batch-wide fact; it's SKU-scoped and false for E1M-AEN803 (#1973)

`docs/bring-up-aen.md` carried a blockquote headed "This batch: the SoM's OSPI
memories are NOT populated," asserting as a present-tense property of "this
batch" that the OSPI0 NOR and HyperRAM are un-stuffed and that boot and app
storage run from on-die MRAM only. That was true of the **E1M-AEN801** SKU on
the earlier 2026-06-15 bench batch, but the maintainer confirmed on 2026-09-05
that the **E1M-AEN803** SKU now on the bench ("ospi memories are there — this
is a new Batch") fits both external memories, and the doc never said so. A
back-reference later in the same file ("like the un-stuffed OSPI memories")
repeated the blanket framing.

Both are now scoped to the SKU rather than to an unqualified "this batch": on
E1M-AEN801 both `ospi_memories.ospi0.assembled` and `hyperram.assembled` are
`false` (`metadata/e1m_modules/E1M-AEN801.yaml`), so MRAM-only stands for that
SKU; on E1M-AEN803 both are `true` (`metadata/e1m_modules/E1M-AEN803.yaml`) —
the `IS25WX256-JHLE` NOR on CS1 and the `S80KS5122GABHM02` HyperRAM on CS0.

The chip-select question the original issue left open ("confirm before
documenting it") is now measured: on the bench module serial `2026W36-0002`,
a JEDEC ID read on OSPI0 CS1 drains `9d 5b 19 10` (ISSI, IS25WX256) at a
20 MHz test rate (alp-sdk#2041), matching the R2 netlist (U10 -> OSPI0_SS1).
The same read at the driver's 100 MHz DT-derived default comes back as a
sampling error rather than silence, so clock headroom above 20 MHz is still
open — two points is not a sweep. The CS0 read in the same session used a NOR
opcode against what should be the HyperRAM and drained all zero bytes; that
is not a probe of the HyperRAM and this fragment claims nothing about its
behaviour. `aen-ospi-regcheck` never applies OSPI0 pinctrl and issues no
device-level transfer (alp-sdk#2041), so nothing in this tree can boot or XIP
from either OSPI0 device yet — the doc's "target MRAM, not OSPI" instruction
for MCUboot/storage partitions is kept, re-scoped from a population claim to
a driver-readiness one, until that lands.

Not touched: `metadata/e1m_modules/E1M-AEN801.yaml`'s chip-select fields were
already corrected in an earlier change (#2007); #1969's HyperRAM
capacity-metadata discrepancy and #1970's missing TF-A HyperRAM driver stay
open; no A32 Linux boot has ever been demonstrated on any AEN module, on
OSPI or otherwise.
