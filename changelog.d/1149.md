### Fixed — `docs/os-support-matrix.md` claimed camera GA on V2N/V2N-M1 Cortex-A, wrong core (#1149)

The v0.2.0 Cortex-A (Yocto) table's Camera row read `**GA** (MIPI CSI-2)` for V2N and `**GA**` for
V2N-M1. Neither is true on the A55/Yocto side: the only camera backend `src/yocto/CMakeLists.txt`
links there is `src/backends/camera/zephyr_stub.c` (unconditional, `silicon_ref = "*"`, priority
0), which returns `ALP_ERR_NOT_IMPLEMENTED` for every op on every SoM — a `stub` per this doc's own
status key (`docs/os-support-matrix.md:9`), not `GA`.

The real MIPI CSI-2 ISP-aware camera backend, `src/backends/camera/v2n_n44_isp.c`, does exist and
is registered for `silicon_ref = "renesas:rzv2n:n44"` — but it is a **Zephyr** backend
(`#include <zephyr/drivers/video.h>`, `zephyr/CMakeLists.txt:812`, opt-in via
`CONFIG_ALP_SDK_CAMERA_V2N_N44_ISP`) for the V2N `m33_sm` core, not the A55/Yocto core the table
row claimed it for. Citing a Cortex-M backend to justify a Cortex-A cell is worse than saying
nothing, because it plans a product around a core that never links the code.

Both cells now read `stub`, with a footnote (`[^cam1]`) naming the real Yocto stub backend + its
link site and the real (but wrong-core) Zephyr ISP backend + its link site, so the distinction does
not get re-conflated later.

### Documented — V2N MIPI CSI-2 sensor path: recorded the data gate instead of guessing a sensor (#1149)

`src/backends/camera/v2n_n44_isp.c` is registered for `silicon_ref = "renesas:rzv2n:n44"` and its
capture path is real, but it resolves a device only through the `alp-camera0..3` devicetree
aliases — and no V2N board or overlay in this repo defines one, so the backend's `_devs[]` NULL
check fires and `alp_camera_open()` on V2N hands back `NULL` with `last_error` =
`ALP_ERR_NOT_READY`. No devicetree was written for it here,
because the values a CSI-2 node needs are not in this tree or its pinned dependencies. What landed
is the two comment blocks that say so precisely, so the next attempt starts from the gap rather
than re-deriving it.

That backend's header used to promise that once the SoC port wired MIPI CSI-2 up to
`drivers/video/`, "these calls go to real silicon for free", and closed with "no open tracking
issue exists yet for that follow-up" — both wrong. It now carries a DATA-GATED block, checked
against the pinned Zephyr v4.4.1 and the `hal_renesas` that pin imports, naming four separate
missing facts:

- **No receiver driver.** Zephyr v4.4.1's `drivers/video/` ships no Renesas RZ/V CSI-2 receiver at
  all — `video_renesas_ra_ceu.c` is the RA-family parallel CEU — and `dts/bindings/video/` carries
  CSI-2 receiver bindings only for NXP (`nxp,mipi-csi2rx.yaml`). ADR 0017's consume-upstream rung
  has nothing to consume yet.
- **No register base.** `dts/arm/renesas/rz/rzv/r9a09g056.dtsi` declares no `csi2`/`cru`/`isp`
  node, `hal_renesas`'s rzv2n `bsp_slave_address.h` carries no CRU entry, and
  `metadata/socs/renesas/rzv2n/n44.json`'s `peripheral_instances` block covers i2c/uart/gpt/gtm
  only — so the board generator has no base to emit either. The real value is in the RZ/V2N
  Hardware User's Manual `r01uh1003ej`, CRU + MIPI CSI-2 register chapters.
- **The CM33 interrupt cell is not a datasheet constant.** `hal_renesas`'s rzv2n `bsp_irq_id.h`
  lists `CRU0_CSI2_LINK_INT_IRQSELn = 494` and `CRU1_CSI2_LINK_INT_IRQSELn = 500` in
  `IRQSELn_Type` — IRQSEL *multiplexer selector* numbers. `IRQn_Type`, the enum that actually
  feeds a DT `interrupts` cell, holds no CRU vector at all; it ends at `SEL126_IRQn = 479`. So the
  cell is a free choice of one `SELn` vector plus an IRQSEL programming step no code in this tree
  performs. Contrast `zephyr/boards/alp/e1m_v2n101_m33_sm/alp_e1m_v2n101_m33_sm_r9a09g056n48gbg_cm33.dts`'s
  `mbox1`, whose `interrupts = <293 2>` came straight out of `IRQn_Type` as `MHU_MSG5_NS_IRQn`.
- **No sensor is chosen.** `metadata/boards/e1m-x-evk.yaml` sets `ov5640: false` and names no
  sensor; the E1M-X carrier exposes bare CSI connectors. Without a part there is no compatible, no
  CCI address, no lane count and no link frequency — and the OV5645 pair named in
  `meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-x-evk.dtsi`'s header belongs to the Renesas
  EVK, not to this carrier.

The carrier dtsi's one-line `- 2x MIPI-CSI cameras.` TODO grew the same DATA-GATED treatment the
TAS2563 audio entry beside it already had, for the Linux/A55 half. It now records what the carrier
*does* carry — the CAM0 control pads (`XEVK_PIN_CAM0_MUX_SEL` = `E1M_X_GPIO_IO16`,
`XEVK_PIN_CAM0_EN` = `E1M_X_GPIO_IO18`, `XEVK_PIN_CAM0_RST` = `E1M_X_GPIO_IO20`, active-low), the
control buses (`XEVK_I2C_BUS_DSI_CSI0` = `E1M_X_I2C2`, `XEVK_I2C_BUS_DSI_CSI1` = `E1M_X_I2C3`),
and the CRU + ISP DMA pools `meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-v2n-som.dtsi`
already reserves (`isp@90000000`, `cru_buffer@b4000000`) — against the four things it does not:
the sensor part; which of the E1M-X edge connector's four CSI instances
(`metadata/e1m/pinout-x-v1.json`, CSI0..CSI3) lands on which of the SoC's two receivers
(`"mipi_csi2": 2`) and on how many lanes, which `metadata/pinmux/v2n.yaml` cannot answer because it
carries no CSI lane row at all; which of the GD32-owned rails in
`metadata/e1m_modules/v2n/gd32-io-mcu-map.csv` (`CAM_EN_LDO0` = `PC3`, `CAM_EN_LDO1` = `PE8`,
`CAM_EN_LDO2` = `PE7`, `CAM_EN_LDO3` = `PE10`) powers which connector; and — for CAM1 specifically
— a Linux I2C master at all, since `E1M_X_I2C3` (`DSI1_CSI_I2C`) terminates on the GD32 IO-MCU
bridge, the same blocker that already defers GT911 touch.

No metadata, schema, Kconfig or CMake changed: the enablement scaffolding was already complete
(`CONFIG_ALP_SDK_CAMERA_V2N_N44_ISP`, `default y if ALP_SOC_RENESAS_RZV2N_N44`, is defined in
`zephyr/kconfigs/power-camera-display.kconfig` and links the backend from `zephyr/CMakeLists.txt`).
Only a sensor decision and the carrier routing are missing, and both are answers, not lookups.
