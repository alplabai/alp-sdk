### Fixed -- the CM33 GD32-bridge test rows expect the firmware's real status codes (#2727)

On GD32 fw 0.3.0 / protocol 0.15 five rows failed against correct firmware. `examples/v2n/v2n-gd32-bridge-hil-soak/src/main.c` `t_gpio` and `t_batch` (and `examples/v2n/v2n-gd32-bridge-functional/src/main.c` `t_batch`) read with an all-ones mask that names bit 8 = E1M IO24, which is unrouted (gd32-bridge-firmware#298, its `GPIO_PAD_UNROUTED_MASK`), so the bridge answered `STATUS_IO` and the batch stopped at op 2; they now use the new `GD32G553_GPIO_ROUTED_MASK`, and `gd32g553_gpio_read` / `gd32g553_gpio_write` return `ALP_ERR_NOSUPPORT` for a mask naming `GD32G553_GPIO_LINE_E1M_IO24`, as the Linux driver refuses line 8. `t_adc_stream_guard` now wants `ALP_ERR_BUSY` (the stream-owned converter), `t_pwm_capture` also accepts `ALP_ERR_NOT_READY` (empty ring), and `t_pwm_single_pulse` moved from PWM1 to PWM4 because PWM0..3 share TIMER0, which `pwm_set_get` never releases (`STATUS_BUSY`). `docs/gd32-bridge-protocol.md` documents all four codes.

Follow-up: `gd32g553_pwm_stop()` is new (`PWM_SET` with `period_ns == 0` and `duty_ns == 0` stops the channel and releases its timer claim; needs the firmware with stop/release, older firmware answers an error), and `gd32g553_pwm_set` now rejects `period_ns == 0` with `ALP_ERR_INVAL`. The GD32 is not reset between CM33 images, so the functional app's scope loop left PWM7 (TIMER7) claimed and the soak's `pwm_single_pulse` on PWM4 got `STATUS_BUSY`; the soak row now stops PWM4..PWM7 first, and the GD32-bridge PWM backend stops the channel on `alp_pwm_close`.
