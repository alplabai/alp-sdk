### Fixed — the 1.8V voltage switch polled the line levels with the internal clock stopped, discarded a clock-gate error, and dropped bus power for the whole switch (#2058)

`sdhc_dwc_set_voltage()` (`zephyr/drivers/sdhc/sdhc_dwc.c:186-299`) could not
complete a 1.8V signal-voltage switch even on hardware that reaches it. Three
separate defects sat in the same sequence; this entry fixes all three and
keeps them distinct, because they are not the same bug.

**Defect 1 (the reason the switch cannot complete) — the DAT-line poll ran
with the internal clock stopped.** The generic SD subsystem's
`sdmmc_switch_voltage()` (upstream Zephyr `subsys/sd/sd_ops.c`, not vendored
in this alp-sdk tree) first sets `card->bus_io.clock = 0` and calls
`sdhc_set_io()`, which lands in `sdhc_dwc_set_io()`'s `ios->clock == 0` branch
and calls `sdhc_dwc_disable_clock(regs)`
(`zephyr/drivers/sdhc/sdhc_dwc.c:949`) — clearing **both**
`DWC_SDHC_CLK_EN_Msk` and `DWC_SDHC_INTERNAL_CLK_EN_Msk` together
(`zephyr/drivers/sdhc/sdhc_dwc.c:159`). `sdmmc_switch_voltage()` then makes a
second `sdhc_set_io()` call to change `signal_voltage`, which clears the
already-clear `DWC_SDHC_CLK_EN_Msk` once more
(`zephyr/drivers/sdhc/sdhc_dwc.c:926`) and calls `sdhc_dwc_set_voltage()`.
Inside the 1.8V case, the poll's clock re-enable previously set only
`DWC_SDHC_CLK_EN_Msk` — the internal clock was still off from the earlier
call — and the poll ran immediately after. `sdhc_dwc_enable_clock()`, the
function that sets `DWC_SDHC_INTERNAL_CLK_EN_Msk` and waits for
`DWC_SDHC_INTERNAL_CLK_STABLE_Msk`, did not run until `sdhc_dwc_set_io()`
called it *after* `sdhc_dwc_set_voltage()` had already returned
(`zephyr/drivers/sdhc/sdhc_dwc.c:933`).

Per the SD Host Controller Simplified Specification's Clock Control register,
SD Clock Enable must not be set before Internal Clock Stable reads 1, and
SDCLK is derived from the internal clock. With the internal clock stopped
there is no SDCLK on the bus; per SD Physical Layer Specification 4.2.4.2 the
card drives CMD and DAT`[3:0]` low and only releases them high within 1ms of
SDCLK appearing at the new voltage. The poll therefore observed the lines
still low and timed out after `DWC_SDHC_1P8V_TIMEOUT_US` regardless of which
bits it tested — unconditionally, independent of the #2042 and #2057 fixes.

Fixed by calling `sdhc_dwc_enable_clock(regs)` — which enables the internal
clock, waits for it to report stable, and only then sets
`DWC_SDHC_CLK_EN_Msk` — in place of the bare `DWC_SDHC_CLK_EN_Msk |=` before
the poll, and propagating `-EIO` if the internal clock never reports stable.
The existing 1ms settle (`k_busy_wait(1000)`) and the `DWC_SDHC_1P8V_TIMEOUT_US`
poll loop are otherwise unchanged.

**Defect 2 — `sdhc_dwc_disable_clock()`'s return value was discarded in
`sdhc_dwc_set_io()`'s `ios->clock == 0` branch**
(`zephyr/drivers/sdhc/sdhc_dwc.c:949`; the other call site,
`zephyr/drivers/sdhc/sdhc_dwc.c:356` inside `sdhc_dwc_clock_set()`, already
checked it). `sdhc_dwc_disable_clock()` returns `false` when
`DWC_SDHC_CMD_INHIBIT_Msk` or `DWC_SDHC_DAT_INHIBIT_Msk` is set — exactly the
state the controller may report while a card holds DAT`[3:0]` low after
CMD11. The gate could then silently not happen while `data->ios.clock` was
still recorded as `0`, leaving the driver's idea of the clock state and the
hardware's diverging with no error anywhere. Fixed by checking the return
value and propagating `-EIO`, matching the existing `:356` call site.

**Defect 3 — bus power (Vdd1) was dropped for the whole switch.**
`sdhc_dwc_set_voltage()` clears `DWC_SDHC_PC_BUS_PWR_VDD1_Msk` unconditionally
on entry, before the `switch (voltage)`. The 1.8V case then wrote
`DWC_SDHC_PC_BUS_VSEL_1V8_Msk` (which does not include the Vdd1 bit) and did
not restore Vdd1 until *after* the `>= 5ms` `DWC_SDHC_1P8V_TIMEOUT_US` gate —
so Vdd1 was off for the whole gate. The SD Host Controller Simplified
Specification's voltage-switch procedure (3.6.1) never has the host remove
Vdd here; only the signalling level changes. If `sd_vdd1_on` gates a load
switch on a given carrier, the previous sequence would have power-cycled the
card mid-CMD11, and any subsequent "success" would be a freshly reset card at
idle rather than a switched one — whether that is the case on any Alp carrier
is not established by this change. Fixed by folding the Vdd1 restore into the
same write that sets the 1.8V VSEL bits, before the gate starts, so Vdd1
stays continuously applied through the switch.

**Not fixed here, and not claimed fixed.** The specification's 3.6.1 also has
the host re-read the 1.8V Signaling Enable bit in `HOST_CTRL2` after the
`>=5ms` gate (abort if the controller cleared it — regulator failure) and,
on any switch failure, fully power-cycle the SD bus before re-initialising at
3.3V. This driver does neither; it returns `-ETIMEDOUT`/`-EIO` and leaves
recovery to the generic layer (upstream Zephyr `subsys/sd/sdmmc.c`, not
vendored in this alp-sdk tree, sets `vol_180_support = false` and returns
`SD_RESTART` — a graceful outcome but not the specification's own one). Left
as TBD — out of scope for this fix, not evaluated here.

**Unreachable on current hardware, for two independent reasons.** SD
enumeration has never completed on E1M-AEN801, the only in-tree consumer of
`snps,dwc-sdhc` — the currently-tracked root cause is #2051 (`SW_RST_CMD`
never self-clears; `SW_RST_R` at register `0x4810202F` stays `0x02`, so
`disk_access_init()` returns `-116`), so `sdmmc_switch_voltage()` is never
reached at all today. Independently, both consuming overlays
(`examples/aen/aen-evk-demo/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay`
and
`examples/aen/aen-sdcard-readout/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay`)
set `no-1-8-v;`, which the driver honours
(`zephyr/drivers/sdhc/sdhc_dwc.c:1032`,
`props->host_caps.vol_180_support = config->no_1_8_v ? 0 : ...`), so the
generic SD subsystem never calls `sdmmc_switch_voltage()` for either example
even once enumeration completes — the 74LVC157 SDIO mux on the E1M-AEN801 EVK
cannot pass a 1.8V logic level. This fix is correct by construction against
the cited specification text, not verified against silicon: no `PSTATE` or
`CLK_CTRL_R` value has ever been captured from AE822 hardware, and this
change was not run on a bench.

Refs #2042, #2057, #2051.
