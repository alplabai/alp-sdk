### Fixed — `ram-run.sh` read the RAM console with an in-session `halt` after `go`, which measured an incoherent core and a failed read on real hardware (#2076)

`scripts/bench/aen/ram-run.sh` loaded, ran and read back Flow C's RAM console
in **one** JLinkExe session: `loadbin`/`setpc`/`go`/`Sleep`, then a second
in-session `halt`, then `mem8`. Measured 2026-09-13 on `e1m-aen-evk-02` and
`e1m-aen-evk-03` against an app whose `main()` was still running, that
second `halt` returned an incoherent core (`SP=0x00000030`,
`FAULTMASK=378E`, the FPS registers mirroring `R0`-`R14`, no `MSPLIM` block
at all) and the `mem8` that followed it failed outright ("Could not read
memory"). A separate, read-only attach to the same board seconds later read
both the core and the buffer cleanly (`IPSR=0`, `CFSR=0`, `BFAR=0`). The
failure was silent by the script's own contract: `bench_jlink_assert_connected`
(`scripts/bench/aen/bench-env.sh:329-401`) only proves the probe opened, and a
`halt` that succeeds syntactically but returns garbage passed it, decoding to
an empty console block indistinguishable from a crashed app.

No root cause is established (Secure Enclave gating a running core, J-Link
script sequencing, or something else) -- this only avoids the session shape
measured broken.

Fixed by splitting the load+run step from the read step into two separate
JLinkExe sessions (`scripts/bench/aen/ram-run.sh:188-250`): session 1
`loadbin`s, `setpc`s and `go`es, then ends on a plain `exit` (no halt, no
reset) that leaves the target running -- the same ending this bench already
ships and bench-verifies for a live app in `flash-jlink.sh` (`RSetType 2` /
`r` / `g` / `exit`, then a separate session reads a live console 3 seconds
later, `scripts/bench/aen/flash-jlink.sh:128-131,167-187`; corroborated by
`docs/aen-bench-bringup.md:439-440`, "read a witness back over the generic
device" / "memory reads work while the CPU runs; register reads error out
harmlessly"). The host then sleeps the same `sleep_ms` between sessions.
Session 2 is a fresh `connect` + `mem8`, with no `halt` first -- the same
no-halt read this bench's own Flow D read-back already uses on a live core
(`scripts/bench/aen/flash-jlink.sh:175-183`). Both sessions are gated by
`bench_jlink_assert_connected`, so a session-2 connect failure now fails the
script with its infrastructure exit code (7) instead of decoding as an empty
console block. The decoder and its output format are unchanged.

`scripts/bench/aen/README.md`'s `ram-run.sh` row is updated to describe the
two-session shape. `scripts/bench/aen/openocd-ram-run.sh` does not load+read
in one session (it only loads+resumes, no console read) and needed no
change.

Not bench-verified by this change -- no board was available (see the issue).
Silicon verification is scheduled separately.

Refs #2076.
