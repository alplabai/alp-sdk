### Fixed — `ram-run.sh` read the RAM console with an in-session `halt` after `go`, and could decode a failed load, a failed read, or the WRONG board's console as a silent success (#2076)

`scripts/bench/aen/ram-run.sh` loaded, ran and read back Flow C's RAM console
in **one** JLinkExe session: `loadbin`/`setpc`/`go`/`Sleep`, then a second
in-session `halt`, then `mem8`. Measured 2026-09-13 on `e1m-aen-evk-02` and
`e1m-aen-evk-03` against an app whose `main()` was still running, that
second `halt` returned an incoherent core (`SP=0x00000030`,
`FAULTMASK=378E`, the FPS registers mirroring `R0`-`R14`, no `MSPLIM` block
at all) and the `mem8` that followed it failed outright ("Could not read
memory"). A separate, read-only attach to the same board seconds later read
both the core and the buffer cleanly (`IPSR=0`, `CFSR=0`, `BFAR=0`). The
failure was silent by the script's own contract: `bench_jlink_assert_connected`
(`scripts/bench/aen/bench-env.sh:329-401`) only proves the probe opened, and a
`halt` that succeeds syntactically but returns garbage passed it, decoding to
an empty console block indistinguishable from a crashed app.

No root cause is established (Secure Enclave gating a running core, J-Link
script sequencing, or something else) -- this only avoids the session shape
measured broken.

Fixed by splitting the load+run step from the read step into two separate
JLinkExe sessions (`scripts/bench/aen/ram-run.sh:286-376`): session 1
`loadbin`s, `setpc`s and `go`es, then ends on a plain `exit` (no halt, no
reset) that leaves the target running. Session 2 is a fresh `connect` +
`mem8`, with no `halt` first. The decoder and its output format are
unchanged.

**Bench-verified 2026-09-13** (`examples/peripheral-io/blink`, whose
`main()` never returns; 6 of 6 clean runs across `e1m-aen-evk-02` and
`e1m-aen-evk-03`) that a plain `exit` after `go` leaves the target running:
every load transcript ended `loadbin ... O.K.`, `setpc`, `go`, `exit`; a
separate attach immediately after found the core still running (`CPU is not
halted.` after `go`) and the kernel's `curr_tick`
(`CONFIG_SYS_CLOCK_TICKS_PER_SEC=10000`) advancing about 1s across a `Sleep
1000`. This is a direct measurement of `exit` after `go` on a core J-Link
itself halted moments before -- a narrower and better-grounded claim than
this fix's first draft made by citing `flash-jlink.sh`'s `RSetType 2`/`r`/
`g`/`exit` (`scripts/bench/aen/flash-jlink.sh:128-131`) as precedent: there
the pin reset reboots the Secure Enclave and J-Link's own attach fails
afterwards (`docs/aen-bench-bringup.md:437-439`, "Attach to CPU failed"), so
`g`/`exit` act on a core J-Link no longer controls -- that shows closing
J-Link does not stop an SE-booted core, not that `exit` after resuming a
core J-Link itself halted leaves it running. Whether `qc` behaves the same
as `exit` remains unestablished and is not claimed. No `Could not read
memory` appeared in any of the 6 runs, and every halted-state register dump
taken (including the pre-`loadbin` halt against a live app) was coherent.

**Review round 2** found three further defects before any of this shipped:
a failed session-2 read (`mem8` itself reporting `Could not read memory.`,
or producing no dump line at all) could still decode as an empty console; a
failed session-1 `loadbin` went unnoticed (DTCM survives the reset it
triggers, so a stale image from an earlier run could boot and be read back
as this run's output); and every JLinkExe call needed routing through the
board-farm's `jlink-run.sh` per-probe isolation wrapper instead of a bare
`-SelectEmuBySN` -- several probes on this bench share one OEM serial, and
with load and read now in separate sessions an unselected probe could load
one board and read a *different* board's console.

**Review round 3, run against real hardware, found the round-2 fixes
themselves broken or incomplete:**

- **The `loadbin ... O.K.` check was wrong in both directions**
  (`scripts/bench/aen/ram-run.sh:362-376`). Too narrow: on silicon (6 of 6
  runs, both boards) every load exited 8 although every load worked --
  JLinkExe V9.74 through `jlink-run.sh` puts SIX lines (the implicit-reset
  banner, `Downloading file [...]...`) between the echoed `loadbin` command
  and `O.K.`, not "immediately after" as the round-2 comment claimed, and a
  fixed `grep -A3` window missed it. Too loose: a case-insensitive
  whole-window scan matches the OPERATOR'S OWN build-dir path (a directory
  named e.g. `demo.k.build` contains the substring `O.K.` and made a
  genuinely failed load report success), or a different, unrelated
  `loadbin` entirely (a preload file's own). Fixed with a window anchored
  on the EXACT echoed command for THIS image, scoped to the lines up to the
  next `J-Link>` prompt, requiring one of them to be the line `O.K.`
  verbatim (case-sensitive, not a substring).
- **Wrapper errors were swallowed, and the transcripts review cited were
  already deleted** (`scripts/bench/aen/ram-run.sh:333`, `:404`). Sessions
  1 and 2 sent the wrapper's stderr to a separate `.err` file nothing
  printed, so `jlink-run.sh`'s own refusal messages (place not held, board
  unpowered, a USB-mask failure, a failed labgrid `show`) never reached the
  operator -- only `bench_jlink_assert_connected`'s generic "produced no
  J-Link output at all". The unconditional `trap ... EXIT` also deleted
  `$WORKDIR` before an operator could read the "Transcript: ..." path
  either message named. Fixed: stderr is merged into the same transcript as
  the preflight already did (`2>&1`), and `$WORKDIR`
  (`scripts/bench/aen/ram-run.sh:149-177`) is now removed only on a
  successful exit -- a failing run leaves it in place and says so.
- **Five documented invocations exited 2** the moment `BENCH_PLACE` became
  required: `scripts/bench/aen/README.md`'s Quick start,
  `examples/aen/aen-eeprom-provision/README.md` (both call sites),
  `examples/aen/aen-tz-secure-log-append/README.md`, and
  `examples/aen/aen-tz-secure-log-probe/README.md`. Each now exports
  `BENCH_PLACE`/`AEN_JLINK_RUN` next to its `ram-run.sh` call.

Also from round 3: the stale "`export JLINK_SN=<serial>`" hint
`bench_jlink_assert_connected` prints on a connect failure (bench-env.sh,
off limits -- PR #2080/#2033 both touch it) is now followed by a
ram-run-specific correction pointing at `BENCH_PLACE`
(`scripts/bench/aen/ram-run.sh:133-147`); the paragraph explaining why the
six sibling scripts that still select by `JLINK_SN` do so conditionally
(deleted from `ram-run.sh` in round 2, but those six still point here for
it) is restored, reworded to say `ram-run.sh` itself no longer works that
way (`scripts/bench/aen/ram-run.sh:100-113`); `AEN_JLINK_RUN` lost its
`$HOME/board-farm/...` default (`scripts/bench/aen/ram-run.sh:79-98`) --
on a real bench host that default WAS the real wrapper, so a forgotten
override would have silently driven a real probe instead of failing
closed; the missing-`BENCH_PLACE` message no longer states a specific probe
count (measured three enumerated on the bench the day of the six-probe
comment; the number drifts); the `mktemp -d` for `$WORKDIR` now honours
`$TMPDIR` (matching `openocd-ram-run.sh`'s own preflight-transcript
`mktemp`) instead of a hardcoded `/tmp`; and the test suite
(`tests/scripts/test_bench_ram_run_two_session.py`) is driven through a
fake wrapper whose default `loadbin` reply is the VERBATIM real six-line
transcript block (not a simplified one), plus dedicated adversarial cases
for both `O.K.`-check directions and the preload-loadbin case, gains a
Linux-only skip (BSD `date` has no `%N`, and macOS's awk lacks
`strtonum()`, which this script's own LOAD-segment parsing depends on --
`python-smoke (macos-latest)` runs `tests/scripts/**`), and pins exact exit
codes instead of a loose `not in (0, 7)`.

`scripts/bench/aen/README.md`'s `ram-run.sh` row documents the full exit
code table (1/2/3/4/5/6/7/8/9), the `arm-zephyr-eabi-nm`/`-readelf` PATH
requirement, and that the app now runs **at least** `sleep_ms`, not exactly
it (the wrapper's own labgrid reservation check and OpenOCD probe-firmware
read add their own overhead per call, measured stretching a 1.5s gap to
about 3.1s on the bench) -- and that the core is left **running** on exit
where the old single-session shape left it halted.

`scripts/bench/aen/openocd-ram-run.sh` does not load+read in one session (it
only loads+resumes, no console read) and needed no change.

**Follow-ups outside this repo, not fixed here:** the `alp-lab` plugin
skill `flashing-and-bench-debugging-aen` and `alp-sdk-internal`'s
`som-batch-provisioning-procedure.md` still describe the old one-session
`ram-run.sh` shape; the board-farm's `jlink-run.sh` itself leaks one
`mktemp -d` (the update-suppression prelude file) per call.

Not bench-verified for the round-2/round-3 follow-on fixes (session-2 read
failure, session-1 loadbin failure, wrapper routing, the corrected `O.K.`
check) -- only the base two-session `exit`-leaves-running behaviour and the
original (now-fixed) `O.K.` check's failure mode were run on silicon; the
rest is covered by `tests/scripts/test_bench_ram_run_two_session.py`
against a fake wrapper only. A further silicon run is scheduled to exercise
