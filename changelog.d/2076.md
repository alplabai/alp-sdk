### Fixed — `ram-run.sh` read the RAM console with an in-session `halt` after `go`, and could decode a failed load or a failed read as a silent, empty console (#2076)

`scripts/bench/aen/ram-run.sh` loaded, ran and read back Flow C's RAM console
in **one** JLinkExe session: `loadbin`/`setpc`/`go`/`Sleep`, then a second
in-session `halt`, then `mem8`. Measured 2026-09-13 on `e1m-aen-evk-02` and
`e1m-aen-evk-03` against an app whose `main()` was still running, that
second `halt` returned an incoherent core (`SP=0x00000030`,
`FAULTMASK=378E`, the FPS registers mirroring `R0`-`R14`, no `MSPLIM` block
at all) and the `mem8` that followed it failed outright ("Could not read
memory"). A separate, read-only attach to the same board seconds later read
both the core and the buffer cleanly (`IPSR=0`, `CFSR=0`, `BFAR=0`). The
failure was silent by the script's own contract: `bench_jlink_assert_connected`
(`scripts/bench/aen/bench-env.sh:329-401`) only proves the probe opened, and a
`halt` that succeeds syntactically but returns garbage passed it, decoding to
an empty console block indistinguishable from a crashed app.

No root cause is established (Secure Enclave gating a running core, J-Link
script sequencing, or something else) -- this only avoids the session shape
measured broken.

Fixed by splitting the load+run step from the read step into two separate
JLinkExe sessions (`scripts/bench/aen/ram-run.sh:260-320`): session 1
`loadbin`s, `setpc`s and `go`es, then ends on a plain `exit` (no halt, no
reset) that leaves the target running. Session 2 is a fresh `connect` +
`mem8`, with no `halt` first. The decoder and its output format are
unchanged.

**Bench-verified 2026-09-13** (`examples/peripheral-io/blink`, whose
`main()` never returns; 6 of 6 clean runs across `e1m-aen-evk-02` and
`e1m-aen-evk-03`) that a plain `exit` after `go` leaves the target running:
every load transcript ended `loadbin ... O.K.`, `setpc`, `go`, `exit`; a
separate attach immediately after found the core still running (`CPU is not
halted.` after `go`) and the kernel's `curr_tick`
(`CONFIG_SYS_CLOCK_TICKS_PER_SEC=10000`) advancing about 1s across a `Sleep
1000`. This is a direct measurement of `exit` after `go` on a core J-Link
itself halted moments before -- a narrower and better-grounded claim than
this fix's first draft made by citing `flash-jlink.sh`'s `RSetType 2`/`r`/
`g`/`exit` (`scripts/bench/aen/flash-jlink.sh:128-131`) as precedent: there
the pin reset reboots the Secure Enclave and J-Link's own attach fails
afterwards (`docs/aen-bench-bringup.md:437-439`, "Attach to CPU failed"), so
`g`/`exit` act on a core J-Link no longer controls -- that shows closing
J-Link does not stop an SE-booted core, not that `exit` after resuming a
core J-Link itself halted leaves it running. Whether `qc` behaves the same
as `exit` remains unestablished and is not claimed. No `Could not read
memory` appeared in any of the 6 runs, and every halted-state register dump
taken (including the pre-`loadbin` halt against a live app) was coherent.

Three further defects, found in review before any of this shipped:

- **A failed session-2 read could still decode as an empty console.**
  `bench_jlink_assert_connected` only proves the probe opened; a connected
  `mem8` that itself reports `Could not read memory.`, or that produces no
  `ADDR = HH HH ...` dump line at all, passed it and decoded as a silent,
  empty console -- exactly the failure mode this fix exists to close, and
  with no root cause established a no-halt read can still fail this way.
  `scripts/bench/aen/ram-run.sh:326-340` now checks the read's own outcome
  before decoding and exits 9 on either failure shape.
- **A failed session-1 `loadbin` went unnoticed.** DTCM survives the reset
  `loadbin` triggers, so a stale image from an earlier run could boot and
  have its console read back as if the new image had loaded.
  `scripts/bench/aen/ram-run.sh:275-293` now requires the `loadbin` line's
  transcript to read `O.K.` (bench-confirmed the success marker above) and
  exits 8 otherwise.
- **Every JLinkExe call now routes through the board-farm's `jlink-run.sh`
  per-probe isolation wrapper** (`scripts/bench/aen/ram-run.sh:54-107`),
  not a bare `-SelectEmuBySN`. Five probes on this bench share OEM serial
  `000603000869`; with load and read now in separate sessions, an
  unselected probe could load one board and read a *different* board's
  `ram_console_buf`, printing it as this run's output -- materially worse
  than the single-session `dev` shape. `ram-run.sh` now requires
  `BENCH_PLACE` (the labgrid-client place name; refused before any probe access if
  unset) and `AEN_JLINK_RUN` (the wrapper path, defaulting under `$HOME`,
  never hardcoded). The wrapper recognizes `-CommandFile`, not
  `-CommanderScript` (every other bench script's flag) -- confirmed against
  the real JLinkExe binary that both name the same option -- so all three
  sessions (preflight, load, read) now pass `-CommandFile`.
  `scripts/bench/aen/bench-env.sh` is **not** touched by this change (PR
  #2080 and draft #2033 both touch it).

Also fixed: `sleep_ms` is now validated as a plain non-negative decimal
integer before any probe access (`0x10`/`abc` previously became `0.000s`
silently, and a negative value only surfaced from `sleep`'s own error after
session 1 had already loaded+gone); every transcript and generated
CommandFile now lives under one `mktemp -d` `$WORKDIR` with `trap ... EXIT`
cleanup (`scripts/bench/aen/ram-run.sh:109-120`), replacing the fixed
`/tmp/jlink.out`-style names a concurrent run on the same host could
overwrite moments before decoding -- reproduced running this file's own test
suite against a live bench session. Routing every session through
`jlink-run.sh` also means the app now runs for **at least** `sleep_ms`, not
exactly `sleep_ms` (the wrapper's own labgrid reservation check and OpenOCD
probe-firmware read add their own overhead per call, measured stretching a
1.5s gap to about 3.1s on the bench), and the core is left **running** on
exit where the old single-session shape left it halted --
`scripts/bench/aen/README.md`'s `ram-run.sh` row now says so.

`scripts/bench/aen/openocd-ram-run.sh` does not load+read in one session (it
only loads+resumes, no console read) and needed no change.

Not bench-verified for the review's three follow-on fixes (session-2 read
failure, session-1 loadbin failure, wrapper routing) -- only the base
two-session `exit`-leaves-running behaviour was run on silicon; the rest is
covered by `tests/scripts/test_bench_ram_run_two_session.py` against a fake
wrapper only.

Refs #2076.
