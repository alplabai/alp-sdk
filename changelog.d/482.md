### Fixed — DEEPX DX-M1 Yocto runtime path consumes DEEPX's official `meta-deepx-m1` layer instead of an unbuildable placeholder (#482)

`meta-alp-sdk/recipes-deepx/dx-rt/dx-rt_2.4.bb` was an intentionally
`SKIP_RECIPE`, unbuildable placeholder written back when `dx_rt` was
assumed to be a private, customer-mirrored-only source tree. DEEPX now
publishes `dx_rt`, `dx_rt_npu_linux_driver`, and a Yocto layer packaging
both (`meta-deepx-m1`) on `github.com/DEEPX-AI`. The placeholder recipe
and its now-empty `recipes-deepx/` directory are deleted.

The V2M (DEEPX DX-M1) MACHINEs -- `e1m-v2m101-a55` / `e1m-v2m102-a55` /
`e1m-v2m103-a55` -- now `require` a new shared
`conf/machine/include/e1m-v2m-deepx.inc`, replacing each conf's
duplicated DEEPX block. The include appends `dx-driver dx-rt dx-rt-cli`
to `IMAGE_INSTALL` and `dx_dma dxrt_driver` to `KERNEL_MODULE_AUTOLOAD`
(DEEPX's `dx-driver` builds those kernel modules but does not autoload
them) when `ALP_ENABLE_DEEPX_DXM1 = "1"`, and pins
`PREFERRED_VERSION_dx-driver = "1.8.0"` /
`PREFERRED_VERSION_dx-rt = "3.2.0"` to match the DX-M1 firmware 2.4.0
these SKUs ship with (per DEEPX's own DX-RT release-note coupling
table; the pin bumps only together with a firmware bump).
`meta-alp-sdk/conf/layer.conf`'s `LAYERRECOMMENDS` now names the real
upstream collection, `meta-deepx-m1` (was the wrong name, `meta-deepx`),
and its BBMASK guidance for non-DEEPX builds no longer references the
deleted `recipes-deepx/` path -- a non-DEEPX build now simply leaves
`meta-deepx-m1` out of `bblayers.conf`.

`meta-alp-sdk/recipes-core/alp-sdk/alp-sdk_0.6.bb` gained a real
`PACKAGECONFIG[deepx-dxm1]` (`-DALP_SDK_USE_DEEPX_DXM1=ON
-DALP_SDK_DEEPX_REQUIRED=ON`, depending on `dx-rt`), auto-enabled only
when the MACHINE carries `deepx-dxm1` in `MACHINE_FEATURES` (the V2M
confs) AND `ALP_ENABLE_DEEPX_DXM1 == "1"` -- so the license-gated
runtime is never pulled into a build that has not opted in.

Docs brought in sync: `meta-alp-sdk/README.md` (layout tree, clone
step now pins the verified `meta-deepx-m1` commit, per-machine runtime
table, licence paragraph clarifying this layer ships no DEEPX code),
`vendors/deepx-dxm1/README.md`'s Yocto-integration section,
`docs/vendor-partnerships.md`'s DEEPX section (records the 2026-09-25
decision), and `docs/bring-up-v2n-m1.md` (the on-module DEEPX-built
firmware must be provisioned separately; verify with `dxrt-cli -s`
against the pinned stack before trusting an inference result). Stale
comments referencing the deleted recipe/path in
`scripts/check_library_pin_parity.py`,
`meta-alp-sdk/recipes-renesas/mera2-drpai-tvm/mera2-drpai-tvm_2.7.0.bb`,
and `meta-alp-sdk/recipes-images/alp-image-common.inc` are corrected.

Not addressed here: a real `bitbake alp-image-edge` bake with
`ALP_ENABLE_DEEPX_DXM1 = "1"` and `meta-deepx-m1` in `bblayers.conf`
(no Yocto build environment in this working environment); V2M HIL
validation of PCIe enumeration, `dxrt_init()`, and a real `.dxnn`
inference remains open, per #482's own acceptance criteria.
