### Fixed — aen-evk-demo no longer drives CC3501E GPIO_30 as I2S_EN on r1 modules (#2138)

`examples/aen/aen-evk-demo/src/cc3501e_gpio_routes.c` (`examples/aen/aen-evk-demo/src/cc3501e_gpio_routes.c:61`
("{ ALP_E1M_GPIO_IO8, 30u },")) is a hand-written, standalone route table --
this app has no `board.yaml`, so it never reaches
`scripts/gen_cc3501e_gpio_routes.py`'s per-revision generation the way
`aen-cc3501e-bringup`/`aen-cc3501e-gpio`/`aen-cc3501e-companion-tour` do. Its
`IO8 -> CC3501E GPIO_30` entry is correct only on **r2**
(`metadata/e1m_modules/E1M-AEN801.yaml`'s base `pad_routes`). On **r1**,
`metadata/e1m_modules/aen/hw-revisions.yaml:44`
("`{ e1m: E1M_GPIO_IO8,  dispatch: direct, doc: \"r1: Alif GPIO (r2 -> CC3501E GPIO_30).\" }`")
moves IO8 to a direct Alif GPIO and re-routes IO21 -- not IO8 -- onto
CC3501E GPIO_30 instead. On an E1M-EVK 2626-R2 carrier, that GPIO_30 net (the
SDIO mux SELECT) reaches `NetP18_2` through R198 and a fitted P18 jumper ties
it to +3V3, so phase 11's `AEN_EVKDEMO_SOUND_PLAYBACK=1` path -- which drives
"I2S_EN" LOW through GPIO_30 -- would short a CC3501E output against +3V3 on
an r1 module with P18 fitted. The default `AEN_EVKDEMO_SOUND_PLAYBACK 0` kept
default builds from hitting this.

The route table is not deleted or regenerated: this app is intentionally a
standalone Zephyr app with no `board.yaml` for the generator to resolve
against (see the table's own file header), and its IO8 entry is still the
correct one for the r2 hardware most of this phase's bring-up ran on. Instead,
phase 11 now refuses to drive the pin at all unless it can positively confirm
the live module's hw_rev over a fresh EEPROM read
(`examples/aen/aen-evk-demo/src/main.c:4161`
("/* --- 0. Refuse unless the live module is CONFIRMED hw_rev 2626-r2 -- */"))
-- the same 128-byte manifest phase 5 decodes, read again here rather than
cached, so this guard holds regardless of whether phase 5 ran or passed. A
read failure, a bad magic, or any `hw_rev` string other than exactly
`"2626-r2"` all FAIL the phase before `ALP_E1M_GPIO_IO8` is ever opened
(`examples/aen/aen-evk-demo/src/main.c:4203`
("refused: hw_rev != 2626-r2 (#2138)")) -- not just a
recognised r1, so an unprovisioned module or a future r3+ board fails safe
here too.

The table's own "REVISION SCOPE" comment
(`examples/aen/aen-evk-demo/src/cc3501e_gpio_routes.c:39`
("* IO8 AND IO13 -- the I2S mux ENABLE and SELECT phase 11 drives -- are BOTH"))
is corrected to say IO8 is revision-scoped (and now guarded at runtime)
instead of claiming, as before, that the table "needs no per-revision
variant" and that the pinout's own `EVK_PIN_I2S_MUX_EN` / `Alif P7.1` prose
was simply stale -- that prose was right for r1, wrong for r2.

Every other `examples/**/cc3501e_gpio_routes.c` was audited for the same
hazard. `aen-sdcard-readout`'s hand-written table only routes IO20 (the SD
mux ENABLE), which `hw-revisions.yaml` does **not** move on any AEN
revision, so it carries no r1 hazard and is unchanged.
`aen-cc3501e-bringup`/`aen-cc3501e-gpio`/`aen-cc3501e-companion-tour` are all
generated per their own `board.yaml`'s resolved `hw_rev` by
`scripts/gen_cc3501e_gpio_routes.py`, which already composes
`pad_route_overrides` correctly -- no hazard, no change.

`tests/scripts/test_aen_cc3501e_routes.py:268`
("def test_standalone_app_route_table_guards_revision_dependent_pads(path):")
adds a regression check: it reads every `e1m` pad
`hw-revisions.yaml`'s `pad_route_overrides` ever moves, and for any
standalone hand-written table that routes one of those pads, asserts the
app's `main.c` opens it only after a `hw_rev_confirmed_r2`
(`tests/scripts/test_aen_cc3501e_routes.py:264`
("REVISION_GUARD_MARKER =")) runtime guard. Reverting
just the `main.c` guard (route table and test left in place) reproduces the
red failure this fix closes; with the guard back, the suite is green.
