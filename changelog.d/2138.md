### Fixed — aen-evk-demo no longer drives CC3501E GPIO_30 as I2S_EN on r1 modules (#2138)

`examples/aen/aen-evk-demo/src/cc3501e_gpio_routes.c` (`examples/aen/aen-evk-demo/src/cc3501e_gpio_routes.c:61`
("{ ALP_E1M_GPIO_IO8, 30u },")) is a hand-written, standalone route table --
this app has no `board.yaml`, so it never reaches
`scripts/gen_cc3501e_gpio_routes.py`'s per-revision generation the way
`aen-cc3501e-bringup`/`aen-cc3501e-gpio`/`aen-cc3501e-companion-tour` do. Its
`IO8 -> CC3501E GPIO_30` entry is correct only on **r2**
(`metadata/e1m_modules/E1M-AEN801.yaml`'s base `pad_routes`). On **r1**,
`metadata/e1m_modules/aen/hw-revisions.yaml:44`
("`{ e1m: E1M_GPIO_IO8,  dispatch: direct, doc: \"r1: Alif GPIO (r2 -> CC3501E GPIO_30).\" }`")
moves IO8 to a direct Alif GPIO and re-routes IO21 -- not IO8 -- onto
CC3501E GPIO_30 instead. On an E1M-EVK 2626-R2 carrier, that GPIO_30 net (the
SDIO mux SELECT) reaches `NetP18_2` through R198 and a fitted P18 jumper ties
it to +3V3, so phase 11's `AEN_EVKDEMO_SOUND_PLAYBACK=1` path -- which drives
"I2S_EN" LOW through GPIO_30 -- would short a CC3501E output against +3V3 on
an r1 module with P18 fitted. The default `AEN_EVKDEMO_SOUND_PLAYBACK 0` kept
default builds from hitting this.

The route table is not deleted or regenerated: this app is intentionally a
standalone Zephyr app with no `board.yaml` for the generator to resolve
against (see the table's own file header), and its IO8 entry is still the
correct one for the r2 hardware most of this phase's bring-up ran on. Instead,
phase 11 now refuses to drive the pin at all unless it can positively confirm
the live module's hw_rev, over a fresh `alp_hw_info_read()` (independent of
phase 5's own read, so this guard holds regardless of whether phase 5 ran or
passed)
(`examples/aen/aen-evk-demo/src/main.c:4162`
("/* --- 0. Refuse unless the live module is CONFIRMED hw_rev 2626-r2 -- */")).
A read failure, an unprovisioned/corrupt manifest, or any `hw_rev` string
other than exactly `"2626-r2"` all FAIL the phase before `ALP_E1M_GPIO_IO8`
is ever opened
(`examples/aen/aen-evk-demo/src/main.c:4195`
("refused: hw_rev != 2626-r2 (#2138)")) -- not just a
recognised r1, so an unprovisioned module or a future r3+ board fails safe
here too.

**Round-2 review.** The decision moved out of `main.c` into
`examples/aen/aen-evk-demo/src/hw_rev_verdict.h`'s
`aen_evkdemo_hw_rev_confirms_io8_safe()` -- a pure function, same pattern as
`sound_verdict.h`/`amp_fault_verdict.h` in that directory -- so it is
unit-tested directly rather than trusted by inspection; `main.c` now calls
`alp_hw_info_read()` (the SDK's own EEPROM-manifest surface, which already
validates magic + `schema_version` + CRC32 via
`alp_hw_info_classify_manifest()`) instead of the hand-rolled `eeprom_24c128`
read + ad hoc magic check round 1 shipped, closing the gap the review named:
round 1 skipped the schema/CRC checks that classifier already gets right.
`examples/aen/aen-evk-demo/prj.conf` now sets
`CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BUS_ID=0` (the SAME portable bus id --
`EVK_I2C_BUS_SENSORS`/`ALP_E1M_I2C0` -- phase 5's own `ctx->carrier_bus`
already reads this identical 0x50 manifest over, confirmed against
`metadata/e1m_modules/E1M-AEN801.yaml`'s `e1m_i2c0:` block) and
`CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BITRATE_HZ=100000` (matching that same
bus's existing rate -- both opens reconfigure the one physical controller on
`open()`, so leaving them mismatched would reclock every other phase's
carrier-bus traffic to whichever ran most recently).
`tests/zephyr/chips/src/test_hw_rev_verdict.c` adds nine `native_sim` ZTEST
cases proving the header end to end through
`alp_hw_info_classify_manifest()`: r2 confirms, r1/blank-erased/bad-magic/
bad-schema/bad-CRC/a `"2626-r"` prefix all refuse, plus two cases that call
the verdict function directly (not through the classifier) -- an
unterminated, field-filling `"2626-r2X"` and a raw read-error status -- to
prove its own bound doesn't trust an unterminated buffer or a status the
classifier never actually returns for a real read failure.

The table's own "REVISION SCOPE" comment
(`examples/aen/aen-evk-demo/src/cc3501e_gpio_routes.c:39`
("* IO8 AND IO13 -- the I2S mux ENABLE and SELECT phase 11 drives -- are BOTH"))
is corrected to say IO8 is revision-scoped (and now guarded at runtime)
instead of claiming, as before, that the table "needs no per-revision
variant" and that the pinout's own `EVK_PIN_I2S_MUX_EN` / `Alif P7.1` prose
was simply stale -- that prose was right for r1, wrong for r2.

Every other `examples/**/cc3501e_gpio_routes.c` was audited for the same
hazard. `aen-sdcard-readout`'s hand-written table only routes IO20 (the SD
mux ENABLE), which `hw-revisions.yaml` does **not** move on any AEN
revision, so it carries no r1 hazard and is unchanged.
`aen-cc3501e-bringup`/`aen-cc3501e-gpio`/`aen-cc3501e-companion-tour` are all
generator-composed (`scripts/gen_cc3501e_gpio_routes.py`) so their route
tables ARE resolved per the revision each build's `board.yaml` declares --
but that resolution is per BUILD, not per module, so it alone would not have
caught the exact #2138 shape (a table built for one revision's hw_rev
running on a live module of a different one). Their real safety reason is
narrower and does not depend on that: none of the three ever calls
`alp_gpio_open()` on `ALP_E1M_GPIO_IO8`, `IO10`, or `IO21` -- the only pads
`hw-revisions.yaml` moves between chips -- in the first place.
`aen-cc3501e-bringup`'s `main.c` opens no GPIO proxy pad at all;
`aen-cc3501e-gpio` only opens `ALP_E1M_GPIO_IO13`
(`examples/aen/aen-cc3501e-gpio/src/main.c:215`
("the GPIO proxy backend (so a portable alp_gpio_open(ALP_E1M_GPIO_IO13)"));
`aen-cc3501e-companion-tour` only opens `ALP_E1M_GPIO_IO15`
(`examples/aen/aen-cc3501e-companion-tour/src/main.c:793`
("alp_gpio_t *io = alp_gpio_open(ALP_E1M_GPIO_IO15);")) -- neither pad is
revision-dependent. No hazard, no change.

`tests/scripts/test_aen_cc3501e_routes.py:319`
("def test_standalone_app_route_table_guards_revision_dependent_pads(path):")
adds a regression check: it reads every `e1m` pad
`hw-revisions.yaml`'s `pad_route_overrides` ever moves, and for any
standalone hand-written table that routes one of those pads, asserts the
app's `phase_sound()` opens it only after a structural
`if (!<guard>(...)) { ... return PHASE_FAIL; }` (comments stripped first, a
brace-depth scan bounds the function body, `<guard>` is looked up per pad in
`PAD_GUARD_FUNCTIONS`)
(`tests/scripts/test_aen_cc3501e_routes.py:265`
("PAD_GUARD_FUNCTIONS = {")). **Round-2 review**: the round-1 version of this
check only grepped `main.c` for the guard function's NAME appearing anywhere
before the `alp_gpio_open()` call, which passed both a `/* TODO: add the
check here */` stub left in the guard's place and the guard's own condition
inverted (`if (guard_ok)` instead of `if (!guard_ok)` -- refuses r2, drives
the pin on r1, the exact short this issue exists to prevent). Proven against
both: reverting just the `main.c` guard call to a bare TODO comment (route
table and test left in place) reproduces one red failure; inverting the
condition (dropping the `!`) reproduces the other; restoring either brings
the suite back to green (17 passed, 1 skipped).
