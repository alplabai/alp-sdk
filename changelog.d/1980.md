### Fixed — the generated board header defined an address macro for I2C parts that are not on the board (#1980)

`scripts/gen_board_header.py` never read the `assembled` key #1977 added to
`i2c_device_entry` (`metadata/schemas/board-preset.schema.json:389-392`), so
every `i2c_devices:` entry got a plain `#define EVK_I2C_ADDR_<NAME> 0x..u`
regardless of whether the part is actually fitted. On the E1M-EVK, U37 (the
PCIe I/O expander) is `assembled: false` (`metadata/boards/e1m-evk.yaml:295`)
— confirmed absent on both bench boards and from the maintainer's I2C
schedule (`changelog.d`'s own #1974 entry) — but the header still defined
`EVK_I2C_ADDR_TCAL9538_PCIE 0x71u` as if it were real. Firmware that reads
"the header defines an address" as "the part is there" would address
silicon that does not exist and get a clean `-EIO`.

**Decision: rename, don't delete or guard.** Deleting the macro breaks any
existing caller at compile time with no explanation, and #1977 kept the
entry rather than deleting it because the footprint is real and other
revisions populate it — the same is true one row down:
`EVK_I2C_ADDR_TCA6408A_MAIN` (`metadata/boards/e1m-evk.yaml:297`) is the
*alternate* population of the same U35 footprint, bench-confirmed on an
earlier EVK revision and a clean NACK on both current boards, and is now
ALSO marked `assembled: false` here (it was left plain in an earlier pass
of this change, which was itself a bug: the exact class this fix exists to
close). `examples/peripheral-io/i2c-device-hub/src/main.c` already and
correctly probes it at runtime alongside `EVK_I2C_ADDR_TCAL9538_MAIN` as a
legitimate cross-revision fallback, so its caller now spells the renamed
`EVK_I2C_ADDR_TCA6408A_MAIN_NOT_ASSEMBLED` macro. A compile-time `#if 0`
guard or outright omission would make that fallback pattern impossible to
write for a newly-unfitted part without hand-editing a generated file. So
`_emit_i2c_devices()` (`scripts/gen_board_header.py:122`) now renames every
macro an `assembled: false` entry contributes — address, `alias`, and any
`calibration` shunt/max-current pair — with a `_NOT_ASSEMBLED` suffix via
the new `_tag()` helper (`scripts/gen_board_header.py:144`) rather than
emitting the plain name. The plain name a reader would reach for out
of habit is no longer defined at all, so accidental use is a compile error
instead of a silent bus probe against nonexistent silicon; the address and
the `doc:` reason both survive under the renamed macro for anyone who
deliberately wants to probe for an earlier/other revision's population.

**Naming, unresolved:** issue #1980 itself flagged three candidate suffixes
as "worth a decision rather than assuming" and suggested `_NOT_FITTED`.
This change keeps `_NOT_ASSEMBLED` (it matches the `assembled:` key name
directly, and the doc-comment prose #1974/#1977 already wrote), but that
choice was made unilaterally, not by the maintainer — flagging it here so
it can still be revisited before the macro name ships in a release.

A second consumer of `assembled` had the same bug in a different shape:
`scripts/alp_orchestrate/slugs.py`'s `_slugs_from_on_module()` (feeding
`_resolve_chip_states()`'s always-True SoM-intrinsic chip set) only skipped
an `on_module.i2c_devices[].devices[]` entry when `assembled == "optional"`
— an `assembled: false` entry (hard DNP) fell through and auto-enabled its
chip driver regardless. E1M-AEN801's OPTIGA Trust M is exactly this case
(`metadata/e1m_modules/E1M-AEN801.yaml`'s `brd_i2c:` entry is
`assembled: false`, DNP=1 on this batch, "must never reach a shipped
devicetree" — yet `CONFIG_ALP_SDK_CHIP_OPTIGA_TRUST_M=y` landed anyway). The
same on_module also names the part via a plain `secure_element:` scalar
field, a second, independent path into the same slug set — fixing only the
`i2c_devices:` loop left that path still leaking the chip in, so the fix
collects every `assembled: false` **or** `optional` chip name from
`i2c_devices:` first and subtracts it from the final slug set regardless of
which path added it. `tests/fixtures/emit-snapshots/proj-aen.zephyr-conf.snap`
and the four build-plan snapshots that embed an AEN801/AEN803 `alp.conf`
(`rpmsg-aen`, `mproc-mailbox`, `audio-i2s-tone`, `iot-fleet-ota`,
`coap-client-get`) are regenerated: each drops its
`CONFIG_ALP_SDK_CHIP_OPTIGA_TRUST_M=y` line.

Beyond the four stale copies of `EVK_I2C_ADDR_TCAL9538_MAIN`'s address
(still `0x72` instead of the #1974-corrected `0x73`) named in review, more
turned up while regenerating this same header and got fixed in the same
pass: `include/alp/boards/alp_e1m_evk.h` (three separate comment blocks),
`docs/boards/e1m-evk.md`, `metadata/boards/e1m-evk.yaml`'s `populated:`
comment, `include/alp/chips/tcal9538.h`, `metadata/chips/tcal9538.yaml`,
`docs/bring-up-aen.md`, and `docs/tutorials/02-i2c-scan.md`'s "expected
scan output" (which also stopped claiming an ACK at the now-unfitted `0x20`
and `0x71`). Comment-only mentions of the now-renamed
`EVK_I2C_ADDR_TCA6408A_MAIN` (no macro-name change needed, since these
never referenced it as a real compiled identifier) are also updated in
`chips/tcal9538/tcal9538.c` and `tests/zephyr/chips/src/test_platform_ics.c`.

`include/alp/boards/alp_e1m_evk_routes.h` regenerates with
`EVK_I2C_ADDR_TCAL9538_PCIE_NOT_ASSEMBLED 0x71u` and
`EVK_I2C_ADDR_TCA6408A_MAIN_NOT_ASSEMBLED 0x20u`
(`include/alp/boards/alp_e1m_evk_routes.h:131-132`) in place of the two
plain macros; no other generated board header changes (only the E1M-EVK's
`i2c_devices:` block currently declares an `assembled: false` entry).
`metadata/schemas/board-preset.schema.json:392` and
`include/alp/boards/alp_e1m_evk.h` are updated to describe the new
behaviour instead of the previous "the generator does not read this key"
limitation note. No new schema key — `assembled` already exists on `dev`
via #1977; this closes only the gap where the generator (and,
independently, the on-module chip-slug walk) ignored it.

The generator also no longer double-prefixes a `doc:` that already opens
with "NOT ASSEMBLED" of its own accord — both entries above do, so the
first pass of this change produced comments reading "NOT ASSEMBLED on this
board revision. U37 PCIe I/O expander ... NOT ASSEMBLED on this EVK
revision ...", the phrase stated twice in one comment. `_emit_i2c_devices()`
now skips its generic prefix when `"NOT ASSEMBLED"` is already present in
the entry's own `doc:` text.

Two macro renames are an ABI change (docs/abi-markers.md);
`docs/abi/v0.16-snapshot.json` is regenerated in this same PR (`REMOVED
macro alp/boards/alp_e1m_evk_routes.h::EVK_I2C_ADDR_TCAL9538_PCIE`, `ADDED
macro ...::EVK_I2C_ADDR_TCAL9538_PCIE_NOT_ASSEMBLED`, and the same pair for
`EVK_I2C_ADDR_TCA6408A_MAIN` / `..._NOT_ASSEMBLED`) — pre-1.0, ABI may
change between minor releases (docs/release-policy.md), and the E1M-EVK
routes header carries no live caller of either removed name outside this
same PR's own example update. `docs/abi/removed-symbols.json` gets a
matching entry for each so the removal reads as `ALLOWED` rather than
`REMOVED` when `tests/scripts/test_abi_snapshot.py`'s
`test_real_tree_reports_zero_removed_against_last_released_snapshot` diffs
the current tree against the actual last-released baseline
(`docs/abi/v0.15-snapshot.json` — `abi.last_released_snapshot()` skips
`v0.16-snapshot.json` because it equals the CURRENT, unreleased version);
without those entries the same test that greenlit #1622's ADC renames goes
red on this one.

Which physical unit the bench serials belong to (`E1M-AEN801` vs
`E1M-AEN803`) is unresolved and tracked separately as alp-sdk#2001; new
prose in this change refers to "the bench E1M-EVK units (serials
2026W36-0001 / 2026W36-0003; SKU disputed, see #2001)" rather than picking
a side. Pre-existing merged text that already names one SKU or the other
(the #1974/#1976 changelog entries, `alp_banner.c`) is #2001's to settle
and is left as-is.

**Review follow-up.** A fifth stale `0x72` copy, missed by the sweep
above, turned up in a live normative Kconfig help string:
`zephyr/kconfigs/chips.kconfig:206-215`'s `ALP_SDK_CHIP_TCAL9538` help
still described U35 as "at 0x72 (A1=1, A0=0)"; corrected to `0x73
(A1=1, A0=1)` with a trailing "CORRECTED 2026-09-05 from 0x72
(alp-sdk#1974)" sentence, matching the citation style already used in
`metadata/chips/tcal9538.yaml:22`.

Two further review findings were checked and are NOT bugs:

- `docs/tutorials/02-i2c-scan.md:173`'s `0x72 ACK -- TCAL9538 I/O
  expander (one of U35/U37 ...)` line is NOT a stale copy of the
  E1M-EVK's #1974 correction. It sits under the "On V2N's on-board
  sensor bus" heading (`docs/tutorials/02-i2c-scan.md:122`), describing
  the E1M-X-EVK / E1M-V2N101 board -- a different board than the one
  #1974 measured. `XEVK_I2C_ADDR_TCAL9538` genuinely is `0x72` there
  (`metadata/boards/e1m-x-evk.yaml:285`, mirrored in
  `include/alp/boards/alp_e1m_x_evk_routes.h:126`, both untouched by
  this change), and the X-EVK's `tcal9538: true # U35/U37 TCAL9538
  (2x)` (`metadata/boards/e1m-x-evk.yaml:54`) carries no `assembled:
  false` on either designator, so "one of U35/U37, the header doesn't
  say which" is still the accurate statement for this board. Changing
  it to `0x73`/U35-only would fabricate a fact this tree does not
  record for the X-EVK.
- `scripts/alp_orchestrate/loader.py`'s `attestation_root ==
  "optiga_trust_m"` check (around line 1122) builds `chip_set` from
  `som_preset["on_module"]` without an `assembled` guard, but no
  `on_module:` entry can carry `assembled` in the first place: every
  scalar `on_module` role (`secure_element`, `wifi_ble`, ...) resolves
  through `$defs/chip_ref` (`metadata/schemas/som-preset-v1.schema.json:433-446`),
  which is a bare string `oneOf` (a chip-id slug or the literal
  `"TBD"`) with no object form to hang an `assembled` key off; the
  only dict-valued `on_module` keys (`i2c_devices`, `ospi_memories`,
  `hyperram`) are excluded from `chip_set` by the existing `isinstance(val,
  str)` check the loader already has. `assembled: false` cannot reach
  `has_optiga` through `on_module` today. No `on_module` schema change
  is made; #1980 is scoped to `i2c_devices[].assembled`.
