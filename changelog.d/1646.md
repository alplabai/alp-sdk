### Fixed — 12 of 122 `alp_handle_op_enter()` failure sites returned `ALP_ERR_INVAL` instead of `ALP_ERR_NOT_READY` (#1646)

`alp_handle_op_enter()` returning `false` means exactly one thing: the handle is closed or
closing. 110 call sites across `src/` already reported that as `ALP_ERR_NOT_READY`; twelve
sites in `src/update_log_dispatch.c`, `src/dsp_dispatch.c`, and `src/i2c_regfile.c` reported
`ALP_ERR_INVAL` instead, indistinguishable from a genuine caller bug (a bad argument). All
twelve now return `ALP_ERR_NOT_READY`, matching the other 110. `dsp_dispatch.c`'s four sites
carried a comment saying the `ALP_ERR_INVAL` was deliberately preserved "to match this op's
pre-#629 null/not-in-use contract" -- `git log -S` confirms #629 itself (`8d861decf`) wrote
that comment, choosing at the time to keep the pre-#629 `ALP_ERR_INVAL` contract rather than
adopt the `ALP_ERR_NOT_READY` convention it was introducing everywhere else. That was a real,
deliberate decision, not stale leftover -- but this repo has no active customers to protect
from the behaviour change, so #1646 drops it same as the other eleven sites.

**NULL-handle rule, decided here:** `src/ble_dispatch.c`'s `alp_ble_gatt_notify()` originally
fused `conn == NULL` (a caller bug) with the `op_enter` failure (a normal disconnect racing
this notify) into one `if`, both mapped to `ALP_ERR_INVAL` -- an early draft of this fix split
the two, keeping `conn == NULL` on `ALP_ERR_INVAL` per ADR-0002's "`ALP_ERR_INVAL` = programmer
error" framing. That draft was self-contradictory: `i2c_regfile.c`'s two sites and
`dsp_dispatch.c`'s four keep their `X == NULL ||` fused with the `op_enter` check and now map
NULL to `ALP_ERR_NOT_READY` too -- so the same PR would have shipped two different answers to
"what does a NULL handle return" depending on which of the twelve sites you're looking at.
Resolved by **matching the dominant house convention instead of inventing a third rule**: ~104
of the 110 already-compliant call sites fuse `X == NULL ||` into the `op_enter` check and return
`ALP_ERR_NOT_READY` for both. `ble_dispatch.c`'s split is reverted; `conn == NULL` now falls
through the same fused check as every sibling and returns `ALP_ERR_NOT_READY`. ADR-0002's
"`ALP_ERR_INVAL` is a programmer error" rule is not actually implemented at 104 of 110 existing
op_enter sites -- retrofitting real ADR-0002 compliance across the codebase is a separate,
much larger change than #1646 (which is scoped to op_enter-status *drift*, i.e. making the
sibling sites agree with each other). Introducing a fresh split at exactly the site this cluster
touches would be the same kind of drift #1646 exists to fix. Next person: if you want to revisit
NULL -> `ALP_ERR_INVAL` codebase-wide, that's a new issue against all ~114 fused sites, not a
re-litigation of cluster 1.

`src/ble_dispatch.c`'s new `ALP_ERR_NOT_READY` leg (a live `conn` whose owner disconnected
between `alp_ble_gatt_notify()`'s argument check and its `op_enter`) had no test coverage --
`tests/zephyr/ble/src/main.c` only ever exercised `alp_ble_gatt_notify(NULL, NULL, 0, NULL, 0)`,
which returns at the earlier `h == NULL` gate and never reaches this leg. Added
`tests/zephyr/ble_gatt_notify_op_enter/`, a small dedicated suite that registers a fake `ble`
backend (priority 200, ahead of `zephyr_drv`'s 100) so it can drive
`alp_ble_open()`/`alp_ble_connect()`/`alp_ble_disconnect()` through the real
`src/ble_dispatch.c` on `native_sim` (which ships no real BLE controller) and assert both the
`conn == NULL` leg and the post-disconnect `op_enter`-failure leg return `ALP_ERR_NOT_READY`.
Kept out of `tests/zephyr/ble` so this always-succeeds fake backend never leaks into that
suite's "no controller -> `ALP_ERR_NOSUPPORT`" smoke test.

Also fixed six stale `@return` docs this change would otherwise have left behind (issues
#1517/#1518's defect class): `include/alp/i2c_regfile.h` (`alp_i2c_regfile_set_write_window`,
`alp_i2c_regfile_stats`) and `include/alp/dsp.h` (all four `alp_dsp_chain_apply_*` variants)
did not list `ALP_ERR_NOT_READY` at all; `include/alp/update_log.h`'s
`alp_update_log_append`/`alp_update_log_append_boot` omitted it, and
`alp_update_log_verify`/`_count`/`_get` had no `@return` error-code documentation whatsoever
for a reachable `ALP_ERR_NOT_READY` (and, for `_count`/`_get`, no `@return` tag at all) -- all
eight now document the real contract.

Cluster 1 of #1646 (`op_enter`-status drift); clusters 2 and 5 remain open.

Cluster 1's fix (`changelog.d/1646.md`'s original entry, folded into `CHANGELOG.md` at release)
normalized `op_enter`-status drift but deliberately left ADR-0002's own text unamended, noting
"retrofitting real ADR-0002 compliance across the codebase is a separate, much larger change
than #1646." This entry is that separate, docs-only follow-up: it does not touch dispatcher
code, it writes down what the code (as landed by cluster 1) actually does.

`docs/adr/0002-error-mechanism.md` gained a dated Amendment (2026-08-27, original text left
intact) with two parts. First, a **scope correction**: the ADR's "programmer error" parenthetical
(split across the Context section's `bus_id` bullet and the Decision section's
`ALP_ERR_OUT_OF_RANGE` sentence) contrasts three `open()`-time codes only — it never defined
`ALP_ERR_INVAL` for the whole public API, so the ~115 non-`open()` sites returning
`ALP_ERR_NOT_READY` for a NULL primary handle were never in violation; they were simply outside
what the ADR governed. Second, the **convention as measured**: `ALP_ERR_NOT_READY` for a handle
(primary, or a secondary handle threaded through the same `alp_handle_op_enter` lifecycle guard —
`alp_ble_gatt_notify`'s `conn`, per cluster 1's fix above, is the only such site in the whole
surface); `ALP_ERR_INVAL` for a malformed argument outside that guard (NULL `cfg`, a NULL
out-buffer with nonzero length); `ALP_ERR_NOSUPPORT` for a missing capability. A wider set of
pre-existing, deliberate per-site outliers (`src/adc_dispatch.c`'s two sites plus its
`alif_e7`/`alif_e8` vendor-extension twins, `src/jpeg_dispatch.c` plus its build-stub twin,
`src/update_log_dispatch.c`'s five unfused NULL-handle checks, and a dozen more `alp_<vendor>_*`
ext entry points) are named and left unchanged — two of the three families are pinned by
`tests/unit/adc_registry` and `tests/unit/jpeg_registry` assertions, which argues *for*
grandfathering rather than the earlier (wrong) claim that nothing consumes the distinction.
Separately, the Yocto/Linux peripheral backend (`src/yocto/peripheral_{gpio,i2c,spi,uart}.c`)
turns out to answer `ALP_ERR_INVAL` for a closed handle too, not just NULL — a whole-backend
divergence from the Zephyr dispatchers' `ALP_ERR_NOT_READY`, recorded as a known, unresolved gap
rather than folded into the per-site outlier list. `docs/adr/README.md`'s ADR-0002 row notes
the amendment.

`metadata/error-catalog.json`'s `ALP_ERR_NOT_READY` summary changed from "Peripheral not
initialised." (too narrow — a closed or mid-operation handle is "not ready" without ever having
been uninitialised) to "The handle is not in a state to perform this operation." No cross-repo
follow-up needed: tan-cli's `explain`-command tests assert a locally-defined fixture string, not
this catalog value.
