### Fixed — 12 of 122 `alp_handle_op_enter()` failure sites returned `ALP_ERR_INVAL` instead of `ALP_ERR_NOT_READY` (#1646)

`alp_handle_op_enter()` returning `false` means exactly one thing: the handle is closed or
closing. 110 call sites across `src/` already reported that as `ALP_ERR_NOT_READY`; twelve
sites in `src/update_log_dispatch.c`, `src/dsp_dispatch.c`, and `src/i2c_regfile.c` reported
`ALP_ERR_INVAL` instead, indistinguishable from a genuine caller bug (a bad argument). All
twelve now return `ALP_ERR_NOT_READY`, matching the other 110. `dsp_dispatch.c`'s four sites
carried a comment preserving the divergence "to match this op's pre-#629 null/not-in-use
contract" for callers this repo has no active-customer obligation to; the comment is deleted
along with the divergence it justified.

`src/ble_dispatch.c:422`'s `alp_ble_gatt_notify()` was the worst of the twelve: it fused
`conn == NULL` (a real caller bug) with `alp_handle_op_enter(&conn->lifecycle, ...)` failing (a
normal disconnect racing this notify on another thread) into one `if`, both returning
`ALP_ERR_INVAL`. A caller could not tell a coding bug from an expected, retryable race. The
check is now split: `conn == NULL` keeps `ALP_ERR_INVAL`; the `op_enter` failure returns
`ALP_ERR_NOT_READY`.

Cluster 1 of #1646 (`op_enter`-status drift); clusters 2 and 5 remain open.
