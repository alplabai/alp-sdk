### Added — V2N/V2M Murata CYW55513 Wi-Fi/BT Yocto stack (#479)

Every E1M V2N/V2M SKU carries an on-module Murata LBEE5HY2FY-922
(Infineon CYW55513) Wi-Fi 6/6E + BT 5.4 module, but `meta-alp-sdk` had
no driver, firmware, or devicetree for it — no image built with a
working `wlan0` or `hci0`.

Added the full Linux-side stack: `meta-alp-sdk/recipes-kernel/cyw-fmac/`
(the out-of-tree Murata `cyw-fmac` backports kmod — the stock 6.1-cip43
in-tree `brcmfmac` has no CYW55513 chip ID) and
`meta-alp-sdk/recipes-kernel/cyw-fmac-firmware/` (the five firmware
blobs across four upstream repos), a `wifi-bt.cfg` kernel-config
fragment (`CONFIG_CFG80211=m`, in-tree `CONFIG_BRCMFMAC` off, Bluetooth
HCI UART/Broadcom config), the `&sdhi2` (WLAN) and `&sci4` (BT) devicetree
nodes in `e1m-v2n-som.dtsi` — both power-sequenced through the two GD32
bridge `REG_ON` lines added at bridge firmware 0.2.12 (see
`0005-gpio-add-gd32-bridge-expander-driver.patch`) — and
`wireless-regdb`/`iw`/`wpa-supplicant`/`bluez5` wired into
`alp-image-common.inc` for every V2N/V2M `MACHINE_FEATURES`.

Not resolved here: re-running SDIO enumeration against this exact node
shape — the 2026-06 bring-up's real blocker (the on-module 32.768 kHz
LPO, sourced from the on-module 5L35023B clock generator) is fixed
separately, tracked in #2293, not part of this change — and verifying
on the bench that xHCI reports no spurious over-current now that PB1
is muxed as the on-module WLAN group's `SD2DAT0` instead of the
carrier's old usb30-overcurrent GPIO parking (the carrier dtsi's
`usb30_pins`/`usb-ovc-disable-hog` pair, copied from the Renesas EVK
reference dts without checking the ALP module's netlist, claimed PB0/PB1
— both on-module WLAN SDIO nets never routed to the E1M connector — and
is removed in this pass; see `e1m-x-evk.dtsi`). See `docs/soms/v2n.md`'s
new Wi-Fi/BT section for the full state.
