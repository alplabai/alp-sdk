### Added — V2N/V2M Murata CYW55513 Wi-Fi/BT Yocto stack (#479)

Every E1M V2N/V2M SKU carries an on-module Murata LBEE5HY2FY-922
(Infineon CYW55513) Wi-Fi 6/6E + BT 5.4 module, but `meta-alp-sdk` had
no driver, firmware, or devicetree for it — no image built with a
working `wlan0` or `hci0`.

Added the full Linux-side stack: `meta-alp-sdk/recipes-kernel/cyw-fmac/`
(the out-of-tree Murata `cyw-fmac` backports kmod — the stock 6.1-cip43
in-tree `brcmfmac` has no CYW55513 chip ID) and
`meta-alp-sdk/recipes-kernel/cyw-fmac-firmware/` (the five firmware
blobs across four upstream repos), a `wifi-bt.cfg` kernel-config
fragment (`CONFIG_CFG80211=m`, in-tree `CONFIG_BRCMFMAC` off, Bluetooth
HCI UART/Broadcom config), the `&sdhi2` (WLAN) and `&sci4` (BT) devicetree
nodes in `e1m-v2n-som.dtsi` — both power-sequenced through the two GD32
bridge `REG_ON` lines added at bridge firmware 0.2.12 (see
`0005-gpio-add-gd32-bridge-expander-driver.patch`) — and
`wireless-regdb`/`iw`/`wpa-supplicant`/`bluez5` wired into
`alp-image-common.inc` for every V2N/V2M `MACHINE_FEATURES`.

Not resolved here: verifying on the bench that xHCI reports no
spurious over-current now that PB1 is muxed as the on-module WLAN
group's `SD2DAT0` instead of the carrier's old usb30-overcurrent GPIO
parking (the carrier dtsi's `usb30_pins`/`usb-ovc-disable-hog` pair,
copied from the Renesas EVK reference dts without checking the ALP
module's netlist, claimed PB0/PB1 — both on-module WLAN SDIO nets
never routed to the E1M connector — and is removed in this pass; see
`e1m-x-evk.dtsi`). See `docs/soms/v2n.md`'s Wi-Fi/BT section for the
full state.

### Fixed — bench-proven Wi-Fi fixes (2026-09-26, E1M-V2M103 unit 2026W38-0001)

Re-ran SDIO enumeration against the node shape above once the 2026-06
bring-up's real blocker (the on-module 32.768 kHz LPO) was fixed
separately (#2293). Four fixes landed from that bench session:

- `sd-uhs-sdr50`/`sd-uhs-sdr104` on `&sdhi2` — without them mmc2 only
  reached "sd high-speed" at 50 MHz; with them it negotiates "sd uhs
  SDR50" at 100 MHz (SDR104 not reached this run). `sdhi2_vqmmc` is
  already a fixed 1.8 V regulator, so no voltage switching is involved.
- `brcm,ccode-map-trivial` on the `wifi@1` node — without it brcmfmac
  cannot pass the cfg80211 country to the firmware.
- `wireless-regdb-static`, `iw`, `wpa-supplicant` (+ `-cli` /
  `-passphrase`), `bluez5` added to the V2N/V2M image install list
  (`alp-image-common.inc`) — the kernel's
  `CONFIG_CFG80211_REQUIRE_SIGNED_REGDB=y` otherwise leaves cfg80211
  stuck in the world regulatory domain with no userspace tools to
  drive Wi-Fi/BT at all.
- `meta-alp-sdk/recipes-kernel/murata-2gy-nvram/` — module-specific
  NVRAM + CLM for the on-module Murata LBEE5HY2FY (Type 2GY), installed
  under brcmfmac's per-board-compatible firmware names so it is picked
  ahead of `cyw-fmac-firmware`'s generic Infineon eval-board blob
  (boardtype `0x0899`, placeholder MAC `00:90:4c`).

Bench-verified: Wi-Fi scan, WPA2/SAE association on 5 GHz channel 60,
DHCP, and country `DE` via the regdb. Open HW note: RSSI on this bench
unit reads ~-70 dBm where a phone reads ~-35 dBm at the same spot —
points at that unit's antenna/RF path (under investigation), not
software. See `docs/soms/v2n.md`'s Wi-Fi/BT section for the full
bench-results writeup.
