### Fixed — `aen-cc3501e-gpio` and `aen-cc3501e-companion-tour` stack-overflowed in `main()` on boot and halted (#1868)

Both examples declared their `cc3501e_t fw;` driver context as a plain
automatic (stack) local in `main()`. `sizeof(cc3501e_t)` is ~32 KB — `rx_scratch`
/ `tx_scratch` / `wifi_scan_buf` / `ble_scan_buf` / `evt_buf` / `sock_buf` /
`spi1_tx_buf` / `spi1_rx_buf` are each sized off `ALP_CC3501E_MAX_PAYLOAD`,
4096 since the v5 protocol bump — against `CONFIG_MAIN_STACK_SIZE=4096` in
both examples' `prj.conf`. The compiler's frame-reservation instruction for
`main()`'s prologue alone (`sub sp, #framesize`) therefore moved `SP` below
`PSPLIM` before a single statement of `main()` ran, and the M55 raised a
UsageFault immediately: `E: ***** USAGE FAULT ***** / E: Stack overflow
(context area not valid)`, faulting PC resolving (`arm-zephyr-eabi-addr2line`
against the built ELF) to `main()`'s own entry
(`examples/aen/aen-cc3501e-gpio/src/main.c:205`, the line the compiler
attributed the prologue to), with `LR` resolving to `z_setup_new_thread`
(`zephyr/kernel/thread.c:659`) — i.e. `main()` never got past its own
prologue, consistent with the captured boot log showing the SDK banner but
never `main()`'s own first `printf`. Confirmed via `sizeof(cc3501e_t)` = 32888
bytes (host GCC build) and, post-fix, via `arm-zephyr-eabi-nm` on a rebuilt
ELF: `fw` now lands in `.bss` (`20000650 00008040 b fw.0`, gpio; `...b fw.4`,
companion-tour) and `main()`'s prologue drops to `sub sp, #28`.

Same defect, same fix already established in `aen-cc3501e-bringup`'s own
`fw` (that example's comment: *"STATIC, not a stack local: ... as a local
the prologue crosses PSPLIM and the M55 raises STKOF -> UsageFault at
main+4 ... Bench-proven: as a local this image never boots."*) — it just
never propagated to its two siblings. `aen-cc3501e-gpio` and
`aen-cc3501e-companion-tour` now declare `static cc3501e_t fw;` too, moving
the context to BSS instead of the main thread's stack. Both rebuilt clean
(`west build`, `alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he`); no
`CONFIG_MAIN_STACK_SIZE` change needed for either — the GPIO/camera-enable
and diagnostic/socket helpers these two call all use small fixed-size wire
structs or (companion-tour's socket buffers) are already `static`, so 4096 B
of real stack is ample once the 32 KB context is off it.

**Second symptom investigated, not fixed here.** The same boot capture shows
the banner printing the raw `CONFIG_BOARD` target (`alp_e1m_aen801_m55_he`)
instead of the live SoM identity (`E1M-AEN801 r1`, as `alp-console` prints on
the same physical module) — the original issue's two guesses (`CONFIG_ALP_SDK_HW_INFO`
never enabled, or a fault before the manifest read) are both wrong.
`CONFIG_ALP_SDK_HW_INFO` defaults to `y` and is on; `scripts/alp_orchestrate`
auto-emits `CONFIG_ALP_SDK_HW_INFO_EEPROM_I2C_BUS_ID=0` (+ address/offset/
bitrate) into every AEN build from the SoM preset's `on_module.eeprom`,
regardless of the app's own `peripherals:` list — confirmed present and
correctly resolved in `aen-cc3501e-gpio`'s own `.config`. The read still
fails because the underlying devicetree node it targets, `i2c2`, is
`status = "disabled"`: none of `aen-cc3501e-gpio` / `aen-cc3501e-bringup` /
`aen-cc3501e-companion-tour`'s board overlays enable it or declare the
`alp-i2c0` alias `alp_hw_info_read()`'s `alp_i2c_open(bus_id=0)` needs — only
`alp-console`'s overlay does (its own `&i2c2 { status = "okay"; ... };` +
`alp-i2c0 = &i2c2;`, bench-validated pad config). So on all three CC3501E
examples the EEPROM read structurally cannot succeed, the banner falls to
the `CONFIG_BOARD` fallback, and the `#1853`/`#1859` `hw_rev`-mismatch guard
(keyed on that same read) is inert on all three, not just this one. Wiring
`i2c2` into three example overlays is a distinct, bench-validated hardware
change (pad config, pull direction, possible pin interaction with each
example's existing SPI1/LP-GPIO wiring) outside this fix's scope — left as a
follow-up.
