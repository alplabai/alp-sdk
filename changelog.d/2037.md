### Fixed — the Alif UTIMER quadrature decoder was configured and then never started (#2037)

`qdec_alif_utimer_init()` programmed the whole channel — pinctrl, clock,
up/down trigger sources, filter, reload, `CNTR_CTRL` bit 0 `EN` (via
`alif_utimer_enable_counter()`) and bit 5 `CNTR_TRIG` — and then never issued
the start. Enabling a channel and starting it are two different registers:
HWRM 13.2.5 names the **global** `UTIMER_GLB_CNTR_START` write as how a
channel is turned on, and nothing wrote it. `#1828` fixed the neighbouring
half by arming the programmatic start *source* (`START_1_SRC[31]` `PGM_EN`),
which is not the same thing as issuing a start.

Measured over SWD on `E1M-AEN803` serial `2026W36-0002` after a clean run
(`CFSR = 0x00000000`):

```
CNTR_CTRL        (0x4800D080) = 0x00000021   EN=1, CNTR_TRIG=1, RUNNING(bit1)=0
GLB_CNTR_RUNNING (0x4800000C) = 0x00000000   bit 12 clear -- no channel running
GLB_CNTR_START   (0x48000000) = 0x00000000   never written
CNTR / CNTR_PTR  (0x4800D0A0) = 0x00000000 0x0000005F
```

The channel sat armed and idle: turning the shaft produced nothing and
`sensor_sample_fetch()` returned success the whole time. The fix is one call
to hal_alif's `alif_utimer_start_counter(global_base, cfg->timer_id)` after
the configuration is complete — the **global** reg base and the timer id,
the same calling convention as `alif_utimer_enable_timer_clock()`. On
silicon, `CNTR_CTRL` bit 1 `RUNNING` (and `GLB_CNTR_RUNNING` bit 12 for QEC0
on UTIMER channel 12) is what proves it took effect — re-measured on the same
board after the fix:

```
CNTR_CTRL        (0x4800D080) = 0x00000023   EN=1, RUNNING(bit1)=1, CNTR_TRIG=1
GLB_CNTR_RUNNING (0x4800000C) = 0x00001000   bit 12 set -- channel 12 running
```

Every other register in the channel read bit-identical to the pre-fix run
(`GLB_CLOCK_ENABLE 0x00001C00`, `START_1_SRC 0x80000000`, `UP_1_SRC
0x00000069`, `DOWN_1_SRC 0x00000096`, `FILTER_CTRL_A 0x00100101`, `CNTR_PTR
0x0000005F`, pads `P3_0`/`P3_1` both `0x00210005`), so nothing else moved to
confound the result.

**What this does not fix, stated because the same run exposed it.** With the
counter now running and nobody touching the shaft, the count advanced
steadily — no stationary encoder should do that. (The **rate** is not known:
the app polls a mod-96 counter every ~300 ms, so the observable is only
`(rate * 0.3) mod 96` and many rates share that residue. What the steadiness
does rule out is a free-run on the UTIMER clock itself, which at MHz rates
would scramble that residue.) So
this change proves the channel starts; it does **not** establish that the
counter is advancing on real quadrature edges, and `aen-qenc-readout` will
now report `PASS` on an untouched shaft. That is a separate defect, being
diagnosed separately; it was previously masked by the counter never running
at all.

No matching stop is added: nothing suspends or unbinds this device. The
driver registers no `pm_device` action and no deinit hook, its
`SENSOR_DEVICE_DT_INST_DEFINE()` passes `NULL` for PM, and a
`POST_KERNEL`-initialised counter that runs for the lifetime of the image is
the intended steady state for a position sensor that is read by polling.

`examples/aen/aen-qenc-readout` no longer prints `decoder armed as
configured` on a `SKIPPED` verdict. The sensor API this driver registers is
`{sample_fetch, channel_get}` only — no `attr_get`, no raw-counter channel —
so the app cannot see `CNTR_CTRL` bit 1 `RUNNING`, and clean reads of a
stopped counter are byte-identical to clean reads of an idle running one.
That over-claim is exactly how this defect survived a bench run. The
`SKIPPED` line now says only what it observed: the reads succeeded and the
count did not change, and confirming the run state needs a debugger read.
