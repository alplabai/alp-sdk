### Fixed — filter both quadrature inputs; withdraw a counter-start "fix" that made the encoder worse (#2037)

**The headline of this fragment used to be "the Alif UTIMER quadrature decoder
was configured and then never started". That was wrong, the fix it described is
withdrawn, and the reasoning is kept here because the mistake is instructive.**

`qdec_alif_utimer_init()` leaves UTIMER channel 12 with `CNTR_CTRL` =
`0x00000021` — `CNTR_EN` (bit 0) and `CNTR_TRIG` (bit 5) set, bit 1 `RUNNING`
clear — and `GLB_CNTR_RUNNING` = `0x00000000`. That was read as "the channel was
never started", and a call to `alif_utimer_start_counter()` was added to issue
the global `GLB_CNTR_START` write.

**It is the correct resting state for a trigger-counting channel, and starting
the channel broke it.** Measured on `E1M-AEN803` serial `2026W36-0002` with the
encoder untouched, after the start call landed:

```
CNTR (0x4800D0A0) advanced 3,999,905,225 counts in 10.000 s = 400,010,738 /s
```

with `UP_1_SRC` (`0x4800D01C`) and `DOWN_1_SRC` (`0x4800D024`) **both written to
`0x00000000`** — the entire ×4 quadrature matrix deselected, so no A/B
transition of any polarity could contribute. That is the peripheral clock rate,
not an encoder rate. Writing `GLB_CNTR_STOP` (`0x48000004`) bit 12 froze it
instantly and completely — three `CNTR` reads 5 s apart, bit-identical
`0xF7E3EFEE` — with `GLB_CNTR_RUNNING` bit 12 going `1` → `0` and `CNTR_CTRL`
`0x00000023` → `0x00000021`.

`GLB_CNTR_START` puts the channel into free-running clocked mode; it does not
make it count encoder edges. With the shipped reload (`CNTR_PTR` =
`counts-per-revolution - 1` = `0x0000005F`) that free-run wraps a whole
revolution every **240 ns**, so the reported angle became uncorrelated noise —
strictly worse than the stuck-at-zero symptom the change was meant to fix. It
was committed and reported as bench-verified before that was understood.

Alif's own QEC flow never starts the channel either. `qec0_app()` in
`Boards/Templates/Baremetal/demo_qec.c` runs `ConfigCounter(TRIGGERING,
TRIANGLE)` → `SetCount` → three `ConfigTrigger` calls → `GetCount` → `Stop`,
with no `Start()` anywhere, and their `MODE_TRIGGERING` performs exactly one
hardware action, `utimer_glb_driver_output_disable()`. The counter increments
from triggers alone.

**A register trap that made the bad fix look verified.** `CNTR_CTRL` bit 1
`RUNNING` is *status*, not control: it is set by `GLB_CNTR_START` and cleared by
`GLB_CNTR_STOP`, and writing it into `CNTR_CTRL` does not take — a write of
`0x00000023` reads back `0x00000021`. The original "proof" that the start fix
had taken effect was that bit changing state, which only ever showed that
something else had started the counter.

### Fixed — the quadrature input filter was applied to one input and not the other (#2037)

`FILTER_CTRL_A` (`0x4800D084`) was programmed `0x00100101` — prescaler 16, taps
1, enabled — while `FILTER_CTRL_B` (`0x4800D088`) stayed at `0x00000000`, so one
quadrature input was filtered and the other ran raw. Both now get the same word.

This is register hygiene, matching what hal_alif's own
`alif_utimer_enable_filter()` does, and it is **not** a fix for any observed
symptom: it was tried against the spurious count and changed nothing. Its
original rationale — that the `SRC_1` decode is level-qualified across the
encoder pair, so skewing one input mis-classifies transitions — only holds if
"channel input A/B" on a QEC channel are the encoder's pads, which is exactly
what is unproven (see below).

### What is still open

**The rotary encoder's decode path is unproven, and the original symptom is
unexplained.** With the counter in its correct resting state, whether it
increments on real quadrature edges has never been observed — no run has had a
hand on the shaft. "The counter was never started" was the wrong explanation for
the stuck-at-zero reading, and no replacement explanation has been established.

`UP_0_SRC` (`0x18`) and `DOWN_0_SRC` (`0x20`) read `0x00000000`. Whether that is
a defect is open: an earlier version of this fragment claimed the SVD marks
`UP_0_SRC` unusable on QEC channels, citing eight `For QEC channels: Reserved,
not used` annotations. **Those eight are on bits `[31:24]` only** (`TRIG12` ..
`TRIG15`); the other 24 fields, bits `[23:0]`, read *"For QEC channels:
Rising/Falling edge of `QEC_TRIGGER0..11` causes counter to increment"*. `SRC_0`
**is** a QEC-channel input path, and that misreading was used to reject a
proposed fix routing the triggers through it.

What survives: `UP_1_SRC` `0x00000069` / `DOWN_1_SRC` `0x00000096` are a
complete, disjoint ×4 matrix over (A,B). What was never established: that
"channel input A/B" on a QEC channel are the encoder's X/Y pads at all. Alif
bind this same `alif,utimer-qdec` driver only under `lputimer0/1/2` in their own
tree, where A/B are that channel's real pads.

`examples/aen/aen-qenc-readout` reports an unattended moving count as **`FAIL` —
spurious counts**, not `PASS`, so none of this can be mistaken for a working
encoder. `counts-per-revolution` stays 96 (24 PPR × 4) while the ×4 matrix is
programmed, and must be revisited if the input path changes.
