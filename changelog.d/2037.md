### Fixed — the Alif UTIMER quadrature decoder was configured and then never started (#2037)

`qdec_alif_utimer_init()` programmed the whole channel — pinctrl, clock,
up/down trigger sources, filter, reload, `CNTR_CTRL` bit 0 `EN` (via
`alif_utimer_enable_counter()`) and bit 5 `CNTR_TRIG` — and then never issued
the start. Enabling a channel and starting it are two different registers:
HWRM 13.2.5 names the **global** `UTIMER_GLB_CNTR_START` write as how a
channel is turned on, and nothing wrote it. `#1828` fixed the neighbouring
half by arming the programmatic start *source* (`START_1_SRC[31]` `PGM_EN`),
which is not the same thing as issuing a start.

Measured over SWD on `E1M-AEN803` serial `2026W36-0002` after a clean run
(`CFSR = 0x00000000`):

```
CNTR_CTRL        (0x4800D080) = 0x00000021   EN=1, CNTR_TRIG=1, RUNNING(bit1)=0
GLB_CNTR_RUNNING (0x4800000C) = 0x00000000   bit 12 clear -- no channel running
GLB_CNTR_START   (0x48000000) = 0x00000000   never written
CNTR / CNTR_PTR  (0x4800D0A0) = 0x00000000 0x0000005F
```

The channel sat armed and idle: turning the shaft produced nothing and
`sensor_sample_fetch()` returned success the whole time. The fix is one call
to hal_alif's `alif_utimer_start_counter(global_base, cfg->timer_id)` after
the configuration is complete — the **global** reg base and the timer id,
the same calling convention as `alif_utimer_enable_timer_clock()`. On
silicon, `CNTR_CTRL` bit 1 `RUNNING` (and `GLB_CNTR_RUNNING` bit 12 for QEC0
on UTIMER channel 12) is what proves it took effect — re-measured on the same
board after the fix:

```
CNTR_CTRL        (0x4800D080) = 0x00000023   EN=1, RUNNING(bit1)=1, CNTR_TRIG=1
GLB_CNTR_RUNNING (0x4800000C) = 0x00001000   bit 12 set -- channel 12 running
```

Every other register in the channel read bit-identical to the pre-fix run
(`GLB_CLOCK_ENABLE 0x00001C00`, `START_1_SRC 0x80000000`, `UP_1_SRC
0x00000069`, `DOWN_1_SRC 0x00000096`, `FILTER_CTRL_A 0x00100101`, `CNTR_PTR
0x0000005F`, pads `P3_0`/`P3_1` both `0x00210005`), so nothing else moved to
confound the result.

**What this does not fix, stated because the same run exposed it.** With the
counter now running and nobody touching the shaft, the count advanced
steadily — no stationary encoder should do that. (The **rate** is not known:
the app polls a mod-96 counter every ~300 ms, so the observable is only
`(rate * 0.3) mod 96` and many rates share that residue. What the steadiness
does rule out is a free-run on the UTIMER clock itself, which at MHz rates
would scramble that residue.) So
this change proves the channel starts; it does **not** establish that the
counter is advancing on real quadrature edges. That is a separate defect,
previously masked by the counter never running at all.

Its source is **internal to the channel, not the pads.** Floating QEC0 X/Y
inputs were the leading theory — the pad word `0x00210005` is AF 5, `REN`=1,
`DSC`=0 (no bias), `SMT`=0 (no Schmitt), and the PEC12R's A/B contacts are
open at a detent — but a bench run walked four pad configurations and the
counter kept advancing through every one: no bias (`0x00210005`), pull-up
(`0x00290005`), pull-up + Schmitt (`0x002B0005`), and AF=0 with `P3_0`/`P3_1`
deselected from the QEC altogether (`0x00290000`). A floating-input mechanism
has to stop when the pin no longer drives the peripheral. `aen-qenc-readout`
therefore reports a moving count on an unattended run as `FAIL — spurious
counts`, not `PASS`.

No matching stop is added: nothing suspends or unbinds this device. The
driver registers no `pm_device` action and no deinit hook, its
`SENSOR_DEVICE_DT_INST_DEFINE()` passes `NULL` for PM, and a
`POST_KERNEL`-initialised counter that runs for the lifetime of the image is
the intended steady state for a position sensor that is read by polling.

`examples/aen/aen-qenc-readout` no longer prints `decoder armed as
configured` on a `SKIPPED` verdict. The sensor API this driver registers is
`{sample_fetch, channel_get}` only — no `attr_get`, no raw-counter channel —
so the app cannot see `CNTR_CTRL` bit 1 `RUNNING`, and clean reads of a
stopped counter are byte-identical to clean reads of an idle running one.
That over-claim is exactly how this defect survived a bench run. The
`SKIPPED` line now says only what it observed: the reads succeeded and the
count did not change, and confirming the run state needs a debugger read.

### Fixed — the quadrature decoder filtered one phase and left the other raw (#2037)

`qdec_alif_utimer_init()` programmed `UTIMER_FILTER_CTRL_A` and never touched
`UTIMER_FILTER_CTRL_B`, so whenever a board asked for the input filter, phase
A was filtered and phase B kept its `0x00000000` reset. Measured on
`E1M-AEN803` serial `2026W36-0002`: `FILTER_CTRL_A 0x00100101`,
`FILTER_CTRL_B 0x00000000`.

That asymmetry matters because the decode is level-qualified **across the
pair**. AE822 SVD, peripheral `UTIMER`: `UTIMER_UP_1_SRC` (`addressOffset
0x1C`) bit 0 `DRIVE_A_RISING_B_0` is *"channel input A is rising and channel
input B = 0 causes counter to increment"*, and its seven siblings are
qualified the same way; `UTIMER_FILTER_CTRL_A` (`0x84`) and
`UTIMER_FILTER_CTRL_B` (`0x88`) are the per-input filters, *"Allows the input
A / B to be sampled periodically"*. Delaying A by the filter's sample depth
while B arrives raw lets a transition be sampled against the other phase's
stale level and classified into the wrong direction — which is how contact
bounce on a mechanical encoder nets counts instead of cancelling. The fix
writes the same word to both registers.

**Stated plainly: this is source-reasoned, not measured.** Its effect on the
spurious count is **unproven** — a candidate, not a demonstrated cure.

**Bench criterion, since nobody will be turning the shaft.** Read `CNTR`
(`0x4800D0A0`) **raw over SWD** at three well-separated intervals; all three
must be **bit-identical**. Any change is a FAIL. Do not substitute the app's
printed degrees: it polls a mod-96 counter, so it cannot distinguish "static"
from "advanced by exactly 96·k". What this can never show is that the counter
tracks real quadrature edges — that needs a hand on the shaft (one detent =
±4 raw counts; one revolution CW = +96, back to the start; then CCW).

**Retracted: the `PGM_EN` lead.** A previous entry here and a comment in the
driver offered as an open lead that `UP_1_SRC`/`DOWN_1_SRC` hold the ×4 masks
`0x69`/`0x96` "with `PGM_EN` (bit 31) clear, while `START_1_SRC` /
`STOP_1_SRC` / `CLEAR_1_SRC` all have it set". There is no bit 31 in those
registers to be clear. Per the SVD, `UTIMER_UP_1_SRC` (`0x1C`) and
`UTIMER_DOWN_1_SRC` (`0x24`) define eight fields in bits `[7:0]` and nothing
else; `PGM_EN [31:31]` is a field of `UTIMER_START_1_SRC` (`0x04`),
`UTIMER_STOP_1_SRC` and `UTIMER_CLEAR_1_SRC` **only**, gating the
*programmatic* start/stop/clear — there is no programmatic up/down to gate.
For the same reason `UP_0_SRC` (`0x18`) and `DOWN_0_SRC` (`0x20`) reading
`0x00000000` is **expected, not a defect**: `SRC_0` is the
`QEC_TRIGGER0..11` raw-input crossbar, and the quadrature decode is programmed
through the `SRC_1` A/B matrix. Walk `(A,B) 00→10→11→01→00` against the SVD
field names and all four transitions land in the up mask `0x69`, all four
reverse transitions in the down mask `0x96` — a complete, disjoint ×4 decode,
which is why `counts-per-revolution` is 24 PPR × 4 = 96 and stays there. The
spurious count's source is still internal to the channel, not the pads: the
four-pad-configuration measurement is unaffected by any of this.

**Next step, recorded rather than taken: `CNTR_TYPE`.** Measured `CNTR_CTRL =
0x00000023` decodes (SVD `UTIMER_CNTR_CTRL`, `0x80`) as `CNTR_EN[0]=1`,
`CNTR_RUNNING[1]=1`, `CNTR_TYPE[4:2]=0` = **Sawtooth**, `CNTR_TRIG[5]=1`,
`CNTR_DIR[8]=0` = Up. Alif's own QEC flow configures **Triangle** instead
(`demo_qec.c` `qec0_app()` passes `ARM_UTIMER_COUNTER_TRIANGLE`, which
`utimer_config_direction()` turns into `CNTR_CTRL_TRIANGLE_BUF_TROUGH =
0x10`). Whether a sawtooth-up channel honours a decrement trigger at all is
stated nowhere we can find; worth one bench comparison.

**Dead end, documented so nobody spends a bench slot on it.** The "channel
drives its own input" theory is impossible: SVD `UTIMER_GLB_DRIVER_OEN`
(`0x10`) defines `DRIVER_OEN_0..DRIVER_OEN_11` across bits `[23:0]` and
nothing above, so QEC channels 12-15 have no driver outputs to loop back, and
Alif's `utimer_glb_driver_output_disable()` on channel 12 writes nothing.
