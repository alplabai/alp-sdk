### Fixed — Alif CPI/CSI driver's `fourcc_to_csi_data_type()` had no RGB mapping beyond RGB565 (#226)

`zephyr/drivers/video/video_alif.c:295`'s `fourcc_to_csi_data_type()` opened
with `/* TODO: Add support for RGB formats. */` and only mapped
`VIDEO_PIX_FMT_RGB565`, even though `zephyr/include/zephyr/drivers/video/video_alif.h:197`'s
`data_mode_settings[]` already carries CPI/IPI hardware config for all five
`CSI2_DT_RGB*` data types.

Checked every packed RGB `VIDEO_PIX_FMT_*` Zephyr v4.4.1 actually defines
(`<zephyr/drivers/video.h>`) against each `CSI2_DT_RGB*`'s bit layout, not
its name:

- `CSI2_DT_RGB888` is **24 bpp, no padding** —
  `zephyr/include/zephyr/drivers/video/video_alif.h:220` says
  `bits_per_pixel: 24` for it despite the entry being named
  `CPI_COLOR_MODE_CONFIG_IPI48_XRGB888`, which is the hardware's internal
  48-bit-IPI-datapath label, not a 32-bit pixel format. Mapped from
  `VIDEO_PIX_FMT_RGB24` and `VIDEO_PIX_FMT_BGR24` (both 24 bpp, no padding)
  — the CSI-2 data-type field encodes bit depth only, not channel order,
  the same reasoning `zephyr/drivers/video/video_alif.c:332-337` already
  applies by mapping all four Bayer orders (`BGGR8`/`GBRG8`/`GRBG8`/
  `RGGB8`) to the single `CSI2_DT_RAW8`.
- `CSI2_DT_RGB444` (12 bpp), `CSI2_DT_RGB555` (15 bpp) and `CSI2_DT_RGB666`
  (18 bpp) are left **unmapped**: Zephyr v4.4.1 defines no packed fourcc at
  those widths.
- `VIDEO_PIX_FMT_RGB565X` (16 bpp, big-endian) is left unmapped: the
  `CSI2_DT_RGB565` table entry documents little-endian packing only, and
  nothing available confirms the CPI IPI packs big-endian on the wire —
  mapping it would risk a silent byte-swap.
- The 32 bpp `VIDEO_PIX_FMT_{A,X}RGB32`/`{A,X}BGR32`/`RGBA32`/`RGBX32`/
  `BGRA32`/`BGRX32` family is left unmapped: `CSI2_DT_RGB888` is 24 bpp per
  the table, and a 32-bit fourcc would misconfigure the IPI bit width.

`fourcc_to_numplanes()` (`zephyr/drivers/video/video_alif.c:155`) and
`fourcc_to_plane_size()` (`zephyr/drivers/video/video_alif.c:67`) are the two
sibling lookups the CPI capture path also consults per fourcc;
`VIDEO_PIX_FMT_RGB24` and `VIDEO_PIX_FMT_BGR24` were missing from both
(defaulting to 0 planes / `UINT_MAX` plane size), which would have moved
the gap rather than closed it. Both now list the two new formats alongside
the existing single-plane group. While there, `VIDEO_PIX_FMT_RGB565` —
already CSI-accepted before this change — was found missing from the same
two functions and added too; `pix_fmt_bpp()`
(`zephyr/drivers/video/video_alif.c:212`) needed no change for any of the
three, since Zephyr's own `video_bits_per_pixel()` already returns their
correct bpp before `pix_fmt_bpp()`'s own switch runs.

**Bench-unverified.** No camera sensor is wired on this hardware batch
(board rev r1, serial 2617-0001, currently not booting per #1883); every
mapping above is reasoned from the CSI-2 data-type/IPI-mode table, not
observed on silicon. Live frame capture, `aen-camera-regcheck` runtime
validation, and buffer/AXI-error checks remain blocked pending a wired
sensor and are unchanged by this fix.
