### Added — Alif Ensemble E8 ISP-Pico: real AE/AWB through the standard Zephyr video ctrl path (#2252)

`zephyr/drivers/video/isp_pico.c` (the VeriSilicon ISP Nano driver,
`vsi,isp-pico`) now drives auto white balance and auto exposure/gain through
the same portable Zephyr video ctrl registry any other video device uses --
`VIDEO_CID_AUTO_WHITE_BALANCE` and `VIDEO_CID_EXPOSURE_AUTO` on the ISP
device -- instead of the driver having no `.set_ctrl` at all (the v4.4
video-API port had dropped the fork driver's old value-pointer ctrl
callbacks along with their only callers of the hal_alif libisp wrapper's
`isp_vsi_set_param()`/`isp_vsi_get_param()`).

3A (AWB + AE) runs from the calibration by default (hal_alif patch 0009,
below) -- a generic ISP driver has no business embedding its own calibration
table, so `isp_apply_wb()` round-trips `isp_vsi_get_param()`/
`isp_vsi_set_param()` to flip only `.enable`/`.op_mode` on whatever
calibration the integrator's build already compiled in (`isp_param_conf.h`,
selected by which `CONFIG_ISP_LIB_*_MODULE` Kconfigs are on) -- no sensor
calibration table lives in this driver. AE's own limits (exposure-time
ceiling, gain ceiling) have no calibration-table equivalent for this sensor,
so they are pushed once, at the first stream start: the exposure-time
ceiling from the sensor's own reported frame interval (`video_get_frmival()`,
now forwarded down the isp -> cam -> csi -> sensor chain by new
`.get_frmival` implementations in `video_alif.c`/`video_csi_dw.c`) and the
gain ceiling from the sensor's own registered `VIDEO_CID_ANALOGUE_GAIN` range
(`video_query_ctrl()`) -- both sensor-agnostic; the one remaining
sensor-specific constant is the register-value-to-library-fixed-point gain
conversion factor, which a future sensor with a different "1x" register value
would need to update. Whenever `CONFIG_ISP_LIB_AE_MODULE` is built, the
driver also forces the sensor's own `EXPOSURE_AUTO`/`AUTOGAIN` to
manual/off at every stream start (`isp_apply_ae_sensor_gate()`), in both
library AE modes, so the ISP's own exposure/gain write-back
(`VIDEO_CID_EXPOSURE`/`VIDEO_CID_ANALOGUE_GAIN`) never fights the sensor's
own AEC. A `k_mutex` now serializes the hal_alif library calls
between the app thread (`isp_set_ctrl()`) and the ISP's own frame-end
workqueue (`isp_bottom_half()`); a ctrl change made mid-stream is recorded
but only takes effect at the next stream start (the ISP must be stopped for
an apply to stick), not live. The `<alp/camera.h>` viewfinder path now also
recycles stale buffers instead of leaking them across a restart.

`isp_flush()`'s stop path (`cancel=true`) now cancel-syncs the frame-end
bottom half before draining buffers back to the caller, closing a window
where an already-queued (or mid-run) bottom half could still hand hardware a
buffer after the caller believed it owned every buffer back. The other path
(`cancel=false`, a plain flush while streaming) waits for the fifo to drain
the normal way, one frame-end at a time, but that wait is bounded: if it
times out with the MI still DMA-ing into the current buffer, it now returns
`-ETIMEDOUT` and leaves every queue and the streaming state untouched,
instead of draining a fifo the hardware is still writing into and reporting
a stop that never happened. A caller that hits the timeout can retry with
`cancel=true`, which does stop the ISP before it drains.

`zephyr/drivers/video/video_alif.c` (the Alif CPI capture controller): the
packed/unpacked Bayer-fourcc translation table (`cpi_unpacked_fmts[]`) now
`break`s on both the forward and reverse lookups. Each `.mem`/`.link` value
is already unique in the table, so neither lookup was actually ambiguous;
the `break`s are defensive/symmetry only, guarding against a future
duplicate row rather than fixing an observed collision.

`zephyr/drivers/video/video_csi_dw.c` (the DesignWare CSI-2 host bridge):
`csi2_dw_init()` now masks every `CSI_INT_MSK_*` interrupt source before
arming the NVIC line, and `csi2_dw_irq_on()` reads (clears) every
read-to-clear `CSI_INT_ST_*` status register before unmasking the real
sources -- closing a window where the CSI-2 host's own interrupt could fire
from a stale/reset register state while a sensor on the same bus was still
completing its own power-up lane park.

hal_alif v2.3.0 carry patches (`zephyr/patches/hal_alif/`): 0003 adds a
packed-BGGR10 Bayer-fourcc-to-pixel-format mapping the wrapper was missing;
0004 fixes a `CONFIG_` prefix typo that silently disabled an AWB-measurement
Kconfig; 0005 ports the AE module's sensor write-back
(`isp_vsi_bottom_half()`) from the pre-v4.4 3-argument `video_set_ctrl()`
form to the pinned Zephyr v4.4.1 `struct video_control` API (dead code until
now -- no example previously enabled `CONFIG_ISP_LIB_AE_MODULE`), and
latches its own write-back failures to log once rather than once per frame;
0006 replaces a generic placeholder sensor-timing table with values derived
from a real sensor's own register facts; 0007 guards `VSI_MPI_ISP_SetCalib()`
in `isp_vsi_update_cfg()` with a once-flag, so the calibration blob loads
once instead of being reloaded (and stomping the driver's own runtime AE/WB
state) on every restart; 0008 carries an OV5647-derived AWB/CCM calibration
(centre line, white-point range, illuminant gains, CCM matrices), selected
by `CONFIG_VIDEO_ISP_VSI_CALIB_OV5647`, in place of the compiled-in ARX3A0
one -- RPi-derived (Raspberry Pi libcamera's `ov5647.json`, BSD-2-Clause),
then scaled onto the INNO-MAKER module on the bench (kR 0.770, kB 0.778;
runs 159/162) against the untouched ARX3A0 table's own internal gain
relation; one scene, provisional, flagged for a further bench-driven
retune. CCM amplifies an existing low-saturation cast on this module's
room scenes (runs 163/164) rather than causing it: runs 171/172
(colour-bar test pattern, all 8 bars at the correct hue and full
saturation, CCM on -- run 172 through `<alp/camera.h>`) and run 178 (the
pattern's faded and dark bars land exactly where expected, e.g. pure red
at raw 110 gives V +50 = BT.601) show the ISP pipeline is colour-correct,
and run 176 (a same-frame CPI raw-vs-ISP comparison) shows the ISP
matches the raw scene to 1.5% while the raw scene itself varies only ~4%
(white ceiling raw R/G 0.98, B/G 0.97). So the muted colour and cast come
from the sensor/lens (likely an IR leak) plus the provisional AWB/CCM
calibration, not from the ISP; CCM ships enabled
(`CONFIG_ISP_LIB_CCM_MODULE=y`) in both ov5647 examples' `prj.conf` --
`aen-isp-ov5647-capture` and `aen-isp-ov5647-viewfinder`, same as
`aen-isp-regcheck` -- and a grey-card/chart calibration will retune that
provisional calibration; the sensor/lens sets the room-colour ceiling.
0009 moves
`VSI_MPI_ISP_SetCalib()` to before the AWB/AE algorithm callbacks are
registered in `isp_vsi_init()`, matching upstream's own order -- without it
neither algorithm ever converges (both callbacks register against a library
that hasn't loaded a calibration yet), so this is the fix that actually gets
AWB/AE running at all.

The AWB/CCM calibration is provisional (one scene, RPi-derived); room-scene
colour stays muted (saturation 0.16 with CCM on vs 0.08 off) because the
sensor/lens delivers a nearly neutral raw scene (±4%, likely IR leak; run
176, ISP matches raw to 1.5%), not because the ISP loses colour.

`examples/aen/aen-isp-ov5647-capture`: a real OV5647 sensor frame through
the full camera -> csi -> cpi -> isp -> memory graph. AE + AWB run by
driver default now (no ctrl calls needed to turn them on), mirroring Alif's
own sdk-alif `samples/drivers/viewfinder` recipe.

User-visible backend changes: `src/backends/camera/alif_isp_pico.c` (the
`<alp/camera.h>` `alif_isp_pico` backend) never gets RGB565 straight from
the ISP -- its MI output is YUV/mono/Bayer only -- so a caller requesting
`ALP_PIXFMT_RGB565` now has that negotiated as a YUV format instead (YUV420
planar tried first, YUYV as the fallback) and converted to RGB565 on the
CPU, via the new table-driven fast path in `src/backends/camera/
yuv_to_rgb565.h` (`tests/unit/camera_yuv_to_rgb565` covers it) rather than
the naive per-pixel reference converter. The backend also recycles stale
buffers instead of leaking them across a restart. New example:
`examples/aen/aen-isp-ov5647-viewfinder`, the portable-header counterpart to
`aen-isp-ov5647-capture` -- same OV5647 pipeline, driven entirely through
`<alp/camera.h>` instead of the raw Zephyr video API. `examples/aen/
aen-isp-regcheck` is updated to match the ISP init-order fix below.

`zephyr/drivers/video/isp_pico.c`: `video_isp_init()` previously enabled the
ISP's IRQs before `fifo_in`/`fifo_out`/`data->dev`/`lib_lock` existed. A core
reset does not reset the ISP, so an MI frame-end already latched by a
previous image could fire the instant the IRQs came on, and the frame-end
bottom half would then lock an uninitialised mutex and HardFault during
boot. IRQs are now enabled last, after that state exists, and the bottom
half ignores frame-ends while no stream is running so a stale latched
frame-end never reaches the VSI lib before `isp_configure()` runs
(bench runs 165/166).
