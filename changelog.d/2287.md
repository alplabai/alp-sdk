### Added — Sony IMX296 Zephyr sensor driver + Raspberry Pi Global Shutter Camera shield; Stage A raw capture bench-verified (#2287)

`zephyr/drivers/video/imx296.c` adds a Sony IMX296 driver for the
INNO-MAKER CAM-IMX296RAW-TRIGGER-compatible module (IMX296LQR-C colour
part), authored from the Sony IMX296 datasheet — no permissive-licence
IMX296 driver exists anywhere to consume (not in upstream Zephyr v4.4.1,
hal_alif, or Espressif esp_cam_sensor; Linux's and libcamera's are
GPL/LGPL, not consumable under this project's licence). Linux's imx296.c
was used strictly as a REGISTER-NAME reference for a handful of names this
datasheet leaves unnamed (e.g. SENSOR_INFO, `0x3148`) — no code, text or
table from it was copied into this driver. ADR-0017-ADJACENT. All-pixel
scan mode only: 1456x1088 `SRGGB10P` RAW10 (the sensor's whole transmitted
frame — 1440x1080 is the datasheet's "recording pixels" crop inside it),
**1 MIPI CSI-2 data lane** (unlike the sibling OV5647/OV9281 shields, both
2-lane), 60.3 frame/s (datasheet mode rate; not measured), 37.125/54/74.25 MHz INCK (any other frequency
rejected at runtime with `-ENOTSUP`). Controls: exposure (lines of
integration via `SHS`), analogue+digital gain (0.1 dB step via `GAIN`), H/V
flip, pixel rate (118.8 Mpix/s), link frequency (594 MHz).

The `raspberry_pi_global_shutter_camera` shield wires the sensor's 54 MHz
`fixed-clock`, CCI address 0x1A, and single-lane endpoint onto the same
board-agnostic `raspberry_pi_camera_module_2`-style label contract as its
siblings (`chosen zephyr,camera`, `&csi_interface`, `&csi_ep_in`,
`&csi_i2c`); build with
`SHIELD="<carrier-connector-shield> raspberry_pi_global_shutter_camera"`.
`examples/aen/aen-camera-firstlight` gets a matching IMX296 `#elif` +
`testcase.yaml` scenario — see `docs/camera-shields.md` for the full
driver/shield/control reference and bench-status split.

**Stage A scope, bench-verified on E1M-AEN803 2026W36-0001 (E1M-EVK,
`csi_i2c` = I2C1 @ `0x49011000`)**: I2C identity (bench run 229 — CCI
`0x1A`; `STANDBY`/`XMSTA` match datasheet POR defaults; SENSOR_INFO
register `0x3148`/`0x3149` reads `0x4A00` — **undocumented in the public
preliminary datasheet**, so treated as an opaque bench-confirmed signature
for the colour LQR variant, not a documented chip-ID register, and gates
`imx296_init()`), CSI-2 streaming, and a full 1456x1088 RAW10 frame
captured through `<alp/camera.h>` and verified against a real scene: bench
run 292 (single capture, no discard, evening light, gain 0) reads mean
pixel value 61.19, max 108, a clean close-out (no crash, no error return)
and no mod-4-column RAW10 byte-phase-slip pattern in the captured image;
its 8x8-block correlation against diag control run 293 (`SHS`=14 written
directly, same light) is 0.98. Both runs are still dim — about 1 code
above black (60) under this bench's evening light — so this confirms the
register writes and capture pipeline now agree and produce a real (if
faint) image, not yet a well-exposed one; better lighting or exposure
tuning is a follow-up. **Run 292's build had `CONFIG_LOG` unset (no log
output at all)**, so nothing about its console — clean or otherwise — says
anything about `INT_IPI_PIXEL_IF_HLINE_ERR` or
`INT_IPI_PIXEL_IF_FIFO_OVERFLOW`: their status on the product build is
UNKNOWN, not "not seen". The `37-80` per-capture and `~10.8k` HLINE_ERR
counts elsewhere in this changelog were measured in EARLIER diag runs (the
269-276-era diag-instrumented builds, and run 285's 16-frame continuous
diag run, which DID have logging), all predating the init-period-wait,
SHS, and CPI-only-pause fixes below. Continuous streaming has not been
benched on the product (non-diag, logging-enabled) build at all, so
whether HLINE_ERR/FIFO_OVERFLOW occur there, post-fix, remains open.

**NOT yet bench-verified, tracked for a later stage**: the ISP-Pico colour
path, auto-exposure, `camera-mjpeg-stream`-style continuous streaming
beyond the single-capture/starvation-paced loop `aen-camera-firstlight`
exercises, and fast-trigger mode (added below, but unverified — see its
own caveats). Whether a paused 2-lane sensor (OV5647, OV9281 — this CPI's
other sensors) can back-pressure the IPI into overflow during a longer
starvation pause is also untested.

`tests/zephyr/video_sensors` adds a real runtime ztest suite
(`imx296_test.c`) against its own I2C emulator (`imx296_emul.c`), cloning
the OV5647/OV9281 emulator+ztest shape: the SENSOR_INFO identity probe
(accept and `-ENODEV` reject paths), the STANDBY/XMSTA/init register-write
ORDER (not just final values), the exact init register values (`VMAX`
1118, `HMAX` 1100, `INCKSEL0..3`, `0x418C`, `BLKLEVEL`, ROI-disable,
`0x3005`, `SHS`/`GAIN`/`REVERSE` defaults), the one fixed format, and the
exposure/gain/flip control paths.

#### Fast-trigger exposure mode (external trigger) — added, UNVERIFIED

`imx296.c` also adds a driver-private control, `IMX296_CID_TRIGGER_MODE`
(`VIDEO_CID_PRIVATE_BASE + 0x01`, default free-run — unchanged behaviour),
switching the sensor into the datasheet's Global Shutter **Fast Trigger
Mode** (`TRIGEN` at `0x300B`, `LOWLAGTRG` at `0x30AE`, `SYNCSEL` at
`0x3036` — "Global Shutter (Fast Trigger Mode) Operation", page 64). This
is the only one of the datasheet's two trigger sub-modes this hardware can
reach: Sequential Trigger Mode is "slave mode only" (page 62) and, like
every sensor on the RPi-style 15-pin CSI connector, this module has no
XVS/XHS lines wired, so slave mode is never reachable. Trigger mode is
still MASTER mode, started by the same `XMSTA` write as free-run; only
frame output and exposure timing become XTRIG-driven afterward. The mode
switch is applied in `imx296_set_stream()`, before `STANDBY` is cancelled,
since "Mode Transitions of Global Shutter Operation" (page 66) requires
it. Setting the control while already streaming is rejected `-EBUSY`.

`examples/aen/aen-camera-firstlight` gets an opt-in `-DAEN_CAMERA_TRIGGER=ON`
CMake option (`CMakeLists.txt`, `trigger_gpio.overlay`): arms the
control and pulses a GPIO on Alif P5_1 (Arduino D4 / `EVK_PIN_CK_DIO4`,
E1M pad M2) to capture and timestamp a few frames, for the sensor module's
own opto-isolated J3 Trig+ header (on the INNO-MAKER module, not the
E1M-EVK carrier). **Trigger electrical polarity is UNVERIFIED** — the
INNO-MAKER module's J3 input circuit has not been checked against that
module's own documentation, so the DT `GPIO_ACTIVE_HIGH`/`GPIO_ACTIVE_LOW`
flag on `imx296-trigger-gpios` is a guess — **do not wire J3 until that
circuit is confirmed**. **UNTESTED ON SILICON**: both the driver's trigger
mode and this example's build mode compile clean (0 warnings) but have not
run with a trigger pulse, and the 150 ms sensor init-period wait added
below (`IMX296_INIT_PERIOD_MS`) covers free-run timing only — trigger-mode
init timing is unhandled and unbenched.

### Fixed — bring-up bugs found and fixed before Stage A shipped (#2287)

- **LP-11 clock-lane park.** `imx296_init()` leaves the sensor in STANDBY,
  and this datasheet documents no register that forces the CSI-2 CLOCK
  lane to Stop-state (LP-11) short of exiting STANDBY into full
  master-mode streaming — the same shape OV5647 hit (#2248), fixed there
  with an explicit lane-park sequence this datasheet gives no equivalent
  registers for. An earlier version of this fix made the D-PHY's
  Stop-state wait (`dphy_dw_slave_setup()`) warn-and-continue on ANY
  timeout, for every sensor; that was wrong (it would have silently
  re-opened the exact class of bug that same wait caught for OV5647,
  #2248) and is reverted. Fixed narrowly instead: `struct
  dphy_csi2_settings` gains a `skip_clk_lane_stopstate` field, set only
  from `raspberry_pi_global_shutter_camera.overlay`'s
  `no-lp11-clock-lane-park` DT property, skipping ONLY the clock-lane
  Stop-state bit for this one sensor; every data-lane bit and the wait's
  timeout stay fatal for this sensor and every other.

- **CSI-2 data lane stuck in LP-11 without a bench-derived register
  write.** Without writing register `0x3005 = 0xF0` (undocumented in the
  datasheet; bench runs #263/#264 found it by sweep, not from the
  register map) the data lane never left LP-11 at all — no HS output.
  `imx296_init()` now writes it unconditionally, documented in-code as
  bench-derived. Also added, datasheet-cited this time (pages 49, 51-52):
  `BLKLEVEL` (`0x3254`, the datasheet's recommended `0x03C`) and the
  `FID0_ROIH1ON`/`FID0_ROIV1ON` pair (`0x3300`, disabled) — the latter is
  this datasheet's actual all-pixel-vs-ROI-mode switch, written explicitly
  so a prior ROI-mode session's crop window can't leak across a warm SoC
  reset (the module stays powered across one).

- **IPI-fatal log/reset flood capped.** `video_csi_dw.c`'s `csi2_dw_irq()`
  used to `LOG_ERR` and IPI-soft-reset on every single
  `CSI_INT_ST_MAIN_IPI_FATAL` event, uncapped — with bad IPI framing this
  could fire once per line, flooding the log and storming the IPI reset
  line. It now logs only the first 16 occurrences per unmask window
  (`CSI2_DW_IPI_FATAL_LOG_LIMIT`), then masks `CSI_INT_MSK_IPI_FATAL` and
  logs one "masked after 16" line; the window resets via
  `csi2_dw_irq_on()`, which now also runs from `csi2_dw_stream_start()` on
  every user stream (re)start, not just from `csi2_dw_configure()` — so a
  mask a previous stream left set no longer hides every fatal on the next
  one. A separate, never-reset `ipi_fatal_total` field keeps the lifetime
  count for diagnostics.

- **Runtime `CSI_IPI_SOFTRSTN` toggle removed from the IPI-fatal ISR.**
  Bench run 271 (product image), WITH the runtime toggle present, panicked
  at buffer close: the CPI's DMA wrote ~2744 bytes past a 3,168,256-byte
  frame buffer's end, corrupting the next heap chunk header
  (`sys_heap_free()`'s hardening check caught it). Bench runs 272-276,
  WITHOUT the toggle, all completed capture+close with no panic — 1
  overrun in 1 run with the toggle vs. 0 in 5 without it: a correlation,
  not a confirmed mechanism (run 271's own logging was disabled, so which
  IPI-fatal event fired that run is unknown). `csi2_dw_irq()` no longer
  soft-resets `CSI_IPI_SOFTRSTN` on any fatal event, matching the vendored
  Alif DFP reference's own IPI-fatal handler, which never resets IPI at
  runtime either. This hazard is not IMX296-specific in principle —
  OV5647/OV9281 use the same zero-slack frame buffers and are **likely
  exposed** but this has **not been bench-reproduced** on either.

- **DW CSI-2 IPI switched to Controller timing mode.** The host's default
  "Camera" IPI mode derives its line timing from the D-PHY clock and
  emitted **no** IPI lines at all for this 1-lane sensor on silicon.
  `raspberry_pi_global_shutter_camera.overlay` now switches the `&csi`
  controller to IPI **Controller** timing mode with fixed
  `csi-hsa`/`csi-hbp`/`csi-hsd`/`csi-vsa`/`csi-vbp`/`csi-vfp` timings
  derived from this sensor's own `HMAX`/`VMAX` (HSD bench sweep: 503 gives
  zero IPI-FIFO overflow; 520 and 531 both overflowed and banded the
  frame). These `ipi-mode`/timing properties live on the `&csi` controller
  node itself, not a per-sensor endpoint, so they apply to whatever sensor
  is stacked on this controller, not IMX296 specifically -- today only one
  sensor is ever wired to a given `&csi` controller, so this is a
  scope note, not a live conflict. `csi2_dw_validate_data()` also drops
  its usual 20% bandwidth margin on the CSI IPI pixel-clock request in
  Controller mode: that margin exists to keep the IPI ahead of the sensor
  in Camera mode, where HSD is *derived from* the resulting clock; in
  Controller mode the DT timings *set* the drain rate instead, and the
  margined request picked a different, starving clock divisor (bare
  request → divisor 3, 133.33 MHz, matching the overlay's derivation;
  margined request → divisor 2, 200 MHz -- **calculated from the
  clock-control divisor rule, not independently bench-measured with a
  scope/analyzer; the margined request was never actually made on the
  bench** (the fix removes it before any hardware run). This is what took
  the capture path from "emits no IPI line at all" to full 1456x1088
  frames. `csi2_dw_validate_data()` also gained a `LOG_INF` (on every
  `set_format`, Controller mode only) reporting the pixel clock actually
  programmed, the DT-fixed `HLINE`, and the line time they work out to --
  so a future clock-control divisor change that silently invalidates this
  overlay's HSD derivation shows up in the log instead of only as a
  re-appeared FIFO overflow.

- **Buffer-starvation pause STANDBY-cycled the sensor on every frame.**
  The starvation pause (`alif_cam_work_helper()`) and its resume
  (`alif_cam_enqueue()`) used to call `video_stream_stop()`/`_start()` on
  the CSI-2 endpoint, driving the sensor into STANDBY on every pause and
  back to RUN on every resume — a full standby-to-run cycle per frame with
  a one-buffer capture/release loop. The datasheet's 8-frame
  initialization period after STANDBY cancel (below) made this worse: the
  kept frame was always still ramping up. Diag run 285 (predating the
  init-period-wait fix below) also showed a RAW10 4-column byte-phase-slip
  pattern with the old endpoint-cycling behaviour, SUSPECTED (not
  confirmed) to be the CPI's frame-boundary tracking desyncing from the
  CSI-2 IPI stream on each endpoint restart. Fixed: the pause now stops
  only the CPI capture engine (`hw_cam_cpi_only_stop()` — `CAM_CTRL` stop,
  `BUSY` poll, soft reset, clear latched interrupts, the same steps
  `alif_cam_stream_stop()` applies to the CPI side of its own teardown)
  and leaves the CSI-2 endpoint and sensor streaming across the stall; the
  resume path restarts only the CPI. A user `stop()`/`close()` is
  unaffected — `alif_cam_stream_stop()` still calls `video_stream_stop()`
  on the endpoint unconditionally, the only stop that ever reaches it
  while a starvation pause is in effect. While paused, the sensor, D-PHY
  and CSI-2 host keep running (and drawing power); frames the sensor sends
  during the pause are simply dropped at the stopped CPI. `hw_cam_cpi_only_stop()`
  lives in the shared CPI driver (`video_alif.c`), so this behaviour change
  applies to OV5647 and OV9281 too, not just IMX296 -- but it is
  bench-verified on IMX296 only; whether a paused 2-lane sensor can
  back-pressure the IPI into overflow during a longer pause is untested,
  and re-bench on OV5647/OV9281 is pending.

- **First frame after every stream start was inside the 8-frame init
  period.** "Standby mode" (datasheet p54): a normal image is output only
  from the 9th frame after STANDBY cancel. `imx296_set_stream(dev, true,
  ...)` used to return as soon as the `XMSTA` write started master-mode
  free-run, so the CPI's own capture-snapshot arm
  (`alif_cam_stream_start()` → `hw_cam_start_video_capture()`, called
  immediately once the sensor's `set_stream` returns all the way back up
  through `csi2_dw_stream_start()`) could land inside that init period.
  Fixed in the sensor driver, not the apps that tripped over it:
  `imx296_set_stream()` now blocks for `IMX296_INIT_PERIOD_MS` (150 ms, 9
  frames of margin over the 132 ms the 8-frame period works out to at
  `IMX296_VMAX` x 1H = 1118 x 14.81us, p44/p53) after the `XMSTA` write,
  before returning — free-run mode only (see the trigger-mode caveat
  above).

- **SHS init-write bug: an accidental 14-line exposure.**
  `imx296_init()`'s hardware-defaults write wrote `IMX296_REG_SHS =
  IMX296_VMAX - IMX296_SHS_DEFAULT` (1104), wrongly applying the
  exposure-lines-to-SHS conversion `imx296_set_ctrl()` uses for control
  values. SHS is the shutter START line, not exposure lines
  ("Calculation Formula of Exposure Time", page 60): the register value
  should be `IMX296_SHS_DEFAULT` (14) itself, giving the intended
  1104-line exposure — not `IMX296_VMAX` minus it. The wrong write put
  SHS=1104 in hardware, a 14-line (~0.2 ms) exposure instead of 1104
  lines — this, not "no light reaching the array", is why every product
  capture before this fix read flat black (mean pixel value 60.15,
  bench runs 288/291): `imx296_set_ctrl()`'s own conversion was already
  correct and is unchanged. Fixed to write `IMX296_SHS_DEFAULT` directly.
  `test_shs_gain_reverse_defaults_written_at_init` asserted the old,
  wrong register value; it now asserts the correct one. Confirmed fixed
  together with the init-period-wait fix above by bench run 292 (see the
  Stage A summary above).

`tests/zephyr/video_sensors` only emulates the IMX296 sensor over I2C/CCI
and never instantiates `video_csi_dw.c` or a clock-control device, so
there is no native_sim harness the DW CSI-2 IPI-timing-mode change above
can be asserted against; no test was added for it.

### Added — IMX296 ROI mode (1280x960) + DW CSI-2 controller-timing that follows any format; bench-verified (#2287, Stage B)

`zephyr/drivers/video/imx296.c` gains a second `video_format_cap`: a
centred 1280x960 `SRGGB10P` crop within the same 1456x1088 full-pixel
array, alongside the existing full-frame mode (`video_set_format()` now
accepts either). "ROI mode" / "Register List of ROI mode" / "Restrictions
on ROI mode" (Sony IMX296 datasheet pp.51-53): `FID0_ROIH1ON`/`ROIV1ON`
(`0x3300`, bit0/bit1) enable the crop; `FID0_ROIPH1`/`ROIPV1`/`ROIWH1`/
`ROIWV1` (`0x3310`/`0x3312`/`0x3314`/`0x3316`, all 16-bit LE) set its
position (88, 64 — centred, both already a multiple of 4) and size (1280,
960 — 1280 ≥ the 80-pixel minimum, 960 ≥ the 4-line minimum, both
multiples of 4). `VMAX` stays the driver's fixed 1118 for both modes
(unchanged by this change) — the datasheet's ROI frame-rate floor is
`VMAX ≥ ROIWV1 + 30 = 990`, so 1118 clears it with margin and the crop
keeps the same 60.3 frame/s the full-frame mode already has, not a
faster rate. `imx296_set_stream()` now writes the position/size registers
and the enable bits (or the disable value, unchanged behaviour) every
stream start, reading back whatever format `video_set_format()` last
selected — full-frame mode is unaffected (still writes `ROI_ENABLE`
disable, now explicitly on every start rather than only once at boot).
Emulator coverage added to `tests/zephyr/video_sensors/src/imx296_test.c`:
`format_caps` now lists both modes, the ROI registers are asserted written
for the 1280x960 format, `ROI_ENABLE` is asserted disabled for the
1456x1088 format, and a size between the two fixed modes is asserted
rejected (`-ENOTSUP`).

`zephyr/drivers/video/video_csi_dw.c` gains two optional DT properties on
the DW CSI-2 IPI controller node, `csi-hline` and `csi-vtotal`
(`zephyr/dts/bindings/video/snps,designware-csi.yaml`): when both are set,
`csi2_dw_validate_data()` DERIVES `hsd`/`vfp` from them and the CURRENTLY
selected format's `hact`/`vact` (`hsd = csi-hline - hsa - hbp - hact`,
`vfp = csi-vtotal - vsa - vbp - vact`, rejecting a negative result with
`-EINVAL`) instead of reading a fixed `csi-hsd`/`csi-vfp` DT value. A fixed
`csi-hsd` is only ever correct for the one `hact` it was bench-swept
against — with IMX296 now offering a second, narrower ROI mode, the fixed
`503` the shield overlay carried would make a 1280-wide capture's IPI line
9% shorter than the sensor's own line time, starving the IPI rather than
draining it. `raspberry_pi_global_shutter_camera.overlay` now sets
`csi-hline = <1972>` and `csi-vtotal = <1118>` in place of the fixed
`csi-hsd = <503>` / `csi-vfp = <25>` it used to carry; the overlay's own
comment re-derives both full-frame values from the new formula —
`hsd = 1972 - 3 - 10 - 1456 = 503`, `vfp = 1118 - 1 - 4 - 1088 = 25` —
and they land EXACTLY on the bench-swept fixed values Stage A verified, so
this change is not expected to alter full-frame behaviour on real
silicon. Boards that don't set `csi-hline`/`csi-vtotal` keep the old fixed
`csi-hsd`/`csi-vfp` code path byte-for-byte. As with the Stage A DW CSI-2
change above, `tests/zephyr/video_sensors` has no `video_csi_dw.c` /
clock-control harness to assert this derivation against; no test was
added for it.

`examples/aen/aen-camera-firstlight` gains an opt-in
`-DAEN_CAMERA_IMX296_ROI=ON` CMake option (default `OFF`, unchanged
1456x1088 full-frame build otherwise) selecting the 1280x960 ROI crop, plus
a matching `build_only` `testcase.yaml` scenario
(`camera_firstlight.imx296_roi`).

**Bench-verified, runs 294/295 (E1M-AEN803 2026W36-0001, logging on,
commit `25d992bd4`)**: run 294 (full-frame, unchanged mode) captured a
clean 3,168,256-byte frame; run 295 (1280x960 ROI) captured a clean
2,457,600-byte frame — both capture and close without error. Run 295's
frame matches an 88,64-offset crop of run 294's (8x8-block correlation
0.91), confirming `IMX296_ROI_POS_H`/`POS_V` (88/64) land where derived,
not just that the driver builds. Neither frame shows the mod-4-column
RAW10 byte-phase-slip pattern Stage A's bring-up used as its own
CSI-2-desync tell (both runs were dim, evening light, gain 0 — expected,
not itself evidence of anything wrong). Console (both runs): `"CSI IPI
Controller-mode: pixclk 133333333 Hz, HLINE 1972 px -> line time 14790
ns"`, matching `raspberry_pi_global_shutter_camera.overlay`'s own
`csi-hline`/`csi-vtotal` derivation exactly. The console ALSO shows 16x
`"Fatal Interrupt at IPI interface. status - 0x10"` (`HLINE_ERR`, per
`video_csi_dw.h`) during `open`/`start`, then `"IPI fatal interrupts
masked after 16"` — `HLINE_ERR` DOES fire at stream start on the product
build, on both the unchanged full-frame mode and the new ROI mode (so
this is not new to Stage B); the count after masking is UNKNOWN
(`csi2_dw_irq()`'s `CSI2_DW_IPI_FATAL_LOG_LIMIT` masking, `video_csi_dw.c`,
stops logging past 16 events — see that mechanism's own comment). Both
frames still arrived clean despite these transient start-of-stream
errors — root cause not yet investigated, filed as a follow-up, not a
regression this Stage B change introduced (Stage A's own runs never had
`CONFIG_LOG` on to have shown it either way, see the Stage A summary
above).

Reviewer-minor follow-up in this same commit-in-progress: `hsd`/`vfp`
now also rejected with `-EINVAL` if they exceed `CSI_IPI_HSD_TIME_MASK`/
`CSI_IPI_VFP_LINES_MASK` (12/10 bits) — `csi2_dw_ipi_set_timings()`'s
register write already masked silently, which would have truncated an
out-of-range derived value into a wrong in-range one instead of failing.
A `BUILD_ASSERT` in `ALIF_MIPI_CSI_DEVICE()` now catches `csi-hline` set
without `csi-vtotal` (or vice versa) at compile time; it does NOT also
assert the fixed `csi-hsd`/`csi-vfp` properties are absent when
`csi-hline`/`csi-vtotal` are set, because `ensemble_e8_peripherals.dtsi`'s
shared `&csi` node sets both unconditionally for every board — that
assertion would fail-build this very shield.
`IMX296_ROI_WIDTH`/`HEIGHT`'s own comment in `imx296.c` now also notes
that keeping `VMAX` at 1118 rather than dropping to the datasheet's
`ROIWV1 + 30 = 990` floor was originally an inference, now confirmed by
run 295. `imx296_set_stream()`'s ROI-write comment now also cites page
51's "one invalid frame when the ROI area changes" note and explains why
`IMX296_INIT_PERIOD_MS`'s existing wait already covers it (every
format switch goes through a stop/change-format/start sequence with the
sensor in STANDBY, never a live switch while streaming).

### Added — IMX296 SRGGB10P through the ISP-Pico pipeline; NOT YET BENCH-VERIFIED (#2287, Stage B)

`zephyr/drivers/video/isp_pico.c`'s `supported_input_fmts[]` (the ISP
driver's own INPUT format gate) gains a `VIDEO_PIX_FMT_SRGGB10P` entry —
the fourcc IMX296's driver (`zephyr/drivers/video/imx296.c`) advertises for
its one fixed all-pixel mode and its new ROI crop alike. Without this
entry `find_format()` rejected the fourcc with `-ENOTSUP` before the ISP
ever saw it, the same gap `VIDEO_PIX_FMT_SBGGR10P` had for OV5647 before
this branch's earlier bring-up added it. `bayer_sample_depth()` (also in
`isp_pico.c`) already had a `VIDEO_PIX_FMT_SRGGB10P` case (10-bit
`PIN_MAPPING`) predating this change — only the input-format cap entry was
missing.

`src/backends/camera/alif_isp_pico.c`'s `ALIF_ISP_INPUT_FOURCC` — until now
a single fixed `VIDEO_PIX_FMT_SBGGR10P` for the OV5647 board this backend
was bench-proven against — is now a compile-time choice:
`DT_HAS_COMPAT_STATUS_OKAY(sony_imx296) ? VIDEO_PIX_FMT_SRGGB10P :
VIDEO_PIX_FMT_SBGGR10P`. Deliberately NOT a runtime `video_get_format()`
probe of the ISP input device: that call is a `alif_cam_set_fmt()`
(`video_alif.c`) SIDE EFFECT, and that call fails outright at IMX296's
