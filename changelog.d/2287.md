### Added — Sony IMX296 Zephyr sensor driver + Raspberry Pi Global Shutter Camera shield, I2C identity silicon-confirmed (#2287)

`zephyr/drivers/video/imx296.c` adds a Sony IMX296 driver for the
INNO-MAKER CAM-IMX296RAW-TRIGGER-compatible module (IMX296LQR-C colour
part), authored from the Sony IMX296 datasheet — no permissive-licence
IMX296 driver exists anywhere to consume (not in upstream Zephyr v4.4.1,
hal_alif, or Espressif esp_cam_sensor; Linux's and libcamera's are
GPL/LGPL, not consumable under this project's licence). Linux's imx296.c
was used strictly as a REGISTER-NAME reference for a handful of names this
datasheet leaves unnamed (e.g. SENSOR_INFO, `0x3148`) — no code, text or
table from it was copied into this driver. ADR-0017-ADJACENT. All-pixel
scan mode only: 1456x1088 `SRGGB10P` RAW10 (the sensor's whole transmitted
frame — 1440x1080 is the datasheet's "recording pixels" crop inside it),
**1 MIPI CSI-2 data lane** (unlike the sibling OV5647/OV9281 shields, both
2-lane), 60.3 frame/s, 37.125/54/74.25 MHz INCK (any other frequency
rejected at runtime with `-ENOTSUP`). Controls: exposure (lines of
integration via `SHS`), analogue+digital gain (0.1 dB step via `GAIN`), H/V
flip, pixel rate (118.8 Mpix/s), link frequency (594 MHz).

**Silicon-confirmed, issue #2287 bench run 229 (an E1M-AEN803
2026W36-0001 on the E1M-EVK, `csi_i2c` = I2C1 @ `0x49011000`): I2C identity
only.** The module answers at CCI `0x1A`; `STANDBY`/`XMSTA` match datasheet
POR defaults at reset; after cancelling standby, the SENSOR_INFO register
(`0x3148`/`0x3149`, 16-bit little-endian) reads `0x4A00` — this register is
**undocumented in the public preliminary datasheet** (its whole I2C bank is
listed as "refer to the other register map file"), so the driver's new
identity check treats the value as an opaque bench-confirmed signature for
the colour LQR variant rather than a documented, bit-decoded chip-ID
register, and gates `imx296_init()` on it. CSI-2 streaming (mode-register
programming, D-PHY lock, a captured frame) has **not** run on this silicon
yet; the driver's advertised Bayer order (`SRGGB10P`) remains a
datasheet-derived claim, not a bench-confirmed one.

The `raspberry_pi_global_shutter_camera` shield wires the sensor's 54 MHz
`fixed-clock`, CCI address 0x1A, and single-lane endpoint onto the same
board-agnostic `raspberry_pi_camera_module_2`-style label contract as its
siblings (`chosen zephyr,camera`, `&csi_interface`, `&csi_ep_in`,
`&csi_i2c`); build with
`SHIELD="<carrier-connector-shield> raspberry_pi_global_shutter_camera"`.

`tests/zephyr/video_sensors` adds a real runtime ztest (`imx296_test.c`)
against its own I2C emulator (`imx296_emul.c`), cloning the OV5647/OV9281
emulator+ztest shape: the SENSOR_INFO identity probe, the
STANDBY/XMSTA start/stop register-write ORDER (not just final values), the
one fixed format, and the exposure/gain/flip control paths.
`examples/aen/aen-camera-firstlight` gets a matching IMX296 `#elif` +
`testcase.yaml` scenario (build-only — see `docs/camera-shields.md` for the
full driver/shield/control reference and honest bench-status split).

This resumes the driver preserved on `feat/imx296-rpi-gs-camera-unbenched`
(issue #2253) with a module now seated; the mono IMX296LLR variant, trigger
mode, and the ISP colour path remain tracked separately.

### Fixed — IMX296 never parks LP-11; give it its own narrow D-PHY opt-out instead of weakening the Stop-state wait for every sensor (#2287)

`imx296_init()` leaves the sensor in STANDBY (no MIPI output at all), and
this datasheet documents no register that forces the CSI-2 CLOCK lane to
Stop-state (LP-11) short of exiting STANDBY into full master-mode
streaming — the same shape OV5647 hit (issue #2248), fixed there with an
explicit lane-park sequence (`zephyr/drivers/video/ov5647.c`,
`ov5647_lane_park()`) this datasheet gives no equivalent registers for. **This
is an inference from the datasheet and this driver's own init() ordering,
not a bench measurement of the D-PHY's Stop-state register during
STANDBY.**

An earlier version of this fix made `dphy_dw_slave_setup()`'s Stop-state
wait (`zephyr/drivers/mipi_dphy/dphy_dw.c`) warn-and-continue on ANY
timeout, for every sensor — that change is reverted here. It was wrong on
two counts: it also justified itself by claiming OV5647 "already shows a
mismatched STOPSTATE on silicon while capturing fine", which is not
supported — `ov5647_lane_park()`'s own bench evidence (issue #2248, bench
run 52) records `CSI_PHY_STOPSTATE` reading `0x00010003`, exactly the
mask this wait wants, not a mismatch. And a global timeout-tolerant D-PHY
is the fatal check that caught OV5647's own real silicon defect (#2248) in
the first place; weakening it for every sensor would have silently
re-opened that class of bug for OV5647, OV9281, and any future sensor.

Fixed narrowly instead: `struct dphy_csi2_settings` gains a
`skip_clk_lane_stopstate` field, set from a new DT bool property on the
SENSOR's own CSI-2 endpoint, `no-lp11-clock-lane-park`
(`zephyr/dts/bindings/video/sony,imx296.yaml`), set only in
`raspberry_pi_global_shutter_camera.overlay`. When set, the Stop-state wait
skips ONLY the clock-lane bit (`CSI_PHY_STOPSTATE_PHY_STOPSTATECLK`,
`BIT(16)`) for that one sensor; every data-lane Stop-state bit, and the
wait's timeout, stay fatal — for this sensor and every other, OV5647
included.

On a later bench pass (issue #2287, same E1M-AEN803/E1M-EVK silicon as
bench run 229's I2C-identity pass), with this opt-out in place, the sensor
streams: the CSI-2 host's frame counter advances once `XMSTA` starts
master-mode free-run. **No frame has been captured yet — the Alif IPI
emits no line.** Whether the opt-out is what let streaming start, versus
some other factor, is NOT independently isolated on this silicon; treat
every register value in this driver, and the capture path end to end, as
unproven past "the frame counter moves".

Also in this pass: `imx296_init()` now writes the `SHS`/`GAIN`/`REVERSE`
defaults to hardware (previously only the video-control-registry cache got
defaults, which could silently disagree with a sensor left running its
prior session's values across a warm SoC reset); the `GAIN` register
comment now states explicitly that it is exposed as the single combined
`VIDEO_CID_ANALOGUE_GAIN` control, with no separate digital-gain control to
split it against; and `tests/zephyr/video_sensors/src/imx296_test.c` gains
coverage for the SENSOR_INFO mismatch → `-ENODEV` path, the
init quiesce-then-reprogram register order (exit standby → read
SENSOR_INFO → re-park before `VMAX`/`HMAX`/`INCKSEL`), the exact init
register values (`VMAX` 1118, `HMAX` 1100, `INCKSEL0..3` =
`0xB0`/`0x0F`/`0xB0`/`0x0C`, `0x418C` = `0xA8` at 54 MHz), and the new
`SHS`/`GAIN`/`REVERSE` default writes.

### Fixed — IMX296 CSI-2 data lane stays in LP-11 without a bench-derived register write; datasheet-cited init registers added; IPI-fatal log/reset flood capped (#2287)

Further bench passes (issue #2287, same E1M-AEN803 2026W36-0001 silicon,
colour IMX296LQR-C module) isolated the data lane specifically: without
writing register `0x3005` (Chip ID = 02h's own register map documents
`0x3000` then jumps to `0x3008` — `0x3005` falls in the undocumented
"refer to the other register map file" gap, same category as
`SENSOR_INFO`) the CSI-2 data lane never leaves LP-11 at all — no HS
output whatsoever. Writing `0x3005 = 0xF0` (bench runs #263/#264) makes HS
data arrive at the CSI-2 host; whether `0xF0` selects some diagnostic mode
versus normal operation is not established (`0x3005` is undocumented in
the datasheet). **At this point in the bench log the Alif IPI still emitted
no line with HS data flowing** — see the later entry below in this same
file for the fix (the DW CSI-2 host's IPI timing mode, not this register).
`imx296_init()` now writes `0x3005 = 0xF0` unconditionally, documented
in-code as bench-derived (no datasheet coverage), not a documented
register write.

Also added, all datasheet-cited (Sony IMX296 datasheet "Register List of
All-pixel scan mode", page 49, and "Register List of ROI mode" /
"Restrictions on ROI mode", pages 51-52 — both previously read but not
fully acted on): `BLKLEVEL` (`0x3254`, black-level offset, the
datasheet's own "Recommended value" `0x03C`) and `FID0_ROIH1ON`/
`FID0_ROIV1ON` (`0x3300`, disabled/`0x00`) are now written explicitly in
`imx296_init()`. The `0x3300` pair is this datasheet's actual
all-pixel-scan-mode-vs-ROI-mode switch (no separate `0x300D` "window
mode" register is documented anywhere in this datasheet — `0x300C`/
`0x300D` fall in the same undocumented gap as `0x3005` above); writing it
explicitly to "disabled" prevents a previous ROI-mode session's cropping
window from leaking into this driver's fixed all-pixel output across a
warm SoC reset (the module stays powered across one).
`tests/zephyr/video_sensors/src/imx296_test.c` gains coverage asserting
all three writes land, in the correct standby-parked ordering.

`zephyr/drivers/video/video_csi_dw.c`'s `csi2_dw_irq()` previously
`LOG_ERR`'d and IPI-soft-reset on every single `CSI_INT_ST_MAIN_IPI_FATAL`
event uncapped — with a sensor emitting bad IPI framing this can fire once
per line, flooding the log and storming the IPI reset line. It now logs
only the first 16 occurrences per unmask window
(`CSI2_DW_IPI_FATAL_LOG_LIMIT`, `video_csi_dw.h`), then masks
`CSI_INT_MSK_IPI_FATAL` and logs one "IPI fatal interrupts masked after
16" line; the per-window count (`csi2_dw_data.ipi_fatal_count`) resets on
the next `csi2_dw_irq_on()`, which now runs from `csi2_dw_stream_start()`
on every stream (re)start as well as from `csi2_dw_configure()` — so a
mask a previous, unrelated stream left set no longer silently hides every
fatal on a later one. A separate, never-reset `ipi_fatal_total` field
keeps the lifetime count for diagnostics.

### Fixed — runtime `CSI_IPI_SOFTRSTN` toggle in the IPI-fatal ISR removed; correlated with a frame-buffer overrun and heap corruption, mechanism unconfirmed (#2287)

Bench run 271 (product image, E1M-AEN803 2026W36-0001), WITH the runtime
`CSI_IPI_SOFTRSTN` toggle present, panicked at buffer close: the Alif
CPI's DMA wrote ~2744 bytes past a 3,168,256-byte frame buffer's end
(`0x02305880`) — measured, and less than one 2912-byte frame row —
corrupting the next `sys_heap` chunk header; `sys_heap_free()`'s
hardening check caught it at release. Bench runs 272-276, WITHOUT the
toggle (same HSD 503 timing), all 5 completed capture+close with no
panic; a 4 KiB `0xA5` guard fill placed past the buffer end showed only
16 bytes changed, identical every run — consistent with ordinary heap
bookkeeping, not a pixel-data overrun. That is **1 overrun in 1 run with
the toggle present vs. 0 overruns in 5 runs without it: a correlation,
not a confirmed mechanism**. The suspected explanation — the CPI gates
its write on HSYNC only (`VSYNC_EN=0`), so soft-resetting IPI while the
CPI is BUSY mid-frame cuts a line and makes the CPI write one row LATE,
past the buffer's configured (`FCFG`) row count — is **not independently
confirmed**: run 271's own logging was disabled, so which specific IPI
fatal event fired that run is unknown. Earlier diagnostic runs at the
same HSD 503 timing (logging enabled) recorded IPI status `0x10` (bit 4,
HLINE error) 37-80 times per capture and one frame-sync error, but
**zero FIFO-overflow (bit 1) events** — the failure this toggle was
originally meant to recover from was not observed firing in those runs
either. The vendored Alif DFP reference (`Driver_MIPI_CSI2.c`'s
IPI-fatal handler) never soft-resets IPI at runtime regardless — it only
reads status and reports the event — which is the practice this change
matches independent of the exact mechanism above.

`csi2_dw_irq()` (`zephyr/drivers/video/video_csi_dw.c`) no longer
soft-resets `CSI_IPI_SOFTRSTN` on any fatal event; it keeps the capped,
log-only `LOG_ERR` + count + mask behaviour from the entry above (no
separate diagnostic-dump API surfaces `ipi_fatal_total` — it is only
printed inline in the "masked after N" log line). Recovery for a
genuinely wedged IPI is now stream-level (stop then start re-arms via
`csi2_dw_irq_on()`) rather than a register poke mid-frame, but that this
actually un-wedges a stuck IPI is **not itself bench-verified** — it is
simply the only recovery path left once the runtime reset is gone. This
hazard is not IMX296-specific in principle: OV5647/OV9281 use the same
zero-slack frame buffers and are **likely exposed** to the same latent
overrun, but that has **not been bench-reproduced** on either sensor. No
frame-buffer padding was added as a band-aid.

### Fixed — IMX296 capture path uses DW CSI-2 IPI Controller-timing mode; the earlier "IPI emits no line" failure is resolved (#2287)

The DW CSI-2 host's default "Camera" IPI mode derives its line timing from
the D-PHY clock and emitted **no** IPI lines at all for this 1-lane sensor
on silicon (see the entry above). `raspberry_pi_global_shutter_camera.overlay`
now switches the `&csi` controller to IPI **Controller** timing mode
(`ipi-mode = "Controller"`) with fixed `csi-hsa`/`csi-hbp`/`csi-hsd`/
`csi-vsa`/`csi-vbp`/`csi-vfp` timings derived from this sensor's own
`HMAX`/`VMAX` — see the overlay's own comment for the full derivation and
the HSD bench sweep (503 gives zero IPI-FIFO overflow; 520 and 531 both
overflowed and banded the frame).

`zephyr/drivers/video/video_csi_dw.c`'s `csi2_dw_validate_data()` also
drops its usual 20% bandwidth margin when requesting the CSI IPI pixel
clock in Controller mode: that margin exists to keep the IPI ahead of the
sensor in Camera mode, where HSD is *derived from* the resulting clock:
in Controller mode the causality is reversed, the DT timings *set* the
drain rate, and the margined request lands on a different, wrong clock
divisor (bench: bare request → divisor 3, 133.33 MHz, matching the
overlay's derivation; margined request → divisor 2, 200 MHz, which starves
the IPI against the sensor instead).

With this fix, the capture path is measurably improved on E1M-AEN803
2026W36-0001, though not clean: full 1456x1088 frames are captured, and
**zero IPI-FIFO-overflow (status bit 1) events** were logged at this
timing — but IPI status `0x10` (bit 4, HLINE error) still fires 37-80
times per capture, plus one frame-sync error per capture, both still
present at HSD 503. Which specific IPI-fatal event fired during bench run
271 (see the entry above) is unknown, because logging was disabled in
that build. **Scene content has not been verified** — every frame
captured so far, at maximum exposure and gain, shows flat noise around
the sensor's black level, consistent with (but not proof of) no light
reaching the array; optics/lighting have not yet been set up on this
bench. Do not read this fix as "the camera produces a real image", or
even as "IPI framing is now clean" — read it as "the capture pipeline no
longer fails to emit lines at all, and the FIFO-overflow failure mode
specifically is not observed at this timing"; the HLINE/frame-sync errors
remain open.

`tests/zephyr/video_sensors` only emulates the IMX296 sensor over I2C/CCI
and never instantiates `video_csi_dw.c` or a clock-control device, so
there is no native_sim harness this DW CSI-2 host / IPI-timing change can
be asserted against; no test was added for it.
