### Fixed — `alp_display_config_t.allow_modeset` read as an unconditional promise the MCU backends do not keep (#1648 tier 2)

`include/alp/display.h`'s doxygen for `allow_modeset` states that
`alp_display_open` "returns `ALP_ERR_INVAL` unless the caller sets this
explicitly". Only the Yocto/Linux backend enforces that: the identifier appears
nowhere in `src/backends/display/zephyr_drv.c` or
`src/backends/display/zephyr_stub.c`, so a default-constructed config that is
refused on A55 opens normally on M55/M33. A customer reading the header on a
Zephyr target expects a refusal that never arrives.

The behaviour is correct; the documentation was not. The whole rationale in that
comment is KMS-specific -- the SDK becomes DRM master and issues
`DRM_IOCTL_MODE_SETCRTC`, and the kernel does not refuse when master is merely
unheld, so opening a display can silently take over an idle framebuffer console
or a VT-switched session. None of that exists on a Zephyr backend, which drives a
dedicated panel it already owns: there is no master to take and no session to
displace, so there is nothing for the flag to protect. Now stated as
Yocto-only, the same way `alp_storage_config_t.allow_unsafe_write` already
documents its own scope with "(ignored elsewhere)".

**Deliberately NOT changed: `allow_unsafe_write`.** #1648 tier 2 lists it as the
same defect, but it is not one -- `include/alp/storage.h` already documents it as
Yocto-only, and the asymmetry is load-bearing. On Linux
`/dev/mmcblk<N>` is the whole-disk node carrying GPT/MBR and the bootloader, and
on some boards `/dev/mtd0` IS the bootloader/FIP partition, so a defaulted config
must not be able to write. A Zephyr backend addresses a dedicated flash
partition, where writing is the ordinary intended operation. Making the Zephyr
backends "honour" the flag would refuse writes by default on every MCU target and
break every existing storage caller -- a regression dressed as a consistency fix.

Documentation only; no behaviour change and no ABI change (the snapshot
regenerates clean).

### Fixed — three portable config fields were accepted, never applied, and returned `ALP_OK` (#1648 tier 1)

`alp_audio_out_set_volume()` on a handle opened `ALP_AUDIO_FMT_S24_LE` / `ALP_AUDIO_FMT_S32_LE`
recorded the requested volume and returned `ALP_OK`, but both the Yocto/ALSA
(`src/backends/audio/yocto_drv.c`) and Zephyr/I2S (`src/backends/audio/zephyr_drv.c`) backends can
only software-scale `ALP_AUDIO_FMT_S16_LE` — so the handle kept playing at full scale regardless
of what the caller asked for, with no error anywhere. Both backends now refuse a non-unity volume
on a format they can't scale with `ALP_ERR_NOSUPPORT` at the `out_set_volume` entry point
(`src/backends/audio/yocto_drv.c:750`, `src/backends/audio/zephyr_drv.c:562`); setting 255
(full-scale, always a no-op) still succeeds on every format.

`src/backends/audio/yocto_drv.c`'s `configure_pcm()` also kept only the return code from
`snd_pcm_hw_params_set_rate_near()` / `snd_pcm_hw_params_set_period_size_near()`, discarding the
rate/period ALSA actually negotiated. Asking for a rate or period the device doesn't support used
to `open()` successfully while silently playing at the wrong speed; `configure_pcm()` now compares
the negotiated value against the request and fails `open()` with `ALP_ERR_NOSUPPORT` on a mismatch,
logging both numbers (`src/backends/audio/yocto_drv.c:289-294`, `:300-305`).

The ADC oversampling backends (`src/backends/adc/alif_e7.c`, `alif_e8.c`) converted the portable
`oversampling_ratio` (a RATIO) to Zephyr's `adc_sequence.oversampling` (a log2 EXPONENT) via
`__builtin_ctz()`, which silently rounds a non-power-of-two ratio down instead of failing — e.g. a
requested 3x or 6x both landed on 1x / 2x, `ALP_OK` either way. Both now refuse a non-power-of-two
ratio with `ALP_ERR_NOSUPPORT` before `__builtin_ctz()` ever runs, via the shared
`alp_adc_oversampling_ratio_ok()` guard (`src/backends/adc/alif_e8.c:171`,
`src/backends/adc/alif_e7.c:158`). The portable Zephyr ADC backend
(`src/backends/adc/zephyr_drv.c`) hardcoded `.oversampling = 0`, dropping the field entirely for
every vendor driver it might run against; it now refuses any ratio greater than 1x with
`ALP_ERR_NOSUPPORT` (`src/backends/adc/zephyr_drv.c:155`) rather than honouring a log2 mapping this
generic, multi-vendor backend has no single driver contract to trust.

No new capability was added: every one of the three families becomes an honest
`ALP_ERR_NOSUPPORT` refusal in place of the previous silent wrong answer, per ADR-0002.
