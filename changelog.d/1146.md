### Fixed — `alp-mcp`'s `peripheral_support` tool read a silicon fact as a support claim (#1146)

`metadata/catalog.json`'s `soms[N].soc_peripherals` map is documented (`scripts/gen_catalog.py`,
#1243) as a literal silicon projection, not "does `<alp/CLASS.h>` work on this SKU" — and
correctly so. `scripts/alp_mcp/server.py`'s `peripheral_support()` MCP tool read that same map
one hop downstream and returned it under keys literally named `supported` / `supported_by`, with
no caveat, in all three of its response modes. An agent asking "does E1M-V2N101 support CAN"
got `can: true` uncaveated, while `alp_can_open()` returns `ALP_ERR_NOT_READY` on every channel:
no CANFD devicetree node exists for V2N/V2M on either core (#1146's own body; see also #914 for
the AEN-side equivalent).

The V2N/V2M SoC (`renesas:rzv2n:n44`, `metadata/socs/renesas/rzv2n/n44.json:67`) integrates 6
CAN-FD controllers in silicon, but the E1M-X V2N module bonds out only **2** of them —
CANFD2 (`CRX2`→`P85`, `CTX2`→`P84`) and CANFD3 (`CRX3`→`P87`, `CTX3`→`P86`), per
`metadata/e1m_modules/v2n/renesas-peripheral-map.tsv:16-19` and `metadata/pinmux/v2n.yaml:28-31`
— and the tool reports at module level, so the module figure is the one that must be quoted, not
the SoC figure.

`peripheral_support()` now returns a `note` field on every successful response (the `sku`-only
map, the `sku`+`peripheral` boolean, and the `peripheral`-only list) stating plainly that
`soc_peripherals` reflects silicon integration only, not portable-API availability or backend
implementation status, and to check `src/backends/<peripheral>/` and the board's devicetree
before assuming a `true` means the peripheral works.

### Documented — CAN-FD on V2N/V2M is blocked upstream, not merely unwritten; both trees now say exactly how (#1146)

The enablement half of this issue was investigated and **deliberately not built**. It cannot be
built honestly at the pinned toolchain, and the reason belongs where the next person will look,
because in both trees a plausible wrong value is sitting one file away from the right one.

The first framing to retire is "there is no driver". Zephyr v4.4.1 *does* ship an RZ CAN-FD
driver and both bindings (`can_renesas_rz_canfd.c`, `renesas,rz-canfd.yaml`,
`renesas,rz-canfd-global.yaml`), and `src/backends/can/zephyr_drv.c` already binds any
`DT_ALIAS(alp_canN)`. Four separate things stop that driver binding on the RZ/V2N CM33, and each
one is vendor data this repo does not carry:

- **No FSP CAN-FD module for RZ/V.** `CONFIG_CAN_RENESAS_RZ_CANFD` selects `USE_RZ_FSP_CANFD`,
  which compiles `fsp/src/${SOC_SERIES_PREFIX}/r_canfd/r_canfd.c`. hal_renesas at Zephyr v4.4.1's
  pin (`06282060fa20cbd21d4ebbc7d46a1fc9533fd24e`) carries that module for RZ/G only —
  `fsp/src/rzg/r_canfd/` and `fsp/inc/instances/rzg/r_canfd.h` exist, the `rzv` counterparts do
  not. Turning the symbol on under `SOC_SERIES_RZV2N` is a CMake configure error on a missing
  source file, and the driver's `#include "r_canfd.h"` does not resolve on the `rzv` include path.
- **No CAN-FD node in the SoC devicetree.** `arm/renesas/rz/rzv/r9a09g056.dtsi` declares none, so
  there is no label to reference and no `reg`/`interrupts` to inherit. The only RZ SoC dtsi that
  carries them is RZ/G3S's `r9a08g045.dtsi`, whose plausible-looking `canfd-global@400c0000` and
  interrupts `373`/`374` (global) and `375..380` (per channel) belong to a different part.
- **No static NVIC vector exists to write.** RZ/V2N's CM33 gives CAN-FD no dedicated vector at
  all: `bsp_irq_id.h`'s `IRQn_Type` enum has zero CANFD entries, and all 20 CAN-FD sources live
  in the separate `IRQSELn_Type` enum (354..373, including `CANFD_INTRCANGERR_IRQSELn` 366 and
  `CANFD_INTRCANGRECC_IRQSELn` 367). They reach the NVIC only by being routed onto one of the
  selectable slots `SEL0_IRQn`..`SEL126_IRQn` (NVIC 353..479) at run time, through
  `R_BSP_SelectIrqSet()`. Upstream's own dtsi hands those slots out (`adc0` = 403 = SEL50,
  `gpt0` = 406..408 = SEL53..55, on up to 453) and both bindings require `interrupts`, so
  choosing slots here would invent an allocation that collides with whatever upstream picks.
- **No PFC function index for the pads.** The module bonds out two of the SoC's six controllers,
  CANFD2 (CTX2 = P84, CRX2 = P85) and CANFD3 (CTX3 = P86, CRX3 = P87), but
  `metadata/pinmux/v2n.yaml` carries pad <-> signal only, with no alternate-function number.
  `RZV_PINMUX()` needs one, and it lives in the RZ/V2N hardware manual's PFC table.

**One hardware number is worth quoting, because the vendor header carries its own trap.** The
CAN-FD register base on this part is `0x42440000` — `R_CANFD_BASE` in hal_renesas's
`R9A09G056N/iodefines/canfd_iodefine.h`. The `(@ 0x400B0000)` in that same file's `R_CANFD`
struct doc-comment is a template annotation, not this SoC's base. Nothing here writes either
value into a node; both are recorded so a future port does not pick the wrong one.

What *is* already in place, so a port need not re-derive it: the clock path.
`RZ_CLOCK_CANFD(ch)` exists in `dt-bindings/clock/renesas_rzv_clock.h`, and
`clock_control_renesas_rz_cpg.c` already maps `RZ_IP_CANFD` onto
`R_BSP_MODULE_START(FSP_IP_CANFD, ch)`; rzv2n's `bsp_feature.h` declares 6 channels, CAN-FD
support and 96 RX message buffers for this part.

**A carrier fact that changes who owns the transceivers.** `CAN_STBY` is not a Renesas pad — it
belongs to the GD32 IO-MCU on `PB13` (`metadata/pinmux/v2n.yaml:197` ("CAN_STBY")), so taking the
TCAN1044 pair out of standby is a bridge GPIO call on either core, not a pinctrl entry. And
CANFD2/CANFD3 are still unattributed in `metadata/e1m_modules/v2n/core-ownership.yaml`, whose
"absence means not attributed" rule leaves `scripts/check_amp_pad_claims.py` unable to see an
A55-vs-CM33 conflict on those pads until a core claims them.

No code changed, and no devicetree node was added on either core. The analysis lands as two
comment blocks in the repo's existing documented-absence idiom (the `wdt0` block from #1153, the
audio block in the carrier dtsi):
`zephyr/boards/alp/e1m_v2n101_m33_sm/alp_e1m_v2n101_m33_sm_r9a09g056n48gbg_cm33.dts:135-205`
("No &canfd node here") for the CM33, and
`meta-alp-sdk/recipes-kernel/linux/linux-renesas/e1m-x-evk.dtsi:84-112`
("DATA-GATED on the kernel side") for the A55, which upgrades a bare one-line TODO into the three
kernel-side values still missing (the `canfd` node's label and compatible string in the
linux-renesas 6.1.x `r9a09g056` dtsi, the `RZV2N_PORT_PINMUX` function index for P84..P87, and
whether the BSP defconfig builds a CAN-FD driver at all). `<alp/can.h>` behaviour is unchanged
and already correct: `src/backends/can/zephyr_drv.c:155` ("return ALP_ERR_NOT_READY") when no
`alp-canN` alias resolves.
