### Fixed — `EVK_PIN_SDIO_MUX_SEL` doc string and `evk_sdio_select_t` enum had the SDIO mux select polarity inverted (#2129)

`metadata/boards/e1m-evk.yaml:139` (`EVK_PIN_SDIO_MUX_SEL`'s `doc:`) said
"0 = M.2 E-key SDIO, 1 = microSD slot" -- the opposite of the carrier
netlist. `E1M-EVK-2626-R2_pinmap.csv` (internal repo, `grep -a ',U38,'`)
shows `SD_D3` on U38 pin 2 (`1|0`) and `M2E_SDIO_D3` on pin 3 (`1|1`); U39
carries the same shape for CLK/CMD. A 74LVC157/74LV3257's `x|0` inputs are
selected when `S` is LOW, so `S` LOW routes the microSD slot and `S` HIGH
routes the M.2 E-key, not the reverse the doc string claimed. Confirmed on
real hardware, not just the netlist: on `e1m-aen-evk-03`, header P18 open
pulls `S` low through `R27` (100k to `0V`) via `R198` (0 ohm to
`NetP18_2`), and a microSD card in `J7` enumerated and read a real sector 0
with the `55 AA` boot signature -- proving `S` LOW is the microSD slot on
this hardware. `metadata/boards/e1m-evk.yaml:140`'s `doc:` (the pin's IDE
hover) is corrected and now carries the full r1/r2 split rather than just
r2: on r1 `S` IS firmware-drivable, via CC3501E `GPIO_30`
(`metadata/e1m_modules/aen/hw-revisions.yaml:46`), with a warning never to
drive it LOW while header P18's jumper is fitted (see the hazard below);
on r2 it is `dispatch: unrouted` (`metadata/e1m_modules/E1M-AEN801.yaml:358-359`
("Physically open on board 2626-R2"), #1854) and hardware-strapped via
`R198`/`R27`/header `P18` instead.

The same inversion was baked into the generated `evk_sdio_select_t` enum:
`metadata/boards/e1m-evk.yaml`'s `mux_enums:` block paired
`EVK_SDIO_M2E_KEY` with `value: 0` and `EVK_SDIO_SDCARD` with `value: 1`
(now swapped, `metadata/boards/e1m-evk.yaml:372-373`, so
`EVK_SDIO_SDCARD = 0` / `EVK_SDIO_M2E_KEY = 1`, matching `MUX_SEL.SDIO
low`/`high` in the same block). **Public ABI change:** no in-tree code
consumes `evk_sdio_select_t`'s values today (the pin isn't
software-drivable at all on r2, and no example opens it on r1 either), so
this changes no behaviour in this repo -- but out-of-tree code that passes
`EVK_SDIO_SDCARD` or `EVK_SDIO_M2E_KEY` as a raw `0`/`1` literal, rather
than the symbolic name, now gets the opposite value. `docs/abi/
removed-symbols.json` gains an entry recording `evk_sdio_select_t`'s
changed hash as an intentional, explained removal against the last
released baseline (`docs/abi/v0.15-snapshot.json`): the typedef's header
move (`alp_e1m_evk.h` -> `alp_e1m_evk_routes.h`, #637) would otherwise
read as a clean `MOVED`, but `scripts/abi_snapshot.py`'s `diff()` only
collapses a header move into `MOVED` when the hash is IDENTICAL, and this
fix also changes the enumerator values -- so without the allowlist entry
it reads as a bare `REMOVED` and fails both the `pr-generated-files.yml`
freeze gate and `tests/scripts/test_abi_snapshot.py::
test_real_tree_reports_zero_removed_against_last_released_snapshot`.
`docs/abi/v0.16-snapshot.json` (the CURRENT snapshot,
`metadata/sdk_version.yaml` pins `version: 0.16.0`) is regenerated via
`scripts/abi_snapshot.py --version v0.16 --output docs/abi/v0.16-snapshot.json`
to carry the new hash. (A follow-up is filed separately to make
`abi_snapshot.py diff()` report this shape as `MOVED`+`CHANGED` instead of
requiring an allowlist entry.)

`include/alp/boards/alp_e1m_evk_routes.h` is regenerated from both

**`include/alp/boards/alp_e1m_evk.h:96-157`'s hand-written SDIO mux block
carried the same inverted `S` mapping, plus a deeper problem: it presented
`/E = 0` as a working route on the stock 74LVC157, which it never was.**
Per the authoritative 2626-R2 carrier netlist, the mux's `Y` pins land on
the SAME nets the SoC's own peripheral pins are wired to (U39 `3Y` =
`E1M_CLK`, `4Y` = `E1M_CMD`, `2Y` = `E1M_SDIO_RST`; U38 `1Y`..`4Y` =
`E1M_D3`..`E1M_D0`). A 74LVC157 is UNIDIRECTIONAL and always actively
drives `Y` -- the selected `A`/`B` input at `/E` = LOW, forced LOW at
`/E` = HIGH -- so it fights the SD host controller's own CLK/CMD output
(and the SD_RST GPIO output `aen-sdcard-readout` drives on
`E1M_SDIO_RST`) in EITHER state, not just when disabled: SD, and
SoC-to-amp I2S through the same-shape U46 mux, can never work through the
stock part at all. A 3257-type FET bus-switch rework of U38/U39/U46 --
now the standard fit -- IS a genuine bidirectional switch: `/E` = LOW
connects (does not drive) the selected side, so the SoC's own driver
passes through cleanly, and `/E` = HIGH is real Hi-Z. That fixes SDIO
(U38/U39, both on `+3V3`) -- proven, SD now works in 4-bit mode -- but
does NOT fix I2S-to-amps: per the 2626-R2 netlist U46's `VCC` (pin 16) is
on `+VIO`, measured 1.8 V on `e1m-aen-evk-03` (maintainer, 2026-09-15),
below a 3257-type part's 2.3-3.6 V spec; as an NMOS pass-gate it only
passes a HIGH of roughly `VCC - Vth`, not a valid I2S level, and with
both amps ACTIVE the TAS2563s produced no audible output even though
every I2S/I2C call returned `ALP_OK` -- confirmed at the bench. A
working U46 needs a switch rated for 1.8 V `VCC` (e.g. TI TMUX1574,
pinout-compatible with SN74CBTLV3257) or the fitted part re-powered from
`+3V3`; neither has landed. The SDIO block's truth table is now scoped to
"with a 3257-type switch fitted" rather than presented as universal, and
the I2S block (`:159-220`) gets the same per-part contention wording for
`/E` PLUS this `+VIO` power-rail finding, alongside a separate
pre-existing bug in that block: it claimed I2S_EN is unconditionally
"driven from Alif via alp_gpio_*", true only on r1 -- on r2 it is
CC3501E `GPIO_30` (`metadata/e1m_modules/aen/from-cc3501e.tsv:21`),
contradicting the block's own r1/r2 summary two paragraphs above it.

The SDIO block's claim that IO21 is CC3501E-proxied is revision-dependent,
not simply wrong: r2 (`metadata/e1m_modules/E1M-AEN801.yaml:358-359`)
leaves it `dispatch: unrouted` and hardware-strapped, exactly as described
above, but r1 (`metadata/e1m_modules/aen/hw-revisions.yaml:46` ("r1: CC3501E GPIO_30 (r2 unrouted)"))
DOES proxy it to CC3501E `GPIO_30` and IS firmware-drivable there -- with a
hardware hazard the block now documents: the same select net reaches
header P18 pin 2 (`NetP18_2`) through R198 (0 ohm), and P18's jumper, when
fitted, ties pin 1 (`+3V3`) to pin 2 -- so driving IO21 LOW on r1 while
the jumper is fitted makes CC3501E `GPIO_30` sink the +3V3 rail.
