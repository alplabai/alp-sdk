### Fixed — `EVK_PIN_SDIO_MUX_SEL` doc string and `evk_sdio_select_t` enum had the SDIO mux select polarity inverted (#2129)

`metadata/boards/e1m-evk.yaml:139` (`EVK_PIN_SDIO_MUX_SEL`'s `doc:`) said
"0 = M.2 E-key SDIO, 1 = microSD slot" -- the opposite of the carrier
netlist. `E1M-EVK-2626-R2_pinmap.csv` (internal repo, `grep -a ',U38,'`)
shows `SD_D3` on U38 pin 2 (`1|0`) and `M2E_SDIO_D3` on pin 3 (`1|1`); U39
carries the same shape for CLK/CMD. A 74LVC157/74LV3257's `x|0` inputs are
selected when `S` is LOW, so `S` LOW routes the microSD slot and `S` HIGH
routes the M.2 E-key, not the reverse the doc string claimed. Confirmed on
real hardware, not just the netlist: on `e1m-aen-evk-03`, header P18 open
pulls `S` low through `R27` (100k to `0V`) via `R198` (0 ohm to
`NetP18_2`), and a microSD card in `J7` enumerated and read a real sector 0
with the `55 AA` boot signature -- proving `S` LOW is the microSD slot on
this hardware. The doc string is corrected and now also notes that `S` is
not firmware-driven on 2626-R2's r2 module revision: `E1M_GPIO_IO21` is
`dispatch: unrouted` (`metadata/e1m_modules/E1M-AEN801.yaml:358-359`
("Physically open on board 2626-R2"), #1854) and is instead
hardware-strapped via `R198`/`R27`/header `P18`.

The same inversion was baked into the generated `evk_sdio_select_t` enum:
`metadata/boards/e1m-evk.yaml`'s `mux_enums:` block paired
`EVK_SDIO_M2E_KEY` with `value: 0` and `EVK_SDIO_SDCARD` with `value: 1`
(now swapped, `metadata/boards/e1m-evk.yaml:372-373`, so
`EVK_SDIO_SDCARD = 0` / `EVK_SDIO_M2E_KEY = 1`, matching `MUX_SEL.SDIO
low`/`high` in the same block). **Public ABI change:** out-of-tree code
that passes `EVK_SDIO_SDCARD` or `EVK_SDIO_M2E_KEY` as a raw `0`/`1`
literal, rather than the symbolic name, now gets the opposite value -- the
enumerator has two real in-tree consumers that prove this is not inert:
`tests/scripts/test_gen_board_header.py`'s
`test_real_evk_header_covers_mux_enums` (binds each enumerator to its own
value so this exact swap is caught, not just presence) and the ABI
snapshot fixture below. `docs/abi/removed-symbols.json` gains an entry
recording `evk_sdio_select_t`'s changed hash as an intentional, explained
removal against the last released baseline (`docs/abi/v0.15-snapshot.json`):
the typedef's header move (`alp_e1m_evk.h` -> `alp_e1m_evk_routes.h`, #637)
would otherwise read as a clean `MOVED`, but `scripts/abi_snapshot.py`'s
`diff()` only collapses a header move into `MOVED` when the hash is
IDENTICAL, and this fix also changes the enumerator values -- so without
the allowlist entry it reads as a bare `REMOVED` and fails both the
`pr-generated-files.yml` freeze gate and
`tests/scripts/test_abi_snapshot.py::test_real_tree_reports_zero_removed_against_last_released_snapshot`.
`docs/abi/v0.16-snapshot.json` (the CURRENT snapshot,
`metadata/sdk_version.yaml` pins `version: 0.16.0`) is regenerated via
`scripts/abi_snapshot.py --version v0.16 --output docs/abi/v0.16-snapshot.json`
to carry the new hash.

`include/alp/boards/alp_e1m_evk_routes.h` is regenerated from both
metadata changes via `scripts/gen_board_header.py` (GENERATED, never
hand-edited); `tests/fixtures/emit-snapshots/proj-aen.carrier-netlist.snap`
and `proj-aen.composed-route-table.snap` were refreshed via
`scripts/check_emit_snapshots.py --update` in the same pass.

`include/alp/boards/alp_e1m_evk.h:96-152`'s hand-written SDIO mux block
carried the same inverted `S` mapping and additionally claimed `/E = 1`
produces "outputs Hi-Z" unconditionally. That is wrong for the part
originally fitted: U38/U39 shipped as 74LVC157 on the original 2626-R2
BOM, and a 74LVC157 forces its Y outputs LOW when disabled (it is a mux
with an output stage, not a tristate bus switch) -- driving the SoC-side
nets (U39 `3Y` = `E1M_CLK`, `4Y` = `E1M_CMD`; U38 `1Y`..`4Y` =
`E1M_D3`..`E1M_D0`) LOW contends with an active SD host controller rather
than isolating it, so it must not be described as a safe default. The
74LV3257 FET bus-switch rework of U38/U39/U46 -- now the standard fit --
genuinely is Hi-Z at `/E = 1`; the block now states both, per part, rather
than asserting one behaviour for both. The block's blanket claim that IO21
is CC3501E-proxied is also revision-dependent, not simply wrong: r2
(`metadata/e1m_modules/E1M-AEN801.yaml:358-359`) leaves it `dispatch:
unrouted` and hardware-strapped, exactly as described above, but r1
(`metadata/e1m_modules/aen/hw-revisions.yaml:46` ("r1: CC3501E GPIO_30 (r2 unrouted)"))
DOES proxy it to CC3501E `GPIO_30` and IS firmware-drivable there -- with a
hardware hazard the block now documents: the same select net also reaches
header P18 pin 1 (`+3V3`) through R198 (0 ohm), so driving IO21 LOW on r1
while P18's jumper is fitted makes CC3501E `GPIO_30` sink the +3V3 rail.

`docs/cc3501e-bridge.md` restated the same two bugs and gains the same
r1/r2 split. Dev's `:82-83` ("`SDIO_MUX_SEL` = `GPIO_30`") and `:518-519`
("`SDIO_MUX_EN` (`GPIO_26`): HIGH (74LVC157 /E = 1 -> Hi-Z)" /
"`SDIO_MUX_SEL` (`GPIO_30`): don't-care while /E is high.") both mislabelled
`SDIO_MUX_SEL` as CC3501E `GPIO_30` unconditionally -- that pin actually
belongs to `IO8`/`EVK_PIN_I2S_MUX_EN` on r2
(`metadata/e1m_modules/E1M-AEN801.yaml:336-337` ("CC3501E GPIO_30 (board 2626-R2; GPIO30 moved here from IO21)"),
`metadata/e1m_modules/aen/from-cc3501e.tsv:21` ("AG33	IO8	GPIO30")); on r2
`IO21` has no CC3501E pin at all. On the branch these are now
`docs/cc3501e-bridge.md:82-88` and its
rewritten "Safe-default mux state" table (`:514-548`), which: states the
same part-dependent LOW-vs-Hi-Z fact as the header above for `SDIO_MUX_EN`
(dropping the "safe-default" framing for the stock 74LVC157 state);
gives `SDIO_MUX_SEL` its r1 (firmware-drivable, `GPIO_30`, same P18 hazard)
vs r2 (hardware-strapped, not a CC3501E pin) split; and adds the
previously-missing `I2S_MUX_EN` row (`GPIO_30` on r2 only -- r1's `IO8` is
a direct Alif GPIO, not CC3501E-proxied at all) with its boot-time HIGH
(disabled) level and the same per-part caveat, since it controls the same
family of mux on U46.
