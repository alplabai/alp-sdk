### Fixed — `EVK_PIN_SDIO_MUX_SEL` doc string and `evk_sdio_select_t` enum had the SDIO mux select polarity inverted (#2129)

`metadata/boards/e1m-evk.yaml:139` (`EVK_PIN_SDIO_MUX_SEL`'s `doc:`) said
"0 = M.2 E-key SDIO, 1 = microSD slot" -- the opposite of the carrier
netlist. `E1M-EVK-2626-R2_pinmap.csv` (internal repo, `grep -a ',U38,'`)
shows `SD_D3` on U38 pin 2 (`1|0`) and `M2E_SDIO_D3` on pin 3 (`1|1`); U39
carries the same shape for CLK/CMD. A 74LVC157/74LV3257's `x|0` inputs are
selected when `S` is LOW, so `S` LOW routes the microSD slot and `S` HIGH
routes the M.2 E-key, not the reverse the doc string claimed. Confirmed on
real hardware, not just the netlist: on `e1m-aen-evk-03`, header P18 open
pulls `S` low through `R27` (100k to `0V`) via `R198` (0 ohm to
`NetP18_2`), and a microSD card in `J7` enumerated and read a real sector 0
with the `55 AA` boot signature -- proving `S` LOW is the microSD slot on
this hardware. The doc string is corrected and now also notes that `S` is
not firmware-driven on 2626-R2: `E1M_GPIO_IO21` is `dispatch: unrouted`
(`metadata/e1m_modules/E1M-AEN801.yaml:358-359` ("Physically open on board 2626-R2"), #1854)
and is instead hardware-strapped via `R198`/`R27`/header `P18`.

The same inversion was baked into the generated `evk_sdio_select_t` enum:
`metadata/boards/e1m-evk.yaml`'s `mux_enums:` block paired
`EVK_SDIO_M2E_KEY` with `value: 0` and `EVK_SDIO_SDCARD` with `value: 1`
(now swapped so `EVK_SDIO_SDCARD = 0` / `EVK_SDIO_M2E_KEY = 1`, matching
`MUX_SEL.SDIO low`/`high` in the same block). Neither enumerator has any
consumer in this repo today (the pin isn't software-drivable on 2626-R2),
so the swap changes no runtime behaviour. `include/alp/boards/alp_e1m_evk_routes.h`
is regenerated from both changes via `scripts/gen_board_header.py` (GENERATED,
never hand-edited); the affected `tests/fixtures/emit-snapshots/proj-aen.carrier-netlist.snap`
and `proj-aen.composed-route-table.snap` goldens are refreshed via
`scripts/check_emit_snapshots.py --update` to match.

`include/alp/boards/alp_e1m_evk.h:104-107`'s hand-written SDIO mux truth
table carried the same inverted `S` mapping and additionally claimed
`/E = 1` produces "outputs Hi-Z"; the stock 74LVC157 instead forces its
outputs LOW when disabled (it is a mux with an output stage, not a
tristate bus switch), so both are corrected. The block's claim that IO21
is CC3501E-proxied (`:109-115`, old text) is also wrong for 2626-R2 per
`metadata/e1m_modules/E1M-AEN801.yaml:358-359` -- only `IO20` (`/E`, CC3501E
`GPIO_26`) is proxied; `IO21` (`S`) is unrouted and hardware-strapped, so
firmware cannot change the SDIO select at runtime on this board.

`docs/cc3501e-bridge.md:82-84` and its "Safe-default mux state" table
(`:519-523`) labelled `SDIO_MUX_SEL` as CC3501E `GPIO_30` -- that pin
actually belongs to `IO8`/`EVK_PIN_I2S_MUX_EN` on 2626-R2
(`metadata/e1m_modules/E1M-AEN801.yaml:336-337` ("CC3501E GPIO_30 (board 2626-R2; GPIO30 moved here from IO21)"));
`IO21` has no CC3501E pin at all on this revision. Both spots are corrected to say `SDIO_MUX_SEL` is
hardware-strapped, not a CC3501E pin, and the `/E = 1` "Hi-Z" claim in the
same table is corrected to "outputs forced LOW" alongside it.

The I2S twin, `metadata/boards/e1m-evk.yaml:124-125` (`EVK_PIN_I2S_MUX_SEL`,
"0 = TAS2563 amps, 1 = M.2 E-key I2S"), was checked against its own netlist
(`U46` pin 2 `1|0` = `AMP_I2S0_WS`) and is correct -- not touched by this
fix.
