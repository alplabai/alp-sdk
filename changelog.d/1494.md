### Fixed — ORT `open()`'s exception path leaked every `OrtValue` created before the throw (#1494)

`src/yocto/inference_ort.cpp`'s `alp_inference_ort_open()` builds one `OrtValue` per
input/output tensor via `CreateTensorWithDataAsOrtValue`, aliasing the SDK-owned buffers.
Its `catch (...)` handler — reached when a `std::vector::resize()` throws mid-loop, e.g.
`std::bad_alloc` sizing an output buffer on a memory-constrained A55 SoM — released only
`cpu_mem_info` / `session` / `env`, unlike the sibling `rc != ALP_OK` teardown four lines
above and `alp_inference_ort_close()`, both of which call `_release_values()` on
`output_values` and `input_values` first. Every `OrtValue` already constructed before the
throw was orphaned; `ReleaseSession` / `ReleaseEnv` do not reclaim `OrtValue`s.

The `catch (...)` handler now calls `_release_values(api, st->output_values)` and
`_release_values(api, st->input_values)` before the `ReleaseMemoryInfo` / `ReleaseSession`
/ `ReleaseEnv` trio, matching both sibling teardown paths. `input_values`/`output_values`
are pre-sized with `assign(n, nullptr)` before either resize loop runs, so the vectors are
always the right size and `_release_values()`'s per-entry null check makes the call safe
whether zero, some, or all entries were populated at the point of the throw.

This backend is gated `OFF` by default (`ALP_SDK_USE_ORT_CPU`) and compiled by no CI gate —
it depends on ORT headers only present inside an aarch64 Yocto work tree — so this fix is
unverified by any build or test; it was reasoned through against the ORT C++ API's ownership
rules and the file's own two working teardown paths, not compiled.
