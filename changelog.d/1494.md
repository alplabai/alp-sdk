### Fixed — `inference_ort.cpp`'s `open()` exception path leaked every `OrtValue` created before the throw (#1494)

`alp_inference_ort_open()` has three teardown paths that must all release the
same set of ORT objects: the `rc != ALP_OK` early return, `alp_inference_ort_close()`,
and the `catch (...)` handler guarding the file's C++/C exception boundary
(every hook is wrapped so a `std::bad_alloc` / `std::length_error` out of
`std::vector::resize` can't unwind across the `extern "C"` ABI into
`inference_yocto.c`). The `catch` handler released only `cpu_mem_info` /
`session` / `env` and skipped the `_release_values(api, st->output_values)` /
`_release_values(api, st->input_values)` pair its two siblings both perform —
so a `resize()` failure partway through populating the input/output tensors
(e.g. `st->output_bufs[i].resize(...)` after the input loop already created
`st->input_values`) leaked every `OrtValue` created up to that point.

Fixed with one guard in the shared `catch` block, mirroring the other two
teardown paths, rather than one fix per throw site: every throw anywhere in
`open()`'s `try` (both tensor-info-gathering loops, both
`CreateTensorWithDataAsOrtValue` loops, `std::make_unique<OrtState>()`) is
caught here, so the single guard covers all of them. `_release_values()`
already tolerates a partially-populated or empty vector, so it's safe
regardless of which loop threw.

This file is behind `ALP_SDK_USE_ORT_CPU` (default `OFF`, not built in CI —
`docs/verification-status.md` records the backend as code-complete,
bench-unverified), so it can't be compiled or run here. New
`tests/scripts/test_inference_ort_open_catch_releases_ort_values.py` is a
structural regression check on the source text instead: it extracts the
relevant `{ ... }` body by brace-counting and asserts both `_release_values()`
calls are present and run before the `ReleaseMemoryInfo`/`ReleaseSession`/
`ReleaseEnv` trio, proven against synthetic "leaky" and "misordered" corpora
(not just the live file) so it can't pass vacuously if the shape drifts.

Follow-up review pass, same PR:

- The three teardown sequences (the `rc != ALP_OK` path, the `catch` handler,
  `alp_inference_ort_close()`) were byte-for-byte duplicated, and that
  duplication is *why* the `catch` copy drifted out of parity in the first
  place. Extracted a single `static void _teardown(const OrtApi *, OrtState *)`
  and call it from all three, so there is now one definition to keep correct
  instead of three to keep in sync. The regression test above now checks that
  `open()`'s `catch` calls `_teardown()` and that `_teardown()` itself
  preserves the values-before-trio order, since the ordering invariant moved
  off the catch block along with the code.
- `_gather_tensor_info()`'s `out.name = raw_name;` is a `std::string`
  assignment that can throw `std::bad_alloc`, and unlike the `OrtValue`s this
  raw allocator-owned name isn't reachable from `open()`'s `catch`, so a throw
  there would leak it. Now freed under a local `try`/`catch` that frees
  `raw_name` and rethrows.
- Same file, `std::vector<int64_t> dims(ndim)` could throw before the
  matching `api->ReleaseTypeInfo(type_info)` a few lines down — near
  unreachable given the `kMaxTensorRank` (32) bound just above it, but same
  leak class. Wrapped the same way.
