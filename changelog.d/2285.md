### Added — word-copy `memcpy()` override + Ethernet buffer sizing for AEN camera streaming throughput (#2285)

`examples/connectivity/camera-mjpeg-stream` on E1M-AEN803 topped out well
short of its OV5647 sensor's frame rate: bench run 223 showed the
camera-capture loop keeping up with 60 fps while the HTTP `/stream` send
took 24-30 ms per 32-41 KB frame, dropping 45-51% of frames.

Two changes landed together; only the Ethernet buffer sizing is
bench-proven on its own to fix run 223's drops (runs 224-228, module
2026W36-0001) -- see the word-copy `memcpy()` entry below for its own,
separately measured A/B:

- **`CONFIG_ALP_SDK_FAST_MEMCPY`** (new Kconfig,
  `zephyr/kconfigs/core.kconfig`, default `n`, enabled explicitly on
  `examples/connectivity/camera-mjpeg-stream`'s AEN801/AEN803 board
  confs; requires Alif Ensemble + GCC + `CONFIG_SIZE_OPTIMIZATIONS` +
  picolibc-from-toolchain): on a
  -Os AEN image, `CONFIG_SIZE_OPTIMIZATIONS` links picolibc's "space"
  multilib, whose `memcpy()` copies one byte at a time. The full
  `CONFIG_SPEED_OPTIMIZATIONS` build copies faster but overflowed this
  app's ITCM budget by about 41 KB running from ITCM RAM, so it isn't
  an option here. The new `src/common/alp_fast_memcpy_core.c` walks a
  word (and, where aligned, four words) at a time instead — falling
  back to the byte loop whenever source/destination don't share the
  same 4-byte alignment phase — compiled at the TU's own -Os (no local
  optimize("O2") — an earlier version paired one with the loop and
  that, not -Os itself, let GCC auto-vectorize the loop to Arm MVE
  Cortex-M55 Q-register instructions, putting `memcpy()` on FPU/MVE
  state everywhere it runs; dropped). It carries
  `__attribute__((optimize("no-tree-loop-distribute-patterns")))` as
  insurance: without it, GCC's loop-idiom pass could rewrite the
  byte-copy loop shape back into a call to `memcpy()` — which, since
  this function *is* `memcpy()`, would recurse forever and hang the
  board. Confirmed against GCC 14.3, that pass does not rewrite this
  exact loop shape at plain -Os; the guard is insurance against a
  future -O2 build of this TU and a future loop edit — this file
  originally paired the guard with a local optimize("O2"), and it was
  under that O2 pairing that the recursion hung the board for real
  (bench run 227, before the network came up). GCC-only: Clang's own
  loop-idiom pass would still do the same rewrite regardless of that
  attribute, so the
  Kconfig depends on the GCC toolchain variant and the core `.c` also
  `#error`s under Clang as a second check. `src/zephyr/fast_memcpy.c`
  aliases `memcpy`/`__aeabi_memcpy`/`__aeabi_memcpy4`/`__aeabi_memcpy8`
  onto the core; Zephyr's link step wraps the `alp_sdk` Zephyr library
  in `-Wl,--whole-archive`, so this object is always pulled in and
  already resolves `memcpy` before the linker reaches picolibc's own
  (non-whole-archive) archive, so there is no multiple-definition
  error. New host unit test `tests/unit/fast_memcpy` (native_sim)
  exhaustively checks every source/destination alignment pair (0-3 byte
  offset each) crossed with every length 0-70 against a byte-at-a-time
  reference copy, calling the core function directly so the test binary
  never defines its own `memcpy()`; that target also compiles in a
  test-only assert that the word loop only ever runs against
  word-aligned pointers, so a mutated alignment check that still
  happens to copy the right bytes on this host still fails the test.

  Buffer sizing (below) is bench-proven on its own to take run 223's
  frame drops to 0%. A same-scene A/B against that buffer-sizing-only
  baseline (E1M-AEN803, module 2026W36-0001, 640x480 @ 30 fps,
  camera-bound) found no measurable gain from this word-copy override:
  A1 (memcpy ON) 30.03 fps / 1,089,750 B/s, B1 (memcpy OFF) 30.03 fps /
  1,092,219 B/s, A2 (memcpy ON) 30.03 fps / 1,088,302 B/s, 0 drops
  throughout. The send-bound case run 223 actually hit is still
  unmeasured — see this example's README.

- **Ethernet TX/RX buffer sizing**, added to both
  `examples/connectivity/camera-mjpeg-stream/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.conf`
  and the AEN803 sibling conf (content-identical, per this example's
  README convention): `CONFIG_NET_BUF_TX_COUNT=64`,
  `CONFIG_NET_PKT_TX_COUNT=32`, `CONFIG_NET_BUF_RX_COUNT=32`,
  `CONFIG_NET_PKT_RX_COUNT=16`, `CONFIG_NET_TCP_MAX_SEND_WINDOW_SIZE=65535`,
  `CONFIG_NET_TX_STACK_SIZE=2048` — overriding the smaller portable
  `prj.conf` defaults for these two hardware targets only (native_sim
  keeps the portable defaults; it has no Ethernet). Bench-proven to
  take frame drops to 0% on its own.

Combined, runs 224-228 reached **60.1 fps** end to end — the OV5647
sensor's own rate — 1803 frames in 30 s, interval stdev 0.1 ms. Two
caveats on that number, both called out in the example's README: it
used a simpler scene with a smaller mean frame (14.7 KB) than the
runs it's compared against, so it is not a clean same-scene A/B; and
the PHY was confirmed at 100 Mbit full duplex with TCP congestion
avoidance making no measurable difference.
