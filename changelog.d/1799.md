### Fixed — the CC3501E firmware docs called async-event delivery future work eight months after it shipped (#1799)

Slave->master async-event delivery landed in **#1721** (merged 2026-08-27,
closing **#130**): the CC35 pulses an attention edge on the existing READY wire
(`GPIO17` -> Alif `P2_6`), the host arms with `cc3501e_attn_arm()` and drains on
the edge, and it was validated on silicon at 135 of 135 firmware pushes across a
40 s armed window with the console timer poll at 60 s — so no timer delivery
could have accounted for it. Eight places in `cc3501e-bridge-firmware:` still described
the whole mechanism as unbuilt.

Two of those were worse than stale. `src/protocol_gpio.c` and
`hal/ti/cc3501e_hw_ti_gpio.c` both said `EVT_GPIO_INTERRUPT` delivery "needs the
next-rev host-IRQ line". The line exists; `gpio_irq_cb()` simply never calls
`event_ring_push()`. A reader following those comments would have specified a
board change to buy something an existing one-line call already reaches. They now
name the real blocker.

`DESIGN.md`'s section is rewritten around what shipped, including the three
properties of the shared wire that are load-bearing rather than incidental —
sticky arm intent (unconditional re-arming in `lock_release()` hangs the device
after `WIFI_SCAN`), the 50 ms empty-drain backoff (the wire also carries READY
flow control, so a transaction end is indistinguishable from an attention pulse;
without the backoff 86 events cost 11888 ISRs instead of 220), and that a full
ring must still pulse (16 boot-time Wi-Fi events fill the ring, and pulsing only
on a successful push is unrecoverable on an idle host). A *dedicated* HOST_IRQ
pad on a later board rev stays documented as future work, which is what would
remove the shared-wire ambiguity in the first place.

**Correcting the prose surfaced two limits that were written down nowhere.**

The firmware pulse is a **build-time opt-in**: `build_ti.ps1 -AttnPulse` sets
`-DCC3501E_ATTN_PULSE=1` and is default OFF, because the wire is a rev-1 bodge
absent on the stock EVK. `ti/package_cc3501e_prod.ps1` builds with
`build_ti.ps1 -Ble` and does not pass it, so the production recipe produces an
image whose attention call links a no-op stub — a host that arms attention never
sees an edge and silently falls back to its timer poll. `prebuilt/CHANGELOG.md`
nonetheless listed the attention edge as a plain 0.4.0 feature; it now records
that whether the shipped `cc3501e-v0.4.0.bin` carries the pulse is **unverified**,
and says to assume it does not until an edge is observed on silicon. The
host-side subscriber fan-out (#1724) is unconditional and unaffected.

And only Wi-Fi events have a producer: `EVT_WIFI_CONNECTED` and
`EVT_WIFI_DISCONNECTED` are the only `event_ring_push()` call sites in the tree.
`EVT_GPIO_INTERRUPT` and every BLE event have none, so they never reach the host
whatever the transport does. `BRINGUP_STATUS.md` §4 and §8 now say so instead of
implying the transport is the gap.

`BRINGUP_STATUS.md` also carried the accuracy fixes made in the extracted
`alplabai/cc3501e-bridge-firmware` repo but never ported back here, which matters
because this copy is the one alp-sdk consumers read: the TL;DR table still
advertised a single **"Wi-Fi connect-STA / soft-AP / sockets … socket APIs
shipped"** row. Sockets do not connect at all on fw 0.4.0 / protocol 5 (#1746),
and soft-AP association is unresolved (#1562, #1385). Those are now three
separate rows carrying their real state and evidence, plus the §0.5 current-state
section (shipping versions, what #1740 and #1743 fixed, open items with
measurements, bench traps). The header date moves 2026-07-08 -> 2026-08-28.

No behaviour changes: comments, docs and one changelog bullet only.
