### Documented — bound a relayed, uncorroborated Alif statement on `app-device-config.json` to what it actually established, and to the firewall carve-out this repo already ships (#1701)

SETOOLS **1.110.00** ships no AE822-specific device config: the stock
`build/config/app-device-config.json` declares `"device": "AE722F80F55D5AS"`,
an **E7** part, not the E1M-AEN801's `AE822FA0E5597LS0`. Every customer
provisioning an AEN801 was either using a config named for different silicon
or hand-editing one with no documented basis for the edit.

A maintainer relayed the following from Alif, second-hand — it was **not**
posted to alp-sdk#1700 or alp-sdk#1701, and as of this writing (2026-09-02)
it appears nowhere else in this repo either:

> The provided app-device-config.json works with either E7 or E8. The part
> number field is just a text field for your own usage. The important thing
> to note is the part number selected when you execute tools-config, as that
> is what app-gen-toc and app-write-mram use.

The previous version of this entry presented that quote as Alif's settled,
confirmed answer and closed the issue on the strength of it, and generalized
"the part-number field doesn't matter" further than the relay supports.
Neither holds up: the quote has no repo-internal corroboration, and this
repo already ships a firewall-policy-sensitive path
(`examples/connectivity/firmware-update-log`'s hardware-firewall proof, via
`scripts/bench/aen/flash-update-log-firewall-probe.sh`) whose own comments
warn that swapping in a generic device config there "can remove the very
firewall rule you are trying to prove" — the opposite of "this field never
matters."

`docs/aen-provisioning.md` §3 now:

- attributes the quote as relayed and uncorroborated, not settled;
- keeps only what is independently bench-established as bench-established —
  **`device` is very likely cosmetic, not silicon-relevant** (the SE reports
  the correct part identity from OTP, `ALIF_PN = AE822FA0E5597LS0`,
  regardless of which part the config file names) and **the HFXO trim fields
  already matched our AE822** (`XO_REG1` readback agrees with the stock
  file's `HFXO_CAP_CTRL`/`HFXO_PFET_GM_CTRL`/`HFXO_NFET_GM_CTRL`);
- marks the "`tools-config -a` binds the ATOC to a part, not this file"
  claim as resting on the relay alone;
- states the firewall exception explicitly: the stock file is fine
  unmodified for the boot/identity path this section covers, but that does
  not extend to firewall-policy-sensitive flows, which already require a
  board-specific `ALP_AEN_DEVICE_CONFIG_JSON` instead of the stock file.

**No new device-config file ships with this change**, in either `alp-sdk` or
`alp-sdk-internal`. `app-device-config.json` remains a licensed SETOOLS
deliverable carrying Alif-owned configuration beyond the `device` string, so
a hand-produced copy would still be inventing vendor-owned content rather
than qualifying it.

The documented guidance for the boot/identity path: use the stock
`app-device-config.json` unmodified, as the reference board does; do not
hand-edit its `device` field. alp-sdk#1701 is item 3 of the Alif escalation
tracked at alp-sdk#1700 and stays **open** pending a citable Alif answer on
the issue thread — this entry no longer claims it closed.
