### Fixed -- UART read: RX overrun and ring overflow are reported, not silent (#2934)

**`alp_uart_read()` no longer returns `ALP_OK` with a corrupted frame on Zephyr.** The polled path calls `uart_err_check()` before every `uart_poll_in()` and returns `ALP_ERR_IO` on an RX overrun, framing or parity error; the check is per poll because on ns16550 UARTs (the Alif UART0..3) each poll reads LSR, which clears the very latch `uart_err_check()` reports. While an RX ring buffer is attached, `alp_uart_read()` drains the ring and blocks on a semaphore signalled by the RX interrupt instead of polling a controller the ISR already owns. The ISR counts bytes the ring cannot store and any hardware FIFO overrun it sees via `uart_err_check()`; the next `alp_uart_rx_ringbuf_pop()` (valid bytes still delivered in `got`) or ring-backed `alp_uart_read()` (reported before it consumes anything) returns `ALP_ERR_IO` once for that loss. A standalone `alp_uart_rx_ringbuf_detach()` now wakes a blocked ring-backed read instead of waiting out its timeout. `alp_uart_read()` and the ring API in `<alp/peripheral.h>` document the overrun behaviour, the shared single-consumer role of `alp_uart_read()` and `alp_uart_rx_ringbuf_pop()`, and that buffer contents are unspecified on `ALP_ERR_IO`.

**`alp_uart_read()` returns `ALP_OK` only when all `len` bytes arrived.** A deadline with fewer bytes, including some, is now `ALP_ERR_TIMEOUT` on every backend (Zephyr polled and ring paths, the sw_fallback and testing doubles, Yocto); the bytes received so far are consumed and the buffer is unspecified, so use `alp_uart_rx_ringbuf_pop()` for partial or streaming reads that need a count. The chip drivers that call it (`a02yyuw`, `tmc2209`, the `*_read_response` modem helpers) already treated `ALP_OK` as a full read, so a short read now surfaces instead of passing as complete. Polled mode cannot see an overrun caused while the same thread is transmitting on ns16550-class UARTs (TX polling clears LSR); attach an RX ring for full-duplex use.
