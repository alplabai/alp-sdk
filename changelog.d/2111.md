### Fixed — the `alp companion wifi connect` console command budgeted a CC3501E STA connect at a 50 s budget, under the 70 s bound (#2111)

The CC3501E bridge firmware's own worst case for one STA connect is 10 s
`Wlan_RoleUp` + 30 s L2 association + 30 s DHCP-lease poll = 70 s
(`cc3501e-bridge-firmware:hal/ti/cc3501e_hw_ti_wifi.c`), which documents
75000 ms as the caller budget that clears it. `src/zephyr/console/
alp_console_companion_wifi.c`'s `ALP_COMPANION_WIFI_CONN_MS` was `50000u`,
under that bound, so a genuinely slow-but-healthy association could time out
before the firmware's own connect finished.

`ALP_COMPANION_WIFI_CONN_MS` `50000u` → `75000u`, matching
`SOCKTP_CONNECT_TIMEOUT_MS` / `CONNTWICE_CONNECT_TIMEOUT_MS`. The same
constant is also passed to `cc3501e_wifi_ap_start()`. That call submits
WIFI_AP_START once and then confirms via an independent channel -- polling
`GET_DIAG_INFO`'s role field until it reports `ALP_CC3501E_ROLE_WIFI_AP`,
bounded by `timeout_ms` (`chips/cc3501e/cc3501e_wifi.c`) -- and the
firmware's own worst case there is a single 10 s `Wlan_RoleUp`
(`CC3501E_WIFI_ROLE_TIMEOUT_MS`), so kept shared rather than split: 75 s is a
harmless (if generous) upper bound on that confirmation poll, not an
incorrect one.

The console's `wifi ap` command handler carried stale comments and a stale
shell error string describing a firmware version that could never confirm
AP_START at all. Corrected to the current behaviour (submit once, confirm via
the diag role within the budget): `ap start "%s" unconfirmed (%d) -- firmware
v4 has no AP status latch (#1385); check for the SSID out of band` →
`ap start "%s" failed (%d)`, with `(not confirmed within the budget)`
appended when the failure is `ALP_ERR_TIMEOUT`. The block comment justifying
the success branch as unreachable dead code is removed -- it is the live
path. `chips/cc3501e/cc3501e_wifi.c`'s own block comment above the CONFIRM
step, which said AP_START "has no such channel" and "`timeout_ms` is
therefore currently unused", is corrected to describe the GET_DIAG_INFO
confirmation poll that follows it, and `docs/cc3501e-companion-commands.md`
describes `wifi ap` the same way.

The same under-provisioned budget existed on more callers wired to the same
CC3501E backend: `examples/aen/aen-cc3501e-bringup`'s
`CC3501E_CONN_TIMEOUT_MS` `15000u` → `75000u` (a 5-try bounded retry loop
re-issues `WIFI_CONNECT_STA` on timeout, so a short budget there let a retry
land on top of the previous attempt's still-running connect);
`examples/connectivity/mqtt-telemetry`'s `WIFI_CONNECT_TIMEOUT_MS` `10000u` →
`75000u`; `examples/connectivity/iot-fleet-ota` / `iot-dashboard` moved an
unnamed `10000u`/`5000` literal onto a named `WIFI_CONNECT_TIMEOUT_MS`
`75000u`; and `examples/connectivity/iot-connected-camera`'s inline `30000` →
`75000u` (its `overlay-aen.conf` wires the same CC3501E path on an E1M-AEN
target, so it is not exempt). All four now read that on E1M-AEN801 with the
CC3501E bridge attached the bridge's worst case is 70 s, and on any other
Wi-Fi backend the value is only an upper bound, not a derived worst case.

`docs/cc3501e-bridge.md`'s bench table said a stuck association blocks the
console "for the full `ALP_COMPANION_WIFI_CONN_MS = 75000u` (75 s)"; reworded
to "up to 75 s; a firmware-reported failure returns sooner" -- the budget is
a ceiling on a hung link, not the duration of every failure.

`chips/cc3501e/cc3501e_wifi.c`'s scan-window comment ("the same shape the
55 s connect budget uses over its own 40 s") is corrected to "75 s ... 70 s".

Comments in `examples/aen/aen-cc3501e-socket-throughput` (`SOCKTP_CONNECT_
TIMEOUT_MS`'s derivation, and `SOCKTP_VERDICT_WAIT_MS`, which is now defined
as `SOCKTP_CONNECT_TIMEOUT_MS` instead of a separately-drifting `45000u`
literal), `aen-cc3501e-connect-twice-probe` (source and README), `aen-cc3501e-
wedge-postmortem` (source and README), and `aen-cc3501e-companion-tour` are
corrected from a stale DHCP/total figure to the current 150-try / 30 s DHCP
figure and the 70 s / 75000 ms bound, without changing any of those files'
already-correct `75000u` values.
