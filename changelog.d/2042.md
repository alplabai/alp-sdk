### Fixed — the DesignWare SDHC driver's `PSTATE` bit-23 macro was misnamed for the CMD line (it reads DAT3), and its 1.8V switch poll checked only that one DAT bit instead of all four (#2042)

`zephyr/drivers/sdhc/sdhc_dwc.h` (was line 145) defined `DWC_SDHC_CMD_LINE_LVL_UP_Pos = 23U`
and `DWC_SDHC_CMD_LINE_LVL_UP_Msk = BIT(23)`, naming that bit as the CMD Line
Signal Level. It is not: per the SD Host Controller Simplified Specification's
Present State Register (offset `024h`, section 2.2.9 in v3.00, the same field
map through v4.20 and unchanged since v1.00), bits `[23:20]` are DAT`[3:0]`
Line Signal Level (bit 20 = DAT0 … bit 23 = DAT3) and bit 24 is CMD Line
Signal Level. Bit 23 is DAT3. The macro's own value was correct — it read a
real, meaningful bit — but its name was wrong, and the code built on that name
accordingly tested one DAT line where it needed four. This file's own adjacent
`DWC_SDHC_CMD_DATA_LINE_STATUS_Msk = 0x01F00000U` (bits 20 through 24
inclusive, four DAT bits plus one CMD bit) is *consistent* with that layout,
but a value being consistent with a spec is not the same as citing the spec,
so the specification section above — not this file's own pre-existing mask —
is the source for the bit positions. (For a reader who wants a second
data point that is emphatically not part of this checkout: Linux encodes the
identical field map in `drivers/mmc/host/sdhci.h` as `SDHCI_DATA_LVL_MASK
0x00F00000`, `SDHCI_DATA_LVL_SHIFT 20`, `SDHCI_DATA_0_LVL_MASK 0x00100000`,
`SDHCI_CMD_LVL 0x01000000` — cited from general knowledge, not read from disk
here; the Linux kernel is not vendored in this tree.) #2035's changelog entry
flagged the naming mismatch at the time without fixing it
(`changelog.d/2035-evk-demo-sdcard-pinctrl-route-fix.md:27-32`). A `PSTATE`
value of `0x020f0000` was once read as "the CMD line is low" on the strength
of the old macro; that conclusion only happened to hold because bit 24 was
also zero in that particular value — the macro itself was reading DAT3, not
CMD, and always had been.

**Likely origin of the `23U`, recorded because it explains the defect rather
than just naming it.** The NXP/Freescale uSDHC block — a different IP
lineage entirely — really does put CMD Line Signal Level at bit 23 in its
`PRES_STATE.CLSL` field, with `DLSL` (the DAT levels) at `[31:24]`; porting a
register definition from a uSDHC-derived header into a DWC_mshc-based driver,
where the two IPs disagree on which line owns which end of that byte, would
produce exactly this off-by-one. What is actually on disk in this repo does
**not** confirm a bit map for either IP — `DWC_SDHC_PSTATE_REG` in
`zephyr/drivers/sdhc/sdhc_dwc.h` (was line 32) is a single opaque `uint32_t`,
`volatile const uint32_t DWC_SDHC_PSTATE_REG;       /* 0x024 Present State                */`,
with no bitfield struct and no `DAT_3_0` or `CMD_LINE_LVL` field names
anywhere under `zephyr/drivers/sdhc/` (`grep -rn "DAT_3_0\|CMD_LINE_LVL\b"
zephyr/drivers/sdhc/` returns nothing). That comment corroborates only that
this register sits at offset `0x024`, consistent with the specification's
Present State Register offset — it says nothing about which bits inside that
word mean what; the bit-position claims earlier in this entry rest on the
specification citation, not on this struct. The driver's vendor-specific
register area genuinely does start at `0x500` (`DWC_SDHC_MSHC_VER_ID_R`,
`DWC_SDHC_EMMC_CTRL_R` at `0x52C`, `DWC_SDHC_EMBEDDED_CTRL_R` at `0xF6C`,
all on disk in the same header), and that does not overlap `0x024` either
way, for what that is worth. The uSDHC-origin theory itself is recorded as
attributed review input, not something confirmed on disk in this checkout:
this `$ZEPHYR_BASE` tree's `modules/hal_nxp/mcux/mcux-sdk-ng` is a
CMake-glue skeleton here — `CMakeLists.txt`, `basic.cmake`, `fixup.cmake`,
and `components/`, `device/`, `drivers/` subdirectories that each hold only
a single `.cmake` glue file — with the actual NXP HAL sources unfetched (the
sibling `middleware/` subdirectory does carry two headers, but they are
unrelated USB config files, not an SD host header). No `fsl_usdhc.h` naming
`PRES_STATE.CLSL` could be located anywhere in this checkout (`find modules
-iname fsl_usdhc.h` returns nothing) to confirm first-hand.

**Severity, stated honestly.** `snps,dwc-sdhc` is instantiated by exactly two
board overlays in this repo, both for E1M-AEN801:
`examples/aen/aen-evk-demo/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay:518`
and
`examples/aen/aen-sdcard-readout/boards/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.overlay:186`,
and both set `no-1-8-v;`. The driver honours that property
(`zephyr/drivers/sdhc/sdhc_dwc.c:981-982`,
`props->host_caps.vol_180_support = config->no_1_8_v ? 0 : ...`), which keeps
`SD_1800MV_FLAG` from ever being set on the card, so the generic SD
subsystem's `sdmmc.c` never calls `sdmmc_switch_voltage()` for either example.
The overlay's own teaching comment already explains why `no-1-8-v` is there:
the 74LVC157 SDIO mux on the E1M-AEN801 EVK runs at 3.3V and cannot pass a
1.8V logic level. So this poll is unreachable on E1M-AEN801 for two
independent reasons — SD enumeration has never completed there at all (a
separate, already-tracked pad-route problem, see below), and even once that
is fixed, the mux hardware means the 1.8V path stays permanently unreachable
on this board. Regression risk from this change is nil, and "wait for a bench
run" would not produce evidence either way on the hardware this repo
currently targets.

**This fix is necessary but not sufficient — it does not make the 1.8V switch
work.** Even on a board that did reach this poll, it cannot succeed as
written today, for a reason unrelated to which bits it checks, and the full
chain needs every hop written down or it looks like the two cited lines
contradict the claim. The generic SD subsystem's `sdmmc_switch_voltage()`
first gates the clock to zero — `subsys/sd/sd_ops.c` (upstream Zephyr,
lines 370-372, not vendored in this alp-sdk tree) sets `card->bus_io.clock =
0` and calls `sdhc_set_io()` — which on this driver lands in the
`ios->clock == 0`
branch and calls `sdhc_dwc_disable_clock(regs)`
(`zephyr/drivers/sdhc/sdhc_dwc.c:911`, its return value discarded — see
below). *That* call, not the one inside `sdhc_dwc_set_voltage()` itself, is
what clears both `DWC_SDHC_CLK_EN_Msk` and `DWC_SDHC_INTERNAL_CLK_EN_Msk`
together (`zephyr/drivers/sdhc/sdhc_dwc.c:159`) — the internal clock is now
off. `sdmmc_switch_voltage()` then sets the new voltage — the same
`subsys/sd/sd_ops.c`, lines 378-379, sets `card->bus_io.signal_voltage =
SD_VOL_1_8_V` and calls `sdhc_set_io()` again — which this time lands in the
`ios->signal_voltage != …` branch, clears the already-clear
`DWC_SDHC_CLK_EN_Msk` once more (`zephyr/drivers/sdhc/sdhc_dwc.c:899`), and
calls `sdhc_dwc_set_voltage()` (`:901`). Inside it, the 1.8V path
re-enables only `DWC_SDHC_CLK_EN_Msk` (`zephyr/drivers/sdhc/sdhc_dwc.c:240`)
— the internal clock is still off from the earlier `:911` call — and this
poll runs immediately after. `sdhc_dwc_enable_clock()`, which is what turns
the internal clock back on, does not run until `sdhc_dwc_set_voltage()`
returns to its caller (`zephyr/drivers/sdhc/sdhc_dwc.c:906`) — too late for
this poll. With the internal clock stopped there is no SDCLK output
regardless of the SD Clock Enable bit, the card never sees a clock edge at
1.8V, and per SD Physical Layer Specification section 4.2.4.2 a card with no
clock holds DAT`[3:0]` low — so this poll times out after roughly
`DWC_SDHC_1P8V_TIMEOUT_US` (10ms) no matter which bits it reads, independent
of the fix in this change. That clock-ordering defect,
`sdhc_dwc_card_busy()`'s "DAT lines" comment against a mask that also
includes CMD, and the ignored `sdhc_dwc_disable_clock()` return value at
`zephyr/drivers/sdhc/sdhc_dwc.c:911` (the checked call at `:329` is fine) are
separate, already-identified defects in the same driver, tracked apart from
this issue and deliberately left untouched here.

**Noted divergence for a future reader, with neither side treated as spec
authority.** The upstream generic SD subsystem's `subsys/sd/sd_ops.c`
(function `sdmmc_switch_voltage()`, roughly lines 320-404 in the Zephyr
v4.4.1 tree this repo's `west.yml` pins — not a path inside this alp-sdk
tree; alp-sdk vendors only `zephyr/drivers/**`) implements the same SD Host
Controller specification voltage-switch procedure, and its own post-switch
check reads, verbatim:
```
	/*
	 * If SD does not drive at least one of
	 * DAT[3:0] high within 1ms, switch failed
	 */
	sd_delay(1);
	if (sdhc_card_busy(card->sdhc)) {
		LOG_DBG("Card failed to switch voltages");
		return -EAGAIN;
	}
```
That "at least one of DAT[3:0] high" wording has no independent spec basis of
its own — it describes whatever its own multi-bit `sdhc_card_busy()` contract
happens to yield, and on this driver that callback is `sdhc_dwc_card_busy()`
(`zephyr/drivers/sdhc/sdhc_dwc.c:946-964`), which masks CMD and DAT`[3:0]`
together and never distinguishes the two at the register level; it is not
evidence for which bit is which, nor for how many DAT lines must be high. The
specification's own host-controller criterion after restarting the clock is
DAT`[3:0]` = `1111b`; anything else is a failure that requires a power-cycle
and re-initialisation at 3.3V. `sdmmc_switch_voltage()`'s looser check and
this driver's stricter one run at different layers and are not required to
agree, but a reader comparing them side by side should not read either
wording as the authority the other lacks.

`sdhc_dwc.h` now names both fields explicitly and derives the combined mask
from them, so the three constants cannot drift apart again:

```c
#define DWC_SDHC_DAT_LINE_LVL_Pos         20U
#define DWC_SDHC_DAT_LINE_LVL_Msk         (0x0FU << DWC_SDHC_DAT_LINE_LVL_Pos)
#define DWC_SDHC_CMD_LINE_LVL_Pos         24U
#define DWC_SDHC_CMD_LINE_LVL_Msk         BIT(DWC_SDHC_CMD_LINE_LVL_Pos)
#define DWC_SDHC_CMD_DATA_LINE_STATUS_Msk (DWC_SDHC_DAT_LINE_LVL_Msk | DWC_SDHC_CMD_LINE_LVL_Msk)
```

The second defect lived in the 1.8V voltage-switch path,
`sdhc_dwc_set_voltage()` in `zephyr/drivers/sdhc/sdhc_dwc.c` (was line 243).
After re-enabling `DWC_SDHC_CLK_EN_Msk`, the driver polled
`DWC_SDHC_PSTATE_REG & DWC_SDHC_CMD_LINE_LVL_UP_Msk` — a single DAT bit,
DAT3, under a macro name that said CMD — and declared the switch stable the
moment that one line read high, even if DAT0, DAT1 or DAT2 had not yet come
up. Per the specification's Present State Register semantics, this poll
needs ALL FOUR of DAT`[3:0]` high to confirm success; CMD Line Signal Level
was never the relevant bit for this check either before or after this
change. The poll now tests `DWC_SDHC_DAT_LINE_LVL_Msk` (bits 20-23) for
equality against itself (all four bits set), leaving the existing `timeout`
variable, its `DWC_SDHC_1P8V_TIMEOUT_US` (10000) initial value, and the
`k_busy_wait(1)` per-iteration granularity all exactly as they were.

The other live call site of the combined mask,
`sdhc_dwc_card_busy()` (`zephyr/drivers/sdhc/sdhc_dwc.c:946-964`), reads
`DWC_SDHC_CMD_DATA_LINE_STATUS_Msk` unchanged in value (`0x01F00000U`) before
and after this change — `DAT_LINE_LVL_Msk` (`0x00F00000U`) OR'd with
`CMD_LINE_LVL_Msk` (`0x01000000U`) reconstructs the same literal bit for bit
— so its behavior is bit-for-bit identical; it needed no edit and is not
being asserted correct by this change either way.

**One more thing for whoever ports this driver to a 1-bit board.** Requiring
all four DAT lines is stricter than the DAT0-alone convention used elsewhere
— e.g. upstream Zephyr's `drivers/sdhc/sam_sdmmc.c` (not vendored in this
alp-sdk tree, whose own `zephyr/drivers/sdhc/` holds only `sdhc_dwc.c` and
`sdhc_dwc.h`) checks only `SDMMC_PSR_DATLL_Pos`, a single bit. On a
board wired 1-bit with DAT1..DAT3 left unrouted, `DWC_SDHC_DAT_LINE_LVL_Msk`
will never read all-ones; the poll will time out deterministically every
time. That degrades gracefully — `-ETIMEDOUT` propagates up, `set_io` fails,
and the SD subsystem falls back to re-initialising at 3.3V rather than
wedging — but it is worth writing down here so a future 1-bit board does not
lose a day rediscovering it.

The 1.8V switch's unreachability on E1M-AEN801 is doubly caused, as above:
SD enumeration has never completed there, a separate pad-route problem
tracked apart from this fix (see
`changelog.d/2035-evk-demo-sdcard-pinctrl-route-fix.md`), and even once
that is fixed, `no-1-8-v` plus the EVK's 3.3V-only mux keep this path
permanently out of reach on that board. This change is a register-naming and
poll-completeness correctness fix verified by reading and by checking the
masks arithmetically (`DAT_LINE_LVL_Msk | CMD_LINE_LVL_Msk` reconstructs
`0x01F00000U` bit for bit); it does not claim the 1.8V switch works
end-to-end, on this board or any other, and nothing here was run on silicon.
