### Fixed — `load_board_yaml(..., metadata_root=R)` mixed two metadata trees: every resolver that reached past it read the in-tree `metadata/` regardless of R (#1485)

`scripts/alp_orchestrate/loader.py`'s `load_board_yaml(path, *, metadata_root=METADATA_ROOT)`
threads the caller's metadata root through the schema/topology pass, but
resolver call sites across `loader.py`, `carveout.py`, `partition.py`,
`kconfig.py`, `validate.py` and `scripts/alp_project_emit/west_libs.py`
reached past it — either straight to the module-global `METADATA_ROOT`
(imported from `.paths` at each module's top), or, one layer further out, to
a `metadata_root: Path = METADATA_ROOT` DEFAULT ARGUMENT on the ADR-0018
library layer (`scripts/alp_orchestrate/libraries.py`'s `resolve_selection` /
`zephyr_kconfig_lines` / `yocto_unwireable` / `yocto_image_install` /
`baremetal_cmake_args`) that a `kconfig.py` call site bound silently by
passing `project` + `slice_` but omitting the third argument. `--metadata-root
<other>` read the requested tree for the schema pass, the storage/carve-out/
partition/SoC-capability checks, and the SoM-preset validators, but the
SDK's own in-tree `metadata/` for: every curated `libraries:` Kconfig line
(base + per-library HW-accelerator backend), the legacy
`library-aliases-v1.json` token table, the curated-library collision check
against `extra_libraries:`, and the standalone `alp_project.py --emit
west-libraries` west.yml fragment. A `board.yaml` could validate `clean`
against facts that exist only in the tree the user explicitly asked NOT to
use, or fail against facts that exist only in the tree they asked for. The
default path (`metadata_root == METADATA_ROOT`, i.e. every CI run, every
example, and `tan validate`) was unaffected — the exposed surface was the
explicit-override callers (`scripts/validate_board_yaml.py --metadata-root`,
`scripts/alp_project.py`).

Fixed by giving `BoardProject` a `metadata_root: Optional[Path] = None`
field plus an `effective_metadata_root()` accessor, set from
`load_board_yaml`'s own `metadata_root` argument. This is a new shape in
alp-sdk, not a mirror of anything tan-cli carries: tan-cli's relocated
planner solves the same problem the opposite way, binding its SDK root once
process-wide via `tan/planner_root.py`'s `bind_sdk_root()` rather than
threading a per-project root. The two `loader.py` sites
(`_resolve_storage` / `_validate_cross_fields`) run before a `BoardProject`
exists, so they now take `metadata_root` as an explicit parameter instead;
every other site that already receives a resolved `BoardProject` now calls
`project.effective_metadata_root()` in place of the module global —
including the five ADR-0018 library-layer call sites in `kconfig.py`, the
`_library_alias_table()` reads (`kconfig.py` now imports `loader.py`'s
already-threaded copy instead of keeping a second, root-less one), the
`extra_libraries:` curated-collision check in `validate.py` (recomputed
per-project; the module-level `_CURATED_LIBRARIES` global stays pinned to
the SDK's own in-tree `metadata/` on purpose -- `check_library_registry.py`'s
self-consistency gate needs the repo's own set, not a project override's),
and `west_libs.py`'s `_emit_library_hw_backends` / `_emit_west_libraries` /
`_load_curated_library_manifest` / `_library_alias_table`, none of which
previously took a `metadata_root` argument at all: `_emit_library_hw_backends`
derived a `repo_root` from `__file__` instead, the other two
(`_load_curated_library_manifest`, `_library_alias_table`) read the
module-level `METADATA_ROOT` import directly, and `_emit_west_libraries`
reached it indirectly through both of them.

`tests/scripts/test_orchestrate_storage.py` gains
`test_flash_device_resolves_against_explicit_metadata_root`, which reproduces
the issue's exact repro against E1M-V2N101 (its `memory_map` derives from the
SoC JSON rather than an inline SoM override, so a scratch root's renamed
region is genuinely reachable only through `metadata_root`): a scratch-only
flash device name resolves against the scratch root, an in-tree-only name
does not, and the in-tree name still resolves against the real `metadata/`
with no override. Confirmed the new test fails on the pre-fix code with the
exact false-pass/false-fail pair the issue describes.

`tests/scripts/test_emit_inference_mac.py` and
`test_emit_cross_core_shmem_cache.py` call `kconfig._emit_inference()`
directly against a hand-built `types.SimpleNamespace` standing in for
`BoardProject` (no `load_board_yaml()` in the loop), so they didn't carry the
new `effective_metadata_root()` method and broke with `AttributeError` under
the full `pytest tests/scripts/` run. Fixed by adding
`effective_metadata_root=lambda: _MR` to each fake project alongside its
other duck-typed attributes.

`tests/scripts/test_orchestrate_libraries.py` gains
`test_curated_library_kconfig_resolves_against_explicit_metadata_root`,
reproducing the adversarial review's manual repro: rename
`CONFIG_CMSIS_DSP_TRANSFORM=y` to a scratch-only marker in a copied metadata
root's `libraries/cmsis-dsp.yaml`, then assert `_slice_alp_conf()` for a
project-wide `libraries: [cmsis-dsp]` board emits the scratch marker (not the
in-tree symbol) under the override, and the reverse with no override.
Confirmed the test fails on the pre-fix `kconfig.py` call shape (the missing
third `metadata_root` argument) with the in-tree symbol leaking through.

`tests/scripts/_orchestrate_support.py` and `test_orchestrate_memory.py`
dropped the `monkeypatch.setattr(alp_orchestrate, "METADATA_ROOT", ...)`
calls their scratch-metadata-root helpers carried: that patch was already
inert (the submodules import `METADATA_ROOT` from `.paths` at their own
module scope, a binding a patch on the `alp_orchestrate` package object never
touches) and the explicit `load_board_yaml(..., metadata_root=...)` argument
was always the only thing that mattered. `BOARD_SCHEMA` keeps its patch --
that one stays a fixed module-scoped import, not threaded through the
project.
