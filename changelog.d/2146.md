### Fixed — TAS2563 amps stayed silent after an I2S restart following clock loss (#2146)

The TAS2563 amps (`0x4d`/`0x4e`) put themselves into software shutdown on
their own -- bench-measured within roughly 100 ms of their TDM/I2S bit clock
stopping, not the ~1 s an earlier pass of this note claimed (see the
register-level bench evidence below) -- and nothing in the audio stack
re-armed them afterwards
(`TAS2563_FAULT_SHUTDOWN_CAUSES`, `include/alp/chips/tas2563.h:376`
("#define TAS2563_FAULT_SHUTDOWN_CAUSES"), citing SLASET3D §7.3.12). The
clock stops on every I2S stop path and on an underrun
(`zephyr/drivers/i2s/i2s_dw.c`'s `tx_stream_disable()`
calls `i2s_clock_disable()`; keeping the clock running across an underrun
instead is tracked separately in #2149), and every in-tree caller set the
amps ACTIVE right after `alp_audio_out_start()` -- since #2132, a
`z_start()` with nothing queued only arms a pending start, so the real
START (and the bit clock with it) does not fire until the first write,
which also explains why
`INT_LTCH0` bit 2 (TDM clock error) was observed latched at the *start* of
playback, not only after a stop/restart.

Added `tas2563_resume()` (`chips/tas2563/tas2563.c`,
`include/alp/chips/tas2563.h:877` ("alp_status_t tas2563_resume")): clears
the latched faults via the existing self-clearing `CLR_INTP_LTCH` bit
(`INT & CLK CFG`, 0x30 bit 2 -- the same mechanism `tas2563_clear_faults()`
already used), then switches `PWR_CTL.MODE` to ACTIVE, in that order --
clearing after ACTIVE would leave a shutdown-causing latch standing.
Precondition: the caller must not call it until after the first successful
`alp_audio_out_write()` following a start or restart, since that write is
what confirms the bit clock is actually running again.

`examples/aen/aen-evk-demo/src/main.c`'s sound phase now checks that
priming write's own return before doing anything else
(`examples/aen/aen-evk-demo/src/main.c:4495` ("silence_rc = alp_audio_out_write")):
on failure it prints the rc, skips `tas2563_resume()` entirely -- leaving
the amps in the shutdown `tas2563_init()` already left them in, rather than
forcing `MODE = ACTIVE` with no confirmed clock, which would reproduce the
exact defect this fix removes -- and fails the phase through its existing
playback-on verdict check
(`examples/aen/aen-evk-demo/src/main.c:4655` ("if (silence_rc != ALP_OK)")).
On success it calls `tas2563_resume()` instead of the old
`tas2563_set_mode(ACTIVE)`; the stale "a quiet stream is already running"
comment, false since #2132, is corrected. The phase's playback-on verdict
also now fails when `resumed_amps != ok_amps`
(`examples/aen/aen-evk-demo/src/main.c:4660` ("if (resumed_amps != ok_amps)")),
so one amp's failed resume no longer PASSes on the strength of the other
amp's PDM-correlated signal. The post-playback fault re-read no longer fails on
`TAS2563_FAULT_TDM_CLOCK`
(`examples/aen/aen-evk-demo/src/main.c:4589-4590` ("shutdown_fault_mask")),
since the bit alone cannot tell a real shutdown apart from a latch that left
`PWR_CTL` at MODE ACTIVE. `include/alp/audio.h`'s
`alp_audio_out_stop()` doc gained an `@note` ordering contract: mute any
external amplifier before calling `alp_audio_out_stop()`, since what
happens to an amp still ACTIVE when the I2S clock stops is chip-specific --
re-arming it afterward is likewise chip-specific (e.g. `tas2563_resume()`),
and that mechanism and the audible thump it produced stay documented on
`tas2563_resume()` (`include/alp/chips/tas2563.h`) rather than duplicated in
`audio.h`. The note's underrun clause -- the clock also stops on an
underrun, not only a deliberate stop -- is scoped to the Zephyr DesignWare
I2S backend (`zephyr/drivers/i2s/i2s_dw.c`); #2149 tracks keeping the clock
running across an underrun instead.

**Dependency: this evk-demo change does not run yet on `dev`.**
`alp_audio_out_start()` on current `dev` fails `-ENOMEM` on an empty TX ring
(`i2s_dw.c`'s `tx_stream_start()` -> `queue_get()`) -- #2132's deferred-start
change, which is what makes "write, then resume" possible at all, has not
landed there yet. Until #2132 merges, `phase_sound()`'s entire
`if (spk != NULL && spk_rc == ALP_OK)` block, including the priming write
and `tas2563_resume()` call above, never executes on a `dev`-only checkout.

**Verification: register-level and audible PASS on `e1m-aen-evk-03`.**
Bench run 2026-09-15 14:58Z, PROBE_RESUME image built from this branch at
`e3fde8705`, both amps, `PWR_CTL`/`INT_LTCH0` read back over I2C:

- Write one block, then `tas2563_resume()`: `PWR_CTL` `0x0c/0x0c`
  (MODE ACTIVE on both amps), `INT_LTCH0` `0x00` immediately after resume.
- After `alp_audio_out_stop()`: `0x0c` at +0 ms, already `0x0e/0x0e` (MODE
  SHUTDOWN on both amps) by the +100 ms poll, and still `0x0e` at +3000 ms --
  the amps shut down within roughly 100 ms of the clock stopping, not the
  ~1 s an earlier pass of this note and of `tas2563_resume()`'s own doc
  claimed (both corrected alongside this fragment).
- Restart WITHOUT calling `tas2563_resume()`: stays `0x0e/0x0e` -- the bug
  this issue reports is reproduced at the register level.
- `tas2563_resume()` called after restart: `0x0c/0x0c` at every checkpoint
  taken -- the fix is confirmed at the register level.
- Gaps of 200 / 500 / 1500 ms between stop and restart, with no
  `tas2563_resume()` call, all ended at `0x0e` -- **no self-heal was observed
  at any tested gap**, so a caller cannot rely on waiting the shutdown out.
- Zero I2C write failures and no faults reported during the run.
- **Open, not diagnosed:** `INT_LTCH0` bit 2 (TDM clock error), `INT_LTCH3`
  bit 6 (boost clock error) and `INT_LTCH4` bit 7 (device power-down event)
  were observed re-latching *during* playback while `PWR_CTL` stayed `0x0c`
  (MODE ACTIVE, not shut down) -- cause not yet diagnosed.

**Audible confirmation.** Attended bench run 2026-09-15 15:20Z on
`e1m-aen-evk-03`, test branch `test/u46-i2s-tas2563-on-reworked-mux` at
`094570cc4` carrying this branch at `bf77cb961` and #2132/#2137 at
`36bc7f03a` (PROBE_RESUME2, RAM load, no MRAM write):

- Tones 1 and 3 each followed `tas2563_resume()` after a successful write,
  with `PWR_CTL` reading `0x0c/0x0c` beforehand: the on-board PDM mics
  measured 1000 Hz at 63.9 dB and 63.4 dB above the in-band median, and
  the maintainer heard both as beeps.
- Tone 2 (restart, no resume) and tones 4-6 (stop, then a 200/500/1500 ms
  gap, then start, no resume) read `0x0e/0x0e`: the mics saw only noise
  and the maintainer heard silence -- exactly the 2 beeps out of 6 tones
  the register readings predict.
- **Thump.** In three trials where the probe called `tas2563_resume()`
  and then stopped the stream within milliseconds, with no further
  writes, the maintainer heard three "kicks". This evidence
  does not separate a power-up pop from a shutdown-on-clock-loss
  transient, so it does not say which one caused it -- see the ordering
  contract on `tas2563_resume()`
  (`include/alp/chips/tas2563.h:843-852` ("@par Ordering contract"))
  and on `alp_audio_out_stop()`
  (`include/alp/audio.h:232-240` ("@note Ordering contract")).

**Known gap this fix does not close.** `tas2563_resume()` only helps a
caller that actually calls it after a restart. A caller who never learns
that an underrun happened -- once #2137 lands, the playback stack will
recover I2S from an underrun transparently; #2137 is still open and
unmerged -- has no trigger to call it at all, and the "no self-heal
observed" result above means the amp will not recover on its own either.
The TAS2563's own clock-error auto-recovery behaviour, if the part offers
one (see this issue's original "Expected" section), remains untested.
