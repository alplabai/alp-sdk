### Fixed — TAS2563 amps stayed silent after an I2S restart following clock loss (#2146)

The TAS2563 amps (`0x4d`/`0x4e`) put themselves into software shutdown on
their own roughly 1 s after their TDM/I2S bit clock stops
(`TAS2563_FAULT_SHUTDOWN_CAUSES`, `include/alp/chips/tas2563.h:376`
("#define TAS2563_FAULT_SHUTDOWN_CAUSES"), citing SLASET3D §7.3.12), and
nothing in the audio stack re-armed them afterwards. The clock stops on
every I2S stop path and on an underrun the backend recovers from
transparently (`zephyr/drivers/i2s/i2s_dw.c`'s `tx_stream_disable()` calls
`i2s_clock_disable()`), and every in-tree caller set the amps ACTIVE right
after `alp_audio_out_start()` -- since #2132, a `z_start()` with nothing
queued only arms a pending start, so the real START (and the bit clock with
it) does not fire until the first write, which also explains why
`INT_LTCH0` bit 2 (TDM clock error) was observed latched at the *start* of
playback, not only after a stop/restart.

Added `tas2563_resume()` (`chips/tas2563/tas2563.c`,
`include/alp/chips/tas2563.h:862` ("alp_status_t tas2563_resume")): clears
the latched faults via the existing self-clearing `CLR_INTP_LTCH` bit
(`INT & CLK CFG`, 0x30 bit 2 -- the same mechanism `tas2563_clear_faults()`
already used), then switches `PWR_CTL.MODE` to ACTIVE, in that order --
clearing after ACTIVE would leave a shutdown-causing latch standing.
Precondition: the caller must not call it until after the first successful
`alp_audio_out_write()` following a start or restart, since that write is
what confirms the bit clock is actually running again.

`examples/aen/aen-evk-demo/src/main.c`'s sound phase now writes one silent
block before touching either amp and calls `tas2563_resume()` instead of
`tas2563_set_mode(ACTIVE)` there; its stale "a quiet stream is already
running" comment, false since #2132, is corrected. `include/alp/audio.h`'s
`alp_audio_out_stop()` doc gained a `@note` that a transparent
underrun/restart recovery restores the SoC-side I2S link only -- an
external codec/amplifier driver may need to be re-armed separately, with
TAS2563 named as the example.

**Host-tested only.** Silicon verification of `tas2563_resume()` itself is
still pending -- it has not yet been run on `e1m-aen-evk-03`. The evidence
motivating this fix, observed on that board (test branch
`test/u46-i2s-tas2563-on-reworked-mux` @ `b572906b1`, both amps audible):
`PWR_CTL` self-transitioning from `0x0c` (MODE ACTIVE) to `0x0e` (MODE
SHUTDOWN) about 1 s after `alp_audio_out_stop(I2S3)`, staying at `0x0e`
after `alp_audio_out_start(I2S3)` restarted playback, and `INT_LTCH0` bit 2
(TDM clock error) already latched within the first 2 s of the *original*
playback start.
