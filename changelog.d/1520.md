### Added — a contract for bench-measured model perf points (`metadata/model_perf/`), and no data to fill it yet

The middle fidelity tier of the edge-AI lifecycle: a customer with **no NPU
toolchain and no silicon** gets exact fit/latency/SRAM for a known model on
their SoM, because we measured it on ours. Tier 1 (the offline static screen)
and tier 3 (`--exact`, which runs the real compiler when the customer happens
to hold it) already ship; this is the one that matters at evaluation time,
when a prospect has neither.

This change lands **the contract only** — schema, validator, tests, capture
recipe. `metadata/model_perf/` is deliberately still empty: a perf point comes
off real silicon or it does not exist, and the first campaign needs a held
bench reservation plus the two open hardware questions below answered.

**`metadata/schemas/model-perf-v1.schema.json`** keys on MEASUREMENT identity,
following `npu-ops-v1.schema.json`'s shape (identity-keyed filename, an
explicit `stance`, and the absence rule stated in the schema's own
`description`). One file per identity at
`metadata/model_perf/<sku>/<target>/<model-slug>-<sha256[0:12]>@<toolchain>-<version>+<hw_rev>+<core>+<profile12>.json`,
where `<target>` is `measured_on.accel_config` when the backend has one and
`measured_on.backend` when it does not (`drpai`, `deepx_dxm1`, `cpu`), and
`<profile12>` digests the toolchain profile — every key under `toolchain` other
than `name` and `version`, today `system_config`, `memory_mode` and `pins`,
derived that way so a profile key added later enters the identity automatically
instead of silently sharing a filename with the points that predate it.

**Every segment after the slug is one that changes the number, and each is
there because leaving it out lets a second measurement silently destroy a first
that is still correct.** The plan proposed
`<sku>/<model-slug>@<toolchain>-<version>.json`, then in its own next task
asked for `person_detect_int8.tflite` captured on `E1M-AEN801` at BOTH
`ethos-u85-256` and `ethos-u55-256` — same SKU, same model, same toolchain, so
the same filename, with the second measurement overwriting the first. The
`<target>` directory fixes that; the model hash in the stem fixes re-benching
changed bytes, because the first point is still the correct answer for a
customer holding the old bytes. `hw_rev`, `core` and the profile digest close
the identical defect on three further axes, each of which was measured as a real
collision before it was fixed: an r1 and an r2 point of the same model on the
same target resolved to one file; an `Ethos_U85_SRAM_Only` and an
`Ethos_U85_SYS_DRAM_Mid` point resolved to one file, whose survivor was the
DRAM-backed one describing a machine the part is not; and every
`backend: "cpu"` point on one SKU resolved to one file, though `E1M-AEN801`
carries `a32_cluster`, `m55_hp` and `m55_he` and an A-class and an M-class
inference of the same model are not comparable. Six such measurements now
produce four files — four distinct identities — where the earlier shape
produced one. It is the same "exactly measured, describes the wrong machine"
hazard the vela-profile question raises, applied to the whole point instead of
to one field.

`measured_on.core` is consequently required, checked against the SKU preset's
`topology:` keys and — only where the SoC spec declares a `paired_core` for the
matched NPU — against that pairing. `metadata/socs/alif/ensemble/e8.json` pairs
the Ethos-U55 high-perf to `m55_hp` and the high-efficiency to `m55_he`, and
pairs the Ethos-U85 to nothing: where the metadata does not know, the gate does
not guess.

`model.source` is required too. A `sha256` is a well-formed 64-hex string
whatever model produced it, so a hash with no provenance passes every
structural check while serving another model's latency under `basis: "bench"` /
`confidence: "certain"`. It takes either shape the campaign actually needs — a
repo-relative path whose bytes are re-hashed against `sha256` and `size_bytes`,
or a `<store>:<path>` citation or URL for the licence-gated and out-of-tree
models that are most of the zoo — and refuses a path on one developer's disk in
either.

`stance: "bench-measured"` is a single-value enum for the same reason
`npu-ops-v1`'s `screening` is: the roadmap explicitly plans a derived data
asset later (a per-NPU throughput model *fitted to these points*), and it must
arrive as a distinguishable, not-yet-invented kind rather than as a silent
redefinition of this one. An estimate that can be mistaken for a measurement
is worse than no estimate.

Every key under `measured` is OPTIONAL, and that is the load-bearing part: a
figure that was not measured is omitted, never estimated and never zero-filled.
`latency_ms_mean` has a `dependentRequired` on `runs`, and `latency_ms_p95` on
both — a mean cannot ship without the evidence of how it was obtained.

**`scripts/validate_metadata.py` gains `_check_model_perf_semantics`** —
fifteen cross-checks a schema cannot express by the time this change lands
(these first thirteen; rule 14 and rule 15 follow below in their own
sections):

1. the PATH is a claim the body must reproduce — SKU directory, target
   directory, and every segment of the
   `<slug>-<sha12>@<toolchain>-<version>+<hw_rev>+<core>+<profile12>` stem;
2. `measured_on.sku` exists under `metadata/e1m_modules/`;
3. `(backend, accel_config)` is a target the SKU actually resolves — derived
   from the host SoC's `npus[]` plus every other SoC spec whose
   `variants[].alp_module_skus` lists the SKU (the on-module DEEPX DX-M1 on
   V2M is found only by that second scan), the same single source of truth
   `tan.model.targets.resolve_targets` reads. It FAILS CLOSED: a SKU whose
   preset or SoC spec cannot be read is a refusal, never a skip;
4. `measured_on.hw_rev` is a key in that family's `hw-revisions.yaml`
   (existence only — a point measured on a `reserved` revision is still a real
   measurement of that revision);
5. `measured_on.core` is a core the SKU's `topology:` declares, and honours a
   `paired_core` where the SoC spec declares one;
6. an `ethos_u` point records BOTH `toolchain.system_config` and
   `toolchain.memory_mode`. Flagless, `ethos-u-vela` picks a default per
   accelerator — `Ethos_U85_SYS_DRAM_Mid` / `Dedicated_Sram_384KB` on the U85,
   DRAM-backed, on a part whose `external_memory_interfaces` declares no DRAM.
   A point captured that way is *exactly measured* and *describes the wrong
   machine*, and recording the profile is the only thing that lets a reader
   tell the two apart. Its `toolchain.name` must also be one the SoC spec's
   own `npu_toolchain` block names (today always `vela`) — `toolchain.name` is
   one of the eight consumer match-key fields, so a `backend: "ethos_u"` point
   naming, say, `dxcom` (DEEPX's compiler) is not cosmetic: it makes the point
   unmatchable, or matchable by the wrong consumer. **This `toolchain.name`
   cross-check is `ethos_u`-only**, for two DIFFERENT reasons on the two
   kinds of backend it excludes. The rationale applies identically to a
   `drpai` or `deepx_dxm1` point, but `metadata/socs/renesas/rzv2n/n44.json`
   and `metadata/socs/deepx/dx/m1.json` (the host SoC specs behind those two
   backends) declare no `npu_toolchain` block at all, since that block is
   written only for an Ethos-U part; there is nothing to cross-check
   `toolchain.name` against for either of them today. Adding an
   `npu_toolchain` block to those two SoC specs — a hardware/toolchain fact
   this change does not state — would let the same guard run for them too.
   `cpu` is excluded for a DIFFERENT reason and it is not the same claim:
   every Alif Ensemble and NXP i.MX93 host SoC spec a `cpu` target resolves
   to (`alif:ensemble:e3`..`e8`, `nxp:imx9:imx93`) DOES declare
   `npu_toolchain.vela` — a CPU point simply has no accelerator toolchain to
   check `toolchain.name` against in the first place, a fact about the
   backend rather than about whether its host SoC spec carries the block.
   Together the two reasons are what the `if backend == "ethos_u":` scoping
   encodes;
7. `latency_ms_p95` is not below `latency_ms_mean` — that is two runs' figures
   pasted into one point;
8. `req_sram_kib * 1024 >= arena_bytes` whenever both are present. The
   on-device selector's fit test is
   `e->arena_sram_kib == 0u || t->req_sram_kib <= e->arena_sram_kib`
   (`src/backends/inference/alp_model_select.c`), so a `req_sram_kib` of 0 —
   or any figure below the arena the same compile reported — fits every arena
   on every engine and turns the fit gate into a check that cannot fail. That
   is the always-fits defect this tier exists to close, re-opened from the data
   side and wearing `basis: "bench"`; the recipe named the hazard in prose and
   nothing enforced it;
9. `measured.runs` meets the recipe's 100-run floor when latency is present, so
   a `runs: 1` point whose mean and p95 are the same single number is refused
   rather than merely discouraged;
10. `capture.date` PARSES with `datetime.date.fromisoformat`, not merely
    matches the ISO shape — `2026-13-45` satisfies the pattern and is not a
    day;
11. a `backend: "cpu"` point reports no nonzero `measured.npu_ops`: there is no
    accelerator on that path, so the figure came from another run's report and
    everything beside it is suspect;
12. no file under `metadata/model_perf/` carries the `_fixture` marker;
13. `capture.reference` AND `model.source` cite a store rather than a local
    filesystem path (a leading `/`, a `C:\` drive prefix, an `OneDrive`
    segment, or a `..` climbing out of the checkout), which would leak a
    developer's machine into a public repo and resolve for nobody else.

The model-perf pass no longer sits behind `if MODEL_PERF_SCHEMA.is_file()`.
Deleting or renaming the schema used to make a point broken fifteen ways
validate at `rc=0`; the glob now runs first, and a missing schema with published
points is itself a failure. A missing schema with no points stays `rc=0` —
there is genuinely nothing to check.

Re-hashing an in-repo `model.source` and requiring it to equal `model.sha256`
deliberately does NOT live in the metadata gate. That path points into
`tests/fixtures/`, which does not exist in the metadata-ONLY scratch clone
`tests/scripts/test_alp_cli_new_som.py::_clone_metadata_gates` runs the gate
against, so a copy there could only ever be a silent skip. It lives in the
pytest suite, which always runs against the real checkout — the same split,
for the same reason, as `_check_soc_vela_memory_profile`'s `source` citations.
The local-path REFUSAL does live in the gate, because it needs no bytes to
decide.

That reachability test asks whether the bytes RESOLVE, never whether the string
looks like a path. Asking the latter inverted the rule outright: it hard-failed
`alp-sdk-internal:models/person_detect_int8.tflite` — the citation form
`capture.reference` mandates — and `https://example.org/zoo/x.tflite`, while
passing the worthless `"somewhere"`, so no point could cite a licence-gated or
out-of-tree model, which is most of the zoo the campaign is for.

**The vacuous-pass trap, and how it is closed.** With `metadata/model_perf/`
empty, every glob-driven check passes over an empty set: green, checking
nothing. So `tests/fixtures/model_perf/E1M-AEN801/ethos-u85-256/person-detect-int8-808cfdfc0cf3@vela-5.1.0+r2+m55_hp+1e562a678c9f.json`
carries a complete perf point that every directory-wide check runs against,
`test_the_perf_point_checks_are_not_vacuous` fails if it disappears, and the
fixture's `_fixture` banner plus check (12) make it structurally impossible to
promote into the published tree. Its identity fields are real (sha256
`808cfdfc0cf3a6fa6f6fa26bfa379ea97c16d5db7334637766e39c3408502e9d`, 300568
bytes, both re-derived from `tests/fixtures/models/person_detect_int8.tflite`);
every value under its `measured` block is a placeholder and says so, as does
its `core`, since nothing in this tree records which core drives the E8's
Ethos-U85. Its `capture.reference` models the SHAPE of a citation rather than a
non-citation, because the recipe tells an operator to copy this file's
structure — a fixture modelling `n/a` would have taught the very shape the gate
exists to refuse.

**Every check is mutation-proved in both directions, 47 mutations, each
green -> RED -> green** — the unmutated document at the path it would
legitimately be committed to must pass before a mutant means anything, then the
mutant must fail with a complaint naming the rule. Fifteen semantic checks,
the schema constraints (`dependentRequired`, the `sha256` pattern,
`additionalProperties`, the `stance` enum, `measured`'s `minProperties`,
`runs`' minimum, the required `core` and `model.source`, and
`capture.reference`'s citation pattern), the resolver's fail-closed behaviour
and its discrete-accelerator scan, and the NPU/core pairing. The identity path
was proved from the other end as well, by writing measurements that differ only
in `hw_rev`, only in the vela profile, and only in the core, and counting the
files: one file under the earlier stem, two under this one, on each axis.
`main()` was proved end to end — a valid published point `rc=0`; the schema
deleted with points on disk `rc=1`; the schema deleted with none `rc=0`.

`capture.reference` also stopped being a three-pattern denylist. A denylist
accepted `see the log`, `ask the operator` and `n/a` — every non-citation
anyone would actually type — so the schema was changed to enforce the citation
shape as an allowlist instead. That allowlist, and `model.source`'s matching
`validate_metadata._STORE_CITATION`, still allowlisted the wrong thing: the
CHARACTER CLASS in front of the colon (`[A-Za-z0-9._+-]*:`), not the store
itself, so `todo:findit`, `x:y`, `ask:Caner` and `note:see the log` all still
read as citations — the exact `see the log` / `ask Caner` shapes the denylist
was replaced to keep out, let back in by the allowlist that replaced it, the
moment a colon followed them. Both expressions now allowlist the STORE
SEGMENT: `alp-sdk-internal`, `https`, or `http`, the only stores that
legitimately appear. This also closes a standing disagreement between the two
— `_STORE_CITATION` permitted `+` (`git+ssh:...`) where the schema pattern did
not — since JSON Schema cannot `$ref` a Python constant, the two patterns are
now required to be byte-identical strings, checked by a dedicated test rather
than left to stay in sync by hand. `C:\bench\run.log` no longer satisfies
either pattern at all (`C` is not one of the three stores); the local-path
refusal (a leading `/` or `\`, a `C:\` drive prefix, an `OneDrive` segment)
still runs first and independently, for both fields, regardless of what the
citation pattern says. That refusal's drive-letter check went through two
shapes before landing correctly. The first widened it to fire on a single
letter followed by `:/` or `:\` ANYWHERE in the string, so
`https:C:\Users\user\log.txt` and `http:D:\bench\run.log` — a drive path
tacked on AFTER a store that reads as legitimate — were caught wherever the
drive letter sat (only a LEADING drive letter was caught before). That widen
was itself unguarded, so a second shape added a word-boundary requirement —
the letter must sit at the string start or after a non-alphanumeric
character — meant to keep it off the `s` immediately before `://` in a real
URL. A word boundary does not discriminate a drive letter from an ordinary
URL path or query token, though: the `a` in `https://example.org/a:/b.log`
sits right after a `/`, satisfying that exact boundary, so that shape
REFUSED that citation — and every citation whose path or query happened to
contain a single-letter token before `:/` — as a local-machine leak. This is
a regression a verification pass caught, not a hypothetical. The check now
discriminates on the SEPARATOR instead of a word boundary: `[A-Za-z]:\`
(backslash, never a legal URL character) is checked ANYWHERE, while
`[A-Za-z]:/` (forward slash) is checked only at the string start or
immediately after the store's own colon — the two positions a drive letter
can legitimately open a reference — so a `c:/` or `a:/` sitting inside an
ordinary path or query segment is read as the URL component it is.

**Left open, deliberately.** A self-consistent point with a fabricated
`model.sha256` and a citation-form `model.source` still passes at `rc=0`: the
store allowlist above closes the "any colon-bearing string is a citation"
hole, but a well-formed `alp-sdk-internal:...` citation is still taken on
faith, because closing it needs a sha256 manifest of known model bytes in
`alp-sdk-internal`, checked by the internal-sync gate — a maintainer decision
in a different repo, out of scope here. Separately, `measured: {"runs": 1}`
with no `latency_ms_mean` present is accepted by both the schema and rule 9
(gated on latency being present) — left as-is rather than closed, because it
publishes a run count over nothing that is asserted, never a number that is
wrong: the schema's `dependentRequired` already refuses `latency_ms_mean` /
`latency_ms_p95` without the run count that produced them, which is the half
of this that is load-bearing. **No longer left open: `https:findit` /
`http:x` / `https:/home/user/x.log`.** A previous round of this change left
these deferred, reasoning that closing them would turn the store allowlist
from three flat store names into a per-store shape table (`alp-sdk-internal`
is not URL-shaped, so it cannot share one), for a hole that "resolves for
nobody, so it is unreproducible in exactly the way a bare `"somewhere"`
already is, just spelled with a colon." Both halves of that reasoning were
wrong, and a verification pass caught it. First, the cost: closing it needs
only a per-store SEPARATOR, not a per-store shape table — the store
allowlist stays a flat three-entry allowlist, now keyed on `<store>:
<separator>` pairs (`_STORE_SEPARATORS`) instead of assuming every store
shares a bare colon. Second, and more important, `https:findit` is not
equivalent to a bare `"somewhere"`: `"somewhere"` fails to resolve as a
repo-relative path and is refused. `https:findit` MATCHES `_STORE_CITATION`
and returns as a citation, which SKIPS the reachability + sha256/size_bytes
re-hash entirely — as a `model.source`, it does not merely fail to
reproduce, it turns the model-bytes integrity check OFF for a fabricated
`sha256`. `https`/`http` now require their own scheme separator (`://`);
`alp-sdk-internal` is unaffected, since a bare colon is its correct and only
citation form. `https:findit`, `http:x` and `https:/home/user/x.log` (the
single-slash variant of the same gap, which the local-path refusal never
caught either, since it is neither a leading local path nor a drive-letter
path) are refused as of this fix.

### Fixed — the E8's Ethos-U85 has no "HG subsystem"; `NPU_HG` is the block's own instance name

The Alif Ensemble E8 has exactly three subsystems — RTSS-HE, RTSS-HP, and the
A32 APSS. `paired_core`'s schema description and
`_check_soc_npu_pairing`'s docstring both invented a fourth ("the E8 U85 on
the HG subsystem") to explain why the U85 legitimately omits `paired_core`.
Grepping the Alif Zephyr, SDK and HAL trees for `RTSS_HG` or "HG subsystem"
returns zero hits. `HG` is the NPU block's own Alif-assigned instance name
(`NPU_HG`, internal codename ZAPHOD, tied to the same block by the
`ZAPHOD_CKOR` bit in `SHMEM_CLK_CTRL`) — not a subsystem.

The conclusion was always correct and stays: `NPU_HG_BASE 0x49042000` is
byte-identical in both M55 cores' generated CMSIS headers -- `rtss_hp/soc.h`
line 3780 and `rtss_he/soc.h` line 3774, both under the Alif DFP's
`Device/soc/AE822FA0E5597/include/` (CMSIS-Pack `AlifSemiconductor.Ensemble`
2.2.0, device `AE822FA0E5597` -- an external vendor package, not vendored in
this tree, so the local checkout path is deliberately omitted) -- unlike the
two Ethos-U55s, which alias one local address (`0x400E1000`) under per-core
names
(`NPU_HP_BASE` / `NPU_HE_BASE`) with an interrupt in only their own core's
NVIC — the control case for what core-pairing actually looks like on this
silicon. The vendor `.pdsc` carries no `Pname` on the U85 `<feature>` element
where both U55 elements carry `Pname="M55_HP"` / `"M55_HE"`, and clock
ownership separates the same way (each U55 gated from its own core's config
block; the U85 gated system-side by `ZAPHOD_CKOR`). Whether the A32 cluster
can also reach the U85 is left unverified, deliberately: there is no A32 SVD
view and no A32 board devicetree NPU node either way.

`tests/scripts/test_soc_npu_pairing.py::test_no_shipped_metadata_or_schema_claims_an_hg_subsystem`
walks `metadata/**` for "HG subsystem" / "HG-subsystem" / "HG_subsystem" and
pins the absence so the fiction cannot come back; mutation-proved by
reintroducing the phrase into `paired_core`'s schema description (green ->
RED, naming the file -> green on revert). Stray comment mentions of the same
fiction in `tests/scripts/test_emit_inference_mac.py`,
`scripts/alp_orchestrate/kconfig.py` and the
`aen-npu-inference-alp-u55` board overlay are corrected alongside for the same
reason, though they are not shipped metadata and the new test does not scan
them. `CHANGELOG.md`'s 2026-05-14 entry, which narrates a since-superseded
`npu_population:` field that once used the same wording, is left as the
historical record it is.

Gen-1 Alif parts (E7/E5/E3/E1/E1C) are unaffected: they declare Ethos-U55s
only and carry no `NPU_HG_BASE` at all — the shared-U85 shape is Gen-2
(E4/E6/E8) only.

### Added — refuse a model-perf point whose vela profile contradicts its own SoC spec (rule 14, no override)

Rule 6 already required an `ethos_u` point to CARRY `toolchain.system_config`
and `toolchain.memory_mode`; nothing checked they agreed with what the
module's own SoC spec declares under `npu_toolchain.vela`. `tan` catches
exactly that mismatch on read — a point recorded under the wrong profile had
already shipped a 5.3x SRAM overstatement at `confidence: "certain"`. A
contradicting point is a mis-measurement, not a deliberate record: leaving it
publishable would force every future consumer (alp-sdk-vscode, dashboards,
customer tooling) to either re-implement the same refusal or repeat the same
error. The maintainer's decision is to refuse it at publish time instead, with
**no override field** — a genuinely off-profile experiment belongs in the raw
capture log `capture.reference` already cites, never in
`metadata/model_perf/`.

`_check_model_perf_semantics` gains rule 14: for a `backend: "ethos_u"` point

### Documented — a bench capture's `hw_rev` is READ off the on-module EEPROM, never typed

`docs/bench/model-perf-capture.md`'s identity table told an operator which
`hw_rev` VALUES are legal (a key in `hw-revisions.yaml`) but not how to find
out which one the module on the bench actually is — leaving the door open to
the exact defect this whole tier exists to close: a hand-typed digit
transposed into a real but wrong revision, publishing a `confidence:
"certain"` point under the wrong module.

`hw_rev` is EEPROM-provisioned per module at production test
(`scripts/program_eeprom.py`) and is the sole authoritative source of SoM
hardware revision — there is no SoM-side ADC cross-check
([`docs/board-id.md`](../board-id.md)). The revision space stays
deliberately open-ended: a legitimately-provisioned new revision must never
be rejected by a fixed enum, so the recipe now says so explicitly rather than
implying a closed list.

The real read path, verified rather than invented: `alp_hw_info_read()` runs
on the module's own firmware over I2C — there is no separate host-side
reader. The recipe now names the portable, any-E1M-SoM command
(`west build -b <target> examples/bringup/board-selftest && west flash`,
Ring-1 per `docs/portability.md` — no chip driver) and the exact line to copy
`hw_rev` from verbatim, `[selftest] SoM identity: <sku> rev <hw_rev> sn
<serial> -> PASS`, plus the two family-specific full-manifest dumps
(`examples/aen/aen-eeprom-manifest`, bench-verified on E1M-AEN801, and
`examples/v2n/v2n-eeprom-manifest-dump`) for when the raw 128-byte manifest is
wanted instead of the summary line. No specific revision is stated anywhere
in the fix — the maintainer was explicitly unsure which one is on the current
bench module, and stating one as fact is exactly the kind of unread claim
this fix removes.

### Fixed — §0(a) treated `ensemble_vela.ini` as unobtainable, and gave the campaign no guidance on which `System_Config` shape to record

`docs/bench/model-perf-capture.md` §0(a) told the operator to "**Get
`ensemble_vela.ini` before you book bench time**" and called it a "**hard
prerequisite** for any Ethos-U capture on the E8" — framing it as a file to go
find. It is not: it already ships inside the Alif SDK tree every AEN capture
host needs anyway, to build the firmware being profiled, at the relative path
`samples/modules/executorch/ensemble_vela.ini` under that SDK checkout's root
(the relative path only — the absolute local one is meaningless on another
machine and is exactly what `check_local_paths.py` exists to refuse). §0(a)
now says what the step actually is: confirm the file is present on the
capture host, and pass it.

Proven against the real file on this checkout, not reasoned from its
existence:

```
vela --accelerator-config ethos-u85-256 --config <ensemble_vela.ini> \
     --system-config Ethos_U85_SRAM_Only --memory-mode Sram_Only \
     --output-dir <tmp> tests/fixtures/models/person_detect_int8.tflite
```

exits `rc=0` and its network summary reports, verbatim, `System configuration
Ethos_U85_SRAM_Only` and `Total SRAM used  72.00 KiB` — one of Alif's own
`System_Config` sections, not one of Arm's built-in eleven, so this single
capture satisfies both rule 14 (a real, declared arena) and rule 15 (a
`system_config` outside the built-in set) at once. §2's "the Alif `.ini` ...
comes from `alp-sdk-internal`" line, which disagreed with the corrected
§0(a), is brought in line: it ships in the Alif SDK tree, not this repo.

**The campaign decision the file's own contents force.** The `.ini` carries
17 sections — 13 `System_Config` (three NPU-level: `Ethos_U85_SRAM_Only`,
`_MRAM`, `_OSPI`; the rest per-core RTSS-HP / RTSS-HE) and 4 `Memory_Mode`.
Measured straight from the file, `Ethos_U85_SRAM_Only` and `RTSS_HP_SRAM_Only`
model different machines despite the same `_SRAM_Only` suffix:
`Sram_burst_length=32` / `Sram_read_latency=2` / `Sram_write_latency=2` /
`Sram_ports_used=Sram_max_reads=Sram_max_writes=2` against
`Sram_burst_length=8` / `Sram_read_latency=29` / `Sram_write_latency=29` with
no `ports_used`/`max_reads`/`max_writes` at all. Both compile `rc=0` for
`ethos-u85-256` under `--memory-mode Sram_Only` on `person_detect_int8.tflite`
— same 72.00 KiB arena, same 7077252 MACs/batch, different flash footprint
(248.95 KiB vs 228.80 KiB). Neither run's network summary prints a cycle count
or an inference-time estimate, so §0(a) states only the memory-timing and
flash-footprint deltas that were actually measured and explicitly does not
claim a latency delta that vela never reported.

`system_config` is one of the `toolchain` keys `_toolchain_profile_digest`
(`scripts/validate_metadata.py`) folds into the filename's `<profile12>`
segment — confirmed against the function itself, which hashes every
`toolchain` key other than `name` and `version`. It is deliberately **not**
one of the eight consumer match-key fields §8 already documents (sku, hw_rev,
core, backend, accel_config, model `sha256`, toolchain name, toolchain
version) — a customer holding no toolchain cannot state a profile. §0(a) now
says both halves: which profile a campaign records changes the point's
on-disk identity and must be a deliberate, stated, consistent choice across
any set of points meant to be compared, even though it never gates a
consumer's match. It recommends the NPU-level `Ethos_U85_SRAM_Only` for a U85
point — the accelerator's own AXI memory view, not an RTSS core's — marked
explicitly as a call to confirm at the bench rather than a sourced fact.
