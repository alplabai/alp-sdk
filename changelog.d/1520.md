### Added — a contract for bench-measured model perf points (`metadata/model_perf/`), and no data to fill it yet

The middle fidelity tier of the edge-AI lifecycle: a customer with **no NPU
toolchain and no silicon** gets exact fit/latency/SRAM for a known model on
their SoM, because we measured it on ours. Tier 1 (the offline static screen)
and tier 3 (`--exact`, which runs the real compiler when the customer happens
to hold it) already ship; this is the one that matters at evaluation time,
when a prospect has neither.

This change lands **the contract only** — schema, validator, tests, capture
recipe. `metadata/model_perf/` is deliberately still empty: a perf point comes
off real silicon or it does not exist, and the first campaign needs a held
bench reservation plus the two open hardware questions below answered.

**`metadata/schemas/model-perf-v1.schema.json`** keys on MEASUREMENT identity,
following `npu-ops-v1.schema.json`'s shape (identity-keyed filename, an
explicit `stance`, and the absence rule stated in the schema's own
`description`). One file per identity at
`metadata/model_perf/<sku>/<target>/<model-slug>-<sha256[0:12]>@<toolchain>-<version>+<hw_rev>+<core>+<profile12>.json`,
where `<target>` is `measured_on.accel_config` when the backend has one and
`measured_on.backend` when it does not (`drpai`, `deepx_dxm1`, `cpu`), and
`<profile12>` digests the toolchain profile — every key under `toolchain` other
than `name` and `version`, today `system_config`, `memory_mode` and `pins`,
derived that way so a profile key added later enters the identity automatically
instead of silently sharing a filename with the points that predate it.

**Every segment after the slug is one that changes the number, and each is
there because leaving it out lets a second measurement silently destroy a first
that is still correct.** The plan proposed
`<sku>/<model-slug>@<toolchain>-<version>.json`, then in its own next task
asked for `person_detect_int8.tflite` captured on `E1M-AEN801` at BOTH
`ethos-u85-256` and `ethos-u55-256` — same SKU, same model, same toolchain, so
the same filename, with the second measurement overwriting the first. The
`<target>` directory fixes that; the model hash in the stem fixes re-benching
changed bytes, because the first point is still the correct answer for a
customer holding the old bytes. `hw_rev`, `core` and the profile digest close
the identical defect on three further axes, each of which was measured as a real
collision before it was fixed: an r1 and an r2 point of the same model on the
same target resolved to one file; an `Ethos_U85_SRAM_Only` and an
`Ethos_U85_SYS_DRAM_Mid` point resolved to one file, whose survivor was the
DRAM-backed one describing a machine the part is not; and every
`backend: "cpu"` point on one SKU resolved to one file, though `E1M-AEN801`
carries `a32_cluster`, `m55_hp` and `m55_he` and an A-class and an M-class
inference of the same model are not comparable. Six such measurements now
produce four files — four distinct identities — where the earlier shape
produced one. It is the same "exactly measured, describes the wrong machine"
hazard the vela-profile question raises, applied to the whole point instead of
to one field.

`measured_on.core` is consequently required, checked against the SKU preset's
`topology:` keys and — only where the SoC spec declares a `paired_core` for the
matched NPU — against that pairing. `metadata/socs/alif/ensemble/e8.json` pairs
the Ethos-U55 high-perf to `m55_hp` and the high-efficiency to `m55_he`, and
pairs the Ethos-U85 to nothing: where the metadata does not know, the gate does
not guess.

`model.source` is required too. A `sha256` is a well-formed 64-hex string
whatever model produced it, so a hash with no provenance passes every
structural check while serving another model's latency under `basis: "bench"` /
`confidence: "certain"`. It takes either shape the campaign actually needs — a
repo-relative path whose bytes are re-hashed against `sha256` and `size_bytes`,
or a `<store>:<path>` citation or URL for the licence-gated and out-of-tree
models that are most of the zoo — and refuses a path on one developer's disk in
either.

`stance: "bench-measured"` is a single-value enum for the same reason
`npu-ops-v1`'s `screening` is: the roadmap explicitly plans a derived data
asset later (a per-NPU throughput model *fitted to these points*), and it must
arrive as a distinguishable, not-yet-invented kind rather than as a silent
redefinition of this one. An estimate that can be mistaken for a measurement
is worse than no estimate.

Every key under `measured` is OPTIONAL, and that is the load-bearing part: a
figure that was not measured is omitted, never estimated and never zero-filled.
`latency_ms_mean` has a `dependentRequired` on `runs`, and `latency_ms_p95` on
both — a mean cannot ship without the evidence of how it was obtained.

**`scripts/validate_metadata.py` gains `_check_model_perf_semantics`**, thirteen
cross-checks a schema cannot express:

1. the PATH is a claim the body must reproduce — SKU directory, target
   directory, and every segment of the
   `<slug>-<sha12>@<toolchain>-<version>+<hw_rev>+<core>+<profile12>` stem;
2. `measured_on.sku` exists under `metadata/e1m_modules/`;
3. `(backend, accel_config)` is a target the SKU actually resolves — derived
   from the host SoC's `npus[]` plus every other SoC spec whose
   `variants[].alp_module_skus` lists the SKU (the on-module DEEPX DX-M1 on
   V2M is found only by that second scan), the same single source of truth
   `tan.model.targets.resolve_targets` reads. It FAILS CLOSED: a SKU whose
   preset or SoC spec cannot be read is a refusal, never a skip;
4. `measured_on.hw_rev` is a key in that family's `hw-revisions.yaml`
   (existence only — a point measured on a `reserved` revision is still a real
   measurement of that revision);
5. `measured_on.core` is a core the SKU's `topology:` declares, and honours a
   `paired_core` where the SoC spec declares one;
6. an `ethos_u` point records BOTH `toolchain.system_config` and
   `toolchain.memory_mode`. Flagless, `ethos-u-vela` picks a default per
   accelerator — `Ethos_U85_SYS_DRAM_Mid` / `Dedicated_Sram_384KB` on the U85,
   DRAM-backed, on a part whose `external_memory_interfaces` declares no DRAM.
   A point captured that way is *exactly measured* and *describes the wrong
   machine*, and recording the profile is the only thing that lets a reader
   tell the two apart. Its `toolchain.name` must also be one the SoC spec's
   own `npu_toolchain` block names (today always `vela`) — `toolchain.name` is
   one of the eight consumer match-key fields, so a `backend: "ethos_u"` point
   naming, say, `dxcom` (DEEPX's compiler) is not cosmetic: it makes the point
   unmatchable, or matchable by the wrong consumer. **This `toolchain.name`
   cross-check is `ethos_u`-only** — the rationale applies identically to a
   `drpai`, `deepx_dxm1` or `cpu` point, but `metadata/socs/renesas/rzv2n/
   n44.json` and `metadata/socs/deepx/dx/m1.json` (the host SoC specs behind
   those backends) declare no `npu_toolchain` block at all, since that block
   is written only for an Ethos-U part; there is nothing to cross-check
   `toolchain.name` against for the other backends today. Adding an
   `npu_toolchain` block to those two SoC specs — a hardware/toolchain fact
   this change does not state — would let the same guard run for them and
   drop the `if backend == "ethos_u":` scoping;
7. `latency_ms_p95` is not below `latency_ms_mean` — that is two runs' figures
   pasted into one point;
8. `req_sram_kib * 1024 >= arena_bytes` whenever both are present. The
   on-device selector's fit test is
   `e->arena_sram_kib == 0u || t->req_sram_kib <= e->arena_sram_kib`
   (`src/backends/inference/alp_model_select.c`), so a `req_sram_kib` of 0 —
   or any figure below the arena the same compile reported — fits every arena
   on every engine and turns the fit gate into a check that cannot fail. That
   is the always-fits defect this tier exists to close, re-opened from the data
   side and wearing `basis: "bench"`; the recipe named the hazard in prose and
   nothing enforced it;
9. `measured.runs` meets the recipe's 100-run floor when latency is present, so
   a `runs: 1` point whose mean and p95 are the same single number is refused
   rather than merely discouraged;
10. `capture.date` PARSES with `datetime.date.fromisoformat`, not merely
    matches the ISO shape — `2026-13-45` satisfies the pattern and is not a
    day;
11. a `backend: "cpu"` point reports no nonzero `measured.npu_ops`: there is no
    accelerator on that path, so the figure came from another run's report and
    everything beside it is suspect;
12. no file under `metadata/model_perf/` carries the `_fixture` marker;
13. `capture.reference` AND `model.source` cite a store rather than a local
    filesystem path (a leading `/`, a `C:\` drive prefix, an `OneDrive`
    segment, or a `..` climbing out of the checkout), which would leak a
    developer's machine into a public repo and resolve for nobody else.

The model-perf pass no longer sits behind `if MODEL_PERF_SCHEMA.is_file()`.
Deleting or renaming the schema used to make a point broken thirteen ways
validate at `rc=0`; the glob now runs first, and a missing schema with published
points is itself a failure. A missing schema with no points stays `rc=0` —
there is genuinely nothing to check.

Re-hashing an in-repo `model.source` and requiring it to equal `model.sha256`
deliberately does NOT live in the metadata gate. That path points into
`tests/fixtures/`, which does not exist in the metadata-ONLY scratch clone
`tests/scripts/test_alp_cli_new_som.py::_clone_metadata_gates` runs the gate
against, so a copy there could only ever be a silent skip. It lives in the
pytest suite, which always runs against the real checkout — the same split,
for the same reason, as `_check_soc_vela_memory_profile`'s `source` citations.
The local-path REFUSAL does live in the gate, because it needs no bytes to
decide.

That reachability test asks whether the bytes RESOLVE, never whether the string
looks like a path. Asking the latter inverted the rule outright: it hard-failed
`alp-sdk-internal:models/person_detect_int8.tflite` — the citation form
`capture.reference` mandates — and `https://example.org/zoo/x.tflite`, while
passing the worthless `"somewhere"`, so no point could cite a licence-gated or
out-of-tree model, which is most of the zoo the campaign is for.

**The vacuous-pass trap, and how it is closed.** With `metadata/model_perf/`
empty, every glob-driven check passes over an empty set: green, checking
nothing. So `tests/fixtures/model_perf/E1M-AEN801/ethos-u85-256/person-detect-int8-808cfdfc0cf3@vela-5.1.0+r2+m55_hp+1e562a678c9f.json`
carries a complete perf point that every directory-wide check runs against,
`test_the_perf_point_checks_are_not_vacuous` fails if it disappears, and the
fixture's `_fixture` banner plus check (12) make it structurally impossible to
promote into the published tree. Its identity fields are real (sha256
`808cfdfc0cf3a6fa6f6fa26bfa379ea97c16d5db7334637766e39c3408502e9d`, 300568
bytes, both re-derived from `tests/fixtures/models/person_detect_int8.tflite`);
every value under its `measured` block is a placeholder and says so, as does
its `core`, since nothing in this tree records which core drives the E8's
Ethos-U85. Its `capture.reference` models the SHAPE of a citation rather than a
non-citation, because the recipe tells an operator to copy this file's
structure — a fixture modelling `n/a` would have taught the very shape the gate
exists to refuse.

**Every check is mutation-proved in both directions, 45 mutations, each
green -> RED -> green** — the unmutated document at the path it would
legitimately be committed to must pass before a mutant means anything, then the
mutant must fail with a complaint naming the rule. Thirteen semantic checks,
the schema constraints (`dependentRequired`, the `sha256` pattern,
`additionalProperties`, the `stance` enum, `measured`'s `minProperties`,
`runs`' minimum, the required `core` and `model.source`, and
`capture.reference`'s citation pattern), the resolver's fail-closed behaviour
and its discrete-accelerator scan, and the NPU/core pairing. The identity path
was proved from the other end as well, by writing measurements that differ only
in `hw_rev`, only in the vela profile, and only in the core, and counting the
files: one file under the earlier stem, two under this one, on each axis.
`main()` was proved end to end — a valid published point `rc=0`; the schema
deleted with points on disk `rc=1`; the schema deleted with none `rc=0`.

`capture.reference` also stopped being a three-pattern denylist. A denylist
accepted `see the log`, `ask the operator` and `n/a` — every non-citation
anyone would actually type — so the schema was changed to enforce the citation
shape as an allowlist instead. That allowlist, and `model.source`'s matching
`validate_metadata._STORE_CITATION`, still allowlisted the wrong thing: the
CHARACTER CLASS in front of the colon (`[A-Za-z0-9._+-]*:`), not the store
itself, so `todo:findit`, `x:y`, `ask:Caner` and `note:see the log` all still
read as citations — the exact `see the log` / `ask Caner` shapes the denylist
was replaced to keep out, let back in by the allowlist that replaced it, the
moment a colon followed them. Both expressions now allowlist the STORE
SEGMENT: `alp-sdk-internal`, `https`, or `http`, the only stores that
legitimately appear. This also closes a standing disagreement between the two
— `_STORE_CITATION` permitted `+` (`git+ssh:...`) where the schema pattern did
not — since JSON Schema cannot `$ref` a Python constant, the two patterns are
now required to be byte-identical strings, checked by a dedicated test rather
than left to stay in sync by hand. `C:\bench\run.log` no longer satisfies
either pattern at all (`C` is not one of the three stores); the local-path
refusal (a leading `/` or `\`, a `C:\` drive prefix, an `OneDrive` segment)
still runs first and independently, for both fields, regardless of what the
citation pattern says. That refusal's drive-letter check is now unanchored
too — `https:C:\Users\user\log.txt` and `http:D:\bench\run.log`, a drive
path tacked on AFTER a store that reads as legitimate, used to be invisible
to it (only a LEADING drive letter was caught); it now fires wherever the
drive letter sits, without also firing on a real `https://`/`http://` URL
(the letter immediately before `://` there is never at a string-start-or-
non-alphanumeric boundary).

**Left open, deliberately.** A self-consistent point with a fabricated
`model.sha256` and a citation-form `model.source` still passes at `rc=0`: the
store allowlist above closes the "any colon-bearing string is a citation"
hole, but a well-formed `alp-sdk-internal:...` citation is still taken on
faith, because closing it needs a sha256 manifest of known model bytes in
`alp-sdk-internal`, checked by the internal-sync gate — a maintainer decision
in a different repo, out of scope here. Separately, `measured: {"runs": 1}`
with no `latency_ms_mean` present is accepted by both the schema and rule 9
(gated on latency being present) — left as-is rather than closed, because it
publishes a run count over nothing that is asserted, never a number that is
wrong: the schema's `dependentRequired` already refuses `latency_ms_mean` /
`latency_ms_p95` without the run count that produced them, which is the half
of this that is load-bearing. Also left open: the store allowlist only
requires `<store>:` plus one non-space character, so `https:findit` and
`http:x` still satisfy it even though neither is a URL (the schema's own
example is `https://example.org/...`) — closing it would mean requiring
`https://` and `http://` (not merely `https:`/`http:`) for those two stores.
Decided against for now: `alp-sdk-internal` is not URL-shaped, so the
allowlist would stop being three flat store names and become a per-store
shape table, for a hole that is a malformed citation rather than a working
one — `https:findit` resolves for nobody, so it is unreproducible in exactly
the way a bare `"somewhere"` already is, just spelled with a colon. The same
gap lets `https:/home/user/x.log` (a single slash, not `https://`'s double)
pass the store-citation pattern too, and the local-path refusal above does
not catch it either, since it is neither a leading local path nor a
drive-letter path — it is the store-allowlist gap wearing a `/`. Revisit if
either shape is ever seen in a real submitted point rather than a probe.

**`docs/bench/model-perf-capture.md`** is the recipe, written BEFORE any bench
time is spent so the first campaign produces points someone else can re-derive:
fixing the identity first, the exact per-backend toolchain invocation (and why
vela's `rc=0` is not a placement verdict), the flash+run procedure per SoM by
reference to the existing bring-up docs rather than restated, latency as
`mean` + `p95` over >= 100 timed runs after >= 10 discarded warm-ups and never
a single shot, the public/private split (points are public, raw captures go to
`alp-sdk-internal` and are CITED not embedded), and a per-field table of what
to do when a figure cannot be measured — omit it.

It also records the two OPEN hardware questions prominently, because a campaign
run before they are answered has to be recaptured: (a) the vela profile
question above, and (b) `req_sram_kib` currently reports the arena alone (the
tier-2 plan records 72 KiB measured for `person_detect_int8.tflite`) against
roughly 307 KiB genuinely SRAM0-resident, so until the per-part answer exists a
point should omit the field rather than publish the arena under a name that
promises more.

One gap is stated rather than glossed, and stated precisely: **no AEN example
times an inference today, and `<alp/inference.h>` exposes no latency
accessor** — `examples/aen/aen-npu-inference-alp` runs `alp_inference_invoke()`
once and prints `RESULT PASS`. But the campaign does not start from nothing:
`examples/camera-vision/ai-object-detection-realtime/src/main.c:227-232` and
`examples/camera-vision/ai-camera-viewer/src/inference_loop.c:112-122` already
bracket `alp_inference_invoke()` with `k_cycle_get_32()` and convert with
`k_cyc_to_us_floor32()`. Neither is a bench harness — one invoke per frame, no
warm-up discard, no run loop, no percentile — so what the first campaign owes is
the recipe's loop, not the measurement primitive. Until it lands a point may
legitimately carry the compile-derived figures and omit latency entirely, which
is exactly what the optional-`measured` design is for.

Nothing consumes this data yet. The tiered resolution in `tan model check`
(precomputed -> exact-if-toolchain -> static, emitting the `basis: "bench"` its
envelope has reserved and never produced) is the tan-cli half and lands
separately.
