### Documented — AEN `memory_map:` gaps investigated; #1975's per-unit evidence corrected (#2053)

`E1M-AEN803.yaml` and `E1M-AEN801.yaml` both carry `mram_main.base:
"TBD"` and neither represents the external OSPI0 HyperRAM/NOR in
`memory_map:`. Both were investigated for this issue; neither ships a
data change here, because both collide with real invariants elsewhere
in the tree rather than a false positive in a check:

- Resolving `mram_main.base` to `0x80000000` is correct for IPC
  carve-out purposes (`scripts/alp_orchestrate/aperture.py`'s
  `classify_region()` already has a whole-device-alias exception for
  it), but trips `scripts/gen_zephyr_board.py::_aen_check_map_overlaps()`,
  which has no such exception and reads the resolved region as
  overlapping `mcuboot` -- a real collision that function's own
  docstring silently relied on `mram_main.base` staying non-integer to
  avoid. Needs a fix to that function before `base` can resolve.
  `metadata/e1m_modules/E1M-AEN801.yaml`/`E1M-AEN803.yaml` document the
  finding in place.
- A `hyperram` `memory_map:` row for `E1M-AEN803` (base `0xa0000000`,
  64 MiB, confirmed against Alif's own Linux devicetree) was tried and
  reverted: its end address `0xa4000000` becomes the highest
  `base + size` across the whole table, and
  `scripts/check_atoc_reservation.py`'s ATOC top-anchor rule requires
  whichever region owns that file-wide maximum to be named `atoc`
  regardless of aperture -- filed as alp-sdk#2069. Both external
  memories' population facts stay correctly recorded in
  `on_module.hyperram` / `on_module.ospi_memories.ospi0`.

What does ship: `metadata/boards/e1m-evk.yaml`'s alp-sdk#1975 record now
also carries a second data point -- a second board (`e1m-aen-evk-03`,
serial `2026W36-0002`) censused 2026-09-12 found all six INA236
answering, confirming the missing-INA236 condition is per-unit, not
batch-wide or design-level.
