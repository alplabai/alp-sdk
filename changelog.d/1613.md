### Fixed — scaffolded `board.yaml` and the `multicore-rpmsg` catalog entry disagreed on the RPMsg carve-out default (#1613)

`metadata/templates/board.yaml`'s commented `ipc:` stanza said `carve_out_kb:
512`; `metadata/templates/catalog-v1.json`'s `rpmsg_carve_out_kb` parameter
said `"default": 256`. Nothing in the tree derived either number, so a reader
could not tell which was intended.

512 is not merely the larger, safer-looking choice: `resolve_carve_outs()`
(`scripts/alp_orchestrate/carveout.py`) prefers the non-cacheable region,
smaller-first, and on RZ/V2N/V2M the only non-cacheable region an
`[a55_cluster, m33_sm]` pair can both reach is `ocram_low`
(`metadata/socs/renesas/rzv2n/n44.json`), which is exactly 512 KiB. A default
of 512 there consumes the *entire* region, leaving nothing for a second IPC
entry.

`metadata/templates/catalog-v1.json`'s existing `256` default is already
proven in tree — `examples/multicore/rpmsg-aen/board.yaml` ships it as-is,
using under 5% of E1M-AEN801's 5632 KiB `mram_main` — and 256 KiB is half of
`ocram_low`, not all of it. `metadata/templates/board.yaml`'s scaffolded
comment now matches at `256`, and both files carry a comment/description
pointing at the SoC facts and allocator behaviour the number is derived
from, so the next reader is not left to guess again.

`alp.lock` regenerated (metadata digest moved).

Note: `examples/multicore/rpmsg-v2n/board.yaml` and
`examples/multicore/heterogeneous-offload/board.yaml` both still declare
`carve_out_kb: 512` against this same `ocram_low` region — out of scope
here (this fix only touches the two scaffolding/catalog defaults), but the
same exhaustion applies to them and is worth a follow-up.
