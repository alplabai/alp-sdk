### Fixed — `alp_i2s`/`alp_audio_out` stop/start/write returned `ALP_ERR_IO` forever after a TX underrun or RX overrun (#2137)

Once an I2S stream started and then went quiet for longer than its queued
audio, `alp_i2s_stop()`, `alp_i2s_start()`, and `alp_i2s_write()` all failed
`ALP_ERR_IO` (`-5`) until the process restarted — `alp_audio_out_*` sits on
top of `<alp/i2s.h>`, so the same gap broke `alp_audio_out_stop()` /
`alp_audio_out_start()` too. **Proven on silicon** (`e1m-aen-evk-03`): on the
previous image (pre-`#2137`), the U46 probe's `alp_audio_out_stop(I2S3)`
followed by `alp_audio_out_start(I2S3)` both returned `-5` on the same
sequence. On a build of the `#2137` fix (`2e92da60a`, merged into test
branch `273b34e76`, image md5 `41d4acff9e9d6aa73d65380395208dc6`), the SAME
sequence printed `alp_audio_out_stop(I2S3) [stop-control, amps still
ACTIVE] -> 0` then `alp_audio_out_start(I2S3) [restart ...] -> 0` --
`stop()` and `start()` each returned `0` on silicon. The bracketed text
is the probe's own fixed label, not a measurement: audibility was NOT
checked in that run, and the underrun precondition itself (the stream
actually reaching `I2S_STATE_ERROR` before that stop) was NOT observed
either -- nothing in the probe prints it. This data is measured on
`2e92da60a` specifically -- review rounds 2 and 3 (this fragment's own
remaining content) were not re-run on silicon; the image's test branch
(`273b34e76`) contains `2e92da60a` but neither later round. The
`write()`-path recovery and the RX-side fix below are unit-tested only,
never run on this bench at any commit.

Root cause: the Alif DesignWare I2S driver follows Zephyr's own trigger
contract, and the backend never issued the ONE trigger that gets a stream
back out of it. When the TX queue runs dry while `RUNNING`, the TX IRQ
drops the stream into `I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:668-699` ("stream->state = I2S_STATE_ERROR;"));
RX does the same on slab/queue exhaustion
(`zephyr/drivers/i2s/i2s_dw.c:805-841` ("stream->state = I2S_STATE_ERROR;")).
From `ERROR`: `DRAIN`/`STOP` need `RUNNING` and `-EIO`
(`zephyr/drivers/i2s/i2s_dw.c:442-470` ("stream->state != I2S_STATE_RUNNING")), `START` needs
`READY` and `-EIO`s too
(`zephyr/drivers/i2s/i2s_dw.c:420-440` ("stream->state != I2S_STATE_READY")), and TX
`i2s_write()` needs `RUNNING` or `READY` and `-EIO`s as well
(`zephyr/drivers/i2s/i2s_dw.c:532-553` ("dev_data->tx.state != I2S_STATE_READY")).
Zephyr's `enum i2s_trigger_cmd` (`include/zephyr/drivers/i2s.h`) gives
exactly two ways out: `I2S_TRIGGER_PREPARE`, valid ONLY from `ERROR`, which
moves to `READY` and drops the queue
(`zephyr/drivers/i2s/i2s_dw.c:449-456` ("stream->queue_drop(stream);")); and
`I2S_TRIGGER_DROP`, valid from any state but `NOT_READY`, which also moves
to `READY`
(`zephyr/drivers/i2s/i2s_dw.c:471-480` ("I2S_STATE_NOT_READY")). `src/backends/i2s/
zephyr_drv.c` used neither.

Fixed at the same shared layer #2132 already routes every `<alp/i2s.h>` and
`<alp/audio.h>` caller through — using only the documented Zephyr trigger
contract, never driver-private state:

- **`z_stop()`** falls back to `DROP` when `DRAIN` fails — covering both the
  pre-existing `#2132` "never really started" case and the new `#2137`
  "underran/overran into `ERROR`" case with one fallback in both
  directions, since `DRAIN` refuses both `READY` and `ERROR` for the
  identical reason (`state != RUNNING`). For TX, when the sidecar's
  `tx_started` already says the stream is not genuinely running, the
  doomed `DRAIN` attempt is skipped entirely rather than issued just to
  watch it fail — `i2s_dw`'s own `DRAIN` refusal logs its own `LOG_ERR`
  (`zephyr/drivers/i2s/i2s_dw.c:460` ("DRAIN trigger: invalid state")), so this also removes a log line on
  an already-known, already-handled path (review round 2, findings 2/3).
  The `DROP` fallback is gated on `h->started` for RX only, matching
  `z_close()`'s own gate — `DROP` tears down real RX clock hardware
  (`zephyr/drivers/i2s/i2s_dw.c:1295-1343` ("i2s_clock_disable(i2s);")), and must not run for an RX
  handle that was never started (review round 2, finding 8). A
  never-started RX handle returns `ALP_OK` in that case (review round 3,
  finding 10) — NOT `DRAIN`'s own `-EIO`, which the finding-8 gate would
  otherwise have surfaced as a user-visible regression from the
  pre-`#2137` behaviour (an unconditional `DROP` that also returned
  `ALP_OK`): stopping something that was never started, or already
  stopped, is benign by the same convention the TX side already follows.
  Otherwise, either trigger succeeding marks the TX flags stopped and
  returns `ALP_OK`; both failing (or `DROP` being skipped for a genuinely
  never-started TX stream, or the RX case above) surfaces `DRAIN`'s own
  failure
  (`src/backends/i2s/zephyr_drv.c:630` ("rc = _errno_to_alp(i2s_trigger(dev, _to_dir(h->cfg.direction), I2S_TRIGGER_DRAIN));")).
  `alp_audio_out_stop()`'s `@return` now documents the both-refused
  `ALP_ERR_IO` case
  (`include/alp/audio.h:249` ("both the primary stop trigger and")).
- **`z_start()`** retries a real `START` that fails `ALP_ERR_IO` with one
  `PREPARE`-then-retry cycle, in both directions; a failed `PREPARE` leaves
  the ORIGINAL `START` error as the reported failure, not `PREPARE`'s own.
  Since `PREPARE` drops the ring (normally already empty for a TX
  underrun; it also frees any block that raced in, since
  `i2s_dw_write()` checks state separately from `queue_put()`,
  `zephyr/drivers/i2s/i2s_dw.c:544-565` ("queue_put(&dev_data->tx.mem_block_queue, mem_block, size);")
  — review round 2, finding 7), the
  retried `START` on TX correctly lands in the pre-existing `#2132`
  empty-queue deferral instead of failing again
  (`src/backends/i2s/zephyr_drv.c:505` ("if (rc == ALP_ERR_IO) {")). That
  deferral branch now also clears `tx_started` via a new
  `_mark_tx_needs_restart()` helper instead of leaving it stale (review
  round 2, finding 2 — see the invariant paragraph below). A successful
  recovery logs one `LOG_WRN` — otherwise-silent evidence a `PREPARE`
  actually ran (review round 2, finding 3).
- **`z_write()`** (TX) retries an `i2s_write()` that fails `-EIO` with the
  same `PREPARE` shape, and retries the write ONCE REGARDLESS of whether
  its own `PREPARE` succeeded (finding 4): a CONCURRENT call (another
  writer's own `PREPARE`, or a `stop()`'s `DROP`) may already have taken
  the stream out of `ERROR` between this write's own trigger failing and
  its own `PREPARE` running, so a refused `PREPARE` here does not prove
  the stream is still stuck — only that it was not FROM `ERROR` at that
  exact instant. If the stream genuinely still is in `ERROR`, the retry
  just gets the same `-EIO` and falls into the existing free-and-report
  path, no new failure mode; previously this case gave up immediately and
  could drop a write a concurrent recovery would otherwise have accepted.
  The TX flag reset (via `_mark_tx_needs_restart()`) runs ONLY when THIS
  CALL's own `PREPARE` succeeded — review round 2's first pass made this
  reset unconditional instead, reasoning that the ORIGINAL `i2s_write()`
  failing already proved `tx_started` stale regardless of what this
  `PREPARE` reports. That reasoning missed that a CONCURRENT call updates
  the very same flags under the very same lock as part of its own
  trigger, so by the time this call's own `PREPARE` observes a refusal,
  the flags already reflect whatever that concurrent call actually did —
  correctly. Round 3 review reproduced this on real API interleavings
  (`fake_i2s_set_write_fail_hook()`, firing a genuine `alp_i2s_write()` /
  `alp_i2s_stop()` / `alp_i2s_start()` call from inside this fake's own
  `-EIO` return, the actual race window): a second writer whose `PREPARE`
  lost the race to a first writer's own recovery had the unconditional
  version clear the first writer's valid `tx_started` and queue its own
  retry, firing a spurious `START` on an ALREADY-RUNNING stream
  (`i2s_dw`'s real `-EIO`) and DROPping the first writer's still-good
  audio (`writerB=-5` observed); a writer whose `PREPARE` lost the race
  to a concurrent `stop()` had it re-arm a restart the caller never asked
  for, resuming playback without an explicit `start()`
  (`running_after_writer=1` observed on a stream the caller had just
  stopped). Reverted to the conditional reset; only the `LOG_WRN` was
  ever conditional on this call's own `PREPARE` succeeding, unchanged.
  The retry itself always runs, with the SAME slab block (never freed
  before the retry, never double-freed after it either way)
  (`src/backends/i2s/zephyr_drv.c:775` ("err = i2s_write(dev, slab_block, bytes);")).

**The RX-side leak (review round 2, finding 1):** the RX ISR's own
`I2S_STATE_ERROR` entry
(`zephyr/drivers/i2s/i2s_dw.c:805-841` ("stream->state = I2S_STATE_ERROR;")) orphaned
the just-filled block on EITHER of its two error exits — a failed
`k_mem_slab_alloc()` for the next block (`k_mem_slab_alloc()` sets `*mem =
NULL` on failure, so the just-filled block's own pointer, held only in a
local, was never freed), or a failed `queue_put()` of the one just filled
(the fresh block the alloc just returned replaces `stream->mem_block`,
so `rx_stream_disable()`'s own free — which only ever frees
`stream->mem_block` — never sees the orphaned one either). With the
2-block slab `src/backends/i2s/zephyr_drv.c` allocates, two overruns
exhausted it and the third `rx_stream_start()` returned `-ENOMEM`
permanently — RX has no NOMEM-as-stale-flag branch (that is TX-only).
Fixed at the actual source, `zephyr/drivers/i2s/i2s_dw.c`: both error
exits now `k_mem_slab_free()` the block they would otherwise have
orphaned, with an inline `alp-sdk issue #2137` note alongside the file's
existing ADR 0017 Tier-2 provenance header. No `zephyr_drv.c` change was
needed for this half of the fix — RX carries no sidecar flags to begin
with (`z_start()` never defers for RX).

**A second, pre-existing RX bug on the same recovery path (review round
3, finding 3):** `rx_stream_start()` never reset `mem_block_offset`,
which the ISR's own `alloc`-failure exit above leaves at the full block
size (set at `zephyr/drivers/i2s/i2s_dw.c:784` ("stream->mem_block_offset = offset;")),
right before that exit). `I2S_TRIGGER_PREPARE` doesn't touch it either
(`zephyr/drivers/i2s/i2s_dw.c:481-488` ("case I2S_TRIGGER_PREPARE:")).
So the first ISR firing after
ANY recovery inherited a stale "already full" offset on a block that was
never actually filled, computed zero frames to read, and queued it as a
"complete" frame anyway — stale/garbage sample data delivered silently on
literally the first frame after every recovery, not a leak or corruption,
but wrong data with no error returned anywhere. Fixed by resetting
`mem_block_offset` to `0` in `rx_stream_start()`
(`zephyr/drivers/i2s/i2s_dw.c:1102` ("stream->mem_block_offset = 0;")),
mirroring `tx_stream_start()`'s own
reset. The fake now mirrors the fixed driver's exact exit order too
(alloc the next block first, free the filled one on either error exit,
enter `I2S_STATE_ERROR` when its own ring is full) — see
`fake_i2s_rx_complete_block()`.

**The `tx_started` invariant (review round 2, finding 2):** the file
header's own `tx_started => !tx_pending_start` invariant broke on this
exact sequence: deferred `start()` → `write()` fires the real `START` →
underrun → `start()`: the real `START` `-EIO`s, `PREPARE` succeeds, the
retried `START` `-ENOMEM`s (the ring is empty again, per the `#2132`
empty-queue deferral) — the NOMEM branch cleared `tx_block_queued` and set
`tx_pending_start`, but left `tx_started` untouched at `true`. `tx_started`
had gone write-only after the original `#2137` fix (nothing read it), so
this went unnoticed until `z_stop()`'s new skip-`DRAIN` check above gave it
a reader again. Fixed by routing that branch through the new
`_mark_tx_needs_restart()` (`src/backends/i2s/zephyr_drv.c:478`
("static void _mark_tx_needs_restart(alp_z_i2s_side_t *s)")) instead of a
manual two-field assign; the invariant now holds via either that function
or `_mark_tx_stopped()` — the file header comment names both.

`include/alp/i2s.h`'s `alp_i2s_start()`/`alp_i2s_stop()`/`alp_i2s_write()` and
`include/alp/audio.h`'s `alp_audio_out_start()`/`alp_audio_out_stop()`/
`alp_audio_out_write()` document that an underrun/overrun is recovered
transparently — the caller does not need to detect or clear the condition
itself before calling any of them again.

Regression tests: `tests/unit/i2s_start_defer/` extends its fake I2S device
to enforce the same state machine — a new `fake_i2s_tx_simulate_underrun()`
(the deterministic, single-threaded stand-in for the real IRQ's "ring found
empty" transition, since native_sim has no interrupt timeline to reach it
asynchronously) drops the fake into `I2S_STATE_ERROR`, from which `START`/
`STOP`/`DRAIN`/write() all refuse exactly as real `i2s_dw` does, and only
`PREPARE`/`DROP` recover it. Covers: start, write, underrun, then stop
returns `ALP_OK`; underrun, then start (re-defers) plus write (fires the
real trigger) plays again; underrun, then write alone resumes playback with
no slab leak or double free (proven against the REAL `k_mem_slab`'s own
free-block count via a new `fake_i2s_slab_free_count()`, not just the fake's
bookkeeping); and PREPARE refused propagates the ORIGINAL error rather than
PREPARE's own, proven via a new `fake_i2s_prepare_call_count()` so the test
can't pass merely by coincidence on a backend with no recovery logic at all.

Review round 2 adds: `fake_i2s_rx_simulate_overrun()` / RX state modeling
(`fake_i2s_rx_running()`, `fake_i2s_rx_in_error()`,
`fake_i2s_rx_slab_free_count()`, `fake_i2s_rx_complete_block()`) and
`test_rx_overrun_recovers_no_slab_leak`, which runs three overrun-and-
recover cycles against the REAL RX `k_mem_slab`'s free-block count, then a
genuine completed-frame `read()` -- this does NOT prove the driver-level
leak fix itself: `zephyr/drivers/i2s/i2s_dw.c` is read-verified and
modelled by the fake (which mirrors the fixed driver's exact free-on-both-
error-exits behaviour), but is not compiled by any test in this suite (or
any other) -- native_sim has no DesignWare I2S hardware for it to target.
The test's own red proof (round 2) reverted the FAKE's own model back to
the pre-fix (leaky) behaviour, not `i2s_dw.c`, to demonstrate the test
catches that class of bug at all;
`fake_i2s_drain_call_count()` and `test_underrun_start_retry_clears_
started_invariant`, which proves the `tx_started` invariant fix by
observing that `z_stop()` skips the real `DRAIN` trigger rather than
issuing a doomed one; `fake_i2s_force_write_fail()` and
`test_underrun_write_retry_fails_after_prepare_succeeds_no_leak`, which
proves a RETRY failure (distinct from the original underrun) surfaces as

refused_propagates_original_error`, the `start()`-side sibling of the
existing `write()` PREPARE-refused case; `fake_i2s_force_drop_fail()` and
`test_stop_both_drain_and_drop_refused_surfaces_drain_error`, which makes
`z_stop()`'s both-refused return path reachable in a test; and
`tests/unit/audio_out_start_defer`'s `test_mono_underrun_stop_start_write_
recovers`, proving the same recovery sequence composes correctly through
`<alp/audio.h>`, not just `<alp/i2s.h>` directly.

Review round 2 also added a knob, `fake_i2s_tx_simulate_concurrent_
recovery()`, and a test built on it, to justify the unconditional-reset
change described above. Round 3 review found and removed both: the knob
cleared `tx_error` directly with no trigger and no flag update, a state
no real caller could ever produce, so the test it backed could not have
caught the bug it was meant to guard — and did not (`prepare_calls == 1`
and `write2_rc == ALP_OK` came out identically whichever version of the
fix ran underneath it). Replaced with `fake_i2s_set_write_fail_hook()`,
which fires a genuine `alp_i2s_*` call from inside `fake_i2s_write()`'s
own `-EIO` return — the actual unlocked race window `z_write()` has, no
knob required — and three tests built on it that DO discriminate:
`test_ilv_a_second_writer_after_concurrent_writer_recovery` (RED on
`4d50eb653`: `writerA=0 running_after_A=1 writerB=-5
running_after_B=0`; GREEN: `writerB=0 running_after_B=1`),
`test_ilv_b_writer_does_not_undo_concurrent_stop` (RED on `4d50eb653`:
`stop=0 running_after_stop=0 writer=0 running_after_writer=1`; GREEN:
`running_after_writer=0 start2=0 running_after_start2=1`), and
`test_ilv_d_writer_resumes_after_concurrent_start_recovery` (passes on
both -- additional coverage, not a discriminator for this specific bug).
