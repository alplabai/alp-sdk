### Fixed — `alp_i2s`/`alp_audio_out` stop/start/write returned `ALP_ERR_IO` forever after a TX underrun or RX overrun (#2137)

Once an I2S stream started and then went quiet for longer than its queued
audio, `alp_i2s_stop()`, `alp_i2s_start()`, and `alp_i2s_write()` all failed
`ALP_ERR_IO` (`-5`) until the process restarted — `alp_audio_out_*` sits on
top of `<alp/i2s.h>`, so the same gap broke `alp_audio_out_stop()` /
`alp_audio_out_start()` too. **Proven on silicon** (`e1m-aen-evk-03`): on the
previous image (pre-`#2137`), the U46 probe's `alp_audio_out_stop(I2S3)`
followed by `alp_audio_out_start(I2S3)` both returned `-5` on the same
sequence. On a build of the `#2137` fix (`2e92da60a`, merged into test
branch `273b34e76`, image md5 `41d4acff9e9d6aa73d65380395208dc6`), the SAME
sequence printed `alp_audio_out_stop(I2S3) [stop-control, amps still
ACTIVE] -> 0` then `alp_audio_out_start(I2S3) [restart ...] -> 0` — the
stop/start recovery path is silicon-proven. The underrun state itself
(the stream actually reaching `I2S_STATE_ERROR` before that stop) was NOT
directly observed on this run — nothing in the probe prints it — so this
data confirms the RECOVERY path works on real hardware, not that the probe
independently confirmed the precondition. The `write()`-path recovery and
the RX-side fix below are unit-tested only, not (yet) run on this bench.

Root cause: the Alif DesignWare I2S driver follows Zephyr's own trigger
contract, and the backend never issued the ONE trigger that gets a stream
back out of it. When the TX queue runs dry while `RUNNING`, the TX IRQ
drops the stream into `I2S_STATE_ERROR`
(`zephyr/drivers/i2s/i2s_dw.c:516-524` ("stream->state = I2S_STATE_ERROR;"));
RX does the same on slab/queue exhaustion
(`zephyr/drivers/i2s/i2s_dw.c:636-647`). From `ERROR`: `DRAIN`/`STOP` need
`RUNNING` and `-EIO` (`zephyr/drivers/i2s/i2s_dw.c:301-321`), `START` needs
`READY` and `-EIO`s too (`zephyr/drivers/i2s/i2s_dw.c:278-283`), and TX
`i2s_write()` needs `RUNNING` or `READY` and `-EIO`s as well
(`zephyr/drivers/i2s/i2s_dw.c:390-394`). Zephyr's `enum i2s_trigger_cmd`
(`include/zephyr/drivers/i2s.h`) gives exactly two ways out:
`I2S_TRIGGER_PREPARE`, valid ONLY from `ERROR`, which moves to `READY` and
drops the queue (`zephyr/drivers/i2s/i2s_dw.c:340-347`); and
`I2S_TRIGGER_DROP`, valid from any state but `NOT_READY`, which also moves
to `READY` (`zephyr/drivers/i2s/i2s_dw.c:329-338`). `src/backends/i2s/
zephyr_drv.c` used neither.

Fixed at the same shared layer #2132 already routes every `<alp/i2s.h>` and
`<alp/audio.h>` caller through — using only the documented Zephyr trigger
contract, never driver-private state:

- **`z_stop()`** falls back to `DROP` when `DRAIN` fails — covering both the
  pre-existing `#2132` "never really started" case and the new `#2137`
  "underran/overran into `ERROR`" case with one fallback in both
  directions, since `DRAIN` refuses both `READY` and `ERROR` for the
  identical reason (`state != RUNNING`). For TX, when the sidecar's
  `tx_started` already says the stream is not genuinely running, the
  doomed `DRAIN` attempt is skipped entirely rather than issued just to
  watch it fail — `i2s_dw`'s own `DRAIN` refusal logs its own `LOG_ERR`
  (`zephyr/drivers/i2s/i2s_dw.c:314`), so this also removes a log line on
  an already-known, already-handled path (review round 2, findings 2/3).
  The `DROP` fallback is gated on `h->started` for RX only, matching
  `z_close()`'s own gate — `DROP` tears down real RX clock hardware
  (`zephyr/drivers/i2s/i2s_dw.c:834-852`), and must not run for an RX
  handle that was never started (review round 2, finding 8). Either
  trigger succeeding marks the TX flags stopped and returns `ALP_OK`; both
  failing (or `DROP` being skipped) surfaces `DRAIN`'s own failure
  (`src/backends/i2s/zephyr_drv.c:592` ("rc = _errno_to_alp(i2s_trigger(dev, _to_dir(h->cfg.direction), I2S_TRIGGER_DRAIN));")).
  `alp_audio_out_stop()`'s `@return` now documents the both-refused
  `ALP_ERR_IO` case (`include/alp/audio.h:226`).
- **`z_start()`** retries a real `START` that fails `ALP_ERR_IO` with one
  `PREPARE`-then-retry cycle, in both directions; a failed `PREPARE` leaves
  the ORIGINAL `START` error as the reported failure, not `PREPARE`'s own.
  Since `PREPARE` drops the ring (normally already empty for a TX
  underrun; it also frees any block that raced in, since
  `i2s_dw_write()` checks state separately from `queue_put()`,
  `zephyr/drivers/i2s/i2s_dw.c:390-402` — review round 2, finding 7), the
  retried `START` on TX correctly lands in the pre-existing `#2132`
  empty-queue deferral instead of failing again
  (`src/backends/i2s/zephyr_drv.c:477` ("if (rc == ALP_ERR_IO) {")). That
  deferral branch now also clears `tx_started` via a new
  `_mark_tx_needs_restart()` helper instead of leaving it stale (review
  round 2, finding 2 — see the invariant paragraph below). A successful
  recovery logs one `LOG_WRN` — otherwise-silent evidence a `PREPARE`
  actually ran (review round 2, finding 3).
- **`z_write()`** (TX) retries an `i2s_write()` that fails `-EIO` with the
  same `PREPARE` shape, but now retries the write ONCE REGARDLESS of
  whether its own `PREPARE` succeeded (review round 2, finding 4): a
  CONCURRENT call (another writer's own `PREPARE`, or a `stop()`'s `DROP`)
  may already have taken the stream out of `ERROR` between this write's
  own trigger failing and its own `PREPARE` running, so a refused
  `PREPARE` here does not prove the stream is still stuck — only that it
  was not FROM `ERROR` at that exact instant. If the stream genuinely
  still is in `ERROR`, the retry just gets the same `-EIO` and falls into
  the existing free-and-report path, no new failure mode; previously this
  case gave up immediately and could drop a write a concurrent recovery
  would otherwise have accepted. The TX flag reset (via the same
  `_mark_tx_needs_restart()`) now runs UNCONDITIONALLY on entering this
  branch, not gated on `PREPARE`'s own success as first implemented:
  the ORIGINAL `i2s_write()` already proves the stream was in `ERROR`
  (`i2s_dw_write()` only `-EIO`s from there,
  `zephyr/drivers/i2s/i2s_dw.c:390-394`), so
  `tx_started` is already known-stale regardless of what THIS `PREPARE`
  call itself reports — gating the reset on it left `tx_pending_start`
  false in exactly the concurrent-recovery case above, silently
  stranding a genuinely-queued retry with no `START` ever fired for it
  (caught by `test_underrun_write_retry_succeeds_despite_refused_
  prepare`, which asserts `fake_i2s_tx_running()`, not just the write's
  own return status). Only the `LOG_WRN` stays conditional on THIS
  call's own `PREPARE` succeeding. The retry itself always runs, with
  the SAME slab block (never freed before the retry, never double-freed
  after it either way)
  (`src/backends/i2s/zephyr_drv.c:715` ("err = i2s_write(dev, slab_block, bytes);")).

**The RX-side leak (review round 2, finding 1):** the RX ISR's own
`I2S_STATE_ERROR` entry (`zephyr/drivers/i2s/i2s_dw.c:630-648`) orphaned
the just-filled block on EITHER of its two error exits — a failed
`k_mem_slab_alloc()` for the next block (`k_mem_slab_alloc()` sets `*mem =
NULL` on failure, so the just-filled block's own pointer, held only in a
local, was never freed), or a failed `queue_put()` of the one just filled
(the fresh block the alloc just returned replaces `stream->mem_block`,
so `rx_stream_disable()`'s own free — which only ever frees
`stream->mem_block` — never sees the orphaned one either). With the
2-block slab `src/backends/i2s/zephyr_drv.c` allocates, two overruns
exhausted it and the third `rx_stream_start()` returned `-ENOMEM`
permanently — RX has no NOMEM-as-stale-flag branch (that is TX-only).
Fixed at the actual source, `zephyr/drivers/i2s/i2s_dw.c`: both error
exits now `k_mem_slab_free()` the block they would otherwise have
orphaned, with an inline `alp-sdk issue #2137` note alongside the file's
existing ADR 0017 Tier-2 provenance header. No `zephyr_drv.c` change was
needed for this half of the fix — RX carries no sidecar flags to begin
with (`z_start()` never defers for RX).

**The `tx_started` invariant (review round 2, finding 2):** the file
header's own `tx_started => !tx_pending_start` invariant broke on this
exact sequence: deferred `start()` → `write()` fires the real `START` →
underrun → `start()`: the real `START` `-EIO`s, `PREPARE` succeeds, the
retried `START` `-ENOMEM`s (the ring is empty again, per the `#2132`
empty-queue deferral) — the NOMEM branch cleared `tx_block_queued` and set
`tx_pending_start`, but left `tx_started` untouched at `true`. `tx_started`
had gone write-only after the original `#2137` fix (nothing read it), so
this went unnoticed until `z_stop()`'s new skip-`DRAIN` check above gave it
a reader again. Fixed by routing that branch through the new
`_mark_tx_needs_restart()` (`src/backends/i2s/zephyr_drv.c:451`
("static void _mark_tx_needs_restart(alp_z_i2s_side_t *s)")) instead of a
manual two-field assign; the invariant now holds via either that function
or `_mark_tx_stopped()` — the file header comment names both.

`include/alp/i2s.h`'s `alp_i2s_start()`/`alp_i2s_stop()`/`alp_i2s_write()` and
`include/alp/audio.h`'s `alp_audio_out_start()`/`alp_audio_out_stop()`/
`alp_audio_out_write()` document that an underrun/overrun is recovered
transparently — the caller does not need to detect or clear the condition
itself before calling any of them again.

Regression tests: `tests/unit/i2s_start_defer/` extends its fake I2S device
to enforce the same state machine — a new `fake_i2s_tx_simulate_underrun()`
(the deterministic, single-threaded stand-in for the real IRQ's "ring found
empty" transition, since native_sim has no interrupt timeline to reach it
asynchronously) drops the fake into `I2S_STATE_ERROR`, from which `START`/
`STOP`/`DRAIN`/write() all refuse exactly as real `i2s_dw` does, and only
`PREPARE`/`DROP` recover it. Covers: start, write, underrun, then stop
returns `ALP_OK`; underrun, then start (re-defers) plus write (fires the
real trigger) plays again; underrun, then write alone resumes playback with
no slab leak or double free (proven against the REAL `k_mem_slab`'s own
free-block count via a new `fake_i2s_slab_free_count()`, not just the fake's
bookkeeping); and PREPARE refused propagates the ORIGINAL error rather than
PREPARE's own, proven via a new `fake_i2s_prepare_call_count()` so the test
can't pass merely by coincidence on a backend with no recovery logic at all.

Review round 2 adds: `fake_i2s_rx_simulate_overrun()` / RX state modeling
(`fake_i2s_rx_running()`, `fake_i2s_rx_in_error()`,
`fake_i2s_rx_slab_free_count()`, `fake_i2s_rx_complete_block()`) and

recovery()` with `test_underrun_write_retry_succeeds_despite_refused_

first written against the conditional-on-PREPARE's-own-success version
