### Fixed — `gen_zephyr_board`'s `zephyr_peripherals_dtsi` refusal blamed the customer for the SDK's vintage (#1354)

`_aen_peripherals_dtsi()` runs before `_aen_flash_partitions()` in `_aen_dts()`, and `atoc`
(#1289) predates `zephyr_peripherals_dtsi` (#1352), so every checkout that carries the newer
field also carries the older region — `_aen_missing_region_message()`'s carefully-worded `atoc`
vintage branch added by #1352 could never actually fire on a real checkout. The message that
DID fire, for an E8 SoC JSON missing `zephyr_peripherals_dtsi`, told the reader to hand-author
`zephyr/dts/alif/ensemble_e8_peripherals.dtsi` and declare it in the SoC JSON — even though that
64+ KiB overlay already ships in every checkout old enough to be missing the key, because the
overlay predates the key that names it. The consumer was sent to author a file already sitting
in their own tree.

`_aen_peripherals_dtsi()` now distinguishes the two cases the way `_aen_missing_region_message()`
already does for `atoc`: when the key is absent, the SoC is `alif:ensemble:e8`, and
`zephyr/dts/alif/ensemble_e8_peripherals.dtsi` is already present in the checkout, the refusal
names the real cause (this alp-sdk predates #1352) and the real fix (upgrade alp-sdk) instead of
telling the reader to recreate a file they already have. Any other missing-key shape (a
genuinely new Ensemble part with no overlay yet) still gets the original authoring-gap message
unchanged — that refusal is correct and #1352's real point.

Both vintage messages (`atoc` and `zephyr_peripherals_dtsi`) also named an unreleased commit and
said "upgrade alp-sdk to a release that includes it," which no tag could satisfy — no published
tag contained either commit at the time #1352 shipped. Both now name v0.16.0-rc1, the first
published release (a pre-release) that contains both commits, as the version floor — not
v0.16.0, whose GA tag came a week later and would otherwise tell a reader already on the rc to
upgrade further.

The `zephyr_peripherals_dtsi` vintage probe also checked the file next to the running script's
own checkout (`REPO`), not the tree the SoC JSON in question was actually loaded from
(`metadata_root`). Those differ under `--metadata-root`, and on the SDK's own default invocation
the vintage branch was provably unreachable — #1352 added the branch and the
`zephyr_peripherals_dtsi` key in the same commit, so no default checkout can have the key absent
while running code that already knows to look for it. The probe now reads from
`metadata_root.parent / "zephyr" / "dts" / ...`, so the file claim, the JSON path, and the
upgrade advice all name the one tree the SoC spec came from.
