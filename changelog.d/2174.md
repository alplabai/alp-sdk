### Fixed — `bench_jlink_run()`'s netns loopback bring-up failed silently instead of refusing (#2174)

`scripts/bench/aen/bench-env.sh:796` ("ip link set lo up 2>/dev/null || true")
tolerated a failed loopback bring-up inside the fresh network namespace
`bench_jlink_run()` masks every J-Link probe under. The header comment on
this same mitigation already documented the failure mode it exists for -- a
new netns starts with loopback DOWN and the J-Link DLL segfaults against it
-- but a netns where `lo` never actually came up (permission, a race, ...)
fell through to JLinkExe unverified.

The line now verifies the bring-up instead of trusting it.
`scripts/bench/aen/bench-env.sh:814` ("lostate=$(ip -o link show lo 2>/dev/null)")
reads the UP flag word `ip -o link show lo` prints, not
`/sys/class/net/lo/flags`: that sysfs file measured stale under an `unshare
--net` namespace with no explicit sysfs remount -- unchanged before and
after `ip link set lo up` -- while `ip`, going over netlink, always reports
the live namespace's real state. A still-down loopback now refuses, with
exit 9,
`scripts/bench/aen/bench-env.sh:816-817` ("bench_jlink_run: loopback did not come up in the fresh netns") --
the same isolation-did-not-take family the three neighbouring checks in this same subshell already use
(target-node-vanished, mask-took, exactly-one-J-Link-visible) -- reused
deliberately, not a new code. That family's raw exit never reaches a
caller's own process exit code: every call site wraps
`bench_jlink_run`/`jlink_run` with `|| true` and translates any failure via
`bench_jlink_assert_connected`'s missing-transcript check into its own exit
7, so this does not collide with `ram-run.sh`'s unrelated, internally
assigned exit 9 ("session 2's `mem8` itself failed").

**Review finding:** the verification itself needs its own guard.
`lostate=$(ip -o link show lo 2>/dev/null)` alone, under the subshell's
`set -e`, aborts the WHOLE subshell with a bare, unexplained `rc=127` the
moment `ip` is missing from the netns -- the command substitution
assignment's own failure trips `set -e` before the "did not come up"
message ever gets a chance to print. `command -v ip` is now checked FIRST,
explicitly:
`scripts/bench/aen/bench-env.sh:810` ("command -v ip >/dev/null 2>&1 || {")
refuses with
`scripts/bench/aen/bench-env.sh:811` ("bench_jlink_run: ip not found in the fresh netns"),
exit 9 again, the same family, before ever reaching the command
substitution that would otherwise abort silently.

Unit tests extract this exact check text out of the real script -- from its
own `set -e` onward, so the extracted copy exercises the SAME errexit
semantics the production subshell does -- and run it for real inside a
genuine fresh `unshare --net` namespace:
`tests/scripts/test_bench_jlink_run.py:385`
("def test_lo_up_lets_the_session_proceed(tmp_path: Path) -> None:"),
`tests/scripts/test_bench_jlink_run.py:395`
("def test_lo_staying_down_refuses_instead_of_silently_continuing(tmp_path: Path) -> None:"),
and `tests/scripts/test_bench_jlink_run.py:410`
("def test_lo_check_missing_ip_refuses_instead_of_a_bare_set_dash_e_abort(tmp_path: Path) -> None:").
Mutation-proven twice: reverting the UP-flag check makes the second test
fail (the session proceeds instead of refusing), and separately removing
the `command -v ip` guard makes the third test fail (a bare exit 127 with
no message, instead of exit 9 with one).

**This does not explain either observed crash class.** A 97-iteration soak
recorded two distinct shapes: a SIGSEGV (`rc=139`) and a glibc heap abort
(`rc=134`, `double free or corruption (top)`) inside the J-Link DLL itself --
heap corruption is a different mechanism from a null/invalid pointer against
a down loopback, and this change does not claim to fix either. It removes
one silent failure the evidence says is worth removing on its own merits,
independent of whether it ever caused a crash.

Closes #2174's narrowed in-tree scope. The identical failure-tolerant line
in `board-farm/bin/jlink-run.sh` is a separate repository this change cannot
reach, and any root-cause hunt for the heap-corruption crash stays out of
this issue.
