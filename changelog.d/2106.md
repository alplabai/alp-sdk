### Fixed — `drone-autopilot`'s hardware scenario named a board target it ships no overlay for, silently dropping every `alp-*` alias and driver (#2106)

`examples/peripheral-io/drone-autopilot`'s only board overlay is
`boards/alp_e1m_aen801_m55_hp_ae822fa0e5597ls0_rtss_hp.overlay`, written for
#1383 item 2 to close the same devicetree-alias gap
`examples/peripheral-io/pwm-led-fade` closed for #1375. `testcase.yaml`'s
`alp_sdk.examples.drone_autopilot.aen` scenario declared a different board
target, `ensemble_e8_dk/ae822fa0e5597ls0/rtss_hp`: introduced at `4a1c1a732`
as `alif_e7_dk_rtss_hp` (an E7 dev kit against an E8 `board.yaml` even then),
then retargeted to the E8 vendor DevKit by `560b256e5` (#1266/#1316,
"documentation for a dev kit CI never builds" by its own commit message) --
three months before `4a375045f` (#1383) added the overlay. That commit never
corrected the scenario. Zephyr resolves a `boards/` overlay by
fully-qualified board target name, so building for `ensemble_e8_dk/...`
picked up no overlay at all, with no error or warning (the scenario is
`build_only: true`, so nothing ever ran to surface it).

The loss was not just the six `alp-*` aliases. Confirmed against both
targets' generated `.config`: on `ensemble_e8_dk/...` `CONFIG_PWM_ALIF_UTIMER`,
`CONFIG_I2C_DW` and `CONFIG_GPIO_DW` are all absent and `pwm_alif_utimer.c`
is never compiled into the image -- the whole driver set the overlay's
`&utimer10`/`&utimer11`/`&i2c2`/`&uart3` nodes pull in was gone, not just the
aliases pointing at it.

`board.yaml` names `som.sku: E1M-AEN801` / `preset: e1m-evk`, the README's
"Hardware" section says E1M-AEN801 + E1M-EVK, and the sibling
`examples/aen/aen-pwm-utimer-pwmleds` / `examples/aen/edgeai-vision-aen`
scenarios that target the same overlay both use the fully-qualified
`alp_e1m_aen801_m55_hp/ae822fa0e5597ls0/rtss_hp` form -- and dual-targeting
the DevKit as well would be actively wrong, since it does not carry the
E1M-EVK pad routing the overlay encodes. So the overlay was right and the
scenario's `platform_allow` was wrong. Corrected `testcase.yaml`'s
`platform_allow` to `alp_e1m_aen801_m55_hp/ae822fa0e5597ls0/rtss_hp`, and
updated the three stale `ensemble_e8_dk/...` mentions that agreed with the
old value -- the README's `[UNTESTED]` banner and `west build -b ...`
command, and `docs/local-ci.md`'s Windows cross-compile example -- to match.

Added `examples/peripheral-io/drone-autopilot` as a third, bounded
`--testsuite-root` on `pr-twister-aen.yml` (same #1101 precedent as the
existing `firmware-update-log` root): before this the corrected target was
built by no CI job -- `pr-twister-aen.yml` only covered `examples/aen` and
`firmware-update-log`, and `pr-twister.yml` filters the AEN scenario out via
`-p native_sim/native/64` -- so a regression back to the wrong target would
have gone unnoticed again.

Verified against the generated devicetree rather than a green build alone: on
the corrected target `build/zephyr/zephyr.dts` carries `alp-i2c0 = &i2c2`,
`alp-uart1 = &uart3`, and `alp-pwm0`..`alp-pwm3 = &esc0`..`&esc3`, all
attributed back to the overlay; on the old `ensemble_e8_dk/...` target none
of the six aliases appear anywhere in the generated tree.

Checked, not assumed, whether the same overlay-vs-declared-target mismatch
recurs elsewhere: of the 20 other `examples/*/*/testcase.yaml` files that
declare `ensemble_e8_dk/...` (across `ai/`, `audio/`, `camera-vision/`,
`connectivity/`, `display/`, `multicore/`), none ships an `alp_e1m_*` overlay
under its `boards/` directory -- every one of those 20 is either genuinely
DevKit-targeted or (where a `boards/` directory exists at all) carries only a
`native_sim_native_64` overlay, so none pairs a real `alp_e1m_*` overlay with
a wrong `ensemble_e8_dk` declaration. #2120's declared-target-with-no-overlay
gate scopes to `alp_e1m_*` `platform_allow` entries and would not have caught
this one, since the declared (wrong) target here was the vendor
`ensemble_e8_dk` board, not an `alp_e1m_*` one; not widened here.
