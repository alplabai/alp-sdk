### Added — a scheduled alarm for silent `dev` merge-queue ejections (#1952)

PR #1887 was enqueued on `dev`, sat at `AWAITING_CHECKS`, and was ejected
without merging while every one of its own checks stayed green -- its four
`merge_group` runs were still `queued` past the ruleset's
`check_response_timeout_minutes` when a starved runner pool never started
them. The ejected PR kept reading `OPEN` / `MERGEABLE` / `CLEAN`, so nothing
in the PR view distinguished "dropped an hour ago and will not merge on its
own" from "still waiting". A human had to notice `dev` had stopped moving
while the queue looked healthy.

`.github/workflows/merge-queue-ejection-alarm.yml` runs
`scripts/merge_queue_ejection_alarm.py` on a 30-minute schedule (also
`workflow_dispatch`-able) to surface exactly that state. It never fails or
blocks CI -- it is an alarm, not a gate.

Detection: a PR targeting `dev` that is `MERGEABLE` / `CLEAN` (which already
encodes every required check passing), is not currently in the merge queue
(live `repository { mergeQueue { entries { pullRequest { number } } } }`
GraphQL query -- verified against the real API before relying on it), and
whose issue timeline's *last* queue-related event is a
`removed_from_merge_queue` with actor `github-merge-queue[bot]` more than 15
minutes ago. That actor check is load-bearing: a human clicking "Remove from
queue" produces the same event type but with *their own* login as actor, and
must not alarm. Validated against this repo's real data, both directions:
PR #1887's three `removed_from_merge_queue` events (the recorded incident)
all carry actor `github-merge-queue[bot]`, and replaying the detector
against its timeline truncated to just after the first (2026-09-04
09:44:43Z) ejection fires true; PRs #1673 and #1670 (`needs-silicon`, held
open on purpose, currently `MERGEABLE`/`CLEAN`) were removed from the queue
with actor `alpCaner` during the incident's manual mitigation and correctly
do not fire. Alarms once per ejection via a PR comment carrying the
timeline event's id as a dedup marker; a second ejection of the same PR
carries a different event id and alarms again.

Known scope limit, stated rather than hidden: the actor field cannot tell a
genuine ejection apart from the queue removing an entry to complete its own
merge -- but that case is excluded for free, since a merged PR's state is
`MERGED`, not `OPEN`, so it never reaches this detector's candidate list.

This is the detection half only. It is not a `check_*.py` gate (nothing in
it validates a diff or blocks a merge, so the four-site quality-registry
lockstep does not apply) and it does not touch the ruleset itself.

Correcting this issue's own now-stale premise: it was filed citing
`check_response_timeout_minutes: 60`. That value was already raised to
`180` on 2026-09-05 (`repos/alplabai/alp-sdk/rulesets/20781492`, per the
issue's own follow-up comments) and is unchanged by this PR --
`check_response_timeout_minutes: 180`, `max_entries_to_build: 1` on the
live ruleset as of 2026-09-06. Neither is touched here; the throughput half
of #1952 (`max_entries_to_build` and the other options) stays open for a
separate, ruleset-owning change.
