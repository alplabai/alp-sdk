### Fixed — `alp companion sock tcp-get` overflowed the shell stack and halted the board (#1743)

Every `alp` console command runs on the Zephyr shell thread, and the companion verbs
descend `shell` -> `cc3501e_request()` -> the SPI transport and then format the result
back out through `shell_print()`. Zephyr's default `CONFIG_SHELL_STACK_SIZE=2048` does
not leave enough room for that chain: with data actually flowing through `sock tcp-get`'s
receive loop it overflowed and took the system down —

```
E:   Stack overflow (context area not valid)
E: >>> ZEPHYR FATAL ERROR 2: Stack overflow on CPU 0
E: Current thread: 0x200001d0 (shell_uart)
E: Halting system
```

Sized from measurement rather than guessed. With `CONFIG_THREAD_ANALYZER` on an
E1M-AEN801:

| path | `shell_uart` peak |
|---|---|
| `alp companion ver` alone | 1044 / 2048 (50 %) |
| after `sock tcp-get` | 1156 / 2048 (56 %) |

Under 900 bytes remained for the receive loop's own formatting, and printf under picolibc
is stack-hungry. `configdefault` now raises the default to **4096 whenever
`ALP_SDK_CONSOLE` is enabled**, which measures 1156 / 4096 (28 %) on the same board —
headroom goes from 892 to 2940 bytes. It costs 2 KB of RAM (~0.8 % of the AEN801's
256 KB) and only on builds that opt into the console; `configdefault` leaves an
application free to choose its own value.

Note the receive buffer was never the problem — it is `static uint8_t rx[512]`, off-stack.
The only stack arrays in that translation unit are `ip[4]` and `req[160]`. The overflow is
call-chain depth, which is why raising the thread's stack is the proportionate fix rather
than shrinking a local.
