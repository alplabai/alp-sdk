### Fixed — E1M-V2M101's `dram_mbit`/`flash_mbit` matched neither the SKU spec nor the module they were read from (#1230)

`metadata/e1m_modules/E1M-V2M101.yaml` carried `dram_mbit: 32768` (4 GiB) and
`flash_mbit: 32768` (4 GB) — copied from the smaller `E1M-V2N101` tier rather
than describing this SKU's own BOM. A bench read of a real V2M101 r1 module
(EEPROM-confirmed, CRC-valid) measured 8 GiB DRAM via
`/proc/device-tree/memory@48000000/reg` and a ~256 GB eMMC — neither of which
matched the committed value, and the eMMC figure didn't match either V2M SKU.

Maintainer ruling: DRAM is 8 GiB (`dram_mbit: 65536`), matching the bench
measurement exactly. eMMC is 16 GiB (`flash_mbit: 131072`) — the SKU's
published spec; the bench module's own eMMC part is a larger lab-only part,
not representative of the shipping BOM, and was not used as the source value.

Regenerated `metadata/catalog.json` (no diff — it doesn't carry memory
capacities), `alp.lock` (metadata digest), and `docs/portability-matrix.md`.
Two more hand-authored docs also stated E1M-V2M101's memory in prose and
were stale — `vendors/renesas-rzv2n/README.md` and `docs/soms/v2n-m1.md` —
both updated in this same change.

This makes E1M-V2M101 equal E1M-V2M102 on DRAM (both `dram_mbit: 65536`)
and give it MORE eMMC than V2M102 (`131072` vs `65536`), inverting the
101 < 102 tier convention seen in the E1M-V2N101/E1M-V2N102 pair (32768 /
65536 on both fields). `E1M-V2M102`/`E1M-V2N101`/`E1M-V2N102` were checked
in isolation and their own `memory:` blocks are internally consistent, but
the cross-SKU tier inversion this introduces is a real, unresolved
contradiction — not invented away here, and not fixed by this change; it is
flagged in the metadata comment and in the two docs above for a follow-up.
Only E1M-V2M101's two values carry a maintainer ruling (#1230); E1M-V2M102's
are unverified — the tier-inversion note above does not extend a
confirmation to it.

A follow-up round changed E1M-V2N102's eMMC figure in
`vendors/renesas-rzv2n/README.md` from 128 Gbit to 64 Gbit, citing
`metadata/e1m_modules/E1M-V2N102.yaml` and `docs/soms/v2n.md` as "two
independent in-tree sources". They are not independent: the doc was
authored the same day as, and is a `git merge-base`-confirmed descendant
of, the metadata commit that introduced `flash_mbit: 65536` — one claim
copied into a second file, not two corroborating measurements. The 128
Gbit figure in the README table was written by `d953e401`, which
copy-pasted the identical "eMMC 5.1, 32 / 128 Gbit" (and identical
"32 / 64 Gbit" LPDDR4X) into both the V2N and V2N-M1 rows in a single
hunk — not a per-SKU transcription of an external spec, and #1230 has
since proven two cells of that same copy-pasted pair wrong for V2M101
(DRAM 32 -> 64 Gbit, eMMC 32 -> 128 Gbit). No eMMC part number or BOM
line in the tree ties E1M-V2N102 to either figure; nobody has ruled on
this SKU the way #1230 ruled on E1M-V2M101. Reverted the README cell to
128 Gbit anyway — on the narrower ground that it's the value already in
place before this branch (matching `origin/dev`), and per the general
"prefer the pre-existing spec-table figure over a same-day, non-independent
metadata-doc pair" precedent this branch is applying consistently below —
not because its own provenance is strong. Un-pinned E1M-V2N102 from
`tests/scripts/test_gen_portability_matrix.py`'s
`test_v2n_v2m_memory_capacities_are_pinned` (which had locked in the
unverified 64 Gbit figure as if it were settled). `metadata/e1m_modules/
E1M-V2N102.yaml` and `docs/soms/v2n.md` are unchanged by that round — the
metadata/doc-vs-spec mismatch for E1M-V2N102 was real, pre-existing, and
still unresolved after it.

A further round found the identical defect shape one row down, resolved
the opposite way and undisclosed: an earlier round in this branch
(58643ae4) had changed E1M-V2M102's eMMC in the same README table from
128 Gbit (the `d953e401` copy-paste value, same provenance caveat as

Rather than pick either candidate figure for either SKU, this round
