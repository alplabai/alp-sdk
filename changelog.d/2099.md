### Added — CC3501E `WIFI_STATUS` surfaces the reason/status code for the most recent connect attempt (#2099)

`alp_cc3501e_wifi_status_t`'s 4th wire byte was an unused `reserved` field,
always 0. It is renamed `last_reason` and documented: the low byte of the
802.11 REASON code from a DISCONNECT event, or the 802.11 STATUS code from an
ASSOCIATION_REJECTED/AUTHENTICATION_REJECTED event — two different code
tables, and nothing on the wire says which one, so `fail_reason == REJECTED`
does not disambiguate them. Requires bridge firmware that publishes the
reason (`cc3501e-bridge-firmware`); older firmware still sends 0, so this is
purely additive — no wire-version bump needed.

Recorded ONLY while the connect attempt's state is CONNECTING, then frozen
and PERSISTS through every later state publish — including a subsequent
`cc3501e_wifi_disconnect()` call (WIFI_DISCONNECT), which republishes this
same frozen value rather than a fresh one — until the next connect attempt
starts and clears it back to 0. `cc3501e_wifi_connect()` itself issues that
same disconnect at entry, before submitting a new attempt, whenever the latch
still shows a FAILED attempt (the pre-existing #1435/#1437 stale-association
cleanup), so that internal disconnect republishes the OLD attempt's value
too. `0` means nothing was recorded for that attempt, not "no cause": a clean
success or a bare timeout also reads `0`. `CONNECTED` always publishes `0`,
unconditionally, even over a since-succeeded transient rejection recorded
earlier in the same attempt. Never holds vendor reason 200
(`WLAN_DISCONNECT_USER_INITIATED`). Known residual: a late event from the
PREVIOUS attempt landing in the brief window right before the new attempt's
own connect call can still be recorded against the new one; the converse also
holds — a reject arriving after an attempt has already been declared TIMEOUT
is lost. The firmware also runs one bounded, transparent retry on a first-pass
status-30 rejection: the retry normally reports its own outcome, but if the
retry's own connect call is itself refused, the byte reports the FIRST pass's
outcome (e.g. REJECTED/30) instead of a generic KICK/0. Scope is the connect
attempt only: a deauth after a successful `CONNECTED` is not recorded, because
the state is no longer CONNECTING.

`alp companion wifi status` prints `reason: <N>` after `fail:  <N>` when
`last_reason` is non-zero. `wifi connect`'s async result line does the same
on both a failure and a timeout, fetched via the new `cc3501e_wifi_status_once()`
— a single, non-retried WIFI_STATUS read (public API, alongside the existing
down-window-retrying `cc3501e_wifi_status()`; its real bound is the shared
request lock's bounded acquire plus the per-phase READY wait, not a
`timeout_ms` argument, which the transport ignores) so a wedged transport
cannot turn this best-effort diagnostic fetch into an extra ~10 s delay with
the connect result held back. The console only trusts the fetched
`last_reason` when the latch's own `state` reads `CONN_FAILED` -- a
`DISCONNECTED`/`CONNECTING` state there means no failure of THIS attempt
ever landed (the submit was bounced `BUSY` by a concurrent worker op, or lost
to a transport IO fault, and the outer loop's own `timeout_ms` simply ran
out), so the byte would otherwise still hold an UNRELATED prior attempt's
stale value. The fetch is skipped entirely when `cc3501e_wifi_connect()`
returned `ALP_ERR_INVAL`: no attempt started, so the latch still holds the
previous attempt's value. This is the host-visible half of the bench gap this
issue tracks: roughly half of `alp-console` station connects were failing
`-5` (`REJECTED`) with nothing to say why.

`rssi_dbm`'s `@warning` (issue #1387, closed) is updated to say so: the wire
slot that would have carried an RSSI-validity flag is the same byte now
carrying `last_reason`, so that option is no longer available on this reply.
No replacement channel is decided here.
