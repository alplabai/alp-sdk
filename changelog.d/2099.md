### Added — CC3501E `WIFI_STATUS` surfaces the 802.11 reason code that ended or rejected a connect (#2099)

`alp_cc3501e_wifi_status_t`'s 4th wire byte was an unused `reserved` field,
always 0. The upcoming `cc3501e-bridge-firmware` (`fix/sta-active-before-
first-connect`) starts publishing the low byte of the IEEE 802.11 reason
code, or the association/authentication status code, that ended or rejected
the most recent connect attempt in that byte — so it is renamed
`last_reason` and documented as such. Scope is the connect attempt only: a
deauth after a successful `CONNECTED` is not reflected, and a disconnect the
bridge itself requested is excluded. Older bridge firmware that never
populates the byte still sends 0, so this is purely additive — no wire-
version bump needed.

`alp companion wifi status` now prints `reason: <N>` after `fail:  <N>` when
`last_reason` is non-zero, and `wifi connect`'s async failure line prints the
same `reason: <N>` suffix (fetched with an independent `WIFI_STATUS` read,
same pattern the RSSI print already uses on the success path). This is the
host-visible half of the bench gap this issue tracks: roughly half of
`alp-console` station connects were failing `-5` (`REJECTED`) after a vendor
`DISCONNECT` event with nothing to say why.

The renamed field is safe against `cc3501e-bridge-firmware`'s CI, which
builds against this header from alp-sdk's `dev` branch: the firmware writes
the reply's 4th byte positionally (`reply_data[3] = ...`) and never
instantiates `alp_cc3501e_wifi_status_t` by name, so nothing there references
the old `reserved` field.

`rssi_dbm`'s `@warning` (issue #1387, closed) is updated to say so: the wire
slot that would have carried an RSSI-validity flag is the same byte now
carrying `last_reason`, so that option is no longer available on this reply.
No replacement channel is decided here.
