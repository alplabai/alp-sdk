### Fixed — absent OV9281 sensor reported `ALP_ERR_IO`, indistinguishable from a genuine I2C bus fault (#2249)

`alp_camera_open()` on the E1M-EVK's J5 CSI-2 pipeline (InnoMaker
CAM-OV9281) returned `ALP_ERR_IO` when no sensor was connected -- the same
code a real bus fault produces -- instead of `ALP_ERR_NOT_READY`. Confirmed
on an E1M-AEN803 (2026W36-0009) with nothing on J5: `RESULT FAIL: camera
did not open -- ALP_ERR_IO` on 3 of 3 cold cycles.

`ov9281.c`'s `ov9281_init()` already reads and validates the sensor's
chip-ID registers (`0x300A`/`0x300B`, a fixed `0x9281`) and correctly fails
its own init -- and therefore its own `device_is_ready()` -- when the
sensor never answers. That not-ready state just never reached
`alp_camera_open()`: `alp-camera0` resolves to the CPI capture controller
(`&cam`, `video_alif.c`'s `alif_video_cam_init()`), which only checked that
its upstream device pointer was non-NULL, and the DesignWare CSI-2 host in
between (`&csi`, `video_csi_dw.c`'s `csi2_dw_init()`) only checked that a
sensor pointer/D-PHY mapping existed in devicetree -- neither called
`device_is_ready()` on the device downstream of it. So an absent sensor
sailed through `alp_camera_open()`'s readiness gate at the CPI and only
surfaced later, as an I2C NACK (`-EIO`) on the first `video_set_format()`
forwarded all the way down to the sensor, which `_errno_to_alp()` maps to
`ALP_ERR_IO`.

Both intermediate drivers now propagate readiness instead of only checking
DT wiring: `csi2_dw_init()` fails with `-ENODEV` when its selected sensor
isn't ready, and `alif_video_cam_init()` fails with `-ENODEV` when its
upstream endpoint device isn't ready (covers both the CSI-2 D-PHY path,
where the endpoint is `&csi`, and the parallel-interface path, where it is
the sensor directly). `alp_camera_open()`'s existing
`!device_is_ready(dev)` check at `src/backends/camera/zephyr_video.c` --
unchanged -- now correctly sees the whole pipeline as not-ready when the
sensor is absent, and returns `ALP_ERR_NOT_READY` as documented in
`<alp/camera.h>`. No new error code: the portable API already reserved
`ALP_ERR_NOT_READY` for exactly this case.

A present, correctly wired OV9281 is unaffected: `ov9281_init()`'s chip-ID
read matches, so the sensor is ready, `csi2_dw_init()`'s new check passes,
`alif_video_cam_init()`'s new check passes, and `alp_camera_open()` proceeds
exactly as before.
