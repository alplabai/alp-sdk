### Fixed — absent OV9281 sensor reported `ALP_ERR_IO`, indistinguishable from a genuine I2C bus fault (#2249)

`alp_camera_open()` on the E1M-EVK's J5 CSI-2 pipeline (InnoMaker
CAM-OV9281) returned `ALP_ERR_IO` when no sensor was connected -- the same
code a real bus fault produces -- instead of `ALP_ERR_NOT_READY`. Confirmed
on an E1M-AEN803 (2026W36-0009) with nothing on J5: `RESULT FAIL: camera
did not open -- ALP_ERR_IO` on 3 of 3 cold cycles.

`ov9281.c`'s `ov9281_init()` already reads and validates the sensor's
chip-ID registers (`0x300A`/`0x300B`, a fixed `0x9281`) and correctly fails
its own init -- and therefore its own `device_is_ready()` -- when the
sensor never answers. That not-ready state just never reached
`alp_camera_open()`: `alp-camera0` resolves to the CPI capture controller
(`&cam`, `video_alif.c`'s `alif_video_cam_init()`), which only checked that
its upstream device pointer was non-NULL, and the DesignWare CSI-2 host in
between (`&csi`, `video_csi_dw.c`'s `csi2_dw_init()`) only checked that a
sensor pointer/D-PHY mapping existed in devicetree -- neither called
`device_is_ready()` on the device downstream of it. So an absent sensor
sailed through `alp_camera_open()`'s readiness gate at the CPI and only
surfaced later, as an I2C NACK (`-EIO`) on the first `video_set_format()`
forwarded all the way down to the sensor, which `_errno_to_alp()` maps to
`ALP_ERR_IO`.

The first attempt at this fix added a `device_is_ready()` check to each
driver's own `_init()` and was wrong: dev-review caught, from a built
image's `.z_init_POST_KERNEL_P_*` link order (`aen-camera-firstlight`,
`alp_e1m_aen803_m55_he`, `SHIELD="e1m_evk_rpi_csi innomaker_cam_ov9281"` --
`csi@49033000` at priority 41, `cam@49030000` at priority 59, `ov9281` at
priority 60), that `csi2_dw_init()` (`CONFIG_VIDEO_MIPI_CSI2_DW_INIT_PRIORITY`,
default 41) and `alif_video_cam_init()` (`CONFIG_VIDEO_ALIF_CAM_INIT_PRIORITY`,
default 59) both run strictly *before* a sensor's own
`CONFIG_VIDEO_INIT_PRIORITY` (default 60, e.g. `ov9281.c`/`arx3a0.c`) --
`CONFIG_CHECK_INIT_PRIORITIES` cannot catch this because the dependency is a
DT `remote-endpoint-label` string, not a `zephyr,init-dep` edge. A
readiness check at init time therefore always saw the sensor as
not-yet-initialized and rejected a genuinely *present* one too, breaking
every Alif CPI camera path.

Both intermediate drivers now check readiness at first USE instead --
`csi2_dw_sensor_ready()` (called from `csi2_dw_get_caps()`/
`csi2_dw_set_format()`/`csi2_dw_get_format()`) and
`alif_cam_endpoint_ready()` (called from `alif_cam_get_caps()`/
`alif_cam_set_fmt()`/`alif_cam_get_fmt()`), both returning `-ENODEV`. By the
time an application calls `alp_camera_open()`, every driver's own
`POST_KERNEL` init -- including the sensor's chip-ID check -- has already
run regardless of priority ordering, so checking there is correct without
requiring any priority reshuffle across drivers (ISP-Pico, ARX3A0, or any
`prj.conf` override). `alp_camera_open()`'s existing `!device_is_ready(dev)`
check at `src/backends/camera/zephyr_video.c` -- unchanged -- still gates
the CPI device itself (a real hardware-init failure of the CPI or CSI-2
host, as opposed to sensor absence), and `_errno_to_alp()`'s existing
`-ENODEV` mapping is what turns the new checks into `ALP_ERR_NOT_READY`. No
new error code.

The link order above is measured on a built image; the present-sensor,
absent-sensor, and I2C-fails-open behaviors of the fixed code are reasoned
from that measurement and from code inspection, not bench-run -- this
board pairing has no bench access to both a populated J5 and a confirmed
absent one in the same session.
