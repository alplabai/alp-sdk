### Fixed — `chips/tmp112/tmp112.c` and upstream Zephyr's TMP112 sensor driver collide at LINK time on E1M-AEN801, so the board now defaults the upstream driver off (#2043)

alp-sdk's chip drivers use the part's natural name by convention
(`chips/tmp112/tmp112.c` defines `tmp112_init`); upstream Zephyr's
`zephyr/drivers/sensor/ti/tmp112/tmp112.c` defines the SAME symbol for the
SAME part. The two only collide when an app pulls both into one image, which
is exactly what `CONFIG_SENSOR=y` did for free on the E1M-AEN801: both board
targets' `.dts` carry a `ti,tmp112` devicetree node
(`zephyr/boards/alp/e1m_aen801_m55_he/alp_e1m_aen801_m55_he_ae822fa0e5597ls0_rtss_he.dts:250`,
mirrored in `_hp`), so upstream's `CONFIG_TMP112` defaults on for every app
built for either target regardless of whether that app uses TMP112 at all.
`examples/aen/aen-evk-demo/prj.conf` had been patching this with
`CONFIG_TMP112=n`, a per-app fix over a per-board defect — the next app to
enable `CONFIG_SENSOR` alongside alp-sdk's own chip driver on this board
would have hit the identical link error with no CI gate to catch it first.

`scripts/gen_zephyr_board.py`'s `_aen_kconfig_defconfig()` now emits a
`config TMP112` / `default n` stanza into both boards' generated
`Kconfig.defconfig`, the same `if BOARD_<sym> ... endif`-scoped pattern that
function already uses for `ROM_START_OFFSET`. This is a board-scoped
default, not a hard disable: Kconfig.zephyr sources a board's
`Kconfig.defconfig` ahead of subsys/Kconfig, so this default only supplies
the value nothing else assigns — an app that genuinely wants the upstream
driver still sets `CONFIG_TMP112=y` explicitly and that assignment overrides
the board default regardless of source order. Confirmed on the real board
target, not just by mechanism: `west build -p always -b
alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he examples/aen/aen-temp-sensor`
links `zephyr/drivers/sensor/ti/tmp112/libdrivers__sensor__ti__tmp112.a`,
and the resolved `.config` carries `CONFIG_TMP112=y`, `CONFIG_SENSOR=y` and
`CONFIG_DT_HAS_TI_TMP112_ENABLED=y` with the board's `default n` in force.
`examples/aen/aen-temp-sensor` is exactly that app (it reads TMP112 through
the upstream sensor API, not alp-sdk's chip driver); its `prj.conf` and
`README.md` now say so explicitly instead of relying on the
devicetree-triggered default that no longer fires on this board. `examples/aen/aen-evk-demo/prj.conf`'s now-redundant
`CONFIG_TMP112=n` line and its explanatory comment block are deleted — the
board default already does that job.

The other thirteen parts the issue's `find` turned up (bme280, bmi323,
bmp581, lis2dw12, lps22hb, lsm6dso, hx711, max31855, max31865, veml7700,
tsl2591, vl53l1x, icm42670) have no board-level `.dts` node today — only
per-example carrier overlays declare them, which `Kconfig.defconfig` cannot
see — so they stay latent and undefaulted here; the naming-convention fix
(a chip-driver symbol prefix) the issue calls out as "Not in scope" is still
not in scope.
