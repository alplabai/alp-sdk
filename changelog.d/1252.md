### Fixed — U-Boot `bootcmd` hardcoded the V2N101 dtb, so V2M SKUs booted a stale/wrong dtb (#1252)

`CONFIG_BOOTCOMMAND` (`meta-alp-sdk/recipes-bsp/u-boot/u-boot/0002-rzv2n-dev-ALP-E1M-production-boot.patch`)
loaded `boot/e1m-v2n101-x-evk.dtb` on both the SD and eMMC branches. All four
V2N/V2M machines (`e1m-v2n101/102-a55`, `e1m-v2m101/102-a55`) share this one
u-boot binary/config (`UBOOT_CONFIG[rzv2n-evk] = rzv2n-dev_defconfig`), but only
the V2N machines' `KERNEL_DEVICETREE` matches that filename — a V2M SKU loaded
a dtb that does not exist in its own image, and the vendor `sd2load`/`emmcload`
env that ran first had the identical defect (`;`-chained, non-fatal), so
`bootimage` ran `booti` against whatever stale content was already at
`0x48000000`.

Fixed by reusing the on-module EEPROM manifest read the DEEPX bring-up
(`board_late_init()`, `alp_som_is_v2n_m1()`) already performs, rather than
swapping one hardcoded name for another. A new `alpselectfdt` U-Boot command
(`board/renesas/rzv2n-dev/rzv2n-dev.c`) sets `alp_fdtfile` to the matching dtb
(`e1m-v2m101-x-evk.dtb` on a V2M-family manifest, `e1m-v2n101-x-evk.dtb`
otherwise) and is invoked from `CONFIG_BOOTCOMMAND` **after** its leading `env
default -a` — that wipe drops any variable set earlier in the boot flow (in
`board_late_init()`, well before autoboot), so the selection has to happen at
that point, not before it. An unreadable manifest makes
`alp_som_is_v2n_m1()` return `false`, so `alp_fdtfile` falls back to the V2N
(non-DEEPX) name — the same dtb this bootcmd hardcoded before this fix, so a
manifest fault degrades to the old behaviour rather than a new failure mode.

New patch: `meta-alp-sdk/recipes-bsp/u-boot/u-boot/0003-rzv2n-dev-select-fdtfile-fatal-image-and-dtb-load.patch`,
wired into `u-boot_%.bbappend`'s `SRC_URI:append:rzv2n-family`.

**Verified by rebuild, not on hardware.** The patch applies cleanly
(`patch -p1`, `git apply --check`, and `git am` all accept it unmodified) on
top of 0001+0002 against the pinned `renesas-u-boot-cip` SRCREV (2024.07,
`bcf29d98`), and `rzv2n-dev_defconfig` rebuilds end to end with the same
cross toolchain and STAGING sysroot the `e1m-v2m101-a55` recipe build uses (0
warnings, 0 errors). `strings` on the resulting `u-boot.bin` confirms
`alpselectfdt` is registered (`_u_boot_list_2_cmd_2_alpselectfdt`) and the
compiled-in default `bootcmd` string matches the patch exactly, both dtb
filenames present. The EEPROM read itself, and which dtb an actual V2M board
loads, are **not** bench-verified — V2M101 bring-up is currently blocked on
separate hardware issues.
