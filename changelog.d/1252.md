### Fixed — the U-Boot bootcmd hardcoded the V2N dtb and let a failed kernel load boot a stale image (#1252, #1302)

Two failures in `CONFIG_BOOTCOMMAND`
(`meta-alp-sdk/recipes-bsp/u-boot/u-boot/0002-rzv2n-dev-ALP-E1M-production-boot.patch`),
both of which present as a successful boot:

**The dtb was a literal (#1252).** `boot/e1m-v2n101-x-evk.dtb` was loaded on both
the SD and eMMC branches. V2M MACHINEs build `renesas/e1m-v2m101-x-evk.dtb`
(`meta-alp-sdk/conf/machine/e1m-v2m101-a55.conf:58`,
`meta-alp-sdk/conf/machine/e1m-v2m102-a55.conf:60`), so every V2M
image asked for a filename it does not contain — and each of those machine confs
already carried the note "the U-Boot bootcmd must load this filename (set
fdtfile)". The name is now `CONFIG_ALP_E1M_FDTFILE`, a Kconfig string defaulting
to the V2N basename, overridden for the V2M MACHINEs by `fdtfile-v2m.cfg`
through the same `*.cfg` channel `prod-boot.cfg` uses. This is the mechanism the
patch's own comment specified as the fix; that comment is updated rather than
left describing the work as future.

The override is scoped per MACHINE and not to `rzv2n-family`, because the family
override covers the V2N SKUs too and would invert the bug. A new V2M MACHINE
needs its own line — "which dtb does this image contain" is a per-MACHINE fact
(`KERNEL_DEVICETREE`), and no wildcard is safe.

**The loads were non-fatal (#1302).** Every load was `;`-chained, so a missing
kernel `Image` or dtb left whatever those addresses already held and
`run bootimage` booted it. Cold, that is garbage. Warm, it is the *previous*
boot's image — which looks like a successful boot of the wrong software, and is
the worse of the two. Both loads are now re-issued with `&&`, `bootimage` runs
only if both landed, and the failure branch prints what could not be loaded and
stops at the prompt.

`Image` is re-loaded even though `bootcmd_check`'s vendor `sd2load`/`emmcload`
already tried, because those envs are rewritten by vendor feature layers
(`meta-rz-drpai`, `meta-rz-opencva`) and cannot be relied on to fail loudly. Same
address and mmc spec, so it is a no-op when the vendor path worked.

**Bench-gated.** This changes a production boot path and has not been booted on
silicon. The new failure mode is a U-Boot prompt rather than a wrong-image boot —
recoverable over serial, not a brick — but a real boot on a V2N and a V2M module
is owed before this is trusted.
