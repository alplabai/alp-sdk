### Fixed — `alp_power_configure_wake_source()` lied about arming a wake source it could never honour on stock AEN builds (#1812)

On a default `alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he` build, pinned
upstream Zephyr 4.4.0's Alif E8 SoC does not `select HAS_PM`, so `CONFIG_PM`
is unreachable and `src/backends/power/zephyr_pm_policy.c` (gated `depends
on PM`) never compiles in. `src/backends/power/zephyr_stub.c`'s wildcard
priority-0 fallback wins `alp_backend_select("power", ...)` instead.
`alp_power_open()` and `alp_power_configure_wake_source()` both returned
`ALP_OK`; only `alp_power_request_sleep()` returned `ALP_ERR_NOSUPPORT` — a
caller found out its setup was pointless only after asking to sleep. No AEN
example called the portable `<alp/power.h>` surface at all, so nothing in CI
noticed.

Shipping the full `alif_aipm` SE-backed power backend the issue's "Proposed
resolution" describes (`SERVICES_power_wakeup_config` /
`_mem_retention_config` / `_stop_mode_request` / the VTOR-save calls for warm
resume) is out of scope for this change: it needs bench time on real E8
silicon this pass didn't have, and faking a sleep path that has never
actually entered STOP on hardware would be worse than the bug it replaces.
Landing that backend is tracked as follow-on work; #1813 settles the
`<alp/power.h>` shape it needs first.

What lands now is the issue's accepted minimum: the failure moves to
configuration time, enforced once in the dispatcher rather than duplicated
per backend. `src/power_dispatch.c`'s `alp_power_configure_wake_source()`
rejects any bit outside what the active backend reported at `open()` time
via the new `alp_power_wake_capabilities()` accessor — `ALP_ERR_NOSUPPORT`,
not `ALP_OK` — before the backend's own op ever runs.

The fix closes this gap on every backend registered for the `power` class
today, and each reports ONLY what it can genuinely deliver:

- `zephyr_stub.c` reports zero armable wake bits — it can arm nothing.
- `zephyr_pm_policy.c` reports `ALP_POWER_WAKE_TIMER` ONLY. Its `_wake_sem`
  has exactly one giver in the whole file, `_timer_expiry` (armed by its own
  `k_timer` when `wake_after_ms > 0`); there is no out-of-band signaller for
  a GPIO IRQ, UART RX, or RTC-alarm-as-distinct-source. An earlier draft of
  this fix advertised RTC/GPIO/UART_RX on the theory that the caller's own
  peripheral setup would cover them — review caught that this backend never
  actually wakes on any of them, so a caller following exactly the protocol
  the header prescribes (check `alp_power_wake_capabilities()`, configure
  the advertised bit, call `request_sleep` with `wake_after_ms == 0`) would
  park on `K_FOREVER` forever: the #1812 shape, reincarnated on a second
  backend. `z_request_sleep` now also refuses `wake_after_ms == 0` outright
  with `ALP_ERR_NOSUPPORT` — belt-and-suspenders, since the dispatcher's own
  INVAL guard only rejects an *empty* bitmap paired with `wake_after_ms ==
  0`, not a non-empty one (e.g. `ALP_POWER_WAKE_TIMER` configured, but
  `wake_after_ms` still passed as `0` by mistake).
- `yocto_drv.c` reports `ALP_POWER_WAKE_RTC` ONLY — the one bit its
  `_program_wakealarm` genuinely arms. Every other bit has no matching
  sysfs knob at all, and even `ALP_POWER_WAKE_RTC` itself only arms
  anything when `wake_after_ms > 0` (the wakealarm is programmed lazily at
  `request_sleep()` time, not by the bitmap) — a caller configuring
  `ALP_POWER_WAKE_RTC` with `wake_after_ms == 0` arms nothing here and
  falls through to whatever the kernel's own already-enabled wakeup
  sources do, unrelated to this backend. **Behaviour change for
  out-of-tree callers**: before this fix EVERY bit besides `RTC` returned
  `ALP_OK` from `alp_power_configure_wake_source()` on a Yocto build and
  was silently ignored; those now return `ALP_ERR_NOSUPPORT`. A caller
  wanting a guaranteed wake on this backend must pass `wake_after_ms > 0`.

A bitmap the dispatcher rejects is now never mirrored into the handle
either, so `alp_renesas_power_supervisor_mode_set`
(`src/backends/ext/renesas/power.c`), which reads that mirror directly and
forwards it to `gd32g553_power_mode_set()`, can never receive one hardware
never agreed to arm.

The three backends also now agree on `alp_power_wake_info_t::realised_mode`
when a call fails outright: `zephyr_stub.c` and `zephyr_pm_policy.c`
(`wake_after_ms == 0`) both report `ALP_POWER_MODE_RUN`, matching
`yocto_drv.c`'s pre-existing failure-path behaviour — none of them echo
back the requested mode as if it had been realised.

`examples/aen/aen-power-smoke` now calls `alp_power_open()` /
`alp_power_wake_capabilities()` / `alp_power_configure_wake_source()` /
`alp_power_request_sleep()` (the exact repro from this issue) and logs the
result, informationally, AFTER its existing WFI/SysTick proof has already
printed its own RESULT line (a real backend's DEEP_SLEEP success would
reboot the core via the SE and skip everything after it, so the probe runs
last, not first). Its `prj.conf` gained `CONFIG_ALP_SDK=y`, without which
`<alp/power.h>` isn't even on the include path. This is now exercised by the
AEN801 board-target build gate. `tests/zephyr/peripheral/src/main.c`'s
native_sim power-mode ZTESTs (the same stub-backend path, no `CONFIG_PM`)
assert the new configuration-time contract directly, and
`tests/unit/power_registry` gained matching coverage for the pm_policy
backend: `ALP_POWER_WAKE_TIMER`-only capability, the `wake_after_ms == 0`
refusal, and a STOP-mode round-down assertion mirroring the yocto test.
