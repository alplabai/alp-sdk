### Fixed — CC3501E `SOCK_SEND` could re-transmit on a lost poll reply, timing out the host on a send that had already succeeded (#1746)

Root cause, diagnosed in `cc3501e-bridge-firmware#88`: the worker-routed
socket opcodes carried no request identity on the wire. `poll_by_repeat()`
(`chips/cc3501e/cc3501e_core.c`) re-sends the **same command with its full
payload** on every retry attempt, and the firmware's
`handle_worker_routed_payload_reply()` treats any poll that finds
`WORKER_IDLE` as a brand-new request. So once a `SOCK_SEND` completed and
`worker_reset()` freed the job slot, the host's next byte-identical poll —
issued because a single `RESP_OK` reply was lost or misframed — read as a
new request and **re-transmitted the payload**. The host, still polling,
burned its full 15 s budget and reported failure on an operation that had
already succeeded, sometimes more than once.

Fixed by giving `CMD_SOCK_SEND` retry identity, mirroring the `seq` byte
`protocol_spi.c`'s `SPI1_TRANSFER` already uses for the identical problem.
`alp_cc3501e_sock_send_t` had an existing always-zero `reserved` byte at
offset 3 — the same offset SPI1 uses — so this is a **semantic** change to
a byte already on the wire, not a layout change: the field is renamed `seq`
in `include/alp/protocol/cc3501e.h`. `cc3501e_sock_send()` assigns a new
per-context free-running `uint8_t` counter (`cc3501e_t::sock_send_seq`)
**once per logical send, before `poll_by_repeat()`**, so the value stays
constant across every retry of that one call — the constancy is what makes
the firmware able to tell a retry from a new request. On the firmware side,
`handle_sock_send()` (`src/protocol_sockets.c`) now keeps a small dedicated
`(seq, reply)` cache — 4 bytes of static RAM, not SPI1's 4 KB, since the
send reply is only a 2-byte queued-count — and serves it on a matching seq
without re-submitting to the worker; a fresh seq falls through to the
worker-routed path unchanged.

`SOCK_RECV` is **not** touched: `alp_cc3501e_sock_recv_t` is `{ handle |
max_len }` with no spare byte, so giving it the same fix is a real layout
change and out of scope here.

Wire protocol bumped v6 → v7 on both sides (`ALP_CC3501E_PROTOCOL_VERSION`,
`cc3501e-bridge-firmware`'s `protocol-version.txt` +
`CC3501E_FW_IMPLEMENTS_PROTOCOL`). The bump is semantic, not structural: an
**old** (v6) host always writes `reserved = 0`, so a **new** firmware
reading byte 3 as a seq without the version gate would see `seq == 0` on
every request from that host and could serve a stale cached reply for a
genuinely new send. The `GET_VERSION` gate in `cc3501e_reset()`
(`chips/cc3501e/cc3501e_core.c`) refuses the link outright on any mismatch,
which is what stops a v7 firmware from ever misreading a v6 host's
always-zero byte as a real retry.

**Not bench-verified.** Both sides build clean (`examples/peripheral-io/
alp-console` for `alp_e1m_aen801_m55_he/ae822fa0e5597ls0/rtss_he`; the
firmware's `ti` backend via `ti/build_ti.ps1 -Ble` and its `stub` CMake
backend) but neither has been flashed — the fix needs a paired FIB reflash
(`cc3501e-bridge-firmware` protocol v7) and host image before a bench run
can confirm the re-execute is actually gone.
