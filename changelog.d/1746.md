### Fixed — a `sock` send could report failure on a transfer the peer received in full (#1746)

Two distinct defects produced the same symptom, and both are now closed.

**1. No request identity, so a lost reply re-executed the send.** `poll_by_repeat()`
re-sends the identical frame on every poll, and the companion's
`handle_worker_routed_payload_reply()` treats a poll that finds an idle worker as a
brand-new request. Once a send completed and the slot was freed, the host's next
byte-identical poll **re-transmitted the payload**, and one lost `RESP_OK` became an
endless re-execute ending in a `-4` timeout on a send that had succeeded. Fixed by
giving `CMD_SOCK_SEND` a `seq` in the byte at offset 3 of
`alp_cc3501e_sock_send_t` — previously `reserved`, always written 0 — assigned once
per logical send so it is constant across the retry loop
(`chips/cc3501e/cc3501e_sockets.c:127` (`p[3] = ++ctx->sock_send_seq`)). Wire
protocol 6 -> 7; companion side is cc3501e-bridge-firmware#89, shipped as its
prebuilt v0.6.0.

**2. The request payload phase raced the companion's re-arm.** A request is two
SS0-framed transfers — a header declaring the length, then the payload — and the gap
between them is `CC3501E_PHASE_SETTLE_US`. `cc3501e_reply_gate()` only waits on the
READY line when it has been proven, and on the measured unit it never is: READY is
CC3501E `GPIO_17` -> Alif `P2_6`, and `P2_6` is `SPI1_SCLK_A`, so enabling its input
buffer degrades the link it would gate. That pad conflict is an Alif pad function,
not a board-revision property, so the fallback applies to any module routing READY
to `P2_6` — r1 as measured here, and R2 unless its netlist moves the line, which
has not been checked. Every phase therefore fell back to a blind
40 us, which the payload phase intermittently out-ran — the payload landed short or
shifted and the companion rejected the frame with `RESP_ERR_INVALID`, surfacing as
`send failed (-1)`. Raised to 250 us
(`chips/cc3501e/cc3501e_core.c:563` (`#define CC3501E_PHASE_SETTLE_US 250u`)).

Bench-measured on E1M-AEN801 serial `2617-0001` (board rev **r1**), protocol 7, against a bare
`accept()` listener, 10 consecutive `alp companion sock tcp-get`:

| phase settle | end-to-end successes | `send failed` |
|---|---|---|
| 40 us | 6/10 | 4/10 |
| 250 us | **10/10** | **0/10** |

**Cost, and why it matters to #1677:** that gap is paid per payload phase, so it is a
throughput tax on anything that streams (OTA_WRITE's 260 B chunks, bulk socket
sends). Any throughput figure taken before this change is not comparable. The value
is empirical, not derived — the real fix is a readable READY line, which needs a
board revision that does not put it on `SPI1_SCLK_A`.

**Measure this surface with a bare `accept()` listener, never an HTTP server.** An
HTTP server logs only a *parsed* request, so it cannot see a connection whose bytes
it never parses — which is exactly the trial that works. That instrument is what
kept this issue mis-characterised as "cannot connect to anything".
