### Fixed — Flow D's `flash-jlink*.sh` now use `$SE_UART` opportunistically for the resident-ATOC check, instead of never checking at all (#2027)

PR #2029 closed the immediate hazard from #2025 by requiring an explicit
`--atoc-unqueryable` acknowledgement before `flash-jlink.sh`,
`flash-jlink-hp.sh`, and `flash-jlink-mramxip.sh` write a replacing ATOC —
but it left the harder half unresolved: these three scripts have no
`$SE_UART` dependency by design (Flow D's whole premise is "J-Link only, no
serial device required"), so wiring `bench_atoc_replace_guard()` in
unconditionally, the way the four Flow A / dual-core / update-log scripts
already do, would have newly required a serial device on a flow that never
needed one. `changelog.d/2025.md` recorded that tradeoff as an unlinked
follow-up; this is it (refs #2025, #2026, #2029).

A new `bench_flowd_atoc_guard()` (`scripts/bench/aen/bench-env.sh:712-771`)
now fronts all three writers
(`scripts/bench/aen/flash-jlink.sh:65`
(`bench_flowd_atoc_guard "$REPLACE_ATOC" "$ATOC_UNQUERYABLE" flash-jlink ALP-HE || exit $?`),
`scripts/bench/aen/flash-jlink-hp.sh:66`
(`bench_flowd_atoc_guard "$REPLACE_ATOC" "$ATOC_UNQUERYABLE" flash-jlink-hp HP-APP || exit $?`),
`scripts/bench/aen/flash-jlink-mramxip.sh:101`
(`bench_flowd_atoc_guard "$REPLACE_ATOC" "$ATOC_UNQUERYABLE" flash-jlink-mramxip ALP-HE || exit $?`)),
placed as the first thing each script does after its own argument parsing —
before `bench_require_setools` resolves anything and well before any of the
three ever touches the J-Link probe. Its own header opens at
`scripts/bench/aen/bench-env.sh:714` (`GUARD (alp-sdk#2027)`):

- **`$SE_UART` exported and usable** — the resident ATOC genuinely IS
  queryable on this bench slot, so the guard calls the SAME
  `bench_atoc_replace_guard()` Flow A uses, at
  `scripts/bench/aen/bench-env.sh:751`
  (`bench_atoc_replace_guard "$replace_atoc" "$tag" "$@"`), never a
  second, weaker copy of its query/parse/allow-list logic. A foreign
  resident entry aborts (exit 5) exactly as it would for `flash-run.sh`,
  and a newly-accepted `--replace-atoc` flag opts out for an intentional
  replace, the same flag Flow A already has. `--atoc-unqueryable` is
  *ignored* on this path — it is the acknowledgement that no check ran, and
  one just did.
- **`$SE_UART` unset** — Flow D's normal, day-to-day case, and unchanged
  from #2029: `--atoc-unqueryable` is still required, and the script still
  aborts (exit 8) without it. The abort message now names *both* ways
  forward — export `$SE_UART` if this bench slot has one wired, or pass the
  flag — where before it named only the flag.

Neither path makes `$SE_UART` a hard requirement of Flow D: an operator on a
genuinely serial-less slot (e.g. `e1m-aen-evk-03`) sees identical behaviour
to before this change, `--atoc-unqueryable` included.

**`flash-jlink-mramxip.sh` carries one open question this change does not
resolve, and could not resolve without a bench** (see
`scripts/bench/aen/flash-jlink-mramxip.sh:66-82`
(`an open question, still UNVERIFIED ON SILICON`)): whether
`maintenance -c $SE_UART -opt gettoc`
itself resets the target. If it does, `AP[3]` (APAddr `0x00300000`) could be
gone by the time this script's own pre-programming halt runs. The guard call
sits as early as possible specifically to give any such reset the most real
time to complete its reboot first, but that is a mitigation, not a proof.
Even in the worst case the existing, already-shipped failure mode is a safe
one: the pre-programming halt gate aborts with `!! HALT FAILED before
programming` (exit 5), and nothing is written — not a silent corruption.
If that abort starts firing specifically on a bench with `$SE_UART`
exported, that is the signal this question needs answering on real silicon.

**Investigated and NOT implemented: an SWD-only resident-ATOC read** (the
third shape the issue asked to weigh, parity with `flash-jlink.sh`'s
existing SWD-only DPIDR preflight). `changelog.d/2025.md`'s own "Open
question" section already assessed this and rejected it: a debug-AP read of
this part's MRAM can return an uncommitted shadow (a `loadbin` that
`verifybin` reports as successful without ever committing to MRAM), and the
same read path has produced a flatly false "Verify successful." against
data that was never written (2026-09-05, 5/5 calls) — see also
`flash-jlink-mramxip.sh`'s own `SetSkipProgOnCRCMatch = 0` note that
"Debug-AP reads of this part are documented to lie in some states." A DPIDR
read is not comparable: it reads a fixed silicon identity register that
cannot be mid-write, not MRAM content that can. Reading the ATOC table
itself would also mean re-deriving SETOOLS' TOC binary layout from raw
bytes — undocumented in the Alif toolkit's own AUGD0005 user guide, which
documents only the `gettoc` CLI's parsed table output, not the on-MRAM
format it is parsed from — a vendor-format reimplementation nothing in this
tree currently does (`scripts/aen_atoc.py` validates the JSON handed to
`app-gen-toc`; it does not read anything back off a module). Nothing here
changes that verdict; a J-Link-only resident-ATOC read remains not
implemented, pending either a documented on-MRAM TOC format or a bench
characterization of exactly which debug-AP read states are trustworthy on
this part.

Added `bench_flowd_atoc_guard()` coverage to
`tests/scripts/test_bench_jlink_connect_guard.py`: `$SE_UART` set and the
guard refusing on a foreign entry (and confirming `--atoc-unqueryable`
cannot silence a real check); `$SE_UART` set and `--replace-atoc` opting
out; `$SE_UART` unset without the flag aborting (exit 8, naming both ways
forward); `$SE_UART` unset with the flag proceeding and printing the
one-line "proceeding WITHOUT the resident-ATOC check" statement; and that
all three writers call `bench_flowd_atoc_guard()` specifically, not a
hand-rolled copy of its decision.
