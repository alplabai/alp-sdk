### Fixed — `isp_pico.c`: dequeued YUV420/NV12 buffers reported `bytesused` 0 (pitch tracked luma only) (#2259)

Silicon-proven on E1M-AEN803 (bench run 200). `zephyr/drivers/video/isp_pico.c`'s
`isp_dequeue()` sized every dequeued buffer as `channel->output_fmt.pitch *
channel->output_fmt.height`, and `src/backends/camera/alif_isp_pico.c`
negotiates the output format with `pitch = 0`. For a pass-through YUV
request (`ALP_PIXFMT_YUV420_PLANAR` / `ALP_PIXFMT_NV12` through
`<alp/camera.h>`), every dequeued buffer therefore reported `bytesused = 0`,
so the backend returned `out->size = 0` and callers copied nothing and saw
stale memory. The RGB565 path hid this because the backend converts using
`width*height`, not `bytesused`; the post-dequeue cache invalidate (guarded
by `CONFIG_DCACHE=y`) also keyed off `bytesused`, so it invalidated 0 bytes
too.

`isp_set_fmt()` now derives an unset (`pitch == 0`) output pitch itself: for
4:2:0 planar/semi-planar YUV (`YUV420`/`YVU420`/`NV12`/`NV21`) that's the
luma-only line stride (one byte per pixel), never
`video_bits_per_pixel()`'s chroma-subsampled average (12 bpp, i.e.
`width*1.5`, not a whole number of bytes/pixel). `isp_dequeue()` now sizes
`bytesused` off `video_bits_per_pixel(pixelformat) * width * height / 8`
directly instead of `pitch * height` -- the full frame size, chroma planes
included, for every output fourcc this driver negotiates. The backend's own
buffer-pool sizing (`alif_isp_pico.c`'s `bytes_per_buf`) had the same
`pitch * height` bug once a non-zero luma-only pitch reached it (it would
have under-allocated 4:2:0 planar buffers by a third); both now share
`alp_isp_frame_size()` (`src/backends/camera/isp_frame_size.h`), unit-tested
under `tests/unit/isp_frame_size/` on `native_sim`.
