### Fixed — `isp_pico.c`: dequeued YUV420/NV12 buffers reported `bytesused` 0 (pitch tracked luma only) (#2259)

Silicon-proven on E1M-AEN803 (bench run 200). `zephyr/drivers/video/isp_pico.c`'s
`isp_dequeue()` sized every dequeued buffer as `channel->output_fmt.pitch *
channel->output_fmt.height`, and `src/backends/camera/alif_isp_pico.c`
negotiates the output format with `pitch = 0`. For a pass-through YUV
request (`ALP_PIXFMT_YUV420_PLANAR` / `ALP_PIXFMT_NV12` through
`<alp/camera.h>`), every dequeued buffer therefore reported `bytesused = 0`,
so the backend returned `out->size = 0` and callers copied nothing and saw
stale memory. The RGB565 path hid this because the backend converts using
`width*height`, not `bytesused`; the post-dequeue cache invalidate (guarded
by `CONFIG_DCACHE=y`) also keyed off `bytesused`, so it invalidated 0 bytes
too.

Both `isp_set_fmt()`'s pitch fill-in and `isp_dequeue()`'s `bytesused` now
route through a new shared header,
`zephyr/include/zephyr/drivers/video/isp_frame_size.h` -- the same header
`alif_isp_pico.c`'s buffer-pool sizing includes, so all three call sites
share one implementation instead of three independently-driftable copies:

- `alp_isp_default_pitch()` fills an unset (`pitch == 0`) output pitch: for
  planar/semi-planar YUV (`YUV420`/`YVU420`/`NV12`/`NV21`/`NV16`/`NV61`/
  `NV24`/`NV42`) that's the luma-only line stride (one byte per pixel),
  never `video_bits_per_pixel()`'s chroma-subsampled average (12 bpp for
  4:2:0, i.e. `width*1.5`, not a whole number of bytes/pixel); every other
  fourcc uses `bpp * width / 8`. `isp_set_fmt()` now returns `-EINVAL` if
  this comes back 0 (an output fourcc neither this function nor
  `video_bits_per_pixel()` can size) instead of silently latching a
  zero pitch. The driver's own RGB888-planar-private default-output-format
  path (`isp_get_fmt()`, hit when no output format has been negotiated yet)
  had the same zero-pitch bug and now goes through the same helper.
- `alp_isp_frame_size()` sizes `bytesused` (and `alif_isp_pico.c`'s
  buffer-pool allocation) off the format's true average bits/pixel,
  chroma included -- `width*height*bpp/8` -- never `pitch * height`, which
  after the pitch fix would size a planar buffer for the luma plane alone.
  `isp_dequeue()`'s `bytesused` is additionally capped at the buffer's own
  `size`, so a mis-sized buffer can't make the following
  `sys_cache_data_invd_range()` invalidate past its end.
- `alp_isp_pixel_bpp()` extends `video_bits_per_pixel()`, which returns 0
  for the two Alp Lab-private fourccs `VIDEO_PIX_FMT_YUV422P` and
  `VIDEO_PIX_FMT_RGB888_PLANAR_PRIVATE` (`isp_pico.c`'s own default output
  format) -- sized the way `fourcc_to_plane_size()`
  (`zephyr/drivers/video/video_alif.c`) splits their planes: `YUV422P` at
  16 bpp (1/2 + 1/4 + 1/4), `RGB888_PLANAR_PRIVATE` at 24 bpp (three equal
  1/3 planes). Both were 0-pitch/0-`bytesused` before this fix too.

Unit-tested under `tests/unit/isp_frame_size/` on `native_sim` -- the test
includes the exact header the driver and backend call, not a stand-in copy,
covering all three helpers (`alp_isp_default_pitch()`,
`alp_isp_frame_size()`, the `YUV420`/`NV12`/`RGB565`/`YUV422P`/
`RGB888_PLANAR_PRIVATE` cases).

Also fixed in passing: `supported_output_fmts[]`'s `YUV422P` entry advertised
a `width_max` of `19200` (a typo -- every other entry in that table is
`1920`), and `examples/aen/aen-isp-ov5647-capture/src/main.c` set
`.pitch = FRAME_WIDTH*3/2` for its `YUV420` output format, which was never
the luma stride this driver now expects -- both corrected to `1920` /
`FRAME_WIDTH`.
