### Fixed — the storage-partition planner offered `flash_device: ospi0`/`ospi1` on SKUs whose preset declares that part not fitted (#2311)

`_known_flash_devices()` (`scripts/alp_orchestrate/partition.py:132`
("def _known_flash_devices(")) still advertised an `on_module.ospi_memories:`
key as a legal `storage[].flash_device:` target even when the SoM preset
marks it `assembled: false`, and `_resolve_flash_device()`
(`scripts/alp_orchestrate/partition.py:480` ("def _resolve_flash_device"))
resolved it to a live descriptor from `capacity_mbit` alone — on `E1M-AEN801`, whose
preset declares `ospi0`/`ospi1` unfitted, a `storage:` entry naming `ospi0`
silently planned a 32 MiB partition on silicon that carries no such part.

Both are fixed: `_known_flash_devices()` excludes an `assembled: false` key
from the advertised set, and `_resolve_flash_device()` refuses it directly
(defense in depth for a hand-built project bypassing the loader's cross-check),
naming the SKU, the device, and the declaring preset file. `assembled:
optional` and an absent key (schema default: `true`) are unaffected.

The same bug class hit `security.psa.its_storage` / `ps_storage`: the
loader's cross-field check (`scripts/alp_orchestrate/loader.py`) accepted
any `on_module.ospi_memories:` key as a valid PSA backing-store reference
without checking `assembled`, so `its_storage: ospi0` was accepted on
`E1M-AEN801` and `secure.py` emitted
`CONFIG_PSA_CRYPTO_ITS_BACKING_STORE="ospi0"` for a part the SKU doesn't
carry. The loader now shares the same `assembled: false` predicate
(`_is_ospi_key_unassembled()`, `scripts/alp_orchestrate/partition.py`) and
raises the specific "not assembled" reason for `its_storage`/`ps_storage`
naming an unfitted OSPI part, instead of the generic "does not resolve"
message. `examples/connectivity/production-deployment/board.yaml` (which
named `ps_storage: ospi0` on E1M-AEN801) is updated to use `mram_main`,
the SKU's real backing store.
