### Fixed — CC3501E power presets never configured the radio (#1679)

`CMD_POWER_POLICY` (0x62), its four presets and the host driver have existed for a
while, and the MCU core half was a real implementation. But nothing in
`firmware/cc3501e/` ever called `Wlan_Set()`, so the Wi-Fi radio stayed fully awake
under every preset — DEEP_SLEEP included. On a Wi-Fi part that is the dominant
term: an associated station that never enters power save keeps its receiver up
continuously, which costs far more than any core idle state saves. In practice the
four presets differed only in core state, which is why the code documented
LOW_POWER and DEEP_SLEEP as sharing one reachable state.

The presets now drive the radio too, via the three knobs `wlan_if.h` exposes:
`WLAN_SET_POWER_SAVE` (active / auto / power-save), `WLAN_SET_POWER_MANAGEMENT`
(always-active / ELP) and `WLAN_SET_LSI` (wake every DTIM vs every Nth DTIM).
LSI is what makes LOW_POWER and DEEP_SLEEP genuinely different, and it gives
`idle_ms_before_sleep` a meaning — that field was previously accepted and discarded
because the vendor Power driver exposes no idle-hysteresis setter.

`Wlan_Set()` is rejected while the radio is down, so the policy is latched and
re-applied once `Wlan_RoleUp(STA)` succeeds; without that, a policy set before
Wi-Fi came up was silently dropped.

**Trade-off.** Waking only every Nth DTIM queues inbound frames at the AP until the
next wake, so DEEP_SLEEP adds hundreds of ms of inbound latency and will cut bulk
throughput hard. That is the preset working as intended, and it is why BALANCED
remains the default.

Also corrects the public header, which described DEEP_SLEEP as "radios off;
wake-on-host only". That was never what the firmware did and still is not — the
station stays associated in every preset.

The radio half runs on the firmware's task, not in the SPI-dispatch ISR the
handler is called from: `Wlan_Set()` is a blocking vendor radio call, and running
it inline failed every preset AND wedged the bridge on silicon (`POWER_POLICY ->
-4`, then `PING -> -5`). A `RESP_OK` to POWER_POLICY therefore means QUEUED, not
APPLIED — the same semantic `OTA_BEGIN` turned out to have.

Because of that, the reply now carries one data byte reporting whether the
PREVIOUS radio apply was realised, and `cc3501e_power_policy()` takes an optional
`bool *radio_ok_out`. Without it a host cannot distinguish an accepted-and-applied
policy from an accepted-and-silently-rejected one — which is exactly how a broken
radio apply went unnoticed on the bench until the return value was checked.

Bench-verified on e1m-aen-evk-01: all four presets report `radio_ok=1` and the
bridge survives each (`PING -> 0`). Bulk throughput under DEEP_SLEEP tracks the
default (798000 vs 799383 B/s), which is correct — 802.11 power save keeps the
station awake while downlink traffic flows and sleeps in the idle gaps, so the
saving is in idle current, not a throughput cut.

**Not measured:** this bench has no way to meter CC3501E current (the only
instrument is a carrier-wide 15 V rail at 1 mA resolution), so no power figure is
claimed. **One unexplained observation:** a single early run showed DEEP_SLEEP
throughput collapse to 617 B/s, and one later run had the DEEP_SLEEP policy call
itself return non-OK. Neither reproduced across the following runs. Recorded here
rather than omitted.

### Added — `cc3501e_power_off()` for long-idle duty cycles (#1679)

The presets are for short gaps. For a node that uplinks once an hour or once a
day, what matters is that the companion draws essentially nothing in between —
`WIFI_EN` gates VPA (3.3 V) through the board's load switch, so cutting it removes
the radio's power rather than idling it, far below anything `PowerWFF3_SLEEP`
reaches.

This deliberately is not a fifth preset: `CMD_POWER_POLICY` travels over the very
link the action kills, so it is a host-side GPIO action alongside
`cc3501e_reset()`. It is **explicit only** — nothing in the driver powers the
device down on its own, because only the application knows when the next uplink is
due and whether anything is in flight.

While off, calls fail `ALP_ERR_NOT_READY` immediately instead of clocking frames
at an unpowered slave. `cc3501e_reset()` is the wake; all device state (the
association, the BLE host, open sockets) is lost with the cold boot. Never call it
with an OTA in flight — it destroys the partially staged image.

Fixing this exposed three recovery defects, one of them long-standing:
`cc3501e_reset()` and `cc3501e_hard_reset()` gated on `initialised`, which made a
downed context unrecoverable; nothing re-armed that flag; and the re-arm has to
happen **before** the `GET_VERSION` compat gate, because that gate reads through
`cc3501e_get_version()`, which itself refuses on a downed context. The last one
also silently bricked any context downed by a version mismatch — there was no way
back through the API.

### Fixed — power presets could wedge the bridge when BLE was enabled (#1683)

Wi-Fi and BLE share the CC3501E's HIF, and `DEEP_SLEEP`'s `WAKE_UP_EVENT_N_DTIM`
long sleep interval starved BLE with it: with BLE advertising, the bridge could
stop answering (`PING -> -5`) and stay that way until a reset.

The long sleep interval is now withheld while BLE is enabled — `DEEP_SLEEP` keeps
`POWER_SAVE_MODE` + ELP but falls back to waking every DTIM, which is
`LOW_POWER`'s radio behaviour. Wi-Fi-only builds keep the full interval.

Two other real defects were found and fixed while isolating this, neither of them
the trigger: both halves of the policy ran in the SPI-dispatch ISR, and the core
half swapped the Power policy function pointer at runtime, racing the idle loop.
The presets now select behaviour purely through Power constraints, which
`PowerWFF3_sleepPolicy` is documented to read, so there is no swap to race.

Bench-measured with BLE advertising between presets, three consecutive runs: the
bridge never wedged (`PING -> 0` throughout). **Not a clean sweep** — one run still
lost a single BLE advertising call with the bridge alive, so a residual
intermittent BLE-op timeout under power presets remains and #1683 stays open for
it. What is fixed is the unrecoverable wedge.
