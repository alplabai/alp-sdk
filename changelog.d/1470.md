### Added — per-NPU op-support metadata, regenerated as ground truth, keyed by support-table identity (ADR-0028)

Replaces the hand-guessed seed (`metadata/npu_ops/{ethos_u,drpai,deepx_dxm1}.json`,
`"version": "2026.08-seed"`, written from general knowledge) with data
produced by running the real toolchains, or transcribed from a cited vendor
manual -- never hand-transcribed from memory. The flat one-file-per-backend
layout is also wrong: a backend can publish more than one distinct table, so
the new shape keys on **support-table identity**, one file per
`metadata/npu_ops/<backend_family>/<variant>@<toolchain>-<toolchain_version>.json`.

- **`ethos_u/u85@vela-5.1.0.json`** (70 ops) and
  **`ethos_u/u55-u65@vela-5.1.0.json`** (53 ops) are parsed programmatically
  from `vela --supported-ops-report` (`ethos-u-vela` 5.1.0's own
  `SUPPORTED_OPS.md`, column 1 of the "Ethos-U85 TFLite Summary Table" and
  the "Ethos-U55 and Ethos-U65 TFLite Summary Table"; the TOSA tables in the
  same report are out of scope -- the alp-sdk adapter accepts only
  `src_format == "tflite"`). Vela publishes exactly these two TFLite tables
  and both are invariant to `--accelerator-config`: regenerating at
  `ethos-u55-32`, `ethos-u55-256`, `ethos-u65-512`, `ethos-u85-128` and
  `ethos-u85-2048` all reproduce the identical `SUPPORTED_OPS.md` (md5
  `93f186ba8653467e46751765d151c3bd`), which is why table identity, not
  silicon-SKU identity, is the file's key. U55/U65 is asserted a strict
  subset of U85, with the delta pinned to exactly 17 ops (`CAST`, `DIV`,
  `EQUAL`, `GATHER`, `GREATER`, `GREATER_EQUAL`, `LESS`, `LESS_EQUAL`,
  `LOGICAL_AND`, `LOGICAL_NOT`, `LOGICAL_OR`, `NOT_EQUAL`, `REDUCE_ALL`,
  `REDUCE_ANY`, `SCATTER_ND`, `SELECT`, `SELECT_V2`); the new
  `scripts/gen_npu_ops.py` re-derives both files from a live `vela` and
  refuses to write anything if a future vela release disagrees with that
  delta.
- **`drpai/onnx-i8@translator-1.12.json`** (47 ops) is hand-transcribed from
  the DRP-AI Translator i8 vendor manual (doc R20UT5336EJ0112 Rev.1.12,
  §4.1.1 "ONNX Operators", table "Supported ONNX Operator List") --
  `authority: vendor-manual`, since the Translator publishes no machine
  report for `scripts/gen_npu_ops.py` to reproduce. A prior extraction pass
  over the same table found only 45 ops, silently dropping `Gather` and
  `Squeeze`; this pass extracts the table programmatically and gets 47, both
  present. One correction against the literal PDF text: the vendor table's
  own entry #38 is spelled "Sofplus" (a documented typo missing the 't');
  it is recorded here as the correct ONNX operator name `Softplus`, which is
  also how the same manual spells it in its own §4.1.2 detail section --
  the vendor's own document is the source for the correction, not an
  assumption.
- **No `deepx` table ships, and that is deliberate, not an omission.** dxcom
  2.3.0 publishes no op-support report of any kind; the only evidence
  available is 15 ONNX ops observed present in a `yolo11n.onnx` it
  demonstrably compiled, which is a lower bound on support, not a support
  table. Shipping a guessed table would mass-produce false "no-fit" verdicts
  on V2M, the SKU where DEEPX is the headline feature. A consuming engine
  (tan's model-fit analyzer, per ADR-0028) MUST treat a backend with no
  table under `metadata/npu_ops/` as `undetermined`, never as "zero ops
  known -> cpu-fallback" -- `test_no_deepx_table_exists` pins the absence so
  it cannot be silently "fixed" back in.

Every file now also carries `applies_to` (the product/toolchain/
toolchain_version it governs, matched mechanically against its own
filename), `authority` (`tool-generated` | `vendor-manual`), `stance`
(currently always `screening`: this data filters candidate ops, it never
certifies that a present op will actually compile), and `provenance` (the
exact reproducing command or the cited doc section, the tool version, and a
content hash of the regenerated report / cited PDF so upstream drift is
detectable without redistributing vendor content).
`metadata/schemas/npu-ops-v1.schema.json` is rewritten for the nested shape
and its `$id` moves to the `github.com/alplabai/alp-sdk` convention the
other 24 sibling schemas already use.

`scripts/validate_metadata.py`'s `_check_npu_ops_semantics` is rewritten to
cross-check, per file: `applies_to` reproduces the file's own path,
`op_namespace` matches its backend-family directory's compiler ingest
format, every `supported_ops` entry is spelled in the vocabulary
`op_namespace` declares (TFLite UPPER_SNAKE vs. ONNX CamelCase/all-caps
acronym, discriminated on the presence of an underscore -- not
`op == op.upper()`, which would false-flag real ONNX acronyms like `LRN`,
`GRU`, `LSTM`), and a `tool-generated` table carries the `_generated`
DO-NOT-EDIT banner while a `vendor-manual` one carries none (there is
nothing to regenerate it from). `tests/scripts/test_npu_ops_metadata.py` is
rewritten to match: every directory-wide check is parametrized over a
recursive glob of `metadata/npu_ops/**/*.json` (not `*/*.json`, which
silently sees nothing if a file is ever reintroduced flat, directly under
`metadata/npu_ops/`), not a hard-coded per-backend list, so a table added
later inherits every check automatically; plus the dedicated
U55/U65-subset-of-U85 invariant and the explicit "no deepx table" test
above. `scripts/test-all.sh`'s `stage_generated_files` now also runs
`gen_npu_ops.py --check`, skipping cleanly (not failing the gate) on a host
without `vela` on PATH, so table staleness has automated coverage wherever
`vela` happens to be installed instead of resting on a human alone.

Nothing consumes this data yet (unchanged from the original landing): it
lands standalone ahead of the `tan.model.analyze` static-fit estimator that
will read it.

### Added — every Ethos-U SoC publishes its Vela memory profile (`npu_toolchain.vela`)

Invoked with neither `--system-config` nor `--memory-mode`, `ethos-u-vela`
5.1.0 picks a default profile per accelerator, and **the failure mode differs
by accelerator** — the U85/U65 one is not the U55 one. Every figure below is
KiB, measured on `ethos-u-vela 5.1.0` against
`tests/fixtures/models/tiny_int8.tflite` (712 B, md5
`07290259e28e1467fa184ef01b71e40a`):

| `--accelerator-config` | flagless `system_config` / `memory_mode` | `sram` | `dram` | `on_chip_flash` | `off_chip_flash` |
|---|---|---|---|---|---|
| `ethos-u85-256` | `Ethos_U85_SYS_DRAM_Mid` / `Dedicated_Sram_384KB` | `0.0` | `0.265625` | `0.0` | `0.0` |
| `ethos-u65-256` | `Ethos_U65_Client_Server` / `Dedicated_Sram_384KB` | `0.0` | `0.109375` | `0.0` | `0.0` |
| `ethos-u55-256` | `Ethos_U55_High_End_Embedded` / `Shared_Sram` | `0.03125` | `0.0` | `0.0` | `0.078125` |
| `ethos-u55-128` | `Ethos_U55_High_End_Embedded` / `Shared_Sram` | `0.03125` | `0.0` | `0.0` | `0.078125` |

…and with the `memory_mode` this block declares:

| `--accelerator-config` | declared `memory_mode` | `sram` | `dram` | `on_chip_flash` | `off_chip_flash` |
|---|---|---|---|---|---|
| `ethos-u85-256` | `Sram_Only` | `0.03125` | `0.0` | `0.234375` | `0.0` |
| `ethos-u55-256` | `Sram_Only` | `0.03125` | `0.0` | `0.078125` | `0.0` |
| `ethos-u55-128` | `Sram_Only` | `0.03125` | `0.0` | `0.078125` | `0.0` |
| `ethos-u65-256` | `Shared_Sram` | `0.03125` | `0.078125` | `0.0` | `0.0` |

**On the U85 and U65 parts** (`e4`/`e6`/`e8` carry a U85; `imx93` a U65) the
flagless default is DRAM-backed and reports `sram_memory_used = 0.0`. On the
Alif parts that number is a fiction twice over:
`metadata/socs/alif/ensemble/e8.json`'s `external_memory_interfaces` lists
only `HexSPI` and `SD/eMMC` — **there is no DRAM on the part** — and a zero
SRAM figure satisfies the on-device fit gate
(`src/backends/inference/alp_model_select.c`: `return e->arena_sram_kib == 0u
|| t->req_sram_kib <= e->arena_sram_kib;`) against ANY arena.

**On the U55-only parts** (`e3`/`e5`/`e7`, and the U55s that sit alongside the
U85 on `e4`/`e6`/`e8`) that is NOT what happens: vela defaults to
`Ethos_U55_High_End_Embedded` / `Shared_Sram`, never touches DRAM, and already
reports a non-zero `sram_memory_used`. The U55 hazard is a different one and
still real — the weights land in `off_chip_flash_memory_used = 0.078125`, i.e.
the OSPI0 NOR, the part every AEN preset declares `assembled: false` and does
not carry (see the `#915` fragment). Declaring `Sram_Only` moves exactly that
`0.078125` into `on_chip_flash_memory_used`, which on an AEN SKU is the on-die
MRAM the weights actually live in.

An earlier draft of this entry credited `tiny_int8.tflite` with
`dram_memory_used = 5.359375` at `ethos-u85-256`. That figure is real but
belongs to a different fixture — it is `keyword_scrambled_8bit.tflite`
(29632 B, md5 `4e22b1bbb5f1a0eea728ec15d481ff7e`) at the same config,
re-measured here to confirm the mis-attribution rather than guess at it.
`tiny_int8.tflite` is `0.265625`.

The profile is a silicon fact derivable from the SKU, so it lands next to the
`npus[]` array that already says which accelerator is on the die — **not** in a
customer's `board.yaml`, whose `models[].compile` is scoped by
`metadata/schemas/board.schema.json` to config *"the SDK cannot derive"*.

| SoC spec | `memory_mode` | Needs a vendor config? |
|---|---|---|
| `alif/ensemble/e3.json` … `e8.json` | `Sram_Only` | yes — `ensemble_vela.ini` |
| `nxp/imx9/imx93.json` | `Shared_Sram` | no |

Every declared `memory_mode` is a section Arm's own `vela.ini` ships, so the
flag works for a customer with no license. Sourced from
`examples/aen/aen-npu-inference-alp/CMakeLists.txt:42-43` (U85),
`examples/aen/aen-npu-inference-alp-u55/CMakeLists.txt:39-40` (U55) and
`vendors/nxp-imx93/README.md:103-108` (U65) — never invented.

**The U65 citation is weaker than the other two, and now says so.** The two
Alif citations point at build files that pass the flag to a real toolchain;
the U65 one points at `vendors/nxp-imx93/README.md`, an **alp-sdk-authored**
page. So `test_every_vela_profile_cites_a_source_that_states_its_memory_mode`
proves alp-sdk agrees with itself on that row — internal consistency, not
vendor grounding. The README does not derive `Shared_Sram` from any named NXP
or eIQ document (its only vendor citation is `AN14413.pdf`, for the PCA9451A
PMIC), so rather than invent a reference the cited section now carries a
provenance note stating plainly that the mode is alp-sdk's own default, what
it was chosen against (measured: the flagless `Ethos_U65_Client_Server` /
`Dedicated_Sram_384KB` reports `sram_memory_used = 0.0`), and that grounding
it in an NXP primary document is open work.

**No Alif part declares a `system_config`, deliberately.** A Vela
`System_Config` section describes ONE accelerator's memory view — on Alif, one
CORE SUBSYSTEM's: the E8's U85 wants `Ethos_U85_SRAM_Only` while its
M55-HE-paired U55 wants `RTSS_HE_SRAM_Only` (*"the Alif ensemble_vela.ini has
no Ethos_U55-specific section; the per-core RTSS_HE config describes the U55's
memory: axi0_port=Sram"*). Every Alif Ensemble part carries two or three
distinct Ethos-U accelerators, so one scalar would be right for one and wrong
for the others. `system_config_requires_vendor_config: true` plus
`vendor_config_filename: "ensemble_vela.ini"` states what is actually known;
a per-accelerator mapping belongs in the slice that has a consumer for it.
Neither name is an Arm built-in, which is why passing one without `--config`
is a hard vela rc=1 (`Section System_Config.Ethos_U85_SRAM_Only not found in
Vela config file`), not a degradation —
`examples/aen/aen-npu-inference-alif/CMakeLists.txt:85-89` already states the
rule in the repo's own words.

**Which makes `vendor_config_filename` informational today, and the schema now
says so.** Both the schema's `if`/`then` and `_check_soc_vela_memory_profile`'s
rule (4) permit `system_config_requires_vendor_config: true` +
`vendor_config_filename: "ensemble_vela.ini"` with no `system_config` — which
is exactly what the six Alif specs declare — but there is no legal vela command
line for that combination. Measured on ethos-u-vela 5.1.0, `--config <ini>
--memory-mode Sram_Only` with no `--system-config` is rc=1, verbatim: `Error:
Incorrect argument to CLI option --config=[...]: Specifying a configuration
file is not allowed when using a default system configuration`. Requiring a
`system_config` alongside the flag would force the per-accelerator guess the
paragraph above deliberately refuses, so the field's `description:` is where
this lands instead: the filename tells a customer which file to obtain, and is
not yet a `--config` a consumer can emit.

`scripts/validate_metadata.py`'s new `_check_soc_vela_memory_profile`
cross-checks the block against the rest of the same spec, which JSON Schema
cannot reach: the block is required on every SoC declaring an `ethos-u*` NPU
and forbidden on every SoC that does not; a `Dedicated_Sram*` mode (vela's own
default on the U85/U65 parts is one) is rejected on a SoC whose
`external_memory_interfaces`
declares no DRAM; a scalar `system_config` is rejected on a multi-accelerator
die and, when outside Arm's built-in set, must carry both the
`requires_vendor_config` flag and the filename; and every `source` citation is
read back — per citation, never over their union — and must literally contain
the `memory_mode` it claims to prove, so a citation that drifts fails instead
of outliving the fact. `tests/scripts/test_vela_profile_metadata.py` pins the
same invariants independently. Both were mutation-proved: 12 mutations
(dropped mode, non-built-in mode, vela's DRAM-backed default on the DRAM-less
E8, an unflagged vendor `system_config`, a scalar `system_config` on the
3-accelerator E8, a first/second/out-of-range citation drift, a missing
vendor filename, an absolute path as the filename, a stray profile on the
DRP-AI-only RZ/V2N) each turn both gates red.

`metadata/catalog.json` is unaffected (regenerated, byte-identical).
