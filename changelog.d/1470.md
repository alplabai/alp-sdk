### Added — per-NPU op-support metadata, regenerated as ground truth, keyed by support-table identity (ADR-0028)

Replaces the hand-guessed seed (`metadata/npu_ops/{ethos_u,drpai,deepx_dxm1}.json`,
`"version": "2026.08-seed"`, written from general knowledge) with data
produced by running the real toolchains, or transcribed from a cited vendor
manual -- never hand-transcribed from memory. The flat one-file-per-backend
layout is also wrong: a backend can publish more than one distinct table, so
the new shape keys on **support-table identity**, one file per
`metadata/npu_ops/<backend_family>/<variant>@<toolchain>-<toolchain_version>.json`.

- **`ethos_u/u85@vela-5.1.0.json`** (70 ops) and
  **`ethos_u/u55-u65@vela-5.1.0.json`** (53 ops) are parsed programmatically
  from `vela --supported-ops-report` (`ethos-u-vela` 5.1.0's own
  `SUPPORTED_OPS.md`, column 1 of the "Ethos-U85 TFLite Summary Table" and
  the "Ethos-U55 and Ethos-U65 TFLite Summary Table"; the TOSA tables in the
  same report are out of scope -- the alp-sdk adapter accepts only
  `src_format == "tflite"`). Vela publishes exactly these two TFLite tables
  and both are invariant to `--accelerator-config`: regenerating at
  `ethos-u55-32`, `ethos-u55-256`, `ethos-u65-512`, `ethos-u85-128` and
  `ethos-u85-2048` all reproduce the identical `SUPPORTED_OPS.md` (md5
  `93f186ba8653467e46751765d151c3bd`), which is why table identity, not
  silicon-SKU identity, is the file's key. U55/U65 is asserted a strict
  subset of U85, with the delta pinned to exactly 17 ops (`CAST`, `DIV`,
  `EQUAL`, `GATHER`, `GREATER`, `GREATER_EQUAL`, `LESS`, `LESS_EQUAL`,
  `LOGICAL_AND`, `LOGICAL_NOT`, `LOGICAL_OR`, `NOT_EQUAL`, `REDUCE_ALL`,
  `REDUCE_ANY`, `SCATTER_ND`, `SELECT`, `SELECT_V2`); the new
  `scripts/gen_npu_ops.py` re-derives both files from a live `vela` and
  refuses to write anything if a future vela release disagrees with that
  delta.
- **`drpai/onnx-i8@translator-1.12.json`** (47 ops) is hand-transcribed from
  the DRP-AI Translator i8 vendor manual (doc R20UT5336EJ0112 Rev.1.12,
  §4.1.1 "ONNX Operators", table "Supported ONNX Operator List") --
  `authority: vendor-manual`, since the Translator publishes no machine
  report for `scripts/gen_npu_ops.py` to reproduce. A prior extraction pass
  over the same table found only 45 ops, silently dropping `Gather` and
  `Squeeze`; this pass extracts the table programmatically and gets 47, both
  present. One correction against the literal PDF text: the vendor table's
  own entry #38 is spelled "Sofplus" (a documented typo missing the 't');
  it is recorded here as the correct ONNX operator name `Softplus`, which is
  also how the same manual spells it in its own §4.1.2 detail section --
  the vendor's own document is the source for the correction, not an
  assumption.
- **No `deepx` table ships, and that is deliberate, not an omission.** dxcom
  2.3.0 publishes no op-support report of any kind; the only evidence
  available is 15 ONNX ops observed present in a `yolo11n.onnx` it
  demonstrably compiled, which is a lower bound on support, not a support
  table. Shipping a guessed table would mass-produce false "no-fit" verdicts
  on V2M, the SKU where DEEPX is the headline feature. A consuming engine
  (tan's model-fit analyzer, per ADR-0028) MUST treat a backend with no
  table under `metadata/npu_ops/` as `undetermined`, never as "zero ops
  known -> cpu-fallback" -- `test_no_deepx_table_exists` pins the absence so
  it cannot be silently "fixed" back in.

Every file now also carries `applies_to` (the product/toolchain/
toolchain_version it governs, matched mechanically against its own
filename), `authority` (`tool-generated` | `vendor-manual`), `stance`
(currently always `screening`: this data filters candidate ops, it never
certifies that a present op will actually compile), and `provenance` (the
exact reproducing command or the cited doc section, the tool version, and a
content hash of the regenerated report / cited PDF so upstream drift is
detectable without redistributing vendor content).
`metadata/schemas/npu-ops-v1.schema.json` is rewritten for the nested shape
and its `$id` moves to the `github.com/alplabai/alp-sdk` convention the
other 24 sibling schemas already use.

`scripts/validate_metadata.py`'s `_check_npu_ops_semantics` is rewritten to
cross-check, per file: `applies_to` reproduces the file's own path,
`op_namespace` matches its backend-family directory's compiler ingest
format, and a `tool-generated` table carries the `_generated`
DO-NOT-EDIT banner while a `vendor-manual` one carries none (there is
nothing to regenerate it from). `tests/scripts/test_npu_ops_metadata.py` is
rewritten to match: every directory-wide check is parametrized over a glob
of `metadata/npu_ops/*/*.json`, not a hard-coded per-backend list, so a
table added later inherits every check automatically; plus the dedicated
U55/U65-subset-of-U85 invariant and the explicit "no deepx table" test
above.

Nothing consumes this data yet (unchanged from the original landing): it
lands standalone ahead of the `tan.model.analyze` static-fit estimator that
will read it.
